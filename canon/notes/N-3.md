## 并发发现的问题

真实的并发运行找出了单元测试没覆盖到的问题：

- 已修：多个进程第一次同时打开协调数据库时，切换到 WAL 模式会立即报“数据库被锁”（8 个同时 start，10 次里失败 2 次；C-99）。后台命令的“最近一批”按事件编号取，排在后面的合入可能先写（#28，C-105）。#17 的修复里又被代码评审连续找出两个漏洞（#30、#31，C-108、C-109）。
- 未修：#29，一个已被判定放弃的排队条目，进程恢复后还能再拿到轮次，可能两个合入同时进行。#27，git 设置了 `branch.autoSetupMerge=always` 时，并发 start 仍会抢 `.git/config` 的锁。
- 流程问题：
  1. `--finish` 在排队之前就提交了“关闭变更”，合入被拒、之后又没人再合入时，变更会停在 done，实际没进 main。
  2. 冲突要等轮到自己才发现（C-55 排了 409 秒才知道有冲突）；同文件提示只在双方都已提交后出现，开工时看不到。
  3. 规则评审每次都对刚改的规则提出新的措辞建议，子 agent 为此开了 C-106、C-107 两个跟进变更，后来主动停手。这正是 C-40 要解决的问题。
  4. 负载 8 到 12 时测试不稳：一个连续启动 26 个进程的测试超时（已改），一次把 5 个测试文件放进一个 `bun test` 卡了 10 分钟以上。floor 可能因此误拒。
  5. `canon work clean` 不能只清自己的 worktree，会顺带清掉别人已合入的；这次没丢东西，但和“只清自己的”这个要求不一致。

## 结论

- 多 agent 并发在 canon 上是可行的，质量守住了：没有丢工作，main 一直是好的，冲突按流程解决，代码评审在 42 分钟里提了 5 个 issue，其中 4 个是真问题并已修好。
- 瓶颈是串行的 floor。每次合入约 2.5 分钟，一小时最多合入约 24 次。5 个 agent 加上它们的跟进变更，就能把队列一直占满。再增加 agent 的数量，不会让合入变快，只会让排队更长。
- 适合并发的是互相独立、规模中等的任务；改同一个文件的任务会在合入时冲突，可以做但要准备返工。每个小的跟进变更都要再排一次队，所以评审建议这类小改动不适合单独开变更。
- 下一步要改的，按价值排序：修 #29；合入成功后才把变更标成 done；排队时先试一次 rebase，提前发现冲突，开工时也提示别人还没提交的同文件改动；落实 C-40；提高测试在高负载下的稳定性；`canon work clean` 支持只清指定的变更。缩短 floor 的办法（只跑受影响的测试，或者像合并队列那样把几个变更放在一起测）需要另外设计。
