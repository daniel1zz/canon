## 怎么做的

2026-11-03，9 个只读的子 agent 各核对一组子领域（按代码量分组，分两轮），覆盖几乎所有生效规则。方法：先读规则和例子、写下代码在每个边界该怎么做，再读代码和测试。这样做是因为 lore 发现评审和作者读同一份文字时，会连过期的内容一起放过（KN-287）。第一轮中途改为只报告、不提 issue，由主 agent 去重和核实后统一提交；第一轮有两组在改之前已经提了 7 个。

## 结论

- 结构上的对应（代码目录和规则领域一一对应、每条规则都有测试点名）是好的，但“规则说的和代码做的一致”只是大体成立：平均每 6 条规则有 1 处矛盾。
- 没有规则描述的用户可见行为更多，平均每组约 6 处；其中一部分是要负责人决定的产品选择（例如已完成的变更能否再标为放弃）。
- 很多例子只在函数层测过、没有经过命令行，或者测试只断言了退出码、没断言“什么都不写”这类结果；#49、#50 就是这样漏掉的。
- 并发核对时让子 agent 直接提 issue 会重复，也绕过了主 agent 的核实，改为只报告后没有再出现问题。

## 后续

按子领域派修复子 agent：修 issue、把没有规则的行为写成规则（产品选择先问负责人）、给没有测试的例子补测试。修完后再决定是否把这种核对做成定期机制（C-54）。
