## 规则

`git pull`、`git merge --ff-only`、`git reset` 这类命令先把暂存区和工作区改成目标提交，再移动 main；main 守卫（BR-2126）在移动 main 时拒绝，git 不会自己改回来。所以守卫拒绝一行 `refs/heads/<main>` 时，如果 hook 所在的 checkout 签出的就是 main，而且被拒绝的新提交是一个已有的提交（别的 ref 包含它，或者它就是 `FETCH_HEAD`），守卫在退出前用 `git read-tree -m -u <新提交> <main 的提交>` 把暂存区和工作区从新提交切回 main 的提交：只改回新提交带来的那些文件，没提交的改动（已暂存的和没暂存的）原样保留，stderr 写 `the index and working tree are back at <main>`。切不回去时（`git read-tree` 失败，例如已暂存的改动和两边都不同）什么都不改，stderr 写 `could not put the index and working tree back at <main>`、git 的原话和 `git status`。

新提交是这次命令刚造的（`git commit`、`git merge --no-ff`、`git cherry-pick`，没有别的 ref 包含它）时不动暂存区和工作区：里面是用户自己的工作。main 没签出在 hook 所在的 checkout 里时也不动。

新提交在某个远端跟踪分支（`refs/remotes/*`）上或者就是 `FETCH_HEAD` 时，stderr 多一行 `to take in the remote's <main>, run canon sync`（BR-2262）。拒绝本身、退出码和别的 ref 都照 BR-2126。

## 例子

- clone 的 main 落后远端，有一个没暂存的修改和一个已暂存的新文件，`git pull origin main` → 退出码非 0，main 不动，远端带来的文件不在暂存区也不在工作区，`git status --porcelain` 和 pull 之前一样，stderr 有 `back at main` 和 `run canon sync`；改动前远端的文件留在暂存区（`A  new.txt`）
- 同样的 clone 里 `git merge --ff-only origin/main` → 被拒绝，`git status --porcelain` 和之前一样，main 不动；`git reset --hard` 之后再 `git reset --hard origin/main` → 被拒绝，stderr 有 `back at main`，工作区是干净的 main，没有远端带来的 `new.txt`
- 在签出 main 的 checkout 里 `git add app.txt` 后 `git commit -qm x` 被拒绝 → 改动仍在暂存区，stderr 没有 `back at main`，也没有 `canon sync`
- 在签出 main 的 checkout 里暂存了一个改动，`git update-ref refs/heads/main <分支 x 的提交>` → 被拒绝，暂存的改动还在，暂存区里没有 x 带来的文件；x 和 main 都改了这个暂存的文件时 stderr 有 `could not put the index and working tree back at main`，暂存区不变
