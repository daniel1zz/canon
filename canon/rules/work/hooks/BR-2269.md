business: 变更的端口

## 规则

`canon work start` 要为变更分配端口（BR-2267），而 `ports` 范围里没有能分配的端口（每个端口要么分给了 worktree 还在的其他变更，要么被 canon 以外的程序占着，BR-2288）时，不分配、不重复使用已分配的端口，但开始照常进行（D-48）：worktree 照常建好、认领照常保留，退出码照常由其他步骤决定；`setup` 和 `after_start` 照常运行，`CANON_PORT` 是空字符串；在 `setup` 之前写一行 `start: CANON_PORT is empty: <原因>`，原因列出范围、占着端口的变更和被别的程序占着的端口，并提示清理不用的 worktree、停掉占着端口的程序或把范围设大；事件表记一条 `port.refuse`，不记 `start.refuse`；协调数据库里不给这个变更记端口。之后这个变更的下一次分配（再 `canon work start <C-n>`，或 `after_stop`）照常再试；`before_land`、`after_land` 没有记录时按 BR-2287 处理。需要端口的命令自己检查 `CANON_PORT` 是否为空。

## 例子

- `ports: 4100-4101`，C-1、C-2 的 worktree 都在，`setup: 'echo "[$CANON_PORT]" > port.txt'`、`after_start: 'echo "[$CANON_PORT]" > hook.txt'`，`canon work start --title "C"` → 退出码 0，输出里有 `start: CANON_PORT is empty: no free port`、`4100-4101`、`C-1` 和 `C-2`，新 worktree 的 `port.txt` 和 `hook.txt` 都是 `[]`，事件表有一条 `port.refuse`、没有 `start.refuse`，数据库里没有新变更的端口记录
- `ports: 4100-4100`，C-9 占着 4100，C-1 开始时没分到端口（`after_start` 写出 `[]`），带 `--release` 停下，清理 C-9 的 worktree 后再 `canon work start C-1` → 这次 `after_start` 写出 `[4100]`
- 范围里还有空的端口 → 输出里没有 `start: CANON_PORT is empty`（BR-2267）
