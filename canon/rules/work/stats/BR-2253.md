## 规则

`canon verdict pending` 列出可以判定的评审拦截，按 `review.block` 事件编号从小到大。合入后评审（BR-2441）写的 `review.block`（`detail.landed` 是 `land.ok` 的编号）记了变更编号、有意见、记了评审看到的提交（合入的提交）就可以判定，不需要拒绝，它那一行写 `reviewed after landing, commit <提交>`，`--json` 里 `refusal` 为 null。其他的 `review.block`（D-89 之前合入时的评审写的）可以判定，当它记了变更编号、它有意见（`detail.findings` 不为空）、它记了评审看到的提交（`detail.commit`，合入流程在写这条事件时记下评审时变更的 `HEAD`），它之后有同一变更、原因为 `review` 的 `land.refuse`（取第一条，就是这次拦截的拒绝），这条拒绝之后这个变更合入成功过（有 `land.ok`），并且它至少有一条意见还没有任何判定（`model` 或 `human`，每条意见有一条就算判完，BR-2254）。没有 `detail.commit` 的旧拦截不可判定：不列，也不算进 `canon stats` 的分母（BR-2255），因为看不出评审当时看到的是哪份代码；人要判它们只能直接用 `canon verdict record`。不按执行者过滤（D-49）。每次拦截写一行 `#<拦截事件编号> <变更编号> <拒绝日期 YYYY-MM-DD，取事件时间的 UTC 日期>  blocked commit <评审看到的提交>`，下面每条意见一行 `  <意见编号>. model <结论或 -> · human <结论或 -> · <意见原文>`，意见从 1 编号，结论是已有判定的 `real`、`spurious` 或 `unclear`，没有判定写 `-`；两次拦截之间空一行。不写合入的提交：判定的是拦截时有没有问题，不看作者后来怎么改。`findings` 是评审给的全部意见，拦住合入的和不拦截的建议混在一起，canon 分不出，所以都列出，判的人自己跳过建议（D-49 的已知限制）。没有可列的写 `(nothing to judge)`。加 `--json` 时输出数组，每项字段为 `block`、`refusal`、`subject`、`ts`、`before`（评审看到的提交）和 `findings`，`findings` 每项字段为 `n`、`text`、`model`、`human`（没有判定时为 null）。

## 例子

- `C-1` 的 `review.block`（事件 10，两条意见，`commit` 是 `X`）之后是 `land.refuse`（事件 11，原因 `review`），之后又提交 `Y` 并合入 → 列出 `#10 C-1 2026-11-04  blocked commit X`，下面两行 `  1. model - · human - · <第一条意见>` 和 `  2. model - · human - · <第二条意见>`；输出里没有 `Y`
- 第 1 条意见有 `model` 的 `real`，第 2 条有 `human` 的 `spurious` → 每条都有判定，不列
- 只有第 1 条意见有判定 → 照样列出，那一行写 `  1. model real · human - · ...`
- 两条意见都没有判定 → 列出
- `C-2` 被评审拦下后还没合入成功 → 不列
- `C-3` 被 `floor` 拦下后合入成功，没有 `review.block` → 不列
- 一条原因为 `review` 的拒绝之前没有 `review.block`（评审没能运行）→ 不列
- `agent:a` 是 `C-1` 的作者，`agent:a` 执行 → 照样列出
- `review.block` 没有 `commit`（这个字段加入之前写的）→ 不列，即使之后合入了
- `C-4` 合入后评审写的 `review.block`（事件 30，`landed` 29，`commit` 是 `Z`，一条意见）→ 列出 `#30 C-4 <日期>  reviewed after landing, commit Z`，下面一行 `  1. model - · human - · <意见>`；之后没有 `land.refuse` 也列出
- 没有任何评审拦截 → 输出 `(nothing to judge)`
