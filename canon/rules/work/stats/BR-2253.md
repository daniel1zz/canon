## 规则

`canon verdict pending` 列出原因为 `review` 的合入拒绝（`land.refuse`）中同时满足以下条件的，按拒绝事件编号从小到大：拒绝记了变更编号，这个变更在拒绝之后合入成功过（有 `land.ok`）；当前执行者这一种判定者（`agent:` 开头的执行者是 `agent`，其他是 `human`，BR-2023）还没有给它写过 `review.verdict`（BR-2254）；当前执行者不是这个变更的作者（作者见 BR-2254）。每一条写出拒绝事件编号、变更编号、拒绝的日期、拦截时的提交（`before`）、合入的提交（`after`，拒绝之后第一条 `land.ok` 的 `sha`）和评审拒绝的信息。`before` 是那条 `land.ok` 的 `base..sha` 之间（`land.ok` 没有记 `base` 时用它之前最近一条 `land.ok` 的 `sha`，即这次合入前 main 的位置）、从 `base` 到它、`canon/changes` 以外的零上下文 diff 的 `git patch-id` 等于拒绝时改动指纹（BR-2068）的最早一个提交；拒绝没有指纹、`land.ok` 没有 `sha`、找不到 `base`、或者没有一个提交对得上时写 `?`。没有可列的写 `(nothing to judge)`。加 `--json` 时输出数组，每项字段为 `refusal`、`subject`、`ts`、`before`、`after`、`message`，`before` 和 `after` 找不到时为 null。

## 例子

- `C-1` 被评审拦下（指纹等于提交 `X` 相对 `base` 的指纹），之后又提交 `Y` 并合入成功 → 列出这条拒绝，`before` 是 `X`，`after` 是合入的 `sha`
- `C-2` 被评审拦下后还没合入成功 → 不列
- `C-3` 被 `floor` 拦下后合入成功 → 不列（不是评审拦截）
- `C-1` 的这次拦截已有 `agent:b` 写的判定，`agent:c` 执行 → 不列；`human:alice` 执行 → 列出
- `C-1` 的认领和合入都是 `agent:a` 做的，`agent:a` 执行 → 不列
- 拒绝没有记改动指纹（指纹加入之前）→ 照样列出，`before` 是 `?`
- `C-4` 的 `land.ok` 没有 `base`，它之前的一条 `land.ok` 的 `sha` 是 `M`，拦截时的指纹等于 `M` 到提交 `Z` 的指纹 → `before` 是 `Z`
- 没有任何评审拦截 → 输出 `(nothing to judge)`
