## 规则

`floor_timing: after` 下 main 上有没测过的提交（最近一个有 `floor.pass`、`floor.fail` 或 `floor.skip` 的提交之后的提交）时，`canon floor watch` 只在下面任一条成立时才测 main 的最新提交（D-59），没到点就睡到最早的到点时间，期间每隔一小段时间（`CANON_WATCH_POLL_MS`，默认 15 秒）重新读 main，main 前移就重新计算：

- main 上次移动到现在不少于 `floor_quiet_minutes`（默认 20）分钟；
- 没测过的合入（`land.ok` 事件，canon 自己直接提交的 open、close 提交不算）不少于 `floor_max_untested`（默认 10）个；
- 最老的没测过的移动到现在不少于 `floor_max_age_minutes`（默认 60）分钟。

“main 移动的时间”取 main 分支 reflog 里的时间，不取提交时间：很早提交、没经 rebase 快进合入的提交，是合入那一刻才让 main 动的；读不到 reflog 才退回提交时间。当前时间取 `CANON_NOW`（ISO 日期，测试用），没设就取系统时钟，不是日期就报错。没有任何一个提交被记为测过时马上测。main 没通过（BR-2220 的记录还在）时不等 quiet 和 age，逐个提交首尾相接地测，和以前一样。`canon floor watch --now` 不看阈值，立即测 main 的最新提交；别的后台进程只在等阈值时，它先停掉那个进程再测，别的进程正在测时，它等那次测完，所以它返回时 main 的最新提交已测过；测的过程中 main 又前移，同一个进程接着测。没有没测过的提交时进程退出。`floor_quiet_minutes: 0` 就是每个合入都立即测（和攒批前一样）。

保证只有这些：进程被杀掉或机器重启后，由下一次合入、`canon brief`、同步（`ensureWatcher`，BR-2219）重新启动它；没有会话再运行这几个命令，又没有进程在等时，没有东西会去测积压的提交。`floor_quiet_minutes` 等是 `canon/config.yaml` 的键，值是分钟（`floor_max_untested` 是个数）。

## 例子

- 基线已测，main 前移一个合入；quiet 20，现在是它之后 19 分钟 → 进程日志写 “waiting until”，不跑 floor，进程还在
- 同上，现在是 21 分钟 → 跑 floor，测的是最新提交，日志写 “main has not moved for 21 min”，进程以 0 结束
- quiet 和 age 都很大，9 个没测过的合入 → 等，不跑 floor；再合入第 10 个 → 马上测，日志写 “10 landings are not tested”
- quiet 很大，最老的没测过的提交 59 分钟前让 main 动的 → 等；61 分钟前 → 测，日志写 “the oldest untested commit is 61 min old”
- main 没通过，之后又合入一个，距上次移动才 1 分钟 → 马上测，日志写 “main is failing, so there is no quiet wait”
- 有没测过的合入，另一个进程在等阈值，运行 `canon floor watch --now` → 等着的进程被停掉（143），最新提交被测过，协调数据库里没有占位
- 等阈值的进程被 SIGKILL 杀掉，下一次 `canon brief` → 启动新的进程，同样在等，旧的占位被接手
