---
id: BR-2219
title: 后台测试同一时间只跑一个，在临时 worktree 里测 main 的最新提交，测完再看 main 有没有前移
status: active
---

## 规则

`canon floor watch` 对 main 的最新提交跑 floor：在 git 公共目录下的 `canon/watch` 临时 worktree 里检出这个提交，先跑 `setup`，再跑 floor，完整输出写进日志 `watch-<提交前 12 位>.log`，记 `floor.pass` 或 `floor.fail` 事件（带提交和日志），之后删掉临时 worktree。同一仓库同一时间只有一个在跑：协调数据库里记着正在跑的进程，它还在时新启动的什么都不做，以 0 结束；它不在了（被杀、机器重启），下一个启动的接手。测完如果 main 又前移了，接着测最新的那个，中间的提交不测；最新提交已经测过时什么都不做，除非 `refs/canon/green` 指向的提交还欠着 `after_green`，这时只补跑它（BR-2270）。例外是通过后 `after_green` 重新构建了 PATH 上的 canon：这时由新构建的 canon 接着测，这个进程结束（BR-2251），所以接着测的始终是最近一次构建的代码。`setup` 以非 0 结束时不跑 floor，记 `floor.fail`（原因 `setup exited <退出码>`），main 记为没通过（BR-2220）。后台测试被 SIGTERM 或 SIGINT 终止时，照 BR-2285 先停掉它启动的全部进程、等它们结束，再删掉临时 worktree、交出位置、退出，不记这次的结果，这个提交下次再测。合入（BR-2218）和 `canon brief` 都会在需要时启动它（main 的最新提交没测过或欠着 `after_green`（BR-2270），也没有在跑的），它在后台运行，不让启动它的命令等。主 checkout 和任何变更 worktree 都不被它改动。

## 例子

- main 前移到 A，没有在跑的 → 开始测 A，日志 `watch-<A>.log`，结束后有一条 `floor.pass` 或 `floor.fail`，提交是 A
- 测 A 期间 main 又前移到 B、C，没配 `after_green` → A 测完同一个进程接着测 C，B 没有事件
- 测 A 期间 main 又前移到 B，A 通过、`after_green` 以 0 结束 → 这个进程不测 B，交给 PATH 上的 canon（BR-2251）
- 测 A 期间又有一次合入启动它 → 新启动的立刻以 0 结束，仍只有一个在跑
- 在跑的进程被 SIGKILL 杀掉 → 下一次 `canon brief` 启动新的，重新测 main 的最新提交
- main 的最新提交已有 `floor.pass` → 启动后什么都不做
- 测试期间主 checkout 有未提交的改动 → 原样保留，`git status` 不变
- `setup` 以 1 结束 → 不跑 floor，记 `floor.fail`，原因 `setup exited 1`，main 记为没通过
