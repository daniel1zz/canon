id: BR-2221
title: canon work start --fix-main 开修复 main 的变更，同一时间只有一个
status: active
---

## 规则

有“main 没通过”的记录、还没有修复变更时，`canon work start --fix-main` 像 `--title` 一样新建并认领一个变更，标题是 `修复 main 上没通过的 floor（<提交前 9 位>）`，`## 为什么` 里写好失败的提交、最近通过的提交、日志路径和输出尾部，并在记录上写下这个变更的编号。已经有修复变更时以退出码 5 拒绝，写明是哪个；没有记录时以退出码 3 拒绝。两个会话同时执行时只有一个成功。修复变更被放弃（`canon work drop`）时，记录上的编号清掉，别人可以再开。修复变更合入后不自动清掉“main 没通过”的记录：只有后台测试通过才清（BR-2222）。但修复变更已经合入、之后的后台测试又在包含它的提交上失败时，记录上的修复变更编号清掉（失败的提交仍记在记录里），别人可以再开下一个修复变更；在不包含它的提交上失败（测试中途 main 前移，失败的是修复合入之前的提交）时不清。

## 例子

- 有记录、没有修复变更 → 退出码 0，新变更 C-12，`## 为什么` 里有日志路径；`canon brief` 写 `being fixed in C-12`
- 再执行一次 → 退出码 5，信息里有 `C-12`
- 没有记录 → 退出码 3
- 两个会话同时 `--fix-main` → 一个退出码 0，一个退出码 5，只多出一个变更
- `canon work drop C-12` → 记录上没有修复变更了，`--fix-main` 又能开
- C-12 合入后，后台测试在包含它的提交上又失败 → 记录上没有修复变更了，`canon brief` 写 `nobody is fixing it yet`，`--fix-main` 退出码 0
- C-12 合入后，失败的是比 C-12 的合入提交更早的提交 → 记录上仍是 C-12，`--fix-main` 退出码 5
- C-12 还没合入，后台测试在更新的提交上又失败 → 记录上仍是 C-12
