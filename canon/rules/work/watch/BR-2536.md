## 规则

对 BR-2535 找出的合入 L（变更 C-n），后台测试按以下步骤撤回；任何一步不成立时不撤回，和 BR-2535 的不定位一样处理（D-137）：

1. L 是杂务（没有变更文件），或者它的改动碰到了单向门的类别（`design_signals`，D-124：持久化数据、对外边界、依赖）时不自动撤回：撤回它的代码不能撤回已经写出去的数据或发出去的东西。
2. 在临时 worktree 里，从 main 当前的提交 M 起，按从新到旧撤回 L 的全部提交；有冲突时不撤回。变更文件 `canon/changes/C-n.md` 不随撤回删除或回到旧样子，而是取 L 上的内容、状态改为 `open`。提交信息是 `canon: revert C-n (the background floor failed on <X 前 9 位>)`，最后一行是 `Canon-Reverts: C-n <L>`。
3. 在撤回后的树上检查（变更文件点名的、这次撤回删掉的文件不算 `path-missing`，BR-2171）：`typecheck_command`、失败的测试文件（`test_command`；floor 不带 `{report}`、不知道哪些文件失败时换成整个 floor）和 `canon check`，都通过才继续；有一项不过就不撤回（例如之后的合入依赖 L）。
4. 记一条 `revert.start` 事件，然后按合入同样的比较并交换把 main 从 M 移到撤回提交（main 期间前移了就从新的 main 重做第 2、3 步，最多 3 次），并像合入一样推送。
5. 建分支 `change/C-n`：在撤回后的 main 上把撤回提交再撤回一次（把 L 的改动重放回来），变更文件状态仍是 `open`，提交信息写明这是撤回后重放的工作和失败的测试文件。分支已经存在时不覆盖，只在事件里写明。
6. 记一条 `land.revert` 事件（变更、L、撤回提交、分支、失败的测试文件、日志）。之后 `canon work due` 列一项 `reverted:C-n`，下一步是 `canon work start C-n`，在分支上修好失败、再合入；C-n 再次合入后这一项消失。main 之后照常由后台测试重测。

后台测试在第 4 步之后、第 6 步之前被终止时，下次后台测试开始前，按 main 上带 `Canon-Reverts:` 而没有对应 `land.revert` 事件的提交补做第 5、6 步。

## 例子

- C-2 被找出，撤回后的树类型检查、`a.test.ts` 和 `canon check` 都通过 → main 上多一个 `canon: revert C-2 (…)` 提交并推送；`canon/changes/C-2.md` 状态是 `open`；分支 `change/C-2` 上 C-2 的改动重放回来；`canon work due` 有 `reverted:C-2 … → canon work start C-2 …`
- 在 C-2 的分支上修好后合入 → `reverted:C-2` 消失
- C-3 依赖 C-2，撤回后类型检查失败 → 不撤回，`revert.skip` 写明 `typecheck_command` 不通过，按向前修处理
- 撤回 C-2 有冲突 → 不撤回，按向前修处理
- 检查撤回后的树期间 main 每次都前移，3 次都没移成 → 不撤回，`revert.skip` 写明 main 一直在动
- `change/C-2` 已经存在 → 不覆盖它，`land.revert` 写明分支已存在、没有替换
- floor 不带 `{report}`、C-2 被找出 → 撤回后的树上跑整个 floor，通过才撤回
- 找出的是杂务 `chore-x` → 不撤回，按向前修处理
- C-2 改了 `canon/config.yaml` 里 `design_signals` 列出的持久化数据路径 → 不撤回，按向前修处理
- 撤回提交已经推上 main，写 `land.revert` 之前后台测试被杀 → 下次开始前补建 `change/C-2` 和 `land.revert`
