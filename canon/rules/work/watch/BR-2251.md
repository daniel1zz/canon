## 规则

`canon floor watch` 在一个提交上通过（BR-2222），`hooks.after_green` 至少有一条命令、而且每一条都以 0 结束时，当作 PATH 上的 canon 刚从这个提交重新构建过：这个进程不再测别的提交（不管 main 有没有前移），先交出后台测试的位置（BR-2219 的占位），在主 checkout 里后台启动 PATH 上的 `canon floor watch`（输出追加到 `watch.log`），启动后记一条 `floor.handoff` 事件（带刚通过的提交 `sha`、PATH 上 canon 的路径 `to` 和日志），自己以 0 结束。新启动的进程照 BR-2219 工作：main 的最新提交已经测过就什么都不做、以 0 结束，所以交接后不会马上再交接，只有它自己又通过一次、又跑完 `after_green` 才会再交接；和合入、`canon brief` 同时启动的后台测试抢同一个占位，同一时间仍只有一个在测。

没有重新构建成功时不交接，同一个进程照 BR-2219 接着测 main 的最新提交：没配 `after_green`、其中有一条以非 0 结束、PATH 上没有 canon、或者启动 PATH 上的 canon 失败（这时说明原因，不记 `floor.handoff`）。交接以后 main 的最新提交没测过时，由新进程去测；新进程没起来或中途退出，下一次合入或 `canon brief` 照 BR-2219 启动后台测试，最新提交不会一直没人测。`floor.handoff` 不算 floor 的运行，不进 `canon stats`（BR-2067 只算 `floor.pass` 和 `floor.fail`）。

## 例子

- 在 A 上通过，`after_green` 是一条以 0 结束的命令，PATH 上有 canon → 有 `floor.pass`（A），之后一条 `floor.handoff`，`sha` 是 A、`to` 是 PATH 上 canon 的路径；PATH 上的 canon 在主 checkout 里以 `floor watch` 启动；这个进程以 0 结束，协调数据库里没有它的占位
- 测 A 期间 main 前移到 B，A 通过、`after_green` 以 0 结束 → 这个进程不测 B，只有 A 的 `floor.pass` 和 `floor.handoff`；B 由新启动的 PATH 上的 canon 去测
- 新启动的进程启动时 main 的最新提交还是 A → 它什么都不做，以 0 结束，没有第二条 `floor.handoff`
- 在 A 上通过，没配 `after_green` → 没有 `floor.handoff`，不启动 PATH 上的 canon；测 A 期间 main 前移到 C 时，同一个进程接着测 C
- `after_green` 以 1 结束 → 没有 `floor.handoff`，同一个进程接着测 main 的最新提交
- `after_green` 以 0 结束，PATH 上没有 canon → 没有 `floor.handoff`，同一个进程接着测
