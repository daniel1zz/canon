## 规则

后台测试（BR-2219）的 floor 失败、它的 JUnit 报告（BR-2339）里有失败或出错的测试，而且项目配了 `test_command` 时，后台测试在同一个临时 worktree 里，不改任何代码，用 `test_command` 把这些测试所在的文件逐个重跑一次，输出接着写进同一份日志（D-137）：

- 每个文件都通过：记一条 `floor.flaky` 事件（提交、这些文件、日志），这个提交按通过处理（BR-2222：记为通过的提交、清掉“main 没通过”的记录、运行 `after_green`），不记 main 没通过。之后 7 天里（天数是 `policies.agenda.flaky_days`，BR-2639）`canon work due` 对每个这样的文件列一项 `flaky:<文件>`，下一步是为它开一个 issue（一个文件一个），修好或隔离它。
- 有文件仍然失败，或者 floor 在跑测试之前就失败了（报告不存在或没有失败的测试，例如装依赖或类型检查失败），或者项目没配 `test_command`：按失败处理（BR-2220），再按 BR-2535 找出让它失败的合入。

## 例子

- floor 在 X 上失败，报告里 `a.test.ts` 有一个测试失败；重跑 `a.test.ts` 通过 → 记 `floor.flaky`，X 成为通过的提交，没有“main 没通过”；`canon work due` 有 `flaky:a.test.ts`，下一步写着开 issue
- 同样的失败，重跑 `a.test.ts` 仍然失败 → 记 main 没通过，接着按 BR-2535 定位
- `a.test.ts` 和 `b.test.ts` 失败，重跑 `a` 通过、`b` 失败 → 按失败处理
- floor 在类型检查就失败、没有报告 → 不重跑，按失败处理
- 7 天里同一个文件再次重跑通过 → 仍是一项 `flaky:a.test.ts`，从最近一次算起
