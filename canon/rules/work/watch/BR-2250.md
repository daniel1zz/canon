id: BR-2250
title: 后台测试进程的代码比 main 旧、读不了被测提交的配置时，交给 PATH 上的 canon 重测，不记 main 没通过
status: active
---

## 规则

`canon floor watch` 用自己的代码读不了被测提交的 `canon/config.yaml` 时，先在测试用的临时 worktree 里运行 PATH 上的 `canon config --schema`（和 BR-2224 同一个检查）。PATH 上的 canon 读得了，说明是这个后台测试进程自己的代码旧了（它启动后 PATH 上的 canon 被 `after_green` 重新构建过，而 main 已经用上了新配置项）：这时不记 `floor.fail`，也不记“main 没通过”，而是记一条 `floor.stale` 事件（带提交、日志和原因），交出后台测试的位置，在后台启动 PATH 上的 `canon floor watch` 接着测这个提交（带环境变量 `CANON_WATCH_HANDOFF=<提交>`），自己以 0 结束。`floor.stale` 不算测过，所以这个提交一定会被新启动的那个、或者之后合入和 `canon brief` 启动的后台测试测到。

PATH 上的 canon 也读不了、PATH 上没有 canon，或者这个进程本身就是为这个提交交接来的（`CANON_WATCH_HANDOFF` 等于被测提交，避免来回交接）时，照旧记 `floor.fail`，原因 `its canon/config.yaml cannot be read`，main 记为没通过（BR-2220）：那样的配置是会话们用的 canon 也读不了的。

## 例子

- 被测提交的配置里有这个进程不认识的配置项，PATH 上的 `canon config --schema` 以 0 结束 → 没有 `floor.fail`，没有“main 没通过”的记录，有一条 `floor.stale`，提交是它；PATH 上的 canon 在主 checkout 里以 `floor watch` 启动，`CANON_WATCH_HANDOFF` 是这个提交；`canon floor watch` 以 0 结束
- 同样的配置，PATH 上的 `canon config --schema` 以 2 结束 → 记 `floor.fail`，`exit` 2，原因 `its canon/config.yaml cannot be read`，main 记为没通过，不启动别的 canon
- 同样的配置，PATH 上的 canon 读得了，但 `CANON_WATCH_HANDOFF` 已经是这个提交 → 记 `floor.fail`，不再交接
- 被测提交的配置这个进程读得了 → 不运行 PATH 上的 canon，照常跑 floor
