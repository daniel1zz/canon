## 规则

后台测试失败时，协调数据库里记一条“main 没通过”：失败的提交、日志路径、输出的最后 40 行、第一次失败的时间和最近通过的提交（`refs/canon/green`，没有时为空）。已经有这条记录时只更新失败的提交、日志和输出尾部，不新建，也不改修复它的变更。`floor.fail` 事件和这条记录在同一个事务里写：记录写不进去时事件也不留，`canon floor watch` 以退出码 4 结束，这个提交在下次启动时重新测试，不会出现记了失败、却没有“main 没通过”的情况。`canon brief` 在主 checkout 和变更 worktree 里都先于其他内容（工作说明之后）输出：main 从哪个提交起没通过、日志路径、输出尾部的最后 10 行、最近通过的提交；还没有人在修时，提示没有认领变更的会话用 `canon work start --fix-main` 去修；已有修复变更时写明是哪个。在变更 worktree 里还写明：这些失败不是这个变更造成的，不要在这个变更里修。

## 例子

- 后台测试在 A 上失败，之前没有记录 → 记录的提交是 A；`canon brief` 第一段写 `main is failing floor since A`、日志路径和 `canon work start --fix-main`
- 之后在 C 上又失败 → 仍是一条记录，提交改成 C，日志改成 C 的，开始时间不变
- C-5 已用 `--fix-main` 开出 → brief 写 `being fixed in C-5`，不再提示 `--fix-main`
- 在 C-9 的 worktree 里运行 `canon brief` → 有一句说明这些失败不是 C-9 造成的
- 没有记录 → brief 不出现这一段
- 失败后写“main 没通过”的记录出错 → `canon floor watch` 退出码 4，没有 `floor.fail` 事件，也没有记录；下次启动重新测这个提交，记下 `floor.fail` 和记录
