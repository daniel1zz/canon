## 规则

后台测试在提交 X 上按失败处理（BR-2534）之后，canon 在通过的提交 G（`refs/canon/green`）和 X 之间找出第一个让它失败的合入，交给 BR-2536 撤回（D-137）。

候选是 main 从 G 到 X 的第一父链上、有 `land.ok` 事件的合入，每个的范围是它记下的合入前的 main（`base`）到合入后的提交。探测一个提交：在 git 公共目录下的临时 worktree 里先跑 `setup`，再跑探测命令，退出码 0 算通过。探测命令按顺序取：失败的测试文件（用 `test_command` 逐个跑，这个提交上不存在的文件算通过）；没有失败的测试文件时用 `typecheck_command`；都没有时用整个 floor。先探测 G，G 不通过就说明探测本身不可靠，不定位；之后对候选按顺序二分，找出探测失败、而它的前一个候选（第一个候选时是 G）探测通过的那一个。每次探测的结果写进同一份日志。

以下情况不定位、不撤回，退回现在的做法（向前修，BR-2221），并在日志和 `revert.skip` 事件里写明原因：没有 G；G 到 X 之间没有带 `base` 的合入；“main 没通过”的记录上已经有修复变更；这条记录开始以后已经自动撤回过一次；探测 G 不通过；二分的结果和探测不一致（最后一个候选也通过）。

## 例子

- G 之后有 C-1、C-2、C-3 三次合入，X 是 C-3；失败的是 `a.test.ts` → 探测 G 通过，C-2 失败，C-1 通过 → 找出 C-2
- 只有 C-1 一次合入 → 探测 G 通过、C-1 失败 → 找出 C-1
- floor 在类型检查就失败、项目配了 `typecheck_command` → 探测命令是它，不跑整个 floor
- `a.test.ts` 是 C-2 新加的 → 在 G 和 C-1 上它不存在，算通过
- 探测 G 时 `a.test.ts` 也失败 → 不定位，`revert.skip` 写明 G 不通过，按向前修处理
- 已经有人用 `--fix-main` 开了 C-9 → 不定位
- 同一条“main 没通过”记录里已经撤回过 C-2，撤回后的重测又失败 → 不再撤回，按向前修处理
