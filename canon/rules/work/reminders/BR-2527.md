## 规则

`canon work due` 不改认领、队列和派发；它算停滞时要判断认领状态，第一次发现认领失效时按 BR-2360 写一条 `claim.expired` 或 `claim.holder-gone`，此外不写事件。它按调用者的执行者身份（BR-2023）列出现在的待办，每件一行：

`<键> <已开时长> <说明> → <下一步命令>`

已开时长写成 `12m`、`3h05m`、`2d4h` 这样的形式，从这件事开始的时间算起。

**主会话**（不是 worker 的执行者）的待办：

| 待办 | 键 | 开始时间 | 下一步 |
|---|---|---|---|
| 未处理的评审意见（BR-2433） | `finding:<n>` | 开出的时间 | 按档位（BR-2502）：没定档的 `canon finding tier`，A 档 `canon finding close`，B 档等别的会话 `canon finding advise`，C 档 `canon finding ask` |
| 等人回答的问题 | `question:<n>` | 提问的时间 | 在对话里问人，再 `canon human answer` |
| 停滞的派发（BR-2522） | `stalled:<C-n>` | BR-2522 的“较晚的那个时间” | 重新派发或 `canon work take` |
| 交回给自己的设计请求（BR-2499） | `design:<C-n>` | 请求的时间 | 按 BR-2499 回答 |
| main 没通过后台测试 | `red-main` | 记下没通过的时间 | `canon work start --fix-main` |
| 合入时没有执行证据的规则（BR-2241）：变更在 main 上已完成，它最近一条 `execution.unverified` 事件里的规则还有生效、在 main 上仍是待重新执行的 | `unverified:<C-n>` | 那条事件的时间 | 在 `rules:` 列出它们的变更里改一行标题点名每条的测试（带 `untested:` 的写一行验收），加 `--finish` 合入 |
| 机器容量紧张（BR-2526 的条件 1 或 2 成立） | `capacity` | 不存起来，写 `now`；`canon work watch` 用它自己第一次看到的时间（BR-2528） | 等 worker 合入，先不派新的 |

一条意见等着负责人回答裁决问题时（BR-2461），只作为问题出现一次，不作为意见重复列出。

**worker** 的待办只有它自己认领或被派到的变更的：设计请求的回答已经到了（`design-answer:<C-n>`），这个变更被重新派发或被 `take`（`delegation:<C-n>`），它自己的合入被拒绝且还没再合入（`land-refused:<C-n>`）。

`--json` 输出一个数组，每项包括 `key`、`since`（ISO 8601）、`summary`、`next`。没有待办时，文字输出一行 `nothing due`，`--json` 输出 `[]`，退出码都是 0。

依据：D-136；`unverified:` 一项按 D-141。

## 例子

- 主会话，有一条 40 分钟前开出、定了 B 档的意见 #12 → 一行 `finding:12 40m … → needs another session: canon finding advise 12 …`
- 主会话，意见 #13 还没定档 → 下一步是 `canon finding tier 13 …`
- 意见 #14 在等负责人回答问题 #60 → 只有一行 `question:60`，没有 `finding:14`
- worker `agent:s:w1` 做 `C-5`，设计负责人回答了它的设计请求 → 一行 `design-answer:C-5`；它看不到主会话的意见
- `C-7` 加 `--finish` 合入时 `BR-3` 没有证据，合入了 → 主会话一行 `unverified:C-7 … landed with BR-3 待重新执行 …`；之后某个变更给 `BR-3` 写了当前文字的通过记录 → 这一行没有了
- 同上，但 `C-7` 那次合入被拒、还没合入 → 没有 `unverified:C-7`
- 什么都没有 → `nothing due`，退出码 0
- 认领都还有效时，运行前后事件表的最大编号不变
