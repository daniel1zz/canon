## 规则

`canon work due` 不改认领、队列和派发；它判断认领状态时，第一次发现认领失效按 BR-2360 写一条事件，此外不写事件。它输出调用者现在的议程（D-151）。

**议程项**一行：`<键> <已开时长> <说明> → <下一步命令>`。已开时长从这件事开始的时间算，写成 `12m`、`3h05m`、`2d4h`；没有开始时间的写 `-`。变更的状态一律取 BR-2571 的主状态和附加标记，议程不另算。

**主会话**（不是 worker 的执行者，BR-2023）的议程分三组，按这个顺序输出，每组一行组头，组里的项缩进两个空格；空的组不输出：

1. **可派的活**：组头和项按 BR-2581。
2. **要判断的事**：组头 `judge: <条数>`。项按下面三档排，档内按开始时间从早到晚：
   - 第一档，影响 main 正确的：main 没通过后台测试（`red-main` → `canon work start --fix-main`）；被撤回的变更（`reverted:<C-n>`，BR-2536）；矛盾类（`contradiction`）的未处理意见；合入后的规则评审没能跑完（`review-failed:<C-n>` → `canon work review-landed --again <C-n>`）。
   - 第二档，挡住别人的：停滞的派发（`stalled:<C-n>`，BR-2522 → 重新派发或 `canon work take`）；合入被拒且没有生效认领的变更（主状态 `land-refused`、没有 `claimed` 标记：`land-refused:<C-n>`）；代码已在 main 待关闭（主状态 `awaiting-close`：`awaiting-close:<C-n>` → `canon change close <C-n> --commit <commit>`）；依赖一个没写 `done_by` 的放弃变更（`dropped-dep:<C-n>`，开始时间取不到，写 `-`）；交回给自己的设计请求（`design:<C-n>`，BR-2499）。
   - 第三档，其余的：其他未处理的评审意见（下一步按档位，BR-2502：没定档 `canon finding tier`，A 档 `canon finding close`，B 档等别的会话 `canon finding advise`）；合入时没有执行证据的规则（`unverified:<C-n>`，BR-2241、D-141）；不稳定的测试（`flaky:<文件>`，BR-2534）。

   同一类有 2 条以上时合成一行：`<类> ×<条数> oldest <最老的时长>: <键，逗号分隔，最多 10 个，多的写 … +<k>> → <下一步命令，编号处写 <n>>`，这一行按它最老的一条排位置。类是键冒号前的部分，评审意见再按矛盾类、档位（没定档、A、B）分开。
3. **等负责人的事**：组头 `owner: <条数>`，提醒主 agent 去问负责人，不算它要判断的事：等人回答的问题（`question:<n>` → 在对话里问人，再 `canon human answer`）；定为 C 档、还没问负责人的意见（`finding:<n>` → `canon finding ask`）；进行中的版本和它的模块里待负责人的成功标准（`criterion:<编号>/S<k>`，开始时间写 `-`）。等着负责人回答裁决问题的意见（BR-2461）只作为问题出现一次。同类合并同上。

另有一行正在跑的整组测试，按 BR-2582，放在三组之后。

主 agent 记下处理结论的项（BR-2583）不出现在议程里。

**worker** 的议程只有它自己认领或被派到的变更的事，一组，组头 `yours: <条数>`：设计请求的回答已经到了（`design-answer:<C-n>`），这个变更被重新派发或被 `take`（`delegation:<C-n>`），它自己的合入被拒绝且还没再合入（`land-refused:<C-n>`）。

`--json` 输出一个对象：`delegate`（BR-2581 的 `room`、`fits`、`reasons`、`changes`）、`judge`、`owner`、`yours`（每项含 `key`、`kind`、`since`（ISO 8601 或 `null`）、`summary`、`next`，不合并）、`heavy`（BR-2582）。议程为空时，文字输出一行 `nothing due`，`--json` 照样输出对象（各组为空），退出码都是 0。

依据：D-151（取代 D-136 的待办清单）；`unverified:` 按 D-141。

## 例子

- 主会话，意见 #12 开了 40 分钟、定了 B 档 → `judge: 1` 下一行 `  finding:12 40m … → needs another session: canon finding advise 12 …`
- 意见 #13 没定档 → 下一步 `canon finding tier 13 …`
- 意见 #14 在等负责人回答问题 #60 → 只有 `question:60`，在 `owner:` 组里，没有 `finding:14`
- 意见 #15 定了 C 档 → 在 `owner:` 组里，下一步 `canon finding ask 15 …`
- main 没通过后台测试、另有一条开了 3 天的 A 档意见 → `red-main` 在那条意见前面
- `C-5`、`C-6` 都停滞，最老的停了 1 小时 20 分 → 一行 `stalled ×2 oldest 1h20m: stalled:C-5, stalled:C-6 → canon work delegate <n> --to <name> or canon work take <n>`
- 只有 `C-5` 停滞 → 一行 `stalled:C-5 …`，不合并
- 23 条 A 档意见 → 一行 `finding A ×23 oldest …`，列 10 个键再加 `… +13`
- `C-7` 合入被拒，worker 还在（认领有效）→ 没有 `land-refused:C-7`；worker 退出、认领失效后 → 有
- `C-343` 的主状态是 `awaiting-close` → `awaiting-close:C-343 … → canon change close C-343 --commit <commit>`
- `C-7` 加 `--finish` 合入时 `BR-3` 没有证据 → `unverified:C-7`；之后 `BR-3` 有了当前文字的通过记录 → 这一项没有了
- 主 agent 对 `stalled:C-5` 写了「交给 C-9」（BR-2583）→ `stalled:C-5` 不再出现
- worker `agent:s:w1` 做 `C-5`，设计请求的回答到了 → `yours: 1` 和 `design-answer:C-5`；它看不到主会话的意见
- 什么都没有 → `nothing due`，退出码 0；`--json` 的 `judge` 是 `[]`
- 认领都还有效时，运行前后事件表的最大编号不变
