## 规则

议程（BR-2527）的第一组列能开工的变更：列哪些、按什么顺序、每项怎么写按 BR-2607。本条定组头里机器有没有空、还能派几个。

**有没有空**按 BR-2526 的三个条件判断，另外把正在跑的整组测试（BR-2582）算进去：

- 内存：BR-2526 条件 1 成立就是没空。
- 负载：上限 `L` 是 BR-2526 条件 2 的上限（`delegate_max_load_per_cpu` × CPU 数）。5 分钟负载达到 `L` 就没空；有整组测试在跑时，达到 `0.9 × L` 就没空（5 分钟负载跟不上刚开始的测试）。比较用没有取整的值。
- 名额：还能派几个 = `delegate_max_workers` − 占用名额的派发数（BR-2526 条件 3 的数法）− 正在跑的整组测试数，小于 0 时算 0。为 0 就没空。
- 测不到的信号按 BR-2526 不参与判断。

`canon work watch` 在这上面再加回差，按 BR-2528。

**有空**时，组头是 `delegate: room for <k> more (<负载情况>)`，`<k>` 是还能派几个。`<负载情况>` 写 `load <一位小数> of <L> on <CPU 数> CPUs, <占用>/<delegate_max_workers> slots`，有整组测试在跑时加 `, <n> full test run(s) running`。

**没空**时，组头是 `delegate: busy (<原因，分号分隔>)`；议程摘要（BR-2529）里在后面加 `; delegatable once it falls: <能派的 C-n，逗号分隔，最多 5 个>`。原因的写法同 BR-2526 的拒绝信息（`memory pressure warn`、`5-minute load 16.2 on 8 CPUs (limit 16)`、`10 of delegate_max_workers (10) in use`）；因整组测试而降低的负载上限写成 `… (limit 14.4 while a full test run is running)`，因整组测试占掉的名额写成 `<n> full test run(s) take the last slot(s)`。

议程只给事实，不派活、不挡派发：自己做还是派出去由主 agent 决定（D-152、D-156），`canon work delegate` 照 BR-2526 自己判断。

`--json` 的 `delegate` 对象：`room`（布尔）、`fits`（还能派几个）、`reasons`（没空的原因）、`load`、`limit`、`cpus`、`held`、`max`、`full_runs`（正在跑的整组测试数）、`changes`（全部能派的变更编号，按顺序），以及 BR-2607 的 `ready`。

依据：D-151 第三部分第 5 条；BR-2526。

## 例子

- 8 个 CPU、负载 4.2、占用 2 个名额、上限 10，没有整组测试，可派 `C-9`、`C-10` → 组头 `delegate: room for 8 more (load 4.2 of 16 on 8 CPUs, 2/10 slots)…`，下面按 BR-2607 两项
- 同上，再有 1 组整组测试在跑 → `room for 7 more (…, 1 full test run(s) running)`
- 负载 15.0、有 1 组整组测试在跑 → 没空，组头 `delegate: busy (5-minute load 15.0 on 8 CPUs (limit 14.4 while a full test run is running))…`；摘要里再加 `; delegatable once it falls: C-9, C-10`
- 负载 15.0、没有整组测试 → 有空
- 负载 16.0 → 没空，原因含 `limit 16`
- 占用 9 个名额、1 组整组测试在跑 → `9 of delegate_max_workers (10) in use; 1 full test run(s) take the last slot(s)`，没空
- 没有能开工的变更，机器很忙 → 没有 `delegate:` 这一组
- 只有标题、`## 要改什么` 还空着的变更 → 它是 `ready-self`，按 BR-2607 只写自己做
