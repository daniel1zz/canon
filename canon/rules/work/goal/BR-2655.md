## 规则

`canon goal check --hook`（BR-2519）在目标没有拦下会话时，再做一次调度检查（D-170）：目标拦下时只输出目标的说明；目标因为连续三次没进展而放行时，不做调度检查。

放行（不拦，原样输出目标那一步的结果，没有就是 `{}`）的情况：

- 这个会话是 worker：hook 进程的身份（BR-2023）是 worker，或者 `session_id` 算出的会话身份是 worker。
- 这个会话关了调度（BR-2660）。
- 现在能做的事一件也没有。**现在能做的事**取自主会话的待办清单（BR-2527）：机器有空位时能开始的变更（第一组，按清单的顺序），以及 judge 组里下一步不是交给别的会话（`needs another session`）的项。owner 组的项、整套测试的运行不算。
- **没有进展**：上一次调度检查拦下这个会话之后，它自己没有记下新的事件（身份是这个会话或它的子 agent `agent:<会话>:<名字>` 的事件，不算 `dispatch.hold`），hook 运行所在工作树的提交和 `git status --porcelain` 的输出也都没变。这时放行，并清掉记下的状态，所以负责人的下一句话之后的第一次停下又会拦下一次。别的会话合入让 main 前进不算这个会话的进展。

否则拦下：记下这个会话现在的状态（它自己最新的事件编号、工作树的提交和改动），记一条 `dispatch.hold` 事件（详情：列出的项的键），输出 `{"decision": "block", "reason": "<说明>"}`。说明依次写：

1. `Dispatch (canon work due): before stopping, act on what you can do now, or stop again to leave it:`
2. 最多 5 行能做的事：先是能开始的变更，每个一行，格式同 `canon work due` 的 `ready:` 行（BR-2607）；再是 judge 组的项，同一种合成一行，格式同 `canon work due`（BR-2527）。更多时加一行 `… <n> more: canon work due`。
3. `Waiting for the owner's answer or for running work: stop again. The owner asked to pause: canon goal dispatch off.`

canon 读不了项目或协调数据库、算不出待办清单时，输出 `{"systemMessage": "canon dispatch check failed: <原因>"}` 放行，不困住会话。

## 例子

- 主会话没开目标，有一个能开始的变更 `C-5`，机器有空位 → `decision: block`，reason 第一行是 `Dispatch (canon work due): …`，有一行 `ready:C-5 …`，记一条 `dispatch.hold`
- 紧接着又停下，期间什么都没做 → 放行，输出 `{}`
- 再一次停下（负责人又说了一句之后） → 又拦下一次
- 拦下后会话认领了一个变更（记下了事件）再停下 → 再拦下，列出现在的清单
- 拦下后别的会话合入、main 前进，这个会话什么都没做 → 放行
- 待办清单里只有 `needs another session` 的 B 级意见和 owner 组的问题 → `{}`
- 机器没有空位，只有能开始的变更 → `{}`
- worker 会话（hook 进程的身份是 `agent:s:w1`）停下 → `{}`
- 会话运行过 `canon goal dispatch off` → `{}`
- 目标拦下会话 → 只有目标的说明，没有 `Dispatch` 一行
- 目标连续三次没进展放行 → 输出目标的 systemMessage，不拦
- 待办清单算不出 → `canon dispatch check failed: …`，放行
