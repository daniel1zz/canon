---
id: BR-2360
title: 认领第一次被发现失效时写一条事件，同一个认领同一种失效只写一条
status: active
---

## 规则

任何命令在判断认领状态时（`canon work status`、`canon brief`、`canon work start`、`canon work clean`、`canon work drop`，以及 `canon events --follow` 第一次查询前和之后每隔至少 5 秒（BR-2357），都经过 BR-2100、BR-2192 的同一个判断），发现一个认领已经失效，就在事件表写一条事件：租约到期的写 `claim.expired`，租约没到期但记下的会话进程已经不在的写 `claim.holder-gone`。事件的对象是变更编号，详情有 `holder`（执行者）、`worktree` 和 `version`（认领表里这一行当时的版本），执行者列写 `canon`。

- 同一个变更编号、同一个 `version`、同一种事件只写一条，靠事件表上的唯一约束保证：几个命令同时发现时也只有一条；打开旧数据库时补上这个约束（BR-2078）。
- 认领之后被接手、续租或改记进程（`version` 变了）再失效，是新的一次，再写一条；认领被释放后重新认领也是：重新认领时 `version` 取这个变更记过的失效事件里最大的 `version` 加 1，所以总比记过的都大，不会和旧事件撞上。
- 同一次判断只得出一种失效（租约到期优先，BR-2192）；但同一个 `version` 先被判断为 `claim.holder-gone`、之后租约又到期，会再写一条 `claim.expired`，因为两者是不同的事件种类。
- 仍然有效的认领不写；`canon work clean`、`canon work drop` 临时占住变更的那一行（BR-2019、BR-2064）不是对变更的认领，不写。
- 这些事件不是工作，不算进 `canon stats` 的任何检查（BR-2067）。
- 记过的失效再被判断到时只读不写，不取写锁。
- 配合 `canon events --follow --kind claim.holder-gone,claim.expired`（BR-2357），能及时看到没人在做的变更；决定见 D-66。

## 例子

- `C-1` 的认领记着的会话进程已经退出，租约还剩 11 小时，运行 `canon work status` → 事件表多一条 `claim.holder-gone`，对象 `C-1`，详情有 `holder`、`worktree`、`version`；再运行一次 `canon work status` 或 `canon brief` → 不再多
- `C-1` 的租约已过期、会话进程也已退出，第一次判断 → 只写一条 `claim.expired`，不写 `claim.holder-gone`，因为租约到期优先（BR-2192）
- `C-1` 的会话进程先退出，判断时记了 `claim.holder-gone`；之后租约到期，再判断 → 同一个 `version` 再写一条 `claim.expired`，共两条
- `canon events --follow --kind claim.holder-gone` 运行中，`C-1` 的会话进程退出 → 最多约 6 秒后（5 秒的判断间隔加 1 秒的查询间隔）输出一行 `claim.holder-gone`，之后不重复
- 同一个失效的认领，两个命令同时判断 → 只有一条事件
- agent:b 接手失效的 `C-1`（`version` 加 1），之后它的会话进程也退出了 → 再写一条 `claim.holder-gone`，`version` 是新的
- `C-1` 的认领失效、记了一条 `claim.holder-gone`，负责人 `canon work stop --release` 释放后，agent:b 重新认领 `C-1`，它的会话进程也退出了 → 再写一条 `claim.holder-gone`（新认领的 `version` 比记过的都大）
- `canon work clean` 占住一个已失效、已记过事件的 `C-1` 后放弃，把原来的认领放回去 → 放回的还是同一个认领，不再写第二条
- 认领仍然有效 → 没有事件
- 旧版本建的协调数据库（没有这个约束）被新版本打开 → 约束补上，之后同一个认领仍只写一条
- `canon work clean` 占住 `C-1` 的那一行，它的进程被杀掉后被别的命令看到已失效 → 不写事件
