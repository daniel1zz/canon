## 规则

`canon work delegate <C-n> --to <name>` 只有在会**新增** worker 时才检查机器容量。新增的意思是：这个变更现在没有生效的派发（从没派过，或已被 `take` 结束，BR-2500）。给已有生效派发的变更重新派发，只是换 worker，不新增；把停滞的变更重新派出去（BR-2522）也属于这种情况，不检查。例外：重新派发把生效的轻派发改成重派发时，只按第 2 条检查负载（BR-2632）。

新增时，下面任一条成立就拒绝（BR-2610 替主会话自己的子 agent 做的派发除外：子 agent 已经在跑，不因容量拒绝，只输出 `machine busy` 一行）：

1. **内存紧张**：
   - macOS：`kern.memorystatus_vm_pressure_level` 是 2（warn）或 4（critical）（从哪一级起算、Linux 的两个百分比，按 `policies.capacity`，BR-2640）；
   - Linux：`/proc/pressure/memory` 中 `some` 一行的 `avg10` 达到 10；没有这个文件时，`/proc/meminfo` 里 `MemAvailable` 低于 `MemTotal` 的 10%。
2. **CPU 紧张**：5 分钟平均负载达到 CPU 数（`availableParallelism`）的 `delegate_max_load_per_cpu` 倍（`canon/config.yaml`，大于 0，默认 2）。比较用没有取整的值，和 BR-2400 一样。轻派发（`--light`，BR-2632，D-161）不看这一条：这一段的 worker 不跑重活，它要跑的重步骤自己按 BR-2630 等负载；这一条成立时，轻派发成功的输出多一行，写法按 BR-2632。
3. **名额用完**：占用名额的派发已经有 `delegate_max_workers` 个（`canon/config.yaml`，正整数，默认 10）。一个派发占用名额，要同时满足：它是生效的，它的变更没有关闭（按 BR-2571 的主状态不是 `landed` 或 `dropped`），并且它没有停滞（BR-2522）。

被拒绝时：
- 不写派发记录，退出码 1；
- 信息列出所有成立的条件，每条带上实测值和上限：内存压力等级或 PSI、`MemAvailable` 的比例，负载（一位小数）、CPU 数和上限，占用的名额数和 `delegate_max_workers`；
- 信息建议等一个 worker 合入，或者等负载降下来再派；
- 事件表记一条 `delegation.refuse`，对象是这个变更编号，原因 `capacity`，详情包含各项实测值和成立的条件。

**测不到的信号**：读不到内存信号（不是 macOS 或 Linux，或者读取失败），或者三个负载平均值都是 0，那一项就算测不到。测不到的项不参与判断，派发照常进行，但输出一行 `capacity: <memory|load> not measured on this platform; delegated without that check`，并在派发事件 `delegation.create` 的详情里记 `unmeasured`。名额总是能数出来。

是否新增 worker、名额够不够、写派发记录，都在同一个写事务里（BEGIN IMMEDIATE）判断：两个会话同时派发时，后一个会数到前一个刚写入的派发；派发在进事务之前和事务里之间被结束了的，事务里按新增算，照样检查容量（#261）。机器读数、停滞和变更是否关闭在进事务之前算好（不管是不是新增都算），事务里只读派发记录并数名额。

**两个会话派同一个变更**：事务里看到这个变更已有生效的派发，派发人（`owner`）是别的执行者，并且它没有停滞（BR-2522，在进事务之前算好）时，按冲突拒绝：退出码 5，不写派发记录，信息写明 `<C-n> is already delegated to <worker> by <owner>; it is not stalled`，并建议改派别的变更、或由派发人重新派发；事件表记一条 `delegation.refuse`，原因 `conflict`。派发人是自己（换 worker、补设计）或已经停滞时，照上面的规则进行。这是并发安全（P4）的完整性检查（D-151 第三部分第 8 条）。

依据：D-136；负载只挡重派发、重步骤另按 BR-2630 等负载，按 D-161；冲突按 D-151 第三部分第 8 条；负责人在 human #67 选了按内存压力判断，并补充「内存和cpu都需要」。

## 例子

- 负载 17.0、8 个 CPU（上限 16），`canon work delegate C-9 --to w1 --light "只写设计稿"`，内存正常、名额够 → 派发，退出码 0，输出有一行 `light: 5-minute load 17.0 on 8 CPUs (limit 16), not checked for C-9: 只写设计稿; …`
- 同上但不带 `--light` → 退出码 1，信息含 `5-minute load 17.0 on 8 CPUs (limit 16)`
- 带 `--light` 但内存紧张 → 照常拒绝，原因只有内存那一条
- 带 `--light`、负载 17.0，已有 10 个占用名额的派发 → 拒绝，信息含 `10 of delegate_max_workers (10) in use`，不含负载
- macOS 内存压力等级 1，8 个 CPU、负载 12.7，占用名额 3 个，新派 `C-9` → 照常派发
- 内存压力等级 2，新派 `C-9` → 退出码 1，信息含 `memory pressure warn`，事件表有 `delegation.refuse`、原因 `capacity`，没有派发记录
- 8 个 CPU、负载 16.0，`delegate_max_load_per_cpu` 默认 → 拒绝，信息含 `5-minute load 16.0 on 8 CPUs (limit 16)`；负载 15.96 → 不因负载拒绝
- 已有 10 个占用名额的派发，新派第 11 个 → 拒绝，信息含 `10 of delegate_max_workers (10) in use`
- 10 个派发中有 1 个的变更已在 main 上关闭，或者已经停滞 → 只占 9 个，第 11 个照常派发
- 内存压力等级 4，重新派发停滞的 `C-3` 给新的 worker → 照常派发，因为不新增 worker
- Linux 没有 `/proc/pressure/memory`，`MemAvailable` 是 `MemTotal` 的 8% → 拒绝，信息含 `MemAvailable 8%`
- Windows：内存测不到，负载是 0 0 0 → 照常派发，输出两行 `capacity: memory not measured …` 和 `capacity: load not measured …`，`delegation.create` 的详情有 `unmeasured: ["memory","load"]`
- 两个会话同时新派，派完前已占用 9 个名额 → 只有一个成功，另一个被拒，信息含 `10 of delegate_max_workers (10) in use`
- 会话 A 已把 `C-9` 派给 `w1`，`w1` 还在做；会话 B 再派 `C-9` → 退出码 5，信息含 `already delegated to w1 by <A>`，事件表有 `delegation.refuse`、原因 `conflict`，派发记录不变
- 同上，但 `C-9` 已停滞 → 会话 B 照常重新派发
- 会话 A 自己把 `C-9` 改派给 `w2` → 照常派发
- 会话 B 和 A 同时第一次派 `C-9` → 一个成功，另一个退出码 5
- 会话 A 给有生效派发的 `C-9` 重新派发，进事务前那个派发被结束了 → 事务里按新增算，名额已满时拒绝，信息含 `in use`
