## 规则

**档案从哪来**：启动 worker 的工具（派发方）在 worker 会话的环境里设 `CANON_WORKER_PROFILE=<档案名>`，和 `CANON_SUBAGENT` 一起（D-125），写它启动 worker 用的档案（例如 Opus 级模型的档案）；两侧空白去掉，空值按没设。canon 不信命令进程自己的环境（会话里的命令可以改它），只信会话开始 hook 的进程环境：会话开始时宿主运行的 `canon brief` hook（BR-2024）读到这个变量，就在协调数据库里为这个会话（BR-2023 认出的 `<会话>`）记下档案，每个会话只记第一次，之后不改；事件表记 `worker.profile`。之后 canon 命令按执行者的会话查这条记录，命令环境里的 `CANON_WORKER_PROFILE` 一律不看。

**能设计的 worker**：worker（`agent:<会话>:<名字>`）的会话记下的档案在 main 上 `canon/config.yaml` 的 `design_profiles` 里（D-162）。`design_profiles` 是可选的字符串列表，默认空；不是字符串列表 → 配置错误，退出码 2（BR-2045）。名单每次都从当前 main 读，不从运行命令的 worktree 读：worker 在自己分支上把自己加进去不生效；名单删掉一个档案，从下一条命令起这个档案的 worker 就按普通 worker 处理。没有记录（会话开始时没设变量、hook 没装或没跑）→ 普通 worker。

能设计的 worker 和别的 worker 的区别：

1. **开新工作和续做**：BR-2498 对新建变更、修复变更和杂务的拒绝对它不成立，按 BR-2012、BR-2457 进行，新建的由它认领，没有派发记录，`work.start`、`chore.start` 的详情记 `worker_profile`。它还可以 `canon work start <C-n>` 认领没有生效派发、也没有活着的认领的打开变更（自己开过又放开的、换了会话要接着做的都这样接回）；有生效派发的变更仍只能是派给它的名字（BR-2498）。
2. **合入设计**：合入时 BR-2501 第 1 项只对下面这些路径照查：`canon/config.yaml`（防止把自己加进名单）、`canon/backlog.md`（负责人的顺序）、`canon/product.md` 和 `canon/releases/`（方向和发布范围，归负责人和主会话）。决策、规则、变更文件的两段、`canon/proposals/`、`design_paths` 列出的文件不查。第 2、4 项读派发记录：变更有生效的派发时照查；没有派发（它自己开的、接回的）时不适用。第 3 项（没回答的设计请求）照查。批量合入里每个成员按自己的合入者在合入时的档案和名单判断。

其余照 worker 的规则：不能 `canon work delegate`（BR-2497）、`take`、`unstall`（BR-2468），不能给评审意见定档和关闭（BR-2502）。它合入的规则和决策照常走合入后的规则评审。

**信任边界**：只防会话里的命令冒充，防不了本机上有意改协调数据库、或在会话开始 hook 运行之前自己调用 hook 的进程；这和 `CANON_SUBAGENT` 的信任程度一样（D-125），属于不正常的动作（D-54）。

## 例子

- main 的 `design_profiles: [sub-opus]`，worker 会话以 `CANON_SUBAGENT=w1`、`CANON_WORKER_PROFILE=sub-opus` 启动，会话开始 hook 记下 `sub-opus`；`agent:s7:w1` 运行 `canon work start --title "x" --owner-gate "none: …" --advances "none: …"` → 新建变更并认领，`work.start` 的详情有 `worker_profile: sub-opus`
- 同上，`canon chore start "整理脚本"` → 开始杂务
- 会话以 `CANON_WORKER_PROFILE=sub-sonnet` 启动 → `canon work start --title` 退出码 1，按 BR-2498
- 会话以 `sub-sonnet` 启动，命令写成 `CANON_WORKER_PROFILE=sub-opus canon work start --title "x"` → 仍按记下的 `sub-sonnet`，退出码 1
- 会话启动时没设变量，后来 `export CANON_WORKER_PROFILE=sub-opus` 再开工 → 没有记录，退出码 1
- 没配 `design_profiles` → 谁都按 BR-2498
- `w1`（`sub-opus`）在自己开的变更里写了决策和规则，`canon work land --finish` → 不因第 1 项拒绝，合入后照常排规则评审
- 同上，变更还改了 `canon/config.yaml` 把 `sub-sonnet` 加进 `design_profiles` → 按第 1 项拒绝，点名 `canon/config.yaml`
- 同上，改了 `canon/product.md` 或 `canon/backlog.md` → 按第 1 项拒绝
- `w2`（`sub-sonnet`）的变更改了规则的 `## 规则` → 按 BR-2501 第 1 项拒绝
- `C-9` 由 `agent:s1` 派给 `w1`（`sub-opus`），`w1` 改了契约清单里的规则 → 不因第 1 项拒绝；`agent:s1` 重新派发、代次 2 之后 `w1` 没接受新设计就合入 → 按第 4 项拒绝
- `w1`（`sub-opus`）开的 `C-12` 放开后，新会话 `agent:s9:w1`（也是 `sub-opus`）运行 `canon work start C-12` → 认领成功；`C-12` 被 `agent:s1` 派给 `w3` 之后再运行 → 退出码 1
- `w1`（`sub-opus`）运行 `canon work delegate C-12 --to w3` → 退出码 2
- `design_profiles` 删掉 `sub-opus` 合入 main 后，`w1` 再运行 `canon work start --title` → 退出码 1
- `design_profiles: sub-opus`（不是列表）→ 配置错误，退出码 2
