## 规则

一个变更有生效的派发（BR-2497，没有被 `take` 结束），在 main 上还没关闭（状态不是 `done` 或 `dropped`），同时满足下面两点时，它是**停滞**的（#255）：

1. 它没有仍然有效的认领：没有认领、认领过期，或持有认领的会话进程已经不在（BR-2100 的认法）；
2. 它的分支（`change/C-n` 或 `change/C-n-<名字>`）最后一次提交的时间，和这个变更最后一次 `canon work delegate`（新派发或重新派发）的时间，两者中较晚的那个，早于现在减去 `delegation_stall_minutes`（`canon/config.yaml`，单位分钟，大于 0，默认 60）。没有分支时只看派发时间。

停滞每次读的时候算，不存起来。显示在：

- `canon work status`：每个停滞的变更一行 `<C-n>: stalled: delegated to <worker>, no live worker and no commit since <时间>`，后面是最后一次提交的时间（没有分支时写 `no branch commit`）、worker 最后一次交接的 `--next`（有的话），以及设计负责人可以做的事：`canon work delegate <C-n> --to <name>` 重新派发，或 `canon work take <C-n>` 接手。`--json` 多一个 `stalled` 字段，列出同样的内容。
- `canon overview` 的 `## 等负责人` 一节（BR-2505）：每个停滞的变更一行，内容同上。
- `canon brief` 的整体进度摘要和计划步骤的状态：按 BR-2506、BR-2372、BR-2373、BR-2374 里写的停滞部分。

不自动重新派发，也不自动接手。

## 例子

- `C-5` 派给 `w1`，`w1` 认领后提交一次就退出（进程不在了），70 分钟没有新提交，`delegation_stall_minutes` 是默认的 60 → 停滞；`canon work status` 有 `C-5: stalled: delegated to w1, no live worker and no commit since …` 一行，写明 `canon work delegate C-5 --to <name>` 和 `canon work take C-5`
- 同上，只过了 30 分钟 → 不停滞
- 同上，`w1` 的进程还在，分支已经两小时没提交 → 不停滞
- `C-5` 是计划 `C-1` 的步骤 `A` 唯一的变更，`C-5` 停滞 → `canon plan status C-1` 的汇总行有 `停滞 1`，详情有 `停滞: A (C-5)`；`--json` 的 `stalled` 是 1、`working` 是 0
- 没有任何停滞的变更 → 计划的汇总行不出现“停滞”，和以前一样
- 设计负责人 `canon work take C-5` 之后 → 派发结束，不再算停滞
- `C-5` 已经合入、在 main 上是 `done`，派发记录还在，worker 进程不在、两小时没有提交 → 不停滞，`canon work status` 没有它的 `stalled` 一行
- `delegation_stall_minutes: 0` → `canon check` 报配置错误（必须大于 0）
