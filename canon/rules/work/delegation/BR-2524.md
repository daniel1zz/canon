## 规则

worker 不能改规则文件（BR-2501），要改规则文字时用整份文件提议，不写“旧句 → 新句”（D-135，#254）：

`canon rule propose <BR-n>` 在认领了变更的 worktree 里运行（没有认领的 worktree 里退出码 2）：把 main 上这条规则的文件原样复制到 `canon/proposals/<C-n>/<BR-n>.md`（`C-n` 是这个 worktree 认领的变更），在开头的 `---` 后面加一行 `proposed_from: <main 上这个文件的 blob 哈希>`，输出这个路径，退出码 0。之后 worker 直接编辑这份副本、随变更提交。main 上没有这条规则 → 退出码 3（新规则仍按 BR-2499 交回）；副本已经存在 → 退出码 5，不覆盖。

`canon work need-design` 的请求文字（BR-2499）后面附上这个变更在 worktree 里的每个提议文件路径。

`canon rule apply <C-n> [<BR-n> ...]` 把这个变更的提议写回规则：不给编号时是全部提议。worker 运行 → 退出码 1；变更还派给 worker（派发没被 `canon work take` 结束，BR-2500）→ 退出码 1，提示先收回；没有提议、或给的编号没有提议 → 退出码 3。每个提议的 `proposed_from` 和 main 上这条规则现在的 blob 比较，有任何一个不同 → 退出码 5，一个都不写，写明哪些规则在提议之后被 main 改过；都相同 → 每个提议去掉 `proposed_from` 那一行后原样写到这条规则在 main 上的路径（字节一致，包括结尾换行）、删掉提议文件（目录空了也删），对每条输出编号、路径和 `git diff` 的改动，记一条 `proposal.apply` 事件，退出码 0。写回后的规则照常走规则评审和证据门，不因来自提议而少任何检查。

## 例子

- worker 在 `C-5` 的 worktree 里 `canon rule propose BR-1` → `canon/proposals/C-5/BR-1.md` 是 main 上 `BR-1` 的全文，开头多一行 `proposed_from: <40 位哈希>`
- worker 把副本里的例子 `- A → B` 改成 `- A → C`、提交、`canon work land` → 不按 BR-2501 拒绝（提议文件不是设计文档）
- worker 再 `canon rule propose BR-1` → 退出码 5
- worker `canon rule apply C-5` → 退出码 1；设计负责人在派发结束前 `canon rule apply C-5` → 退出码 1
- 设计负责人 `canon work take C-5` 后 `canon rule apply C-5` → `BR-1` 的文件和副本去掉 `proposed_from` 后一字不差，例子是 `- A → C`，输出含 `+- A → C`，提议文件没了
- 提议之后 main 上的 `BR-1` 被别的变更改过 → `canon rule apply C-5` 退出码 5，信息含 `BR-1 changed on main since proposed`，规则和提议都不动
