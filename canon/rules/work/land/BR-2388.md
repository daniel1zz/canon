## 规则

合入因 `canon check` 被拒绝时（原因 `check`），`land.refuse` 事件记下这次的内容树（变更分支去掉关闭提交后的树）和 rebase 到的 main 提交。之后 `canon work land` 在入队之前（检查 worktree 干净之后、做关闭提交之前，所以也在 `lessons` 检查（BR-2161）之前，不打印重叠提示（BR-2062））查这个变更最近的一个合入事件（`land.ok`、`land.refuse`、`land.killed`、`land.lost`、`land.interrupt`）：它是原因 `check` 的拒绝，并且现在的内容树和 main 的提交都和它记下的相同，就当场重跑一遍 `canon check`（测试报告、其他分支上的变更、main 的待办清单都按现在的读）。还有发现 → 不入队，立即以原因 `check`、退出码 1 拒绝，信息写明和哪个时间、哪个事件的拒绝内容相同、`canon check` 仍有发现，并列出现在的发现；记一条 `land.refuse`，同样记下内容树和 main，带上现在的发现（BR-2094），带 `repeat_of`：最近那次拒绝本身带 `repeat_of` 时沿用它，所以一连串重复拒绝都指向最初那次。没有发现了（例如之后用 `canon work test` 补上了测试报告），或者当场跑不了 `canon check` → 照常入队，不打印提示，由轮到它时的完整检查决定。带 `repeat_of` 的拒绝不算这项检查新的运行和拒绝（BR-2067、BR-2068 的检查统计不计它，BR-2095 按发现种类的拆分也不计）；`canon stats --since` 的并发摘要（BR-2155）按原因数拒绝时照常算它，因为它是会话实际看到的一次拒绝。

只对 `check` 这样做：来源核对（`source`）要抓取网页，措辞判断（`review`，BR-2239）要调用模型，版本检查（`release`）要读负责人的回答，同样的内容再跑一次结果可能不同，照常入队；冲突、floor、超时、有未提交的改动、main 前移等也照常入队。

## 例子

- `C-1` 合入因 `canon check` 报 `ref-dangling` 被拒，什么都不改再 `canon work land` → 不入队，退出码 1，信息含 `nothing changed since` 和现在的发现，事件表多一条原因 `check`、带 `repeat_of` 的 `land.refuse`
- 第二次被立即拒绝之后，再合入一次（仍然什么都没变）→ 仍然立即拒绝，`repeat_of` 仍指向最初那次拒绝
- 同样被拒之后，内容没改，但被引用的变更出现在了一个变更分支上（`canon check` 不再报它）→ 照常入队
- 同样被拒之后，改了一个文件并提交 → 照常入队
- 同样被拒之后，main 前移了一个提交（内容没改）→ 照常入队
- 合入因 floor 失败被拒（原因 `floor`），什么都不改再合入 → 照常入队
- 合入因措辞判断被拒（原因 `review`），什么都不改再合入 → 照常入队，措辞判断再跑一次
- 被拒之后又合入成功过一次（最近的事件是 `land.ok`）→ 照常入队
- 最初一次 `check` 拒绝之后又立即重复拒绝了两次 → `canon stats` 里 `check` 只算 1 次拒绝；并发摘要的 `refused` 里 `check` 是 3
