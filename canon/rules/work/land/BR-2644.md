## 规则

main 有「没通过后台测试」的记录（BR-2220，`canon work due` 的 `red-main`）时，`canon work land` 和 `canon chore land` 在工作树干净、有 floor 之后，排队和其余检查之前拒绝，原因 `red-main`，退出码 1，写一条 `land.refuse` 事件，不排队，除非下面任一条成立：

- 这次合入的就是修复变更（`canon work start --fix-main` 开的、记在这条记录上的那个变更）；
- 修复变更已经合入（它合入的提交在 main 上，带不带 `--finish` 都算，同 BR-2221）：之后由下一次后台测试判断，合入不再等；
- main 上已合入的 `canon/config.yaml` 里 `policies.landing.pause_on_red_main` 是 `false`（默认 `true`，D-164）。读的是 main 上的配置，不是这个变更自己的树，所以变更不能给自己关掉；main 上的配置读不了时照样拒绝，信息写明读不了。

拒绝信息写明：main 从哪个提交开始失败、现在失败在哪个提交、失败的测试文件（没有报告或在测试之前就失败时照实写）、日志路径；有修复变更时写它的编号和「等它合入」，没有时写 `canon work start --fix-main`；最后写怎样关掉这条。

重跑之后通过的测试文件不会让 main 有这条记录（BR-2534），所以偶发失败不会暂停合入；负载达到重步骤上限时的第 1、2 次失败也不会（BR-2666），所以机器过载不会暂停合入。自动撤回（BR-2535）直接移动 main，不经过合入，不受这条影响。

这样 main 坏着时不会有别的工作再叠上去，修复也不用和别人的合入抢（负责人 2026-11-23：选了「main 红时暂停落地」，并答「默认打开，所有项目一样」）。

## 例子

- main 从 `9564c3237` 起没通过，没有修复变更，`C-1181` 合入 → 退出码 1，原因 `red-main`，信息含 `since 9564c3237`、失败的测试文件和 `canon work start --fix-main`；没有排队
- 同上，`C-1187` 是用 `--fix-main` 开的修复变更，它合入 → 照常合入
- `C-1187` 已经合入、后台测试还没跑完，`C-1181` 合入 → 照常合入
- 修复变更 `C-1187` 还没合入，`C-1181` 合入 → 拒绝，信息写 `the fix is C-1187, not landed yet`
- main 上 `policies: {landing: {pause_on_red_main: false}}` → 照常合入，只有原来的提示
- 变更自己的分支把 `pause_on_red_main` 改成 `false` → 仍按 main 上的默认拒绝
- 杂务 `canon chore land` → 同样拒绝
