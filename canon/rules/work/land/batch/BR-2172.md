---
id: BR-2172
title: 轮到的合入者把紧跟在后面等着的合入一起测，只跑一次 floor
status: active
---

## 规则

`land_batch_max` 大于 1 或者是 `all` 时（`floor_timing` 为 `after` 时不一起测，一个一个合入，BR-2218），合入者轮到并 rebase 到 main 之后，按排队顺序取紧跟在它后面的条目一起测，连它自己最多 `land_batch_max` 个（`all` 表示不设上限，队列里等着的都取）；在它持有轮次时拿回保留位置的条目（BR-2177）排在它前面，最先被取（BR-2178）。只取这样的条目：还在等、由支持一起测的 canon 排进队列（旧版本的合入者看不懂“已在别人的批里合入”，永远不拉进来）、合入者进程还在而且心跳没过期、worktree 干净；遇到第一个不符合的就停，不越过它取后面的。在一个临时 worktree 里把这些变更按顺序逐个 rebase 到前一个之上，组成一条提交链；某个变更在链上 rebase 冲突，只有它离开这一批、回到队列等自己的轮次，照常处理（BR-2015、BR-2153），后面的变更接着加到它前面那个之上（BR-2173）。

每个变更自己的步骤（`canon check`、来源核对、规则评审、`before_land`）在它那一段的链顶上跑，`CANON_BASE` 是它下面那个提交；这些步骤在 floor 之前跑，领头的先跑，成员的在它加到链上时跑（单独合入也是这个顺序，BR-2014）；floor 只在整条链的顶上跑一次（整批只改 `floor_skip_paths` 时照样跳过，BR-2164）。全部通过、每个成员的 worktree 仍是加入时的 HEAD 并且干净、合入者仍持有轮次 → 领头在一个事务里把全部成员锁定（有一个已经不在这一批里就一个都不锁，回到 BR-2173 的处理）；锁定之后成员被信号终止也不再放弃自己的条目、不撤回关闭提交，因为它马上就在 main 上了；main 用比较并交换移到链顶（移动失败就解锁，成员回到队列照常等），每个变更保留自己的提交，按排队顺序排在 main 上。每个变更各记一条 `land.ok`（成员的带 `batched_by`），各跑一次 `after_land`，`CANON_BASE` 是它下面那个提交（领头的是合入前的 main），`CANON_HEAD` 是它在 main 上的提交。成员自己的 `canon work land` 看到自己已合入后，把自己的分支从加入时的 HEAD 比较并交换地移到它在 main 上的那个提交，文件跟着更新，再照常收尾（`--finish` 释放认领）。一批里中间的提交没有单独跑 floor，只有成为 main 的链顶跑过（BR-2106）。成员在这一批里时既不超时，也不做排队冲突预测。`canon stats` 里成员的成功不算 floor 的运行。

## 例子

- `land_batch_max: 3`，A 轮到时 B 正在后面等，两者改不同的文件 → floor 只跑 1 次，两个都合入；main 的顶是 B 的提交，A 的提交在它下面；B 的 worktree 的 HEAD 变成 main，里面也有 A 的文件
- 同上并且都加了 `--finish` → 两个变更在 main 上都是 `status: done`，两个认领都释放
- A 和 B 改了 `app.txt` 的同一行 → B 不进这一批；A 单独合入，floor 跑 1 次；B 轮到时以 `conflict` 被拒
- `land_batch_max: all`，A 领头时后面有 4 个在等 → 5 个一起测，floor 只跑 1 次，全部合入
- B 已被锁定，这时 B 的合入者收到 SIGTERM → B 的条目不变成失败，A 移动 main 后 B 记为已合入
- `land_batch_max: 2`，A 后面 B、C 都在等 → 只取 B，C 等自己的轮次
- 排在 A 后面的是旧版本 canon 排进来的条目 → 不进这一批，它后面的也不进
- 没写 `land_batch_max`（默认 1）→ A、B 各自合入，floor 跑 2 次
