---
id: BR-2191
title: 一起测合入后成员的分支或文件跟不上时保持原样，并提示 rebase 到 main
status: active
---

## 规则

成员的 `canon work land` 看到领头已经把它在批里合入（BR-2172）后，把自己的分支从加入时的 HEAD 比较并交换地移到它在 main 上的提交，索引和文件跟着更新（在 git 的索引锁下一步做完，BR-2258）。未提交的改动只在不需要更新的文件上时照常移动，改动保留。下面几种情况下跟不上，就保持原样、不丢任何东西，照常收尾（这次合入算成功，`--finish` 照样释放认领），并打印提示，写明用 `git rebase main` 追上：

- 分支在加入之后又有了新提交（HEAD 不再是加入时的提交）：分支和文件都不动，提示 `branch moved after it joined the batch`。
- worktree 里有未提交的改动，正好落在要更新的文件上：分支移回加入时的提交，文件和改动都保留，提示 `local edits keep this worktree's files`。
- 别的 git 命令占着这个 worktree 的 `index.lock`，或者复制、替换索引出错（BR-2258）：分支和文件都不动，提示写明原因。替换索引出错后撤销本身也失败时不算保持原样：按 BR-2258 如实写明文件或 HEAD 现在在哪里，仍提示 `git rebase main`。

## 例子

- B 在 A 的批里被合入，这之前 B 的 worktree 又提交了 `late.txt` → B 的 `land` 结果是已合入，HEAD 仍是带 `late.txt` 的那个提交，输出里有 `git rebase main`
- B 在 A 的批里被合入，main 上改过的 `app.txt` 在 B 的 worktree 里有未提交的改动 → B 的 HEAD 仍是加入时的提交，`app.txt` 里还是那份改动，输出里有 `git rebase main`
- B 在 A 的批里被合入，worktree 没变 → HEAD 变成它在 main 上的提交（BR-2172）
- B 在 A 的批里被合入，B 的 worktree 里 `b.txt` 有未提交的改动，`b.txt` 在加入时的提交和 main 上的提交里一样 → HEAD 变成它在 main 上的提交，`b.txt` 的改动还在
- B 在 A 的批里被合入，跟上 main 时替换索引出错、撤销也没能把文件放回去 → 这次合入照样算成功，输出写明文件现在是 main 上提交的内容、`git status` 会显示它们，并提示 `git rebase main`，不说分支保持原样
- B 在 A 的批里被合入，跟上 main 时替换索引出错、撤销成功 → HEAD 和文件仍是加入时的提交，输出写明原因、说分支保持原样，并提示 `git rebase main`
