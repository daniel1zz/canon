## 规则

合入者是 worker（`agent:<会话>:<名字>`，BR-2023）时，`canon work land` 和 `canon chore land` 在重新基于 main 之后、合入之前，按下面几项检查候选（合入的 base 到候选提交的改动），有一项不过就拒绝合入，退出码 1，main 不动，提示写明哪一项、哪些文件或规则，并写明“交回设计负责人：canon work need-design（BR-2499），或由设计负责人 canon work take（BR-2500）”：

1. **改了设计文档**：新增、修改、删除或改名了设计文档（`work/delegation` 的术语表：决策、规则、`product.md`、发布范围、`config.yaml`、`backlog.md`、`design_paths` 列出的路径），或者改了变更文件的 `## 为什么`、`## 要改什么`。例外只有激活：变更 `rules:` 列出的、main 上是规划中的规则，只把 `status: planned` 改成 `active`、删掉 `will_amend`，其他文字一个字都不变。规则文字要随实现改（包括 `will_amend` 的目标），就交回设计负责人。
2. **派发后设计变了**：变更 `rules:` 列出的规则和它们引用的决策，在设计版本（BR-2497）上和在当前 main 上的文字不一样（不计空白），也就是有人在派发之后改了这份设计。设计负责人重新派发（BR-2497）之后才放行。
3. **还有没回答的设计请求**：这个 worker 为这个变更提的设计请求（BR-2499）有还是 `pending` 的。

按 D-128。`design_paths` 和设计文档的范围从 main（合入的 base）读，不从候选读：候选改了它们也不影响这次检查。没有派发的杂务只查第 1 项。

不是 worker 的合入者不做这些检查。

生效时 BR-2458 的“不检查业务文件边界”改成：不是 worker 的合入者不检查；worker 合入杂务时按 BR-2501 第 1 项检查设计文档。

## 例子

- `agent:s7:w1` 合入 `C-9`，候选改了 `canon/decisions/D-40.md` → 退出码 1，提示点名 `D-40` 和交回的两个办法
- 同上，候选只把 `BR-50` 的 `status: planned` 改成 `active` → 放行
- 同上，候选把 `BR-50` 改成 `active` 并改了一句例子 → 退出码 1，点名 `BR-50`
- 同上，候选激活 `BR-50`，它的 `will_amend: [BR-30]`，候选改了 `BR-30` → 退出码 1，点名 `BR-30`
- 派发之后 `agent:s1` 在 main 上改了 `BR-50` 的规则段 → `w1` 合入退出码 1，写明设计版本以来 `BR-50` 变了；`agent:s1` 重新派发后 `w1` 再合入 → 放行
- `w1` 有一个 `pending` 的 `#3` → 退出码 1，点名 `#3`
- 候选在 `canon/config.yaml` 里把 `design_paths` 删掉，同时改了 `docs/DESIGN.md` → 退出码 1，点名两个文件（范围按 main 读）
- 候选改了 `C-9.md` 的 `## 进展` 段 → 放行；改了 `## 要改什么` → 退出码 1
- 主会话 `agent:s1` 合入同样的候选 → 不做这些检查
- `agent:s7:w1` 合入一个杂务，改了 `canon/rules/x/BR-1.md` → 退出码 1
