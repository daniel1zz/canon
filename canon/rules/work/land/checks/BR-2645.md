## 规则

`canon work land` 和 `canon chore land` 在 rebase 之后、`canon check` 之前，比较这个分支和 main 从分叉点（两者的 merge-base）以来各自改了什么。main 没动过（分叉点就是 main）时什么都不做。下面任一条成立就算有重叠：

- 同一个路径两边都改了；
- 项目的 `test_select_command` 给 main 那边改的路径和给这个分支改的路径挑出了同一个测试文件。

有重叠时，`test_select_command` 给两边都挑出的测试文件（只给 main 那边挑出的不跑：按它的判断，这个分支的改动不影响它们，D-168），不管有没有报告，都在要合入的树上用 `test_command` 跑，先等机器负载（同其余合入测试），按 BR-2302 同时跑几个，同时跑时失败的单独重跑一次（BR-2303）。只有路径重叠、没有两边都挑出的测试文件时什么都不跑。合入先写一行，说明为什么要跑：哪些路径两边都改了、哪些测试文件两边共用（各最多列 5 个），以及要跑几个文件。有一个文件失败就拒绝，原因 `check`，退出码 1，信息写明失败的文件、它是因为 main 新进的改动被挑出来的、怎样在本地重跑，再附上它的输出末尾。

没有重叠时什么都不跑，合入照常（D-137：普通情况普通处理）。项目没有 `test_select_command` 或 `test_command` 时也不跑：canon 不读源码判断哪些测试相关（D-64）。`test_select_command` 自己出错时拒绝，退出码 4。

main 上已合入的 `canon/config.yaml` 里 `policies.landing.cross_tests` 是 `false` 时整步跳过（默认 `true`，D-164）。读的是 main 上的配置，不是这个变更自己的树，所以变更不能给自己关掉。

两个变更各自在自己的树上通过，合在一起才坏，这一步在合入时就挡住它，而不是等后台测试把 main 测红（负责人 2026-11-23 经对面会话转述，选了「canon 挑测试更全」）。

## 例子

- 分支改了 `src/a.ts`，main 分叉以来改了 `src/a.ts` 和 `src/b.ts`，选测脚本给 main 那边挑出 `a.test.ts`、`b.test.ts`，给分支挑出 `a.test.ts` → 合入写 `both changed src/a.ts`，在合并后的树上只跑 `a.test.ts`
- 分支改 `src/a.ts`，main 改 `src/b.ts`，脚本给两边都挑出 `shared.test.ts`，给 main 那边还挑出 `b.test.ts` → 写 `test_select_command picks shared.test.ts for both`，只跑 `shared.test.ts`
- 两边都改了 `docs/x.md`，脚本给哪边都不挑测试 → 不跑，照常合入
- 分支改 `src/a.ts`，main 改 `docs/x.md`，没有共同路径，也没有共同测试 → 不跑，照常合入
- 分支从当前 main 分出来，main 没动过 → 不跑
- `b.test.ts` 在合并后的树上失败 → 退出码 1，原因 `check`，信息含 `b.test.ts` 和 `canon work test b.test.ts`
- main 上 `policies: {landing: {cross_tests: false}}` → 不跑；变更自己的分支改成 `false` → 仍按 main 上的默认跑
- 项目没有 `test_select_command` → 不跑
