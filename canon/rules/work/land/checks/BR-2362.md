id: BR-2362
title: 合入新增的规则或决策编号，已被分配给别的变更的 worktree 时，合入被拒
status: active
---

## 规则

`canon work land` 合入的改动里，每个“新增”的规则或决策编号，都要查协调数据库里它的分配记录（`canon rule new`、`canon decision new` 分配编号时写的 `id.allocate` 事件，记着分配时所在的 worktree）。“新增”指：被合入的树里有一个规则或决策文件，它的编号在 main 上没有任何规则或决策文件用；同一个编号的文件只是换了路径（main 上删掉一个、合入里在别处新增，编号相同）不算新增。

判断只看分配记录里的 worktree：

- 分配在这次合入的变更自己的 worktree → 通过。
- 分配在主 checkout → 通过。主 checkout 里分配的编号常被会话带进变更里合入，所以不算“别的变更”；也不比较是哪个会话分配的，因为 worktree 才是记录里稳定的字段。
- 没有分配记录（旧文档、协调数据库被重置、手写的编号，或记录里没有 worktree）→ 通过。
- 分配在别的 worktree → 退出码 1，原因是 `check`，main 不动。消息写出这个编号、持有它的 worktree（路径形如 `<仓库>.worktrees/C-n` 时同时写出 `C-n`），并说明用 `canon rule new` 或 `canon decision new` 重新分配一个编号。

一起测的合入，每个成员各自判断，用它自己的 worktree。

依据：`canon check` 只看被合入的树，查不出别的变更已经分配、还没合入的编号；先合入的赢，后合入的那个变更分配到的编号被拒为 `id-duplicate`、只能改号。在先合入的变更手写了别人的编号时就拒绝它，被拒的是造成冲突的那一方（#140）。

## 例子

- 变更 `C-5` 的 worktree 里 `canon rule new` 分配了 `BR-501` 并合入 → 通过
- 变更 `C-5` 合入手写的规则 `BR-501`，而 `BR-501` 是在 `C-6` 的 worktree 里分配的 → 退出码 1，原因 `check`，消息含 `BR-501` 和 `C-6`，说明用 `canon rule new` 重新分配
- 同样的情形，新增的是决策 `D-90`，分配在别的 worktree → 退出码 1，消息含 `D-90`，说明用 `canon decision new`
- 变更合入的 `BR-501` 是在主 checkout 里分配的 → 通过
- 变更合入手写的 `BR-501`，协调数据库里没有 `BR-501` 的分配记录 → 通过
- 变更把 main 上的 `BR-7` 换了目录（文件移动，编号不变），而 `BR-7` 的分配记录在别的 worktree → 通过，因为 `BR-7` 不是新增
- 变更只改了 main 上已有的 `BR-7` 的文字 → 不查，通过
