id: BR-2308
title: canon work status 列出没有结果的合入，进程不在的标 interrupted
status: active
---

## 规则

`canon work status`（和 `--json`）列出还没有结果的合入：每个 worktree 只看最近一条 `land.start`（BR-2307），它之后没有这次合入的终结事件，而且 worktree 目录还在时，按它记下的进程分三种：进程还在 → `running`；进程已经不在（没有这个 pid，或 pid 现在属于启动时间不同的进程，D-11）并且这次合入的分支最新提交已经在 main 上（它在队列里有过条目、没有 rebase 在进行）→ `landed`：只写 pid、开始时间、“合入已经到了 main，没有记录结果”和下一步 `canon work land`，不算 interrupted，不列遗留物；进程已经不在而提交不在 main 上 → `interrupted`，写明 pid、开始时间、“没有记录合入结果”，并点出留下的东西（这个进程的排队条目、分支上的关闭提交、做到一半的 rebase 和对应的 `git rebase --abort`）和下一步命令 `canon work land`；读不到进程表或没记下进程 → `unknown`，不说被杀掉。排队条目的进程已经不在时，队列里的那一行也标 `(lander process gone)`。有终结事件的合入不列。`status` 不改任何东西，只有判断认领状态时第一次发现认领失效会写一条事件（BR-2360）。

## 例子

- 合入进程被 `kill -9`，事件表只到 `land.turn` → `status` 的队列里是 `landing ... (lander process gone)`，另有一行 `interrupted`，写着 pid 和“没有记录合入结果”
- 合入进程被 `kill -9`，那时还在做关闭提交（没有条目）→ `interrupted`，说明分支上有关闭提交
- 合入正在 floor 里（进程还在）→ `running`，不报被杀掉
- 合入被 `kill -9`，那时 main 已经移到分支的最新提交（关闭提交在 main 上）、还没有 `land.ok` → `landed`，不是 `interrupted`，没有“left behind”
- 合入以 `land.refuse` 结束 → 不列
- 合入被 `kill -9` 之后，这个 worktree 又合入成功了（有 `land.ok`）→ 不列
- 合入被 `kill -9` 之后 worktree 已经被 `canon work clean` 清掉 → 不列
- 读不到进程表 → `unknown`
