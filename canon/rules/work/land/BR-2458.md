## 规则

从已认领杂务的工作树运行 `canon chore land`，使用业务变更相同的队列、检查、floor 配置时机、main 比较并交换和后台结果；不因修改代码、规则、决策或配置路径而拒绝，也不因杂务身份跳过原检查。成功释放本会话的认领和 handoff，不创建 Change 文档或关闭文档提交，输出工作已完成。没有杂务认领以退出码 2 拒绝，不匿名排队。失败、超时、后台跟随和中断沿用共享合入要求。

通用 work 命令按 D-100 的身份处理杂务的交接、状态、测试、预评审、接手、解锁、后台结果、清理及归档；brief 显示杂务身份与 handoff，不要求读取不存在的文档。杂务改动文档仍进入合入后评审。执行证据继续按业务 Change 的规则检查，不因杂务身份绕过。

## 例子

- 杂务提交代码后合入 → main 包含修改，无新增 Change 文档或关闭提交，认领和 handoff 被释放
- floor 失败 → 退出码 1，main 不动，工作与认领保留
- 杂务改有效的 active 规则 → 不因路径拒绝，仍接受检查与合入后评审
- 杂务伪造其他 Change 的 passes → 原执行证据检查拒绝，main 不动
- 杂务改 active 规则的行为并合入 → 杂务没有关闭提交，不计算也不新增执行证据，这条规则已有的通过记录保持原样
- 杂务和业务变更同时排队，两种身份分别领头 → 每个成员仍执行自己的检查、关联自己的身份，不互相覆盖
- 在业务变更或未认领的工作树运行 chore land → 退出码 2，无杂务排队
- 杂务停下并交接 → 下一会话 brief 显示下一步，不输出 canon show 杂务身份
- `canon work status` → 按 BR-2192 列出未完成的杂务
- 未完成的杂务（工作树干净、没有自己的提交）遇到 `canon work clean` → 保留，理由是杂务还没完成合入
- `canon work drop <杂务身份>` 碰到未合入的提交或未提交文件 → 先归档到 refs/canon/archive 再删除
- 子 agent 的杂务连续被拒 → 按 BR-2454 停下，主会话按 BR-2455 放行
