## 规则

`canon work land --finish` 让 main 移动、关闭变更或完成 chore（BR-2018）之后，从主 checkout 在后台启动 `canon work clean <变更> --after-landing`（自己的进程组，输出写到协调数据库目录下的 `logs/clean-<变更>.log`）。合入的输出写一行 `<变更>'s worktree is removed in the background once nothing runs inside it, when canon work clean would remove it (log: <路径>)`，并说明 `canon work after-land --wait <变更>` 会报告它。启动不了时，合入照样成功，输出说明没删以及之后怎样手动删。

`canon update` 和 `canon uninstall` 从主 checkout 合入自己的 chore，worktree 里没有它们的进程，所以不在后台删，而是在合入的同一个进程里立刻按 BR-2019 删掉，留下时输出 `kept <路径>: <原因>`。

`--after-landing` 只删这一个 worktree，删不删按 BR-2019 的条件判断。合入的进程和运行它的 shell 在退出前都还在 worktree 里，所以只要留下的唯一原因是有进程在里面（按 BR-2019，这时不删），就再试，每次都重新按 BR-2019 判断：第一次立刻试，之后依次隔 1、2、4、8、15、30、30、30 秒再试，最多试 9 次，等待一共 120 秒；留下的原因是别的（有未提交的改动、有提交不在 main 上、被认领等），或者最后一次仍有进程在里面，就留下这个 worktree，输出原因；因为进程而留下的，还写上 `run canon work clean <变更> once you have left it`。不管怎样结束，最后一行都是 `clean: done`。

`canon work after-land --wait <变更>`（不写变更时取最近一次开始的删除）也等这次删除结束（等待的时限、超时后的输出和退出码按 BR-2167），结束后输出 `removal of the landed worktree (log: <路径>): finished`，下面列出删掉或留下的那几行。

## 例子

- 在一次性的 shell 里 `land --finish` 合入 C-1 → 输出含 `C-1's worktree is removed in the background`；之后 `canon work after-land --wait C-1` 输出含 `removed <C-1 的 worktree>`，目录已经不在
- 合入后有一个进程在 C-2 的 worktree 里，1 秒后退出 → 等它退出后删掉
- 有一个 `zsh` 一直停在 C-3 的 worktree 里 → 第 9 次试过（约 120 秒后）仍在，留下，输出含 `kept <路径>: in use by` 和 `run canon work clean C-3 once you have left it`
- C-4 合入后 worktree 里多了一个没提交的文件 → 立刻留下，原因 `uncommitted changes`，不等待
- `canon update` 合入 → 输出结束时它的 chore worktree 已经删掉，`git worktree list` 只剩主 checkout
