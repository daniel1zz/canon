## 规则

`canon work land` 在工作树干净之后、查重复拒绝（BR-2388）和排队之前，把只看分支内容和协调数据就能判定的拒绝原因一起算完：新文档缺声明字段（BR-2624）；带 `--finish` 时再加变更文件缺失、`## 教训` 没填或重复（BR-2161）、`owner_gate` 没批准（BR-2616）。各项的判定和单独报出时的文字按各自的规则，不因合在一起而改变。

- 一项都没有 → 照常往下走。
- 只有一项 → 拒绝，原因和信息与那条规则单独报出时相同。
- 有几项 → 一次拒绝，退出码 1，信息第一行写有几项要改，之后每项一行，前面是序号和方括号里的原因；`land.refuse` 事件的原因是第一项的原因，详情的 `refusals` 按顺序列出每一项的原因。
- 有拒绝、而且带 `--finish` 时，再在当前分支（还没 rebase 到 main）上跑一次 `canon check`，有发现就在信息后面加一段 note，最多列 20 条，写明 rebase 之后还会再查。这些发现只是提示，不单独成为拒绝：rebase 到 main 之后结果可能不同，真正的拒绝仍由排队之后的检查决定。没有别的拒绝时不跑这一次检查，不给每次合入多加时间。

这样一次合入就能看到全部要改的地方，不用改一项、合一次、再看到下一项（负责人 2026-11-23：「canon的一些约束是给你兜底的，而不应该变成卡住你的上限」）。

## 例子

- `--finish`，`## 教训` 没填、`owner_gate` 没批准 → 一次拒绝，信息开头 `2 things to fix before this landing can go on:`，下面 `1. [lessons] …`、`2. [owner-gate] …`；事件原因 `lessons`，`refusals` 是 `lessons`、`owner-gate`；不跑相关测试，不排队
- 同上，分支上还有一个指向不存在文档的引用 → 信息后面多一段 note，列出 `canon check` 的这条发现
- `--finish`，只有 `owner_gate` 没批准 → 拒绝，原因 `owner-gate`，信息和 BR-2616 单独报出时相同，没有 note
- 不带 `--finish`，`## 教训` 没填 → 不算拒绝，照常合入（BR-2161 只在关闭时要求）
- 什么都不缺 → 不额外跑 `canon check`，照常排队
