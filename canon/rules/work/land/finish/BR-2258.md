## 规则

canon 在一个 worktree 里移动它检出的分支、并让索引和文件跟着变的两处（撤回关闭提交，BR-2018；一起测的成员跟上它在 main 上的提交，BR-2172、BR-2191），都先按 git 的约定以独占方式建这个 worktree 的 `index.lock`，持锁时比较并交换地移动分支、更新索引和文件，做完再删锁（D-39）。所以这期间会话里的 `git commit`、`git add` 被 git 以 `index.lock` 已存在拒绝，不会把旧的索引提交到新的 HEAD 上：撤回之后 HEAD 和文件都是 `open`，成员跟上之后 HEAD 里有这一批带来的文件。

`index.lock` 已被别的 git 命令占着时最多等 2 秒；还占着就不移动分支、不动索引和文件，按各自的规则说明没做成（撤回：`was not reopened`，原因写明 `index.lock`；成员：分支保持原样，提示 `git rebase main`）。canon 只删自己建的锁。

复制或替换索引出错（例如磁盘满）时同样不做成：索引在移动分支之前复制，复制失败就什么都不动；替换失败就把文件和分支都移回去，HEAD、索引、文件都回到移动前，按上面同样的方式说明，原因写明出错信息。撤销本身也没做成时如实说明，不说保持原样：文件放不回去（例如期间有编辑器直接改了文件）就写明 `the files could not be put back`，文件留着目标提交的内容，`git status` 把它们显示为未提交的改动，编辑保留；HEAD 移不回去就写明 HEAD 和索引现在各在哪个提交。未提交的改动挡住文件跟着变、把 HEAD 移回去又失败时也一样，写明 HEAD 现在在哪个提交，不说分支保持原样。

## 例子

- 撤回关闭提交、分支刚移到关闭提交之前的那一刻，会话运行 `git commit -qam fix` → 这个提交以 `index.lock` 已存在失败；撤回成功，HEAD 是关闭提交之前的提交，HEAD 里变更是 `open`，变更文件没有未提交的改动，会话改的文件仍是未提交的改动
- 撤回时 worktree 的 `index.lock` 一直存在（别的 git 命令还在跑）→ 不撤回，HEAD 仍是关闭提交，没有未提交的改动，输出 `was not reopened` 并写明 `index.lock`；那个锁文件还在
- 一起测的成员 B 跟上 main、分支刚移到它在 main 上的提交的那一刻，B 的会话运行 `git commit -qam fix` → 这个提交失败；B 的 HEAD 是它在 main 上的提交，里面有领头带来的 `a.txt`，B 对 `b.txt`（不是 `a.txt`，两边内容一样）的未提交修改还在
- 没有别的 git 命令占着锁 → 和以前一样一步做完，没有多等
- 撤回时复制索引出错，或者替换索引出错（`ENOSPC`）→ HEAD 仍是关闭提交，变更文件仍是 `done`，没有未提交的改动，`index.lock` 已删，结果写明出错信息
- 撤回时替换索引出错（`EIO`），而且这期间变更文件被编辑器直接改过 → HEAD 仍是关闭提交，结果写明 `the files could not be put back`，不写 `left as they were`，编辑还在
- 撤回时变更文件有未提交的改动（文件跟不过去），把 HEAD 移回关闭提交又失败 → 结果写明 `HEAD could not be moved back` 和 HEAD 现在是关闭提交之前的提交，不写 `left as they were`，改动还在
