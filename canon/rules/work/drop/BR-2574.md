## 规则

一个变更有生效的派发（BR-2497）时，放弃它的两个命令都同时结束这条派发，和设计负责人 `canon work take` 结束派发的效果一样（派发记录写上结束时间，BR-2500），并记一条 `delegation.end` 事件（含是哪个命令结束的）：

- `canon work drop <C-n>` 成功删除 worktree 和分支之后（BR-2064、BR-2102）；拒绝或失败、什么都没删时不结束。包括只在分支上的变更。
- `canon change drop <C-n>` 把变更文件改成 `dropped` 之后；拒绝时不结束。

派发结束后它不再算停滞（BR-2522）、不占派发名额（BR-2526）；以后再 `canon work delegate` 照常是新的一代。没有派发、或派发已经结束时，放弃照旧，不写 `delegation.end`。

在这条规则之前放弃的变更，派发没有结束，按 BR-2571 由 `drop.done` 事件算成 `dropped`，同样不算停滞。

## 例子

- `C-671` 只在分支上，派给 `w1`，`canon work drop C-671` 成功 → 派发结束，`canon work status` 不再列它的派发，`canon work due` 没有 `stalled:C-671`，事件表有 `delegation.end`
- `canon work drop C-5` 因为 worktree 里有进程被拒（退出码 5）→ 派发不变，没有 `delegation.end`
- main 上的 `C-6` 派给 `w2`，`canon change drop C-6` → 文件是 `dropped`，派发结束
- `C-7` 没有派发，`canon work drop C-7` → 照常放弃，没有 `delegation.end`
- 旧数据：`C-8` 在这条规则之前已经 `canon work drop`，派发还开着 → 主状态 `dropped`，不算停滞
