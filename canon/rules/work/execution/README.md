# 执行记录（work/execution）

一次执行就是一个变更（D-32）：变更在 `rules:` 里列出它要执行的规则，它的合入改了行为哈希的规则没列出也算，加 `--finish` 合入时，有证据的规则由关闭提交写成“规则编号 → 行为哈希、方式”的通过记录；没有证据的不写记录，照常合入，以待重新执行进 main，`canon work due` 提醒到有人执行它为止（D-141）。规则的执行状态不靠手写，由当前规则的行为哈希和各个已完成变更的通过记录算出；先合后测（`floor_timing: after`，D-31）时还要等 main 的后台测试覆盖到这条记录。这里只说明那一次执行验证过，不宣称规则和代码完全一致。

## 业务

- **执行证据**：关闭变更时它要执行的规则怎样找证据、证据怎么算，没有证据时怎样记下和提醒。

## 术语

- **要执行的规则**：变更 `rules:` 里列出的、或者变更的合入改了行为哈希的，合入后是生效的、而且当前行为哈希没有别的已完成变更的通过记录的规则（BR-2241）。
- **行为哈希**：规则 `## 规则` 和 `## 例子` 两段算出的哈希（BR-2236）。
- **通过记录**：已完成变更 front matter `passes:` 里的一项，规则编号 → 行为哈希和方式（BR-2237）。
- **方式**：`test`（变更改了点名它的测试）、`acceptance`（`## 验收` 里的一行）、`migration`（迁移时已有测试）；后面带 `wording` 的是只改了 `## 规则` 段、沿用上一条记录方式的记录，合入后由措辞判断复核（BR-2243、BR-2239）。
- **执行状态**：规划中、已通过（C-n）、待 main 测试（C-n）、待重新执行四种（BR-2246）。
- **验收行**：变更 `## 验收` 段里写一条带 `untested:` 的规则怎么验、看到了什么的一行（BR-2241）。
