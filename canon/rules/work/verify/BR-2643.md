## 规则

`canon work test <文件…>`（点名测试文件、不带 `--all`）在一个变更的 worktree 里运行，而这个变更挡着别的变更（有打开的变更按 BR-2564 在等它，一层层算，同 BR-2635），并且项目的 `policies.capacity.critical_lane`（BR-2640，默认 `true`）没关时，走**关键链通道**：

- 不进负载队列（BR-2630），不等 5 分钟负载降下来；
- 改进整台机器只有一个名额的关键链队列：前面有一条在跑就排队，排队时照 BR-2576 的样子说明前面还有几条；拿到名额就开跑，跑完（通过、失败或被终止）交回名额，下一条才开始；进程没了的名额作废（BR-2577）；
- 开跑前先输出一行 `canon: critical-path lane: <C-n> holds <它挡着的变更，逗号分隔>; these named files do not wait for the machine load and run one at a time on this machine (BR-2643; policies.capacity.critical_lane: false turns it off)`；
- 排队、开始、结束记成事件 `test.lane.wait`、`test.lane.start`、`test.lane.end`，详情和 `test.full.*` 一样，另有 `holds`（它挡着的变更）。

不点名文件的 `canon work test`、`--all`、合入和后台的 floor 不走这条通道，照 BR-2576 和 BR-2630 等名额和负载。没挡着谁的变更、不在变更 worktree 里的运行、`critical_lane: false` 时，点名文件的运行照 BR-2630 等负载。

议程和 `canon work watch` 的 heavy 一行（BR-2582）在通道里有运行或排队时，后面加 `; critical lane: <正在跑的变更和已跑多久>, <k> waiting`（没人在跑写 `none running`，没人排队不写 waiting）。

这条通道一次只多跑一条命令，机器满时仍可能更慢；它让一条长链不被几分钟的短测试卡住（负责人 2026-11-23，经主神空间主会话转述：「关键链上的短命令不看负载、排队一条条跑 要」）。

## 例子

- `C-1060` 等 `C-1163`，负载 24、上限 16，在 `C-1163` 的 worktree 里 `canon work test a.test.ts` → 输出 `canon: critical-path lane: C-1163 holds C-1060; …`，不等负载，马上开跑；事件有 `test.lane.start`，没有 `load.wait`
- 同时 `C-1200`（也挡着别人）在跑通道里的测试 → `C-1163` 的这次运行排在它后面，说明前面有 1 条；它跑完 `C-1163` 才开跑
- 同上但不点名文件 `canon work test` → 照常等整组名额和负载
- `--all` → 照常
- `C-5` 没挡着谁 → 照 BR-2630 等负载
- `policies: {capacity: {critical_lane: false}}` → `C-1163` 的点名运行也等负载
- 通道里 `C-1163` 跑了 2 分钟、还有 1 条在排 → heavy 一行结尾 `; critical lane: C-1163 2m, 1 waiting`
