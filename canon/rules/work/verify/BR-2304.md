id: BR-2304
title: canon work test 被 SIGTERM、SIGINT 或 SIGHUP 终止时停掉它启动的全部进程
status: active
---

## 规则

`canon work test` 在类型检查、运行测试文件或单独重跑（BR-2226、BR-2302、BR-2303）时收到 SIGTERM、SIGINT 或 SIGHUP：不再开始新的文件，不开始单独重跑，然后停掉它启动的全部进程。停的步骤就是 BR-2285 写的那一套（SIGSTOP 冻结、SIGTERM 加 SIGCONT、等、SIGKILL、再等、读不出进程表时的说明），对象换成 `canon work test` 启动的进程，不另写一套；只有两处不同：一是只停它的子孙进程，组里别的进程不动（BR-2285 里不是组长的做法），因为它常和别的进程在同一个终端作业里，例如 `canon work test | tee`；二是等的时候收到第二个信号（任何一种）就立刻给还在的进程发 SIGKILL，不等满 10 秒。SIGTERM 和 SIGHUP 同样处理。

停完打印 `stopped by <信号>: <r> test file(s) were running, <m> not started`，不运行 `canon check`，不打印汇总，记一条 `work.test`（比平常多 `signal`，值是信号名），退出码 SIGTERM 143、SIGINT 130、SIGHUP 129（和 BR-2099 一样）。数法：r 是收到信号时正在运行的文件个数（类型检查时 0）；m 是没有最终结果的其余文件，包括没开始的，和已经同时失败、还在等单独重跑的（BR-2303）：这些文件不算失败。`work.test` 的文件数和失败数只算已经有最终结果的文件（通过，或失败而且不会再重跑）。

一个文件的进程因为信号结束（`signalCode` 有值，或 `sh` 以 129、130、143 退出），而 canon 在这之前已经收到停止信号，或在这之后 0.5 秒内收到，这个文件不算失败、不重跑、不记结果，算在收到信号时正在运行的 r 里。往整个进程组发 Ctrl-C 时，子进程和 canon 差不多同时收到 SIGINT：不会再开新文件，也不会重跑。因为信号结束而 canon 没有收到停止信号的文件（例如被 OOM 杀掉），照常算失败。

## 例子

- 同时运行 3 个文件、还有 5 个没开始时收到 SIGTERM → 3 个文件的 `sh`、`bun test` 和它们启动的 git 都结束，打印 `stopped by SIGTERM: 3 test file(s) were running, 5 not started`，没有 `canon check:` 行，退出码 143，`work.test` 带 `signal: "SIGTERM"`，失败数 0
- 一次一个（`test_jobs: 1`）运行第 2 个文件时收到 SIGINT → 它的进程全部结束，打印 `stopped by SIGINT: 1 test file(s) were running, <剩下的个数> not started`，退出码 130
- 对整个进程组发 SIGINT，正在运行 2 个文件 → 两个文件都因 SIGINT 结束，一个也不算失败，不开新文件，不重跑，退出码 130
- 类型检查运行时收到 SIGTERM → 类型检查的进程结束，`stopped by SIGTERM: 0 test file(s) were running, <选出的个数> not started`，退出码 143
- 单独重跑阶段，2 个同时失败的文件还没重跑，收到 SIGTERM → `stopped by SIGTERM: 0 test file(s) were running, 2 not started`（再加上没开始的），这 2 个不算失败，`work.test` 的失败数不含它们
- 一个测试文件的进程忽略 SIGTERM → 10 秒后收到 SIGKILL，然后才打印 `stopped by` 那一行并退出
- 等的时候又收到一次 SIGINT → 立刻对还在的进程发 SIGKILL，不再等 10 秒，退出码仍由第一个信号决定
- 收到 SIGHUP → 和 SIGTERM 一样，退出码 129
- 一个文件被外部的 `kill -9` 杀掉，canon 没有收到信号 → 算失败（`FAIL`，退出码 137）
- 没收到信号、正常结束 → `work.test` 没有 `signal`
