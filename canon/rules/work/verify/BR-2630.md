## 规则

每个重步骤（work/verify 的术语表：`canon work test`，点名文件的也算；合入在轮次里跑的 floor 和它补跑的测试文件；后台 floor watch 对 main 的运行；`canon heavy run`，BR-2631）在跑第一个项目命令之前过一道负载关（D-161）。不管是主会话、子 agent、轻派发还是重派发的 worker 跑的（BR-2632），都一样。

**判定**：负载上限 `L` 按 BR-2526 第 2 条算（运行这一步的仓库读到的 `delegate_max_load_per_cpu` × CPU 数，比较用没有取整的 5 分钟负载）。下面的判定、登记和放行时间的记录都在负载队列的整机互斥里做（同 BR-2577 的互斥目录）。互斥保证的是：有步骤在排队或在 60 秒间隔里时，新来的不会绕过队列；机器空闲时同时到的几个步骤都可以立刻开始，不保证一次只开一个。

- 队列空、负载低于 `L`、离上一次**从队列放行**已满 60 秒（或从没放行过）→ 立刻开始，不进队列，不输出，不记放行时间。机器空闲时不因间隔变慢。
- 否则进队列，按到达顺序排，每项记下它自己的 `L`。排在第一个、负载低于它的 `L`、离上一次从队列放行已满 60 秒时，它开始，并记下这次放行时间。一次只放一个：5 分钟负载跟不上刚开始的步骤。队首的 `L` 比后面的小时后面的也跟着等，不插队（已知限制：几个仓库配了不同的上限时，按最严的那个排）。
- 这一次读不到负载（三个平均值都是 0，或读取失败）→ 这一次的负载条件按满足算，其余条件照旧：队列空、不在 60 秒间隔里就立刻开始；队列不空时新来的照样进队列，只有队首能放行，照样隔 60 秒。

**队列存储**：BR-2577 的状态目录下的 `load-waits/`，存法、坏项和读写失败照 BR-2577；每项另记步骤种类（`test`、`land`、`floor`、`heavy-run`）和它的 `L`，放行时间记在同一目录。显示主题时写 `<编号>（<worktree 路径>）`，几个仓库的同号变更分得开。

**和别的关的先后**：

- 整组测试先按 BR-2576 拿名额，再过负载关；等负载时名额不放。BR-2576 里点名文件的测试“立刻开始”只是说不等名额，负载关照过。
- 合入在拿到轮次之后、跑 floor 和补跑测试之前过关；这一轮不跑 floor 也不补跑测试（例如只改了 `floor_skip_paths` 里的路径）时不过关。批量合入整批只过一次关，批里各成员不再各自过。合入在轮次里等负载时，后面的合入一起等：这时机器已经过载，后面的合入多半也要跑测试；`canon work land --stop` 停下等待并放出轮次。
- 后台 floor watch 每一批运行过一次关，等的时候不再为同一批另排一项。
- **嵌套**：重步骤运行的项目命令的环境里有 `CANON_HEAVY_STEP=1`；在这样的环境里再进来的重步骤（例如 `test_command` 里调用了 `canon heavy run`）不过关，直接开始，不然外层等内层、内层等负载降下来。
- `setup`、`before_land` 和生命周期 hook 不是重步骤，不过关。

**等的时候**：进队列时输出一行 `canon: waiting for the machine load: 5-minute load <一位小数> on <CPU 数> CPUs (limit <L>); <n> step(s) ahead on this machine; the wait does not count toward test_timeout_minutes`；前面的步骤数变了再输出一行，此外最多每 5 分钟输出一行当时的负载。后台合入和后台测试的这一行写进它们的日志，跟随的 `canon work land`、`canon work test` 照常转出来。

- 不设等待上限：等到负载降下来，或被停下。等的时间不算进 `test_timeout_minutes`（BR-2466、BR-2580 的起点改成过了负载关之后）、合入的 floor 时限和 `work.test` 事件的 `ms`。
- 收到 SIGTERM、SIGINT 或 SIGHUP：退出队列，不跑任何项目命令，以信号对应的退出码结束（BR-2304）；手里的整组测试名额和合入轮次随进程结束放出（BR-2577、合入队列的规则）。`canon work test --stop`、`canon work land --stop` 也这样停下等待中的步骤。

**事件**：进队列时记 `load.wait`（详情：步骤种类、负载、`L`、前面几个）；从队列放行时记 `load.start`（详情含等了多少毫秒）。立刻开始的不记。

依据：D-161。

## 例子

- 8 个 CPU、负载 17.0（`L` 16），worker `w1` 在 `C-9` 的 worktree 里运行 `canon work test src/a.test.ts` → 输出 `canon: waiting for the machine load: 5-minute load 17.0 on 8 CPUs (limit 16); 0 step(s) ahead on this machine; …`，负载降到 15.9 后开始类型检查，事件表有 `load.wait` 和 `load.start`
- 同上，`w1` 是轻派发（BR-2632）→ 一样等
- 主会话自己在 worktree 里运行 `canon work test`，负载 17.0 → 一样等
- 负载 12.0，队列空，过去 60 秒没有从队列放行 → 立刻开始，没有等待行，没有 `load.wait`
- 负载 15.96 → 低于 16，按上一条
- 负载 17.0 时 `C-9`、`C-10`、`C-11` 先后进队列；负载降到 14.0 → `C-9` 开始，`C-10` 的等待行变成 `0 step(s) ahead`；60 秒内负载一直是 14.0，`C-10` 仍不开始；放行 `C-9` 满 60 秒、负载仍低于 16 → `C-10` 开始
- `C-11` 刚从队列放行、队列已空，20 秒后 `C-12` 到达，负载 12.0 → 进队列，放行 `C-11` 满 60 秒后开始
- 负载 12.0，但队列里还有 `C-9` 在等 → 新来的 `C-12` 排在 `C-9` 后面，不插队
- 两个 worktree 在同一时刻运行 `canon work test`，负载 15.0、队列空 → 两个都立刻开始（互斥只保证队列判定不乱，立刻开始的不受间隔限制）
- `full_test_slots` 是 1，负载 17.0，`C-9` 拿到整组测试名额后在等负载，`C-10` 的整组测试来了 → `C-10` 按 BR-2576 等名额，`C-9` 的名额不放
- 负载 17.0，`C-9` 合入，这一轮要补跑测试 → 拿到轮次后输出等待行，负载降下来后才跑；只改了 `canon/notes/` 的合入 → 不等
- 批量合入 3 个成员，负载 17.0 → 整批只有一条 `load.wait`
- 负载 17.0，后台 floor watch 要测 main → 等，等待行写进它的日志
- `test_command` 是 `canon heavy run -- bun test {file}`，负载 17.0，`canon work test` 过关后跑它 → 里面的 `canon heavy run` 直接开始，不再排队
- `test_timeout_minutes` 是 30，等负载 40 分钟，测试跑了 5 分钟 → 不超时
- 等负载时 `canon work test --stop` → 退出队列，没有跑任何测试，名额放出
- 排在第一个的 `C-9` 的进程被杀，队列项还在 → 不算，`C-10` 按条件开始
- 另一个仓库也有 `C-9` 在等 → 两项分别写成 `C-9（<两个 worktree 路径>）`
- Windows 读不到负载，队列空，过去 60 秒没有从队列放行 → 直接开始，没有等待行
- 读不到负载，队列里有 `C-9` 在等 → 新来的 `C-12` 排在后面；`C-9` 在上次放行满 60 秒后放行，`C-12` 再隔 60 秒
