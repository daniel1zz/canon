## 规则

整组测试（BR-2576）在协调数据库的事件表里记三种事件，subject 是变更或杂务编号，main 的后台 floor 没有编号时为空：

- `test.full.wait`：要排队时记一条，`detail` 是 `{subject, pid, pid_start, ahead}`，`ahead` 是当时前面的组数；有名额立刻开始的不记；
- `test.full.start`：拿到名额、开始跑时，`detail` 是 `{subject, pid, pid_start}`；
- `test.full.end`：跑完或被停下、名额交还时，`detail` 是 `{subject, pid, pid_start, duration_ms, outcome}`；`duration_ms` 从开始算，不含排队；`outcome` 是 `passed`、`failed` 或 `stopped`（信号或超过 test_timeout_minutes）。

事件的 worktree 是通用的事件列（BR-2131）。`pid`、`pid_start` 是跑这组测试的 canon 进程；一组在跑 = 有 `start`、没有同一 `pid` 加 `pid_start` 的 `end`，并且这个进程还活着：进程被杀时没有 `end`（BR-2577）。点名了测试文件的 `canon work test` 不记这三种事件。

## 例子

- 立刻开始并通过的整组测试 → 一条 `start`、一条 `end`（`outcome` 为 `passed`），没有 `wait`
- 排在一组后面的 → 先 `wait`（`ahead` 为 1），轮到后 `start`，再 `end`；`duration_ms` 只从 `start` 算
- 有测试失败的整组测试 → `end` 的 `outcome` 为 `failed`
- 被 SIGTERM 停下 → `end` 的 `outcome` 为 `stopped`
- 被 SIGKILL 杀掉 → 有 `start` 没有 `end`，它的进程已不存在
- `canon work test src/a.test.ts` → 不记这三种事件
- 后台 floor 的整组运行 → subject 为空，三种事件照记
