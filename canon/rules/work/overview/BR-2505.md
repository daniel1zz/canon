## 规则

`canon overview`（D-129、D-131）在 canon 项目里任何位置运行，按下面的顺序输出五节，每节以 `## <节名>` 开头，退出码 0：

1. `## 当前版本`：进行中的版本是状态 `active` 的全部版本，按编号的数值排序；没有 `active` 时取状态 `planned` 中编号数值最小的一个；都没有时这一节第一行是 `(no release in progress)`。每个进行中的版本依次输出（D-131）：
   - 它在 `canon release status` 里的那一行（BR-2328）；因为没有 `active` 才取的 `planned` 版本，下面再一行 `(没有 active 的版本，取编号最小的 planned；正在做的版本把 status 改成 active)`；
   - 它自己的成功标准：一行 `成功标准 <总数> 条：已满足 <a>  未满足 <b>  待负责人 <c>  未证明 <d>`，然后每条一行，缩进两个空格；
   - 它 `features` 里的每个模块，按列表顺序（不存在的和 `dropped` 的不列）：一行 `  模块 <F-n> <标题>  成功标准 <总数> 条：…`（计数同上），然后它的每条成功标准一行，缩进四个空格。

   每条成功标准的一行是 `[<状态>] <编号和一个空格（有编号时）><文字>`，已满足的后面加 `  证据：<编号，用逗号分隔>`，有 main 上没放弃的变更在 `advances` 里写了它（BR-2517）时再加 `  推进：<变更编号>`，取编号最大的 3 个、从大到小，用逗号分隔（状态、编号和文字按 BR-2504）。不管有没有进行中的版本，main 上最近 7 天有改了目标（BR-2510 的那几种改动，按每个提交和它的父提交比较）的提交时，这一节最后再一行 `最近 7 天的目标改动：`（D-130），然后每个这样的提交一行 `  <提交号前 9 位> <提交标题>`，下面每处改动一行，缩进四个空格，最新的提交在前；没有时不输出。
2. `## 计划`：和不带编号的 `canon plan status` 输出的行一样（BR-2373）；没有计划时 `(no plans)`。
3. `## 等负责人`：先每个等人回答的问题一行 `问题 #<n> <问题的第一行>`（同 `canon human pending` 的范围），再每个分级为 C 的未处理评审意见一行 `意见 #<n> <点名的编号>: <意见文字的第一行>`，最后进行中的版本和它们的模块里每条待负责人的成功标准一行 `成功标准 <版本或模块编号>: <文字>`；三样都没有时 `(nothing)`。
4. `## 待办顺序`：`canon change list` 列出的未完成变更里排在最前面的 5 个，顺序和标记同 `canon change list`（BR-2149、BR-2291），每个一行 `<C-n> <标题>`，有标记时后面加 `  (<标记>)`；多于 5 个时再一行 `… 还有 <k> 个（canon change list）`；没有时 `(none)`。
5. `## 最近合入`：最近 5 次合入的变更（协调事件里主题是变更编号的 `land.ok`，杂务不算），最新的在前，每个一行 `<C-n> <标题> <合入时间，UTC，到分钟>`，后面按它在 main 上的 `advances`（BR-2517）加 `  → <引用，用逗号分隔>`、`  （不推进：<理由>）` 或 `  （没写 advances）`；标题取 main 上的变更文件，读不到时只写编号；没有时 `(none)`。

`--json` 输出一个对象，内容相同：`releases`（进行中的版本，没有时空数组；每项含 `id`、`title`、`status`、`fallback`（是否因为没有 active 才取的）、`counts`（同 `canon release status --json`）、`criteria` 和 `features`（每项含 `id`、`title`、`criteria`）；每条成功标准含 `id`（没有编号时 `null`）、`text`、`state`（`met`、`unmet`、`owner`、`unproven`）、`evidence`、`advanced_by`（编号数组））、`plans`（每项含 `id`、`title`、`total`、`done`、`percent`）、`waiting`（含 `questions`、`findings`、`criteria` 三个数组，`criteria` 每项含 `doc` 和 `text`）、`backlog`（每项含 `id`、`title`、`marks`）、`backlog_more`（没列出的个数）、`landed`（每项含 `id`、`title`、`at`、`advances`（引用数组、`{"none": "<理由>"}` 或 `null`））、`goal_changes`（每项含 `sha`、`subject`、`changes`）。

## 例子

- `R-1` shipped、`R-2` planned、`R-3` active → 进行中的版本是 `R-3`
- `R-3`、`R-5` 都是 active → 两个都列，`R-3` 在前
- `R-1` shipped、`R-2` planned、`R-3` planned → 列 `R-2`，它那一行下面有 `(没有 active 的版本，…)` 的提示
- `R-10` 和 `R-9` 都是 planned、没有 active → 列 `R-9`
- 所有版本都 shipped 或 dropped，或没有版本 → `## 当前版本` 第一行是 `(no release in progress)`，其余四节照常输出
- `R-2` 有 3 条成功标准：一条已满足（证据 `C-4`）、一条待负责人、一条没标记 → `成功标准 3 条：已满足 1  未满足 0  待负责人 1  未证明 1`，三行分别以 `  [已满足]`、`  [待负责人]`、`  [未证明]` 开头，第一行末尾 `证据：C-4`；`## 等负责人` 里有一行 `成功标准 R-2: <那条的文字>`
- `R-3` 的 `features: [F-1]`，`F-1` 有一条 `- S1 五个分支各有构筑通关。（未满足）`，`C-7`、`C-9` 的 `advances` 写了 `F-1/S1` → `  模块 F-1 <标题>  成功标准 1 条：已满足 0  未满足 1  待负责人 0  未证明 0` 和 `    [未满足] S1 五个分支各有构筑通关。  推进：C-9, C-7`
- `R-3` 列着 dropped 的 `F-2` → 不列 `F-2`
- 有 1 个等人回答的问题 #7、1 条分级 C 的意见 #3、1 条分级 A 的意见 #4 → `## 等负责人` 有 `问题 #7 …` 和 `意见 #3 …`，没有 #4
- 7 个未完成变更 → `## 待办顺序` 列前 5 个，再一行 `… 还有 2 个（canon change list）`
- 被认领的变更 → 那一行末尾 `  (claimed)`
- 最近合入了 C-8（`advances: [R-3/S1]`）、一个杂务、C-9（没写 `advances`）→ `## 最近合入` 第一行 C-9 末尾 `（没写 advances）`，第二行 C-8 末尾 `→ R-3/S1`，没有杂务
- 三天前 main 上一个提交给 `R-3` 加了一条成功标准“支持手柄” → `## 当前版本` 最后有 `最近 7 天的目标改动：`、那个提交一行、下面一行写着 `R-3` 和“支持手柄”
- 改目标的提交在 8 天前 → 不列
- `--json`，没有进行中的版本 → `releases` 是 `[]`
