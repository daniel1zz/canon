---
id: BR-2223
title: 同一个仓库里 canon 一次只建一个 worktree，并发的 start 不会读到别人建了一半的 worktree
status: active
---

## 规则

同一个仓库（所有 worktree 共用一个 git 公共目录）里，`canon work start` 添加 worktree（以及 setup 失败时删掉它）、`canon work clean` 删除 worktree 时持有这个仓库的 worktree 锁（`<git 公共目录>/canon/worktree.lock`）的排他模式，一次只有一个；每个 canon 命令打开工作区、`canon work start`、`canon work clean` 和重叠提示读 worktree 列表时持有同一把锁的共享模式，可以多个一起读，但不会和正在进行的添加或删除同时进行。等锁的进程等到锁放开后照常执行，不报错；最多等 300 秒，超过就以退出码 4 失败，信息以 `waited` 开头并写明锁文件。持有锁的进程退出（包括被杀掉）时锁自动放开。在持有锁的 git 命令的 hook 里运行的 canon（环境变量 `CANON_WORKTREE_LOCK_HELD=1`）不再等这把锁。

不在本规则范围内：`canon work land` 一起测时建的临时 worktree、`canon work drop` 的删除和列表，它们还直接调用 git、不持锁（D-33）。

原因：git 添加 worktree 时先建 `.git/worktrees/<id>/`、写 `gitdir`，再写 `commondir`；这期间另一个 `git worktree add` 或 `git worktree list` 读到空的 `commondir` 就直接失败：`fatal: failed to read .git/worktrees/<id>/commondir`（issue #32；git 2.50.1 上 8 个并发 `git worktree add`，40 轮里有 2 到 5 轮出现）。

## 例子

- 另一个 canon 进程正在建 worktree，`.git/worktrees/half/` 里有 `gitdir`、`commondir` 是空文件；这时直接运行 `git worktree list` → 失败，报 `failed to read .git/worktrees/half/commondir`；这时运行 `canon work start --title "T"` → 等那个进程放开锁，然后退出码 0，得到 C-1 的 worktree
- 同样情形，canon 的 `git worktree add` 和读 worktree 列表 → 都等到锁放开才执行，成功，列表里没有 `half`
- 另一个进程一直持有排他锁，等待上限是 300 毫秒（测试里调小）→ 300 毫秒后失败，错误属于环境错误（退出码 4），信息是 `waited 300 ms for the worktree lock …/.git/canon/worktree.lock …`；那个进程放开后再读 → 成功
- 持有锁的进程被 `kill -9` 杀掉 → 下一个 `canon work start` 不用等，立刻成功
- canon 的 `git worktree add` 触发项目的 `post-checkout` hook，hook 里运行 canon 读 worktree 列表 → 不等父进程持有的锁，直接读，成功；不会互相等到超时
- 8 个进程同时 `canon work start --title "T<i>"` → 8 个都退出码 0（BR-2132），没有一个因 `failed to read .../commondir` 失败
