## 规则

`canon work stop --reason <原因> --next <下一步>` 为当前 worktree 认领的变更记录 handoff（原因、下一步、可选备注、操作者、时间），覆盖同一变更之前的 handoff；默认保留认领，加 `--release` 时释放；当前 worktree 没有认领时退出码 3；当前 worktree 正被一次 `canon work clean` 或 `canon work drop` 删除（它的占位还有效，BR-2019、BR-2064）时，退出码 5，提示写明这个 worktree 正在被删除，不记 handoff；那次 clean 或 drop 已经被杀掉、占位失效时，按没有认领处理（退出码 3）。

原因是固定的五种之一，状态计算（BR-2571）只读它，不读下一步的文字（D-151）：

- `land`：做完了，等合入；
- `design`：等设计（设计没定或有矛盾，配合 BR-2499）；
- `owner`：等负责人，必须用 `--on` 指明在等哪一个：一个问题编号（`#12` 或 `12`），这个问题要关联到这个变更（`canon human ask --change <C-n>` 或在它的 worktree 里问的）；或者一条成功标准 `R-n/S<k>`、`F-n/S<k>`，要在 main 上存在；
- `deps`：等依赖（`depends_on` 里的，BR-2564）；
- `partial`：做了一部分，别人可以接着做。

用法错误都是退出码 2，什么都不记：没给 `--reason`、原因不是这五种；`owner` 没给 `--on`；别的原因给了 `--on`；`--on` 指的问题不存在或没关联到这个变更，提示用 `canon human ask --change <C-n>` 重新问；`--on` 指的成功标准在 main 上没有时退出码 3。

`canon work status` 的交接行和 `canon brief` 在变更 worktree 里显示交接时，在下一步前面写出原因（`owner` 带上 `--on`）。没有原因的旧交接写 `unrecorded`，用 BR-2575 补上。

## 例子

- 先 stop `--reason partial --next "write the test"`，再 stop `--reason land --next "land it"` → handoff 只剩原因 `land`、“land it”，认领还在
- stop `--next "land it"` 不带 `--reason` → 退出码 2，提示列出五种原因，不记 handoff
- `canon human ask --change C-1 "要不要恢复招降？"` 得到 #12，在 `C-1` 的 worktree 里 stop `--reason owner --on 12 --next "等负责人回答 #12"` → 记下原因 `owner`、指向 #12
- `--reason owner` 不带 `--on` → 退出码 2
- `--reason owner --on 13`，#13 关联的是 `C-2` → 退出码 2，提示用 `canon human ask --change C-1`
- `--reason owner --on R-2/S9`，main 上 `R-2` 没有 `S9` → 退出码 3
- `--reason partial --on 12` → 退出码 2
- 在主 checkout（没有认领）执行 stop → 退出码 3
- `canon work drop C-1` 正在删除 `C-1` 的 worktree 时，在那个 worktree 里执行 stop → 退出码 5，提示里有 `being deleted`，没有新的 handoff
- 占住 `C-1` 的那次 drop 已经被杀掉 → 在那个 worktree 里执行 stop 退出码 3
