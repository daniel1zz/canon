## 规则

`canon brief` 在输出任何别的内容之前，先看协调数据库记下的路径是不是指向仓库原来的位置：

- **旧的 worktree 目录**：认领、交接、合入队列里记的某个 worktree 路径已经不存在，而现在的 worktree 目录（BR-2047）下有同名的目录 → 那个路径所在的目录是旧的 worktree 目录。
- **旧的主 checkout**：合入后评审记的日志路径、或最近的后台 hook 记的日志路径形如 `<目录>/.git/canon/logs/<文件>`，已经不存在，而这个协调数据库旁边的 `logs/` 里有同名文件 → 那个 `<目录>` 是旧的主 checkout。
- 用默认的 worktree 目录（`<主 checkout>.worktrees`）时，两者能互相推出：找到一个就有另一个。配了 `worktrees` 的只认找到的那一个。

找到旧位置时，在一个写事务里把旧前缀（路径本身或它下面的路径）换成新前缀：认领、合入队列、交接、事件的 worktree 列，合入后评审的日志路径，以及事件详情里以完整路径出现的旧路径。改写过的认领清掉记下的会话进程（进程号和启动时间）：那是旧位置、可能是另一台机器上的进程，在这里会被碰巧同号的进程冒充（D-165）。然后对现在 worktree 目录下的每个 worktree 运行 `git worktree repair`，记一条 `state.relocate` 事件（旧和新的主 checkout、旧和新的 worktree 目录、改写的行数、修好的 worktree 数），brief 输出一行 `canon: this repository moved from <旧> to <新>; rewrote <n> path(s) in the coordination database and repaired <m> worktree link(s) (BR-2649)`。

什么都没找到时什么都不做、不输出，只多三次小查询。改写之后再运行 brief 就找不到旧位置了，所以这一行只出现一次。合入队列的结果文字等历史文字里的旧路径不改。

## 例子

- 仓库从 `/old/place/game` 挪到 `/new/game`，认领记着 `/old/place/game.worktrees/C-1`，`/new/game.worktrees/C-1` 存在 → 认领改成 `/new/game.worktrees/C-1`，进程清空；事件里的 `/old/place/game` 和日志路径都改成新的；输出那一行，有一条 `state.relocate`
- 同一个仓库再运行一次 `canon brief` → 不再输出那一行
- 没有认领指向旧位置，只有合入后评审的日志记着 `/old/place/game/.git/canon/logs/landed-review-1.log`，新位置的 `logs/` 里有这个文件 → 照样找到旧位置并改写
- 仓库没挪过 → 什么都不输出，没有 `state.relocate`
