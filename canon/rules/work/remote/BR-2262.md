id: BR-2262
title: canon sync 在本地 main 能快进到远端 main 时移动 main
status: active
---

## 规则

`canon sync` 先取远端的 main（`git fetch --no-tags <远端> +refs/heads/<main>:refs/remotes/<远端>/<main>`，最多等 `remote_timeout_seconds` 秒），再比较：远端 main 和本地 main 相同时什么也不动，输出 `already up to date`，退出码 0；本地 main 是远端 main 的祖先时，用合入移动 main 的同一个比较并交换把 main 移到远端的提交（没有 worktree 签出 main 时带放行标记 `CANON_LAND_MAIN` 的 `git update-ref`，有 worktree 签出 main 时在那里带标记的 `git merge --ff-only`，那个 worktree 必须干净，BR-2125），写 `sync.ok` 事件（`from`、`to`），输出 `fast-forwarded <main> ... to ...`，退出码 0；`floor_timing: after` 时随后照 BR-2219 启动后台测试。远端 main 是本地 main 的祖先（本地领先）时什么也不动，输出本地领先几个提交、下次合入会推，退出码 0。sync 从不合并、不 rebase、不推送。没写 `remote` 时退出码 2；取远端失败或超时时退出码 4，main 不动；签出了 main 的 worktree 有未提交改动时退出码 1（`main-dirty`），main 在比较和移动之间被别人移动时退出码 1（`main-moved`），这两种和取远端失败都写 `sync.refuse` 事件并带原因（`main-dirty`、`main-moved`、`fetch`）。

## 例子

- 裸仓库的 main 比本地 main 多一个提交 R，主 checkout 签出 main 且干净，装了 canon 的 git hook → 退出码 0，本地 main 是 R，主 checkout 的文件是 R 的，事件表有 `sync.ok`
- 两边相同 → 退出码 0，输出 `already up to date`，没有 `sync.ok`
- 本地 main 比裸仓库多 2 个提交 → 退出码 0，main 不动，输出里有 `2`
- 主 checkout 签出 main、有未提交改动，远端多一个提交 → 退出码 1，main 不动，`sync.refuse` 的原因 `main-dirty`
- 没写 `remote` → 退出码 2，main 不动
- `remote: nowhere` → 退出码 4，main 不动，`sync.refuse` 的原因 `fetch`
