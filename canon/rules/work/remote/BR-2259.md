title: 合入移动 main 之后把 main 推到配置的远端
status: active
---

## 规则

main 上已提交的 `canon/config.yaml` 写了 `remote` 时，`canon work land` 每次移动 main、结束排队轮次之后（两种 `floor_timing` 下都是；分批合入的每个成员各一次，包括被别人的批合进去的），读出本地 main 这时指向的提交，执行 `git push --porcelain --no-follow-tags <远端> <提交>:refs/heads/<main>`：只推这一个 ref，不带标签，不加 `--force`，环境里设 `GIT_TERMINAL_PROMPT=0`，最多等 `remote_timeout_seconds` 秒（默认 60；推送被拒后的取远端和推送共用这一个时间，见 BR-2260）。推送成功，或者被拒绝后取一次远端的 main（`git fetch --no-tags <远端> +refs/heads/<main>:refs/remotes/<远端>/<main>`）发现它已经包含这个提交（比它新的推送先到了），都算推上去了：写一条 `push.ok` 事件（`remote`、`sha`），输出一行 `pushed <提交前 9 位> to <远端>`。没写 `remote` 时不推送，不写推送事件，不输出推送的行。合入被拒绝、超时或没有移动 main 时不推送。

## 例子

- `remote: origin`，`origin` 是一个本地裸仓库，合入 `C-1` 让 main 到 A → 裸仓库的 `main` 是 A，`refs/remotes/origin/main` 是 A，事件表有 `push.ok`（`sha` 是 A），输出有 `pushed`，裸仓库里没有别的分支和标签
- 同上，main 上有标签 `v1` → 裸仓库里没有 `v1`
- 没写 `remote` → 裸仓库不变，事件表没有 `push.ok`、`push.fail`
- `floor_timing: after` 下合入 → 不等后台测试，照样推 A
- 别的合入先把 main 移到 A 的子提交 B 并推了 B，这次的推送晚到、推 A 被拒 → 取远端后发现 B 包含 A，记 `push.ok`，不记 `push.fail`
- 合入因为 `dirty` 被拒 → 不推送，没有推送事件
