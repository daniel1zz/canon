title: "清理 worktree 绝不丢工作"

## 规则

`canon work clean` 只删除同时满足以下条件的 worktree：不是当前所在的 worktree、没有被认领、没有未提交改动、所有提交都已在 main 上、没有不能重新生成的被 git 忽略的文件、没有别的进程把当前目录放在它里面；其余的保留，并列出原因（被忽略的文件列出路径，进程列出 pid 和命令名）。被忽略的文件只要路径里有一段匹配 `canon/config.yaml` 的 `regenerable`（文件或目录名，可以用 glob，不含 `/`），就算能重新生成；配置了 `regenerable` 时它取代默认列表，没配置时默认是 `node_modules`、`dist`、`build`、`out`、`coverage`、`.next`、`.nuxt`、`.turbo`、`.cache`、`.parcel-cache`、`target`、`__pycache__`、`.pytest_cache`、`.mypy_cache`、`.venv`、`venv`、`.gradle`、`*.pyc`、`.DS_Store`。查不出有哪些进程时，保留并写明原因。删除一个 worktree 时，先在同一个事务里确认它的变更没有任何认领并占住它，删完再放开；这期间对这个变更的 `canon work start` 以退出码 5 被拒（同一个操作者在同一个路径上也一样），所以不会有会话拿到一个马上被删掉的 worktree；在读认领之后、占住之前被别人认领的，保留，原因是“claimed”。占住时记下执行 clean 的进程，clean 被中途杀掉时，进程不在了这个占位就立刻失效（BR-2100），不会挡住别人一整个租约。

## 例子

- C-1 已经 `--finish` 合入 → 被删除
- C-2 有一个没合入的提交 → 保留，原因是“1 commit(s) not on main”
- C-3 已合入，worktree 里有被忽略的 `.env` → 保留，原因列出 `.env`
- C-4 已合入，只有被忽略的 `node_modules/` → 被删除
- 配置 `regenerable: ["cache-*"]`：`cache-v1/` 能重新生成，`node_modules/` 不再算能重新生成 → 只有后者所在的 worktree 被保留
- 列不出进程（`lsof` 执行失败）→ 已合入的 worktree 也保留，原因写明列不出进程
- `clean` 检查 C-6 期间，另一个会话认领了 C-6 → C-6 保留，原因是“claimed”，那个会话的认领不受影响
- `human:x` 在一个终端 clean C-7 的同时，在另一个终端 `canon work start C-7` → start 退出码 5
- clean 正在删 C-8 时被杀掉 → 之后别人 `canon work start C-8` 照常成功
- C-5 已合入，pid 4242 的 `zsh` 当前目录在 C-5 里 → 保留，原因是“in use by pid 4242 (zsh)”
