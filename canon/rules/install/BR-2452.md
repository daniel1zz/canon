## 规则

`canon/config.yaml` 没有 `links_since`（没写这个键，或写成 null）而 main 已有提交时，项目算过期，按 BR-2084 列出、按 BR-2085 提示。`canon update` 像别的过期项一样开变更合入（BR-2086）：在变更的 worktree 里把 `links_since` 写成开变更时 main 的完整提交编号（写成 null 的那一行换掉，没写的在文件末尾加一行，前面加一行说明它的注释），文件里其余的行原样不动，和别的过期项一起提交、合入。值的含义见 BR-2424。

已经有 `links_since` 的值时不算过期，`canon update` 从不改它，哪怕它不在当前历史里（那由 BR-2424 报）。main 还没有提交时也不算过期：这时不需要它（BR-2424），第一次提交之后 `canon update` 再写。

## 例子

- main 有提交，`canon/config.yaml` 没有 `links_since` → `canon update --check` 退出码 1，列出 `links_since missing`；`canon update` 退出码 0，main 上的 `canon/config.yaml` 末尾有 `links_since: "<开变更时 main 的完整编号>"`，原来的行和注释都在；之后 `canon update --check` 退出码 0
- `canon/config.yaml` 写着 `links_since: null` → 同样算过期，更新后那一行换成编号，文件里只有一个 `links_since`
- `canon/config.yaml` 已经写着 `links_since: "<某个编号>"`，别的 skill 过期 → `canon update` 合入后它还是原来的编号
- main 还没有提交 → `canon update --check` 不列 `links_since`
