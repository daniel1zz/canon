title: main 守卫拒绝 git pull --rebase 移动 main 时，提示先 git rebase --abort 再 canon sync
status: retired
---

## 规则

本地 main 和远端各自前移过时，`git pull --rebase` 先在分离的 HEAD 上把本地的提交接到远端的提交后面，最后才移动 main；main 守卫（BR-2126）拒绝这一步后，git 停在 rebase 中间：HEAD 分离，main 没动，`git rebase --abort` 能把它整个撤销。所以守卫拒绝一行 `refs/heads/<main>` 时，如果 hook 所在 checkout 的 git 目录里有 `rebase-merge/`（`git rev-parse --git-path rebase-merge`），它的 `head-name` 就是这个 ref，而且它的 `onto`（rebase 接到的提交）在某个远端跟踪分支（`refs/remotes/*`）上或就是 `FETCH_HEAD`，stderr 在拒绝的话后面多一行 `canon: git rebase stopped with <main> unmoved; to take in the remote's <main>, first run git rebase --abort, then canon sync.`。

其余情况不加这一行：没有 rebase 在进行；rebase 的不是 main；rebase 接到的是只在本地的提交（那时 `canon sync` 帮不上）；rebase 用的是 apply 后端（`rebase.backend=apply`、`--apply`），它在移动 main 之前已经删掉了 `head-name`，`git rebase --abort` 在那里失败。拒绝本身、退出码照 BR-2126；这一行之外不改暂存区、工作区和 rebase 的状态（HEAD 分离时 BR-2284 本来就不动它们）。

## 例子

- main 和远端各自前移过，checkout 干净，`git -c rebase.backend=merge pull --rebase origin main` → 退出码非 0，stderr 有 `first run git rebase --abort, then canon sync`，main 仍是本地的提交，HEAD 分离；随后 `git rebase --abort` 退出码 0，HEAD 回到 `refs/heads/main`、指向本地的提交，`git status --porcelain` 为空，没有远端带来的 `new.txt`
- 同样的 clone 里，main 被 rebase 到一个只在本地分支 x 上的提交（`git rebase x`）被拒绝 → stderr 有拒绝的话，没有 `rebase --abort`
- 同样的 clone 里，`git -c rebase.backend=apply pull --rebase origin main` 被拒绝 → stderr 没有 `rebase --abort`
- 在签出 main 的 checkout 里 `git commit`、`git pull --no-rebase` 被拒绝 → 没有 rebase 在进行，stderr 没有 `rebase --abort`（BR-2284、BR-2286 的例子照旧）
