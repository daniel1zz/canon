## 规则

`canon/config.yaml` 的 `related_pick_command` 是可选的挑选命令（D-90）。它取自 main 上的配置，读法同 BR-2074：`canon context` 读运行时 main 指向的提交，`canon work review` 读它开始时 main 的提交；运行命令的 checkout 自己的配置不算。main 上没有这个键，或值为 `null`、空字符串、只有空白时不挑选：输出和 BR-2387 完全一样，不多一行，也不运行任何命令。

设了时，`canon context <规则或决策编号>` 和 `canon work review` 对 BR-2387 的每份文档 A，取它的融合排序前 50 名作候选（不到 50 份就全部取），在运行命令的 checkout 根目录用 `sh -c` 运行这条命令一次（没有候选时不运行，也没有这一段）。命令的标准输入是提示：A 的编号、标题和正文全文，之后每个候选一行 `- <编号> <标题>: <摘要>`，按融合排名排；摘要是正文去掉 `#` 开头的行、连续空白合成一个空格后的文字，超过 220 个字符时截到 219 个加 `…`。命令在标准输出给出一个 JSON 列表，最可能相关的在前，每项是 `{"id":"<编号>","reason":"<一句理由>"}`（`reason` 可以没有）或只是编号字符串；整个输出不是 JSON 时，取第一个 `[` 到最后一个 `]` 之间的文字。

命令挑中了候选时，BR-2387 那一段的标题行改为 `Related to <A> (the first <n> picked by related_pick_command from the fused top 50, then references both ways, shared text and names; check they do not contradict it):`，n 是列出的挑中份数。之后先按命令给的顺序列出挑中的候选，至多 10 份，同一编号只算第一次；每份一行 `  <编号> <标题>  (picked: <理由>; <BR-2387 的理由>)`，没给理由时写 `picked`，没有 BR-2387 的理由时不写 `; ` 和它后面的部分；理由里的换行和连续空白合成一个空格，超过 120 个字符时截到 119 个加 `…`；下一行是 BR-2387 的句子行。然后是融合排序前 10 名里没被挑中的，写法同 BR-2387。挑中的候选可以在融合前 10 名之外。

编辑 hook（BR-2421）、`canon check` 和合入都不运行这条命令。挑选只是提示：不拦截，退出码不变。缓存见 BR-2444，失败见 BR-2445。

## 例子

- main 上没有 `related_pick_command` → `canon context BR-1` 的相关文档一段和 BR-2387 的输出一字不差，没有运行任何命令
- main 上的命令输出 `[{"id":"BR-9","reason":"都改朝向"}]`，`BR-9` 在融合排序里是第 2 名 → 标题行是 `Related to BR-1 (the first 1 picked by related_pick_command from the fused top 50, …`，第一份是 `  BR-9 <标题>  (picked: 都改朝向; …)`，之后是融合前 10 名里的其他文档，`BR-9` 不再出现
- 命令读到的标准输入含 `BR-1` 的正文全文和一行 `- BR-9 <标题>: <摘要>`
- 有 12 份相关文档，命令挑中融合第 12 名的 `BR-12` → `BR-12` 排在最前，之后是融合前 10 名，共 11 份
- 命令输出 `Here you go: ["BR-9"] done` → 认出 `BR-9`，那一行是 `  BR-9 <标题>  (picked; …)`
- 只在变更 worktree 的 `canon/config.yaml` 里设了命令，main 上没有 → 在这个 worktree 里 `canon context BR-1` 和 `canon work review` 都不运行它
- main 上设了命令，在 worktree 里改了 `BR-1` 的文件 → 编辑 hook 输出的相关文档不运行它；`canon check` 也不运行它
- `canon context src/billing`（路径）→ 不运行命令
