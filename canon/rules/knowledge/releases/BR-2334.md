## 规则

`canon release ship R-n` 开始时取 `refs/canon/accepted` 指向的提交（D-89、D-105）：没有这个 ref 时退出码 1，信息提示先运行 `canon accept`；`R-n` 在这个提交上不存在或不是版本时退出码 3，信息提示验收之后创建的版本要重新验收；BR-2331 和 BR-2333 的条件都在这个提交的语料上评估。`R-n` 在 main 上的文件和这个提交上的不一致时退出码 1，提示重新验收再发（D-105）。这个提交落后 main 时，输出写明落后几个提交、发布的是已验收的提交。通过检查后按 BR-2457 开一个杂务（标题 `发布 R-n：<版本标题>`），不创建 Change 文档或占 C 编号，在它的 worktree 里把 `R-n` 的 `status` 改成 `shipped`、写入 `shipped_at`（已验收提交的完整提交号）、记下 `release.ship` 事件（BR-2332）、提交、按 BR-2458 合入；release.ship 始终关联此次非空杂务身份，在哪个目录里运行都行；合入成功后在 `shipped_at` 那个提交上打 git tag `release/R-n`，退出码 0，输出里有提交号和 tag。合入被拒退出码 1，排队超时退出码 75，都不打 tag。tag 打不上（同名 tag 已存在等）时在标准错误输出警告，已经合入的记录不撤销，退出码仍是 0；文档里的 `shipped_at` 是准的，tag 只是方便。

## 例子

- 条件都满足，`refs/canon/accepted` 在提交 `abc…` → `R-1` 变成 `shipped`、`shipped_at` 是 `abc…` 的完整提交号，杂务认领已释放，无新增 Change 文档，输出含 `shipped R-1`，`git rev-parse release/R-1` 等于 `shipped_at`，退出码 0
- 验收之后 main 又合入了两个不碰 `R-1` 的变更 → 照常发布，`shipped_at` 仍是已验收的提交，输出含落后 2 个提交的说明
- 没有 `refs/canon/accepted` → 退出码 1，信息含 `canon accept`，没有杂务
- 验收之后 `R-1` 的文档在 main 上又被改过 → 退出码 1，提示重新验收，没有杂务
- 发布后 `canon check` 通过：`## 目标`、`## 范围`、`## 不做` 和发布时一样，标着 `R-1` 的规则和发布时一样
- 在一个别的变更的 worktree 里运行 `canon release ship R-1` → 同样成功，那个变更不受影响
- 合入被拒（例如 floor 不过）→ 退出码 1，没有 tag，`R-1` 在 main 上仍不是 shipped
- 仓库里已经有一个叫 `release/R-1` 的 tag → 合入照常完成，标准错误有警告，退出码 0，`shipped_at` 仍写在文档里
