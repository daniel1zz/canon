## 规则

`canon release ship R-n` 通过 BR-2331 和 BR-2333 之后，按 BR-2457 开一个杂务（标题 `发布 R-n：<版本标题>`），不创建 Change 文档或占 C 编号，在它的 worktree 里把 `R-n` 的 `status` 改成 `shipped`、写入 `shipped_at`（开始时 main 的完整提交号）、记下 `release.ship` 事件（BR-2332）、提交、按 BR-2458 合入；release.ship 始终关联此次非空杂务身份，在哪个目录里运行都行；合入成功后在 `shipped_at` 那个提交上打 git tag `release/R-n`，退出码 0，输出里有提交号和 tag。合入被拒退出码 1，排队超时退出码 75，都不打 tag。tag 打不上（同名 tag 已存在等）时在标准错误输出警告，已经合入的记录不撤销，退出码仍是 0；文档里的 `shipped_at` 是准的，tag 只是方便。

## 例子

- 条件都满足，main 在提交 `abc…` → `R-1` 变成 `shipped`、`shipped_at` 是 `abc…` 的完整提交号，杂务认领已释放，无新增 Change 文档，输出含 `shipped R-1`，`git rev-parse release/R-1` 等于 `shipped_at`，退出码 0
- 发布后 `canon check` 通过：`## 目标`、`## 范围`、`## 不做` 和发布时一样，标着 `R-1` 的规则和发布时一样
- 在一个别的变更的 worktree 里运行 `canon release ship R-1` → 同样成功，那个变更不受影响
- 合入被拒（例如 floor 不过）→ 退出码 1，没有 tag，`R-1` 在 main 上仍不是 shipped
- 仓库里已经有一个叫 `release/R-1` 的 tag → 合入照常完成，标准错误有警告，退出码 0，`shipped_at` 仍写在文档里
