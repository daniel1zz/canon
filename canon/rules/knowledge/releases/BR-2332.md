id: BR-2332
title: 版本只能经 canon release ship 变成 shipped，发布后不能改回去
status: active
business: 发布
---

## 规则

合入时，一个版本在合入的树里是 `shipped`、而在 main 上不是（新增的，或状态原来是别的），必须有这次合入所属工作（业务变更或杂务，取合入关联的同一个身份）的 `release.ship` 事件，事件里的版本编号和 `shipped_at` 与文件里的一致，事件只由 `canon release ship` 在查过 BR-2331、BR-2333 之后写；没有就拒绝合入，原因 `release`，退出码 1，main 不动。main 上已经是 `shipped` 的版本，合入后必须仍是 `shipped`、`shipped_at` 不变、文件还在，否则同样拒绝。所以手写 `status: shipped` 合不进 main。

## 例子

- 变更里手写把 `R-1` 的状态改成 `shipped`、写上一个 40 位提交号，合入 → 被拒，原因 `release`，信息说只有 `canon release ship R-1` 能发布
- 变更里新增一个直接写着 `status: shipped` 的 `R-2` → 被拒（原因 `check`：它的 `shipped_at` 那个提交里没有它，BR-2325；或 `release`）
- `canon release ship R-1` 自己开的杂务把 `R-1` 改成 `shipped` → 合入成功，`release.ship` 事件关联这个杂务身份
- main 上 `R-1` 已发布，变更把它改回 `active` → 被拒，原因 `release`
- main 上 `R-1` 已发布，变更改了它的 `shipped_at` 或把它删掉 → 被拒（`canon check` 先发现的原因是 `check`：新的 `shipped_at` 不是装着它的提交，或规则还指着被删的版本；否则原因是 `release`）
- main 上 `R-1` 已发布，变更只改了它的 `## 成功标准` → 不因这条被拒
- 变更把 `R-2` 从 `planned` 改成 `active` → 不因这条被拒
