## 规则

`canon check` 对版本的组合和取消报下面的拦截发现（D-130）：

- `ref-dangling`：版本的 `features` 里有不存在的模块，或 `merged_into` 指向不存在的版本。
- `file-invalid`：`features` 不是模块编号的列表；`merged_into` 写在不是 `dropped` 的版本上，或指向自己。
- `release-composition`：没发布也没取消的版本的 `features` 里有 `dropped` 的模块；同一个模块出现在两个及以上没发布也没取消的版本的 `features` 里（每个版本各报一次，写出另一个版本；模块按 BR-2521 合起来算）；`merged_into` 一路走下去走不到没取消的版本（指向的版本已取消又没写 `merged_into`，或绕成一圈）。
- `release-dropped`：没作废的规则写着 `release: R-n` 而 `R-n` 是 `dropped` 且没有最终并入的版本（BR-2521，D-133），或写着 `feature: F-n` 而 `F-n` 是 `dropped`。并进了别的版本的，它的规则算进那个版本（BR-2521），不报。

已取消的版本的 `features` 里有什么都不报。已作废的规则不报。

状态是 `open` 的变更（有没有计划都一样）写着 `release: R-n` 而 `R-n` 同样无处可去，或写着 `feature: F-n` 而 `F-n` 是 `dropped` 时，不是发现：`canon check` 在标准错误输出一行 `hint change-link-dropped: <C-n> is linked to <R-n 或 F-n>, which is dropped…`（有 `merged_into` 时提示改关联到哪个版本），不改退出码（D-139、D-151）。关联只是工作量的归属（BR-2568），不影响任何版本能不能发。

## 例子

- `R-5` 的 `features: [F-1, F-9]`，没有 `F-9` → `ref-dangling`
- `R-5` active、`R-6` planned，两个都列着 `F-1` → `release-composition`，`R-5` 和 `R-6` 各一条
- `R-1` shipped 列着 `F-1`，`R-6` planned 也列着 `F-1` → 不报（已发布的不算）
- `R-5` 列着 dropped 的 `F-2` → `release-composition`
- `R-3` dropped、`merged_into: R-4`（`R-4` active），`BR-7` 还写着 `release: R-3` → 不报，`BR-7` 算 `R-4` 的规则（BR-2521）
- `R-3` dropped、没写 `merged_into`，`BR-7` 还写着 `release: R-3` → `release-dropped`
- `R-2` 并入 `R-3`、`R-3` 并入 `R-4`（active）→ 不报；`R-3` 又改成并入 `R-2` → 绕成一圈，`release-composition`
- `BR-8` 写着 `feature: F-2`，`F-2` dropped → `release-dropped`
- `BR-8` 同样的标签但已作废 → 不报
- `open` 的 `C-4` 有计划，写着 `release: R-3`，`R-3` dropped、没写 `merged_into` → 不是发现，一行 `hint change-link-dropped`，退出码不变
- `open` 的 `C-5` 写着 `feature: F-2`，`F-2` dropped → 一行 `hint change-link-dropped`
- `done` 的 `C-6` 写着 `release: R-3` → 不提示
- `R-4` active 写着 `merged_into: R-2` → `file-invalid`
