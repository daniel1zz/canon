## 规则

`canon release ship R-n` 的检查按这个顺序：版本存在且没发布、标着它的规则全部已通过（BR-2333），最后是负责人的确认；确认这一步只在前两步都过了才查，所以前两步不过的，退出码按 BR-2333，不管有没有 yes。负责人的确认要求记录过 yes：`canon human` 里有一个已回答的问题，文字含 `ship R-n`（整个编号，不分大小写；`ship R-1` 不匹配 `ship R-12`），回答是 `yes`（也认 `y`、`是`、`确认`、`同意`，不分大小写），并且回答是负责人本人在终端给的，或是 agent 用 `--relayed` 转述且转述的话和 Claude Code 提问工具的记录一致（BR-2276 的 `match`）。有多个这样的问题时，最近回答的那个算数，后来的 `no` 撤销之前的 `yes`。不满足时退出码 1，信息说明缺什么、怎么补（先 `canon human ask`、用提问工具问负责人、再 `canon human answer <n> yes --relayed "<原话>"`），不开变更、不写任何文件、不记 `release.ship` 事件。

## 例子

- 没有任何名字里带 `ship R-1` 的问题 → 退出码 1，信息含 `canon human ask`，没有新变更
- 问题 `ship R-1: 发这一版吗？` 还没有回答 → 退出码 1
- 同一个问题回答 `no` → 退出码 1，信息说负责人没有确认
- 先回答 `yes`，后来另一个 `ship R-1` 的问题回答 `no` → 退出码 1
- 只有 `ship R-12` 回答了 yes，现在发 `R-1` → 退出码 1
- agent 转述 `yes`，但没有提问工具的记录（witness 不是 `match`）→ 退出码 1，信息说转述的话对不上 Claude Code 的记录
- `R-9` 不存在、也没有任何 `ship R-9` 的回答 → 退出码 3（BR-2333），不是 1
- 负责人在终端直接回答 `yes`，或 agent 转述的话和提问工具的记录一致 → 通过这一步（继续按 BR-2333、BR-2334）
