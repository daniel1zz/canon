## 规则

合入时，一个版本在合入的树里变成 `shipped`（BR-2332 要的 `release.ship` 记录也有）时，查两件事：`shipped_at` 必须被验收过——它等于 `refs/canon/accepted` 指向的提交或是它的祖先，而且有对应的 `accept.ok` 事件（ref 不存在、提交解析不出，都算不满足）；BR-2331 的负责人确认仍然有效。不重算 BR-2333 的规则与计划条件（为什么不重算见 D-105）。任一不满足，合入被拒，原因 `release`，退出码 1，main 不动；信息写明缺哪一件，并提示重新运行 `canon release ship R-n`。被拒后发布杂务的工作树和认领还在（BR-2458），条件重新成立后在里面重新运行 `canon chore land` 也能合入，不必从 `release ship` 重来；两条路每次合入都重查。

## 例子

- 通过检查后、发布的杂务合入前，main 上又合入了一个让 `R-1` 某条规则待重新执行的变更 → 照常合入：发布的内容是 `shipped_at` 指向的已验收提交，不重算条件，`R-1` 在 main 上变成 `shipped`
- `shipped_at` 等于 `refs/canon/accepted`，有它的 `accept.ok` 事件 → 合入成功
- 合入等待期间负责人又验收了一个更新的提交（`refs/canon/accepted` 前移）→ `shipped_at` 是它的祖先，照常合入
- `shipped_at` 写成一个从未被验收的提交（没有它的 `accept.ok` 事件）→ 合入被拒，原因 `release`，信息含 `accept.ok`
- 仓库里没有 `refs/canon/accepted` → 合入被拒，原因 `release`，信息提示 `canon accept`
- 通过检查后、合入前，负责人对另一个 `ship R-1` 的问题回答了 `no` → 合入被拒，原因 `release`，信息说确认已失效；后来又回答了 `yes`，重新运行 `canon chore land` → 合入成功，`R-1` 是 `shipped`
