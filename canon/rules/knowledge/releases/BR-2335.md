## 规则

合入时，一个版本在合入的树里变成 `shipped`（BR-2332 要的 `release.ship` 记录也有）时，还要在合入的树上再满足两件事：标着它的规则（作废的不算）全部是“已通过”、标着它的计划所有步骤已完成（和 BR-2333 同一套算法，D-79），并且最近回答的 `ship R-n` 问题仍是有效的确认（BR-2331，后来的 `no` 撤销之前的 `yes`）。任一不满足，合入被拒，原因 `release`，退出码 1，main 不动；信息列出不是“已通过”的规则和没完成的计划步骤，或说明确认已失效，并提示重新运行 `canon release ship R-n`。每次合入都查，包括合入被拒或超时后直接运行 `canon work land --finish`。

## 例子

- `canon release ship R-1` 通过检查后、发布变更合入前，main 上又合入了一个改了 `R-1` 里一条规则行为的变更（这条规则变成待重新执行）→ 合入被拒，原因 `release`，信息列出这条规则，`R-1` 在 main 上仍不是 `shipped`
- 通过检查后、合入前，main 上标着 `R-1` 的计划 `C-5` 多了一个还没人做的步骤 `2` → 合入被拒，原因 `release`，信息含 `plan C-5` 和 `not done: 2`；之后步骤 `2` 由一个已合入的变更完成，直接运行 `canon work land --finish` → 合入成功
- 通过检查后、合入前，负责人对另一个 `ship R-1` 的问题回答了 `no` → 合入被拒，原因 `release`，信息说确认已失效
- 上面两种被拒之后直接运行 `canon work land --finish`，规则仍待重新执行或最近的回答仍是 `no` → 仍被拒，原因 `release`
- 被拒之后规则重新通过（或负责人后来又回答了 `yes`），直接运行 `canon work land --finish` → 合入成功，`R-1` 是 `shipped`
- 通过检查后、合入前没有任何变化 → 合入成功（BR-2334）
