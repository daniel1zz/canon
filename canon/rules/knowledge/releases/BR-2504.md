## 规则

版本文档 `## 成功标准` 一节里，每个不缩进的列表项（行首是 `- `、`* ` 或 `数字. `），只有列表符号之后以 `S<数字>` 加空格开头时才是一条成功标准，`S<数字>` 是它的编号（D-131、D-151）；它下面缩进的子项和续行都属于它。不缩进、却不以这样的编号开头的列表项是说明文字（例如验收方式），不是成功标准：不算状态、不计数、不能被依赖或推进；`canon check` 提示它（BR-2566），`canon release migrate-criteria` 给它编号或把它移出列表（BR-2567）。编号在同一份文档里不重复（BR-2516），变更用 `<文档编号>/S<数字>` 引用它（BR-2517）。

一条成功标准的状态只看它第一行末尾的标记（括号全角半角都算，冒号全角半角都算）：

- `（已满足：<证据>）`：证据里至少写了一个文档编号（写在反引号里的是举例，不算，同 `canon check` 的引用规则）→ 已满足，证据就是这些编号；一个编号也没有 → 未证明。
- `（未满足）` 或 `（未满足：<说明>）` → 未满足。
- `（待负责人）` 或 `（待负责人：<说明>）` → 待负责人。
- 没有标记，或括号里是别的内容 → 未证明：带了编号就是在说“这是一条要达到的结果”，没写证据就还没证明。

这条成功标准的文字是第一行去掉列表符号、编号和末尾标记。模块文档（BR-2507）的成功标准按同样的方式算。标记由写文档的会话按证据改，待负责人的那几条谁能改见 BR-2510。版本标着的规则全部已通过，不会让任何一条成功标准变成已满足（D-129）。证据编号不存在时由 `canon check` 照常报 `ref-dangling`。成功标准的状态在 `canon overview`（BR-2505）、`canon brief`（BR-2506）和 `canon release status`（BR-2328）里看得到。

## 例子

- `- S1 标着 R-5 的规则全部通过。（已满足：BR-584、C-497）` → 已满足，证据 `BR-584`、`C-497`
- `- S2 负责人玩通主线。(已满足: C-12)`（半角括号和冒号）→ 已满足，证据 `C-12`
- `- S2 负责人玩通主线。（已满足：负责人说可以了）` → 未证明（证据里没有文档编号）
- `` - S2 负责人玩通主线。（已满足：`C-12`） `` → 未证明（反引号里的编号是举例）
- `- S3 五个体系各有构筑通关。（未满足：还差两个）` → 未满足，编号 S3，文字“五个体系各有构筑通关。”
- `- S4 负责人完整玩通主线前半部分。（待负责人）` → 待负责人
- `- S5 不需要人在旁边解释。` → 未证明
- `- S5 不需要人在旁边解释。（见 N-4）` → 未证明（不是三种标记之一）
- `1. S6 存档能读回。（未满足）` → 编号 S6，未满足
- 一条下面有缩进的子项，子项末尾写了 `（已满足：C-3）` → 不影响这一条，只看第一行
- `- 验收方式：开发会话自己按清单逐条验收。` → 不是成功标准，不计数
- `- 负责人玩通主线。（已满足：C-12）`（没有编号）→ 不是成功标准，不计数，标记也不算
- `- S3五个体系各有构筑通关。` → 不是成功标准（`S3` 后面没有空格）
- 版本文档没有 `## 成功标准` 一节，或这一节没有带编号的列表项 → 0 条成功标准
- 版本的规则全部已通过，成功标准都没有标记 → 每条都是未证明
