## 规则

成功标准、版本由哪些模块组成、哪些版本和模块不做了，是负责人定的目标（D-130）。合入时把合入的树和 main 上的每个版本文档和模块文档比较，出现下面任一种就算这次合入改了目标：

- 成功标准（BR-2504 的列表项）的文字，空白合并成一个空格之后，在 main 上同一份文档里没有，或 main 上有的一条在合入的树里没有了：新增、删除或改了文字；新建的文档里有成功标准也算新增。
- main 上状态是待负责人的一条（按文字对应），在合入的树里状态不是待负责人了。
- 一个版本的 `features` 列表的成员变了（只换顺序不算）。
- 一个版本或模块变成 `dropped`、或从 `dropped` 变回别的状态，或 `merged_into` 变了。

已发布的版本不比较（它们冻结，BR-2325、BR-2515）。只改已满足、未满足、未证明之间的标记和证据，不算改了目标。

改了目标时，合入必须是一个变更（杂务一律拒绝），变更文件 front matter 的 `owner_answers` 是 `canon human` 问题编号的列表，其中至少一个已经有回答；否则拒绝合入，退出码 1，信息写出每一处改动（文档编号，和那条成功标准的文字或变化的字段），提示先用 `canon human ask` 问负责人、回答记下后把问题编号写进 `owner_answers`。`owner_answers` 不是正整数列表时变更文件报 `file-invalid`。

## 例子

- 变更给 `R-5` 加一条成功标准“支持手柄”，`owner_answers: [51]`，问题 #51 已回答 → 合入
- 同样的改动没写 `owner_answers` → 拒绝，退出码 1，信息里有 `R-5` 和“支持手柄”
- `owner_answers: [52]`，#52 还没回答 → 拒绝
- 把 `（未证明）` 的一条改成 `（已满足：C-9）` → 不算改
- 把 `（待负责人）` 的一条改成 `（已满足：C-9）` → 算改，要 `owner_answers`
- `R-5` 的 `features` 从 `[F-1, F-2]` 改成 `[F-2, F-1]` → 不算改
- `R-5` 的 `features` 加了 `F-3` → 算改
- `canon release drop R-3 --into R-4` 之后合入 → 算改
- `canon release start R-5` 之后合入 → 不算改
- 杂务改了一条成功标准的文字 → 拒绝
- `owner_answers: [abc]` → `file-invalid`
