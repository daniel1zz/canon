## 规则

合入时把合入的树和 main 上的每个版本文档和模块文档比较（已发布的版本不比较，它们冻结，BR-2325、BR-2515），出现下面任一种就算这次合入改了目标（D-130）：

- 成功标准（BR-2504 的列表项）的文字，空白合并成一个空格之后，在 main 上同一份文档里没有，或 main 上有的一条在合入的树里没有了：新增、删除或改了文字；新建的文档里有成功标准也算新增。
- main 上状态是待负责人的一条，在合入的树里同一份文档中没有文字相同（空白合并后）、状态仍是待负责人的一条：删掉了、改了文字或改了状态，都算它离开了待负责人。
- 一个版本的 `features` 列表的成员变了（只换顺序不算）。
- 一个版本或模块变成 `dropped`、或从 `dropped` 变回别的状态，或 `merged_into` 变了。

只改已满足、未满足、未证明之间的标记和证据，不算改了目标。

改了目标的合入照常合入（AI 可以自己调整目标，负责人事后在 `canon overview` 和 `canon brief` 里看到并纠正，BR-2505、BR-2506），合入时先输出一行 `goal: <C-n> changes the goal:`，再每处改动一行（文档编号，和那条成功标准的文字或变化的字段）。两个例外拒绝合入，退出码 1：

- 改了目标的是杂务：目标的改动要有变更文件的 `## 为什么` 说明理由，提示改用变更。
- 有成功标准离开了待负责人：那是负责人本人的验收，变更文件 front matter 的 `owner_answers`（`canon human` 问题编号的列表）里要至少有一个问题已经回答、且是为这个变更问的（`canon human ask --change <C-n>`）；否则拒绝，信息写出那几条成功标准，提示先问负责人。`owner_answers` 不是正整数列表时变更文件报 `file-invalid`。

## 例子

- 变更给 `R-5` 加一条成功标准“支持手柄” → 合入，输出 `goal: C-n changes the goal:` 和一行写着 `R-5` 和“支持手柄”
- 变更给 `R-5` 的 `features` 加 `F-3`，或 `canon release drop R-3 --into R-4` 后合入 → 合入，列出改动
- 把 `（未证明）` 的一条改成 `（已满足：C-9）` → 不算改，没有 `goal:` 那几行
- `R-5` 的 `features` 从 `[F-1, F-2]` 改成 `[F-2, F-1]` → 不算改
- `canon release start R-5` 之后合入 → 不算改
- 把 `（待负责人）` 的一条改成 `（已满足：C-9）`，没写 `owner_answers` → 拒绝，退出码 1
- 把 `- 负责人玩通主线。（待负责人）` 改成 `- 负责人玩通了主线。（已满足：C-9）`（文字和状态一起改）→ 同样算离开待负责人，拒绝
- 删掉一条待负责人的成功标准，没写 `owner_answers` → 拒绝
- 同样的改动，`owner_answers: [51]`，#51 是为这个变更问的、已回答 → 合入
- `owner_answers: [48]`，#48 已回答但是为别的变更问的或没写变更 → 拒绝
- 杂务改了一条成功标准的文字 → 拒绝，提示用变更
- `owner_answers: [abc]` → `file-invalid`
