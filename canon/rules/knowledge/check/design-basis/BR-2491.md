## 规则

`canon/config.yaml` 的 `design_signals` 按单向门的三类给出路径的 glob：`persistent`（持久数据的结构、版本、迁移、恢复）、`boundary`（跨进程、外部服务、认证或权限、外部工具的配置）、`dependency`（新增或更换依赖）。没写的类用默认值：`dependency` 是常见的包清单和锁文件（`**/package.json`、`**/bun.lock`、`**/package-lock.json`、`**/pnpm-lock.yaml`、`**/yarn.lock`、`**/requirements*.txt`、`**/pyproject.toml`、`**/Cargo.toml`、`**/go.mod`、`**/Gemfile` 等，完整列表以代码 `DEFAULT_DESIGN_SIGNALS` 为准），`persistent` 是 `**/migrations/**`，`boundary` 为空；某类写成 `[]` 就不看这一类。`canon/` 下的文件不算。写了未知的类，或值不是 glob 列表，是配置错误，退出码 2。

在一个变更或杂务的 worktree 里运行 `canon check` 时，如果这次工作（相对它的 base，加上还没跟踪的文件）改到某一类的路径，而这个变更的文件没有 `## 方案依据` 一节、或这一节只有模板占位行（整行是 `<...>`），就在标准错误输出写一条 `note:`，不算 finding，不影响退出码。这条提示写明 `BR-2491, D-124`，说明在哪里写（变更文件的路径；杂务没有变更文件，提示新选择要放进变更里做），列出要写的内容：沿用了哪个决策的哪一部分、新做了什么选择、最坏的失败、证据、什么结果能证明它选错了，以及按触发的每一类要回答的问题（附最多 3 条触发的路径）：

- `persistent`：数据以后怎样演进（旧文件加新的一节、迁移），坏了怎样恢复（损坏、恢复后再写一次），并说明试过最小的失败情形；
- `boundary`：外部对象自己的配置和限制（官方文档或源码）；文档回答不了的，在真实部署方式下做一次最小探测；
- `dependency`：为什么用这个依赖而不是自己写或用别的，以及它在实际运行环境里的限制。

证据按还没消除的不确定性取：来源能回答的给来源，来源回答不了的做最小实验，不是改到路径就每类都要实验。沿用一个决策时，只有它明确决定过的部分、而且前提没变，才只写“沿用哪个决策的哪一部分”；超出那部分的都是新选择，要按上面回答。只提示不拦，是因为路径看不出这次是不是新选择（D-124）。主 checkout 里不给这条提示。

## 例子

- 变更改了 `package.json`，变更文件没有 `## 方案依据` → `canon check` 的标准错误输出含 `this work touches one-way-door paths (BR-2491, D-124)` 和 `dependency (package.json): why this dependency over building it or another one`；退出码不变
- 同上，`## 方案依据` 下只有 `<what it reuses>` → 仍有这条提示
- 同上，`## 方案依据` 下写了内容 → 没有这条提示
- 只改了 `src/a.ts` 和 `canon/changes/C-1.md` → 没有这条提示
- `design_signals: {persistent: ["game/src/save_game/**"]}`，变更改了 `game/src/save_game/store.gd` → 提示 `persistent`
- `design_signals: {dependency: []}`，改了 `package.json` → 没有提示
- `design_signals: {saves: ["a/**"]}` → 退出码 2，信息含 `design_signals`
