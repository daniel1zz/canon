# 检查（knowledge/check）

`canon check` 检查整个 `canon/` 是否自洽：文件格式、编号唯一、引用存在、领域的代码位置（README 的 `code:` 或 `code_root` 下的目录）和代码目录对得上、规则有测试的名字点名（读测试报告的记账，BR-2005）、本变更碰的测试文件有当前内容的报告（BR-2344）、必填段落非空、没有残留的模板占位行、规则 `lists` 声明的代码列表和文字及代码对得上、规则和决策的 `links` 只记正文点名的引用（BR-2426）、测试不读 `floor_skip_paths` 下的真实文件。合入时也会跑它（`work/land`）。另有三种只提示、不算发现的输出：固定加载的文字超出预算（BR-2257），架构总览没写出早就有的领域的代码目录（BR-2352），和某个顶层领域的规则评审提示接近 `review_max_prompt_kb`（BR-2375）。总览 `canon/architecture.md` 有内容时，还查它写的路径（BR-2171）、新增领域有没有写进去（BR-2352）、引用的决策有没有被取代（BR-2353）、修订或取代它引用的决策时有没有改总览（BR-2354）。

## 业务

- **文档的格式和必填**：一份文档自身写全了没有：该有的段落在不在、空不空、模板占位行清掉没有、例子写的是不是现在的行为。
- **编号和引用**：文字和 front matter 里提到的编号指向的东西存在，而且是它该是的那一类。
- **文字和仓库对得上**：文档里写的路径、摘录和代码列表，在仓库里还找得到、还和代码一致。
- **规则和测试互相点名**：每条生效的规则有会运行的测试点名它，测试点的规则还在，本变更碰过的测试文件有当前内容的报告。
- **领域和代码对得上**：每个领域有 README，领域和 `code_root` 下的目录一一对应，代码路径写在该写的地方，名字像技术层时说一声。
- **架构总览的检查**：`canon/architecture.md` 有内容时，新增的领域写进去了没有、它引用的决策还作不作数。
- **承诺落到规则**：决策许下的行为有一条生效或计划中的规则接住、规则链回决策，推迟到以后的行为不会无声丢掉。
- **固定加载的文字大小**：每个会话开始都会读到的那些文字有多大，超预算时说一声。
- **检查怎么跑和怎么报**：`canon check` 遍历仓库时不被符号链接绊住，每条发现怎么输出，有发现时退出码是几。

## 术语

- **发现（finding）**：一条检查结果，带种类（如 `ref-dangling`）、文件和说明。
- **提示（hint）**：写在标准错误上、以 `hint ` 开头的一行，不算发现，不改变退出码。
- **测试名**：JUnit 报告里一个 `testcase` 的外层 `testsuite` 名、`classname` 和 `name`；只有会运行的（没有 `skipped`）测试名里的规则编号才算这条规则有测试（BR-2005）。
- **报告记账**：协调数据库里每个（测试文件路径，文件内容的 git blob 哈希）一行的 `testcase` 列表（BR-2337）；`canon check` 只读它，不运行任何东西。
- **共享代码**：`shared` 列出的、不属于任何业务领域的代码（共享内核，BR-2116）；`code_root` 和 `shared` 写在 `canon/config.yaml`，声明在 `src/knowledge/check/config-keys.ts`。
