title: 待办清单里的编号必须是存在的变更
status: active
business: 编号和引用
---

## 规则

`canon/backlog.md` 里排进清单的每个编号（BR-2148 认定的列表项开头的编号），如果没有这个编号的变更，也没有这个编号自己的变更分支（`change/C-n`、`change/C-n-…`）上提交的它的变更文件（BR-2291，负责人也能排还没合入的变更），就是失效的编号。已完成或已放弃的变更不算失效。没有 `canon/backlog.md` 时什么都不报。

失效的编号只拦截加进它的人：main 最新提交上的 `canon/backlog.md` 和这个 checkout 的起点（`git merge-base HEAD main`）上的 `canon/backlog.md` 都没有列出这个编号时，`canon check`、`canon work test` 和合入报告一条 `ref-dangling`（位置 `canon/backlog.md:<行号>`，说明 `lists C-n, which is not a change`），拦截合入，这只会发生在改了 `canon/backlog.md` 的工作里，也就是负责人打错编号的那一次。其中任何一份已经列了这个编号时（它的分支后来被 `canon work drop` 删了，或者本地没有那个分支；或者负责人已在 main 上删掉这一行，这个 worktree 还没 rebase），它只是一条提示，不算发现、不影响退出码：`canon check` 在标准错误上、`canon work test` 和合入在输出里写一行 `note: canon/backlog.md:<行号>: lists C-n, which is not a change on main or on a local change branch; remove the line, or restore its branch`。原因：删分支的人不改清单，没碰清单的合入和 main 上的检查不能因此被拦住。

## 例子

- 清单第 3 行是 `- C-99`，main 最新提交的清单和这个 checkout 起点的清单里都没有 `C-99`，也没有 `C-99` 这个变更 → `canon check` 报告 `ref-dangling`，位置 `canon/backlog.md:3`，说明 `lists C-99, which is not a change`（整行的格式见 BR-2189），退出码 1；这次改清单的合入被拒，原因 `check`
- 清单里的 `C-1` 已经 done，`C-2` 已经 dropped → 都不报告
- 没有 `canon/backlog.md` → 不报告
- 清单是 `- C-9`，main 上没有 `C-9`，分支 `change/C-9-x` 上有 `canon/changes/C-9.md` → 不报告
- 新加的一行 `- C-9`，只有分支 `change/C-9-x`，上面没有 `C-9` 的变更文件 → 报告 `ref-dangling`
- main 的清单已经列了 `- C-9`（当时分支上有它），之后 `canon work drop C-9` 删了分支；一个没改清单的变更合入 → 照常合入，输出里有 `note: canon/backlog.md:<行号>: lists C-9, which is not a change on main or on a local change branch; remove the line, or restore its branch`
- 同样情形，在主 checkout 里 `canon check` → 退出码 0，标准错误有这条 `note:`
- worktree 从列着失效编号 `C-9` 的 main 上开出，之后负责人在 main 上删掉了 `- C-9` 那一行，这个 worktree 没 rebase、也没改清单 → 在它里面 `canon check` 和 `canon work test` 只输出 `note:`，退出码 0
- main 最新提交的清单没有 `C-9`（负责人已删掉那一行），这个 worktree 起点的清单列着 `- C-9`，worktree 没改清单 → 只输出 `note:`，退出码 0
