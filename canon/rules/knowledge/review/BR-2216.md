## 规则

规则评审和常驻说明的重复评审都用配置里的 `review` 命令：canon 在一个临时 worktree 里用 `sh -c` 运行它：这个 worktree 在 main 的提交上（分离 HEAD，不检出分支），建在 canon 的状态目录下，不在项目的受控目录里；规则评审和重复评审共用同一个，只在真有评审要跑时才建，评审结束后（通过、拦下、超时、非 0 退出、无效结论、被信号终止，都一样）删掉；批量合入也用 main 的提交，不用批量链上的提交。这样变更改不了评审用的脚本，也改不了 `claude -p` 读的 `CLAUDE.md`、`.claude/settings.json` 和 `.claude/skills`（D-51）。临时 worktree 删不掉时，合入以环境错误被拒绝，不会把结论当作通过。评审提示本身已带着评审要读的全部文字，所以不用变更的目录。把评审提示从标准输入交给它，从标准输出里取第一个 `{` 到最后一个 `}` 之间的文字当作 JSON 结论，前后可以有别的文字。结论里 `verdict` 必须是 `ok` 或 `block`；`findings` 是字符串列表，没有或不是列表时当作没有意见。命令以非 0 退出时，错误是 `review command exited <退出码>: <标准错误的前 500 个字符>`；输出里没有 JSON、JSON 解析不了、或 `verdict` 是别的值时，是无效结论；这两种情况合入都被拒绝（BR-2009、BR-2143），拒绝信息另起一行说明评审是在 main 提交的哪个临时 worktree 里运行的、那里只有提交进 git 的文件，被 git 忽略的文件（如 `node_modules`、`.env`、`*.local.json`）不在，评审命令不能依赖它们。

## 例子

- 命令输出 `Here is my answer: {"verdict":"block","findings":["BR-1 is vague"]} done` → 结论 `block`，意见 `BR-1 is vague`
- 命令输出 `{"verdict":"ok"}` → 结论 `ok`，没有意见
- 命令先读完标准输入再回答 → 读到的就是完整的评审提示
- 命令输出 `looks fine to me`（没有 JSON）、`{"verdict":"ok",}`（解析不了）或 `{"verdict":"maybe"}` → 无效结论
- 命令向标准错误输出 `boom` 并以退出码 3 结束 → `review command exited 3: boom`，下一行写明 main 的提交和 `git-ignored files such as node_modules`
- 变更改了评审脚本（例如 `scripts/review-claude.sh`）→ 运行的是 main 上的那一版
- 变更加了 `CLAUDE.md` 的一行、改了 `.claude/settings.json` 或新增一个 skill → 评审命令的工作目录里是 main 上的版本，没有变更的改动；main 上已有的这些文件都还在
- 评审通过、被拦下、超时或被信号终止之后 → `git worktree list` 里没有这个临时 worktree
- 主 checkout 在别的分支上或有未提交的改动 → 评审照样在 main 的提交上运行
- 临时 worktree 删不掉（例如被锁住）→ 合入被拒绝，原因 `environment`，不算评审通过
- 评审命令读 `.env`（被 git 忽略，只在 worktree 里有）→ 读不到，命令失败，合入被拒，信息里有 main 的提交和被忽略文件不在的说明
- 评审通过或拦下 → 信息里没有这句说明
