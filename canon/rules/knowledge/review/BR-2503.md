## 规则

合入后的代码评审（BR-2070，项目在 `after_land` 里运行 `scripts/code-review.ts` 时才有）的评审范围里有 worker 的合入时，对每个这样的合入按 BR-2501 记在 `land.ok` 里的派发快照（不按现在的 main 或派发），提示另外给出：快照里契约清单每一项在快照的设计版本上的全文，以及这次合入自己的 diff（它的 base 到它的提交），要求再找一类问题：这段 diff 定下了一个业务上的选择（用户能看到的结果、出错时怎么办、存下来的数据格式、对外的接口），而契约清单都没写到。

只看改了 `canon/` 以外文件的 worker 合入：业务选择在代码里，只改 `canon/` 的合入没有可找的；整个范围没有改 `canon/` 以外的文件时，按 BR-2070 不调用评审命令，这一条也不让它调用。

这一类发现的类别是 `design-gap`，除 BR-2071 要的几项外还要写明是哪一次合入：提示给每次 worker 合入列出它的 `land.ok` 事件编号和合入提交，发现写其中一个；同一个变更可以合入几次，变更编号只作显示。写的不是这个范围里 worker 合入的 `land.ok` 编号 → 丢弃，打印 `dropped ...`；每条开一个带 `canon-design-gap` 标签的 issue，写明变更、合入者、设计负责人、代码位置和那个没写到的选择，交给设计负责人决定补规则还是改代码，不交给 worker。

按 D-128。哪些代码算“业务选择”、契约清单算不算“写到”，由评审命令判断，canon 判定不了；测试判定的是：有 worker 的合入时提示里有上面的全文、diff 和这条要求，没有时没有；评审命令返回 `design-gap` 发现时开出的 issue 带标签并写明上面几项；评审命令没返回时不开。canon 不判定、也不统计这一类发现准不准：issue 由设计负责人按平常的 issue 流程关闭。项目没运行 `scripts/code-review.ts` 时没有这一项，`canon work delegate` 会提示（BR-2497）。

生效时 BR-2070 的“只找安全和并发问题”改成：只找安全和并发问题，范围里有 worker 的合入时再按本条找 `design-gap`；BR-2071 接受的类别加上 `design-gap`。

## 例子

- 范围里有 `agent:s7:w1` 合入的 `C-9`，它的契约清单只有 `BR-50`，`C-9` 的 diff 写了“敌人丢失目标 2 秒后回巡逻”，`BR-50` 没写丢失目标 → 评审可以报一条 `design-gap`，开 `canon-design-gap` issue，写明设计负责人 `agent:s1`
- 同上，`BR-50` 写了“丢失目标 2 秒后回巡逻” → 不报这一类
- 同上，契约清单里的 `docs/DESIGN.md` 写了丢失目标 2 秒后回巡逻 → 不报这一类（它在清单里，提示里有全文）
- 派发之后、评审之前 `agent:s1` 把丢失目标写进了 `BR-50` → 提示里仍是 `land.ok` 记下的设计版本上的 `BR-50`
- 范围里只有主会话的合入 → 提示里没有这一类要求
- 范围里只有一个 worker 合入，它只改了 `canon/` 下的文件 → 按 BR-2070 不调用评审命令
- 用假的评审命令返回一条 `design-gap` 发现 → 开一个 `canon-design-gap` issue，正文有变更、合入者、设计负责人和代码位置；返回的 `design-gap` 缺 `land.ok` 编号、或编号不在这个范围的 worker 合入里 → 丢弃，打印 `dropped ...`
- 同一个范围里 `C-9` 按代次 1 和代次 2 各合入一次，发现写了第二次的 `land.ok` 编号 → issue 写的是第二次的设计负责人和快照
- 代码里只是内部变量命名、函数怎么拆 → 不算业务选择；测试验证的是提示里有这条界线，实际报不报由评审命令判断
