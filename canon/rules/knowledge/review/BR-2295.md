---
id: BR-2295
title: 关掉评审的配置改动要单独合入，不能和要评审的改动在同一次合入里
status: active
---

## 规则

被合入的树（rebase 之后）里 `review` 是 `none` 或没有配置，而 main 上（合入开始时 main 的提交，一起测时是整批的 base，同 BR-2248）的 `review` 不是同一个值时，这次合入就是在关掉或删掉评审；这时它只要还新增、修改或删除了需要评审的文件（`canon/rules`、`canon/decisions` 下的文件，BR-2009；常驻说明，BR-2143），合入就被拒，退出码 1，原因 `review`，main 不动。信息先给出评审命令的写法（例如 `review: "claude -p --output-format text"`），再说明 `review: none` 是负责人的决定：用 `canon human ask` 问负责人，得到同意后把只改 `canon/config.yaml` 的那个变更单独合入。理由：关掉评审的同一次合入里的文字改动，正好是没人评审就进了 main 的那一批；`canon/config.yaml` 本身不在规则评审（BR-2009）和常驻说明评审（BR-2143）的范围内，单独合入至少让关掉评审这件事成为一次看得见的合入。main 上已经是 `review: none` 时，这一步不拒绝（BR-2074 照常跳过评审）。

## 例子

- main 上 `review: "claude -p"`，变更把它改成 `review: none`，又改了一条规则 → 退出码 1，原因 `review`，信息里先出现 `claude -p --output-format text`，再出现 `canon human ask`，main 不变
- main 上没有 `review`，变更加上 `review: none`，又改了 `CLAUDE.md` → 拒绝，原因 `review`
- 同一个变更只把 `review` 改成 `none`，不改规则、决策或常驻说明 → 照常合入
- main 上已经是 `review: none`，变更改了一条规则 → 不由这一步拒绝，按 BR-2074 跳过评审、合入
- main 上 `review: "claude -p"`，变更把这一行删掉，又改了一条决策 → 拒绝，原因 `review`
