## 规则

canon 自己的仓库发布新的 canon（`after_green` 运行 `scripts/release.ts`，在后台测过的提交的临时 worktree 里，BR-2222）之前先做发布评审：这个提交里每个 `.claude/skills/canon-*/SKILL.md` 的全文和 `canon brief` 的工作说明一起交给配置的 `review` 命令（取自这个提交的 `canon/config.yaml`，`CANON_REVIEW_KIND` 按 BR-2366），找写在两处、或在一处写了两遍的同一条要求；拦截标准只有 `duplication`，结论由 canon 按标准推出（同 BR-2367），不比较这次和上次的差别，所有重复都算。这些文字和上一次发布评审时完全相同（按全部文字的哈希，记在协调数据库的 `release.review` 事件里）时沿用那次的结论，不再调用评审命令。提示超过 `review_max_prompt_kb` 时拆成几次调用：每次都带评审说明、工作说明和“这是第几次、共几次”的说明（固定部分，说明按最长的写法预留）；skill 按目录名顺序依次装进块，一块不超过（预算减固定部分）的一半，下一个装不下就开新的一块；每次调用装其中两块，每两块都同在一次调用里，所以任意两个 skill 至少同时出现在一次调用里，每次调用不超过预算。最大的 skill 超过（预算减固定部分）的一半时，它放不进任何一块，这时不调用评审命令，以退出码 4 失败，信息写明需要多少 KB（固定部分加两倍最大的 skill）和 `review_max_prompt_kb` 至少要调到多少。拦截时不发布任何东西（`dist/canon` 和 `dist/skills` 保持上一次发布的样子），在标准错误输出写明每条发现，以退出码 1 结束，并把发现写到 GitHub 上标题固定为 `Release check: canon's shipped skills repeat a requirement`、带 `canon-review` 标签的 issue，同一根因一个 issue 按 BR-2072；沿用的拦截结论不再写 GitHub。通过时按 BR-2412 发布。没有配置 `review`、评审命令失败、写 GitHub 失败时，以退出码 4 失败并且不发布；发布评审不接受 `review: none`（合入时那是明确跳过评审，D-51；发布跳过评审正是 #159、#182 的来源），同样以退出码 4 失败。`bun scripts/release.ts --check` 只对当前 checkout 做这次评审并打印结论，拦截时退出码 1，不发布也不写 GitHub。

## 例子

- `canon-a` 和 `canon-b` 都写着“合入前先跑测试”，评审回答 `duplication` → 退出码 1，`dist/canon` 还是原来的内容，`dist/skills` 不变，标准错误输出有这条发现，GitHub 上新建了标题为 `Release check: canon's shipped skills repeat a requirement` 的 issue
- 同样的文字下一次后台测试通过时再运行 → 评审命令没被调用，仍退出码 1、打印同样的发现，GitHub 上没有新的 issue 或评论
- 已有同标题的未关闭 issue #31 → 发现评论在 #31 下，不新建
- 评审回答没有发现 → 一次调用，提示里有每个 `canon-*` 的 SKILL.md 全文和工作说明，没有项目自己的 skill；随后发布
- 文字没变，再运行一次 → 输出 `verdict reused`，评审命令没被调用，照常发布
- 6 个 skill 合计超过预算 → 拆成几次，每次不超过预算、都有工作说明，任意两个 skill 至少同在一次里
- 预算减固定部分是 100 KB，最大的 skill 60 KB、其余各 10 KB → 退出码 4，信息有 `raise review_max_prompt_kb to at least`，评审命令没被调用
- 同样的预算，最大的 skill 50 KB → 照常拆分，每次调用不超过预算
- `review: none`，或评审命令以退出码 3 结束 → 退出码 4，`dist/canon` 没有被写
