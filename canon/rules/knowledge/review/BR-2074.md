## 规则

要不要评审，看这次合入改了什么（BR-2009 和 BR-2143 列出的文件）。怎么评审：评审命令 `review`、时限 `review_timeout_minutes`（BR-2296）、每次调用提示的预算 `review_max_prompt_kb` 和同时运行的调用数 `review_parallel`（BR-2359）和常驻说明清单 `instructions`（BR-2143），都取自合入前 main 上（合入开始时 main 的提交；一起测时，每个成员取它下面那个提交，BR-2172）的 `canon/config.yaml`，也就是已经合入、可信的配置；不取自被合入的树，也不取自运行 `canon work land` 的 worktree 读到的配置。理由：取自变更自己的树时，变更可以在同一次合入里把评审命令换成总是回答 ok 的命令，给自己的文字放行（#115）。所以在一次合入里改 `review`，只对之后的合入生效；同一次合入把 `review` 改成 `none` 或删掉，它自己的文字照样由原来的命令评审。

合入前的 main 上没有配置 `review`（没有这个键，或者值为 `null`、空字符串、只有空白）时，改了这些文件的合入照常成功，不因此被拒（D-89 修改 D-51），也不排评审（BR-2441）：它写一条 `review.skip`（`docs`、`landed`、`reason` 为 `unconfigured`），输出这些文件没有评审就合入了、验收会因此不通过，再给出评审命令的写法：把 `review` 设成从标准输入读提示、在标准输出给出结论 JSON 的命令（BR-2216），例如 `review: "claude -p --model sonnet --output-format text"`；然后建议 `review: none` 先用 `canon human ask` 问负责人，得到同意后单独合入；canon 不核对写 `none` 的是谁、问没问过。

`review: none` 表示项目明确不评审：合入照常进行，输出 `review: none — <文件> landed without a review`，写一条 `review.skip`（`reason` 为 `none`）。`none` 不是命令，不按 BR-2197 检查。写成 `None`、`"none "` 这类去掉空白、不分大小写后是 `none` 的值是配置错误（BR-2045）。例外：正在关闭的变更带审查判定为措辞修改的通过记录时，没有评审命令来判断，没有配置和 `review: none` 都拒绝合入（原因 `review`，BR-2239）。

## 例子

- 改了一条规则，main 上没有 `review` → 合入成功，输出含这条规则的编号和 `landed without a review`，`claude -p --model sonnet --output-format text` 出现在 `review: none` 之前，含 `canon human ask`；事件表有一条 `review.skip`，`reason` 是 `unconfigured`；没有排队的评审
- 只新增了一个版本文档，main 上没有 `review` → 同样合入成功，输出含这个版本的编号
- 只删了一条决策，main 上 `review: ""` 或 `review: "  "` → 同样，`reason` 是 `unconfigured`
- main 上是 `review: none`，改了一条规则 → 输出含 `review: none`，`review.skip` 的 `reason` 是 `none`，合入成功
- 只改了代码和变更文件，main 上没有 `review` → 不评审，没有 `review.skip`，合入成功
- main 上的评审命令回答 `block`，变更把 `review` 换成总是回答 `ok` 的命令，又改了一条规则 → 合入后用 main 上的命令评审，评审事件是 `review.block`，变更里那条命令没有运行
- main 上没有 `review`，变更同时设了评审命令、又改了一条规则 → 合入成功，这条规则没有评审（`reason` 是 `unconfigured`），变更自己的命令没有运行；之后改规则的合入用这条命令评审
- worktree 建立时 main 上还是 `review: none`，之后 main 上改成了评审命令，这个 worktree 没动 `review`、改了一条规则再合入 → 用 main 上现在的评审命令，这条规则被评审
- main 上配了评审命令，变更把 `review` 改成 `none` 或删掉，又改了一条规则 → 合入成功，这条规则在合入后照样由原来的命令评审
- `review: none`，关闭的变更带一条 `… wording` 的通过记录 → 拒绝，原因 `review`
