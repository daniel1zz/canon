title: 有规则或决策改动但没有配置评审命令时拒绝合入，review 写成 none 才明确跳过评审
status: active
---

## 规则

是否评审、用哪个评审命令，看被合入的树（rebase 之后，也就是将成为 main 的那棵树）里的 `canon/config.yaml`，不看运行 `canon work land` 的 worktree 合入开始时读到的配置。

一次合入新增、修改或删除了 `canon/rules` 或 `canon/decisions` 下的文件，被合入的树里却没有配置 `review`（没有这个键，或者值为 `null`、空字符串、只有空白）时，合入被拒，退出码 1，原因 `review`，main 不动；信息列出要评审的文档，先给出评审命令的写法：把 `review` 设成从标准输入读提示、在标准输出给出结论 JSON 的命令（BR-2216），例如 `review: "claude -p --output-format text"`；再说明 `review: none` 是负责人的决定，要先用 `canon human ask` 问，同意后单独合入（BR-2295）。

`review: none` 表示项目明确不评审：main 上已经是这个值时，这样的合入照常进行，输出 `review: none` 和被跳过的文档，并写一条 `review.skip` 事件。`none` 不是命令，不按 BR-2197 检查。在同一次合入里把 `review` 改成 `none` 见 BR-2295；写成 `None`、`"none "` 这类去掉空白、不分大小写后是 `none` 的值是配置错误（BR-2045）。例外：正在关闭的变更带审查判定为措辞修改的通过记录时，没有评审来判断，没有配置和 `review: none` 都拒绝合入（原因 `review`，BR-2239）。

## 例子

- 改了一条规则，配置里没有 `review` → 退出码 1，原因 `review`，信息含这条规则的编号，`claude -p --output-format text` 出现在 `review: none` 之前，信息含 `canon human ask`，事件表没有 `review.skip`，main 不变
- 只删了一条决策，配置里 `review: ""` 或 `review: "  "` → 同样被拒，原因 `review`
- main 上是 `review: none`，改了一条规则 → 输出含 `review: none`，事件表多一条 `review.skip`，合入成功
- 只改了代码和变更文件，配置里没有 `review` → 不评审，合入成功
- worktree 建立时 main 上还是 `review: none`，之后 main 上改成了评审命令，这个 worktree 没动 `review`、改了一条规则再合入 → rebase 后的树用评审命令，这条规则被评审
- main 上配好了评审命令，worktree 从更早、还没有 `review` 的 main 建立，没动 `review`、改了一条规则 → 不因“没有配置”被拒，规则被评审
- `review: none`，关闭的变更带一条 `… wording` 的通过记录 → 拒绝，原因 `review`
