## 规则

`canon finding close` 先按 BR-2453 核对修复提交或原文，再按意见的档位（BR-2477）核对谁能结案（D-118）。结案的人是谁，只从宿主环境判断，不看 `--as` 和 `CANON_ACTOR`：环境里有 `CODEX_SESSION_ID` 或 `CODEX_THREAD_ID`，或者 `CLAUDECODE=1`（不论有没有 `CLAUDE_CODE_SESSION_ID`），就是 agent 会话；都没有、执行者是 `human:<用户名>` 的就是负责人，任何档位都只要 BR-2453 的凭据。agent 会话按下面的顺序检查，先成立的一条决定结果，被拒时退出码是 1，什么都不写。这些检查读的都是写入时那一刻的状态：档位、意见和问题的读取、检查和写入在同一个写事务里，别的会话在这之前提交的升档或反对都会被看到；读 git 的检查都用同一个 main 提交（#222、#224）：

- 还没定档 → 拒绝，提示先 `canon finding tier`。
- 已定档、带了 `--owner <问题编号>` → 按 BR-2480 核对负责人的批准，通过就能结案，不论哪一档。
- C 档没带 `--owner` → 拒绝，提示用 `canon finding ask` 问负责人。
- A 档按修复（`--fixed`）结案 → 可以；按不成立（`--spurious`）结案 → 拒绝，提示升到 B。
- B 档，结案的是子 agent 或派出的 worker（按 BR-2479 不独立的）→ 拒绝，提示由它的会话按另一个会话的支持结案，或者问负责人（带 `--owner` 的那一条照样可以）。
- B 档 → 要有另一个会话按 BR-2479 支持的就是这一种结案（同一个修复提交，或同一段原文；按不成立结案时还要按 BR-2479 是对现在的文档给的）；结案的会话自己的、和它同一个会话的（它的上级会话或别的子 agent，按会话编号算，不看子线程）意见都不算支持（#225）；任何一个会话对这种结案最新的意见是反对 → 拒绝；没有支持 → 拒绝，提示去找另一个会话，没有别的会话可找时改问负责人（`canon finding ask`，再 `--owner`）。

`finding.close` 事件另外记下档位，以及凭据：负责人结案的写 `by: owner`，B 档写支持它的会话，用了负责人回答的写问题编号（和引用的原文）。

## 例子

- agent 会话关还没定档的 #1 → 拒绝，退出码 1，输出含 `has no tier yet`；带着负责人已批准的 `--owner` 也一样先被拒绝
- #1 是 A 档，`--fixed` 一个修复提交 → 关闭；`--spurious "untested: fixture"` → 拒绝，输出含 `a spurious close needs another session's support`
- #1 是 B 档，只有结案的会话自己记了支持 → 拒绝
- #1 是 B 档，另一个会话支持修复提交 X，结案用的是更新的提交 Y → 拒绝；那个会话后来又反对 X → 用 X 结案被拒绝，输出含 `opposes`；它再支持 Y → 用 Y 结案成功，事件里有 `tier: B` 和那个会话
- #1 是 B 档，没有别的会话支持 → 拒绝，输出含 `ask the owner instead (canon finding ask 1, then --owner <question>)`；负责人批准后带 `--owner` 结案 → 关闭
- #1 是 C 档，不带 `--owner` → 拒绝，输出含 `the owner decides`
- 不在 agent 会话里的人关还没定档的 #1 → 关闭，事件里有 `by: owner`
- #1 是 A 档，结案读完档位之后、写入之前，另一个会话把它升到 C → 结案被拒，输出含 `is tier C`
- #1 是 B 档，有顾问支持修复 X，结案写入之前顾问又提交了反对 → 结案被拒，输出含 `opposes`
- Codex 会话 `root-s` 支持修复 X，它的子 agent（同一个 `root-s`，子线程 `child-t`）结案 → 拒绝，输出含 `this is a subagent`；同一会话的另一个子 agent 的支持也不算；负责人批准了这次结案后，子 agent 带 `--owner` 结案 → 关闭
