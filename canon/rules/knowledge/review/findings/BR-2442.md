## 规则

合入后的规则评审和重复评审（BR-2441）结束时，每条点名拦截标准的意见（BR-2367）先交给 `review_verify` 配置的核实命令判断是否成立，再写评审事件。核实命令和 `review` 一样取自合入前 main 上的配置（BR-2074），在同一个临时 worktree 里运行（BR-2216），时限是 `review_timeout_minutes`（BR-2296），环境变量 `CANON_REVIEW_KIND` 是 `verify`；每条意见运行一次，标准输入里有这条意见点名的标准的说明（和评审提示里的那一句相同）、意见原文，以及它点名的每份文档在合入的提交上的全文：一份都没点名的，是它所挂的文档（规则评审的是这次评审的文档，重复评审的是改动的常驻说明）。核实命令在标准输出里给出 JSON `{"holds": true|false, "reason": "<理由>"}`。

- `holds` 为 `true`：意见按 BR-2434 记成未处理的意见，日志写 `review finding verified (<理由>): <意见>`；
- `holds` 为 `false`：不记成未处理的意见，日志写 `review finding rejected by review_verify (<理由>): <意见>`；
- 没有配置 `review_verify`：意见原样记成未处理的意见，日志写 `review finding not verified (no review_verify on main): <意见>`；
- 核实命令运行失败、超时、没有输出 JSON，或 JSON 里没有布尔的 `holds`：同样原样记账，日志写 `review finding not verified (<原因>): <意见>`，原因里有 `review_verify could not run` 或 `review_verify gave no "holds" true or false`。

一条拦截意见都不会被悄悄丢掉：每次核实的结果（`finding`、`holds` 为 `true`、`false` 或 `null`、`reason`）都记在这次评审的 `review.ok` 或 `review.block` 事件的 `verified` 里，被核实命令否定的也在，`verifier` 是用的核实命令（没有时为 `null`），供 `canon stats` 统计；未处理的意见记的事件就是这条评审事件，提交是合入的提交。有意见记成未处理的意见时，日志多一行，写明记成了哪几条（`#编号`）和 `canon context <id>` 列出它们。建议（`note`）不交给核实命令。

## 例子

- 意见 `[contradiction] BR-1 和 BR-7 的「三天」矛盾`，核实命令答 `{"holds":true,"reason":"两条都写了到账天数"}` → 记成未处理的意见，挂在 `BR-1` 和 `BR-7` 上，日志含 `review finding verified (两条都写了到账天数)`
- 核实命令答 `{"holds":false,"reason":"BR-7 写明只适用于海外订单"}` → 没有未处理的意见；`review.block` 的 `verified` 里有这条意见，`holds` 为 `false`
- 没有配置 `review_verify` → 记成未处理的意见，日志含 `not verified (no review_verify on main)`，`verified` 里这条的 `holds` 为 `null`
- 核实命令以 2 退出 → 记成未处理的意见，日志含 `review_verify could not run`
- 核实命令答 `{"holds":"yes"}` → 记成未处理的意见，日志含 `gave no "holds" true or false`
- 意见点名了这次合入没改的 `BR-7` → 核实命令的标准输入里有 `BR-7` 的全文
- 评审只给了 `note` → 核实命令没有运行
- 变更把 `review_verify` 换成总是答 `false` 的命令 → 核实这次合入的意见用的是合入前 main 上的那一个
