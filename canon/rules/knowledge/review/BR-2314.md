## 规则

`scripts/code-review.ts` 每次合入后运行（`after_land`，BR-2070），先不调评审命令，只比较 `refs/canon/code-reviewed`（git 公共目录里的引用，上一次评审到的提交）到 `CANON_HEAD` 的范围（D-59）：范围里没测评过的合入（`land.ok` 事件）少于 `review_max_unreviewed`（默认 10）个，并且最老的一个距现在不到 `review_max_age_minutes`（默认 60）分钟时，输出 `code-review: deferred — N landing(s) not reviewed yet (reviewed in a batch at <review_max_unreviewed> or after <review_max_age_minutes> min)` 并以 0 结束，不调评审命令，引用不动。任一条件到点就评审整个范围（BR-2070 的 diff 和全文是整个范围的，BR-2210 的 issue 写明范围）。`CANON_CODE_REVIEW_FORCE=1` 不看阈值立即评审，这时 `CANON_BASE`、`CANON_HEAD` 可以不设，默认取已评审引用和 main 的最新提交（协调多个子 agent 的 agent 在一批完成后用它）。同一时间只有一个评审在跑，靠协调数据库的 `code_reviewer` 表（和 `canon floor watch` 的 `watcher` 表一样，D-11）：评审开始前在一个事务里认领，表里没有持有者、持有者就是自己、或持有者的进程确认已经不在（`ps` 读不出进程表时按还在算，不接手）时写下自己的进程（pid 和进程启动时间）并开始；否则其余的等它结束（`CANON_CODE_REVIEW_NOWAIT=1` 时不等，输出 `another code review is running; it covers this range` 后以 0 结束），再按新的引用重新判断。评审结束只删自己写的那一行，持有者已被别人接手时不动别人的。等了 30 分钟还在跑就报错。旧版本留下的 `canon/code-review.lock` 文件不再读，也不删。当前时间取 `CANON_NOW`（ISO 日期，测试用）。评审留在 `after_land` 里，所以 `canon work after-land --wait` 读到的 `code-review:` 行（BR-2166、BR-2167）仍有答案，deferred 行就是答案。

## 例子

- 引用在 B，之后合入了 9 个、最老的刚合入 → 第 9 个合入的 after_land 日志是 `code-review: deferred — 9 landing(s) not reviewed yet (reviewed in a batch at 10 or after 60 min)`，没有调评审命令
- 同上，第 10 个合入 → 评审收到 B 到第 10 个的整个范围，调一次评审命令，输出 `reviewed 10 landing(s) in one batch`
- 一个合入，最老的 59 分钟前合入 → deferred；61 分钟前 → 评审
- `review_max_unreviewed: 2`，第 2 个合入 → 评审两个
- `CANON_CODE_REVIEW_FORCE=1`，没设 `CANON_BASE` 和 `CANON_HEAD`，有 1 个没评审的合入 → 评审它
- 两个评审同时启动、范围相同 → 只有一个调评审命令、提交一次 issue；另一个等它结束，看到引用已经移到末尾，输出 `already reviewed in a batch; nothing to review`
- 同上，另一个带 `CANON_CODE_REVIEW_NOWAIT=1` → 输出 `another code review is running; it covers this range`，不调评审命令，以 0 结束
- 持有者被 SIGKILL 杀掉，表里还留着它的行 → 下一个评审确认它的进程不在，接手并评审
- 持有者的行还在、它的进程还在，但 `ps` 读不出进程表 → 不接手，按持有者还在算
- 持有者被别人接手后才结束 → 它不删现在持有者的行
