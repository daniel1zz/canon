## 规则

canon 装进项目、项目没改过的文件，是被合入的树里 `.claude/skills/.canon-skills.json`（`canon install`、`canon update` 写的清单，BR-2081）列出、当前内容的哈希和清单里记录的一致的文件。重复评审（BR-2143）找这次合入改动过的常驻说明时不算这些文件：它们不列进改动过的文件，不附全文，也不附 diff；一次合入改动的常驻说明只有这些文件时（比如只有 `canon update` 的变更），不做重复评审，评审命令不被调用。项目在这些文件里改不了什么（改了下次 `canon update` 就要 `--force`），所以它们之间的重复不能成为项目的拦截意见。它们的 description 仍列在提示里作为对照，那一行末尾标 `(shipped by canon)`，提示写明：标着它的文字由 canon 写入、在本项目里改不了，两处都是它时既不拦截也不写成提示；项目自己的文字和它重复时照 BR-2143 拦截，结论说保留 canon 的那一处、改项目自己的那一处。清单里列了、但内容和记录的哈希不一致的文件（项目改过）、清单没列的 skill，都算项目自己的文字，照常评审；清单不存在或不是合法 JSON 时，没有文件算 canon 装进来的，全部照常评审。清单取自被合入的树，不取自 main：`canon update` 的变更本身就改清单。一个变更把 skill 文件和清单里的哈希一起手改，可以让自己的改动跳过这次评审；canon 不防这种做法，清单只该由 canon 写，这样改过的内容下次 `canon update` 也会当成 canon 的文件直接覆盖。

## 例子

- 变更只有 `canon update` 写的 `.claude/skills/canon-design/SKILL.md` 和清单，文件内容的哈希和清单一致 → 不做重复评审，评审命令没被调用
- 同一个变更还改了 `CLAUDE.md` → 做重复评审，提示里是 `# Changed in this landing: CLAUDE.md`，没有 `canon-design/SKILL.md` 的全文和 diff，它的 description 那一行末尾是 `(shipped by canon)`
- 变更在 `CLAUDE.md` 新加一行，和 `canon-design` 的 description 说的是同一条要求，评审回答 `duplication` → 这条意见按 BR-2442 核实后记账
- 项目自己改了 `.claude/skills/canon-design/SKILL.md`，内容的哈希和清单不一致 → 照常评审，提示里有它改动后的全文，description 那一行没有 `(shipped by canon)`
- 项目自己的 `.claude/skills/mine/SKILL.md`（清单没列）改了 → 照常评审
- 清单不是合法 JSON，变更改了 `.claude/skills/canon-design/SKILL.md` → 照常评审
