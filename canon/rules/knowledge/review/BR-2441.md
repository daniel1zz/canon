## 规则

一次合入移动 main、写下 `land.ok` 之后，它改了 BR-2009 或 BR-2143 要评审的文件、合入前的 main 上又配了评审命令（BR-2074）时，合入在协调数据库里为它排一次评审：记下合入的排队号、变更、合入前 main 的提交（`base`）、合入的提交（`head`）和 `land.ok` 的事件编号，输出一行 `review: <文件> are reviewed after the landing, in the background (log: <路径>)`，有变更时接着写 `canon work after-land --wait <变更>` 会报告它；然后在没有活着的评审进程时，在后台启动 `canon work review-landed`（自己的进程组，输出追加到协调数据库目录下的 `logs/landed-reviewer.log`）。一起测时每个成员按自己的 `base` 和 `head` 各排一次。没有配评审命令时不排，见 BR-2074。合入不等评审，评审的结论也不改变合入的结果（D-89）。

`canon work review-landed` 先在协调数据库里登记自己是唯一的评审进程（已有活着的就输出 `another reviewer is running` 并以 0 退出），把仍是 `running` 的评审改回排队（只有评审进程会运行评审，所以它们的进程已经死了），然后按排队的先后一次运行一个；没有排队的评审时，在同一个写事务里注销自己并退出，所以合入时排上的评审要么被正在退出的进程取走，要么由合入启动的新进程运行。同一个 clone 里同时最多只有一个评审在运行。每个评审把输出追加到自己的日志 `logs/landed-review-<排队号>-<land.ok 编号>.log`：第一行写明变更、合入的提交和 `base`，最后一行是 `review: done`，或评审命令运行失败、超时、结论无效（BR-2216、BR-2296）时的 `review: could not run: <原因>`；失败的评审写一条 `review.fail`（`landed`、`commit`、`message`），不自动重试，接着运行下一个。`canon work review-landed` 被 SIGTERM 或 SIGINT 终止时，先停下正在运行的评审命令（BR-2296）、删掉临时 worktree、注销自己再退出，正在运行的评审留在 `running`，下一个评审进程从头再运行它。

环境变量 `CANON_LANDED_REVIEWER` 为 `0` 时，合入照样排队，但不启动评审进程；`canon work after-land --wait` 等的评审还在排队或留在 `running`、又没有活着的评审进程时，它启动一个（BR-2167），所以排上的评审不会被丢下。被中断后事后补记的 `land.ok`（BR-2309）不知道 `base`，不排评审。

## 例子

- 合入改了 `BR-1`，合入前的 main 上 `review` 是一条命令 → `land.ok` 之后排一次评审，输出含 `are reviewed after the landing, in the background`，合入结束时评审命令还没有运行过；之后评审进程运行它，日志最后一行是 `review: done`
- 评审回答 `block` → 合入已经成功、main 已经前移，评审事件是 `review.block`
- 合入只改了代码 → 不排评审，不启动评审进程
- 两次合入先后排了两次评审，评审进程正在运行第一次 → 第二次合入不另起进程；第一次结束后同一个进程运行第二次，两次评审没有同时运行
- 已有一个活着的 `canon work review-landed`，再运行一个 → 输出 `another reviewer is running`，退出码 0
- 评审进程被杀时有一个评审是 `running` → 下一个评审进程把它改回排队并运行
- 评审命令以 3 退出 → 这次评审记为失败，有一条 `review.fail`，日志最后一行是 `review: could not run: ...`；排在它后面的评审照样运行
- 一起测的两个成员都改了规则 → 排两次评审，各自的 `base` 是自己下面的那个提交
- `CANON_LANDED_REVIEWER=0` 时合入 → 评审排上了，没有评审进程；`canon work after-land --wait` 启动它并等到这次评审结束
