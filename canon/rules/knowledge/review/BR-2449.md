## 规则

`canon work review-landed --again <C-n>` 取这个变更最新的一条 `land.ok`，为那次合入再排一次 BR-2441 的评审，按 BR-2441 启动评审进程，自己不等。只有这次合入的评审失败了（最近排的那次是 `failed`），或者从来没有为它排过评审（例如 D-89 之前在合入里评审的合入），才重新排；新排的评审取 `land.ok` 里记的 `base` 和合入的提交，排队号沿用失败的那次（没排过时用这个变更最近一次 `landed` 的排队号），日志是新的一份（`logs/landed-review-<排队号>-<land.ok 编号>-again-<n>.log`，从没排过时没有 `-again-<n>`）。被评审的文档照旧取自那次合入；评审命令和它的设置（`review`、时限、提示预算等）却取自重新排的那一刻 main 的提交，在那个提交的临时 worktree 里运行，提交记在 `landed_reviews.reviewer`：重排多半是因为评审命令本身坏了、之后在 main 上修好了，用合入前的旧命令只会再失败一次（#215，D-117）。代码是运行它的 canon 自己的。输出一行写明这次合入的提交和 `base`、是失败后重排还是之前没排过、用的是 main 哪个提交的评审命令（`with main's review command at <提交>`）、日志路径，以及 `canon work after-land --wait <C-n>` 会报告它；之后 `canon work after-land <C-n>` 报告的就是这次新排的评审。失败且没有同一提交后来 `done` 的评审，`canon work status` 每条一行列出（带日志路径和这条命令），谁都不用翻日志才知道要重排（#196）。

退出码：重新排上为 0；`--again` 的值不是 `C-<数字>` 为 2；这个变更没有 `land.ok`，或从没排过评审、又找不到它 `landed` 的排队号为 3；最近一次 `land.ok` 没有记 `base`（中断后补记的，BR-2309）为 1；这次合入的评审已经完成（`done`）、还在排队或正在运行为 5，信息写明它的状态和日志，什么都不排。

## 例子

- 合入时的评审命令坏了（脚本读的 profile 已删），评审 `failed`；之后 main 上把 `review` 换成能用的命令，再 `--again` → 新排的评审用 main 现在的命令，日志写 `run again with main's review command at <提交>`，评审跑完 `review: done`；评审的仍是那次合入的 `BR-1`
- 一条合入后评审 `failed`、没有重排 → `canon work status` 有一行 `the review after the landing of C-1 failed`，含日志路径和 `canon work review-landed --again C-1`；重排成功（`done`）之后这一行消失

- `C-5` 最近一次合入的评审 `failed`（提示超过预算）→ 重新排一次，`base` 和合入的提交与失败的那次相同，排队号相同，日志名以 `-again-1.log` 结尾，退出码 0；评审进程运行它后 `canon work after-land --wait C-5` 报告的是这次，日志最后一行是 `review: done`
- `C-5` 的评审已经 `done` → 退出码 5，信息里有 `done`，没有新排
- `C-5` 的评审还是 `queued` → 退出码 5
- `C-6` 合入时没有排评审（D-89 之前的合入），有 `land.ok` 和 `landed` 的排队号 → 排上，日志名没有 `-again`
- `C-999` 没有 `land.ok` → 退出码 3
- `C-7` 最近一次 `land.ok` 是中断后补记的，没有 `base` → 退出码 1
- `--again 5` 或 `--again foo` → 退出码 2
