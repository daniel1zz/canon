## 规则

每次合入移动 main 之后，canon 按这次合入的改动（合入前的 main 到合入的提交）算出它的关键程度，`critical` 或 `normal`，连同成立的理由记在 `land.ok` 事件的 `criticality` 字段里。下面任一条成立就是 `critical`，理由写成成立的那几条：

- 改了持久化数据的结构或迁移：改动的文件匹配项目配置的 `critical_paths`；
- 改了 `canon/rules` 或 `canon/decisions` 下的生效规则或已接受的决策（只移动文件、只改引用记录的不算）；
- 改了两个以上领域的代码目录（按 `code_root` 下的领域目录算，`shared` 里的共享代码不算一个领域）；
- 改了行为哈希的生效规则里，有一条没有会运行的测试点名它；
- 改动的文件在最近 14 天里被撤回的合入（BR-2535）改过。

会话可以在 `canon work land` 时加 `--critical "<理由>"` 把一次合入调成 `critical`，理由记在同一字段里；没有把 `critical` 调成 `normal` 的办法。关键程度不拦合入，也不改变合入做哪些检查（D-141；和质量标准共用同一套独立判定，D-145）；它只决定合入后的验收（BR-2544）。被判为 `normal`、之后又被撤回的合入，撤回时记一条 `criticality.miss` 事件（变更、合入的 `land.ok` 编号、撤回的原因），用来校准上面这几条。

## 例子

- 合入改了 `canon/rules/work/BR-1.md` 的例子 → `criticality` 是 `critical`，理由含 `rules or decisions`
- 合入只改了 `src/work/land/land.ts` 和它的测试，`BR-1` 有测试点名，最近没被撤回过 → `normal`
- 同上，会话加 `--critical "touches the queue lock"` → `critical`，理由含 `touches the queue lock`
- 合入改了 `src/work/a.ts` 和 `src/knowledge/b.ts` → `critical`，理由含两个领域
- 合入改了 `src/kernel/x.ts` 和 `src/work/a.ts`（`kernel` 在 `shared` 里）→ 不因跨领域算 `critical`
- 一个 `normal` 的合入三小时后被后台测试撤回 → 有一条 `criticality.miss` 事件，带它的 `land.ok` 编号
- 没有任何选项能让一次 `critical` 的合入记成 `normal`
