## 规则

关键程度按 BR-2543。`critical` 的合入一定、`normal` 的合入按项目配置的 `accept_sample`（0 到 1 之间的比例）抽中时，canon 为它排一次合入后的验收，在后台运行，合入不等它，它的结果也不改变合入的结果和退出码（D-141）。

验收由项目配置的 `accept_command` 运行，它是一个独立的 agent，不是写这个变更的会话：canon 在合入的提交的临时 worktree 里运行它，从标准输入给它这次合入改了行为哈希的生效规则（编号和全文）、变更编号和合入的提交，要求它从产品的真实入口（命令行或网页）按每条规则的例子去做，对每条回答 `pass` 或 `fail`，以及做了什么、看到了什么。每次验收记一条 `accept.landed` 事件（变更、`land.ok` 编号、提交、每条规则的结果和看到的东西）。

有规则 `fail` 时不另起拒绝，走已有的路：main 的后台测试因同一次合入失败时，按 BR-2534 到 BR-2536 撤回；否则 `canon work due`（也就在 `canon brief` 的 Due now 里，BR-2527）出现一项 `acceptance:<C-n>`，写明变更、它合入时的执行者和没通过的规则，直到这些规则在之后的一次验收里通过，或者有变更为它们写了新的当前文字的通过记录；生效时 BR-2527 的主会话待办表一并加上这一行。命令运行失败或超时时，这次验收记为失败（`accept.fail`），`canon work after-land` 报出来，不算通过也不算不通过。没有配置 `accept_command` 时不验收，`land.ok` 之后输出一行写明这次合入没有合入后的验收。

## 例子

- 一次 `critical` 的合入改了 `BR-1`，`accept_command` 回答 `BR-1` 为 `pass` → 有一条 `accept.landed` 事件，`canon work due` 里没有这个变更
- 同上，回答 `fail`，看到的是“`canon work land` 退出码 0，但 main 没有前移” → `canon work due` 有一行 `acceptance:C-1`，写明 `BR-1` 和合入的执行者；合入早已成功，main 不动
- `accept_sample: 0.2`，十次 `normal` 的合入 → 大约两次排了验收
- `accept_sample: 0`，`normal` 的合入 → 不验收；`critical` 的照样验收
- 验收命令超时 → `accept.fail`，`canon work after-land` 报告它，`canon work due` 没有 `acceptance:` 项
- 没有配置 `accept_command` → 合入后输出一行说明没有验收，没有 `accept.landed` 事件
