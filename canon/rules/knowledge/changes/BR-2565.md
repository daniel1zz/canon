## 规则

被检查的那棵树里，各变更的 `depends_on`（BR-2561）连成的图里有环时（包括依赖自己），`canon check` 对环上每个变更的文件各报一条 `depends-cycle`，退出码 1，信息写出整个环，从这个变更出发再回到它，形如 `C-1 → C-2 → C-1`。只看这棵树里的变更文件：只在别的分支上的变更不算进来（D-149）。成环是完整性问题（D-139、D-148），所以合入在 rebase 之后的树上跑 `canon check` 时同样拒绝：两个分支各加一条边，单看哪一个都不成环，先合入的那个进了 main，后合入的那个 rebase 之后成环，被拒。环上的变更是什么状态都算；`done_by` 和 `depends_on` 里的成功标准都不算依赖的边。

## 例子

- `C-1` 写 `depends_on: [C-2]`，`C-2` 写 `depends_on: [C-1]` → 两条 `depends-cycle`，一条在 `C-1` 的文件上，信息含 `C-1 → C-2 → C-1`；一条在 `C-2` 的文件上，信息含 `C-2 → C-1 → C-2`
- `C-1` 写 `depends_on: [C-1]` → 一条 `depends-cycle`，信息含 `C-1 → C-1`
- `C-1 → C-2 → C-3`，没有回到 `C-1` 的边 → 没有发现
- `C-4` 依赖 `C-1`，`C-1`、`C-2` 互相依赖 → 只有 `C-1`、`C-2` 各一条，`C-4` 没有
- 分支 A 给 `C-1` 加 `depends_on: [C-2]` 并合入；分支 B 给 `C-2` 加 `depends_on: [C-1]`，在 B 自己的树上 `canon check` 没有发现；B 合入时 rebase 之后成环 → 合入被拒，原因是 `canon check`，信息含 `depends-cycle`
- `C-1` 依赖只在别的分支上的 `C-7`，那个分支上 `C-7` 依赖 `C-1` → 在 `C-1` 的树上没有发现
