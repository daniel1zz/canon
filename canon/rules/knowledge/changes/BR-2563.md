## 规则

决定关联的那一步可能在开工之后，所以 `canon change link <C-n>` 在当前 checkout（通常是变更自己的 worktree）里改 `C-n` 文件的关联，随所在变更一起提交（D-148、D-149）。参数：`--release R-n`、`--feature F-n`、`--issue <n>[,<n>…]`、`--depends C-a[,C-b…]`、`--done-by C-m`；每个参数写 `none` 时删掉对应的键。给了的参数整体替换原来的值，没给的不动；`--release` 和 `--feature` 只留一个：写其中一个时删掉另一个。成功时输出 `<C-n> → <改了什么>`，提示随变更一起提交，记一条 `change.link` 事件。

`--done-by` 只用于 `dropped` 的变更，其余参数只用于 `open` 的变更。检查按这个顺序，任何一项不过都不改文件：一个参数都没给，同时给 `--release` 和 `--feature`，值的格式不对（同 BR-2562），`--done-by` 写的是 `C-n` 自己（退出码 2）；当前 checkout 里没有 `C-n`（退出码 3，提示到有这个变更文件的 worktree 里运行）；`C-n` 的状态不是这个参数要的（退出码 2，信息写出它现在的状态）；版本、模块或变更不存在，查法同 BR-2562 的 `canon change new`（退出码 3）；写入后依赖会成环（退出码 1，信息按 BR-2565 写出环）。

## 例子

- `C-9` 的 worktree 里 `canon change link C-9 --feature F-2`，`C-9` 原来写着 `release: R-1` → `C-9` 有 `feature: F-2`，没有 `release`，输出以 `C-9 →` 开头
- `canon change link C-9 --depends C-3,C-4`，原来是 `depends_on: [C-2]` → `depends_on: [C-3, C-4]`
- `canon change link C-9 --issue none` → `C-9` 没有 `issues`
- `canon change link C-9`（一个参数也没有）→ 退出码 2
- `canon change link C-5 --done-by C-9`，`C-5` 是 `dropped` → `C-5` 有 `done_by: C-9`
- `canon change link C-5 --done-by C-9`，`C-5` 是 `open` → 退出码 2，文件不变
- `canon change link C-9 --release R-1`，`C-9` 是 `done` → 退出码 2
- `C-3` 写着 `depends_on: [C-9]`，`canon change link C-9 --depends C-3` → 退出码 1，信息含 `C-9 → C-3 → C-9`，文件不变
- 在主 checkout 里运行，`C-9` 只在它自己的分支上 → 退出码 3
