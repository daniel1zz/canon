## 规则

每个变更的状态在每次读的时候算出，不存起来（D-151）。只用命令写下的事实：main 最新提交上的变更文件（下称 main）、变更自己的分支（`change/C-n` 或 `change/C-n-<名字>`，BR-2291）上的变更文件、协调数据库里的认领、派发、合入队列、交接、等人回答的问题和事件，以及 git 提交时间；不读交接的下一步、备注和变更正文里的文字（只看 `## 为什么`、`## 要改什么` 两节是不是空的）。`canon change list`、`canon brief`、`canon work status`、`canon work due`、`canon overview` 和派发名额（BR-2526）都用这一个算法，不各算各的。

算哪些变更：main 上的、只在自己分支上的，以及只在协调数据里出现的变更编号（有认领、派发记录、交接或 `drop.done` 事件，main 和分支上都没有它的文件）。

**主状态**：从上往下，第一条成立的就是它的主状态，每个变更正好一个：

1. `landed`：main 上是 `done`。
2. `dropped`：main 上是 `dropped`；或者 main 上没有它、没有它的分支，事件表里有它的 `drop.done`（只在分支上建过、已经 `canon work drop` 的变更）。
3. `missing`：main 上没有它、没有分支上有它的文件、也没有 `drop.done`，但协调数据里有它（认领、生效的派发或交接）。
4. `awaiting-close`（代码已在 main，待关闭）：main 上是 `open`，没有分支，没有有效的认领（BR-2100 的认法），事件表里有过它的认领（`claim.take`，开过工），`rules` 不为空且列的每条规则在 main 上都是 `active`。它是要判断的事，不算可开始，用 `canon change close`（BR-2573）关闭。
5. `in-queue`：合入队列里有它的条目，状态是等待或正在合入。
6. `land-refused`：它最近一次合入的事件（`land.start`、`land.ok`、`land.refuse` 中最新的）是 `land.refuse`。
7. `in-progress`：有有效的认领。
8. `stalled`：有生效的派发（BR-2497，没被 `take` 或放弃结束），按 BR-2522 停滞。
9. `delegated`：有生效的派发，没停滞。
10. `waiting-owner`：有一个没回答的、关联到它的问题（`canon human ask --change <C-n>`，或在它的 worktree 里问的；撤回的按 BR-2628、记了暂定答案的按 BR-2636 不算），或者 `depends_on` 里有一条在 main 上是待负责人的成功标准（BR-2564、D-149）。只有这两种事实算等负责人。
11. `waiting-deps`：`depends_on` 里还有别的没满足的依赖（BR-2564）。
12. `handed-off`：有交接（`canon work stop` 写的），附交接原因（BR-2025）；旧交接没写原因的，原因是 `unrecorded`。
13. `ready-delegatable`：上面都不成立，并且能派给 worker：只有一处有它的文件（main，或正好一个分支），两节任务都不空（不只有空行和模板的 `<…>` 占位行），并且 `canon work delegate` 不会因为设计没发布到 main 拒绝它（契约清单的判断按 BR-2497）。
14. `ready-self`：其余的，可以开始但只能自己做；附上不能派的原因（哪几项设计没在 main 上、哪一节是空的、几个分支）。

轻变更（杂务合入时写进关闭提交的变更文件，带 `chore:`，BR-2458）在 main 上就是 `done`，按第 1 条是 `landed`；还没进 main 时（只在杂务的 worktree 里），它的杂务身份在合入队列里就是 `in-queue`，杂务身份有有效认领就是 `in-progress`，其余按上面的次序。

**附加标记**，和主状态同时给出，各自独立成立：

- `handoff`：有交接。
- `deps_unmet`：有没满足的依赖（BR-2564，含待负责人的成功标准）。
- `owner_question`：有没回答的、关联到它的问题（不算的同上）。
- `claimed`：有有效的认领。
- `ambiguous`：几个分支上都有它（BR-2293）。
- `closed_on_branch`：只在分支上，分支上写着 `done`（BR-2294）。
- `overlap`：范围可能和别的变更重叠；现在总是 false，由 D-148 第 D 步填入。

## 例子

- main 上 `C-3` 是 `done`，还留着派发记录和交接 → `landed`
- `C-671` 只在分支上建过，`canon work drop C-671` 后分支没了，事件表有 `drop.done`，派发记录还在 → `dropped`，不是 `stalled`
- 派发记录指向 `C-9`，main 和所有分支上都没有 `C-9` 的文件，也没有 `drop.done` → `missing`
- `C-343` 在 main 上是 `open`，列的规则 `BR-1`、`BR-2` 在 main 上都是 `active`，开过工（有 `claim.take`），现在没有分支、没有认领 → `awaiting-close`，不是 `ready-*`
- 同上，但 `BR-2` 还是 `planned` → 不是 `awaiting-close`，按后面的次序判定
- 同上，但从没开过工（没有 `claim.take`）→ 不是 `awaiting-close`
- 合入被拒之后又在合入队列里等 → `in-queue`；被拒后还没再合入 → `land-refused`，即使认领还有效
- 有有效的认领，同时有交接 → `in-progress`，标记 `handoff`、`claimed`
- 派给 `w1`，`w1` 进程不在、70 分钟没提交 → `stalled`；30 分钟 → `delegated`
- `canon human ask --change C-5 "…"` 没回答 → `waiting-owner`，标记 `owner_question`；回答之后不再是
- 没关联变更的问题 → 不让任何变更变成 `waiting-owner`
- `C-6` 依赖 `R-2/S3`（待负责人）→ `waiting-owner`，标记 `deps_unmet`
- `C-5` 依赖 main 上 `open` 的 `C-3`，没有认领 → `waiting-deps`；有认领 → `in-progress`，标记 `deps_unmet`
- 交接原因是 `land`，没有认领 → `handed-off`，原因 `land`
- 交接原因是 `owner`、指向的问题还没回答 → `waiting-owner`；回答之后 → `handed-off`，原因 `owner`
- main 上的 `C-7` 只有标题，`## 要改什么` 是模板占位行 → `ready-self`，原因写明 `## 要改什么` 是空的
- main 上的 `C-8` 两节都写了，列的 `BR-30` 只在它的分支上 → `ready-self`，原因写明 `BR-30` 没在 main 上
- main 上的 `C-8` 两节都写了，列的规则都在 main 上、没有分支 → `ready-delegatable`
- 杂务合入后 main 上的轻变更 `C-40`（`chore: chore-…`，`done`）→ `landed`
- 轻变更 `C-41` 只在杂务的 worktree 里，它的杂务身份正在合入队列里 → `in-queue`
