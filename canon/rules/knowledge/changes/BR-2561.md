## 规则

变更 front matter 里的关联（D-148）有这几个键，都可以不写，不写不算错（D-139）：

- `release: R-n` 或 `feature: F-n`：变更属于哪个版本或哪个功能模块，只写一个；写模块时，它属于列着这个模块的版本（BR-2509），不用再写版本。
- `issues: [<n>, …]`：变更修的 GitHub issue 编号，正整数。
- `depends_on: [C-a, R-n/S<k>, …]`：变更依赖的变更，或依赖的一条成功标准（`R-n/S<k>`、`F-n/S<k>`，编号按 BR-2504），依赖什么时候算满足按 BR-2564。
- `done_by: C-n`：只写在 `dropped` 的变更上，说明它的工作由 `C-n` 做了（BR-2564 按 `C-n` 算）。

格式不对时这个变更的文件不读入，`canon check` 报 `file-invalid`，信息写出是哪个键：`release`、`feature`、`done_by` 不是一个对应前缀的编号，`issues` 不是正整数的列表，`depends_on` 不是变更编号和成功标准的列表。格式对时 `canon check` 还报：同时写了 `release` 和 `feature`（`file-invalid`，信息说只写一个，模块的版本从版本的 `features` 读出）；`done_by` 写在不是 `dropped` 的变更上，或写的是变更自己（`file-invalid`）；`release` 或 `feature` 指向的文档不存在（`ref-dangling`）；`depends_on` 里的成功标准找不到时，按 BR-2517 查 `advances` 的同样办法报 `ref-dangling`。`depends_on`、`done_by` 指向的变更不存在不报：被依赖的变更可以还只在它自己的分支上（D-149）。这几个键和已经不再读的 `plan`、`steps`（BR-2594）一样是 canon 自己的字段，项目声明的文档类型不能在 `fields` 里用它们（`canon` 读配置时报配置错误）。

## 例子

- `C-2` 写 `release: R-1`，`R-1` 存在 → 没有发现
- `R-1` 已发布，发布之后新建的 `C-4` 写上 `release: R-1` → 没有发现（发布只冻结规则的标签，BR-2326）
- `C-2` 写 `feature: F-3`，`F-3` 存在 → 没有发现
- `C-2` 同时写 `release: R-1` 和 `feature: F-3` → `file-invalid`，信息含 `release` 和 `feature`
- `C-2` 写 `feature: F-9`，没有 `F-9` → `ref-dangling`，信息含 `F-9`
- `C-2` 写 `feature: 3` → `file-invalid`，`C-2` 不读入
- `C-2` 写 `issues: [12, 40]` → 没有发现；写 `issues: [0]` 或 `issues: ["#12"]` → `file-invalid`
- `C-2` 写 `depends_on: [C-1]`，`C-1` 只在分支 `change/C-1` 上 → 没有发现
- `C-2` 写 `depends_on: C-1`（不是列表）→ `file-invalid`
- `open` 的 `C-2` 写 `depends_on: [R-1/S2]`，`R-1` 有成功标准 `S2` → 没有发现；`R-1` 没有 `S2`，或写的是 `R-9/S1` 而没有 `R-9` → `ref-dangling`，信息含这个引用；`done` 的 `C-2` 这样写 → 不报
- `C-2` 写 `depends_on: [R-1/2]` → `file-invalid`
- `dropped` 的 `C-2` 写 `done_by: C-5` → 没有发现；`open` 的 `C-2` 写 `done_by: C-5` → `file-invalid`；`dropped` 的 `C-2` 写 `done_by: C-2` → `file-invalid`
- 什么关联都没写的变更 → 没有发现
- `canon/config.yaml` 声明的类型写 `fields: [depends_on]` → 配置错误，信息含 `depends_on`；写 `fields: [steps]` 同样是配置错误
