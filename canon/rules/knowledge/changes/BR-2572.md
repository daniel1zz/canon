## 规则

`canon change list` 每一行行尾括号里的第一项是这个变更的主状态（BR-2571），后面才是 BR-2291、BR-2564 的标记；所以每一行都有括号。主状态写成它的名字，有细节时加冒号：

- `handed-off: <原因>`，原因带指向时写在后面，例如 `handed-off: owner #12`；
- `waiting-owner: <问题和成功标准>`，例如 `waiting-owner: #12, R-2/S3`；
- `delegated: <worker>`、`stalled: <worker>`；
- `ready-self: <不能派的原因>`，例如 `ready-self: BR-30 not on main`；
- 其余只写名字。

`--json` 的每一项在原有的键（BR-2291、BR-2564）之外加：

- `state`：主状态的名字；
- `flags`：对象，`handoff`、`deps_unmet`、`owner_question`、`claimed`、`ambiguous`、`closed_on_branch`、`overlap` 七个布尔值（BR-2571）；
- `owner_questions`：没回答的、关联到它的问题编号，没有时是空数组；
- `delegation`：生效的派发 `{ worker, owner, epoch, stalled_since }`（没停滞时 `stalled_since` 是 `null`），没有生效的派发时是 `null`；
- `land_refused_at`：主状态是 `land-refused` 时那次拒绝的时间，否则 `null`；
- `not_delegatable`：主状态是 `ready-self` 时不能派的原因（字符串数组），否则空数组；
- `handoff` 对象多两个键：`reason`（BR-2025 的原因，旧交接是 `unrecorded`）和 `on`（原因指向的问题编号或成功标准，没有时 `null`）。

`depends_on`、`waiting_for` 和这些键合在一起，脚本不用再读别的数据就能算出每个变更的状态和依赖。

`--all` 还列出已经结束或找不到文件的变更（BR-2571 的第 1 到 3 种主状态）；没有文件的项 `title` 和 `status` 是 `null`，文字输出的标题写 `(no file)`。不带 `--all` 时照旧只列 `open` 的和只在分支上标成 `done` 的（BR-2291、BR-2294）。

## 例子

- main 上 `C-1` 两节都写了、列的规则都在 main 上，没人动过 → `C-1 … (ready-delegatable)`，`--json` 里 `state` 是 `ready-delegatable`，`flags` 全是 `false`
- `C-2` 只在分支上，交接原因 `land`，认领已放开 → `C-2 … (handed-off: land; on branch change/C-2-x; handoff: land it)`，`--json` 里 `handoff.reason` 是 `land`
- `C-5` 依赖 main 上 `open` 的 `C-3` → `C-5 … (waiting-deps; waiting for C-3)`，`flags.deps_unmet` 是 `true`
- `C-6` 有没回答的问题 #12（`--change C-6`）→ `(waiting-owner: #12)`，`owner_questions` 是 `[12]`
- `C-7` 只有标题 → `(ready-self: ## 为什么 is empty, ## 要改什么 is empty)`，`not_delegatable` 里有同样的原因
- 派给 `w1`、`w1` 在做 → `(in-progress; claimed)`，`delegation.worker` 是 `w1`、`stalled_since` 是 `null`
- 只在分支上建过、已经 `canon work drop` 的 `C-671` → 不带 `--all` 时不列；带 `--all` 时列出 `C-671 (no file) (dropped)`，`--json` 里 `title` 是 `null`、`state` 是 `dropped`
- 旧交接没有原因 → `(handed-off: unrecorded; handoff: …)`
