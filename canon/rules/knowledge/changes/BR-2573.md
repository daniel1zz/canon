## 规则

变更的工作已经由别的提交带进 main（例如手工合入），变更文件却还是 `open` 时，`canon change close <C-n> --commit <提交>` 在当前 checkout 的变更文件里写下 `status: done` 和 `landed_in: <完整的 40 位提交号>`，记一条 `change.close` 事件（含提交号），输出 `<C-n> → done, landed in <提交号前 9 位> (<文件路径>; commit it with your change)`，退出码 0。和 `canon change drop` 一样，文件随调用者自己的变更一起提交、合入；合入之后它在 main 上是 `done`，主状态是 `landed`（BR-2571）。

- 当前 checkout 里没有 `<C-n>` 这个变更 → 退出码 3，什么都不写。
- `<C-n>` 不是 `open` → 退出码 2，提示它现在的状态，什么都不写。
- 没给 `--commit` → 退出码 2。
- `--commit` 在仓库里找不到，或者不在 main 上（不是 main 最新提交的祖先或它本身）→ 退出码 3，什么都不写。

`landed_in` 只能写在 `done` 的变更上，值是 7 到 40 位的十六进制提交号；写在别的状态上或写法不对，`canon check` 报 `file-invalid`。

## 例子

- main 上 `C-343` 是 `open`，它的代码和规则已经在 main 的 `42c1f369` 里；在另一个变更的 worktree 里运行 `canon change close C-343 --commit 42c1f369` → 退出码 0，`C-343` 的文件变成 `status: done`、`landed_in: 42c1f369…`（40 位），事件表多一条 `change.close`
- 同上，再运行一次 → `C-343` 已经是 `done`，退出码 2，文件不变
- `--commit` 是只在某个变更分支上、没进 main 的提交 → 退出码 3，文件不变
- `--commit deadbeef`，仓库里没有这个提交 → 退出码 3
- `canon change close C-999 --commit 42c1f369`，没有 `C-999` → 退出码 3
- 变更文件是 `open` 却写着 `landed_in` → `canon check` 报 `file-invalid`
