# 变更的关联和状态（knowledge/changes）

一个变更和别的东西的关联：属于哪个版本或功能模块、修哪些 GitHub issue、依赖哪些变更，以及依赖什么时候算满足（D-148、D-149）；以及每个变更现在处在什么状态，只从命令写下的事实算出，所有读状态的命令都用同一个算法（D-151）。关联写在变更文件自己的 front matter 里，只有这一份；由 `canon change new`、`canon work start --title`、`canon change link` 写入，不靠会话事后补。

不管：版本和模块本身（`knowledge/releases`）；变更执行哪些规则（`rules`，由合入写）；待办顺序是负责人排的（`knowledge/documents`）；开工和列表的其余部分（`work/session`）。

分类：支撑领域。依赖是否满足、变更的状态每次读的时候算出，不另存。

依赖：`knowledge/documents`（读变更文件）、`knowledge/releases`（版本和模块是否存在）、`work/session`（只在分支上的变更、交接）、`work/claims`、`work/delegation`、`work/land`、`work/humans`（认领、派发、合入队列和等人回答的问题，状态从它们写下的数据算出）。

## 术语

- **关联**：变更 front matter 里的 `release` 或 `feature`、`issues`、`depends_on`，以及放弃的变更上的 `done_by`。
- **依赖满足**：被依赖的变更在 main 上已经合入（`done`），或被放弃时写明了由哪个已合入的变更做了；判定见 BR-2564。
- **主状态**：一个变更此刻处在哪一种状态，按固定次序判定，每个变更正好一个（BR-2571）。
- **旧计划**：D-148 之前变更文件里的 `## 计划` 步骤表，和做步骤的变更 front matter 里的 `plan: C-n`、`steps`；现在只用来提示迁移（BR-2595）。
- **附加标记**：和主状态同时成立的事实，例如有交接、依赖没满足、有等负责人的问题（BR-2571）。
- **当前这一批**：没写 `release` 也没写 `feature` 的未结束变更，等于 AI 会话自己定的交付范围；`canon change list` 能看到全部，`canon overview` 只列其中正在做和在等的（BR-2505，D-151 第四部分）。

## 业务

- **关联的写法**：变更 front matter 里关联的几个键怎么写，写错时 `canon check` 怎么报。
- **关联由命令写入**：新建、开工和之后修改时，哪些命令把关联写进变更文件，参数错了怎么拒绝。
- **负责人批准**：变更用 `owner_gate` 写明负责人要批准什么；批准前不能完成（D-158）。
- **依赖**：依赖什么时候算满足、没满足的变更怎样不被当作可开始，依赖成环怎样被拒绝，一个版本或模块的变更按依赖现算出的图。
- **变更的状态**：每个变更的主状态和附加标记怎样从变更文件、协调数据和 git 提交算出，列表怎样给出它们，代码已经在 main 的变更怎样关闭。
- **旧计划数据**：计划去掉之后（D-148），变更上留下的 `plan`、`steps` 和 `## 计划` 节怎样不再影响任何检查，还没迁移的项目怎样被提示把没做完的步骤建成变更。
