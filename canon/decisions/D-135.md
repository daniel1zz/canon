id: D-135
title: worker 交回规则文字用整份文件的提议，由设计负责人一条命令套用
status: accepted

## 背景

issue #254。worker 改规则文字要交回设计负责人（D-128，按 BR-2499、BR-2501）。实际做法是 worker 在变更文件里写 `- BR-n：<旧句> → <新句>`，设计负责人手工或用脚本贴进规则文件。某个项目 2026-11-17/18 一晚三次出错：例子行本身带 `→`，按第一个 ` → ` 切开的脚本把 13 条规则写成“条件 → 新结果 → 旧结果”；规则文件折行、缩进，旧句对不上原文；贴完没有任何检查。

## 方案

1. worker 用 `canon rule propose` 复制规则全文到 `canon/proposals/<C-n>/<BR-n>.md` 编辑，记下复制时 main 上的版本；设计负责人收回后 `canon rule apply` 原样写回，main 在提议之后改过就整批拒绝；`canon check` 报关闭了还没套用的提议。采用：交的是整份文件，没有切句子、对原文这一步，写回是逐字节复制；版本记录让过期的提议不会覆盖别人的修改。
   - 来源：src/work/land/checks/delegation.ts “const FIXED_DESIGN = ["canon/decisions/", "canon/rules/", "canon/releases/"];”
2. 提议放在 `canon/changes/<C-n>/` 下。否决：worker 合入时把 `canon/changes` 下的 `.md` 当成变更文件、和派发时的任务哈希比较（BR-2501 第 1 项），提议文件会被当成改了任务而拒绝。
3. 让 worker 直接改规则文件，合入时由设计负责人批准。否决：违反 D-128（设计由主会话定），等于取消 BR-2501 第 1 项。
4. 结构化的“旧句 → 新句”对照表加自动替换。否决：还是要在折行和缩进过的原文里找句子，#254 的三次出错正是这一步。
5. 三方自动合并（main 在提议后改过时尝试合并）。否决：规则文字的合并冲突需要人判断，自动合并可能静默写出混合的规则；整批拒绝更安全，提议重做的成本低。

## 决定

采用方案 1：提议和套用按 BR-2524，关闭后遗留的提议按 BR-2525 由 `canon check` 报出。只做已有规则的提议；新规则还是用 `canon work need-design` 交回，因为新规则要分配编号和领域，由设计负责人建。

## 后果

- 设计负责人不再贴句子；`canon rule apply` 输出每条规则的 `git diff`，看得到改了什么。
- 提议文件随变更分支走，worker 合入时一起上 main 也不影响规则；关闭前没套用的由 `canon check` 报出。
- main 在提议后改了同一条规则时要重新提议，这是有意保守。
- 决策文件的提议没有做；需要时另开。
