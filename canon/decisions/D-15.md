---
id: D-15
title: 代码目录按约定和规则领域一一对应，子领域只写业务
status: accepted
---

## 背景

C-81 让规则领域可以分子领域，每个子领域的 README 用 `code:` 写自己管哪些代码路径，`canon context <路径>` 靠这些路径找规则。负责人看过之后提出（2026-11-03）：子领域不能带代码路径，“业务是业务……不然每次都要更新还可能出错”；接着又说：“目录本来也应该按照ddd来划分的，和baseline其实是一致的；业务的代码目录和baseline的目录应该一一对应”。分析利弊和风险后，负责人选了建议的方案：“按建议做”。

当时的事实：

- 子领域的代码路径只能写到文件这一级：`src/work/work.ts` 里同时有开始、合入、清理，改它之前 `canon context` 要列出 34 条规则（C-81 合入后实测；C-81 记录的是 33 条）。
- 代码挪动或改名后，README 里的路径不会自动更新；BR-2079 只能发现“路径不存在”，发现不了“路径还在、但代码已经不是这个领域的”。
- 一个行为常常跨子领域（合入要用认领），只看一个子领域会漏掉相关规则。
- C-81 挪了 74 个规则文件，合入评审把它们全部当成删除加修改重新评审了一遍。

## 方案

1. 每个 README（包括子领域）都写代码路径，即 C-81 的做法。否决：要人工维护，代码一挪就可能错；而且只能写到文件这一级，一个文件里有多个子领域的代码时（`src/work/work.ts`）照样要列出 34 条规则。
   - 来源：canon/changes/C-81.md “子领域的代码路径只能写到文件这一级”
2. 不声明归属，运行时从代码注释和导入这个文件的测试里找规则编号。否决：找到的都是对的，但不全。实测 `src/knowledge/query.ts` 的注释只提到 BR-2008、BR-2053、BR-2112、BR-2113，漏掉了它最核心的 BR-2007；测试只覆盖有测试的规则，`untested` 的规则永远找不到。
   - 来源：src/knowledge/query/query.ts “An id matches whole ids only”
3. 运行时从 git 历史里找改过这个文件的变更，再取这些变更的规则。否决：噪音太大，实测 `src/knowledge/query.ts` 被 C-1、C-3、C-13、C-80、C-81 改过，这些变更列出的规则合起来 35 条，大部分和这个文件无关。
4. 代码目录按约定和规则领域一一对应：`canon/rules/work/land/` 对应 `<code_root>/work/land/`，什么也不用声明；`code_root` 和 `shared`（不属于任何业务领域的共享内核）写在 `canon/config.yaml`，对别的项目是可选的。没有 `code_root` 时，顶层领域的 README 照旧用 `code:` 写到目录一级，子领域不写代码位置。跨子领域的行为由 `canon context <文件>` 在运行时读这个文件的相对导入，带上被导入代码所在的领域，并列出同一顶层领域下其余子领域的名字。采用：业务只写在规则里，代码位置不需要维护；`canon check` 能发现没有对应领域的目录（BR-2118）。
   - 来源：src/knowledge/query/query.ts “export function importedPaths(root: string, file: string): string[]”
5. 方案 4，但对所有项目强制。否决：很多框架规定了目录结构，例如 Next.js 的 `app/`、Rails 的 `app/models`、Go 按包分目录、monorepo 的 `packages/*`，强制按领域分目录会和它们冲突。

## 决定

- 配置了 `code_root` 时，领域 `<领域路径>` 的代码就是 `<code_root>/<领域路径>`；任何 README 都不写 `code:`（BR-2116、BR-2117）。`canon check` 报出没有目录的领域、不属于任何领域也不在 `shared` 下的目录（BR-2118）。只放测试或测试数据的目录不例外：测试放在它测的代码旁边，否则列进 `shared`。
- 没有 `code_root` 时，顶层领域的 README 用 `code:` 写代码目录（BR-2006、BR-2079），子领域只写业务；`canon context <路径>` 只能落到顶层领域，并列出子领域的名字（BR-2113、BR-2120）。
- `canon context <文件>` 带上它导入的代码所在的领域，单独标出，只列规则（BR-2119）。
- 防止共享代码变成杂物堆：`canon stats` 报出共享代码占 `code_root` 的比例，超过 20% 时提示（BR-2121）。
- 合入评审不再评审原样挪动的文件（BR-2009），以后按领域挪规则或代码时不会重新评审一遍。
- canon 自己启用 `code_root: src`、`shared: [src/kernel]`，代码按领域重新组织，在单独的变更里做。

## 后果

- 加子领域时要同时建它的代码目录，否则 `canon check` 报 `code-layout`；把代码挪进子领域目录就是给代码归属，不用改任何 README。
- 进行中的变更 C-41（每个源文件都归属一个领域）被这个决策取代：启用 `code_root` 后，BR-2118 已经保证每个目录都有归属。
- 读导入只认相对路径，按 JS/TS 的写法解析；别的语言、或用路径别名（如 `@/x`）的项目，导入的领域不会出现，`canon context` 仍按约定匹配。
- 20% 这个阈值没有数据依据，是起点；canon 自己启用后先看实际比例，2027-02 复查。
