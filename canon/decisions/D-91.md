---
id: D-91
title: canon 的 skill 跟着发布走：after_green 先全量重复评审，通过才把二进制和 skill 快照一起发布
status: proposed
---

## 背景

下游项目运行 `canon update` 时 canon 的每个 skill 一起变，项目合入时的重复评审（BR-2143）把 canon 自己 skill 之间的重复当作这次合入带进来的，拦下更新变更；项目改不了 canon 的文件。#159、#182 两次出现。canon 仓库自己的合入只把改动过的 skill 全文放进提示，其他 skill 只给 description（BR-2143），所以两个 skill 正文之间的重复在源头查不出来。负责人选了方案 B（canon human #23）：canon 发布新版本前在自己仓库把所有发出的 skill 一起评审一次，下游合入不再评审 canon 装进来的文件（BR-2410，C-462）。

查证时发现一个前提问题：编译好的 `dist/canon` 安装的 skill 原来取自它所在仓库的 `.claude/skills`（BR-2082），也就是主 checkout 的工作树，而主 checkout 签出的是 main，每次合入都在前移。`after_green` 只决定二进制从哪个提交构建，skill 却总是 main 上最新、还没测过也没评审过的文字。只在 `after_green` 里加一次评审，拦得住二进制，拦不住下游真正拿到的 skill。

## 方案

1. 发布把二进制和 skill 快照一起放进 `dist/`，发布前全量评审：采用。`after_green` 运行 `scripts/release.ts`，对测过的提交里所有 `canon-*` 的 SKILL.md 全文和工作说明做一次重复评审（BR-2411），通过才编译、把 skill 复制到 `dist/skills-<提交>`、用符号链接 `dist/skills` 一次切换（BR-2412）；编译好的 canon 先从 `dist/skills` 安装（BR-2082）。评审只在发出的文字变了时才付费调用一次，同样的文字沿用结论；下游拿到的正是评审过的那一套。
   - 来源：canon/config.yaml “不从没测过的 main 构建”
2. 只在 `after_green` 里评审，skill 仍从仓库工作树读：否决。评审拦下时二进制不更新，但下游照样从 main 的工作树拿到没评审的 skill，正是要防的情况。
3. 把 skill 编进二进制：否决。安装代码按目录读文件（逐个比较哈希、写清单），编进二进制要额外的代码生成步骤和一套不同的读法，得到的效果和方案 1 相同（skill 和二进制来自同一个提交）。
4. canon 仓库每次改 skill 的合入都把所有 skill 全文放进重复评审：否决。负责人要的是每次发布一次付费评审，不是每次合入；而且合入时评审过的文字到发布之间还会被别的合入改动。
   - 来源：canon/rules/knowledge/review/BR-2143.md “改动过的 `.claude/skills/<名字>/SKILL.md` 还附上被合入的树里的全文”

## 决定

采用方案 1。拦截时什么也不发布（`dist/` 保持上一次发布），`scripts/release.ts` 以退出码 1 结束，标准错误输出写明发现，并像合入后的代码评审一样在 GitHub 上新建或评论一个 `canon-review` issue（BR-2072 的做法）；`after_green` 的失败记在事件表里（BR-2222），不改变测试结果。

## 后果

- 下游通过 `canon update` 拿到的 skill 落后 main：最多落后到下一次后台测试通过并且发布评审通过。改了 skill 想马上发给项目，合入后运行 `canon floor watch --now`。
- 发布评审拦下时二进制也不更新，修复 skill 之前 PATH 上的 canon 停在上一个版本；修法是开变更改 skill 文字，下一次通过时发布。
- 主 checkout 的 `dist/` 多了 `skills-<提交>` 目录（保留最近两个）和 `dist/skills` 链接；`dist/skills` 被人换成普通目录时发布以退出码 4 拒绝。
- canon 仓库自己运行 `canon update` 时，比较的对象也变成发布的 skill：main 上比发布新的 skill 会被当成项目里改过的文件，保留（BR-2089）或拒绝覆盖（BR-2081），不会被旧文字悄悄覆盖。
- npm 包里的 `dist/canon.js` 不受影响，仍从包里的 `.claude/skills` 安装；以后发布 npm 包时同样要先跑发布评审（`bun scripts/release.ts --check`）。
