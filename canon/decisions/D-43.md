title: 合入后一致性抽查：只查改到的领域，后台运行，按 issue 结案原因算准确率，低于停用线自动停
status: proposed
---

## 背景

规则评审只看文字，测试检查只看测试名里有没有规则编号（BR-2005）。规则写“退出码 3”、代码返回 1、点名它的测试测的是别的东西时，两道检查都放行。C-13 用独立子 agent 逐条对照过一次，查出 4 个真问题（#1 到 #4），但没有定期机制。lore 的自查曾经比它省下的还贵（D-1），所以每次花多少、什么时候停要先定好。负责人 2026-11-04 要求做（“先保证其他”），并要求它每次合入都花 token，所以要能配置、其他项目默认不开。

## 方案

1. 作为 `before_land` 检查，不一致就拒绝合入：否决。一次 AI 调用要几分钟、结论有误报，挡住合入的代价比晚一点发现大；D-1 定的是合入后的代码评审不拦合入，这里同理。
   - 来源：canon/rules/knowledge/review/BR-2070.md “合入后的代码评审看完整 diff 和改动文件的全文”
2. 定期把所有领域都查一遍：否决。canon 有二十多个领域，一次全查是二十多次调用，大多数领域自上次以来没改过，花的 token 大多白费。
3. 作为 `after_land` 后台命令，只查这次合入改到规则或代码的领域，每个领域一次调用，每次合入最多查几个领域由参数定：采用。改动刚发生时最可能不一致，范围和花费都跟着改动走；复用代码评审的提 issue、去重和失败处理（BR-2072、BR-2211）。
4. 发现提成和代码评审同一个标签 `canon-review` 的 issue：否决。两种评审的准确率要分开算，才能单独停掉不准的那个；用单独的标签 `canon-consistency`。
5. 准确率只靠负责人手工统计：否决。没人统计就一直花下去。脚本每次运行前自己从 GitHub 读这个标签下已关闭 issue 的结案原因（`completed` 算对，`not planned` 算错），够数且低于停用线时不再调用评审命令。

## 决定

采用方案 3 和 5。`scripts/consistency-review.ts` 作为 `hooks.after_land` 的一条命令运行，不拦合入；不写进 `hooks.after_land` 就不运行，所以用 canon 的其他项目默认不开，开不开、每次查几个领域由各项目自己定（BR-2271）。发现提成带 `canon-consistency` 标签的 issue，一个根因一个（BR-2272）。停用标准：这个标签下已关闭的 issue 至少 10 个、其中按 `completed` 关闭的不到一半时，脚本不再调用评审命令，只输出一行说明（BR-2273）；两个数都可以用参数改。输出行以 `code-review: consistency: ` 开头，这样 `canon work after-land` 不用改就会照抄它们（BR-2166）。

## 后果

- 每次查一个领域就是一次 AI 调用，提示里是这个领域的规则、点名它们的测试段落和领域代码，可能有几万 token；默认每次合入只查改动文件最多的一个领域，超过 `--max-bytes` 的领域跳过并写明。
- 重复的 issue 按 triage 的做法以 `not planned` 关闭，也算成误报，准确率会偏低一点；停用线留了余量。
- canon 仓库自己开不开、每次查几个领域，留给负责人决定，这次不写进 `canon/config.yaml`。
