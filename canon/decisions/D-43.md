## 背景

规则评审只看文字，测试检查只看测试名里有没有规则编号（BR-2005）。规则写“退出码 3”、代码返回 1、点名它的测试测的是别的东西时，两道检查都放行。C-13 用独立子 agent 逐条对照过一次，查出 4 个真问题（#1 到 #4），但没有定期机制。lore 的自查曾经比它省下的还贵（D-1），所以每次花多少、什么时候停要先定好。

负责人 2026-11-04 要求做，做成了 scripts/consistency-review.ts（作为 `hooks.after_land` 的命令，按领域调用评审命令，发现提成 `canon-consistency` issue，按结案原因算准确率）。之后：

- 独立评审指出几处问题，负责人先选“先关掉”（C-251 去掉了 `hooks.after_land` 里的这一条），又选按评审重做（C-298 修订了本决策和规则）。
- **真实使用只有一次（2026-11-04）。** 事件表里它作为 `after_land` 命令只运行过一次（事件 3795、3799，退出码 0），输出是“no domain's rules or code changed; nothing to check”，没有调用过评审命令；GitHub 上 `canon-consistency` 标签下没有 issue。现在在 `canon/config.yaml` 里是关着的。
- 修订时发现的几处缺口（结案原因算不准、评审读不到共享内核、最大的领域永远超过字节上限）都只是读代码得出的，没有一条来自真实运行，所以再往上加机制没有依据。

## 方案

1. 保留并继续修订：否决。花的功夫都是为一个只运行过一次、没有任何发现的检查，没有数据说明它值得留。
2. 作为 `before_land` 检查，不一致就拒绝合入：否决。一次 AI 调用要几分钟、结论有误报，挡住合入的代价比晚一点发现大（D-1 同理）。
3. 整个删掉，不做自动的一致性抽查：采用。负责人 2026-11-04 的选择（原话）：“整个删掉 (推荐)”。

## 决定

暂不做自动的一致性抽查。删除 scripts/consistency-review.ts、src/knowledge/review/consistency.ts 和它们的测试，规则 BR-2271、BR-2272、BR-2273 退役，canon-triage 里关于 `canon-consistency` 结案原因的一段删掉（C-299）。

原因：它真实运行过一次，没有发现任何问题，没有调用过评审命令，没有提过 issue；负责人选择删掉。

什么情况下值得重新考虑：出现一类“规则、代码、测试三者不一致，而规则评审和测试检查都放行”的问题，并且手工检查不再够用（例如反复漏掉，或者手工查一次的间隔长到问题已经上线）。重新做时先有真实发现，再决定准确率怎么算，不预先搭统计和停用机制。

## 后果

- 这个需求眼下由手工只读检查覆盖：像 #1 到 #4 那样，由人或子 agent 对照规则、测试和代码读一遍，发现的问题手工提 issue。
- 删除前的代码在 git 历史里：最后一个还带着它的提交是 `6856e77`（C-296 的收尾提交）；要恢复就从那里取 scripts/consistency-review.ts 和 src/knowledge/review/consistency.ts。
- `code-review.ts` 里为它留的 `rule` 字段和类别参数已一并去掉；合入后的代码评审（BR-2210）不受影响。
