## 背景

规则评审只看文字，测试检查只看测试名里有没有规则编号（BR-2005）。规则写“退出码 3”、代码返回 1、点名它的测试测的是别的东西时，两道检查都放行。C-13 用独立子 agent 逐条对照过一次，查出 4 个真问题（#1 到 #4），但没有定期机制。lore 的自查曾经比它省下的还贵（D-1），所以每次花多少、什么时候停要先定好。负责人 2026-11-04 要求做（“先保证其他”），并要求它每次合入都花 token，所以要能配置、其他项目默认不开。

之后对 D-43 的独立评审指出了几处问题，负责人当天先选“先关掉”（C-251 去掉了 `hooks.after_land` 里的这一条），又选择按评审重做（选项“D-35、D-43、D-40 一并重做”，D-35 和 D-40 在 C-255 里重做成了 D-49 和 D-57）。按 D-54（只修正常操作会引出的问题）对照现在的代码和真实数据逐条核对：

- **真实使用只有一次（2026-11-04）。** 事件表里它作为 `after_land` 命令只运行过一次（事件 3795、3799，退出码 0），输出是“no domain's rules or code changed; nothing to check”，没有调用过评审命令；GitHub 上 `canon-consistency` 标签下一个 issue 也没有。背景里的 #1 到 #4 是 C-13 手工逐条对照时提的，没有这个标签。所以下面所有问题都是读代码和 canon-triage 得出的，不是真实运行中遇到的。
- **准确率算不准（属实，改）。** canon-triage 把“已经在 main 上修好”、重复、已知限制和被决策否决的 issue 都关成 `not planned`（`gh issue close` 只有 `completed` 和 `not planned` 两种原因），它们都被当成误报。没人分拣时 issue 一直开着，不计入已关闭数，停用线永远到不了。
- **评审命令不独立、材料不全（部分属实）。** 评审命令在主 checkout 里运行，合入之后 main 可能已经前移，它读到的可能不是被查的提交（改）。只给领域自己的代码，`src/kernel/` 和 `scripts/` 不给，规则要的行为在那里时会误报 `code-mismatch`（改成提示里写明）。它读项目的 `CLAUDE.md` 不是问题：评审命令本来就该按项目的规矩读。同一类模型评审同一类模型写的代码，这一点和 D-49 一样没有办法缓解，写成已知限制。
- **领域选择不看规则改动（属实，改）。** 按改动文件数排，一条规则的改动会输给另一个领域的五个代码文件，而规则改动最可能带来不一致。
- **最大的领域永远查不到（属实，已知限制）。** 提示超过 `--max-bytes` 的领域每次都跳过；按字节粗算 `cli/install` 的规则（约 54000）加代码（约 81000）已经到约 135000，再加点名规则的测试段落就会超过 150000。跳过时输出里写明了，加大 `--max-bytes` 就能查，花费也跟着涨，这是负责人要定的花费上限，不加机制。
- **D-49 的判定不能直接用。** D-49 的判定对象是评审拦截合入时的每条意见（`review.block` 事件），一致性抽查的发现是合入之后的 GitHub issue，没有拦截事件可判；要用就得为 issue 另写一套盲判，这是还没在真实使用里出现过的新机制，这次不做。

## 方案

1. 作为 `before_land` 检查，不一致就拒绝合入：否决。一次 AI 调用要几分钟、结论有误报，挡住合入的代价比晚一点发现大；D-1 定的是合入后的代码评审不拦合入，这里同理。
   - 来源：canon/rules/knowledge/review/BR-2070.md “合入后的代码评审看完整 diff 和改动文件的全文”
2. 定期把所有领域都查一遍：否决。canon 有二十多个领域，一次全查是二十多次调用，大多数领域自上次以来没改过，花的 token 大多白费。
3. 作为 `after_land` 后台命令，只查这次合入改到规则或代码的领域，每个领域一次调用，每次合入最多查几个领域由参数定：采用。改动刚发生时最可能不一致，范围和花费都跟着改动走；复用代码评审的提 issue、去重和失败处理（BR-2072、BR-2211）。
4. 发现提成和代码评审同一个标签 `canon-review` 的 issue：否决。两种评审的准确率要分开算，才能单独停掉不准的那个；用单独的标签 `canon-consistency`。
5. 准确率只靠负责人手工统计：否决。没人统计就一直花下去。脚本每次运行前自己从 GitHub 读这个标签下已关闭 issue 的结案原因（`completed` 算对，`not planned` 算错），够数且低于停用线时不再调用评审命令。
6. 为准确率另建一套判定（每条发现由 canon 运行的盲判命令判，像 D-49 那样，或为这个标签加专门的结案标签、人工抽样）：否决。结案原因本来就是分拣的一个结论，只要分拣把 `not planned` 留给“评审说错了”，它就是够用的准确率；盲判是一套新机制，而这个检查到现在只运行过一次、一个发现都没有，没有数据说明现在的做法不够。
7. 保留原样（`not planned` 不分原因，只算已关闭的）：否决。评审指出的两个缺口都是正常使用会遇到的：分拣关 issue 时就会这样关，没人分拣时就会一直开着。

## 决定

采用方案 3 和 5，按评审修订（D-43 仍是 `proposed`，只改这一条，不新建决策）。`scripts/consistency-review.ts` 作为 `hooks.after_land` 的一条命令运行，不拦合入；不写进 `hooks.after_land` 就不运行，所以用 canon 的其他项目默认不开，开不开、每次查几个领域由各项目自己定（BR-2271）。发现提成带 `canon-consistency` 标签的 issue，一个根因一个（BR-2272）。停用标准有两条（BR-2273）：这个标签下未关闭的 issue 不少于 10 个时（没人在处理，已关闭数到不了停用线），或已关闭的至少 10 个、其中按 `completed` 关闭的不到一半时，脚本不再调用评审命令，只输出一行说明；三个数都可以用参数改。结案原因的含义写进 canon-triage：这个标签的 issue 只在评审说错了（复现不出来）时关成 `not planned`，已经在 main 上修好、重复、已知限制、被决策否决的都关成 `completed`。评审命令在 `CANON_HEAD` 导出的代码树里运行；领域按改到的规则文件数排在改动文件数之前（BR-2271）；提示写明共享内核和 `scripts/` 没给它，只有展示出来的代码明确做了别的事才算 `code-mismatch`。输出行以 `code-review: consistency: ` 开头，这样 `canon work after-land` 不用改就会照抄它们（BR-2166）。

## 后果

- 每次查一个领域就是一次 AI 调用，提示里是这个领域的规则、点名它们的测试段落和领域代码，可能有几万 token；默认每次合入只查一个领域（改了规则的优先，再看改动文件数），超过 `--max-bytes` 的领域跳过并写明。
- 已知限制（D-54）：结案的是分拣的 AI，和写代码的是同一类模型，准确率是它的判断，不是人的判断；只有出现真实的发现、能和人的判断对照之后才值得再加机制。这个检查关着，打开要负责人决定。
- 已知限制：超过 `--max-bytes` 的领域一直查不到；评审和被查的代码是同一类模型；共享内核和 `scripts/` 里实现的行为评审看不到，只靠提示要求它不因此报。
- canon 仓库自己开不开、每次查几个领域，留给负责人决定：现在关着（C-251），这次修订不重新打开，也不写进 `canon/config.yaml`。
