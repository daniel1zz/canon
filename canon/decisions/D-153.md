## 背景

#280：项的声明（D-144、BR-2546）让项目在 `canon/config.yaml` 里写任意正则（`pattern` 槽位和 `none`），canon 读文档时同步地拿它们去对每一项。像 `(a+)+` 这样的写法在回溯引擎里随输入长度指数增长，C-635 的复现里 30 项就让 `canon show` 用了 22 秒；`canon check` 读全部文档，每多一项就多一份。这属于「检查的分寸」里的安全问题，也违反 P5：读出的元信息会错。

C-635 还实测到，Bun 用的 JavaScriptCore 回溯超过上限时不报错，直接返回没对上，所以这类正则不只是慢，还会悄悄读错。项目的配置也可能来自别人的仓库，canon 不能假设写正则的人知道哪些写法危险。

## 方案

1. **用线性时间、不回溯的引擎（re2js，Google RE2 的纯 JavaScript 移植）跑读项时的全部正则；声明时按 RE2 语法核对，不支持的写法（查找、反向引用）是配置错误，信息写出文件、key、正则原文和原因**：采用。不管正则怎么写，匹配时间都随输入线性增长，不需要判断哪种写法危险，也不会被引擎半途放弃；代价是少了查找和反向引用两类写法，而项的元信息只是短的标记，用不到它们；re2js 没有运行时依赖，能打包进单文件的 `dist/canon.js`。
   - 来源：https://github.com/le0pard/re2js “designed to operate in time proportional to the size of the input”
   - 来源：canon/changes/C-635.md “`canon show ADR-1 --json` 用了 22 秒”
2. **保留 JavaScript 自带的引擎，声明时用静态检测（safe-regex、redos-detector 一类）拒绝危险写法**：否决。这类检测是启发式的，会漏，漏掉的照样卡住；正则还要嵌进模板拼成整条，单独检测一个槽位的正则看不到拼起来之后的回溯；检测器自己也要设步数上限，超过就给不出结论。
   - 来源：https://github.com/davisjam/safe-regex “both false positives and false negatives”
   - 来源：https://github.com/tjenkinson/redos-detector “If this limit is hit error will be hitMaxSteps”
3. **保留自带的引擎，给匹配加时限**：否决。JavaScript 没法中断一次正在运行的匹配，要放到 worker 或子进程里才能限时，读文档会从同步变成异步，每项多一次进程间往返；超时以后这一项读成什么也得另定规则。而 Bun 自带的引擎已经有一个步数上限，C-635 实测它到上限就把对得上的项当成对不上，正说明「到时限就放弃」会读错。
   - 来源：canon/changes/C-635.md “回溯到一定步数就放弃，不报错，直接当成没对上”
4. **用原生模块 node-re2**：否决。它要编译 C++ 扩展，`bun build` 打不进单文件，安装 canon 时还要有编译环境；re2js 用纯 JavaScript 做到同样的线性保证。
   - 来源：https://github.com/le0pard/re2js “RE2JS is a pure JavaScript port”

## 决定

采用方案 1。语法和配置错误见 BR-2546，用时的保证见 BR-2547；依据和实测数字写在 C-635 的「方案依据」里。

## 后果

- 项目的 `pattern` 和 `none` 按 RE2 语法写：不能用查找和反向引用，码位写 `\x{…}`，`\s`、`\S`、`\d`、`\w` 只认 ASCII。已经用了这些写法的项目，升级后命令退出码 2，按信息改写即可。
- canon 内置的声明也走同一个引擎；`ids` 槽位分隔符后的空白写成和 JavaScript 的 `\s` 等价的字符类，行为不变。
- 多一个打包进 `dist/canon.js` 的依赖，打包后大约多 240 KB；读全部教训的时间从 3 毫秒变成 15 毫秒，启动时间没有可测的差别。
- 以后 canon 别处要跑项目写的正则时，也用这个引擎，不再用 `new RegExp`。
