## 背景

D-2 定了四种扩展方式，但没定 `canon/config.yaml` 具体怎么写。实现 C-1 时有几处真实的取舍：策略参数怎么命名、现有的 `review` 和 `after_land` 怎么并入 hook、项目自己的文档类型怎么声明、几个 hook 是同步还是后台运行。配置写错时所有命令都要以退出码 2 失败（D-2），所以形状越简单，写错的机会越少，报错也越好懂。

## 方案

1. 策略参数按模块嵌套（`claim: {lease_hours}`、`land: {stale_minutes, timeout_minutes}`）。否决：只有五个参数，嵌套多一层缩进，却没有减少歧义。
2. 策略参数平铺、名字带单位（`claim_lease_hours`、`lander_stale_minutes`、`land_timeout_minutes`、`worktrees`、`tests`）。采用：一眼能看出单位，校验也最简单。
3. `review` 也挪进 `hooks.before_land`。否决：评审的协议不同（stdin 收提示、stdout 给 JSON 结论，只在规则或决策变了时才跑），硬塞进通用 hook 要么丢掉这些语义，要么让 hook 变复杂。
4. `review` 保留为顶层配置，作为内置的第一个 `before_land` 步骤；`after_land` 挪进 `hooks`。采用。旧的顶层 `after_land` 当作未知 key 报错，提示改成 `hooks.after_land`，不悄悄兼容。
5. `after_start`、`after_stop` 在后台运行，和 `after_land` 一样。否决：它们很快，同步运行能把输出直接给正在干活的 agent（例如提示要读的东西）；退出码照样不影响结果。只有 `after_land` 在后台，因为它常常很慢（构建、代码评审），而合入者不该等它。
6. 文档类型声明在 `types:` 下，键是类型名，写明 `prefix`、`dir`、`statuses`、`default`，可选 `fields`（必填的额外 front matter 字段）。内置的四种类型只能声明 `fields`。采用。另一种做法是每种类型一个配置文件，否决：类型很少，分散到多个文件反而难查。

## 决定

- 平铺的策略参数：`claim_lease_hours`（默认 12）、`lander_stale_minutes`（默认 10）、`land_timeout_minutes`（默认 60，`--timeout` 可覆盖）、`worktrees`（默认 `<checkout>.worktrees`，相对路径按主 checkout 解析）、`tests`。数值可以是小数，但必须大于 0。（注，2026-11-04：之后加入的 `land_keep_place_minutes` 是例外，可以是 0，表示冲突被拒后不保留排队位置，见 BR-2177。）
- `hooks:` 下有 `after_start`、`before_land`、`after_land`、`after_stop`，每项是一条命令或命令列表。`before_land` 在 floor、`canon check` 和内置评审之后、移动 main 之前，在即将成为 main 的代码树上依次运行，第一个非 0 就拒绝合入。`after_start`、`after_stop` 同步运行，`after_land` 在后台运行，三者的退出码都不影响结果。
- `types:` 声明文档类型。声明的类型自动参与编号分配、读取、`canon check`、搜索和上下文；命令是 `canon doc new|list|status`。
- 模板放在 `canon/templates/<类型名>.md`，没有时用内置模板；有模板文件却没有对应类型时算配置错误。
- 命令以路径开头（含 `/`）而文件不存在时算配置错误；命令名是 PATH 上的程序时不检查，因为那要在每个命令里启动子进程。

## 后果

- canon 自己的 `canon/config.yaml` 要把 `after_land` 挪进 `hooks`。
- 每次 hook 运行都写一条 `hook.run` 事件，C-9 的统计可以用。
- 新增 `config` 领域管这些规则；租约、心跳、超时这些参数的规则仍在 `work` 领域，写明默认值和配置项。
