## 背景

#322 报 zhushenkongjian 一夜并行开发 15 个以上变更，只合入了 5 个变更和 5 个杂务，排队超时、反复被拒。C-720 原计划按路径分几条合入队列（负责人 2026-11-28 回答问题 #78、#79）。设计前量了 2026-11-27 12:00 到 11-28 06:00 的协调数据库和合入日志：

- 108 次轮到合入。轮次中位数约 60 到 90 秒，但 18 次超过 5 分钟的长轮次占全部轮次时间的 82%（37213 秒里的 30654 秒）。
- 长轮次的时间几乎都花在 BR-2645 的交叉测试上：一次跑 200 到 884 个测试文件（项目一共 1322 个），一个文件一个文件串行跑，全程占着唯一的轮次。原因是 BR-2645 跑的是 test_select_command 给 main 那边挑出的全部测试，而分支分叉越久，main 那边积累的改动越多。
- 单个游戏变更只挑 40 到 150 个测试；抽了 5 对相邻的游戏提交，两边共同挑中的都约 38 个。
- 72 次被拒里 25 次是 before_land hook，都在拿到轮次之后才被拒；看过的拒绝信息（规则按键、教训格式、决策参考链接、变异测试证据）只取决于变更自己的内容。
- 排队时机器负载常常只有 5 到 11（18 核）。

分道救不了这个：游戏变更之间仍然串行；而且游戏变更都带 `canon/` 下的变更文件和规则，会同时占游戏和文档两条道。一个不知道我倾向的子 agent 挑战设计时指出了同样的问题，还指出分道会让 `canon check` 管的引用完整（P5）在两条道同时移动 main 时失守。负责人 2026-11-28 回答问题 #81：「先修交叉测试（推荐）」，做完再量，仍然排队才做分道。

## 方案

1. 按路径分几条合入队列，主 agent 可以改：否决（先不做）。上面的数据说明瓶颈在轮次里的重步骤，不在只有一条队列；D-82 也因为两条队列同时移动 main 要重跑步骤而否决过同类做法。
   - 来源：canon/decisions/D-82.md “范围合入走单独的一条队列，和全量合入同时前移 main：否决”
2. 交叉测试只跑 test_select_command 给两边都挑中的测试文件：采用。只给 main 那边挑中的测试，按 test_select_command 的判断只读 main 那边改的文件，这个分支的改动不影响它的结果，它在合并后的树上和在 main 上结果一样，main 的后台测试本来就跑它；两边都挑中的，才是“各自通过、合在一起才坏”可能出现的地方。前提和 BR-2645 一样信 test_select_command（D-64），不读源码。
   - 来源：canon/rules/work/land/checks/BR-2645.md “两个变更各自在自己的树上通过，合在一起才坏”
3. 合入自己跑的测试（BR-2542、BR-2381、BR-2645）按 `canon work test` 的规则同时跑几个：采用。BR-2302 只在至少有 1 个 CPU 空闲时才多开一个，同时跑时失败的文件单独重跑一次（BR-2303），已经在 `canon work test` 上用了很久；D-26 记的负载 150 是几个全量 floor 同时跑，不是这种按空闲 CPU 开的。
   - 来源：src/work/verify/verify.ts “another one only while at least 1 CPU is idle”
   - 来源：canon/decisions/D-26.md “多个 floor 同时跑曾出现负载 150、70 多个假失败”
4. before_land 在排队前先在分支上预跑一次，失败就不进队列：采用。只看内容的检查不再占轮次才被拒；轮次里照旧在要成为 main 的树上再跑一次（BR-2057），所以不放松任何检查。代价是通过的合入多跑一遍 hook（不占轮次）。
5. 给交叉测试设上限，超过就少跑：否决。悄悄少测，漏掉的问题由后台测试发现，main 红了冻结所有合入，代价从排队挪到了冻结。
6. 交叉测试挪到合入之后，当作后台测试的一部分：否决。同样让 main 更常变红、冻结合入；这一夜已经因 main 红了拒了 11 次。

## 决定

采用方案 2、3、4：BR-2645 改为只跑两边共同挑中的测试；BR-2645、BR-2542、BR-2381 跑测试时和 `canon work test` 一样同时跑几个；新规则 BR-2652 让 before_land 在排队前预跑。分道（方案 1）等这些落地后再量 zhushenkongjian，仍然排队时另开变更。

## 后果

- 交叉测试从一次最多 884 个文件降到两边共同挑中的数量（通常约 40 个），而且同时跑；长轮次应从几十分钟降到几分钟。合入后用 `canon stats --since` 再量一次：长轮次仍占大头，就说明判断错了，回到方案 1。
- 交叉测试更窄了：test_select_command 漏挑的测试，交叉测试也不会跑。这和 BR-2645 原来的前提一样（D-64），由 main 的后台测试和自动撤回兜底（BR-2535、BR-2536）。
- 预跑在分支自己的树上，`CANON_BASE` 是分支和 main 的分叉点；只在 main 移动后才会通过的 hook 可能被预跑误拒，这时 rebase 到 main 再合入。hook 可以读 `CANON_HOOK_PREVIEW=1`，自己决定预跑时跳过。
- 同时跑的合入测试和 `canon work test` 一样受 `test_jobs` 和 CPU 空闲控制，进轮次前照旧过负载关（BR-2630）。
