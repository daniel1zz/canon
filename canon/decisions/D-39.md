## 背景

issue #36：撤回关闭提交（BR-2018）先用 `git update-ref HEAD parent sha` 比较并交换地移动分支，再用另一条 `git read-tree -m -u sha parent` 更新索引和文件。两条命令之间 HEAD 已经是 parent，索引还是关闭提交的树（`status: done`）；这时会话里的 `git commit -am fix` 会做出一个仍是 `status: done` 的提交，reopen 却报告成功。一起测的成员跟上 main（BR-2172、BR-2191）是同一个两步写法，间隙里的提交会把这一批带来的文件删掉。

实测（git 2.50.1 Apple Git-155，2026-11-04）：

- 用 reference-transaction hook 在分支移动之后立刻运行 `git commit -qam fix`，改动前两处都能复现：reopen 返回成功但 HEAD 是间隙里的新提交；成员的间隙提交以 0 退出。
- worktree 的 `index.lock` 存在时，`git commit -am` 和不带 `-a` 的 `git commit` 都以 128 退出，`fatal: Unable to create '.../index.lock': File exists.`

## 方案

1. 先更新索引和文件，再比较并交换地移动 HEAD。否决：间隙只是换了位置；间隙里的提交落在关闭提交上面、带着 `open`，之后 HEAD 的交换失败，留下的状态要另外判断怎么收拾。
2. 改用一条 `git reset --keep parent`。否决：它不是比较并交换（移动 HEAD 时重新读 HEAD），而且它自己也是先放开索引锁再移动 HEAD，间隙还在。
3. 按 git 的锁文件约定拿住 `<index>.lock`（以独占方式新建），持锁时比较并交换地移动 HEAD，再用 `GIT_INDEX_FILE` 指向一份索引副本运行 `git read-tree -m -u`，成功后把副本改名成索引，最后删掉锁。采用。所有会写索引的 git 命令（`commit`、`add`）都要先建这个锁文件，建不了就失败，所以持锁期间没有提交能做成；持锁之前已经读了旧 HEAD 的提交，它最后的比较并交换会因为 HEAD 已经变了而失败。
   - 来源：src/kernel/git.ts “fd = openSync(lock, "wx");”
   - 来源：src/kernel/git.ts “const sync = gitEnv(wt, { GIT_INDEX_FILE: scratch }, "read-tree", "-m", "-u", from, to);”

## 决定

用方案 3，放在 `src/kernel/git.ts` 的 `moveBranch`；reopen（`src/work/land/finish/finish.ts`）和成员跟上 main（`src/work/land/batch/batch.ts`）都改用它。锁被别的 git 命令占着时最多等 2 秒（git 自己不等这个锁，`git status` 刷新索引时会短暂拿它），之后放弃移动，按各自规则说明原因（BR-2258）。canon 只删自己建的锁，别人的锁从不删。

## 后果

- 撤回关闭提交和成员跟上 main 时，HEAD、索引、文件要么一起变，要么都不变；会话在这一刻的提交被 git 拒绝，会话重试即可。
- 一个崩溃的 git 留下的 `index.lock` 会让这两步不做（等 2 秒后放弃），和 git 自己在这种情况下拒绝一样；canon 不替人删它。
- 不走 git 锁约定的写法（直接 `git update-ref HEAD`、`git reset --soft`）不受约束，这和 git 自己的行为一致。
