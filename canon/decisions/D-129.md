## 背景

负责人 2026-11-17 提出（#248）：问进度时会话总从最近做的小变更往回讲，整体规划要负责人提醒才出现；原话“这个没法让canon做成一个命令吗”。数据分散在 `canon release status`、`canon plan status`、`canon/backlog.md`、`canon change list` 和 `canon human pending` 里。更要紧的是 `canon release status` 只数规则：zhushenkongjian 的 `R-5` 显示“已通过 620”，可版本文档 `## 成功标准` 里“五个体系各至少有一条构筑能通关全部主线世界”“负责人完整玩通主线前半部分”没有任何记录，现有命令不会提示。成功标准是自由文字，canon 现在完全不读它。

负责人在两个问题上做了选择：成功标准的状态记在哪（问题 #48，选“写在版本文档里”）；issue 提到的“变更文件里标为人工验收的项”canon 没有这个概念，是否另加（问题 #49，选“不另加”：需要负责人验收的事写成成功标准并标“待负责人”）。

## 方案

1. 成功标准每一条在第一行末尾写标记：已满足（带证据编号）、未满足、待负责人；没有标记或已满足没写证据的显示“未证明”：采用（负责人选定）。状态和证据跟版本文档一起进 git，改动走合入和规则评审；证据编号由 `canon check` 现有的引用检查保证存在。
   - 来源：https://github.com/daniel1zz/canon/issues/248 “没有证据的条目明确显示为「未证明」，而不是因为规则全过就显示完成”
2. 用命令把每条的状态记到协调数据库（`canon release criterion R-5 2 --met --evidence C-12`），文档不动：否决。按条目序号对应，文档改了序号就对不上；数据只在本机（product.md 不做多台电脑），也不经过合入时的检查；负责人没选它。
   - 来源：canon/product.md “协调状态只存在本机这个 checkout 里”
3. 不加标记，从成功标准的文字里推断（提到规则就看规则状态）：否决。文字是自由的，推断出来的“已满足”正是 #248 要消灭的那种冒充；P5 要求规划中的东西不冒充已实现。
   - 来源：canon/product.md “规划中的规则标明还没做，不冒充已实现”
4. 总览放进 `work/session`（和 `canon work status` 同一个业务）：否决。`work/session` 已有 36 条规则，超过拆分提示；总览读的是版本、计划、问题、评审意见和待办五个领域的数据，是给负责人看的进度报告，不是会话的开工和交接，所以单独一个子领域 `work/overview`。
   - 来源：canon/rules/work/session/README.md “工作从开始到结束在 worktree 里怎么过”

## 决定

成功标准的标记和状态按 BR-2504；`canon overview` 的五节按 BR-2505；没认领变更的会话，`canon brief` 打印总览摘要按 BR-2506。“人工验收”不另设概念（问题 #49）。当前版本由版本状态决定（BR-2505），不另加配置键：`active` 本来就是“正在做的版本”的标记。

## 后果

- 已有项目的成功标准都没有标记，第一次看总览时全部是“未证明”；要由会话按证据逐条补标记，这正是要暴露的事实。
- `canon release ship` 不检查成功标准，照旧只要求规则全过和负责人的 yes（BR-2331、BR-2333）；要不要把成功标准也作为发布条件，另由负责人定。
- 没认领变更的会话每次开头多 2 到 4 行。brief 里的摘要不算规则的执行状态：zhushenkongjian 里算一次要 4.7 秒（2026-11-17 实测），每个会话开头都付不起；规则的数量只在 `canon overview` 里算。
