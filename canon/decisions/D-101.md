## 背景

负责人要求 Codex 能运行现有工作流。身份、技能目标和 hook 输入目前绑定 Claude。Codex 已有 AGENTS.md、仓库 skills 和 hooks，但事件里的编辑内容是 patch，原生提问以问题 id 关联回答。实机父子会话的 shell 进程各自读取环境的哈希，验证 CODEX_SESSION_ID 相同、CODEX_THREAD_ID 不同；父会话两者相同。

## 方案

1. 每次都安装两个宿主的入口。否决：未使用 Codex 的现有项目会无端增加文件，并因另一端缺少配置而提示过期。
   - 来源：src/install/update.ts “Updating is never automatic”
2. 明确选择 claude、codex 或 all；之后按 canon 的清单与管理标记识别已安装的目标，共用业务流程。采用：普通终端与 agent 中调用产生同样的结果，不凭用户已有的 .codex 目录接管设置；所有目标一起预检，另一端有冲突时不半装。
   - 来源：https://learn.chatgpt.com/docs/build-skills.md “For repositories, Codex scans `.agents/skills`”
3. 只按当前进程环境选安装目标。否决：普通终端和 CI 的更新结果会不同，混用两个宿主时会漏更新。
4. 顺便把技能源迁往新目录。否决：发布及源头定位已经引用现有目录，本次保留单一源头，向各目标分发即可。

独立子 agent 在不知道推荐项时挑战以上方案，指出不能仅凭目录存在认领配置、必须先完成所有目标预检、暂存路径必须覆盖新资产、身份命名不能破坏主会话两段结构；本方案均采用。模块审查：身份归一化只负责宿主上下文，安装只负责项目资产，协调和评审继续复用；没有新数据库或插件框架。文件和进程边界用真实临时仓库测试。

## 决定

选择明确安装目标，路径、生命周期和管理段按 BR-2459、BR-2460；不是按当前进程猜目标。保留现有单一技能源，避免技能在两套宿主中各维护一份。

执行者与原生线程关系记录按 BR-2023，存活探测按 BR-2100。真实 Codex hook 进程没有会话环境变量，因此用启动 payload 和已有共享事件表恢复亲缘；不引入额外数据库或依赖不稳定的 transcript。这让环境变量不完整的原生子线程仍可被父会话接管。

运行时只在边界翻译原生工具输入，继续调用已有业务流程。常驻说明评审按 BR-2143，编辑检查按 BR-2402，快照按 BR-2182，问答记录按 BR-2275。

## 后果

- Claude 旧入口、身份及自定义 reviewer 不变；用 --agent codex 或 --agent all 增加 Codex 入口。回退可移除 Codex 管理资产，不迁移共享协调数据库。
- hook 配置写入不代表宿主已信任或已执行，安装提示用户在 Codex 完成 hook trust。没有可识别会话 id 的第三方客户端仍需显式 CANON_ACTOR；异步提问尚无最终回复的工具结果不作为人类回答证据。
- 不通过解析不稳定 transcript 猜问答，canon usage 原有日志统计的范围另按其规则，不把它当成协调身份或问答佐证。
