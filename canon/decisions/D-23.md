## 背景

本会话里一次改认领的变更弄坏了 `src/config` 和 `src/cli` 下的测试，只有合入时的 floor 发现，结果是一次被拒的合入加上约 2.5 分钟重新排队。工作说明只说“在 worktree 里只跑和改动相关的测试”，哪些算相关由 agent 自己猜，而它最容易漏掉的正是间接用到改动的测试。另一次把多个测试文件放进一个 `bun test` 卡住（Bun 1.3.x 的缺陷，升级到 1.4.4 后修好，#35），所以 CLAUDE.md 要求一个文件一次地运行。canon 要给别的项目用，测试工具不一定是 bun。

## 方案

1. 挑选：改过的测试文件，加上相对导入（经过源码文件传递）用到改过文件的测试文件，加上测试名写了本变更碰过的规则的测试文件。采用：导入的读法和 `canon context` 共用，不用声明任何东西；测试名按规则编号对应是 canon 已有的约定，能补上靠导入找不到的测试（比如通过子进程运行 CLI 的测试）。
   - 来源：scripts/select-tests/imports.ts “Repo paths of the relative imports in a file, read at run time”
2. 只挑改过的测试文件和同目录的测试。否决：本会话那次漏掉的正是别的目录里间接导入的测试。
3. 用 `bun test --changed` 这类测试工具自带的挑选。否决：只有部分工具有，canon 要支持任意测试命令；而且它们不知道规则和测试名的对应。
4. 运行命令：新增 `test_command`，必须含 `{file}`，canon 对每个文件替换一次。采用：npm、vitest、pytest、go 的命令都能写成这样；必须含占位符，写错时在读配置时就报错，而不是跑起来才发现文件没传进去。
5. 运行命令：在 `test_command` 后面直接追加文件路径，不用占位符。否决：有的工具要求路径在中间（比如 `go test {file} -run X`），追加做不到；两种写法都支持又多一种出错方式。
6. 运行命令：从 floor 里推断（比如去掉 `&& bun test` 前面的部分）。否决：floor 是任意 shell 命令，推断不可靠，猜错时是无声的。
7. 没写 `test_command` 时默认用 `bun test {file}`。否决：猜测项目的测试工具，猜错时会报一堆不相干的错误；没写就明确失败并给出例子。

## 决定

用方案 1 挑选、方案 4 运行（BR-2157、BR-2158、BR-2159、BR-2160）。文件依次运行，不并行：几个 worktree 同时测试时负载已经很高，再并行会让测试更不稳。工作说明改成合入前运行 `canon work test`。

## 后果

- 只在运行时读取改动文件（不导入）的测试不会被选出，例如读 skill 文件的安装测试；输出里写明这一点，需要时用 `--all`，floor 也仍然跑全量。
- 改了被大量导入的文件（如 `src/invocation/config.ts`）时，几乎全部测试都会被选出，用时接近全量，这是正确的结果。
- 每次运行在事件表里记 `work.test`，以后可以对比“合入前跑过 canon work test”和“floor 被拒”的关系，判断它是否真的减少了被拒的合入。
