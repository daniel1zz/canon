id: D-58
title: 被杀掉的合入：开始时记 land.start，之后由 status、下一次 land、after-land 和 brief 对照进程报出来
status: accepted
---

## 背景

2026-11-04 事故：子 agent 把 `canon work land --finish`（C-273）当后台 Bash 任务启动后结束了自己的回合，harness 把合入进程杀掉。`canon events --subject C-273` 只有 `start.ok`、`work.test`，之后什么都没有；`canon work status` 里认领还在、队列是空的；协调者过了约 1 小时 45 分钟才发现。

本机复现（2026-11-04，临时项目，真实 CLI，`kill -9` 只杀 canon 进程）：

| 杀的时机 | 事件表 | 队列 | worktree | 之后 `status` / 再次 `land` |
| --- | --- | --- | --- | --- |
| 关闭提交的时候（入队前） | 只有 `claim.renew` | 空 | 关闭提交在分支上，变更文件写着 `done` | `status` 一切正常、什么都没报；再次 `land` 直接合入，一个字不提上一次 |
| 排队等轮次 | 到 `queue.enter` 为止 | 条目 `waiting`，进程已死，照常列出 | 关闭提交留着 | `status` 列出一个看起来正常的 `waiting`，认领标 `expired: session process exited`；不报死因 |
| floor 运行中 | 到 `land.turn` 为止 | 条目 `landing`，进程已死 | 关闭提交留着；floor 的子进程成了孤儿（ppid 1）继续跑 | 同上；再次 `land` 成功，什么都没说 |
| rebase 中途（用手工留下的 rebase 状态代表） | 同上 | 同上 | HEAD 游离、有冲突文件 | 再次 `land` 以 `on-main` 拒绝，信息里完全没提 rebase |

三个共同点：没有任何终结事件（`land.ok`、`land.refuse`、`land.killed`、`land.lost` 都没有）；已有的 SIGTERM 处理（BR-2099）对 SIGKILL 不起作用；死掉的排队条目只在后面某个合入者查轮次时被悄悄标成 `abandoned`，之后从 `status` 里消失，队列看起来就是空的（事故里的样子）。canon 已经有“进程是否还在”的探测（D-11，`isGone`，认领和排队条目都用），合入开始时却没有记下是哪个进程。

## 方案

1. 不改，靠协调者自己盯：否决。事故就是这样，花了 1 小时 45 分钟；`kill -9`、harness 超时、会话被关都是日常用法（D-11 背景已写明工具超时杀合入者是常态）。
2. 合入一开始就记一条 `land.start` 事件（带合入者的 pid 和启动时间），“被杀掉”由事件表和进程探测推出来：该 worktree 最近一条 `land.start` 之后没有终结事件，且 `isGone` 证明进程不在：采用。不加表、不加列；每个出口本来就写终结事件（BR-2026），所以不用新增“结束”记录；活着的进程不会被判成死的（pid 加启动时间，读不到进程表时说“不确定”，不下结论）。
   - 来源：src/work/claims/liveness.ts “True only when the process is provably gone”
3. 新建 `landings` 表，开始时插一行、每个出口把它改成终态：否决。出口很多（拒绝、超时、批里被别人合入、信号、异常），漏改一个出口就会把正常结束的合入报成被杀；事件表已经有每个出口的记录，再存一份状态是重复。
4. 把入队提前，让队列条目充当“开始记录”：否决。条目有排队语义，别的合入者会把它算成排在前面的条目；而且条目被标成 `abandoned` 后 `activeQueue` 就不列了，这正是事故里“队列是空的”的来源。条目也覆盖不到入队之前的关闭提交阶段。
5. 让合入进程脱离调用者（setsid、守护进程）活下来：否决。调用者再也拿不到退出码和输出（项目要求直接读退出码），而且 canon 进程会在会话结束后继续占着 floor 和队列。也不是负责人要的：负责人要的是被杀掉时能发现。
6. 只看 git 痕迹（分支上有关闭提交但 main 上没有）：否决。只覆盖 `--finish` 且已提交关闭提交之后；没有进程信息，分不清“正在跑”和“被杀”。

## 决定

- **记录**：`canon work land` 认领续期成功后、做任何慢事（关闭提交、入队）之前，记一条 `land.start`，内容有 `pid`、`pid_start`（`selfProcess()`）和 worktree。读不到进程表时 pid 记为空，之后只会显示“不确定”。
- **终结**：`land.ok`、`land.refuse`、`land.killed`、`land.lost` 以及下面的 `land.interrupt` 是终结事件。一个 `land.start` 之后、同一 worktree 的下一条 `land.start` 之前，出现同一个变更（或同一个 worktree）的终结事件，这次合入就结束了；一起测时领头替成员记的 `land.ok` 按变更匹配。入队前收到 SIGTERM/SIGINT 时，处理函数补记 `land.killed`，免得被当成被杀掉。实际顺序：从 `land.start` 到入队之间（关闭提交，包括 pre-commit 钩子，和入队）都是同步的，所以这段时间里的 SIGTERM 要等入队做完才会被处理，那时 `land.killed` 在“有条目”的分支里记；入队前的分支也记，是为了以后有人在入队前加了 await 规则仍然成立。
- **判定**：每个 worktree 只看最近一条 `land.start`（更早的在下一次合入开始时已经被处理，见下）。没有终结事件时：进程不在（`isGone`）→ 被杀掉；进程还在 → 在跑；读不到进程表或没记下进程 → 不确定。worktree 目录已经不在的不报（已清理）。卡住但进程还活着的合入一直是 `running`，canon 不替人判断它是不是卡死了。
- **已到 main 的不撤回**：进程不在、但这个合入者在队列里有过条目、分支最新提交已经是 main 的祖先（在 `moveMain` 之后、记 `land.ok` 之前被杀）时，合入已经发生：`status` 标 `landed`；下一次 `land` 把条目标 `landed`、补记 `land.ok`（`recovered: true`，没有 `base`、`diff`）并结束，不撤回关闭提交。选 `land.ok` 而不是带标记的 `land.interrupt`：统计的合入数、红 main 的修复判定（`fixLandedIn`）和变更的合入记录（`earlierLandings`）只认 `land.ok`；它们都把缺 `base` 或 `diff` 的 `land.ok` 当成“不知道”，不会算错。
- **报告**：
  - `canon work status`（含 `--json`）新增 “Landings not finished” 一节：在跑的显示 `running`，被杀掉的显示 `interrupted`，写明 pid、开始时间、没有结果事件，并点出留下的东西：这个 pid 的队列条目、关闭提交在分支上、rebase 做到一半；最后一行是下一步命令。队列里进程已不在的条目也标上 `(lander process gone)`。
  - 同一个 worktree 的下一次 `canon work land`：在做任何检查之前报出上一次被杀掉、清理并记 `land.interrupt`（引用那条 `land.start` 的编号），之后正常继续。清理：队列条目标 `abandoned`（`lander process gone`）；HEAD 恰好是这个变更的关闭提交时撤回它（和 BR-2099 的信号处理一样，BR-2018）；rebase 做到一半时只写出 `git rebase --abort`，不替人执行，因为那可能是人在被杀之后自己开始的 rebase，撤销会丢他的冲突解决。
  - `canon work after-land <C-n>` 找不到这个变更的合入时，如果它有被杀掉或还在跑的合入，说出来而不是只说“没有合入跑过 after_land”。
  - `canon brief` 在被杀掉合入的 worktree 里多一行同样的话。

## 后果

- 事故再发生时，协调者在 `canon work status` 里立刻看到 `interrupted`，下一个 `land` 把现场收拾好，不需要人去翻事件表。
- 已知限制：进程在写下 `land.start` 之前（启动到认领续期之间，约几十毫秒）被杀掉没有任何记录，只有这一小段发现不了。floor 的子进程在 `kill -9` 之后成为孤儿继续跑，canon 没有记下它的 pid，只能在报告里提醒，不能替人停掉；这不属于这次的范围，另记 issue。
- 一个已清理的 worktree 不再被报；change 没被清理时，被杀掉的报告一直在，直到下一次合入或 `canon work clean`。
- 不改库表；旧 canon 写的事件没有 `land.start`，不会被报。
- 这个决定同时是 BR-2099 的补充：SIGKILL 拦不住，所以靠记录加探测发现，而不是靠处理函数。
