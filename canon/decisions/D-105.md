## 背景

D-89 定了发版发布 `refs/canon/accepted` 指向的提交、没有验收过的提交时拒绝；验收命令已落地（BR-2462）。D-61 原来让 `canon release ship` 取开始时 main 的提交作为 `shipped_at`，发布条件在那个提交上评估一次，合入时再在「合入的树」上重算一遍（BR-2335），防止排队期间条件失效。D-61 也承认过一个洞：手写 `shipped_at` 只要伪造一条协调库事件就能过合入检查。规则「已通过」的判定除了树还读活的 `refs/canon/green` 和报告记录（src/work/execution/state.ts）。

## 方案

1. `shipped_at` 改取 `refs/canon/accepted` 指向的提交，条件仍在它上面评估一次；合入时不重算条件，改查恒定或便宜的事（内容见 BR-2335，新增的是验收祖先一项）：采用。新增的检查同时堵上手写 `shipped_at` 的洞：还得伪造 ref 移动和验收事件。
   - 来源：src/work/execution/state.ts “With floor_timing after, a record counts only once refs/canon/green, the last commit”
2. 合入时在 `shipped_at` 的冻结树上重算条件：否决。`executionStates` 读活的 `refs/canon/green`：之后规则行为改了、change 文件在 green 顶端被更新，同一棵冻结树重算会从已通过翻成待重新执行，发版合入被误拒、永不收敛——重新引入 D-89 要消灭的问题。
3. 照旧在合入的树上重算：否决。验收之后 main 又合入的变更可能让 R-n 的某条规则待重新执行，而被发布的内容是 accepted 快照，没问题也被拒。
4. 要求发版时 `refs/canon/accepted` 等于 main 当前提交：否决。D-89 明说发版发已验收的提交而不是 main 的最新提交；强制相等等于逼负责人每次先验收再立刻发版。

## 决定

`canon release ship` 的提交来源、拒绝和输出见 BR-2334（含 R-n 在 main 上改过时的拒绝——chore 改的是 main 顶端的副本，必须仍是验收看到的那份——和落后提示）；合入检查见 BR-2335。

## 后果

- `release/<R-n>` tag 打在 accepted 提交上；BR-2462 的后代比较并交换保证它在 main 历史里。tag 指向的提交里 R-n 还是 `active`（shipped 状态在之后的合入里才进 main），这一点和原来一样。
- 浅克隆解析不出 `shipped_at` 或 `refs/canon/accepted` 时按 BR-2335 列为问题拒绝合入。
