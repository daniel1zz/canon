## 背景

#161：`canon work land` 在调用它的进程里从头跑到尾。调用的工具超时、宿主在 60 分钟时杀掉后台命令、会话被关，合入就跟着被杀。排队位置会保留（D-75），被杀掉的合入也能被发现（D-58），但要有人发现并重来，正在跑的 floor 也白跑了。队列忙时等 35 到 79 分钟是常事；zhushenkongjian 项目一天记到 32 次 `land.killed`，工人改用 `nohup` 之后变成 0 次。

D-58 当时否决了“让合入进程脱离调用者”，理由是调用者拿不到退出码和输出，而且合入会在会话结束后继续占着 floor 和队列。负责人 2026-11-09 定了（canon human #11，“只脱离（推荐）”）：调用的人按 Ctrl-C 只是不再跟着看，合入在后台继续。

本机实测（2026-11-09，Bun）：用 `detached: true` 启动的子进程自成进程组；父进程收到 SIGINT、SIGHUP 退出后，子进程照样跑完。canon 已经这样运行后台的 code review 等待进程。

## 方案

1. 不改，由调用者自己用 `nohup` 或类似办法：否决。每个调用者都要知道这件事，忘了就丢一次合入；实测一天 32 次被杀就是这样来的。
   - 来源：canon/decisions/D-75.md “其余是工人自己的工具超时（0 到 30 分钟）”
2. 后台合入，前台立即返回，之后用另一个命令查结果：否决。项目说明和 skill 都要求直接读 `canon work land` 的退出码；改成立即返回，所有调用者都要改成先启动再轮询，合入是否成功也不再由这条命令的退出码说出来。
   - 来源：src/work/land/guide.ts “read its exit code directly, not through a pipe”
3. 合入在独立的后台进程里运行（自己的进程组，输出写到日志），前台进程跟着打印输出，合入结束时用同样的退出码返回；前台被杀、断开或按 Ctrl-C 只是不再跟着看：采用。调用者照旧直接读退出码；D-58 否决方案 5 的第一个理由（拿不到退出码和输出）因为有前台跟随而不成立；第二个理由（会话结束后还占着队列）正是负责人要的行为，并且有明确的停止命令，`canon work status` 照常把它列为 `running`。
   - 来源：canon/decisions/D-58.md “让合入进程脱离调用者（setsid、守护进程）活下来：否决”
   - 来源：src/knowledge/review/code-review-batch.ts “its own process group and its own log”
4. 前台跟随，但 Ctrl-C 也停掉后台合入：否决，负责人选了只脱离（canon human #11）。停止另有明确命令。
5. 常驻的合入服务，所有合入交给它排队执行：否决。要安装并保持一个长期运行的服务，出了问题还要另一套发现办法；独立进程加事件表里的 `land.start`（D-58）已经够用。
   - 来源：canon/decisions/D-58.md “不加表、不加列；每个出口本来就写终结事件”

## 决定

用方案 3：

- **后台合入**：`canon work land` 启动一个独立的后台合入进程（自己的进程组，标准输入不接），它的标准输出和标准错误写到协调数据库旁 `logs/` 下这次合入自己的目录里（`out`、`err`），结束时把退出码写进同一目录的 `exit`。后台合入进程就是 `canon work land` 本身，带环境变量 `CANON_LAND_RUN`（值是前台进程号和那个目录）；只有父进程正是那个前台进程时才是后台合入。不能靠把变量从环境里去掉：实测 Bun 不带 `env` 启动子进程时用的是进程启动时的环境，floor 和 hook 照样会继承它，所以按父进程判断，它们里面再运行的 `canon work land` 照常作为前台。`land.start` 记的进程是后台合入进程，另记 `run`（那个目录）。
- **跟随**：前台进程把后台合入的输出按原来的流（标准输出、标准错误）打印出来，合入结束时以它的退出码退出。后台合入进程没写 `exit` 就不在了（例如被 `kill -9`），前台说明这一点并以 75 退出，再运行 `canon work land` 时按 BR-2309 报出并清理。
- **脱离**：前台收到 SIGINT、SIGTERM 或 SIGHUP 时，只说合入仍在后台继续、怎么接上、怎么停止，以 75 退出；后台合入不受影响。
- **接上**：在同一个 worktree 再运行 `canon work land`，最近一次合入还在后台运行 → 不新开合入，从头打印它的输出并跟随，规则同上。最近一次后台合入已经结束、但它的结果没有被任何前台打印到结尾 → 打印它的输出，以它的退出码退出，不新开合入；之后再运行才是新的合入。
- **停止**：`canon work land --stop` 向这个 worktree 正在运行的合入进程发 SIGTERM，按 BR-2099 让出轮次并撤回关闭提交，等它结束后打印它的输出、以 0 退出；没有正在运行的合入时以 3 退出。
- `--timeout`、`--finish`、`--as` 原样交给后台合入。

## 后果

- 调用者的工具超时、会话结束不再杀掉合入；`land.killed` 只剩明确停止和真正的信号。
- 合入在会话结束后可能还在跑，占着自己的排队位置直到结束；`canon work status` 列为 `running`，`canon work land --stop` 结束它。
- 每次合入多一个前台进程和一个日志目录；日志不自动清理，和 floor 的日志一样。
- 信号处理（BR-2099）现在作用在后台合入进程上，测试直接用 `CANON_LAND_RUN` 启动后台合入进程来验证它。
- 如果以后要让前台立即返回（方案 2），可以加一个选项，不改本决定的默认行为。
