## 背景

D-128 让主会话定设计，派发时记下设计负责人（BR-2497），之后只有它能收回派发（BR-2500）。2026-11-27 zhushenkongjian 从笔记本迁到 Mac Studio：65 个还没结束的派发的设计负责人是笔记本上的主会话 `agent:9e301322`，它已经不存在，新主会话收不回也重派不了，只能直接改协调数据库解锁（C-716 的「为什么」）。主会话只要换了身份（会话结束后开新会话）就会这样，不只是换机器。

## 方案

1. 新命令 `canon work adopt`，按旧设计负责人名下认领记下的会话进程判断它是否结束，判断不了时由运行者带 `--gone` 声明：采用。和 `canon work take --stopped` 同一个做法：canon 看得到的进程以 canon 为准，看不到的由主会话负责声明并记进事件，事后可查。
   - 来源：canon/rules/work/delegation/BR-2500.md “认领记下的会话进程已经不在 → 接手”
2. 判断不了时要负责人的原话（`--relayed`）才接管：否决。旧会话结束是事实判断，不是方向或留给人的决定（P7）；要人确认会让开发卡在人身上，而这正是负责人要避免的（2026-11-27「全力推进开发」）。
   - 来源：canon/product.md “方向和明确留给人的问题走 `canon human`，其余都不等人”
3. 让 `canon work take` 直接接受任何主会话收回：否决。去掉了设计负责人这个身份，两个都活着的主会话会互相抢对方派出去的活，违反 D-128 让设计由一个主会话定的初衷。
   - 来源：canon/decisions/D-128.md “设计由主会话定：worker 在派发时固定的设计版本内执行”
4. canon 自动把结束了的设计负责人的派发转给下一个主会话：否决。哪个会话是“下一个”只有主 agent 知道（可能同时有几个主会话），自动转容易转错；命令加上 `canon work take` 被拒时的提示已经够找到它。
   - 来源：canon/product.md “判断交给主 agent，不靠不停地加拦截”

## 决定

采用方案 1：BR-2646；议程提示接管见 BR-2647，加上安静多久的条件是为了不把同时开着的另一个主会话当成已经结束；BR-2500 被拒时的提示指向它，并写明派发之后只有 BR-2646 能改设计负责人。

## 后果

- 换机器或换会话后，新主会话运行一次 `canon work adopt --from <旧会话> --gone`，再照常 `canon work take`、`canon work delegate`，不用再改数据库。
- `--gone` 是运行者的声明：旧会话其实还活着（例如在另一台机器上）却被接管，旧会话之后的 `canon work take` 会因为不再是设计负责人被拒，信息指向 `canon work adopt`，它可以再接管回来；事件表里有每次接管的 `gone: asserted`，可以追查。
- 持久数据：接管只改派发记录的 `owner` 一列，每个变更记一条 `delegation.adopt` 事件（从谁到谁、怎么判断的），不迁移、不删任何数据；接管错了，被接管的一方再运行一次 `canon work adopt` 接回来，事件表能还原每一步。
- 认领里记下的进程来自另一台机器时，本机碰巧同号的进程会被当成“还在”而拒绝接管：仓库挪过之后，`canon brief` 改写路径时一并清掉这些进程（BR-2649）；没挪位置、只是换了会话时不受影响。
