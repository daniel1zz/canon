## 背景

负责人 2026-11-19 定的方向：「不能因为模型会错就不相信模型」「应该加强最后验收，模型也是有纠错能力的」，关键节点才重、轻量节点就轻，harness 要能按模型种类组装，并跟着模型进化。负责人在会话里从四个方案中选了「D 为主加 A 的关键程度」（见方案 1 到 4）。

本仓库 2026-11-02 到 11-19 的实测（协调数据库 `.git/canon/state.db` 和 `.git/canon/logs/`）：

- 646 次合入，最近一周每天约 24 次。
- 合入前的 `canon work test`（最近一周 258 次）：耗时中位数 8.6 分钟，90% 在 20.8 分钟以内，平均挑 68 个测试文件，6 次超时；259 次里 16 次报失败，这是模型在过程中自我纠错用的信号。
- 合入后的规则评审：168 次里 133 次因为太大被拆开，拆开的那些每次提示合计中位数约 898 KB（平均 7.5 次调用），最大 52 MB。C-602 只改了 BR-2497 一条规则，评审发了 874 KB；BR-2497 加上它引用的文档约 44 KB，引用它的文档约 53 KB。
- 评审意见：「矛盾」100 条修复、4 条误报；「不可测」10 条修复、5 条误报，其中 4 条是测试其实已经存在（#265）；「复述」30 条修复、6 条误报。
- 合入被拒：评审（合入时让模型判断规则改动是不是只改措辞）137 次，冲突 38，证据（执行的规则没有以它命名、报告最新的测试）27，`canon check` 22。
- 合入后 main 变红 33 次。11 月 4 日一天 15 次；11 月 8 日以后 11 次里 8 次没人修、下一轮自己就过了（BR-2392、BR-2044、BR-2307 这类受负载影响的计时测试），要修 main 的只有 3 次。
- `canon accept` 只成功过 1 次（11-14），之后 main 又走了 455 个提交；现在 707 条可疑引用挡着它。验收要求整个仓库没有遗留问题，而每次合入都会产生新的遗留问题，所以它跑不完。最后验收名义上有，实际上没在运转，真正把关的是过程中的强制步骤。
- canon 不记录会话用的是哪个模型。Claude Code 的 SessionStart hook 输入里可能带模型名（不保证每次都有），`/model` 切换后有 PostModelSwitch hook；Codex 每个 hook 的输入都带当前模型。

## 方案

1. **合入就是验收，按关键程度调强度**（A）：去掉过程中的强制步骤，合入时按 canon 算出的关键程度决定验收多强。单独采用时否决：真正有破坏性的改动常常看起来很小，会被判成轻节点；而合入时由模型判断的环节准确率不高（措辞判断拒了 137 次），会误拒重要的改动。它的「关键程度」部分并入方案 4 采用。
   - 来源：canon/config.yaml “改动不导入它、也不碰它点名的规则时照样能弄坏它”
2. **先合入，在 main 上分批验收**（B）：否决。每次合入出错概率 6% 时，10 个一批约 46% 的批次失败，验收点几乎不前进；向前修要找原作者，而会话会结束。
   - 来源：canon/decisions/D-89.md “负责人随时运行；发版前必须有”
3. **模型开工时声明验证计划，canon 核对**（C）：否决。声明会变成套话；开工多一步，和「默认轻」相反；核对「声明的证据存在而且新鲜」就是现在的证据检查换了个名字。
   - 来源：canon/rules/work/execution/BR-2241.md “要执行的规则每条都要有证据”
4. **出错自动撤回、验收按规则逐条前进，加上方案 1 的关键程度**（D 加 A）：采用。合入只做完整性检查和改动直接相关的机械检查；main 的后台测试失败时，先不改代码重跑，过了的记为不稳定测试，真坏了就定位到那次合入、撤回、把变更连同失败退回给它的分支，由模型纠正后再合；验收是每条规则的属性，不再要求整个仓库清零。关键程度由 canon 按事实算，模型只能调高；关键改动合入前跑全量测试，并由独立的 agent 从真实入口验收；普通改动按比例抽查。外部也有同样的教训：只靠文字让模型自己决定省哪些步骤，模型会把它当成省步骤的许可。
   - 来源：https://github.com/obra/superpowers/issues/1120 “permission to skip steps”
5. **按模型等级预先分好权限**：否决。能力强不等于守规矩；手写的等级表每出一个新模型就要改；同一个模型在不同宿主里能用的东西也不同。改为先记录模型和宿主，用实测的通过率决定抽查比例；两周数据看不出差别就不做分档。
   - 来源：canon/decisions/D-89.md “核实命令本身也会错”

## 决定

采用方案 4，分步计划见 C-603。本决定在计划的 C 步（撤回）和 E 步（去掉强制步骤）落地时、随它们改写的规则一起接受；在那之前它是提议中的方向，现有的证据检查、措辞判断、向前修和整仓验收照旧有效（编号见后果）。各步的行为写在它们各自的规则里：

- 记录每个会话的模型和宿主；
- 合入后的规则评审只看改动的文档和直接相关的文档（顺带解决 #265）；
- main 的后台测试失败时识别不稳定测试，真坏了就定位并撤回那次合入、退回给变更分支；
- 验收按规则逐条记录，验收点自动前进到「之后改过的规则都已验收」的最新提交，取代整仓清零的验收；
- 去掉过程中的强制步骤（证据检查、合入时的措辞判断），合入只跑改动直接相关的测试；接上关键程度：关键改动合入前全量测试加独立验收，普通改动抽查；
- 有了两周以上的模型数据，再决定是否按模型调抽查比例、组装不同的说明。

不随任何因素变的：规则本身；不可逆、动共享东西的操作要问人；认领、冲突、并发这些完整性检查。

## 后果

- 合入变快：普通改动不再等 8 到 20 分钟的合入前测试和措辞判断；代价是 main 上可能短时间有坏提交，靠自动撤回限制在一个后台测试批次以内（`floor_max_untested`、`floor_quiet_minutes`）。撤回之前已经基于坏提交开工的会话，要在它们的分支上跟着 main 重新 rebase。
- 评审花费预计降到现在的十分之一左右；看不到整个领域后，跨领域的矛盾靠验收时的相关文档挑选（D-90）补，漏掉的会在之后的评审或验收里出现。
- 验收点会真正前进，发版（`canon release ship`）不再被整仓的遗留问题卡住。
- 关键程度的算法一开始一定不准；按「漏掉了什么」（被撤回的合入、之后被修的变更）调整，这需要先把这些记下来。
- 架构总览（canon/architecture.md）里合入流水线的执行记录、措辞判断和后台 floor 的向前修，由 C、E 步在接受本决定时一起改写。
- 在 C、E 步落地前照旧有效的：BR-2241（证据）、BR-2239 和 BR-2243（措辞判断）、D-31 的向前修、D-89 和 D-104 的整仓验收。
- 要修改的决策：D-89（验收的定义、措辞判断）、D-104（验收只对 main 的当前提交）、D-32 中「执行的规则要有证据」的部分、D-31 中「main 失败时向前修」的部分；具体由各步的变更在规则里改，并在这里的状态里引用。
