## 背景

负责人 2026-11-21 问：要不要把写文档改成用 CLI 写入，好做 JSON Schema 校验——现在 front matter 写入时没有校验。接着指出这和 #293 是同一个问题（会话必须做的决定被设计成可选字段，所以会被忘掉），而且不止变更，所有文档类型都一样。

事实：

- #293：`C-1068` 要负责人点头，要求只写在文字里，会话没问就完成了。D-158 加了 `owner_gate`，但它是可选字段，会话忘了写时照样不拦。
- 变更的 `advances` 也是可选的，合入只给一行提示；canon 自己的 `C-669` 合入时就收到这行提示。
- 只能手写、没有命令参数的判断类字段：规则 `business`、决策 `amends` 和 `revised_because`、变更 `advances`；`revised_because` 写错只是提示。`canon quality new` 已经在分配编号前要求 `--aspect`、`--judge`、`--covers`。
- 近 7 天被拒的合入：zhushenkongjian 427 次里只有 2 次是 front matter 格式错（`file-invalid`），canon 50 次里 0 次；多的是跨文档的问题（`ref-dangling` 142、`rule-business-unmapped` 136、`release-dropped` 128），逐个文件的格式校验看不到这些。
- 项目在 `types.<类型>.fields` 声明的字段只查非空（BR-2054），可以和内置字段同名：声明 `business` 会让 `rule new` 写出空值；质量标准的同名字段会盖掉参数给的值。

设计前让一个不看推荐的子 agent 挑战了几个方案，它指出：

- 问题的重点不是“写入不校验”（数据不支持），而是每个判断该在哪一步表态；
- 只写下字段不等于有人照做（`owner_gate` 要配合 D-158 的拦截）；
- 复制文件、`canon rule apply`、分支开始后才加的字段，都会绕过新建命令；
- JSON Schema 的正则会回溯，违反 D-153，也表达不了正文项的模板。

负责人选了“声明 + 按步表态”，并选定变更、规则、决策、版本的判断字段都要在新建时表态。

## 方案

1. 类型声明字段的格式和表态的步骤，那一步的命令当场要求；`canon doc set` 改值；`canon check` 校验格式；合入拒绝缺字段的新文档：采用。
   - 会话在建文档的那一刻就得想这件事，答案是“没有”也要写 `none: <理由>`。
   - 写进 front matter 的是命令写的值，符合 D-144 “canon 命令写的放 front matter”；这里把它扩到“会话交给命令的判断”。
   - 格式沿用 BR-2546 的槽位类型和 RE2 正则（D-153），不另立一套。
   - 合入检查兜住绕过命令的写法；旧文档不追溯。
   - 来源：src/knowledge/quality/commands.ts “Who judges it: test, agent or owner”
2. 所有写入（front matter 和正文）都走 CLI，hook 拒绝直接改文件：否决。
   - hook 只管编辑工具，shell 和别的进程照样能改；rebase 冲突只能手改；正文走 CLI 只是把同样的校验提前，挡不住跨文档的问题。
3. 模板放占位，合入时拒绝没填的：否决。
   - 判断推到最后才做：`owner_gate` 到合入时才想起来，负责人的批准已经来不及挡什么。
4. 用 JSON Schema 文件做声明：否决。
   - 它的 `pattern` 是会回溯的正则，违反 D-153；表达不了正文项的模板和跨文档引用；报错不针对类型和字段。
   - 来源：canon/rules/knowledge/documents/items/BR-2547.md “项目声明的正则不会让 `canon check`、`canon show` 这些读文档的命令卡住”

## 决定

- BR-2619：类型在 `fields` 下声明字段的格式和 `due: create`。
- BR-2620：新建命令当场要求，缺了不分配编号。
- BR-2621：`canon doc set` 改值。
- BR-2622：`canon check` 校验格式。
- BR-2623：内置类型的表态字段。
- BR-2624：合入拒绝缺字段的新文档。

## 后果

- 新建文档的命令都多了参数；会话少给一个就退出码 2，信息写明怎么补。
- 会话可能写 `none: n/a` 这类敷衍的理由：canon 判断不了，评审能看到。
- main 上给一种类型加了新建时表态的字段，正在做的分支新增的文档要补一条 `canon doc set` 才能合入。
- 现在只有“新建时”这一步；以后有字段只能在开工或合入时才知道，再给 `due` 加取值。
- 不导出 JSON Schema：编辑器读不了 `.md` 里的 front matter 校验，需要时再加。
- 实现分几步：声明和校验（BR-2619、BR-2621、BR-2622），新建命令和内置声明（BR-2620、BR-2623），合入检查（BR-2624）。
