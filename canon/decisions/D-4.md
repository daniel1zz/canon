## 背景

BR-2022 规定每个退出码只有一种含义，并且穷举了退出码 1 的情形（都是结果检查的拒绝）。issue #3 实测：缺参数（`canon show`）、未知命令（`canon bogus`）、在 git 仓库外执行，都退出 1。原因有两个：命令行库 citty 遇到用法错误一律 `exit 1`；canon 把所有 `io` 错误（git 失败、打不开协调数据库、不在仓库里）也映射成 1。agent 看到 1 会以为是检查拒绝，去改代码，而真正的问题是用法或环境。负责人让 agent 自行决定（2026-11-03，“一直往下做”）。

## 方案

1. 环境错误也归入 1，在 BR-2022 里写明。否决：1 就不再只表示“被检查拒绝”，agent 无法据此区分要改代码还是要修环境，C-9 的统计也会混进环境故障。
2. 环境错误归入 2。否决：2 表示“调用方写错了”，重试同一条命令没有意义；环境错误往往修好环境后原样重试就行，两者处理方式不同。
3. 用法错误归入 2；环境错误（不在 git 仓库里、git 命令失败、协调数据库打不开、读不到 main 上的文档）用一个新的退出码 4；canon 自身未处理的异常（bug）用 70（`EX_SOFTWARE`）。采用。
4. 每种环境错误各用一个退出码。否决：agent 对这些错误的处理都一样（报告、修环境、重试），分开只会增加要记的东西。

## 决定

- 2：用法错误（包括 citty 报的缺参数、未知命令、不带子命令）、输入无效、配置写错。
- 4：环境错误。消息写明是哪一步、底层命令的输出。
- 70：canon 自身的 bug（未处理的异常），打印调用栈。
- 1 仍然只表示 BR-2022 列出的检查拒绝；新 worktree 的 setup 失败是其中一种，内部改用专门的错误类别，不再借用 `io`。

## 后果

- BR-2022、CLAUDE.md、cli 领域 README 的退出码说明同步修改。
- 依赖“git 失败退出 1”的调用方要改成看 4；目前只有 canon 自己的测试。
