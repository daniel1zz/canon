## 背景

`canon work test` 选测试文件靠三条：测试自己被改、测试的相对导入（直接或间接）到达改过的文件、测试名点名碰过的规则（BR-2157、D-23）。启动 CLI（`Bun.spawn(["bun", MAIN, "work", "status"])`）来测改动代码的测试不导入被改的模块，三条都碰不到它。实际红过两次 main：C-309 改了 `canon work status` 的输出，`src/work/session/brief.test.ts` 里的 BR-2192 用例没被选出，main 一直红到 C-313。完整测试集要更少地运行（另一个 agent 在做分批），合入前的选择必须更准。

2026-11-04 在 C-317 的 worktree 里测量（基线提交 `020bfd2`，三个文件并行运行，机器上还有别的会话在跑，耗时只作数量级）：

- 85 个测试文件，其中 54 个启动 CLI（都写着 `join(import.meta.dir, …, "main.ts")` 这样只由字符串写成的入口路径）；54 个全都在字符串里点名了至少一条已注册的命令。
- 这 54 个文件各自用 `sh scripts/test.sh <file>` 运行：全部通过；每个 2 到 147 秒，中位数 19 秒，合计 1832 秒（三个并行，约 12 分钟）。所以“全部选出”每次要多付约 30 分钟的 CPU 时间，不可取；只选点名了被改命令的才划算。
- 命令表：`src/cli/tree.ts` 只导入各领域的 `commands.ts`，每个文件用 `entry("名字", 序号, 命令, "分组")` 注册命令（C-132、D-15）；34 条命令，分布在 17 个模块里。命令表导入全部模块，所以从入口文件顺着导入走会到达一切。
- 命令模块之间有真实的导入：`src/work/session/commands.ts` 导入 `src/install/commands.ts` 的 `noticeUpdates`。

## 方案

1. 静态，从代码推出（采用）：测试里找由字符串写成的入口路径；入口文件导入的源码里找 `entry(...)` 注册，得到“命令词 → 注册它的模块”；测试把某条命令的词写成字符串（`"work", "status"` 连着，或 `"work status --json"` 写在一个字符串里；顶层单词命令只在作为参数时才算：两侧是 `(`、`[`、`,` 和 `,`、`)`、`]`；JSON/YAML 文本里的 `"verdict"` 和 `"brief --json"` 这样的长字符串开头都不算），就当作它导入了这条命令的模块；模块或它导入的文件改过就选出，理由 `drives canon work status (src/work/session/commands.ts changed)`。测试还依赖入口文件和它导入的文件（`runs the CLI (…)`），但不依赖没点名的命令的模块：从命令表（一个不注册命令的文件）到命令模块的边不走。不用手写任何清单；新命令、改名、换模块都自动跟上。
   - 来源：src/cli/tree.ts “every domain defines its commands in commands.ts in its own directory”
   - 代价：命令词不是字符串字面量时（`canon(root, ...args)` 里拼出来的）看不到；这样的测试只在入口文件一侧的改动时选出。测量里 54 个文件全都点名了命令，没有这种情况。单词命令（`"check"`）只在作为参数时才算（C-319 审查：`brief.test.ts` 的评审配置字符串里有 `{"verdict":"ok"}`，曾因此多选）；写在 `["a","verdict"]` 这样的 JSON 数组文本里仍会多选，多选只多花时间，不会漏掉；写成 `"brief --json"` 单词加参数的长字符串则看不到，和拼出来的命令词一样只靠入口文件一侧的改动选出。
2. 配置清单（`cli_tests` 之类，像 `always_tests`）：否决。每新增一个启动 CLI 的测试都要记得登记，漏了就和这次事故一样悄悄不选；54 个文件、每次改命令还要判断归属，清单必然过时。`always_tests` 只适合少数读遍 src/ 的测试（C-267）。
3. 改动在 `src/cli/main.ts` 可达的任何源码里，就选出同领域目录下所有启动 CLI 的测试：否决。可达就是几乎所有源码（命令表导入一切），等于每次选出全部 54 个（约 30 分钟 CPU），违背“不要每次都退回整个测试集”；只按目录划分又会漏掉别的目录里驱动这条命令的测试（`src/cli/backlog.test.ts` 驱动 `canon brief`，代码在 `src/work/session/`）。
4. 每个启动 CLI 的测试都选出（`--all` 的子集）：否决，理由同 3。
5. 运行时记录：每个测试跑一遍，记下它启动的 CLI 读了哪些文件，下次按记录选：否决。要先把 54 个文件跑一遍并长期维护一份记录，记录是缓存，会过时；静态读法已经足够准。

## 决定

采用方案 1。实现在 src/work/verify/cli-tests.ts（已搬到 scripts/select-tests/cli-tests.ts，D-64）（读测试和命令表）和 `src/work/verify/verify.ts` 的 `selectTests`；规则是原有的 BR-2157（原地改，加条件和例子）。

- 入口文件：测试里 `join(…)` / `resolve(import.meta.dir, …)` 且参数全是字符串字面量，得到的路径是个源码文件，并且它导入的源码里有 `entry(...)` 注册，就是 CLI 入口。读注册时不读注释。
- 命令：`entry("status", 50, status, "work")` 是 `work status`；没有分组时是顶层命令。子命令（`rule new`）归给注册它的顶层命令的模块。
- 到达：从入口文件和每个被点名命令的模块各做一次广度优先的导入遍历；不从“非命令模块”进入命令模块（那是命令表）。改过的文件被到达就记一条理由，带到达它的路径。
- 不改合入的 floor、不改 `always_tests`、不改 `--all`。

## 后果

- 改一个常用命令的模块（例如 `src/work/session/commands.ts`）会选出 19 个启动 CLI 的测试文件（C-317 里改一行复现，2026-11-04），比以前多，但这正是 C-309 漏掉的那类测试；改一个小命令只选出点名它的几个文件。
- 命令词来自字面量，所以启动 CLI 又用拼出来的命令词的测试看不到；新写这样的测试要么写出命令词，要么加进 `always_tests`。这条限制记在 BR-2157 的规则文字里。
- 约定依赖：命令用 `entry(...)` 注册（D-15）、测试用只含字符串的路径指向入口文件。其中一个变了，这种测试就退回只靠“入口文件一侧改动”选出；`verify.test.ts` 里的例子会在命令表写法变化时失败。
- 识别不到就失败（C-319 审查）：测试用 `join(import.meta.dir, …)` 指向 `main.ts` 却找不到文件，或入口文件和它导入的文件里没有注册命令时，`canon work test` 以退出码 4 失败并写明原因；以前这时悄悄退回只看导入的选法，正是让 main 变红的那类漏选。输出里有一行 `CLI tests: N file(s) spawn the CLI, M command(s) known`，`verify.test.ts` 里有一条对本仓库真实目录的测试：至少 50 个启动 CLI 的测试、30 条命令，重构 `entry(...)` 或入口路径会让它失败。
- 命令模块之间的导入（`src/work/session/commands.ts` 导入 `src/install/commands.ts`）有测试覆盖。

## 补充（2026-11-05，#117）：运行时读的数据文件

和 CLI 一样，运行时读文件的测试也不导入被读的文件：`src/install/install.ts` 的 `skillsSource` 读 `.claude/skills`，只改 `.claude/skills/canon-*/SKILL.md` 时 install、init、update、uninstall 的测试一个都选不出。

测量（2026-11-05，C-328 的 worktree）：`src/` 里用 `import.meta.dir` 加字符串字面量拼路径的非测试文件只有 `install.ts`（读 `.claude/skills`）和 `watch.ts`（拼 `main.ts`，是代码文件，已由导入的读法覆盖）；其余读文件的 `readFileSync`、`readdirSync` 都以项目根目录起头（`join(root, ".claude", …)`、`join(root, "canon", "templates")`），读的是被测项目，测试里是临时目录，不是 canon 自己的文件。

- 方案 A（采用）：沿用本决定读测试入口路径的同一个函数，从源码读出这种路径；改过的非代码文件落在路径下，这个源码文件就算“读到了改动”，随后走原有的导入遍历和命令遍历，理由 `reads <路径> (… changed, via <模块>)`。从代码推出，不用清单。代价：只看得到由字符串拼出的路径；以项目根目录为起点的读、运行时拼出的路径看不到（目前没有读 canon 自己文件的这类代码）。改 `.claude/skills` 会选出约 36 个测试文件，因为 `brief`、`work start`、`work status` 经 `noticeUpdates` 真的读它；这是真实依赖，不是多选。
- 方案 B：源码文件里导出一个声明读取路径的常量，选择时读它：否决。要靠作者记得声明，漏了就悄悄不选，和 `always_tests` 清单是同一个问题；而 A 在测量里能可靠识别唯一的一处读取。
- 方案 C：把 `.claude/skills/**` 加进 `always_tests`：否决，那是手写清单，且会让每次改动都多跑这些测试。

实现在 src/work/verify/data-reads.ts（已搬到 scripts/select-tests/data-reads.ts，D-64） 和 `selectTests`；规则 BR-2157 原地加了条件和例子。
