id: D-54
title: 按真实使用中的频率和代价判断问题，极端情况记为已知限制，不为它加机制
status: proposed
---

## 背景

GitHub 上 115 个 issue 里有 65 个来自合入后的自动代码评审（`canon-review` 标签）。关于后台测试的一串 issue（#99、#101、#102、#106、#107、#108、#109）都是评审推演出来的事件交错，没有一个是真实使用中遇到的：协调数据库 `.git/canon/state.db` 的 `events` 表里 5 条 `floor.after_green`，没有一条带 `rerun: 1`，也就是这些交错的前提（补跑上一个提交的 `after_green`）一次都没发生过。修它们却让 `src/work/watch/watch.ts` 和 `stop.ts` 涨到约 630 行，BR-2270、BR-2285 里也多了一串例外。

2026-11-04 负责人的原话：

- “不要设想不存在的问题”
- “这个应该固化到canon的认知中，同时不要为极端情况下的问题付出很多努力导致架构复杂”

负责人选了“评审和分拣都改 (推荐)”：合入后的代码评审只报正常使用中会遇到的问题，每条写明谁在哪个正常操作里会遇到；分拣时，只在测试里强行构造出来的情形不算复现，除非会丢数据或是安全问题，否则以“真实使用中没见过”关闭，真的发生了再打开。

## 方案

1. 能在测试里构造出来的发现都修：否决。上面的数字说明，这样修的问题在真实使用里没出现过，代价却是几百行代码和规则里的例外；这些代码本身又成了评审的新目标，一个发现引出下一个（#99 之后的六个都在同一段停止进程的代码里）。
   - 来源：https://sre.google/sre-book/simplicity/ “every line of code changed or added to a project creates the potential for introducing new defects and bugs”
2. 按真实使用中出现的频率和出现时的代价判断一个问题，再和修它要加的复杂度比；极端情况（少见的事件交错、少见的平台配置、不是安全边界的恶意输入）记成已知限制，写在相关决策的“后果”或规则里一行，不为它加机制；会丢数据和安全问题例外，照修：采用。
   - 来源：https://martinfowler.com/bliki/Yagni.html “The code for the presumptive feature adds some complexity to the software, this complexity makes it harder to modify and debug that software, thus increasing the cost of other features.”
3. 只改分拣，评审照旧什么都报：否决。分拣能关掉构造出来的 issue，但每条仍要有人复现、写评论、关闭；评审不报，这些工作就不会产生。
4. 只改评审，分拣照旧把测试里构造出来的情形算复现：否决。评审是 AI 判断，仍会漏进构造出来的发现；分拣时按“测试里能构造就算复现”，它们照样会变成代码。

## 决定

采用方案 2，写进 canon 告诉 agent 怎么判断问题的每个地方：

- 合入后的代码评审（BR-2070）只报正常使用中会遇到的安全和并发问题，每条的出错情形写明谁在哪个正常操作里会遇到；少见的事件交错和极端配置不报，除非会丢数据或是安全问题。
- 分拣（canon-triage）：只在测试里靠屏障、预置状态或假程序强行做出来的情形不算复现；不丢数据、不是安全问题的，以 `not planned` 关闭，写明“真实使用中没见过，真的发生了再打开”。
- 设计（canon-design）和排查（canon-diagnose）：按每个情形在真实使用中多常见来衡量方案的复杂度，极端情况记成已知限制。
- `canon/product.md` 在“一个机制如果不支撑任何一条，就删掉”后面加一句：只为极端情况存在的机制也算不支撑。

## 后果

- 评审报得更少，会漏掉一些真实但少见的问题；它们真的发生时会有人遇到并提 issue，那时再修，有了真实的复现。
- 丢数据和安全问题不受这条限制，评审和分拣照旧对待。
- 后台测试（`src/work/watch/`）已经为构造出来的交错加的代码不在这里删，按负责人的安排在设计评审之后另做简化。
- 规则评审的提示没有要求列出每个边界情况，不改。
