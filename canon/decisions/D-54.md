id: D-54
title: 只修正常操作会引出的问题，需要不正常配置或动作的情形记为已知限制，不为它加机制
status: accepted
---

## 背景

GitHub 上 115 个 issue 里有 65 个来自合入后的自动代码评审（`canon-review` 标签）。关于后台测试的一串 issue（#99、#101、#102、#106、#107、#108、#109）都是评审推演出来的事件交错，没有一个是真实使用中遇到的：协调数据库 `.git/canon/state.db` 的 `events` 表（2026-11-04 查询）里有 6 条 `floor.after_green`（`select count(*) from events where kind='floor.after_green'`），带 `rerun: 1` 的 0 条（`json_extract(detail,'$.rerun')=1`），也就是这些交错的前提（补跑上一个提交的 `after_green`）一次都没发生过。样本范围：这些数字只来自本仓库这一个 clone（同一个库里 `sync.*` 事件也是 0 条），不代表其他项目里的 canon；出现真实复现就重新打开这条决策。修它们却让 `src/work/watch/watch.ts` 和 `stop.ts` 涨到约 630 行，BR-2270、BR-2285 里也多了一串例外。

2026-11-04 负责人的原话：

- “不要设想不存在的问题”
- “这个应该固化到canon的认知中，同时不要为极端情况下的问题付出很多努力导致架构复杂”

负责人选了“评审和分拣都改 (推荐)”：合入后的代码评审只报正常使用中会遇到的问题，每条写明谁在哪个正常操作里会遇到；分拣时，正常操作引不出的情形不算问题，除非会丢数据或是安全问题，否则关闭，真的发生了再打开。

独立评审（review-D53-D54-D55.md）判本决策“需要修订”，两点：例外清单漏掉 P4（“不丢工作、不互相覆盖、不弄坏 main”），“少见的交错让 `refs/canon/green` 指向没测过的提交”既不丢数据也不是安全边界，按原字面评审不报、分拣关闭；“构造出来的”判据对并发问题天然成立（“并发 bug 的测试几乎必然要用屏障”），而且“频率”和“正常操作”是两个标准，agent 无法判断该用哪一个。

## 方案

1. 能在测试里构造出来的发现都修：否决。上面的数字说明，这样修的问题在真实使用里没出现过，代价却是几百行代码和规则里的例外；这些代码本身又成了评审的新目标，一个发现引出下一个（#99 之后的六个都在同一段停止进程的代码里）。
   - 来源：https://sre.google/sre-book/simplicity/ “every line of code changed or added to a project creates the potential for introducing new defects and bugs”
2. 只用一条判据：这个情形是否由正常操作引出，再和修它要加的复杂度比；需要不正常的配置或动作才会出现的情形记成已知限制，写在相关决策的“后果”或规则里一行，不为它加机制；丢数据、安全问题和破坏 P1 到 P7 任一条承诺的例外，照修：采用。
   - 来源：https://martinfowler.com/bliki/Yagni.html “The code for the presumptive feature adds some complexity to the software, this complexity makes it harder to modify and debug that software, thus increasing the cost of other features.”
3. 只改分拣，评审照旧什么都报：否决。分拣能关掉构造出来的 issue，但每条仍要有人复现、写评论、关闭；评审不报，这些工作就不会产生。
4. 只改评审，分拣照旧把测试里构造出来的情形算复现：否决。评审是 AI 判断，仍会漏进构造出来的发现；分拣时按“测试里能构造就算复现”，它们照样会变成代码。

## 决定

采用方案 2，写进 canon 告诉 agent 怎么判断问题的每个地方：

**判据（一条）**：这个情形是否由正常操作引出。对 canon，多个会话同时工作、同时合入就是正常使用。测试怎么重现它（屏障、预置状态、假程序）不是判据：两次正常合入之间的竞态，用屏障强制出来，也是真实的。

**已知限制**：需要不正常的配置或动作才会出现的情形，例如用户给 `ps` 套的包装脚本、没人用的非默认 git 后端、在某一步中间对某个特定进程发 SIGKILL、不是安全边界的恶意输入。

**例外**：丢数据、安全问题，或破坏 `canon/product.md` 里 P1 到 P7 任一条承诺。例如 P4（不互相覆盖、不弄坏 main）：少见的交错让一个没测过的提交被标成已通过，就破坏了承诺，照修。

同样的词写进 canon 告诉 agent 怎么判断问题的每个地方：

- 合入后的代码评审（BR-2070）只报正常操作会引出的安全和并发问题，每条的出错情形写明谁在哪个正常操作里会遇到；需要不正常配置或动作的情形不报，除非会丢数据、是安全问题，或破坏项目的承诺。评审提示是各项目共用的，没有项目上下文，所以提示写“破坏项目承诺的”，括号里说明在 canon 自己的仓库里指 `canon/product.md` 的 P1 到 P7。
- 分拣（canon-triage）：能点名谁在哪个正常操作里遇到，就算复现，不管测试用没用屏障；需要不正常配置或动作的情形记成“已知限制”，不丢数据、不是安全问题、不破坏承诺的，以 `not planned` 关闭，写明“需要不正常的配置或动作，在正常使用中发生了再打开”。
- 设计（canon-design）和排查（canon-diagnose）：对每个情形问同一个问题，正常操作会不会引出它；引不出的记成已知限制。
- `canon/product.md` 在“一个机制如果不支撑任何一条，就删掉”后面加一句：只为不正常的配置或动作才会出现的情形而加的机制也算不支撑，丢数据、安全问题和破坏承诺的除外。

## 后果

- 评审报得更少，会漏掉一些需要不正常配置或动作才出现的问题；它们真的发生时会有人遇到并提 issue，那时再修，有了真实的复现。
- 丢数据、安全问题和破坏 P1 到 P7 承诺的问题不受这条限制，评审和分拣照旧对待。少见但由正常操作引出的并发交错也在这一类里。
- 后台测试（`src/work/watch/`）已经为构造出来的交错加的代码不在这里删，按负责人的安排在设计评审之后另做简化。
- 规则评审的提示没有要求列出每个边界情况，不改。
