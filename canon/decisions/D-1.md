title: 以七条承诺为中心，把 lore 重建为 canon，只保留必要的部分

## 背景

到 2026 年 11 月，旧系统 lore 有 80 个顶层命令（加上子命令约 190 个）、约 19.2 万行源码、27 个 gate 和 hook、43 个 skill，每个会话注入约 5.9 万 token 的指令。2026-11-02 对线上仓库的审计测到：

- 检查 agent 做法的机制大多在拦合理的操作：提交检查里“分支没有新提交”这一条，抽样 20 次全是误拒；git 安全检查 54 次拒绝里 46 次误拒；编辑锚点检查抽样 270 次里 148 次误拒，约 7% 的拒绝之后 agent 改用 shell 绕了过去。
- 没人用的流程记录：240 条决策记录，0 条被追踪到结果；calibration 统计里 96% 的“人工判断”是 agent 写的；snapshot_accuracy 评审判失败 90 次，0 次是真问题；按任务记录的 evidence 调用 6,367 次，累计约 43 小时。
- baseline 规则本身有价值（agent 依据规则回答问题 20 题答对 16.5 题，没有规则时答对 13 题；写规则的过程查出 61 个确认的缺陷），但围绕它的机制没有价值：25,255 个 baseline 版本里 81.7% 是 coverage 映射写入；引用 gate 的 35 次拒绝里只有 2 次有用。
- AI 评审只在 spec 和 ADR 文字上有回报（抽样驳回 15 次全是真问题）；代码的安全和并发评审结论大多是真的，但因为只看一个 plan 的 diff，重复和过时的结论很多。
- 30 天里 agent 有 273 次绕过搜索，直接 grep 导出的 Markdown 镜像。

负责人定了七条承诺（`canon/product.md` 的 P1 到 P7），以及“证明责任在保留一方”的原则。

## 方案

1. 在原系统上删减，再原地按 DDD 重构。否决：大部分代码本身就是要删掉的流程，搬动 669 个以后要删的文件是浪费，而且中间状态会拖很久。
2. 保留 SQLite 作为事实来源，只做精简。否决：知识必须和它描述的代码在同一个提交里改（P1、P5），而 git 已经提供了历史、diff、blame 和备份。
3. 在同一个仓库里新旧并行重建，最后一次性切换。先试过（`next` 分支），后否决：旧项目的 hook、规则和测试一直在干扰（git 安全检查拦了删除临时 worktree；一次路径写错就跑了旧系统 2000 多个测试），而且切换要删 6000 多个文件、挪动新代码。
4. 在原路径新建仓库，继续叫 lore。试过，后否决：这个名字仍然把每个 agent 引向旧系统（`lore` 命令、40 个 `lore-*` skill、写着 `lore start` 的用户规则），而且挪走旧仓库会让它的 skill 链接失效。
5. 新建仓库并改名为 canon，旧的 lore 原样保留作为归档。采用。

## 决定

- 知识是 `canon/` 下的 Markdown 文件：每条规则一个文件（`rules/<领域>/BR-n.md`），决策、变更、笔记也各自一个文件。并发会话的脚本模拟显示：每条规则一个文件时误冲突为 0%，所有人往同一个文件末尾追加时为 53%（8 个会话时分别为 3.3% 和 59%）。
- 编号由协调数据库（git 公共目录里的 SQLite）分配，永远大于文件里出现过的最大编号，绝不重复使用。
- 协调状态（认领、合入队列、handoff、给人的问题、事件）存在这个数据库里，同一个 checkout 的所有 worktree 共用。只支持单机。
- 检查只看结果，只在两个边界：协调状态写入（比较并交换）和合入（rebase 到 main、floor、`canon check`、规则评审、main 的比较并交换）。没有任何 hook 检查 agent 怎么干活。
- AI 评审只对规则和决策的文字有阻断作用，并以整个领域为上下文；代码评审在合入之后跑，不阻断。
- 验收就是测试：测试名写规则编号，`canon check` 双向核对。
- 上下文由 AI 主动拉取（`canon context`），给的是整个领域，从不每轮注入。
- 旧仓库就是归档：本地 `~/Projects/zz/lore`，GitHub `github.com/daniel1zz/lore`，都保持不变。旧文档库（包括旧系统的规则）不迁移，因为那些规则描述的是这次重建要去掉的行为。新规则编号从 `BR-2001` 开始，同一个编号不会在两个系统里指不同的东西。

## 后果

- 没有 HTTP 服务、dashboard、Turso 同步、seat、phase、AC 记录、evidence 日志、引用 gate、coverage 映射、calibration，写入时也不再要求填决策字段。
- 旧编号（`BR-1` 到 `BR-1613`、`AS-n`、`AD-n`）只存在于归档仓库里。
- 每个检查都在事件表里记录拒绝原因，因此能算出它准不准；不值得的检查就删掉。
