## 背景

负责人要“主 agent 充分发挥主观能动性，真正智能调度，而不是等着我发现问题，应该是一个固化的机制”。当时的实况：待办清单（D-151）里要判定的事积了 114 条、最老的 8 天；8 个时好时坏的测试没人开 issue；机器有 10 个空位，能派的变更没人派；主会话一轮做完就停下，问负责人“下一步要不要做 X”。

待办清单已经在会话开始、`canon work watch` 和合入后打印，但打印只是让会话看见，会话一轮结束时照样停下。常驻说明只剩约 50 字节（D-169），再加一句“结束前先看待办清单”既放不下，也已经证明约束不住。每个项目都已经装了 Stop hook（`canon goal check --hook`，D-132），但它只在会话开了目标模式时才起作用，而且只看版本的成功标准。

独立 agent 对方案的质疑（采纳的）：只看 main 有没有前进来判断进展是错的，别的会话合入也会推进 main；worker 会话也触发同一个 Stop hook；会话可能正在等负责人回答，Stop 的输入里没有“这一轮在问人”的字段；B 级意见要别的会话处理，不该逼主会话做；用户要暂停时 Stop hook 不能硬拉会话回来（#328）。

## 方案

1. 在已有的 Stop hook 里加调度检查（采用）：默认对主会话开着，目标没拦下时，待办清单里有它现在能做的事就拦下一次并列出来；它自己有了进展（自己的事件、工作树的改动）才再拦，没进展就放行，下一轮第一次停下再拦。worker、关了调度的会话、没有能做的事时放行。代价是每轮最多多一次续写；会话在等负责人时再停一次就放行。不占常驻说明的预算。
   - 来源：https://code.claude.com/docs/en/hooks “prevents Claude from stopping. Omit to allow Claude to stop”
   - 来源：src/work/reminders/agenda.ts “the one place that works out what the main agent should hear about”
2. 目标模式默认打开（否决）：它看的是成功标准，时好时坏的测试、评审意见、停滞的派发都不在里面；没有进行中的版本时什么都不做。
3. 在常驻说明里加一句“结束前先处理待办清单”（否决）：预算只剩约 50 字节（D-169）；会话本来就看得见待办清单，照样停下，文字约束不住。
4. canon 自己在后台起 worker 会话做能开始的变更（否决）：只覆盖能派的活，要判定的事一条也碰不到；绕开主会话来协调的分工（D-151），会和主会话抢同一个变更；负责人不在时也在花钱。
5. 拦到待办清单清空为止，连续三次没进展才放行（否决）：负责人只是问一句话，会话也要被拉着处理三轮积压；别的会话推进 main 时可能永远凑不满三次。
6. 用 UserPromptSubmit hook 在负责人每说一句时注入待办清单（否决）：只是又一处“看得见”，不改变会话一轮结束就停下这件事。
   - 来源：https://code.claude.com/docs/en/hooks “when Claude Code is already continuing as a result of a stop hook”

## 决定

停下时的调度检查按 BR-2655，开关按 BR-2660；BR-2519 没有目标时改成接着做调度检查。

## 后果

- 什么结果证明它错了：一周的 `dispatch.hold` 里，超过一半拦下之后会话什么都没做就再停下（清单列的不是它能做的事）；或负责人说问话的轮次被拉去做杂事。前者修清单，后者改成只在会话自己的工作结束时检查。
- 主会话每一轮结束前，都会看到它现在能做的事（最多 5 行），要么去做，要么再停一次表示留着；`dispatch.hold` 事件记下每次列了什么，之后能用 `canon stats` 算它带来了多少行动。
- 待办清单的质量变得更要紧：清单里列了做不了或不该做的事，就会每轮打扰一次。这类噪声靠修清单本身（例如交给别的会话的 B 级意见已经不列），不靠关掉检查。
- 没有会话开着时，没有人处理待办清单；这个检查管不到，需要时由负责人用定时任务开会话。
- 子 agent 一律是 worker、不能写规则，所以要新规则的变更派出去会被 BR-2501 拒绝、交回主会话（C-647 就是这样）；派发前先把规则放到 main 上。
