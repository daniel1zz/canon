title: 未完成变更的列表从变更分支读 main 上还没有的变更，已开始的排在待办清单之后、没开始的之前
status: proposed
amends: [D-20]

## 背景

工作说明让没有任务的 agent 取 `canon change list` 里第一个没被认领的变更（D-20）。但用 `canon work start --title` 新建的变更，变更文件在合入前只在它自己的分支上。delegate 项目里 C-1 的会话 `canon work stop --release` 之后，主 checkout 里 `canon change list` 输出 `(no changes)`，C-1 只出现在 brief 最后一行的 handoff 列表里；照工作说明做的新会话找不到事做。canon 自己仓库里同时开着的变更（例如这次的 C-260）也一样只在分支上。要决定两件事：从哪里找这些变更，以及它们和待办清单、其他变更怎么排。

## 方案

从哪里找：

1. 从本地分支 `change/C-n`、`change/C-n-…` 直接读变更文件（`git show <分支>:canon/changes/…`）。采用：这和 `canon work start C-n` 接手只在分支上的变更（BR-2107）找的是同一处，能列出的就一定能开始；worktree 删掉了、会话没写交接就结束了，分支都还在。
   - 来源：src/work/session/session.ts “A change that is not on main but on its own branch”
2. 只读 handoff 表，列出有 handoff 的变更。否决：会话崩溃、没执行 `canon work stop` 的变更没有 handoff，照样漏掉；handoff 表里也没有标题和状态。
3. 从各个 worktree 的工作目录读。否决：worktree 删掉后就读不到了（BR-2107 的例子里 worktree 已被删掉、分支还在），还要读未提交的文件，而 start 读的是分支。
   - 来源：canon/rules/work/session/BR-2107.md “同样情形，但 worktree 已被删掉、分支还在”
4. 新建变更时先把变更文件提交到 main。否决：要么 agent 直接写 main（违反“只有合入才动 main”），要么每次新建都排一次合入，代价远大于这个问题。

怎么排：

1. 待办清单里的按清单排在最前；然后是没列进清单、已经开始的（有 handoff 或变更分支）；最后是其余的，各自按编号。采用：清单仍然只由负责人决定（D-20 不变）；没开始的新工作排在已经有人做了一半的后面，做了一半的工作分支越放越旧、越容易冲突。只在分支上的变更清单列不了（`canon check` 报 `ref-dangling`，BR-2150），所以总在“已开始”这一组。
2. 已开始的排在所有变更前面，包括清单里的。否决：任何 agent 只要 `canon work stop --release` 就能把自己的变更插到负责人排好的顺序前面，负责人失去排序权（D-20 “只有负责人改这个文件”）。
   - 来源：canon/decisions/D-20.md “只有负责人改这个文件”
3. 不分已开始和没开始，清单之外全按编号（D-20 原来的做法）。否决：只在分支上的变更编号往往比 main 上没开始的大（新建得晚），会排在后面；释放了的半成品要等前面没开始的都被取走才轮到。

## 决定

- `canon change list`（含 `--json`）和主 checkout 里 `canon brief` 的待办行，除了当前 checkout（brief 用 main）里的变更，也列出只在变更分支上的变更，从分支读，标出分支、handoff 和认领（BR-2291）。
- 顺序：清单 → 清单之外已开始的 → 其余，后两组按编号（BR-2148、BR-2291）。这修订了 D-20 的“清单之外的按编号排在最后”。

## 后果

- 每次 `canon change list` 和 `canon brief` 多一次 `git for-each-ref`，加上每个只在分支上的变更两次 git 调用。
- 分支上的变更文件坏了时这两个命令失败（退出码 4），不悄悄跳过；要修那个分支或用 `canon work drop` 放弃它。
- 用 `canon work start --title` 新建的变更有分支，排在清单之外没开始的变更前面；它被认领期间标着 `claimed`，别的 agent 跳过它。
