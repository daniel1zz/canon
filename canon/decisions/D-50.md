id: D-50
title: 未完成变更的列表从变更分支读 main 上还没有的变更，已开始的排在待办清单之后、没开始的之前
status: proposed
amends: [D-20]
---

## 背景

工作说明让没有任务的 agent 取 `canon change list` 里第一个没被认领的变更（D-20）。但用 `canon work start --title` 新建的变更，变更文件在合入前只在它自己的分支上。delegate 项目里 C-1 的会话 `canon work stop --release` 之后，主 checkout 里 `canon change list` 输出 `(no changes)`，C-1 只出现在 brief 最后一行的 handoff 列表里；照工作说明做的新会话找不到事做。canon 自己仓库里同时开着的变更（例如 C-260）也一样只在分支上。要决定：从哪里找这些变更，它们和待办清单、其他变更怎么排，以及分支上的情况不正常时（文件坏了、几个分支、关闭了没合入、文件提交在别的变更的分支上）怎么办。

## 方案

从哪里找：

1. 从本地分支 `change/C-n`、`change/C-n-…` 读这个变更自己的变更文件，按列出分支时它指向的提交读。采用：这和 `canon work start C-n` 接手只在分支上的变更（BR-2107）找的是同一处，能列出的就能开始；worktree 删掉了、会话没写交接就结束了，分支都还在；按提交读，分支在中途被删也不失败（#110）。
   - 来源：src/work/session/session.ts “A change that is not on main but on its own branch”
2. 只读 handoff 表，列出有 handoff 的变更。否决：会话崩溃、没执行 `canon work stop` 的变更没有 handoff，照样漏掉；handoff 表里也没有标题和状态。
3. 从各个 worktree 的工作目录读。否决：worktree 删掉后就读不到了（BR-2107 的例子里 worktree 已被删掉、分支还在），还要读未提交的文件，而 start 读的是分支。
   - 来源：canon/rules/work/session/BR-2107.md “同样情形，但 worktree 已被删掉、分支还在”
4. 新建变更时先把变更文件提交到 main。否决：要么 agent 直接写 main（违反“只有合入才动 main”），要么每次新建都排一次合入，代价远大于这个问题。
5. 读每个变更分支上的所有变更文件，包括提交在别的变更分支上的（例如 `change/C-2-x` 上的 `C-7.md`）。否决：`canon work start C-7` 只找 `C-7` 自己的分支，列出来也开始不了，又回到“列表里的东西开始不了”；这样的文件随所在的变更合入后自然出现。每个分支还要多读整个目录。

怎么排：

1. 待办清单里的按清单排在最前，不管它在 main 上还是只在分支上；然后是没列进清单、已经开始的（有 handoff 或变更分支）；最后是其余的，各自按编号。采用：清单仍然只由负责人决定；没开始的新工作排在已经有人做了一半的后面，做了一半的分支越放越旧、越容易冲突。负责人要把只在分支上的变更提前或推后，写进清单就行：`canon check` 认分支上的变更文件，不报 `ref-dangling`（BR-2150）。
2. 已开始的排在所有变更前面，包括清单里的。否决：任何 agent 只要 `canon work stop --release` 就能把自己的变更插到负责人排好的顺序前面，负责人失去排序权（D-20 “只有负责人改这个文件”）。
   - 来源：canon/decisions/D-20.md “只有负责人改这个文件”
3. 不分已开始和没开始，清单之外全按编号（D-20 原来的做法）。否决：只在分支上的变更编号往往比 main 上没开始的大（新建得晚），会排在后面；释放了的半成品要等前面没开始的都被取走才轮到。

分支上的情况不正常时：

1. 一个分支上的变更文件读不了，整个命令失败。否决：brief 每个会话开始都运行，别人做了一半的一个坏分支会让所有会话的 brief 失败、看不到其他工作。改成只影响这一项：brief 说一行照样列其余的（退出码 0），change list 列完其余的再以退出码 4 失败（BR-2292）。
2. 同一个变更在几个分支上时列成可以开始的。否决：`canon work start` 这时拒绝（BR-2107），所以标 `ambiguous`，工作说明让 agent 跳过（BR-2293）。
3. 只在分支上标成 `done` 的变更按 `done` 过滤掉。否决：这是合入被杀掉、关闭提交没撤回的半成品，过滤掉就又从列表里消失；所以照样列出，标 `closed on branch, not landed`，`canon work start` 能接手它去合入（BR-2294）。

清单里失效的编号（#112：清单列了只在分支上的变更，之后分支被 `canon work drop` 删掉）：

1. 只拦截加进这个编号的那次工作（main 上提交的清单还没列它），其余合入、`canon work test` 和 main 上的 `canon check` 只提示一行（写明行号和怎么修）；`canon work drop` 放弃清单还列着的变更时照常删除，再提示一行。采用（协调者决定，方案 1 加方案 3）：打错编号的是改清单的那一次，拦它正是 BR-2150 的目的；删分支的人不改清单（清单只由负责人改），所以和清单无关的合入、main 上的检查不能因为别人删了分支被拦住。
   - 来源：canon/rules/work/drop/BR-2064.md “变更文件的状态不改”
2. 只要这次合入改了 `canon/backlog.md` 就检查全部编号。否决：负责人为了调一行顺序改清单时，会被别人早先删分支留下的旧编号拦住，而那不是这次改动造成的。
3. 照旧在每次合入都拦截。否决：一次 `canon work drop` 之后，所有和清单无关的合入都被拒，直到负责人改清单（#112）。
4. `canon work drop` 遇到清单还列着的变更就拒绝。否决：放弃是正当操作，agent 又不能改清单，拒绝只会让工作卡住。

## 决定

- `canon change list`（含 `--json`）和主 checkout 里 `canon brief` 的待办行，除了当前 checkout（brief 用 main）里的变更，也列出只在它自己的变更分支上的变更，按列出时的提交读，标出分支、handoff 和认领（BR-2291）；提交在别的变更分支上的变更文件不列。
- 顺序：清单 → 清单之外已开始的 → 其余，后两组按编号（BR-2148、BR-2291）；只在分支上的变更也能写进清单（BR-2150）。
- 清单里失效的编号只拦截加进它的那次工作，其余只提示；放弃清单还列着的变更时提示负责人删那一行（BR-2150、BR-2064）。
- 读不了的文件只影响自己那一项（BR-2292）；几个分支标 `ambiguous` 并跳过（BR-2293）；分支上关闭了没合入的照样列出、能接手（BR-2294）。
- 这修订了 D-20 的两处：“清单之外的按编号排在最后”，以及“agent 发现的新工作照常建成变更，自动排在最后”。现在 agent 用 `canon work start --title` 新建的变更有分支，算已经开始的，排在清单之外没开始的变更前面，不再总在最后。可以接受：它只排在清单之外的变更里，负责人排进清单的顺序不受影响；它被认领期间标着 `claimed`，别的 agent 不会去取；它的会话结束、认领失效后，排在前面正是想要的，半成品先做完。负责人不同意这个位置时，把要先做的变更写进待办清单（只在分支上的也可以，BR-2150）。
  - 来源：canon/decisions/D-20.md “agent 发现的新工作照常建成变更，自动排在最后”

## 后果

- 每次 `canon change list`、`canon brief`、`canon check`、`canon work test` 和合入时的检查多一次 `git for-each-ref`，加上每个变更分支一到两次 git 调用；change list 和 brief 再多一次读 main 上变更文件名的 `git ls-tree`，check 和 work test 再多读一次起点上的清单。
- 只在分支上的变更按 main 的最新提交判断：main 上已经有这个编号就不从分支列（旧 worktree 里看不到 main 后来合入的变更，它们留下的分支不能当成没合入，BR-2294）。清单编号算不算“已经列过”，看 main 的最新提交和这个 worktree 的起点两处：负责人在 main 上删掉一行后，没 rebase 的 worktree 不会被当成加进了它（BR-2150）。
- `canon check` 的结果取决于本地有哪些变更分支：清单刚加上只在分支上的变更时，在没有这个分支的克隆里会报 `ref-dangling`；进了 main 以后，分支不在只是一行提示。
- 分支上的变更文件坏了时，brief 提示一行，`canon change list` 以退出码 4 结束；要修那个分支或用 `canon work drop` 放弃它。
