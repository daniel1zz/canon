## 背景

D-23 定下“文件依次运行，不并行”，理由有两条。第一条是几个测试文件放进一次 `bun test` 时卡住：那是 Bun 1.3.x 的缺陷，1.4.4 已修好（#35），而且 canon 本来就是一个文件一个进程，同时运行几个进程不是那种用法，这条理由已经不成立。第二条是“几个 worktree 同时测试时负载已经很高，再并行会让测试更不稳”，这是一个判断，机器忙时成立，机器空时不成立。

现在的代价（2026-11-04 事件表的 `work.test`）：事件 #4233 选出 57 个文件用了 1200 秒，#4267 38 个文件 888 秒，#4257 26 个文件 736 秒，每次 12 到 20 分钟，是每个变更最主要的等待。负责人 2026-11-04 定了方向：“要，动态并发跑”，即按机器当前的空闲程度决定同时跑几个，机器忙满时退回一次一个。

本机实测（Apple M1 Pro，6 个性能核加 2 个能效核，`os.availableParallelism()` 为 8，内存 16 GB）：

- 同一时刻的两种量法给出相反的结论：1 分钟负载 12.9 到 13.3（按“负载减核数”算是超载、没有空位），而用 `os.cpus()` 的时间计数每 2 秒量一次，空闲的 CPU 有 1.9 到 2.7 个。负载平均把等 I/O、等锁的线程也算进去，在 macOS 上和“还有没有空闲的 CPU”不是一回事。
- 一个测试文件（`src/work/verify/verify.test.ts`）在负载 20 到 25 时：墙钟 52 到 54 秒，user 约 11 秒、sys 约 21 秒，平均只用约 0.6 个 CPU，大部分时间花在启动 git 和 canon 子进程上；最大的单个进程常驻内存约 112 MB。
- 实现后的对比（同一台机器，同一组 26 个测试文件，`canon work test --all`，`tests` 限定为这 26 个，去掉类型检查，每种设置各跑两次；开始时的 1 分钟负载平均就是当时别的会话造成的）：

  | 设置 | 用时（秒） | 同时最多 | 开始时 1 分钟负载 | 失败 |
  |---|---|---|---|---|
  | `test_jobs: 1` 第一次 | 422.8 | 1 | 20.6 | 0 |
  | `test_jobs: auto`（8 核上限 4）第一次 | 147.6 | 4 | 3.6 | 0 |
  | `test_jobs: 1` 第二次 | 389.2 | 1 | 7.7 | 0 |
  | `test_jobs: auto` 第二次 | 160.7 | 4 | 3.6 | 0 |
  | `test_jobs: 8`（一次，对照） | 125.9 | 8 | 5.3 | 0 |

  `auto` 比一个一个跑快约 2.6 到 2.7 倍；5 次里没有出现只在同时运行时才有的失败，所以没有触发单独重跑。`auto` 在这台机器上就是 4，所以没有另外跑 `test_jobs: 4`；`8` 只比 `auto` 快约 18%（125.9 对 147.6 和 160.7 的平均 154），和 `auto` 比收益不大，这是上限取一半的依据。负载在运行中是别的会话持续变化的，每组只有两次，不能当作精确的加速比，只能说明方向和量级。
- 所以忙时多开文件只会互相抢 CPU，空时一个文件用不满一个 CPU，同时跑几个能把一次运行缩短到几分之一。

## 方案

### 怎样量机器还有多少空

1. 固定个数：配置写几个就同时跑几个，不看机器。否决：机器由很多会话共用，盲目并行在忙时（负载 36、8 核）会让每个会话都更慢，正是 D-23 担心的情况；它只适合做上限，不能做默认。
2. 开始时读一次 1 分钟负载平均，算出个数，整次运行不变。否决：
   - Windows 上 `os.loadavg()` 总是返回 `[0, 0, 0]`，canon 给别的项目用，在 Windows 上会以为机器全空、开到上限。
     - 来源：https://nodejs.org/api/os.html#osloadavg “On Windows, the return value is always [0, 0, 0]”
   - macOS 上和空闲 CPU 对不上（上面实测：负载 13 时仍有 2 个多 CPU 空闲）；Linux 上负载也算进等磁盘的进程。
   - 一次运行 12 到 20 分钟，开头的读数很快就过时。
3. 每有一个文件结束时重新读负载平均。否决：除了 2 的前两条问题，负载平均是 1 分钟的指数平均，自己刚开的文件要将近一分钟才反映出来，开头几秒会一口气开到上限，再过一分钟才发现超了。
4. 用 `os.cpus()` 的时间计数，每 2 秒量一次这 2 秒里空闲的 CPU 个数（空闲时间占比乘 CPU 个数），每个文件结束时和每 2 秒的定时检查时各判断一次（BR-2302 用同一条规则），每个窗口最多多开一个，窗口从本次运行上一次开文件或上一次评估起算，不到 2 秒不评估。采用：
   - Linux、macOS、Windows 上 `os.cpus()` 都给时间计数，不依赖 `ps`、`/proc` 之类的平台命令。
   - 2 秒内的读数，几乎没有滞后；“只用上次开文件之后的测量、一次最多开一个”保证自己刚开的文件先被量进去，不会一下开满。
   - 量的是整台机器，所以别的会话、别的程序的占用都算在内。
   - 失败情况：（a）几次 `canon work test` 同时看到同一批空闲 CPU，同一个 2 秒里各开一个，会多开几个；只是一次判断的量，下一个 2 秒就看到了，已经开了的文件跑完（十几到几十秒）为止。（b）Linux 容器限制了 CPU 配额时，`os.cpus()` 看到的是宿主机的 CPU 和宿主机的空闲，空闲数是按宿主机量的，会高估；但上限用 `os.availableParallelism()`（它按亲和性和容器的限制缩小），所以同时运行的个数仍被容器的 CPU 数挡住。空闲数乘 `os.cpus().length`（量的就是这么多个 CPU），上限用 `os.availableParallelism()`，两个数各管各的。cgroup 配额不是整数个 CPU 时 `availableParallelism` 可能仍偏大，这时项目自己写 `test_jobs`。（c）`os.cpus()` 返回空列表，开始时就量不出来：整次一次一个，打印一行写明原因，`work.test` 记 `cpu: "unreadable"`。运行中间某个窗口里计数器全都没前进：这个窗口不多开，本次运行第一次这样时打印一行，`work.test` 记 `cpu: "stalled"` 和窗口个数，不悄悄当作机器是空的，也不悄悄当作机器是忙的。（e）Linux 上 libuv 读 `/proc/stat` 时丢掉 iowait（`linux.c` 里 `&skip`），它既不在 idle 里也不在合计里，所以等磁盘的时间不算空闲、也不算忙：窗口里的空闲份额不会因此虚高，但等磁盘多的机器会量到偏忙一点的读数（偏向少开）。至少 1 个空闲 CPU 按整数计数器比较（空闲增量乘 CPU 个数不小于合计增量），不用浮点数。（d）内存不在量的范围内：macOS 的 `os.freemem()` 只算完全空闲的页（本机实测约 240 MB，而大量缓存页随时可回收），拿它判断会一直以为内存不够；单个文件约 112 MB，上限（见下）是 CPU 个数的一半，8 核时 4 个文件不到 0.5 GB，所以不量内存，靠上限挡住。
5. 用 canon 协调数据库做全机的名额：所有 `canon work test` 一起最多同时跑 N 个文件。否决：协调数据库按项目分，看不到别的项目和别的程序的占用；进程被杀时名额要回收，又是一种出错方式；而方案 4 量整台机器，已经把别的会话算在内。
6. 交给测试工具自己并行（如 `bun test` 一次传多个文件、vitest 的线程池）。否决：只有部分工具有，canon 要支持任意 `test_command`（D-23 方案 4）；D-23 一个文件一个进程的做法也是为了避开一次 `bun test` 多文件的问题。

### 上限和配置

7. 新增配置 `test_jobs`：不小于 1 的整数，或 `auto`；默认 `auto`。`auto` 的上限是 CPU 个数的一半向下取整（至少 1）；写成数字时上限就是这个数。无论哪种，到上限之前每多开一个都要满足方案 4 的“至少 1 个 CPU 空闲”；写成 `1` 时完全不量，和以前一样一次一个。采用。
   - 上限取一半而不是全部 CPU：一个文件平均只用约 0.6 个 CPU，但启动子进程时会短时间用满不止一个；留一半给同时在跑的别的会话和它们的类型检查。8 核上限 4 个，按上面一个文件平均 0.6 个 CPU 算，4 个约占 2.4 个 CPU，在本机常见的 2 个左右空闲 CPU 附近。
   - 数字是上限、不是固定个数：负责人要的是动态；固定个数就是方案 1。
   - 默认 `auto` 而不是 `1`：负责人要的是默认就快。代价：别的项目里，几个测试文件共用同一个外部资源（同一个端口，比如都用 `CANON_PORT`；同一个临时文件；同一个数据库）时，同时运行会互相干扰。canon 判断不了测试用了什么外部资源，所以由项目写 `test_jobs: 1`；并且有方案 9 的单独重跑，这类干扰显示成“同时运行时失败、单独运行通过”，不会被当成真正的失败，也不会被悄悄吞掉。
8. 不加配置项，总是自动。否决：容器配额（方案 4 的失败情况 b）和共用外部资源的项目（方案 7）都需要一个关掉或压低的办法。

### 失败、不稳定和输出

9. 一个文件失败时，如果它运行期间本次运行还有别的文件在跑，等其他文件都结束后，单独再运行它一次，以单独运行的结果为准，两次结果都打印，汇总里写明哪些文件是“同时运行时失败、单独运行通过”。重跑最多 3 个文件（BR-2303）：同时失败的超过 3 个时一个也不重跑，打印原因，它们都算失败。否决“重跑一部分”：选哪几个没有道理，结果不好解释；否决“按比例”：57 个文件的 10% 是 6 个，14 个文件的 10% 是 1 个，3 这个数不随选出的个数变，两三个不稳的文件是这个办法要解决的情况，几十个同时失败说明别的出了问题（机器出故障或改动弄坏了很多测试），重跑只会多等几十个文件的时间。例如 57 个里 50 个失败，不做 50 次依次重跑。采用：floor 跑全量时文件是依次运行的，单独运行的结果才是合入时会看到的结果；不重跑的话，负载导致的超时（本仓库 `scripts/test.sh` 每个测试 30 秒）会让 agent 去追一个不存在的失败，再花十几分钟重跑整次。代价：真正失败的文件多跑一次（几十秒）；一个单独运行也偶尔失败的测试被这次单独运行碰巧通过时会少报一次，所以这种情况一定打印出来并记进事件。
10. 不重跑，失败就是失败。否决：见 9，同时运行带来的失败和真正的失败分不开。
11. 所有失败都重跑一次（包括本来就单独运行的）。否决：单独运行时失败已经是 floor 会看到的结果，重跑只是在掩盖不稳定的测试。
12. 有文件失败就不再开新文件（fail fast）。否决：C-194 定下一次运行要报出所有问题，agent 一次修完；合入前只跑相关文件，剩下的文件不多。
13. 每个文件的输出整段收下来，结束时一次打印（结果行和失败时的最后 40 行），按结束的先后打印。采用：现在就是整段收下来再打印，同时运行也不会交错；按结束先后打印能马上看到进度。汇总里失败文件的列表按选出的顺序，两次运行的结果容易对比。否决按选出顺序打印每个文件：前面一个慢文件会压住后面所有已经结束的结果。
14. 开始的顺序：按选出的顺序（路径排序）。否决“先开历来最慢的文件”：事件表没有记每个文件的用时，要新增记录；不按这个排，最坏多等大约一个文件的用时。

### 前后的步骤、信号、`--all`

15. 类型检查（BR-2226）仍在所有测试文件开始之前单独跑完，`canon check`（BR-2227）仍在所有测试文件（包括单独重跑）结束之后跑。采用：类型检查本仓库只要几秒（事件 #4301 那次一个文件都没选出，整次 4 秒），和测试同时跑省不了多少，却要改变 BR-2226 定下的输出顺序。
16. 被 SIGTERM、SIGINT 或 SIGHUP 终止时：不再开新文件，每个命令（类型检查、每个测试文件、每次单独重跑）在自己的进程组里启动，停的时候给每个正在运行的进程组发 SIGTERM，等它们结束（最多 10 秒），第二个信号或超时后发 SIGKILL，再等最多 5 秒（BR-2304）。退出码 143、130、129。打印停掉了几个、几个没开始（同时失败、还没重跑的算没开始，不算失败），记一条带 `signal` 的 `work.test`。因信号结束的子进程，在 canon 收到停止信号之前或之后 0.5 秒内，不算失败、不重跑，否则 canon 自己发的 SIGTERM 会被当作失败去重跑。采用，理由：
   - 现在依次运行时 canon 被终止也会留下正在跑的 `bun test`，同时运行会留下好几个；用户要求被终止的运行要停掉每个文件的进程树。
   - 进程组不需要读进程表：D-55（2026-11-04 在本变更开始后合入）已经否决了用 `ps` 跟踪、冻结、等待、SIGKILL 的整套办法（读不出 `ps`、守护进程等情形堵不住，每次补丁又成为评审的新目标），BR-2285 只剩给进程组发 SIGTERM。这里不照 BR-2285 的“不等”，因为测试文件的进程留下会继续占着机器，也会和下一次运行抢同一个端口和临时文件，所以等它们结束；只处理真实发生的情况（D-54）：离开进程组的进程、canon 被单独 SIGKILL 后留下的进程是已知限制，和以前一样。
   - 否决“只给 canon 的进程组发信号”：常见的启动方式（agent 工具的 Bash、`canon work test | tee`）里 canon 不是组长，组里还有别的进程。
   - 否决“照评审意见 D5 用 BR-2285 的 SIGSTOP 冻结加 SIGTERM 加等待那一套”：那一套在写评审意见之后被 D-55 删掉，BR-2285 已经不是那样。
   - 代价：测试文件放在新的会话里，不再收到终端的 Ctrl-C，只靠 canon 转发；canon 被 SIGKILL 时它们不会随终端一起结束。
   - 来源：src/knowledge/review/review.ts “process.kill(-proc.pid, "SIGKILL")”（评审命令已用同样的 `detached` 加给 `-pid` 发信号的办法）
17. `--all` 和不带 `--all` 一样按 `test_jobs` 和空闲 CPU 同时运行。采用：`--all` 文件最多，最需要快；一个文件一个进程不变（BR-2159）。

## 决定

采用方案 4、7、9、13、14、15、16、17：新增 `test_jobs`（默认 `auto`，上限为 CPU 个数的一半；写数字是上限；`1` 完全依次运行），每 2 秒量一次空闲 CPU，至少 1 个空闲、未到上限、量的那段在上次开文件之后时多开一个，一个都没在跑时立即开下一个；同时运行时失败的文件最后单独再跑一次；被信号终止时停掉所有正在跑的文件的进程树。这修改了 D-23 的“文件依次运行，不并行”：仍是一个文件一个进程，但可以同时运行几个；机器忙满时（量不到空闲 CPU）退回一次一个，就是 D-23 原来的做法。规则：BR-2302（同时运行几个）、BR-2303（单独重跑，最多 3 个）、BR-2304（信号，进程组）、BR-2158、BR-2159、BR-2045。

## 后果

- 一个卡住的文件没有每个文件自己的超时（和 D-23 一样，不新增），它占着一个名额直到结束；同时运行时别的文件仍在剩下的名额里运行，所以卡住的文件现在只拖慢自己，不再挡住后面所有的文件。
- 空闲的机器上，一次运行的用时最多缩到约原来的几分之一（上限 4 时，最多约 1/4，再加上一个慢文件的尾巴）；忙满的机器上和以前一样。
- 同时运行的文件让每个文件自己的墙钟用时变长，单个文件的用时不再能直接和以前比较；`work.test` 加 `jobs`（上限）、`peak`（实际最多同时跑了几个）、`cpu` 和 `stalledWindows`（量 CPU 的情况）、`rerun`、`rerunFiles`、`passedAlone`、`passedAloneFiles`、`rerunSkipped`（单独重跑），被信号终止的加 `signal`；文件数每个文件只算一次。
- 别的项目里共用外部资源的测试文件，升级后同时运行可能互相干扰；它们会出现在“同时运行时失败、单独运行通过”里，看到后写 `test_jobs: 1`。
- 容器里量到的空闲是宿主机的，上限由 `os.availableParallelism()` 挡住；配额不是整数个 CPU 时项目自己写 `test_jobs`。
- 项目要先把 canon 升级到带 `test_jobs` 的版本，再写 `test_jobs`：旧版 canon 读到未知的键，所有命令以退出码 2 失败（BR-2045）。所以本变更不在本仓库的 `canon/config.yaml` 里写 `test_jobs`（BR-2248，默认 `auto` 已经生效）。
- floor 跑全量的方式不变，这里只改 `canon work test`。
