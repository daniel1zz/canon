## 背景

D-23 定下“文件依次运行，不并行”，理由有两条。第一条是几个测试文件放进一次 `bun test` 时卡住：那是 Bun 1.3.x 的缺陷，1.4.4 已修好（#35），而且 canon 本来就是一个文件一个进程，同时运行几个进程不是那种用法，这条理由已经不成立。第二条是“几个 worktree 同时测试时负载已经很高，再并行会让测试更不稳”，这是一个判断，机器忙时成立，机器空时不成立。

现在的代价（2026-11-04 事件表的 `work.test`）：事件 #4233 选出 57 个文件用了 1200 秒，#4267 38 个文件 888 秒，#4257 26 个文件 736 秒，每次 12 到 20 分钟，是每个变更最主要的等待。负责人 2026-11-04 定了方向：“要，动态并发跑”，即按机器当前的空闲程度决定同时跑几个，机器忙满时退回一次一个。

本机实测（Apple M1 Pro，6 个性能核加 2 个能效核，`os.availableParallelism()` 为 8，内存 16 GB）：

- 同一时刻的两种量法给出相反的结论：1 分钟负载 12.9 到 13.3（按“负载减核数”算是超载、没有空位），而用 `os.cpus()` 的时间计数每 2 秒量一次，空闲的 CPU 有 1.9 到 2.7 个。负载平均把等 I/O、等锁的线程也算进去，在 macOS 上和“还有没有空闲的 CPU”不是一回事。
- 一个测试文件（`src/work/verify/verify.test.ts`）在负载 20 到 25 时：墙钟 52 到 54 秒，user 约 11 秒、sys 约 21 秒，平均只用约 0.6 个 CPU，大部分时间花在启动 git 和 canon 子进程上；最大的单个进程常驻内存约 112 MB。
- 所以忙时多开文件只会互相抢 CPU，空时一个文件用不满一个 CPU，同时跑几个能把一次运行缩短到几分之一。

## 方案

### 怎样量机器还有多少空

1. 固定个数：配置写几个就同时跑几个，不看机器。否决：机器由很多会话共用，盲目并行在忙时（负载 36、8 核）会让每个会话都更慢，正是 D-23 担心的情况；它只适合做上限，不能做默认。
2. 开始时读一次 1 分钟负载平均，算出个数，整次运行不变。否决：
   - Windows 上 `os.loadavg()` 总是返回 `[0, 0, 0]`，canon 给别的项目用，在 Windows 上会以为机器全空、开到上限。
     - 来源：https://nodejs.org/api/os.html#osloadavg “On Windows, the return value is always [0, 0, 0]”
   - macOS 上和空闲 CPU 对不上（上面实测：负载 13 时仍有 2 个多 CPU 空闲）；Linux 上负载也算进等磁盘的进程。
   - 一次运行 12 到 20 分钟，开头的读数很快就过时。
3. 每有一个文件结束时重新读负载平均。否决：除了 2 的前两条问题，负载平均是 1 分钟的指数平均，自己刚开的文件要将近一分钟才反映出来，开头几秒会一口气开到上限，再过一分钟才发现超了。
4. 用 `os.cpus()` 的时间计数，每 2 秒量一次这 2 秒里空闲的 CPU 个数（空闲时间占比乘 CPU 个数），文件结束和每 2 秒各判断一次，每次最多多开一个，而且只用在本次运行上一次开文件之后才开始的那段测量。采用：
   - Linux、macOS、Windows 上 `os.cpus()` 都给时间计数，不依赖 `ps`、`/proc` 之类的平台命令。
   - 2 秒内的读数，几乎没有滞后；“只用上次开文件之后的测量、一次最多开一个”保证自己刚开的文件先被量进去，不会一下开满。
   - 量的是整台机器，所以别的会话、别的程序的占用都算在内。
   - 失败情况：（a）几次 `canon work test` 同时看到同一批空闲 CPU，同一个 2 秒里各开一个，会多开几个；只是一次判断的量，下一个 2 秒就看到了，已经开了的文件跑完（十几到几十秒）为止。（b）Linux 容器限制了 CPU 配额时，`os.cpus()` 看到的是宿主机的核和宿主机的空闲，会高估；这时把 `test_jobs` 写成配额的个数。（c）有的环境 `os.cpus()` 返回空列表或时间全是 0，量不出来：这时一次一个，并打印一行写明原因，不悄悄假设机器是空的。（d）内存不在量的范围内：macOS 的 `os.freemem()` 只算完全空闲的页（本机实测约 240 MB，而大量缓存页随时可回收），拿它判断会一直以为内存不够；单个文件约 112 MB，上限（见下）是 CPU 个数的一半，8 核时 4 个文件不到 0.5 GB，所以不量内存，靠上限挡住。
5. 用 canon 协调数据库做全机的名额：所有 `canon work test` 一起最多同时跑 N 个文件。否决：协调数据库按项目分，看不到别的项目和别的程序的占用；进程被杀时名额要回收，又是一种出错方式；而方案 4 量整台机器，已经把别的会话算在内。
6. 交给测试工具自己并行（如 `bun test` 一次传多个文件、vitest 的线程池）。否决：只有部分工具有，canon 要支持任意 `test_command`（D-23 方案 4）；D-23 一个文件一个进程的做法也是为了避开一次 `bun test` 多文件的问题。

### 上限和配置

7. 新增配置 `test_jobs`：不小于 1 的整数，或 `auto`；默认 `auto`。`auto` 的上限是 CPU 个数的一半向下取整（至少 1）；写成数字时上限就是这个数。无论哪种，到上限之前每多开一个都要满足方案 4 的“至少 1 个 CPU 空闲”；写成 `1` 时完全不量，和以前一样一次一个。采用。
   - 上限取一半而不是全部 CPU：一个文件平均只用约 0.6 个 CPU，但启动子进程时会短时间用满不止一个；留一半给同时在跑的别的会话和它们的类型检查。8 核上限 4 个，按上面一个文件平均 0.6 个 CPU 算，4 个约占 2.4 个 CPU，在本机常见的 2 个左右空闲 CPU 附近。
   - 数字是上限、不是固定个数：负责人要的是动态；固定个数就是方案 1。
   - 默认 `auto` 而不是 `1`：负责人要的是默认就快。代价：别的项目里，几个测试文件共用同一个外部资源（同一个端口，比如都用 `CANON_PORT`；同一个临时文件；同一个数据库）时，同时运行会互相干扰。canon 判断不了测试用了什么外部资源，所以由项目写 `test_jobs: 1`；并且有方案 9 的单独重跑，这类干扰显示成“同时运行时失败、单独运行通过”，不会被当成真正的失败，也不会被悄悄吞掉。
8. 不加配置项，总是自动。否决：容器配额（方案 4 的失败情况 b）和共用外部资源的项目（方案 7）都需要一个关掉或压低的办法。

### 失败、不稳定和输出

9. 一个文件失败时，如果它运行期间本次运行还有别的文件在跑，等其他文件都结束后，单独再运行它一次，以单独运行的结果为准，两次结果都打印，汇总里写明哪些文件是“同时运行时失败、单独运行通过”。采用：floor 跑全量时文件是依次运行的，单独运行的结果才是合入时会看到的结果；不重跑的话，负载导致的超时（本仓库 `scripts/test.sh` 每个测试 30 秒）会让 agent 去追一个不存在的失败，再花十几分钟重跑整次。代价：真正失败的文件多跑一次（几十秒）；一个单独运行也偶尔失败的测试被这次单独运行碰巧通过时会少报一次，所以这种情况一定打印出来并记进事件。
10. 不重跑，失败就是失败。否决：见 9，同时运行带来的失败和真正的失败分不开。
11. 所有失败都重跑一次（包括本来就单独运行的）。否决：单独运行时失败已经是 floor 会看到的结果，重跑只是在掩盖不稳定的测试。
12. 有文件失败就不再开新文件（fail fast）。否决：C-194 定下一次运行要报出所有问题，agent 一次修完；合入前只跑相关文件，剩下的文件不多。
13. 每个文件的输出整段收下来，结束时一次打印（结果行和失败时的最后 40 行），按结束的先后打印。采用：现在就是整段收下来再打印，同时运行也不会交错；按结束先后打印能马上看到进度。汇总里失败文件的列表按选出的顺序，两次运行的结果容易对比。否决按选出顺序打印每个文件：前面一个慢文件会压住后面所有已经结束的结果。
14. 开始的顺序：按选出的顺序（路径排序）。否决“先开历来最慢的文件”：事件表没有记每个文件的用时，要新增记录；不按这个排，最坏多等大约一个文件的用时。

### 前后的步骤、信号、`--all`

15. 类型检查（BR-2226）仍在所有测试文件开始之前单独跑完，`canon check`（BR-2227）仍在所有测试文件（包括单独重跑）结束之后跑。采用：类型检查本仓库只要几秒（事件 #4301 那次一个文件都没选出，整次 4 秒），和测试同时跑省不了多少，却要改变 BR-2226 定下的输出顺序。
16. 被 SIGTERM 或 SIGINT 终止时：不再开新文件，用 BR-2285 后台测试已有的做法停掉每个正在运行的文件的全部进程（先 SIGTERM，最多等 10 秒，还在的 SIGKILL），打印停掉了几个、几个没开始，记一条带 `signal` 的 `work.test`，退出码 130 或 143（和 BR-2099 一样）。采用：现在依次运行时 canon 被终止也会留下正在跑的 `bun test`，同时运行会留下好几个；子进程不另开进程组，所以从外面杀整个进程组（终端的 Ctrl-C、工具超时杀进程组）照样能杀到它们，只有 canon 自己单独收到信号时才需要它去停。否决“每个文件开在自己的进程组里，收到信号时杀进程组”：canon 被 SIGKILL 时，这些进程组从外面杀 canon 的进程组也杀不到。`ps` 读不了（如不带 POSIX 工具的 Windows）时，按 BR-2285 的做法打印一行写明可能没停干净。
17. `--all` 和不带 `--all` 一样按 `test_jobs` 和空闲 CPU 同时运行。采用：`--all` 文件最多，最需要快；一个文件一个进程不变（BR-2159）。

## 决定

采用方案 4、7、9、13、14、15、16、17：新增 `test_jobs`（默认 `auto`，上限为 CPU 个数的一半；写数字是上限；`1` 完全依次运行），每 2 秒量一次空闲 CPU，至少 1 个空闲、未到上限、量的那段在上次开文件之后时多开一个，一个都没在跑时立即开下一个；同时运行时失败的文件最后单独再跑一次；被信号终止时停掉所有正在跑的文件的进程树。这修改了 D-23 的“文件依次运行，不并行”：仍是一个文件一个进程，但可以同时运行几个；机器忙满时（量不到空闲 CPU）退回一次一个，就是 D-23 原来的做法。规则：BR-2302（同时运行几个）、BR-2303（单独重跑）、BR-2304（信号）、BR-2158、BR-2159、BR-2045。

## 后果

- 空闲的机器上，一次运行的用时最多缩到约原来的几分之一（上限 4 时，最多约 1/4，再加上一个慢文件的尾巴）；忙满的机器上和以前一样。
- 同时运行的文件让每个文件自己的墙钟用时变长，单个文件的用时不再能直接和以前比较；`work.test` 加 `jobs`（上限）、`peak`（实际最多同时跑了几个）、`rerun`（单独重跑的文件数）、`passedAlone`（其中单独运行通过的个数），被信号终止的加 `signal`。
- 别的项目里共用外部资源的测试文件，升级后同时运行可能互相干扰；它们会出现在“同时运行时失败、单独运行通过”里，看到后写 `test_jobs: 1`。
- 容器里看不到 CPU 配额，需要项目自己写 `test_jobs`。
- floor 跑全量的方式不变，这里只改 `canon work test`。
