## 背景

负责人（2026-11-12，canon human #31、#33、#34 及对话）：“每次独立agent去做有个问题，一个是主agent不知道啥情况，一个是独立agent又要读很多上下文”；“我是希望很多事情能快速协调确认好，而不是一遍遍去评审打回”；“主agent作为调度的他知道更多的上下文”。#33 先定了“队列只做机械检查，检查通过的让主agent开始评审合并”；听过这样会把每次迭代重新拦在门口、主 agent 也读不过来之后，#34 改为：“还是保持之前那套把。然后三次没有合并成功再给主Agent”。

D-89 定的做法是：规则评审挪到合入之后，拦截意见交给另一个核实命令判断（BR-2442），之后每次评审再把挂着的意见逐条复问（BR-2450）。这仍然是“不知道上下文的模型读一遍、记账、下次再读一遍”。

实测（2026-11-12）：

- zhushenkongjian 近 7 天：合入成功 505 次，被拒 1143 次；其中规则评审 549、冲突 175、worktree 不干净 135、全量测试 87、缺执行证据 68、`canon check` 67。评审移到合入之后的版本在 13:44 发布，那边最后一次评审拒绝在 13:29；最后一次全量测试拒绝在 11-10。
- 同期去掉评审拒绝后，到下一次合入之前被拒过的有 284 段：1 次 148、2 次 61、3 次及以上 75（约每天 11 个）。这 75 段里的拒绝原因：冲突 114、全量测试 56、不干净 49、缺证据 40、`canon check` 30、超时 9、hook 7、来源 6。
- 同期每天约 72 次合入；main 上每个提交改动的行数中位数 26、九成以下 438，一周共约 46 万行：主 agent 读不过每一次合入。
- 主 agent 关不掉任何意见：`canon verdict record` 不让 agent 用（BR-2254），核实命令（`review_verify`）在用 canon 的项目里一个都没配，意见全部原样记账、一直挂着，只能等下一轮评审复问。
- 认领写明了是谁派的子 agent：`agent:<会话>:<名字>`。

## 方案

1. **合入照旧只等机械检查；合入后评审的意见交给主 agent 当场处理；子 agent 的变更连续被拒三次就停下交给主 agent（采用）**：正常的合入不等任何人，符合 D-89 的“迭代不必百分百、验收兜底”；主 agent 只在两种时候介入：评审报了拦截意见（它知道意图，判断快，要改就通知还带着上下文的子 agent），和子 agent 自己过不去（多半是冲突，正是派活时该错开的事）。判断“不成立”要引一段被点名文档的原文，canon 机械地核对原文确实在文档里，偏向放过的风险由它和验收时逐条有处置兜底。
   - 来源：canon/architecture.md “认领的持有者是会话，子 agent 的名字写在后面”
2. **照 D-89：后台用更强的模型核实、之后逐条复问（否决）**：主 agent 不知道核实了什么，核实的模型每条都要从零读点名的文档，复问又让同一条意见在每次评审后被重读一遍，正是负责人要去掉的“一遍遍重读”。
   - 来源：canon/rules/knowledge/review/findings/BR-2450.md “按编号从小到大逐条复问一次”
3. **子 agent 的合入过了机械检查后等主 agent 评审合并（#33 先选的，否决）**：把每次迭代重新拦在门口，主 agent 在等人回话或跑长命令时所有合入都停着；每天约 72 次合入、一周约 46 万行改动，主 agent 读不过来，读多了上下文被压缩，“主 agent 知道得最多”这个前提也就没了。负责人听过之后改选方案 1（#34）。
   - 来源：canon/decisions/D-89.md “认领、合入队列、main 的比较并交换、冲突检查照旧每次严格”
4. **主 agent 先批准、子 agent 再进队列（否决）**：同方案 3 一样拦门，还会去看之后过不了机械检查的差异。
   - 来源：canon/rules/work/stats/BR-2254.md “执行者以 `agent:` 开头 → 退出码 1，信息写明 agent 的判定不手工记”
5. **连续被拒只在说明里要求子 agent 停下（否决）**：子 agent 被拒后的默认动作就是改了再落地，只写在说明里挡不住第四次、第五次；要在 canon 里硬停。
   - 来源：canon/rules/work/land/BR-2388.md “还有发现 → 不入队，立即以原因 `check`、退出码 1 拒绝”

## 决定

采用方案 1。

- 合入后的规则评审和重复评审照旧在后台运行、不拦合入；拦截意见不再交给核实命令，全部记成未处理的意见，并在 `canon work after-land` 和会话提示里交给主 agent。去掉 `review_verify` 和逐条复问。
- 主 agent 用 `canon finding close` 当场处理每条意见：`--fixed <提交>`（main 上改过意见点名的文档的提交）或 `--spurious "<原文>"`（这段原文逐字在意见点名的某份文档里）。agent 和人都可以用。
- 子 agent 认领的变更，自上次合入（或开工）以来被拒满三次，第四次 `canon work land` 不再排队，信息写明交给主 agent；主会话处理后（指导子 agent、接手或丢掉）用一条命令放行。只数子 agent 能改、或派活时能避免的拒绝（冲突、不干净、`canon check`、缺证据、hook、来源、配置项、发版）；排队超时和环境问题不算。主会话和人自己认领的变更不计数。
- 验收时每条意见都要有处置（D-89）不变。

## 后果

- 主 agent 要处理每条拦截意见；按以往每次被拦约 3.5 条估计，改规则的合入每次几条，读的是意见点名的那几份文档，不是整个规则库。
- 子 agent 被硬停后要停下汇报；canon-parallel 写明这一步和主 agent 的处理方式。
- 判断“不成立”不再要另一个模型同意；`canon stats` 按关闭方式分开数，以后能看出主 agent 放过了多少。
- 分两个变更做：C-494 做意见那一半（交给主 agent、`canon finding close`、去掉核实和复问），之后的变更做连续三次被拒那一半。
