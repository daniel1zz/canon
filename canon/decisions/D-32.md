## 背景

负责人的工作方式是先设计再执行：新项目里先设计好产品、写完整个 baseline（`canon/rules`），再开发，baseline 用来约束执行。负责人对“执行”的定义（2026-11-03，原话）：“本质上就是一次执行啊，记录这次执行验收通过了，如果改了规则或者Baseline,那就把相应baseline的状态改一下，新一轮执行不就可以，我们真正说要去判断是不是完全一致那肯定是要代码分析等等，而不是说有了执行就保证百分百”；并指出“不一定是所有规则都能写成代码的测试”。

现在的 canon 做不到：

- 规则只有生效和作废两种状态（`src/knowledge/documents/types.ts`）。生效的规则没有测试点名它时，`canon check` 报 `rule-untested`（BR-2005）；检查的是整个文档库，任何一条发现都拒绝合入。先写好的 baseline 合不进 main，除非每条都硬写一个 `untested:` 理由，于是“还没做”和“做不了自动测试”混在一起。
- 没有任何地方记录一条规则有没有被执行过、执行之后有没有被改过。已有的：变更的 `rules:` 列出它新增、修改、作废的规则（153 个变更全都写了），`## 任务` 勾选清单，handoff（BR-2025）。
- 测试点名只看标题，`describe` 也算（`src/knowledge/check/test-titles.ts`）；只改规则文字的合入跳过 floor（BR-2164），旧测试仍然点名这条规则。
- `canon/rules` 的 git 历史：200 次新增、343 次修改、83 次移动（`git log --name-status -M`）；独立评审统计修改里约 37% 只改了 2 行以内。

D-1 的数据同时说明两件事：baseline 规则本身有价值（有规则时 agent 20 题答对 16.5 题，没有时 13 题）；而 lore 围绕它的执行记录没有价值（按任务记录的 evidence 调用 6,367 次，coverage 映射写入占 baseline 版本的 81.7%，96% 的“人工判断”是 agent 写的）。

## 方案

1. 保持现状，规则只写已实现的行为。否决：先设计的 baseline 无处可放，负责人的工作方式走不通。
   - 来源：src/knowledge/check/check.ts “has no running test whose title names it”
2. 规划中的规则放在变更里，合入时并进 `canon/rules`（OpenSpec 的做法）。否决：草案不在 `canon/rules`，`canon context` 看不到，别的会话不受它约束，违背“baseline 用来约束执行”；跨变更互相引用的草案编号会被报 `ref-dangling`。
   - 来源：https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md “are the source of truth — they describe how your system currently behaves”
   - 来源：https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md “its deltas merge cleanly into the source of truth”
3. 规划中的规则放在单独目录（`canon/plan/<领域>/`），实现时移进 `canon/rules`。否决：要另维护一套和领域一一对应的目录和 README，`canon context` 要读两处；它也不处理“规则改了要重新执行”。纯移动不触发规则评审这一点它占优。
   - 来源：src/work/land/checks/steps.ts “--find-renames=100%”
4. 不加状态，规则是否实现只看有没有测试点名它。否决：先写代码、忘了写测试的变更不再被拒绝，“没做”和“做了没测”分不开；改规则例子后旧测试仍点名它，会被当成已验证。
   - 来源：src/knowledge/check/test-titles.ts “const CALLS = new Set(["test", "it", "describe"”
5. 规则有规划中状态；变更声明它执行哪些规则，合入时要有证据；通过时记下规则行为部分的哈希，规则改了行为就要重新执行。采用。
   - 来源：src/knowledge/documents/model.ts “Rule ids this change adds, edits or retires”
6. 在方案 5 里按提交先后判断“通过晚于修改”。否决：rebase 会把通过排到别人的修改之后，算成通过了它没见过的文字；搬目录会让所有被搬的规则变成待重新执行。改为比较内容哈希。
7. 只改措辞时由改规则的变更自己声明“行为不变”。否决：这是 agent 自己证明自己，正是 D-1 里 96% 的“人工判断”的情况；改由合入时已有的独立规则审查判断。
8. 要执行的规则只看变更 `rules:` 的声明，漏写靠规则评审发现（C-242 时定下）。否决：C-236 漏写 `rules:` 改了四条规则的 `## 规则`，评审没有拦，四条规则悄悄变成待重新执行（#104）；改为把合入改了行为哈希的规则也算进来，不靠声明。
   - 来源：src/work/execution/evidence.ts “export function executedRules(”

## 决定

规则状态加 `planned`（规划中）：

- 规划中的规则不要求测试，不报 `rule-untested`，缺测试不挡合入（缺 `## 规则` 段或例子照样由 `canon check` 报出，BR-2033、BR-2034）；`canon context`、`canon show` 标明“规划中”。生效的规则照旧必须有测试或 `untested:`。
- 规划中的规则改成生效，必须由一个在 `rules:` 里列出它的变更来做。

一次执行就是一个变更。变更 `rules:` 里列出的规则，凡是合入后是生效的、而且行为哈希没有匹配的通过记录（新的、行为改了的、从没通过的），加 `--finish` 合入时每条都要有证据，缺一条就拒绝：

- 这个变更新增或修改了一个标题点名它的测试；或
- 规则带 `untested:`，变更的 `## 验收` 段里有一行写这条规则：怎么验的、看到了什么。

**没列进 `rules:` 的修改**（实现时定下，C-242，#104）：变更的合入改了行为哈希的规则，没列进 `rules:` 也算这个变更要执行的规则，同样要证据，或者由规则审查判为措辞修改；否则漏写 `rules:` 的变更合入时什么都不查，规则悄悄变成待重新执行（C-236 就是这样）。只移动、内容没变的规则哈希不变，不算。

**行为哈希**：只算 `## 规则` 和 `## 例子` 两段，空白统一后取哈希。标题、背景、README、术语改了不影响状态。

**通过记录**：满足上面条件的规则，canon 在关闭变更的提交里把“规则编号 → 行为哈希、方式（测试 / 验收）”写进变更文件的 front matter。规则的状态由当前行为哈希算出，不靠手动维护的字段：

| 状态 | 判定 |
|---|---|
| 规划中 | `status: planned` |
| 已通过（C-n） | 生效，某个已完成变更的通过记录和当前行为哈希相同 |
| 待 main 测试（C-n） | 生效，有相同的通过记录，但还没有被 main 的测试覆盖（只在先合后测时出现，见下） |
| 待重新执行 | 生效，没有和当前行为哈希相同的通过记录 |

记录的格式见 BR-2237（`passes:` 里 `<规则编号>: "<哈希> <方式>"`，方式是 `test`、`acceptance`、`migration`，审查判定为措辞修改的后面加 `wording`），验收行的格式见 BR-2241（`- BR-n：<怎么验的> → <看到了什么>`）。

**先合后测时的已通过**（实现时定下，C-182）：本决定原先假设 main 上的测试都通过了 floor，但 D-31 的 `floor_timing: after` 下合入不等 floor。所以 `after` 下一条记录只有在 `refs/canon/green`（最近一次后台测试通过的提交）里也有时才算已通过，否则显示“待 main 测试”；`before` 下 main 上每个提交合入前都测过，记录立即算数（BR-2246）。这是最简单的、不会把没测过的提交显示为已通过的判定：只读一个 ref 和那棵树里的变更文件，不另记任何东西。

**只改措辞**：`## 规则` 改了而 `## 例子` 没改时，合入时的规则审查另外判断这次修改是措辞还是行为。判为措辞，沿用上一条通过记录的方式写一条新哈希的记录，注明“审查判定为措辞修改”；判为行为，规则变成待重新执行。`## 例子` 改了一律算行为变了。

审查的判断怎么进关闭提交（实现时定下，C-182）：关闭提交在排队之前做，审查在 rebase 之后才跑，所以关闭提交先按“措辞”写好记录（值后面带 `wording`，BR-2243），审查在同一次合入里确认；审查判为行为、没有回答或没有配置审查命令时，这次合入被拒，关闭提交照常撤回（BR-2239），没确认的记录到不了 main。判断本身另记在这次审查事件的 `wording` 字段里，事后可查。不另存别处，也不在关闭提交之后再改提交，因为合入的必须是检查过的那个提交（BR-2106）。

**执行期间规则被别人改了**：合入 rebase 之后，某条要执行的规则的行为哈希和变更分支上的不同（别人先合入改了它），拒绝合入，提示按新文字重新验证。

**进度**：新命令按领域和按变更列出各种状态（实现时是四种，含先合后测下的“待 main 测试”）的数量和编号（BR-2247）。

**迁移**：现有的生效规则都有会运行的测试；实现这个决定的变更为它们各写一条通过记录，方式注明“迁移：已有测试”（`migration`）。具体做法（实现时定下，C-182，BR-2245）：main 上还没有任何通过记录时，第一个加 `--finish` 合入的变更在关闭提交里为每条有会运行的测试点名的生效规则写迁移记录；之后再写迁移记录会被拒。别的项目升级后也一样只迁移一次。先合后测时迁移记录同样要等 main 的测试通过才算已通过。

带 `untested:`、没有测试的生效规则（canon 自己没有，别的项目可能有）不写迁移记录，迁移后是待重新执行：迁移时没有人验证过它，写成通过就是没验证的“通过”；某个变更在 `rules:` 里列出它、在 `## 验收` 写一行之后才算通过。

不宣称规则和代码完全一致：通过只说明那一次执行验证过。

P1 和 P5 的表述按负责人确认的写法修改（见 `canon/product.md`）。

## 后果

- 新的拒绝有两种：`--finish` 时要执行的规则缺证据（声明在 `rules:` 里的，以及合入改了行为哈希、没声明的）；rebase 后要执行的规则被别人改了。两种都在事件表里记原因，误拒多就调整（P6）。
- 只改规则错别字不增加工作；改了例子就要动测试，这是有意的：例子就是测试要验证的东西。
- 验收记录只给 `untested:` 的规则用，每次执行一行；目前 canon 自己没有这类规则，它的效果要等新项目试运行时才有数据。
- D-12 的测试覆盖怎么算不变：`canon check` 仍然只认会运行的测试标题（BR-2005），验收记录不让任何规则算作“有测试”，只在 `--finish` 时作为带 `untested:` 的规则的执行证据，所以不需要把 D-12 列进 `amends:`。
- 规则评审要多输出一个判断（措辞还是行为），评审出错时，通过记录里的“审查判定为措辞修改”可以事后查。
- 修改 D-1 里“验收就是测试”：能测试的规则仍然只认测试，写不成测试的规则可以用验收记录。
