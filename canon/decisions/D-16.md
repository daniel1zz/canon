---
id: D-16
title: main 只能通过 canon work land 移动：用 reference-transaction hook 拦住其他移动
status: accepted
---

## 背景

D-1 定下 canon 只在两个边界检查结果，其中一个是合入 main（rebase、floor、`canon check`、规则评审、main 的比较并交换）。但到 C-89 为止，这个边界只对走 `canon work land` 的人生效：在主 checkout 里 `git commit`、`git merge`、`git update-ref`、`git push . x:main` 都能直接移动 main，完全绕过 floor、检查和评审。

lore ADR-052（`~/Projects/zz/lore/docs/requirements/adr/ADR-052-*.md`，git 2.50.1 实测）记下的事实：E3，main 在另一个 checkout 里签出时，`git update-ref refs/heads/main NEW OLD` 照样成功、没有警告，那个 checkout 随后把反向的改动显示为已暂存；E7，`prepared` 状态下拒绝 `refs/heads/main` 的 `reference-transaction` hook 能拦住普通的 `update-ref` 和在 main 上的 `git commit`（`fatal: ref updates aborted by hook`），带标记的 `update-ref` 放行，并且 hook 必须忽略新旧值相同的行，因为 `git reset` 会产生这样的行。

C-89 在本机（git 2.50.1，Apple Git-155）的临时仓库里重新测了一遍，结果记在 `canon/changes/C-89.md`。另外测到：`git pack-refs --all` 会先在 packed-refs 里写一行新值等于当前值的 main，再删掉松散副本（新值全零），所以“删除”和“不动”都必须放行；`git commit --no-verify` 仍被拒绝；`git -c core.hooksPath=/dev/null` 能绕过它。

## 方案

1. 不加守卫，靠工作说明（`canon brief` 输出的 WORKFLOW_GUIDE）提醒 agent 走 `canon work land`：否决。说明只是提示，漏掉了没有任何东西会发现；而直接改 main 正是合入这个边界要挡住的结果。
   - 来源：canon/product.md “Canon 只在两个边界检查结果：协调状态写入时，和合入 main 时。”
2. canon 装一个 `reference-transaction` hook，在 `prepared` 状态拒绝让 main 指向新提交的更新，只放行 `canon work land` 用环境变量点名的那个提交：采用。git 的每一种 ref 更新（commit、merge、update-ref、push、pull、reset）都经过它，非 0 退出会中止整个更新。
   - 来源：https://git-scm.com/docs/githooks “This hook is invoked by any Git command that performs reference updates.”
   - 来源：https://git-scm.com/docs/githooks “In these states, a non-zero exit status will cause the transaction to be aborted.”
3. 只靠远端的分支保护（服务器端 hook 或托管平台的 protected branch）：否决。canon 是本地优先的，没有远端也要能用，协调状态也只支持单机；本地直接移动 main 时远端根本不知道。
   - 来源：canon/decisions/D-1.md “同一个 checkout 的所有 worktree 共用。只支持单机。”
4. 用 pre-commit hook：否决。它只在 `git commit` 时运行，`--no-verify` 就能跳过，也拦不住 `update-ref`、`merge` 的快进和 `push`。
   - 来源：https://git-scm.com/docs/githooks “can be bypassed with the --no-verify option”

## 决定

canon 的安装（`canon init`、`canon install`、`canon update`）把一个带标识行的 `reference-transaction` hook 写进 `git rev-parse --git-path hooks` 给出的目录（BR-2123）；已有别人的同名 hook 时不覆盖，拒绝并写明路径（BR-2124）。hook 只看 `refs/heads/<main>`，放行删除、不动的行、main 还不存在、main 上还没有 `canon/config.yaml` 这几种情况，其余要求 `CANON_LAND_MAIN` 等于新值（BR-2126）。`canon work land` 只在它自己移动 main 的那条 git 命令里设置这个变量（BR-2125）。

这是 D-1 里“合入 main”这个边界的执行，不是检查 agent 怎么干活：它不管 agent 在自己的 worktree 里做什么，只管结果有没有经过合入。

## 后果

- 在主 checkout 里直接提交、合并、`git pull` 远端的 main 都会被拒绝。要同步远端的 main，或人确实要直接改 main，需要人自己决定绕过（例如 `git -c core.hooksPath=/dev/null pull`）；hook 的拒绝提示不写绕过办法，只指向 `canon work land`。
- 它挡的是失误和抄近路，不是安全边界：能改 `core.hooksPath` 或删掉 hook 文件的人都能绕过。
- 较老的 git 没有 `reference-transaction` hook（lore ADR-052 记为 2.28 之前；C-89 没有在旧版本上核实），在那里它不运行，canon 也不会发现。
- hook 文件不在仓库的提交里，每个 clone 都要运行一次 `canon install` 或 `canon update`；`canon brief` 和 `canon work start` 会按 BR-2085 提示它缺少。
- 测试里要在 main 上直接造提交时，需要先 `git commit-tree`，再带着 `CANON_LAND_MAIN=<新提交>` 执行 `git update-ref`。
