---
id: D-41
title: 每个变更的端口记在协调数据库里，从配置的范围里取最小的空闲值
status: accepted
---

## 背景

C-103：用 canon 的项目里，几个变更的 worktree 同时启动开发服务器、数据库这类本地服务时会抢同一个端口。要给 `setup` 和每条 hook 命令一个 `CANON_PORT`，在配置的范围（例如 `ports: 4100-4199`）里分配，同一个变更每次拿到同一个值，两个进行中的变更不会拿到同一个值。要回答的问题：值从哪里来；什么时候算“不再进行中”、端口可以给别的变更；范围用完时怎么办。

外部做法（2026-11-04 核对过原文）：

- uzi 在配置里写 `portRange`，每启动一个 agent 就从范围开头往后找：跳过本次已经分出去的，再试着监听这个端口，能监听的就用，并把它记进 uzi 的状态文件。值不是按编号算的，同一个 agent 下次不保证拿到同一个值。另外 uzi 是把 `devCommand` 里的 `$PORT` 文字替换掉，不是设环境变量。
- Conductor 给每个本地 workspace 分一段 10 个端口，`CONDUCTOR_PORT` 是这一段的第一个，脚本和终端都能读到。

canon 已有的条件：协调数据库（`<git 公共目录>/canon/state.db`）所有 worktree 共用，编号就是在里面用一个写事务分配的（`CoordDb.allocate`），并发的 `canon work start` 不会拿到同一个编号（BR-2132）。变更的 worktree 在 `canon work clean`、`canon work drop` 之前一直在；停下（`canon work stop`）会释放认领，但 worktree 不动，之后同一个变更还会再开始。

## 方案

1. 按变更编号算：`起 + (编号 mod 范围大小)`，不存任何东西。否决：范围有 100 个端口时 C-3 和 C-103 拿到同一个值，违反“两个进行中的变更不会拿到同一个值”；要避免只能把范围设得比编号还大，项目做久了编号总会超过。
   - 来源：src/work/db.ts “allocate(prefix: string, floor: number, actor: string): string”
2. 记在协调数据库里：变更第一次需要端口时，在一个写事务里取范围里没被进行中的变更占着的最小值，记下（变更、端口、worktree 路径）；以后同一个变更直接读记录。记录的 worktree 已经不在了（清理或放弃之后），这个端口就可以给别的变更。采用：分配和编号一样在一个写事务里完成，并发也不会重复；同一个变更停下再开始仍是同一个值；不需要探测端口。
   - 来源：src/work/db.ts “return tx.immediate();”
3. 像 uzi 那样每次运行时探测：从范围开头找第一个能监听的端口。否决：变更自己的开发服务器正占着它的端口时，下一次探测会跳过它、换一个值，做不到“同一个变更每次拿到同一个值”；探测和真正启动服务之间还有空档，两个变更可能探到同一个空端口。
   - 来源：https://raw.githubusercontent.com/devflowinc/uzi/main/cmd/prompt/prompt.go “findAvailablePort finds the first available port in the given range, excluding already assigned ports”
   - 来源：https://raw.githubusercontent.com/devflowinc/uzi/main/README.md “The range of ports Uzi can use for development servers”
4. 像 Conductor 那样每个变更分一段（例如 10 个），`CANON_PORT` 是第一个。否决（这次不做）：C-103 要的是每个变更一个端口；分段让同样的范围能同时开的变更少到十分之一；要几个端口的项目可以把范围设大，以后真有需要再加段长的配置。
   - 来源：https://www.conductor.build/docs/reference/environment-variables “First port in a range of 10 ports assigned to a local workspace”

“不再进行中”的判断另有两种做法：按认领（停下就释放）——否决，停下再开始会换端口；按变更文件的状态（关闭就释放）——否决，合入后到清理之前 worktree 里的服务可能还开着，而且要读 main 的文件。按记录的 worktree 还在不在判断，和服务实际可能还在运行的时间一致。

## 决定

采用方案 2。`ports` 配置写成 `起-止`（含两端，都在 1 到 65535 之间，起不大于止）；不写时不分配，`CANON_PORT` 是空字符串。端口记在协调数据库的 `ports` 表（每个端口一行，变更编号唯一），在写事务里分配：先找这个变更的记录，在范围内就用它；不在（范围改过）就删掉重分；没有记录时，把记录的 worktree 已经不存在的行删掉，再取最小的空闲值。范围里的端口都被占着时 fail loud：`canon work start` 被拒（退出码 5，撤回刚建的 worktree、释放认领，信息列出占着端口的变更），hook 这次当作失败（`before_land` 因此拒绝合入，其他事件结果不变）。`canon work start` 在建好 worktree、跑 `setup` 之前分配并记下 worktree 路径；hook 时还没有记录的变更（`ports` 配置之前开始的）按约定的 worktree 路径（`<worktrees 目录>/<变更编号>`）分配。没有变更的事件（`after_green`）`CANON_PORT` 是空字符串。

## 后果

- 新增配置键 `ports`（config 领域，`src/config/config-keys.ts`）和规则 BR-2267、BR-2268、BR-2269。按 BR-2248，本仓库要用它得在之后另一次合入里写进 `canon/config.yaml`；canon 自己是命令行工具，暂时用不上。
- 端口记录只在 worktree 不在之后、下一次分配时才回收；worktree 留着不清理的变更会一直占着端口。范围要按同时开的 worktree 数设，留出余量。
- 只保证 canon 分给变更的端口互不相同，不保证这个端口没被 canon 以外的程序占着；范围应选机器上没有别的服务用的一段。
- 一起测（D-26）时批的临时 worktree 里跑的 `setup` 不属于任何一个变更，canon 不给它设 `CANON_PORT`（那段代码属于 `work/land`，这次不改）。
