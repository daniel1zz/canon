## 背景

D-35 定了 `canon verdict pending` / `record`：由“没参与这个变更的执行者”对照拦截前后的提交，给一次评审拦截判 `real` 或 `wording`，按判定者是 agent 还是人分开统计。2026-11-04 的独立评审指出了几处缺口，负责人当天选择按评审重做（选项“D-35、D-43、D-40 一并重做”）。逐条核对的结果：

- **“作者不能判”挡不住作者。** 作者检查是拿执行者名字做字符串比较，执行者名字来自 `CANON_ACTOR` 或会话 id（BR-2023）。实测：本会话（`agent:3d606482`）执行 `canon verdict pending` 列出 6 次拦截；同一个会话设 `CANON_ACTOR=agent:zzzz` 后列出全部 38 次，包括它自己写的变更。
- **agent 和人的区分只看 `CLAUDECODE=1`。** 实测：去掉 `CLAUDECODE` 后执行者是 `human:apple`。所以不在 Claude Code 里跑的 agent（例如本机装着的 Codex CLI）记下的判定会算成人的，D-35 想用“人的判定校准 agent 的判定”就不成立。
- **canon 的身份模型本来就不防冒充。** D-18 定了排他靠 worktree、执行者只到会话一级，并写明 canon 面对的是互相配合的 agent；BR-2023 让 `CANON_ACTOR` 优先。所以 canon 能保证的只有：在 Claude Code 会话里不能把自己记成 `human:`。它保证不了“这个执行者没参与过这个变更”，也保证不了“不在 Claude Code 里的执行者是人”。
- **一次拦截通常不止一条意见。** 事件表里 36 条 `review.block`，33 条有不止一条意见（`detail.findings` 是数组；去掉以“建议（不拦截）”开头的意见后仍有 31 条不止一条）。每次拦截只记一个 `real|wording`，记不下“第 1 条是真问题、第 2 条不是”，而评审准不准正是要按每条意见来看。
- **判定者先看到了修复。** D-35 给判定者拦截时的提交、合入的提交和评审的拦截信息，判定者是在知道作者怎么改之后再判断“当时有没有问题”，这是事后偏差。
- **引用的论文支持的比 D-35 写的少。** arXiv 2306.05685 测的是聊天助手回答的两两偏好（MT-Bench、Chatbot Arena），不是代码或规则里的缺陷是否真实存在，“80% 以上一致”不能搬过来；它点名的自我偏好（self-enhancement）偏差在这里也没有缓解：评审、作者、判定者都是同一类模型，D-35 只靠“不同会话”分开。
- 还有一处小事：D-35 写“main 只靠合入前移”，D-38 让 `canon sync` 也能前移 main。这只影响没有 `base` 的合入（事件 3063 之前的），那时还没有 `canon sync`，所以那个回退办法仍然成立，但理由要写成“这些合入发生在 `canon sync` 出现之前”。
- 到 2026-11-04 事件表里还没有任何 `review.verdict`，换掉事件格式不用迁移旧数据。

2026-11-04 同一天的第二次评审（D-49 与 D-57）又发现：事件表里有 45 条 `review.block`、0 条 `review.verdict`，也就是还没有任何真实使用；而 `canon verdict run` 加上它的提示、解析、进程管理和测试已经写完。负责人看了评审后选择了“缩小：去掉自动判定 (推荐)”。所以本决定改成只保留手工记，自动判定作为暂不采用的选项记下来。

评审还指出，原来按指纹在合入范围里找“拦截时的提交”不可靠：合入流程会把变更 rebase 到 main，作者修完再合入时又 rebase 一次，指纹相同的提交的树是第二次合入时的 main 加变更，不是评审看到的代码。更简单也更准的做法是拦截时就把评审看到的提交记在事件里。

问题是：判定的单位是什么、判定记什么、评审看到的提交从哪里来、canon 对“谁判的”能写下什么样的保证。

## 方案

1. 保留 D-35，只把作者检查从执行者名字换成 worktree（BR-2131：每条事件记着运行它的 worktree），在变更自己的 worktree 里写过事件的就算作者。否决：worktree 也是执行者自己选的，作者只要在主 checkout 或别的目录里执行判定就绕过了；它和执行者名字一样只防得住无心之失，不防冒充，换了一个字段不改变 canon 能保证什么。
   - 来源：canon/decisions/D-18.md “canon 面对的是互相配合的 agent，不需要防冒充”
2. 保留 D-35 的做法和数据，只在报告里加一句“判定者身份未核实”。否决：说清了限制，但判定仍然按一次拦截记一个结论，一次拦截通常有好几条意见，记不下哪条是真问题。
   - 来源：canon/rules/work/BR-2023.md “去掉首尾空白后有值时用它”
3. 按每条意见手工记判定，记成 `human`、自报；拦截事件直接记评审看到的提交。采用。
   - 按每条意见判，因为评审的结论本来就是一组意见。
   - 来源：src/knowledge/review/review.ts “List every blocking defect you find, not only the first”
4. 由 canon 运行判定命令（`canon verdict run`），把拦截时的代码树导出到没有 `.git` 的目录，让项目的 `review` 命令给每条意见一个 `model` 判定。暂不采用：到 2026-11-04 事件表里有 45 条拦截、0 条判定，没有真实使用；花费没有量过；评审指出它还带着需要另行解决的问题（判定命令没有超时、同一个模型评自己写的意见）。等负责人手工判过一批、看过结论之后再重新考虑；到那时按当时的数据重新设计，不沿用已写的实现。
5. 每次拦截之后自动判定（在合入流程里跑判定命令）。暂不采用，理由同方案 4，而且花多少 token 要负责人先决定。
6. 继续用一个结论判整次拦截（`real|wording`）。否决：一次拦截通常不止一条意见，一个结论判不出哪条是真问题。

## 决定

采用方案 3，方案 4、5 暂不采用：

- 判定的单位是一条意见：`review.block` 事件 `detail.findings` 里的一项，从 1 编号。`review.block` 事件另记 `commit`：评审那一刻变更的 `HEAD`，也就是评审看到的提交（BR-2253）。只判已经合入的变更的拦截（拦截之后有原因为 `review` 的 `land.refuse`，再之后有 `land.ok`），并且事件记了 `commit`。没有 `commit` 的旧拦截不可判定：不列出，也不算进统计的分母。
- `canon verdict pending` 按拦截列出每条意见和它已有的判定，只写评审看到的提交，不写合入的提交。每条意见有一条判定（`model` 或 `human`）这次拦截就算判完，所以手工记完就能清空列表（BR-2253）。
- `canon verdict record <拦截事件编号> <意见编号> real|spurious|unclear --reason "..."` 记一条 `judge: human` 的判定；Claude Code 会话里的执行者（`agent:`）不能用（BR-2254）。
- `canon stats` 按 `model` 和 `human` 分开报告每条意见的判定，分母只算可判定的拦截；`real` 和 `spurious` 合计不到 10 个时不给比例，并写明 `human` 是自报的（BR-2255）。
- 没有任何地方自动判定。

## 后果

- `review.verdict` 的格式是每条意见一条：`block`、`refusal`、`finding`、`verdict`、`judge`、`reason`、`before`。D-35 的格式没有写进任何事件，不用迁移。`canon verdict run` 和 BR-2290 去掉，事件表里没有它写过的事件。
- canon 写下的“谁判的”只有它能保证的部分：`human` 的判定是自称的，不在 Claude Code 里跑的 agent 也会记成 `human`（D-54）；`record` 只拒绝 Claude Code 会话里的执行者。
- 已知限制：评审给的 `findings` 里，拦住合入的意见和不拦截的建议混在同一个数组里，canon 分不出，所以 `pending` 两种都列，判的人自己跳过建议；统计的意见数里也含这些建议，`spurious` 的比例因此不能直接当成“评审拦得对不对”。等手工判过一批、重新考虑自动判定时，再决定要不要让评审把两者分开输出。
- 已知限制：拦截事件没有记 `commit` 的旧拦截（45 条里写这个字段之前的全部）不可判定，只能用 `canon verdict record` 直接记，统计里不算。
- 最少样本沿用 D-35 的思路：`model` 和 `human` 各自 `real` 加 `spurious` 不到 10 个时不报比例；到 `review` 的复审日期（`check_reviews`），如果手工判定还是 0 个，就停止这个办法。这一条没有程序强制，复审时对照 `canon stats` 的数字判断。
