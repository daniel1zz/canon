## 背景

D-35 定了 `canon verdict pending` / `record`：由“没参与这个变更的执行者”对照拦截前后的提交，给一次评审拦截判 `real` 或 `wording`，按判定者是 agent 还是人分开统计。2026-11-04 的独立评审指出了几处缺口，负责人当天选择按评审重做（选项“D-35、D-43、D-40 一并重做”）。逐条核对的结果：

- **“作者不能判”挡不住作者。** 作者检查是拿执行者名字做字符串比较，执行者名字来自 `CANON_ACTOR` 或会话 id（BR-2023）。实测：本会话（`agent:3d606482`）执行 `canon verdict pending` 列出 6 次拦截；同一个会话设 `CANON_ACTOR=agent:zzzz` 后列出全部 38 次，包括它自己写的变更。
- **agent 和人的区分只看 `CLAUDECODE=1`。** 实测：去掉 `CLAUDECODE` 后执行者是 `human:apple`。所以不在 Claude Code 里跑的 agent（例如本机装着的 Codex CLI）记下的判定会算成人的，D-35 想用“人的判定校准 agent 的判定”就不成立。
- **canon 的身份模型本来就不防冒充。** D-18 定了排他靠 worktree、执行者只到会话一级，并写明 canon 面对的是互相配合的 agent；BR-2023 让 `CANON_ACTOR` 优先。所以 canon 能保证的只有：在 Claude Code 会话里不能把自己记成 `human:`。它保证不了“这个执行者没参与过这个变更”，也保证不了“不在 Claude Code 里的执行者是人”。
- **一次拦截通常不止一条意见。** 事件表里 36 条 `review.block`，33 条有不止一条意见（`detail.findings` 是数组；去掉以“建议（不拦截）”开头的意见后仍有 31 条不止一条）。每次拦截只记一个 `real|wording`，记不下“第 1 条是真问题、第 2 条不是”，而评审准不准正是要按每条意见来看。
- **判定者先看到了修复。** D-35 给判定者拦截时的提交、合入的提交和评审的拦截信息，判定者是在知道作者怎么改之后再判断“当时有没有问题”，这是事后偏差。
- **引用的论文支持的比 D-35 写的少。** arXiv 2306.05685 测的是聊天助手回答的两两偏好（MT-Bench、Chatbot Arena），不是代码或规则里的缺陷是否真实存在，“80% 以上一致”不能搬过来；它点名的自我偏好（self-enhancement）偏差在这里也没有缓解：评审、作者、判定者都是同一类模型，D-35 只靠“不同会话”分开。
- 还有一处小事：D-35 写“main 只靠合入前移”，D-38 让 `canon sync` 也能前移 main。这只影响没有 `base` 的合入（事件 3063 之前的），那时还没有 `canon sync`，所以那个回退办法仍然成立，但理由要写成“这些合入发生在 `canon sync` 出现之前”。
- 到 2026-11-04 事件表里还没有任何 `review.verdict`，换掉事件格式不用迁移旧数据。

问题是：判定的单位是什么、谁来判、判定者看到什么、canon 对“谁判的”能写下什么样的保证。

## 方案

1. 保留 D-35，只把作者检查从执行者名字换成 worktree（BR-2131：每条事件记着运行它的 worktree），在变更自己的 worktree 里写过事件的就算作者。否决：worktree 也是执行者自己选的，作者只要在主 checkout 或别的目录里执行判定就绕过了；它和执行者名字一样只防得住无心之失，不防冒充，换了一个字段不改变 canon 能保证什么。
   - 来源：canon/decisions/D-18.md “canon 面对的是互相配合的 agent，不需要防冒充”
2. 保留 D-35 的做法和数据，只在报告里加一句“判定者身份未核实”。否决：说清了限制，但 agent 的判定仍然由能看到修复的执行者手工填，作者能给自己判；一条拦截一个结论的问题也没解决。
   - 来源：canon/rules/work/BR-2023.md “去掉首尾空白后有值时用它”
3. agent 的判定不再由 agent 手工记，而是由 canon 自己运行判定命令做出：`canon verdict run` 把拦截时那个提交的代码树导出到一个没有 `.git` 的临时目录，在那里运行项目配置的 `review` 命令，提示里只有这次拦截的每条意见和那个提交改了哪些文件，不给修复、不给合入的提交、不给之后的历史；命令对每条意见回答 `real`、`spurious` 或 `unclear`，canon 照原样记下，判定者记成 `model` 和所用的命令。人仍然用 `canon verdict record` 手工记，按每条意见记，记成 `human`，报告写明这是自报的：canon 只知道它不是在 Claude Code 会话里记的。Claude Code 会话里的执行者不能用 `record`。采用。
   - 理由：这样“判定者没参与这个变更”由构造保证，而不是靠执行者名字：判定命令是 canon 启动的新进程，拿到的只有 canon 给的那些内容，作者的对话和修复都不在里面。canon 能写下的保证正好是它做到的：`model` 的判定是哪个命令、看了哪个提交做出的；`human` 的判定是谁自称做的。
   - 判定者只看拦截时的代码和意见，不看修复，是为了避开事后偏差：知道了结果的人会把当时的情况看得和结果更一致。这项研究的对象是人，对模型有没有同样的效应没有找到直接的研究；不给修复至少拿掉了这个可能的来源。
   - 来源：https://www.ebi.ac.uk/europepmc/webservices/rest/search?query=EXT_ID:39913490%20AND%20SRC:MED&resultType=core&format=json “Hindsight bias arises when people do not realize how extensively observing an event has changed their perception of the world”
   - 按每条意见判，因为评审的结论本来就是一组意见。
   - 来源：src/work/land/checks/steps.ts “findings: v.value.findings”
   - 模型判定有已知的偏差，所以 `model` 和 `human` 的结论从不相加；这篇论文测的是聊天回答的偏好，只用来说明这些偏差存在，不用来说明模型判定和人一致。判定命令默认就是评审用的命令，同一类模型的自我偏好偏差没有缓解，只能靠负责人另配一个不同的模型命令（见“需要负责人决定”）。
   - 来源：https://arxiv.org/abs/2306.05685 “including position, verbosity, and self-enhancement biases, as well as limited reasoning ability”
   - 来源：https://arxiv.org/abs/2306.05685 “Evaluating large language model (LLM) based chat assistants is challenging”
4. 盲判定换成另一种：判定者只看拦截时的代码、不看评审的意见，自己找问题，再和评审的意见对照。否决：这是再跑一次评审，D-35 已经以“和被判定的对象是同一类判断”否决过；而且对照两组自由文字的意见是否“指的是同一个问题”又要一次判断。现在的问题是“这条意见说的问题在当时的代码里存不存在”，给判定者看意见是必须的。
5. 每次拦截之后自动判定（在合入流程里跑判定命令）。否决作为本决定的一部分：多久判一次、花多少 token 要负责人决定（见“需要负责人决定”），这里只做命令。
6. 继续用一个结论判整次拦截（`real|wording`）。否决：36 次拦截里 33 次不止一条意见，一个结论判不出哪条是真问题。

## 决定

采用方案 3：

- 判定的单位是一条意见：`review.block` 事件 `detail.findings` 里的一项，从 1 开始编号。只判已经合入的变更的拦截（拦截之后有原因为 `review` 的 `land.refuse`，再之后有 `land.ok`）。拦截时的提交仍按 D-35 的办法用指纹在合入的范围里找（BR-2253）；没有 `base` 的合入用前一条 `land.ok` 的 `sha`，这些合入都在 `canon sync`（D-38）出现之前，那时 main 只靠合入前移。
- `canon verdict pending` 按拦截列出每条意见和它已有的 `model`、`human` 判定，只写拦截时的提交，不写合入的提交（BR-2253）。
- `canon verdict run --limit <n>` 取最早的 `n` 个还没有 `model` 判定、找得到拦截时提交的拦截，每个运行一次判定命令（项目配置的 `review`），把每条意见的结论记成 `judge: model` 的 `review.verdict`；`--dry-run` 只列出要判的拦截和每个提示的字符数，不运行命令、不写事件（新规则）。
- `canon verdict record <拦截事件编号> <意见编号> real|spurious|unclear --reason "..."` 记一条 `judge: human` 的判定；Claude Code 会话里的执行者（`agent:`）不能用（BR-2254）。
- `canon stats` 按 `model` 和 `human` 分开报告每条意见的判定，`real` 和 `spurious` 合计不到 10 个时不给比例，并写明 `human` 是自报的（BR-2255）。

## 需要负责人决定

判定多久做一次、每次花多少 token：在负责人决定之前，canon 不自动运行任何判定，只有命令。2026-11-04 用 `canon verdict run --limit 50 --dry-run` 量过真实数据的提示大小（结果写在 C-255）；判定命令还会读导出目录里的文件，读多少没有量过，所以实际 token 要以第一次运行为准。

- 选项 A：手工分批。待判的拦截攒到 10 个时，有人执行一次 `canon verdict run --limit 10`。花费可控、每批都能被人看到；代价是没人想起来就不判。
- 选项 B：每周一次，每次上限 N 个拦截（例如 10），由一个定时任务执行。花费有上限、不用人记；代价是要搭定时任务，每周的花费即使没人看也会发生。
- 选项 C：每次评审拦截之后（例如 `after_land` hook）判一次。数据最及时；代价是花费跟着拦截次数涨，而且判定命令和评审在同一时间跑同一类模型。
- 推荐 A：现在 36 次拦截、0 个判定，先手工判一批 10 个，看一次判定实际花多少 token、结论和人的判断是否一致，再决定要不要换成 B。还要决定的一件事：判定命令要不要换成和评审不同的模型（例如另配一个 Codex 命令），以减少同一类模型的自我偏好偏差；不换就沿用 `review`。

## 后果

- `review.verdict` 的格式换成每条意见一条：`block`、`refusal`、`finding`、`verdict`、`judge`、`reason`、`before`，`model` 的还有 `command`。D-35 的格式没有写进任何事件，不用迁移。
- canon 写下的“谁判的”只有它能保证的部分：`model` 的判定是哪个命令看着哪个提交做出的；`human` 的判定是自称的，不在 Claude Code 里跑的 agent 也会记成 `human`。报告里写明这一点。
- 已知限制（D-54）：不在 Claude Code 里的 agent 记下的 `human` 判定、`CANON_ACTOR` 设成 `human:` 的 agent，canon 都认不出；所以不再检查“判定者没参与过这个变更”，`human` 一律写明自报。
- 判定命令看不到修复，靠的是它的工作目录里只有导出的代码树、提示里没有修复；它如果自己去读别的路径，canon 挡不住（判定命令由项目配置，和评审命令一样受信任）。
- 找不到拦截时提交（指纹加入之前、压成一个提交、rebase 时改了内容）的拦截不能盲判，`canon verdict run` 跳过并报个数；人仍然可以手工记。
- 最少样本和放弃标准沿用 D-35 的思路：`model` 和 `human` 各自 `real` 加 `spurious` 不到 10 个时不报比例；到 `review` 的复审日期（`check_reviews`），如果 `model` 判定不到 10 个就停止这个办法；人和 `model` 判过的同一批意见有 10 个以上时，结论不一致超过 3 个就不再采用 `model` 的判定。这两条目前没有程序强制，复审时对照 `canon stats` 的数字判断。
