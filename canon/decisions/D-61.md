id: D-61
title: 版本（release）：版本文档、规则的 release 标签、状态进度和发布快照
status: accepted
---

## 背景

负责人按版本逐步开发：先做 MVP，再做 v1、v2，而且版本是提前规划好的（2026-11-05）。D-32 已经让规则可以先写成规划中，每条生效规则的状态由行为哈希算出，P1 要的“当前真相”因此是 `canon/rules` 这一份。现在缺四样东西：

- 规则属于哪个版本：规划中的规则一大堆，看不出哪些是 MVP、哪些是 v1。
- 每个版本自己的记录：目标、用户、范围、不做什么、成功标准。这是版本的 PRD，现在没有地方放。笔记（`N-n`）没有状态，而版本有“规划中、进行中、已发布”。
- 发布时的快照：发布之后别人改了范围，要查得出“当时发的是什么”。
- 进度：一个版本的规则有几条已通过、几条还没做，一眼看出能不能发。

约束：规则、决策、变更都是 `canon/` 下的文件，由 `canon check` 在合入时检查（P5）；人只做留给人的决定（P7），“这个版本能发了”是方向，所以要负责人确认；canon 自己约 450 条规则不需要补标版本。

## 方案

1. 版本文档 `R-n`（`canon/releases/R-n.md`，带状态）加规则上的可选标签 `release:`、状态进度命令和发布快照（提交号加 git tag）：采用。基线还是 `canon/rules` 一份（P1）；版本文档有状态和固定的几节，`canon check` 能检查引用和发布后不许改的部分；进度由已有的执行状态算出，不另存一份。
   - 来源：canon/product.md “规划中的规则标明还没做，不冒充已实现。”
2. 版本 PRD 写成笔记，规则上只加标签：否决。笔记没有状态，所以“规划中、进行中、已发布”没处放，发布后不许改范围也没法检查；笔记是调研和证据的地方，把版本范围混进去会让两种文档的读者互相找不到。
   - 来源：src/knowledge/documents/types.ts “statuses: undefined, defaultStatus: undefined”
3. 每个版本复制一份 baseline（`canon/rules` 的带版本副本）：否决。同一条规则会有几份文字，哪份是当前真相要靠人判断，违背 P1；规则评审、`canon context`、测试点名都要按版本各做一遍。
   - 来源：canon/product.md “任何时候，AI 都能从一个地方”
4. 只用 git tag 标版本：否决。tag 只指向一个提交，不带目标、范围、不做什么，也没有规划中的状态；版本还没发时 tag 不存在，规划无处放。tag 只作为发布时的便利标记。
   - 来源：src/work/watch/watch.ts “export const GREEN_REF = "refs/canon/green";”
5. 用外部跟踪器的里程碑（GitHub milestone 等）：否决。会话读不到它，`canon check` 也检查不了；产品明确不做网页界面，信息放在仓库文件里，人和 AI 读的是同一份。
   - 来源：canon/product.md “网页 dashboard 或 HTTP API：人直接看仓库里或 GitHub 上的文件”

## 决定

**版本文档。** 新的内置文档类型 `release`，编号 `R-n`，文件 `canon/releases/R-n.md`，状态 `planned`（默认）、`active`、`shipped`。front matter 除了 `id`、`title`、`status`，还有只由 `canon release ship` 写入的 `shipped_at`（发布时 main 的提交号）。必有的节：目标、用户、范围、不做、成功标准、故事地图切片。`canon release new --title` 分配编号并写模板，和 `canon decision new` 一样。

为什么不用 `types:` 声明：声明出来的类型没有 `shipped_at` 这种只能由命令写的字段，没有 `canon release` 命令，也没有“发布后范围不许改”的检查；这三样都要 canon 自己的代码，所以做成内置类型，和决策、笔记并列。副作用：别的项目如果已经声明了前缀 `R` 或目录 `releases` 的类型，升级后会和内置类型冲突，`canon` 会报配置错误，要改名。

**规则的标签。** 规则 front matter 可选 `release: R-n`：引入这条行为的版本；版本发布后不再改。之后的版本改了这条规则的行为，加 `changed_in: [R-m]`。没写 `release:` 的规则不属于任何版本，不要求补标。`changed_in` 必须和 `release:` 一起写，里面的每个版本都必须晚于 `release:`（编号按数值比较）：`R-2` 可以改 `R-1` 的规则，`R-1` 不能自己改自己，也不能被更早的版本改（BR-2322）。`release:` 和 `changed_in` 不进行为哈希（D-32），改标签不影响规则的执行状态。未发布版本里的规划中规则可以改 `release:` 挪到别的版本。

**检查（`canon check`）。**

- `release:`、`changed_in` 必须指向存在的版本文档：不存在报 `ref-dangling`（前缀 `R` 只属于版本，存在的就是版本）。
- 状态是 `shipped` 的版本必须有 `shipped_at`（完整提交号），别的状态不许有。
- 已发布版本的“目标”“范围”“不做”三节，和 `shipped_at` 那个提交里的同名三节（空白统一后）必须一样，不一样报 `release-frozen`。用 `shipped_at` 的提交里的内容当基准，不用另存副本。
- 已发布版本的规则标签不许变：`shipped_at` 的提交里标着这个版本、现在还在的规则，现在必须仍然标着它；`shipped_at` 之后新增或新标的规则不许标这个版本（后面的版本改它，写 `changed_in`）。违反报 `release-frozen`。
- 版本文档的评审：合入改了 `canon/releases` 下的文件，和改了规则、决策一样交给规则评审（BR-2009）；评审的提示里，对每个改动的版本和每条带标签的改动规则，给出这个版本的全文和标着它的规则，评审可以拦下“标 `R-1` 的规则做了 `R-1` 的“不做”里排除的事”这类矛盾。

**状态进度。** `canon release status [R-n]`：每个版本里标着它的规则按 D-32 的状态分组（已通过、待 main 测试、待重新执行、规划中），给出数量；已发布版本里写了 `changed_in` 的规则单独列为“发布后又改了”。不给编号时每个版本一行汇总。`--json` 给同样的内容。状态的算法复用 `canon progress` 的（BR-2246），不另存。`canon show`、`canon context` 在带标签的规则旁写 `release R-n`，有 `changed_in` 时写 `changed in R-m`。

**发布。** `canon release ship R-n`：

- 标着 R-n 的规则（作废的不算）必须全部是“已通过”：有规划中、待重新执行、待 main 测试的，一律拒绝（退出码 1），消息列出每一条。没有任何规则标着它也拒绝：没有可以发布的行为。
- 必须有负责人的确认：`canon human` 里有一个问题，文字里写着 `ship R-n`，回答是 `yes` 或 `是`（只认这两个词）；回答由负责人本人在终端写，或由 agent 用 `--relayed` 转述，且转述的原话也是 `yes` 或 `是`、和 Claude Code 提问工具的记录一致（BR-2276 的 `match`）。问题带 `--option` 时，`canon human answer` 在记录阶段就要求转述的回答是原话对应的那个选项，负责人选了 no 的话 agent 记不成 yes（BR-2021）；ship 对回答和原话各查一次，是第二道。没有这样的问题、回答不是 yes、转述对不上记录，都拒绝，消息说明怎么补。多个问题时看最近回答的那个，后来的 `no` 会撤销之前的 `yes`。agent 没有负责人的记录就发不了。
- 成功时把 `status: shipped` 和 `shipped_at: <发布时 main 的提交号>` 写进 R-n，并打 git tag `release/R-n` 指向这个提交。文档里的提交号是准的，tag 只是方便：tag 打不上（已存在、仓库不让写）时报出来，不撤销已经合入的记录。

**怎么合入快照。** 规则是“一切经变更合入”，发布也不例外。采用 `canon update` 的做法：`canon release ship` 自己开一个变更、在它的 worktree 里写 R-n、提交、`--finish` 合入，合入后再打 tag；在哪个目录里运行都行。不要求先在某个变更里运行，因为发布是一个由负责人确认触发的独立动作，不该混进别的工作；也不要求发布者手写文件，所以手写的 `status: shipped` 合不进 main：合入时，一个版本在合入的树里是 `shipped`、main 上不是时，必须有这次变更自己的 `release.ship` 事件（`ship` 命令在查过全部条件、确认过负责人的回答之后才写），事件里的提交号和文件里的一致；已经是 `shipped` 的版本不许改回去。`shipped_at` 取 `ship` 开始时 main 的提交号，不是发布变更自己的提交：那是“发出去的版本”，发布变更只是记录它。`ship` 先取这个提交号，再按它读版本和规则状态做检查；合入时在合入的树上再查一次“标着它的规则全部已通过”和“负责人的确认仍有效”（没被后来的 no 撤销），任一不满足以原因 `release` 拒绝（BR-2335），所以排队或超时之后直接 `canon work land --finish` 也要重新满足。发布变更排队时如果有人改了这个版本的三节或标签，合入后的 `canon check` 会因为和 `shipped_at` 不一致而拒绝，重新运行 `ship`。

**skill。** `canon-product` 里故事地图的版本切片写进版本文档的“故事地图切片”；笔记留调研和证据；线上方的行变成标着这个版本的规则。

## 后果

- 规则多了可选标签，canon 自己的规则不补标，所以现有项目不受影响；用版本的项目才有 `canon/releases/`。
- 已发布版本的范围检查靠 git 里 `shipped_at` 的提交；浅克隆里没有那个提交时，`canon check` 报错而不是跳过（不静默放过）。
- 发布需要负责人回答一次问题；负责人不在时发布等着，这是有意的（P7：方向留给人）。
- 版本的进度和 `canon progress` 用同一套状态，不会出现两种“已通过”。
- 已知限制：发布的快照是 main 的一个提交，不是副本；要看“发布时的规则全文”，用 `git show <shipped_at>:canon/rules/...`。
- 已知限制：`release.ship` 事件是本地协调库里的一行；能拿到 shell 的 agent 可以直接改库写一行，绕过“只经 `canon release ship` 发布”。这和 BR-2021 承认的限制同类（canon 分不出转述和编造，也防不了改库），所以合入检查（BR-2332）防的是误操作和手写 `status: shipped`，不是有意的伪造；真正的把关是负责人的确认和评审。
- 版本状态 `planned` 到 `active` 没有命令，靠手改 front matter，这是预期做法：它只是进度标记，不放行任何事；只有 `shipped` 受检查保护。
- 拆分已发布的规则时：已发布版本的规则标签不许变（BR-2326），所以拆出来的新规则不能标那个已发布的版本；标后面的版本，原规则的行为变了则在原规则上写 `changed_in`。
- 别的项目已经声明了前缀 `R` 或目录 `releases` 的类型时，配置报专门的错误：说明它们已是内置版本类型的前缀和目录，并给出迁移办法（改自己类型的前缀和文档编号，或改目录名、搬文件）（BR-2045）。
