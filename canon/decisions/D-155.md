## 背景

2026-11-21 凌晨两个项目都出了同样的事。zhushenkongjian 的 main 从 02:23 起后台测试不通过，直到 07:44 才有人开修复变更；唯一在干活的会话手上有自己的变更，而 BR-2220 的提示只叫没认领变更的会话去修，还叫它别在自己的变更里修。它 4 次 `canon work test`（每次 18 到 25 分钟）都撞上同一个 main 的失败。canon 自己的 main 也从 11-20 23:05 红到第二天早上。议程（BR-2527）其实把 `red-main` 排在判断组第一档，但提示文字和可以推后（BR-2583）让它没起作用；“main 没通过”的记录里也没有失败的测试文件，会话分不出哪些失败是 main 的。

负责人 2026-11-21 在会话里说“我们现在应该有优先级的概念，并且主 Agent 可以动态调整优先级”，接着在三个问题里选了：优先级管开工和派活顺序、合入排队顺序、打断手上的活；负责人定的压过主 agent（主 agent 随时可调、要写理由，不能调低负责人定的；修 main 自动最高；worker 不能调）；用几个档位，不用一条完整排序。一次不看推荐的独立评审指出：这次的事主要是提醒没送到；main 一坏就叫人修会关掉自动撤回（BR-2535 见到修复变更就不定位）；能设 P0 就等于能叫停所有人；打断应该先给能派活的主会话、先派 worker。负责人据此又选了：主 agent 只能设 P1 到 P3；三步都做。

## 方案

1. 档位存在协调数据库里，命令设置，立刻生效：采用。和 D-73 的理由一样，改 `canon/backlog.md` 或变更文件要先合入才生效，负责人想插队的那一刻已经晚了（#141）；这次多了“主 agent 随时调”，等合入更不行。D-20 否决数据库是因为负责人在 GitHub 上看不到、没有历史：每次设置都写事件（谁、何时、理由或原话），`canon change list` 和 `canon work status` 列出现在的档位，`backlog.md` 仍是同一档里的顺序。
   - 来源：canon/decisions/D-20.md “顺序存在协调数据库里，用命令调整。否决”
2. 档位写在变更文件的 front matter 里：否决。新建的 P0 变更只在自己的分支上，别的会话看不到；主 agent 要改别人的变更就得合入一次那个文件，等在它想重排的队列里；已关闭的变更留着过时的档位（D-20 方案 3 的理由）。
   - 来源：canon/decisions/D-20.md “已完成的变更还留着过时的数字”
3. 不分档，让主 agent 也编辑 `backlog.md`：否决。负责人选了档位；同时编辑同一个文件合入冲突（D-20 方案 2）；一条完整排序里分不出哪些位置是负责人定的。
4. 用拒绝强制打断（有没人做的 P0 时，拒绝别的会话开工和合入较低档的变更）：否决。自动撤回定位期间所有人都被挡住；等依赖或负责人的 P0 认领了也做不了，整个项目停住；被挡的会话最快的出路是抢着开修复变更，正好关掉自动撤回。打断只做成提醒，送到会话手里。
   - 来源：.claude/skills/canon-design/SKILL.md “refuse rarely: only to keep main correct”
5. 只修提醒、不要档位（main 坏了时暂停注定失败的测试）：否决作为全部方案，部分采用。提醒送不到确实是这次的主因，第 1 步就修它；但负责人要的是能动态调整的优先级，开工和合入顺序也要跟着档位走。

## 决定

采用方案 1（BR-2602），分三步：

1. main 坏了谁看到谁修：BR-2598、BR-2599、BR-2600、BR-2601。
2. 档位：BR-2602、BR-2603、BR-2604、BR-2605。
3. 打断：BR-2606。

## 后果

- 新领域 `work/priority`：档位由谁设、存在哪、怎样显示，不属于合入队列、议程或变更状态中的任何一个，放进其中之一会让另外两个反过来依赖它；三处怎样用档位仍写在各自领域的规则里。
- D-34 和 D-73 的“agent 不能自己插队”改为：主 agent 可以把变更调到 P1 到 P3，合入顺序跟着变；P0 只来自修复 main 的变更和负责人。负责人的话照旧不核对（D-73），主 agent 冒充负责人调低档位挡不住，只有事件记录可查。
- D-20 的待办清单仍只由负责人编辑，它成了同一档里的顺序。
- D-151 的议程多了 `interrupt` 项和不能推后的 `red-main`；状态仍从事实算出，档位是一条新的事实，已关闭的变更的档位不起作用。
- 几个主 agent 来回调同一个变更的档位，canon 不拦，每次都记事件、发打断提醒；靠 `canon events --kind priority.set` 事后查。
- P3 在合入队列里可能一直被更高档的插到前面；它占着会话，等得越久 rebase 冲突越多。这是已知限制，不另设机制。
