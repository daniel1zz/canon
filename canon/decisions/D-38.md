## 背景

合入只更新本机的 main，推到 GitHub 一直靠人做，已经两次出现几十到几千个提交只在本机（C-39）。C-39 要求：合入成功后把 main 推到配置的远端；推送失败不改变合入结果，但要写 `push.fail` 并在 `canon brief` 里提示；另加 `canon sync`，只在能快进时把远端的 main 拉到本地。要决定三件事：用已有的 `after_land` hook 还是内置步骤；`floor_timing: after`（D-31）下每次合入都推，还是只推后台测试通过的提交（`refs/canon/green`）；`canon sync` 怎样移动 main。

实测（git 2.50.1，本地裸仓库当远端，C-39 里做的）：

- `git push <远端> <提交>:refs/heads/main` 成功后，git 同时把 `refs/remotes/<远端>/main` 更新成这个提交（这是实测结果，git-push 的文档没写；它依赖远端有默认的 fetch 规则，`git remote add` 自带），所以“本地 main 上有多少提交没推上去”可以只在本地用 `git rev-list --count refs/remotes/<远端>/main..main` 算出来，不用联网。
- 先推了较新的提交 B，再推它的祖先 A，git 拒绝，`--porcelain` 输出 `[rejected] (non-fast-forward)`。也就是说，两次推送的先后和读 main 的先后反过来时，后到的旧推送会被拒，虽然远端已经有它要推的全部提交。
- `Bun.spawnSync` 的 `timeout` 到时会用 SIGTERM 杀掉子进程，返回 `exitedDueToTimeout: true`；ssh 连不上时可以靠它结束，不会让合入者一直挂着。
- 本仓库 `origin` 的 main（`git ls-remote`）是本地 main 的祖先，`refs/remotes/origin/main` 和它相同，落后本地 main 465 个提交。

## 方案

1. 用 `hooks.after_land` 配一条 `git push origin main`：否决。after_land 在后台运行，退出码不影响结果，canon 只把它当成一条命令，记 `hook.run` 和日志，不知道推的是什么，写不出 `push.fail` 的原因，也说不出还差几个提交；每次合入各起一个后台进程，几次合入挨得近时推送的先后和 main 前移的先后可能相反，旧的推送会被远端拒绝，留下假的失败。
   - 来源：canon/decisions/D-3.md “三者的退出码都不影响结果”
   - 来源：https://git-scm.com/docs/git-push “a non-fast-forward update will lose history”
2. 用 `hooks.after_green`，只推后台测试通过的提交：否决。和方案 1 一样写不出推送失败的记录；而且 main 没通过可能持续很久（要等修复变更合入），这段时间合入的工作都只在本机，正是 C-39 要解决的丢失风险；远端落后又会让从 `origin/main` 建 worktree 的工具在旧代码上干活（C-39 记的 lore KN-534）。
   - 来源：canon/changes/C-39.md “推送不只是为了备份”
3. 内置步骤：合入移动 main、结束轮次之后，由 `work/remote` 把本地 main 当时指向的提交推到配置的远端，只推 `refs/heads/<main>` 这一个 ref，不带标签，不强推，有超时；`floor_timing` 是 `before` 还是 `after` 都在每次合入后推：采用。canon 自己执行推送，知道成功、失败和原因，能写 `push.ok`、`push.fail`；被拒绝时先取一次远端的 main，远端已经包含要推的提交（比它更新的推送先到了）就算推上去了，不是失败，这样不用加锁也不会有假的失败；只有远端确实有本地 main 没有的提交时才算失败，canon 不强推、不合并，交给人决定。远端是本机 main 的备份，main 上有没测过的提交时远端也一样有，修复变更向前修好后照样推上去。
   - 来源：https://git-scm.com/docs/git-push “to prevent such loss of history”
4. `canon sync` 用 `git pull`（或 fetch 再 merge）：否决。main 守卫（D-16）会拒绝，而且 merge 会在 main 上造出没经过合入的合并提交。
   - 来源：canon/changes/C-39.md “现在要拉取只能用”
5. `canon sync` 先取远端的 main，只在本地 main 是它的祖先时，用合入移动 main 的同一个比较并交换（带 D-16 的放行标记，签出了 main 的 worktree 在那里 `merge --ff-only`）把 main 移到远端的提交；分叉时报错、什么也不动：采用。快进不丢任何一边的历史；分叉时怎么合是人的决定。
   - 来源：https://git-scm.com/docs/git-merge “When not possible, refuse to merge and exit with a non-zero status.”

## 决定

2026-11-04 独立评审后修订（C-294）：负责人选了“D-38 推送和 sync (推荐)”，只改了推送的等待时间一处（见后果和已知限制），方案和决定的其余部分不变。

采用方案 3 和 5，新建子领域 `work/remote`：

- 配置 `remote`（git 远端的名字，没写就不推送，`canon sync` 以退出码 2 失败）和 `remote_timeout_seconds`（一次推送或取远端最多等多久，默认 60 秒）。读的是 main 上已提交的配置，因为推的是 main。
- 推送（BR-2259）：`canon work land` 移动 main、结束排队轮次之后推，所以推送慢不占别人的轮次；推的是推送时本地 main 指向的提交，分批合入（D-26）的每个成员各推一次，后推的发现远端已经有了，不算失败。推送失败不改变合入结果（BR-2260）。
- 一次推送最多等 `remote_timeout_seconds`：被拒后取远端的 main 和推送共用这一个时间，推送用掉的从取远端里扣（BR-2260）。
- `canon brief` 在没有认领变更的 worktree 里提示没推上去的提交数，只在本地计算（BR-2261）。
- `canon sync` 只快进（BR-2262），分叉时退出码 5、什么也不动（BR-2263）。D-16 里“main 只能通过 `canon work land` 移动”改为：只能通过 `canon work land` 和 `canon sync` 的快进移动；sync 只把 main 快进到远端已有的提交，不经过排队和 floor，因为远端的提交不是本机的变更（C-39 定下 sync 不放进 `work/land`）。

## 后果

- 每次合入多一次网络请求，合入者多等几秒；网络不通时最多多等 `remote_timeout_seconds`（推送和被拒后的取远端合起来，不是两倍），合入照样成功，brief 会一直提示，下一次合入或推送成功后提示消失。
- 远端被别人推了本地没有的提交时，之后每次推送都失败，直到人决定怎样合并；canon 不会替人强推或合并。
- 在本仓库启用要分两次合入（BR-2248）：先合入代码，后台测试通过、PATH 上的 canon 重新构建后，再在 `canon/config.yaml` 里写 `remote: origin`。启用后第一次推送会把本地 main 上全部没推的提交一次推上去。
- `canon sync` 和一次正在进行的合入同时移动 main 时，由比较并交换决定谁先：sync 先移动，那次合入以 `main-moved` 被拒、重新合入；合入先移动，sync 以 `main-moved` 失败、什么也不动。
- `canon sync` 移动 main 后，`floor_timing: after` 下照常启动后台测试；同步进来的提交没有在本机测过，和合入一样由后台测试发现问题。

### 已知限制（D-54）

2026-11-04 独立评审的几条，需要不正常的配置或动作才出现，不为它们加机制：

- `canon sync` 带进的是远端上本机以外的人写的提交（网页编辑、PR 合并），不经 floor；`floor_timing: before` 下这些提交没在本机测过，P4 的“main 上每个提交都测过”对它们不成立。本项目的前提是一台电脑开发（product.md），`sync` 在本仓库一次也没运行过（`events` 表 `sync.*` 0 条）；出现真实的外部提交再重新打开。
- 远端 main 有本地没有的提交（分叉）时，之后每次推送都失败，直到人合并；没有单独的备份分支。这需要有人往远端 main 写，同上。
- 远端没有默认的 fetch 规则时，`refs/remotes/<远端>/main` 不会更新，`canon brief` 会把全部历史当作没推上去的。
- 两次合入的推送同时被拒、同时取远端时，可能因抢同一个引用的锁而记一条假的 `push.fail`；不丢数据，下一次推送成功后提示消失。
