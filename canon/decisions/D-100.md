## 背景

#188 的负责人要求：杂务不开变更、不占 C 编号，但有自己的工作树、分支、认领，共享队列和检查；不按修改路径检查业务边界。BR-2086、BR-2278、BR-2334 的自动入口原来都创建 Change。协调数据以字符串 subject 关联，没有到变更文档的外键。

## 方案

1. 分支保存工作身份，沿用现有 subject：采用。C 仍关联文档，杂务没有文档；分支在认领释放后仍能恢复身份，事件保存完整标题。共享认领、交接、队列及合入，避免另外登记一份完成状态。
   - 来源：src/work/db.ts “subject    TEXT PRIMARY KEY”
2. 新建统一 works 表作为全部工作的身份权威：否决。本次不需要任意分支改名后自动恢复；增加表仍不能把 Git 创建和数据库登记变成一个事务，旧 C 还需注册和对账，生命周期消费者仍需修改。
   - 来源：src/work/session/session.ts “const claim = takeClaim”
3. 杂务直接提交 main：否决。绕过共享队列和 main 的比较并交换，不能保证并发合入安全。
   - 来源：canon/product.md “多个会话同时工作，不丢工作、不互相覆盖”

## 决定

杂务 subject 为 `chore-<完整 UUID>`，分支为 `chore/<UUID>-<slug>`，工作树目录以 subject 命名。不占知识编号，不建知识文档或开工/关闭文档提交。分支恢复身份和类型，事件保存标题与生命周期，claim 仅保存所有权（具体输出和退出码见 BR-2457）；C 文档缺失不是杂务。

`canon chore start` 开始或接回，`canon chore land` 共用合入并完成工作（移动 main 的是同一条流水线，这是对 D-16 的局部修改）；通用 work 命令处理杂务。每个批次成员独立识别身份。更新、卸载、发布记录改走杂务，局部修改 D-10、D-46、D-61 中必须开变更的要求，其余要求不变。D-88 仍有效，不恢复扫描。

hook 的环境变量按 BR-2199：新增工作身份和类型两个变量，`CANON_CHANGE` 保持文档编号语义。通用结果增加 subject、workKind，不覆盖结果判别 kind；旧 change 结果字段保留为 subject 的兼容别名。事件关联始终使用 subject。子 agent 的 `--as` 约定同样覆盖 `canon chore` 的认领命令（对 D-62 的局部修改），检查见 BR-2340。

## 后果

- 不新增队列或状态表，不迁移历史 C。规则执行证据、计划和业务待办仍以 Change 文档为载体。
- 接回、歧义拒绝和标题不可恢复时的输出按 BR-2457；任意重命名分支后不猜测恢复。
- D-99 的连续被拒停下和 D-13 的归档照原样适用到杂务，内容不变，所以不列入 `amends:`。
- 旧二进制不能参与含杂务的合入。启用前结束旧 lander、排空活动队列，再以新版本恢复工作；回退前先完成或归档杂务。本次不新增版本协商。
- 卸载删除配置后的重试和批次边界按 BR-2278、BR-2172。
