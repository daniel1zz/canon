## 背景

2026-11-03 本仓库最近 6 小时：52 次合入，每次合入拿到轮次后约 4.4 分钟（几乎全是 floor），排队等待中位数约 3 分钟、90% 在 27 分钟内、最长 44 分钟；约三分之一的尝试被拒。实测 floor 里 `bun test` 占约 99.5%（负载 10 到 16 时 394 秒，45 个文件顺序跑），耗时随机器负载明显变化，同一台机器上并行跑多个 floor 只会互相拖慢。floor 是项目自己的命令，canon 无法让它变快。5 次 floor 失败里 3 次是同一个偶发失败的测试（#32），1 次超时，只有 1 次是真错误。

负责人的方向（原话）：“合并进去之后再测试，而不是测试成功再合并，有问题就改就行”；“不用找是谁不过啊，针对不过的测试去修复代码就行啊”；“或者这个可以作为配置开关，用户针对项目做不同的选择，如果开发阶段那肯定越方便越快越好”。main 没通过时其他合入照常进行；修复它的变更排在最前面。给出设计前请一个看不到设计的子 agent 反驳过一次，构建只来自测过代码、单例的后台测试、只测最新提交、失败记录不重复这几条来自它。

## 方案

1. 只保留先测再合（BR-2014），靠分批合入提吞吐：否决作为唯一方案。分批失败的处理和批的大小仍要改进（另一个变更），但合入仍要等 floor，等待时间随 floor 和负载变长；负责人在开发阶段要的是不等。
2. 先合后测，失败时自动二分找出是哪个变更、撤回它：否决。负责人明确不追查是谁；二分要在后台反复跑 floor，正是最贵的东西；撤回会让合入了的工作又消失。
3. 先合后测，失败时只记下来，由下一个空闲会话针对失败去修（向前修），做成配置开关，默认仍是先测再合：采用。合入只等几十秒的自身检查；不改默认行为，已有项目升级后不受影响。
   - 来源：canon/notes/N-3.md “瓶颈是串行的 floor”
4. 失败时由后台直接新建一个修复变更文件：否决。变更文件要进 main 必须经过合入，main 的守卫（BR-2126）不允许后台进程直接写 main；改为在协调数据库里记失败，由会话用 `canon work start --fix-main` 开变更。
5. `after` 模式下 `after_land` 照常重新构建 PATH 上的 canon：否决。合入了把命令行本身弄坏的变更时，所有会话的 canon 一起坏掉，连修复变更都合不进去；构建改为只来自通过的提交（`after_green`）。

## 决定

采用方案 3：

- `floor_timing: before | after`，默认 `before`（BR-2218）。`after` 下合入跑完每个变更自己的步骤就移动 main，不跑 floor、不分批。
- 后台测试 `canon floor watch`：同一时间一个，在临时 worktree 里测 main 的最新提交，测完再看有没有更新的（BR-2219）。
- 失败：协调数据库记一条“main 没通过”，`canon brief` 排在最前面（BR-2220）；`canon work start --fix-main` 开唯一的修复变更（BR-2221）。修复变更合入时插队由另一个变更做。
- 通过：`refs/canon/green` 前移、清掉失败记录、运行新的 `hooks.after_green`（BR-2222）。本仓库切到 `after`，`bun run build` 从 `after_land` 挪到 `after_green`，输出到主 checkout 的 `dist/canon`。
- `product.md` 的 P4 改写：`before` 下 main 永远测过；`after` 下 main 可能短时没通过，由修复变更向前修好。

## 后果

- `after` 下 main 可能是红的：从红的 main 起步的会话会看到不是自己造成的失败，brief 告诉它不要在自己的变更里修。
- 只测最新提交：失败记录对应的是“最近通过的提交到这次失败之间”的一整段变更。
- 偶发失败的测试也会产生“main 没通过”，修它就是修复变更要做的事。
- 从 `after` 切回 `before` 要在 main 通过时进行，否则之后每次合入的 floor 都会因为已有的失败被拒。
- `after_land` 在 `after` 下运行于没测过的代码上（代码评审照常）；只应来自测过代码的步骤放 `after_green`。
- `canon stats` 的 floor 计数在 `after` 下来自 `floor.pass`/`floor.fail` 事件，后台失败不算合入被拒。
