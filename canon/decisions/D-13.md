## 背景

C-8 和 D-6 让 `canon work drop` 在会丢工作时（分支上有不在 main 上的提交、worktree 有未提交的改动）不删除，而是用 `canon human ask` 问人，人回答 yes 后再执行才删除（当时的 BR-2065、BR-2066）。旧 lore 的复盘 KN-783 数过：同类的问人一共 42 次（31 次删除 worktree，11 次丢弃 stash），几乎都是“删吧”，结论是只要有可靠的存档，这一步人工确认就没有必要。lore SPEC-197 的做法是先写到 `refs/lore/archive/...`，读回校验成功再删除。

2026-11-03，负责人在 Claude Code 的对话里被问到：`canon work drop` 是继续“每次都问人”，还是改成“把分支和未提交的改动存档到 `refs/canon/archive/C-n`，确认能读回后直接删除”。负责人的原话是：「存档后直接删」。

C-52 还发现，被 git 忽略、又不能重新生成的文件（例如 `.env`）同样会在删除 worktree 时丢掉，所以存档要包括它们。

## 方案

1. 保持每次问人。否决：负责人不选它；KN-783 的数据说明这些问题几乎都被同意，问人只是让工作停下来等，而存档已经让删除可以撤销。
2. 存档并读回校验，成功后直接删除，不问人。采用（负责人的选择）。
3. 存档后仍然问人。否决：存档已经让删除可以恢复，再问人只多了等待，没有多保住任何东西。
4. 用 `git stash create` 存未提交的改动。否决：实测（git 2.50.1）它只记录已跟踪文件的改动，未跟踪文件和被忽略的文件都不在里面。改为用临时索引（`GIT_INDEX_FILE`）把工作区当前的全部文件（含未跟踪的和不能重新生成的被忽略文件）写成一个提交，第一个父提交是分支的最新提交；worktree 自己的索引不受影响。

## 决定

- `canon work drop` 会丢东西时，先把分支的最新提交和 worktree 当前的文件存成一个提交，放在新的 `refs/canon/archive/<C-n>/<时间>` 下（只新建，不覆盖），读回校验：这个 ref 指向这个提交、包含存档时的文件树、包含分支的最新提交、每个未提交和被忽略的文件都在里面、存档后工作区没有再变。全部通过才删除；任何一步失败都什么都不删，退出码 4（BR-2102、BR-2103）。
- `drop.done` 事件记下存档 ref；输出写明怎么恢复（重建分支、重建 worktree、`git restore --source=<ref>`）。
- 别的操作者持有有效认领，或者有别的进程的当前目录在 worktree 里时，不删除，退出码 5（BR-2064）：那是有人还在用它，存档救不了正在进行的会话。
- 取代 D-6 中关于 `canon work drop` 的部分（方案 2 的讨论、“`canon work drop` 也接受转述”、`canon work drop` 输出里写明转述者）；D-6 关于 `canon human answer` 转述人的回答、如实记录的决定不变。

## 后果

- BR-2065、BR-2066 退役，由 BR-2102、BR-2103 取代；CLAUDE.md 里“`canon work drop` 会问人”的说法改掉。
- 存档 ref 不会自动清理，会一直占用仓库空间；需要时手工 `git update-ref -d`。
- 存档只在本机仓库里，和协调状态一样不跨机器（产品说明的“不做的事”）。
- 嵌套的 git 仓库（未跟踪目录里有 `.git`）只会存成一个 gitlink，里面的文件不在存档里。
