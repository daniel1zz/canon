title: 规则真正冲突时按最后生效的需求修改确定执行依据
status: accepted
---

## 背景

负责人在本次对话要求「真的有规则冲突时应该以最新的为准」，并在问题 #24「你说“规则冲突以最新为准”，这里的“最新”按什么判断？」选择「最后生效的需求修改（推荐）」。另两个选项是规则文件最后修改的提交、规则创建顺序；回答已通过 canon human answer 原样记录。

D-32 已把 baseline 定位为先设计、约束执行的需求依据。一个需求后来正式改变，另一份规则还留着旧说法时，执行依据应跟随需求的改变；修改标题、错字或移动旧文件不能让旧需求重新取得优先级。本次只补工作引导，不让 CLI 自动判定自然语言的冲突或生效顺序。

## 方案

1. **按最后生效的需求修改处理真实冲突（采用）**：负责人的选择。根据决策、完成的变更和 Git 中行为内容的差异确认生效顺序，先确定执行依据，再清理旧说法。代价是无法从记录确定顺序时，必须明确报告缺失证据，不能只看文件的最后提交。
   - 来源：canon/decisions/D-32.md “baseline 用来约束执行”
2. **按规则文件最后修改的提交处理（否决）**：能直接从 Git 取到，但错字修正、改标题、移动和 rebase 都可能改变表面顺序，没有改变需求含义；不符合负责人选择的口径。
   - 来源：canon/decisions/D-32.md “rebase 会把通过排到别人的修改之后”
3. **按规则创建顺序或编号处理（否决）**：确定、简单，但旧规则可以承载最近正式改变的需求，新建规则也可能只是引用既有要求，创建顺序不能代表需求生效顺序。
   - 来源：.claude/skills/canon-rules/SKILL.md “Most requirements change an existing rule; edit it in place, keep its id.”

## 决定

- canon-rules 集中说明冲突处理：先核对适用范围、条件和例外；只有同一情形要求不兼容的结果才使用最新需求的优先级，不把不同情形的规定误判为冲突。
- 最新指最后正式生效的需求修改，依据记录与行为差异确认，不按文件时间、编号或最后一次文字编辑判断；没有生效的草案和提议不覆盖已生效要求。无法证明先后时列出冲突和缺失证据，按原有未定选择流程处理，不猜测。
- 变更写明采用的要求及其依据，再按 D-93 的写入分工修正旧说法、改成引用或作废已无剩余要求的规则，并核对受影响的引用和测试。不能只选一条执行、让冲突永久留在 baseline。
- canon-design 和 canon-test 的入口引用 canon-rules 的这节说明，不再另写一套优先级。现有规则评审、检查和验收继续执行，不因为有了优先级就绕过合入检查。

## 后果

- 需求修改顺序清楚的冲突可以直接按已定要求处理，不必为同一取舍重新问负责人；记录不足时仍需明确处理未定选择。
- 这项引导依赖读取历史内容，不能自动发现所有冲突，也不提供自然语言一致性的形式化保证。
