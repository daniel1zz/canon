## 背景

issue #89：`canon floor watch` 在一个提交上通过后，先在一个事务里记 `floor.pass`（C-208），再运行 `hooks.after_green`（本仓库用它重新构建 PATH 上的 `dist/canon`）。进程在这两步之间被杀掉（OOM、重启、杀进程组），这个提交已经算测过（`tested()` 为真），没有任何地方补跑 `after_green`，PATH 上的 canon 一直停在旧版本，直到 main 再前移并通过一次。

实测（2026-11-04）：`src/work/watch/watch.test.ts` 的 BR-2270 用例在 `after_green` 运行时 SIGKILL 整个进程组，之后 `canon brief` 不启动任何后台测试。

## 方案

1. `after_green` 跑完之后才记 `floor.pass`。否决：`floor.pass` 是“测过了”的标记（BR-2219），推迟它会让被杀掉的那次整个 floor 重跑（本仓库约 13 分钟），而且 `after_green` 很慢时，这期间合入和 `canon brief` 都以为 main 没测过。
2. 只靠已有的 `hook.run` 事件判断：否决：`hook.run` 只在一条命令结束后才写，不带提交，分不出是哪次通过的、是不是全部命令都跑了。
3. `floor.pass` 在同一次写入里带 `after_green: true`（欠着），全部命令跑完后记 `floor.after_green`（不欠了）；`refs/canon/green` 指向的提交欠着时，下一个后台测试只补跑 `after_green`。采用。欠着的标记和“测过了”一起写下，所以任何时刻被杀都不会丢；补跑不重跑 floor。
   - 来源：src/work/watch/watch.ts “ws.db.event(ws.actor, passed ? "floor.pass" : "floor.fail", null, { sha, log, exit: code, ...(passed ? {} : { why }), ...(due ? { after_green: true } : {}) });”

## 决定

用方案 3（BR-2270）。只看 `refs/canon/green` 指向的提交：更晚的通过自己会运行 `after_green`。跑完不论退出码都算结束，补跑时 `setup` 失败也算结束，免得每次 `canon brief` 都重试一个坏掉的 `after_green`。

## 后果

- `after_green` 最多晚一次后台测试启动（下一次合入或 `canon brief`）才补跑。
- 这条规则之前记下的 `floor.pass` 没有标记，从不算欠着。
- 补跑也被杀掉时还欠着，下一个后台测试再补跑；一个每次都会把进程杀掉的 `after_green` 会被每次启动的后台测试重试。
