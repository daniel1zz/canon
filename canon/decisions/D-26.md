## 背景

合入是串行的：每次合入都在即将成为 main 的那棵树上跑 floor（约 2.5 分钟），一次只有一个合入者。N-3 实测队列连续 32 分钟不空，一小时最多合入约 24 次；再加 agent 只会让排队更长。负责人提出“多个带权重的队列”：权重只改变顺序，floor 的总次数不变，吞吐不会提高。真正能提吞吐的是少跑 floor：只改文档时不跑（BR-2164），以及几个等着的合入一起测一次。约束：只在本机一台电脑上跑（product.md 不做多机）；多个 floor 同时跑曾出现负载 150、70 多个假失败；只有测过的提交能成为 main（BR-2106）；排队时的冲突预测（D-22、BR-2153）在没进批时照常有效，进了批就由链上的 rebase 判断。N-3 的 16 次轮到合入里 floor 拒绝 0 次，说明一起测的那批绝大多数会整体通过。

## 方案

1. 不合并测试，保持一次一个。否决：floor 次数等于合入次数，吞吐上限不变。
   - 来源：canon/notes/N-3.md “瓶颈是串行的 floor”
2. 合并队列式的批量测试：轮到的合入者把紧跟在后面、还在等的几个合入按排队顺序依次 rebase 成一条提交链，只在链的最上面跑一次 floor，通过就把 main 移到链顶，每个变更保留自己的提交；失败就把这批拆开。采用。GitHub 的合并队列和 bors 都这样做，批量大小可配。失败后的拆法有两种：bors 对半拆再测（bisect），或者退回一个一个合入。采用退回逐个合入：批量上限默认很小（这里设 4），对半拆最多省一次 floor，却要多一套状态；floor 很少失败，失败时多花的只是一次 floor。
   - 来源：https://github.com/bors-ng/bors-ng “bors actually tests them in batches (and bisects if a batch fails)”
   - 来源：https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue “contains code changes from the target branch, pull request #1, and pull request #2”
   - 来源：https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue “You can specify a maximum group size”
3. 推测式并行测试（Zuul 的依赖管道、Uber SubmitQueue）：假设前面的都会通过，同时给每个前缀各跑一次测试。否决：它用更多并行的机器换时间；canon 只有一台电脑，几个 floor 同时跑会抢 CPU：多个 worktree 同时跑全量测试曾出现负载 150、70 多个假失败，N-3 里负载 8 到 12 时测试就已经不稳，结果反而更慢、更不可信。
   - 来源：https://zuul-ci.org/docs/zuul/latest/gating.html “it assumes that all jobs will succeed and tests them in parallel accordingly”
   - 来源：canon/notes/N-3.md “负载 8 到 12 时测试不稳”

## 决定

用方案 2，失败时退回逐个合入。

- 新配置 `land_batch_max`（正整数，默认 1，即不合并）；本仓库设 4。
- 轮到的合入者（领头）先照常 rebase 到 main；然后按排队顺序取紧跟在后面、还在等、进程还在、没被标成单独合入的条目，最多凑够 `land_batch_max` 个；遇到第一个不合格的就停，不越过它取后面的（排队顺序不变，BR-2020）。
- 在一个临时 worktree 里把这些变更依次 rebase 到前一个之上；某个变更在链上冲突，就从它开始的都不进这一批，留在队列里照常等。
- 每个变更自己的步骤（`canon check`、来源核对、规则评审、`before_land`）在它自己那一段链顶上跑；floor 只在整条链顶跑一次（只改 `floor_skip_paths` 时照样跳过）。
- 任何一步失败，或者某个成员的 worktree 期间变了、进程不在了：这一批作废，成员回到队列并标成单独合入（不再被拉进别的批），领头自己照常单独合入。所以一个变更只会因为它自己单独合入时的结果被拒，不会因为同批的别人被拒。
- 全部通过：main 用比较并交换移到链顶；每个成员的条目记成已合入、记下它那一段的提交；成员自己的进程看到后，把自己的分支比较并交换地移到那个提交，再照常收尾（`--finish` 释放认领等）。

## 后果

- 一批 k 个变更只跑 1 次 floor；全部通过时省 k−1 次。一批失败时比逐个合入多跑 1 次 floor。
- main 上同一批里中间的提交没有单独跑过 floor，只有链顶跑过；BR-2106 的“测过的提交”指成为 main 的那个链顶。GitHub 合并队列也是这样。
- 成员等待期间不能再改自己的 worktree，否则这一批作废（和 BR-2106 一样）。
- 领头进程在移动 main 之后、记下成员已合入之前死掉：成员回到队列再合入一次，rebase 后没有新内容，不丢工作。
- `canon stats` 里同批的成员不算 floor 的运行。
