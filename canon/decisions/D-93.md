title: baseline 规则只由负责该任务的主会话亲自编写
status: accepted

## 背景

负责人在本次对话选择「全部由主 agent 亲自写规则」。D-32 把 baseline 定位为先设计、约束执行的需求依据。现有 canon-rules 要求写前检索、优先改原规则和用引用复用，但不区分主会话与子 agent；canon-parallel 又允许子 agent 完成带规则的整个变更，测试、排查和设计引导也会直接要求执行者补规则。

这次只调整 canon 自带 skill 的分工引导。模型能力与上下文完整性不由角色名保证，不把「主会话一般用更强模型」当成已经验证过的错误率结论。主会话掌握负责人的需求与任务取舍，亲自维护验收依据；子 agent 提供实现中的事实和建议。

独立核对指出，写入权限、语义责任和并发冲突是三件事；多个顶层会话也不意味着存在一个全项目主会话。因此这里按任务范围确定负责的主会话，保留 D-62 的 worktree 持有与交接边界。

## 方案

1. **所有 baseline 规则由负责该任务的主会话亲自写，子 agent 只读并报告建议（采用）**：负责人选定；规则的检索、归属、引用和实际文字由同一个责任会话处理，避免执行者自行改动验收依据。代价是实现中发现的规则缺口需要交回主会话，依赖该选择的工作要等；不依赖它的工作继续。
   - 来源：canon/decisions/D-32.md “baseline 用来约束执行”
2. **主会话定稿，允许子 agent 在授权范围内代写规则，或写入主会话给出的原文（否决）**：往返可以更少，但写入仍分散给实现者，授权范围含糊或发现跨领域缺口时边界仍会扩大；负责人选择了全部亲自写，不保留这个例外。
   - 来源：.claude/skills/canon-parallel/SKILL.md “the main agent holds the whole context and makes the decisions”
3. **按领域指定子 agent 为规则维护者，只把跨领域选择交回主会话（否决）**：独立核对提出的替代方案，可以分担写规则，但仍允许子 agent 写 baseline，与负责人这次选定的分工不同。多个主会话的范围重叠仍由既有认领、worktree 和合入流程协调，不为此新增全项目维护者或锁。
   - 来源：canon/decisions/D-62.md “主会话和子 agent”

## 决定

- canon-rules 集中说明写入边界：负责该任务的顶层主会话亲自新增、修改、作废和移动 baseline 规则；正文、标题、例子、元信息和状态都包括在内。子 agent 不代写已定原文，也不为了符合现有实现而改规则或放宽测试预期。
- 主会话先检索并决定复用、修改、新建及引用，再派实现与测试。子 agent 可以调研、核对、提出建议；发现缺口或矛盾时报告规则编号、具体情形和建议，由主会话决定并写入，相关工作等待，不相关工作继续。
- 多个主会话仍按各自任务与规则范围工作，不建立唯一的全项目主会话。主会话只改自己持有的 worktree；子 agent 持有的变更需要改规则时，先停下并通过既有流程交接，再由主会话改。规则、测试与代码继续遵守项目的同次提交和合入要求，不另开直接改共享 checkout 的通道。
- canon-parallel 在派发前准备规则，在任务书里写规则编号和预期。canon-test、canon-diagnose、canon-design、canon-triage、canon-product、canon-domains 中直接要求执行者补写或移动规则的入口指向 canon-rules，不另定义一套权限。
- 不增加 CLI 权限检查、hook、向量检索或新审批流程；这次不修改搜索引导，不自动更新其他项目安装的 skill 副本，更新仍按 D-9、D-10。

## 后果

- 实现与测试仍可并行，baseline 的实际写入集中到每项任务的主会话；主会话不可用时，相关规则调整必须等待或按既有交接流程换一个顶层会话接手。
- 主会话仍可能漏掉已有规则或误读需求；分工不是语义正确性的保证，已有检查、评审和验收继续使用。
- 这是工作引导，不是文件权限隔离；没有新增阻止子 agent 绕过引导的运行时机制。
