---
id: D-59
title: 全量测试和代码评审按阈值攒批，不逐次合入都跑
status: proposed
---

## 背景

2026-11-04 负责人给出的数字：15 小时内约 138 次合入，平均每小时 9 次，高峰每小时 23 次。

- `floor_timing: after` 下后台全量测试（`canon floor watch`，BR-2219）对 main 的最新提交首尾相接地测：每 8 到 13 分钟出一个结果，每次运行 6 到 28 分钟。机器 8 核，负载约 20，测试因超时偶发失败。
- 每次合入后 `hooks.after_land` 里的代码评审（`scripts/code-review.ts`，BR-2070、BR-2210）调一次 Sonnet，一天约 170 次调用。

两件事都是“每次合入都做一遍”，而它们只需要保证：每个合入过的提交最终被测过、被评审过。负责人的要求：两件事都少跑，不丢覆盖，也不靠任何人记得去触发。

## 方案

1. 不改：否决。负载和超时失败已经出现，评审调用量随合入数线性增长。
   - 来源：canon/config.yaml “先合后测（D-31、BR-2218）：开发阶段合入不等 floor”
2. 评审改挂在 `after_green`（测过才评审）：否决。main 红的时候 `after_green` 不运行，评审会停；而 `canon work after-land --wait` 读的是这次合入日志里的 `code-review:` 行（BR-2166、BR-2167），挪走后它拿不到答案。
3. 只让协调多个子 agent 的 agent 决定什么时候跑：否决。没有协调者时没人记得；几个会话同时在合入时也各自以为别人会触发。
4. 开集成分支，合入先进集成分支、攒够了再合 main：否决。出现两份共享记忆（集成分支和 main 的规则、决策、变更各一份），多一次合并，后面还要检测它们之间的矛盾。
5. 只用“没有后续合入”这一个触发（无定时器）：否决。所有会话都停了以后没有上限，积压的提交一直不测、不评审。
6. 按阈值攒批：后台测试和代码评审各自有“安静了一段时间、积压到一定个数、最老的积压够久”三个触发条件，任何一个满足就跑一次，覆盖整个积压范围：采用。
   - 来源：src/work/watch/redmain.ts “main is failing floor since”

## 决定

**后台全量测试（BR-2219 及其后续规则）**

- 新配置项 `floor_quiet_minutes: 20`、`floor_max_untested: 10`、`floor_max_age_minutes: 60`。main 上有没测过的提交时，满足任一条就测最新的提交：main 的最新一次移动已过 quiet 分钟；没测过的合入（`land.ok` 事件）达到 max_untested 个；最老的没测过的移动已过 max_age 分钟。数合入而不数提交：一次合入可能有几个提交，canon 自己还会直接在 main 上提交“open/close”。
- “main 的移动时间”取 main 分支 reflog 的时间，不取提交时间：一个很早提交、没有 rebase 就快进合入的提交，提交时间是几小时前，但 main 刚刚才动。读不到 reflog 时才退回提交时间。
- 后台进程在积压没到点时睡到最早的到点时间，期间 main 前移就重新计算；没有没测过的提交时退出。进程死了（被杀、机器重启）由下一次合入、`canon brief`、`canon sync` 里的 `ensureWatcher` 接手。诚实的保证只有这一条：积压最晚在“下一次有会话运行这几个命令之后”和到点时间两者中较晚的那个时刻开始测；没有会话再运行 canon 命令、而进程又被杀掉时，没有东西能唤醒它。
- 只改了 `floor_skip_paths` 下的路径（相对最近测过的提交）时，不跑 floor，记一条 `floor.skip` 事件，`tested()` 把它当作测过；日志里写明。
- main 没通过（BR-2220 的记录还在）时忽略 quiet，逐个提交首尾相接地测，和现在一样，好尽快发现修好没有。
- `canon floor watch --now` 立即测，不看阈值；协调多个子 agent 的 agent 在验证完一批后跑它（canon-parallel skill）。没加 `--now` 的 `canon floor watch` 是后台进程自己用的命令，按阈值等。
- `canon work status` 和 `canon brief` 在有没测过的合入时显示个数和下一次测试的时间或条件。
- BR-2222 的后果：重新构建 PATH 上 canon 的 `after_green` 最多比 main 晚 max_age 分钟（最坏更久，见保证）。

**合入后的代码评审（BR-2070、BR-2210，第二个变更）**

- 评审仍留在 `after_land`，每次合入运行一次脚本；脚本先不调 AI，只比较 `refs/canon/code-reviewed` 到 `CANON_HEAD` 的范围：不到 `review_max_unreviewed: 10` 个合入且最老的没评审合入不到 `review_max_age_minutes: 60` 分钟时，打印 `code-review: deferred` 一行并以 0 结束。到点就评审整个范围，评审成功（issue 已提交）后才用比较并交换推进引用；失败时引用不动，下次再试。
- 末尾那批没有“后续合入”来触发：`canon brief` 也判断是否到点，到点就在后台启动评审，不开守护进程。

## 后果

- 全量测试从“每个提交都测”变成“每批一次”：约 138 次合入每天只剩下几十次运行，负载下降；失败时的定位范围从一个提交变成一批，修 main 的变更要在批里找出原因（运行记录里有范围）。
- 评审调用从每天约 170 次降到约 17 次到 30 次；一个评审 issue 覆盖一批，每条发现尽量写明负责的变更。
- 红 main 的反馈延迟最多多出 max_age 分钟；PATH 上 canon 的重建同样。负责人可以用 `floor_quiet_minutes` 等三个键调回去，设成很小的值就接近现在的行为。
- 进程死了且无人运行 canon 命令时积压不会被测：这是已知限制，写在规则里。
