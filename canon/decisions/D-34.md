## 背景

`after` 模式（D-31）下 main 可能没通过，修复变更排在别的合入后面，就要等它们一个个合入完。负责人的要求（原话）：“并且有插队机制吗，有些需要优先合入的应该可以插队”；问到谁能插队时，负责人选了“修复变更自动插队，负责人可以标优先，agent 不能自己插队”。在这之前，合入严格按进入队列的顺序（BR-2020）。

## 方案

1. 入队时算一次优先级，存进队列表：否决。负责人在别人排队以后才标的优先、排队期间才出现的修复记录都不生效；要生效还得另做刷新。
2. 每次查看轮次时从 main 上的待办清单和协调数据库重新算：采用。每次多一次 `git cat-file`，代价小；负责人改清单马上生效。
   - 来源：canon/decisions/D-31.md “修复它的变更排在最前面”
3. 用命令行参数（例如 `canon work land --urgent`）标优先：否决。agent 能自己加参数，等于自己插队，负责人明确不要。
4. 在待办清单的列表项后面加标记（例如 `[优先]`）：否决。和排序混在同一行，不如单独一节一眼能看出哪些在插队；单独一节里的变更同时也排进了待办顺序，这正是“先做、先合”的意思。
5. 读变更自己 worktree 里的待办清单：否决。变更改自己那份就能插队；只读 main 上已提交的那份。

## 决定

采用方案 2：修复 main 的变更最先，其次是 main 上 `canon/backlog.md` 的 `优先合入` 一节列出的变更，其余按入队顺序；正在合入的不打断（BR-2232）。

## 后果

- 每个等待的合入者每次查看轮次时多读一次 main 上的待办清单。
- 低优先级的条目可能一直被后来的高优先级条目插到前面；修复变更只有一个，`优先合入` 由负责人控制，实际不会无限插队。
- 一起测（BR-2172）取成员的顺序跟着优先级走。
