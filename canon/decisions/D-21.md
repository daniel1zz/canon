---
id: D-21
title: 评审建议记在合入事件里，挂到它点名的文档上，下次评审这份文档时替换
status: accepted
---

## 背景

规则评审的“建议”不阻止合入，但 agent 常常为一条建议单独开一个变更。前 22 个变更里有 10 个在跟进建议（C-40）。N-3 的并发实测里，子 agent 为建议开了 C-106、C-107 两个跟进变更，每个都要再排一次约 2.5 分钟的 floor，而每次合入又对刚改的规则提出新的建议，停不下来。只写进 CLAUDE.md 不够：lore 的经验是规则写在常驻说明里、agent 读过，同一个会话里照样违反（C-40 里引用的 KN-183、KN-675）。所以要在机制上让建议有一个去处，并在有人要改那份文档时自动出现。

## 方案

1. 合入成功时，`land.ok` 事件记下这次评审的文档和建议；建议挂到它点名的文档上，没点名的挂到这次评审的所有文档上；一份文档只保留最近一次评审给它的建议，下次评审它时替换。`canon context` 和变更 worktree 里的 `canon brief` 显示这些建议，合入输出和工作说明写明建议不单独开变更。采用：不新增文件，不会越积越多（每份文档最多一批）；改一份文档时一定会再评审它，建议是否仍然成立由那次评审重新判断，不需要人或 agent 手动标“已处理”。
   - 来源：canon/notes/N-3.md “子 agent 为此开了 C-106、C-107 两个跟进变更”
   - 来源：src/knowledge/review/notes.ts “of them goes to every reviewed document, so no note is lost.”
2. 把建议写进变更文件的一个段落。否决：合入之后变更就关闭了，建议跟着沉在已完成的变更里，下一个改这条规则的人要翻遍所有变更才找得到；段落只增不减，也说不清哪条已经处理过。
3. 每条建议建一个 GitHub issue 或一个待办变更。否决：这正是要消除的做法，每条建议都会变成要排队的工作；代码评审的 issue 是给真缺陷的，混进措辞建议会稀释它。
   - 来源：canon/changes/C-40.md “前 22 个变更里有 10 个是在跟进规则评审的“建议””
4. 只在 CLAUDE.md 和工作说明里写“建议不单独开变更”。否决：没有机制保证，lore 的经验说明这样守不住；而且建议没有去处，agent 只能要么忽略、要么开变更。
   - 来源：canon/changes/C-40.md “只写进 CLAUDE.md 大概率守不住”

## 决定

- 评审建议只记在成功合入的 `land.ok` 事件里（BR-2145），不写文件，不开变更，不提 issue。
- `canon context` 列出上下文里规则和决策的未处理建议（BR-2146）；在变更的 worktree 里，`canon brief` 列出这个变更提到的文档的未处理建议（BR-2147）。改到这份文档的人顺手处理；下次评审替换旧建议。
- 合入输出和 `canon brief` 的工作说明都写明：建议不拦截、不单独开变更；只有“拦截”和真缺陷马上处理。

## 后果

- 从这次合入开始的建议才有记录；之前的建议只在旧的 `review.ok` 事件里，不显示。
- 建议点名的编号要准确；评审提示本来就要求每条建议写明编号。没点名的建议挂到这次评审的每份文档上，可能多显示几处。
- 一份文档改了但评审没跑（没配置评审）时，旧建议照旧显示，可能已经过时。
- 效果要看数据：之后一段时间里，因建议而开的变更数应接近 0。
