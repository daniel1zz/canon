## 背景

执行者只到会话一级（BR-2023，D-18）：同一个 Claude Code 会话里，主 agent 和它派出的子 agent 是同一个执行者，认领分不开它们。D-18 当时的判断是“一个 agent 只做一个变更，两个 agent 不会通过 canon 进入同一个 worktree”，并且明说“同一个会话的两个 agent 如果不顾提示进入同一个 worktree，canon 分不开它们，也挡不住”。

这个前提在 C-337 里被事实打破：主 agent 用“目录不存在就取最后一个 worktree”的写法进了 worktree，落进子 agent 正在做的 C-336，在那里提交并尝试合入。它不是“不顾提示”：提示根本没有出现，因为进入 worktree 不经过 canon 的认领命令；合入时 BR-2104 比较的是执行者，两边相同，所以通过。事故是同一个 Bash 调用里先 `cd` 进别人的 worktree，再 `git commit`、再 `canon work land`。

要拦的是：同一个会话里，一个 agent（常见是主 agent）误进另一个 agent 正在做的变更的 worktree，并在那里提交、合入、放开认领。合作的 agent 的误操作，不是防冒充（沿用 D-17、D-18 的前提）。

### 第一轮查证（2026-11-05，Claude Code 2.1.318，文档）

- hooks 文档：子 agent 里的 PreToolUse、PostToolUse 等输入带 `agent_id` 和 `agent_type`，主会话里的调用没有 `agent_id`；settings 里的 hook 在子 agent 里照常运行。
- `agent_id` 不在 Bash 命令的环境变量里；`CLAUDE_CODE_CHILD_SESSION=1` 对主会话和子 agent 一样，不能区分；`CLAUDE_ENV_FILE` 不给 PreToolUse，而且是会话级的文件。
- PreToolUse 返回 `updatedInput` 会改写命令，Claude Code 按改写后的输入重新核对权限规则。`permissionDecision: "allow"` 会跳过用户对整条命令的确认（deny 和 ask 规则仍生效），`"ask"` 让用户确认；不给 `permissionDecision` 时 auto 模式可能拒绝被 hook 改过的调用。canon 不能用 `allow` 替用户批准命令。
- PreToolUse 返回 `deny` 或退出码 2 能拦住调用；D-30 已实测 bypassPermissions 下同样拦得住。
- `CwdChanged` 只在主会话里的 shell 命令改变目录时触发，不能拦截。`SubagentStop` 有，退出时不保证触发（D-11 查到 lore 的会话结束类 hook 约 16% 不触发）。

历史：D-17（C-91、C-93）做过“hook 注入身份”，D-18 撤回，理由是每次调用多约 36 ms、放行规则太宽（#26）、没装 hook 的项目没有保护，以及“canon 本来就不允许两个 agent 进同一个 worktree”。D-30 证明第一条不成立（每次约 60 ms，占 0.1%），最后一条被 C-337 证明不成立；#26 和未装 hook 的缺口仍然成立。

### 第二轮实测（2026-11-05，同一版本，`claude -p --model haiku`，haiku 子 agent，每个命令单独一个调用）

目录：`/private/tmp/claude-501/-Users-apple-Projects-zz-canon/0b2e14ae-7ccf-499b-9f18-e0c549f25f21/scratchpad/hookexp`（`hook2.sh` 是 hook，`s/raw_*.jsonl` 是 `--output-format stream-json --verbose` 的原始输出，`summarize.sh` 从中取出子 agent 每个 Bash 调用的 tool_result，`s/log_*.jsonl` 是 hook 日志）。结论以工具返回的 `is_error` 和文字为准，不用模型自述（模型自述有错：它多次把“被拒”说成“可能是子 agent 的环境问题”）。

**实测一：子 agent 的 `cwd` 不是它自己的目录。**

- 主会话 `cd a` 之后，子 agent 的第一个调用的 `cwd` 是 `a`（继承主会话当时的目录）。
- 子 agent 用一个单独的调用 `cd b`，下一个调用的 `pwd` 仍然是 `proj`（目录不跨调用保留），hook 收到的 `cwd` 也一直是主会话的目录。
- 所以子 agent 每个调用都要自己 `cd`，hook 看到的 `cwd` 永远不是子 agent 的 worktree。**原方案 2（按 `cwd` 登记在场者）的前提不成立。**

**实测二：hook 能把 `agent_id` 注入命令。** 子 agent 的命令里 `$EXP_AGENT` 是它的 `agent_id`，主会话的命令里为空。注入本身可行；问题在权限。

**实测三：只返回 `updatedInput`（不给 `permissionDecision`）时，改写后的命令还能不能被权限规则匹配。** 命令是 `git status --short`（允许规则 `Bash(git status*)`）和 `git log --oneline -1`（Claude Code 内置的只读命令，不需要规则就放行）。`none` 是 hook 不改写的对照。`-p` 模式没有人可以确认，所以“需要确认”在这里表现为 `is_error: true`；`-p` 里原文是 “requires approval” 的，交互模式下就是弹确认。

| 权限模式 | 对照（不改写） | 前缀写法 `CANON_ACTOR=<id> <命令>` | 分号写法 `export CANON_ACTOR=<id>; <命令>` |
|---|---|---|---|
| default | 两个都执行 | 两个都被拒（`Permission to use Bash has been denied`，交互时是确认） | 两个都被拒（`This Bash command contains multiple operations. The following part requires approval: export CANON_ACTOR=…`） |
| acceptEdits | 未测 | 两个都被拒（`This command requires approval`） | 两个都被拒（同上，`export` 一段需要确认） |
| dontAsk | 两个都执行 | 两个都被拒（`…denied because Claude Code is running in don't ask mode`） | 两个都被拒（同上） |
| auto | 两个都执行 | 两个都执行 | 两个都执行 |
| bypassPermissions | 未测 | 两个都执行 | 两个都执行 |

原始输出：`s/raw_{none,prefix,export}_{default,dontAsk,auto}.jsonl`、`s/raw_{prefix,export}_{acceptEdits,bypassPermissions}.jsonl`。default、dontAsk、auto 三个模式的第一次运行（没有用 stream-json，只有 hook 日志和模型自述）结果相同。

**实测四：再给一条放行规则 `Bash(export CANON_ACTOR=*)`（这是 D-17 做过、因 #26 撤回的规则）。** 分号写法和换行写法（`export CANON_ACTOR=<id>` 换行再接命令）在 default、acceptEdits、dontAsk 下，`git status --short`（有自己的规则）执行了，但 `git log --oneline -1`（原本靠内置只读放行）被拒：命令被改写成带前缀的复合命令之后，内置的只读放行不再适用，每个没有写进规则的命令都要确认或被拒。原始输出：`s/raw_w_{export,exportnl}_{default,dontAsk,acceptEdits}.jsonl`。

结论：**不给 `permissionDecision` 的注入，只在 auto 和 bypassPermissions 下不影响权限；在 default、acceptEdits、dontAsk 下，子 agent 的每个 Bash 命令都要确认（交互）或被拒（dontAsk、`-p`），连只读的 `git log` 也一样。** 补放行规则能让写进规则的命令通过，但内置只读放行失效，而且那条规则 `export CANON_ACTOR=*` 就是 #26 的问题（它匹配任何以这个前缀开头的 export，包括同一行里设别的环境变量；规则里的 id 每个子 agent 不同，写不成精确匹配）。

## 方案

每个方案的“拦不住”里都有三件事不在 canon 管辖内，不再逐个重复：用户自己在终端操作（不经 Claude Code，没有 hook）；非 Claude Code 的 agent（没有 `agent_id`）；故意绕过的 agent（改环境变量、换路径写法）。

1. **hook 按调用的 `cwd` 登记谁在 worktree 里，拒绝别的身份（原推荐）**：否决。前提（hook 看到的 `cwd` 是调用者自己的）被实测一推翻。独立审查还指出三点：转换规则（主会话先进入、子 agent 后进入、`SubagentStop`、空闲超时）有竞态；依赖不保证触发的 `SubagentStop`；没核对 C-337 的实际命令。核对结果：事故是同一个调用里 `cd` 进去再提交、合入，hook 只看得到调用开始时的 `cwd`，这个方案本来就拦不住它。
   - 拦得住：没有可靠的依据，hook 看到的 `cwd` 是主会话的。
   - 依据：本文实测一。
2. **hook 注入身份，不给 `permissionDecision`（恢复 D-17）**：PreToolUse hook 在子 agent 的每个 Bash 命令前加 `export CANON_ACTOR='agent:<会话>:<agent_id>'`（或前缀写法），canon 照 BR-2023 用它构成执行者。否决：在常用的权限模式下不可用，见实测三、四。
   - 拦得住（假设注入生效）：别的 agent 在这个 worktree 里运行 `canon work land`、`stop`（退出码 5），C-337 的那次合入会被拒。
   - 拦不住：`git add`、`git commit`、改文件这类不经过 canon 的操作；没装 hook 的项目；hook 失败的那一次调用（要放行，否则整个会话的 Bash 都不能用）。
   - 代价（实测）：default、acceptEdits 下子 agent 的每个 Bash 命令都要用户确认，dontAsk 下全部被拒，auto 和 bypassPermissions 下没有影响。补放行规则会重新引入 #26，而且内置的只读放行仍然失效。
   - 失败方式：身份缺失时退回会话一级，是无声的退化。
   - 依据：本文实测三、实测四。
3. **`permissionDecision: "allow"` 的注入**：否决，不实测。它跳过用户对整条命令的确认，canon 不能替用户批准命令。
   - 来源：https://code.claude.com/docs/en/hooks.md “PreToolUse decision control”
4. **只在 auto、bypassPermissions 下注入**：hook 读输入里的 `permission_mode`，别的模式不改写。否决：保护随权限模式开关，default 下的子 agent 没有身份，而“没有 `agent_id` 注入”和“主会话”在 canon 看来一模一样，没法大声失败。
5. **派发时给子 agent 起名字，名字写在 canon 命令的参数里（`--as`）**：不用 hook，不改写命令。主 agent 派发时为每个子 agent 起一个名字，认领和之后的持有者命令都带 `--as <名字>`，执行者是 `agent:<会话>:<名字>`；没带名字的调用（主会话）不是这个持有者。采用（提议）。
   - 做法：`canon work start --title "…" --as <名字>`（或 `canon work start C-n --as <名字>`）认领时，持有者记为 `agent:<会话前 8 位>:<名字>`；这个 worktree 里的 `canon work land`、`stop`（BR-2104）要带同一个 `--as <名字>`，不带或带错 → 退出码 5，提示写明持有者是子 agent `<名字>`，不是它的话不要进入这个 worktree。`--as` 是普通命令参数，写在 canon 命令后面，所以匹配用户的 `Bash(canon work *)` 之类的规则，不像环境变量前缀那样让整条命令的权限匹配失效（实测三里 `git status --short` 被 `Bash(git status*)` 匹配而前缀写法不被匹配；canon 命令用 `--as` 是否同样匹配，实现时要用实测确认）。
   - 拦得住：C-337 的合入。主会话没有名字，`cd` 进别人的 worktree 之后，同一个调用里的 `canon work land`、`stop` 照样被拒，单个调用里先 `cd` 再合入也被拒，因为检查发生在 canon 命令里，不在 hook 对 `cwd` 的猜测上。
   - 拦不住：`git add`、`git commit`、改文件这类不经 canon 的操作（和方案 2 一样）；子 agent 起始时忘了 `--as`：认领记成会话一级，没有保护，而且这时是无声的；canon 能做的是让主 agent 事后看得见：`canon work status` 和 `canon events` 里执行者没有名字，canon-parallel 的核对步骤加一条。子 agent 之后再带 `--as` 运行 `land` 会被拒（持有者是 `agent:<会话>`），这时是大声的。
   - 身份缺失或格式不对要大声失败：`--as` 的值只允许字母、数字、`-`、`_`，其他 → 退出码 2、什么都不写；`--as` 不在 Claude Code 会话里用（`CLAUDECODE` 没有设）→ 退出码 2；不同时给 `--as` 和 `CANON_ACTOR`（两个来源冲突）→ 退出码 2。
   - 子 agent 结束后主会话接手：子 agent 和主会话是同一个进程，认领的进程探测（BR-2100）放不开，租约又是 12 小时（BR-2011），所以必须有一个显式命令。最小的改法不加新命令：主会话运行 `canon work stop --release --as <名字> --next "<下一步>"`，也就是它明确写出子 agent 的名字来放开认领；事件里记的执行者是这个名字，看不出是主会话还是子 agent 运行的（执行者只到名字一级，P6 的粒度没有变），再 `canon work start C-n` 认领。这样接手需要主 agent 主动写出名字，C-337 那样“误进”不会发生；它也不防主会话故意写。不恢复 BR-2129 的 `--takeover`。
   - 和现有规则的关系：BR-2023 增加“`--as` 构成 `agent:<会话>:<名字>`”一条，和 `CANON_ACTOR=agent:x:y`（照原样使用）同一个形式，不新增执行者形式；BR-2011 的“同一个执行者也被拒绝”一句、BR-2104 的“边界”一句、BR-2131 的末句要改；canon-parallel skill 的派发清单加“主 agent 起名，`start` 和之后的持有者命令都带 `--as <名字>`”。
   - 失败方式：不依赖任何 hook，没有“hook 装了但没生效”的状态；没装 canon 的项目本来就没有协调。
   - 需要先查实：`--as` 写在命令后面是否让 `Bash(canon work *)` 之类的规则照常匹配（预期照常，按“实测三”对照组的行为）；事件表、`canon stats`、`canon status` 里出现 `agent:<会话>:<名字>` 的形式是否破坏现有按执行者的统计（BR-2023 已允许这种值，D-18 留下的统计按 worktree 分，预期不破坏）。
   - 依据：本文实测三。
   - 来源：canon/decisions/D-18.md “只是一个普通的名字，不再解析”
6. **不做，只靠文字**：否决为唯一手段。在 `canon brief` 和 skill 里写“进入 worktree 只用 `canon work start` 打印的路径，不要用 `ls | tail` 之类推出来”，C-337 的教训写进变更文件。理由：单独什么都拦不住，只降低误进的概率；但文字部分和方案 5 一起做（见决定）。
7. **推迟，等 Claude Code 把 `agent_id` 放进环境变量或把 `cwd` 做成子 agent 自己的**：否决（现在不做）。现在的 Claude Code 不提供这两样，canon 没办法让它们成立。如果方案 5 实现后事件表里仍然出现误进，再回来评估。

## 决定

**否决方案 1（按 `cwd` 登记）和方案 2、3、4（hook 注入）；提议方案 5（派发时起名，`--as` 带名字）加方案 6 的文字部分。** 按实测，注入在 default、acceptEdits、dontAsk 下让子 agent 的每个命令需要确认或被拒，不给 `permissionDecision` 时没有办法避免，canon 又不能用 `allow`；补放行规则回到 #26。所以不选注入。

- 实现前要先做“需要先查实”里的两项，结果写进变更文件；`--as` 写在 canon 命令后面不被权限规则匹配的话，退回本决定重新评审，不硬做。
- 认领的持有者可以带名字（`agent:<会话>:<名字>`）；主会话不带名字，进不了子 agent 持有的 worktree 的 `land`、`stop`。
- `--as` 的值缺失、格式不对、不在 Claude Code 会话里用、和 `CANON_ACTOR` 同时给 → 退出码 2，什么都不写。
- 接手：主会话运行 `canon work stop --release --as <名字> --next "<下一步>"`，不新增命令。
- `canon brief` 的工作流说明加一句：进入 worktree 只用 start 打印的路径；canon-parallel skill 的派发清单加起名和 `--as`。
- 不做 hook。

## 后果

- C-337 那类“主会话进入子 agent 的 worktree 之后 `canon work land`”会被拒绝（退出码 5），不论 `cd` 和 `land` 是不是写在同一个调用里。这是原方案 2 拦不住、注入方案只在 auto 和 bypassPermissions 下才拦得住的情形。
- **仍然拦不住**：不经过 canon 的操作（`git add`、`git commit`、改文件）仍然会落进别人的 worktree，被拒的只有 canon 的 `land` 和 `stop`；子 agent 没带 `--as` 认领时没有保护，且是无声的，只能靠主 agent 在事件表里核对；`cwd` 不是子 agent 自己的（实测一），所以任何按 `cwd` 判断的 hook 都没有可用的依据，没有别的办法在 hook 里拦 `git commit`。
- 这个方案的名字是 agent 自己写在命令里的，不是 Claude Code 证明过的 `agent_id`：它防误操作，不防一个主动写出别人名字的 agent（沿用 D-17、D-18 的前提：合作的 agent）。
- 不增加 hook，不改写命令，不装放行规则；D-1 和 D-30 的“只记录、不拦”不受影响，所以 `amends` 只列 D-18。
- 要改的规则：BR-2023（增加 `--as`）、BR-2011（同一执行者那句和 start 的 `--as`）、BR-2104（“边界”一句）、BR-2131（末句），以及 `--as` 的错误情形各一个例子；新规则放 `work/claims` 领域。D-18 的“决定”和“后果”里关于“同一会话的 agent 进同一个 worktree，canon 挡不住”的两句由本决定修正（接受时生效）。
- 要改的代码：`src/work/workspace.ts`（执行者的确定，BR-2023）、`src/work/claims/claims.ts`（持有者检查和拒绝提示）、`src/work/commands.ts`（`start`、`land`、`stop` 的 `--as` 参数）、`.claude/skills/canon-parallel/SKILL.md`。hook 相关的代码（`src/config/hooks.ts` 现在在这里，领域重划之后可能搬到 `src/work/hooks/`；`src/cli/install/hook.ts`）这次不动。
