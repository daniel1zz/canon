---
id: D-62
title: 同一会话里主 agent 和子 agent 怎样不进入对方认领的 worktree
status: proposed

## 背景

执行者只到会话一级（BR-2023，D-18）：同一个 Claude Code 会话里，主 agent 和它派出的子 agent 是同一个执行者，认领分不开它们。D-18 当时的判断是“一个 agent 只做一个变更，两个 agent 不会通过 canon 进入同一个 worktree”，并且明说“同一个会话的两个 agent 如果不顾提示进入同一个 worktree，canon 分不开它们，也挡不住”。

这个前提在 C-337 里被事实打破：主 agent 用“目录不存在就取最后一个 worktree”的写法进了 worktree，落进子 agent 正在做的 C-336，在那里提交并尝试合入。它不是“不顾提示”：提示根本没有出现，因为进入 worktree 不经过 canon 的认领命令；合入时 BR-2104 比较的是执行者，两边相同，所以通过。

本次查证（2026-11-05，Claude Code 2.1.318）：

- hooks 文档：子 agent 里的 PreToolUse、PostToolUse 等输入带 `agent_id` 和 `agent_type`，主会话里的调用没有 `agent_id`；settings 里的 hook 在子 agent 里照常运行（hooks.md “Hooks from settings files … also run inside subagents”）。输入里还有 `session_id`、`cwd`（“after Claude runs `cd`” 为新目录）、`tool_use_id`。
- `agent_id` 不在 Bash 命令的环境变量里。这个子 agent 的环境里和 Claude Code 有关的变量是 `CLAUDECODE`、`CLAUDE_PID`、`CLAUDE_CODE_SESSION_ID`、`CLAUDE_CODE_CHILD_SESSION` 等，没有一个是 agent 标识；env-vars.md 写明 `CLAUDE_CODE_CHILD_SESSION=1` 对 Bash 工具派生的所有子进程都设（主会话也一样），不能用来区分。`CLAUDE_ENV_FILE` 只给 SessionStart、Setup、CwdChanged、FileChanged，不给 PreToolUse，而且是会话级的文件，几个 agent 同时跑会互相覆盖。
- PreToolUse 返回 `updatedInput` 会改写命令，但 Claude Code 对改写后的命令重新核对权限规则；不带 `permissionDecision` 时，auto 模式可以拒绝这种“被 hook 改过”的调用（hooks.md “PreToolUse `updatedInput` in auto mode”）。`permissionDecision: "allow"` 会跳过用户对整条命令的确认。
- PreToolUse 返回 `deny` 或退出码 2 能拦住调用；D-30 已实测 bypassPermissions 下同样拦得住。
- `CwdChanged` hook 只在“主会话里的 shell 命令改变了工作目录”时触发，输入是 `old_cwd` 和 `new_cwd`，不能拦截，只能用 `systemMessage` 提示。`SubagentStop` 有，输入带 `agent_id`，退出时不保证一定触发（D-11 查到 lore 的会话结束类 hook 约 16% 不触发）。
- 没有查到：子 agent 的 Bash 调用里 `cwd` 是不是它自己的目录（还是跟着主会话）。这个子 agent 不能再派子 agent，没有实测；实现时必须用真实的主会话加子 agent 先测。

历史：D-17（C-91、C-93）做过“hook 注入身份”，D-18 撤回，理由是每次调用多约 36 ms、放行规则太宽（#26）、没装 hook 的项目没有保护，以及“canon 本来就不允许两个 agent 进同一个 worktree”。D-30 已经证明第一条不成立（每次约 60 ms，占 0.1%），最后一条被 C-337 证明不成立；#26 和未装 hook 的缺口仍然成立。

要拦的是：同一个会话里，一个 agent（常见是主 agent）误进另一个 agent 正在做的变更的 worktree，并在那里提交、合入、放开认领。合作的 agent 的误操作，不是防冒充（沿用 D-17、D-18 的前提）。

## 方案

每个方案的“拦不住”里都有三件事不在 canon 管辖内，不再逐个重复：用户自己在终端操作（不经 Claude Code，没有 hook）；非 Claude Code 的 agent（没有 `agent_id`）；故意绕过的 agent（改环境变量、换路径写法）。

1. **注入身份（恢复 D-17）**：PreToolUse hook 在子 agent 的每个 Bash 命令前加一行 `export CANON_ACTOR='agent:<会话>:<agent_id>'`，canon 照 BR-2023 用它构成执行者；认领、BR-2104 的持有者检查随之按 agent 分开。否决。
   - 拦得住：别的 agent 在这个 worktree 里运行 `canon work land`、`stop`、`stop --release`（退出码 5）；别的 agent 的 `canon work start`、`drop`。只有这个方案能拦住 C-337 里那次合入。
   - 拦不住：`git add`、`git commit`、改文件这类不经过 canon 的操作，仍然落进别人的 worktree；没装 hook 或 PATH 上没有 canon 的项目；hook 失败的那一次调用（要放行，否则会话的所有 Bash 都不能用）。
   - 认领和交接：现有认领的持有者是主会话的 `agent:<会话>`，改后子 agent 的认领和主会话的认领是两个名字。主会话启动变更、子 agent 去合入（D-18 说“又可行了”的做法）会被拒绝，子 agent 做完由主会话收尾也会被拒绝，要恢复 `--takeover` 之类的显式交接（BR-2129 已退役）。事件表、认领表、`canon stats` 里出现新形式的执行者，旧数据不动。
   - 失败方式：身份缺失时退回会话一级，是无声的退化（和“必需的值缺失要大声失败”冲突）；hook 装了但没生效时 canon 看不出来。
   - 其他代价：auto 模式可能拒绝“被 hook 改过”的命令；要么再装一条放行规则（#26 的老问题，规则只能写成通配），要么用 `allow`（跳过用户对整条命令的确认），两者都不好。要改的规则：BR-2023、BR-2011、BR-2104、BR-2127 到 BR-2130（恢复或重写）、BR-2131、BR-2185 旁加一条。
   - 来源：https://code.claude.com/docs/en/hooks.md “a hook changed this call's input after auto mode reviewed it”
   - 来源：https://code.claude.com/docs/en/env-vars.md “subprocesses Claude Code spawns via the Bash, PowerShell, and Monitor tools”
   - 来源：canon/decisions/D-30.md “本会话约 2 小时调用 Bash 152 次”
2. **hook 只拒绝，不改写：按 worktree 记录谁在里面（在场登记）**：PreToolUse hook（和现在的快照 hook 同一个入口）读 `agent_id`、`session_id`、`cwd`。`cwd` 在一个有有效认领的 canon worktree 里时，canon 查这个 worktree 的在场登记（新表，worktree 对应当前在场者：主会话，或某个 `agent_id`，加最后一次出现的时间）：没有登记就登记这次调用的身份；是在场者就放行并刷新时间；不是就拒绝，说明谁在里面、怎么进、怎么让出。不改执行者，不改命令，不装放行规则。采用。
   - 在场者的转换（规则里写细）：主会话先进入、子 agent 后进入时，在场者交给这个子 agent（主会话派它去做）；子 agent 在场时，主会话和别的子 agent 被拒绝；`SubagentStop` 或超过空闲时间（配置项，默认值在规则里定）后，让回主会话或空出；`canon work` 下加一个显式的让出或接手命令，在 worktree 外也能运行，给“子 agent 没正常结束”和“主会话要接手收尾”用。
   - 拦得住：在场登记之后的所有调用，不管命令是 `git commit`、改文件还是 `canon work land`，都在命令运行之前拒绝，所以也拦得住不经过 canon 的操作；主会话 `cd` 进去之后的下一个调用就被拒绝，提示它回去。
   - 拦不住：**单个调用里先 `cd` 进别人的 worktree 再做事**。hook 只能看到调用开始时的 `cwd` 和命令文字，像 C-337 那样用算出来的路径进入时，如果“进入、提交、合入”写在一个调用里（例如 `cd $(ls … | tail -1) && git commit && canon work land`），第一个调用不会被拒绝，被拒绝的是紧接着的下一个调用（`cwd` 已经在里面）。命令里直接写出 worktree 路径、也只能靠文字匹配，算出来的路径看不到；D-30 已经论证过解析命令文字不可靠，这里不做。`git -C <路径>` 同理。另有一个误拒风险：被拒绝时 agent 要用一个单独的 `cd <目录>` 出来，这种最简单的形式放行（只认整条命令就是一个 `cd`），带 `&&` 的不放行。
   - 认领和交接：认领表、执行者、交接记录（handoff）都不动；新加一张在场表，旧数据库打开时补表（BR-2078 的做法）。D-18 说的“同一会话的 agent 进同一个 worktree，canon 挡不住”变成“只在调用级挡，且只挡下一个调用”。
   - 失败方式：和快照 hook 一样，canon 崩溃或不在 PATH 上时放行，同时输出 `systemMessage` 告诉用户（不然一个坏掉的 canon 会让整个会话没法用 Bash）；`canon update --check` 把缺少的 hook 报为过期。拒绝本身是大声的：退出码 2、写明原因和出路。
   - 需要先查实：子 agent 的 `cwd` 是不是它自己的；如果跟着主会话，在场登记要改用别的依据，这个方案要重做。
   - 与 D-1 的关系：D-1 写的是“没有任何 hook 检查 agent 怎么干活”，D-30 已经修正过一次，保持“只记录、不拦”。这个方案是拦，但拦的不是命令做什么，而是调用在哪个 worktree、那个 worktree 的在场者是谁，属于 P4（互不覆盖）的边界检查，不是判断 agent 的做法；D-1 的 hook 误拒数据（54 次里 46 次误拒）是对命令文字的判断，这里不解析命令。采用时要修改 D-1 和 D-30 的说法。
   - 来源：https://code.claude.com/docs/en/hooks.md “fire the same configured hooks as in the main conversation”
   - 来源：https://code.claude.com/docs/en/hooks.md “Other hook events don't have access to this variable”
   - 来源：canon/decisions/D-1.md “没有任何 hook 检查 agent 怎么干活”
   - 来源：canon/decisions/D-18.md “同一个会话的两个 agent 如果不顾提示进入同一个 worktree，canon 分不开它们，也挡不住”
3. **只提醒，不拒绝**：同样的在场登记，但命中时只用 `systemMessage` 提示用户和 agent（主会话的 `cd` 另外用 `CwdChanged` hook 提示，它只在主会话触发，正好是 C-337 的情形），不拒绝调用。否决。
   - 拦得住：什么都拦不住，只是让用户和 agent 看见。优点是不会误拒、不与 D-1 冲突。
   - 拦不住：agent 往往不理会 `systemMessage`（它主要给用户看），C-337 里主 agent 在那个 worktree 里提交并尝试合入，没有停；用户不盯着时等于没有。
   - 认领和交接：不动。失败方式：提醒本身是大声的，但没人会读。要改的规则：新增一条提醒规则。
   - 来源：https://code.claude.com/docs/en/hooks.md “They can't block the directory change”
4. **不靠 hook：worktree 绑定第一次进入它的身份**：由 canon 在 `canon work start`、`canon work land` 等命令里记下“谁第一个进入”，之后别的身份进入就拒绝。否决。
   - 否决原因：canon 命令运行时拿不到调用者的 `agent_id`（环境里没有，上面已查）；能得到的只有会话 id 和 `CLAUDE_PID`，两者对主会话和子 agent 相同（D-11）。没有 hook 就没有可以绑定的东西；有 hook 就回到方案 1 或 2。
   - 也不能靠“hook 先记一条、canon 命令再去对”：多个 agent 同时在运行时，canon 命令分不清哪一个在途调用是自己的（`tool_use_id` 不在环境里），对错的时候正好是两个 agent 同时在同一个目录里，也就是要拦的情形。
   - 来源：canon/decisions/D-11.md “多个并行子 agent 都记为同一个”
5. **不做，只靠文字**：在工作流说明（`canon brief`）和 skill 里写“进入 worktree 只用 `canon work start` 打印的路径，不要用 `ls | tail` 之类推出来”，C-337 的教训写进变更文件。否决为唯一手段，但文字部分仍然要写（见决定）。
   - 拦得住：什么都拦不住，只降低误进的概率；文字不会改变一个已经决定用算出来的路径的 agent 的做法。
   - 认领和交接：不动。失败方式：无声。要改的规则：无。
6. **方案 1 加方案 2**：否决，现在不做。覆盖最全（方案 1 补上方案 2 拦不住的单调用合入），但继承方案 1 的全部代价，而 C-337 的危害是“落进别人的 worktree 提交并尝试合入”，方案 2 在这之后的下一个调用就拦住，合入尝试只有在写成同一个调用时才会通过。如果实现后的事件表里仍出现同一调用内的合入，再单独提方案 1，它和方案 2 不冲突，可以叠加。

## 决定

采用方案 2（hook 只拒绝，按 worktree 的在场登记），同时做方案 5 里的文字部分。

- 执行者、认领表和交接记录不改；BR-2023、BR-2011 的“同一会话是同一个执行者”仍然成立。
- 实现时先用真实的主会话加子 agent 实测：子 agent 的 `cwd`、`agent_id` 在嵌套子 agent 里的取值、`SubagentStop` 的触发情况，实测结果写进变更文件；`cwd` 不是子 agent 自己的则退回本决定重新评审。
- hook 只在 worktree 有有效认领时检查；拒绝用退出码 2 并写明在场者和出路；canon 自己失败时放行并输出 `systemMessage`；`canon update --check` 报缺失。
- 单独的 `cd <目录>` 放行；不解析别的命令文字。
- `canon brief` 的工作流说明加一句：进入 worktree 只用 start 打印的路径。

## 后果

- 同一会话里，一个 agent 进入别人的 worktree 之后，下一个调用被拒绝，不论它做什么；以前这种情形没有任何提示。
- 同一个调用里先进入再提交、合入，这次决定仍然拦不住；这一点要写进规则的边界，并在实现后看事件表里的拒绝和 `canon work land` 的记录，数据说明有必要时再叠加方案 1。
- 每次 Bash 调用多一次 canon 启动（快照 hook 已经在做；两件事能放进同一次启动，实现时合并，避免多一个进程）。
- 要改的规则：新增“在场登记”和“拒绝进入别人在场的 worktree”两条规则（`work/claims` 领域），新增 hook 安装规则（接在 BR-2185 旁），BR-2104 的“边界”一句、BR-2011 的原因一句和 BR-2131 的末句要改成指向新规则；D-18 的“决定”和“后果”里关于“挡不住”的两句，D-1 的“没有任何 hook 检查”一句，在接受时标为被本决定修正（`amends`）。
- 要改的代码：`src/cli/install/hook.ts`（hook 命令常量、合并、`planHook`、`hookStatus`）和 `src/cli/install/update.ts`（`--check` 列表）；`src/work/snapshots/commands.ts` 的 `--hook` 读 stdin 的写法可以照用；`src/work/db.ts`（新表和旧库补表）；`src/work/claims/` 下新增在场登记和检查（认领查询用 `claims.ts` 里已有的函数）；`src/work/commands.ts` 注册新的 hook 命令和让出命令。
- 没有 hook 的环境（用户终端、别的 agent 工具、没装 canon hook 的项目）里仍然没有这层保护；这是接受的边界，和 D-18 一致。
