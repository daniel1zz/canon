## 背景

执行者只到会话一级（BR-2023，D-18）：同一个 Claude Code 会话里，主 agent 和它派出的子 agent 是同一个执行者，认领分不开它们。D-18 当时的判断是“一个 agent 只做一个变更，两个 agent 不会通过 canon 进入同一个 worktree”，并且明说“同一个会话的两个 agent 如果不顾提示进入同一个 worktree，canon 分不开它们，也挡不住”。

这个前提在 C-337 里被事实打破：主 agent 用“目录不存在就取最后一个 worktree”的写法进了 worktree，落进子 agent 正在做的 C-336，在那里提交并尝试合入。它不是“不顾提示”：提示根本没有出现，因为进入 worktree 不经过 canon 的认领命令；合入时 BR-2104 比较的是执行者，两边相同，所以通过。事故是同一个 Bash 调用里先 `cd` 进别人的 worktree，再 `git commit`、再 `canon work land`。

要拦的是：同一个会话里，一个 agent（常见是主 agent）误进另一个 agent 正在做的变更的 worktree，并在那里提交、合入、放开认领。合作的 agent 的误操作，不是防冒充（沿用 D-17、D-18 的前提）。

### 第一轮查证（2026-11-05，Claude Code 2.1.318，文档）

- hooks 文档：子 agent 里的 PreToolUse、PostToolUse 等输入带 `agent_id` 和 `agent_type`，主会话里的调用没有 `agent_id`；settings 里的 hook 在子 agent 里照常运行。
- `agent_id` 不在 Bash 命令的环境变量里；`CLAUDE_CODE_CHILD_SESSION=1` 对主会话和子 agent 一样，不能区分；`CLAUDE_ENV_FILE` 不给 PreToolUse，而且是会话级的文件。
- PreToolUse 返回 `updatedInput` 会改写命令，Claude Code 按改写后的输入重新核对权限规则。`permissionDecision: "allow"` 会跳过用户对整条命令的确认（deny 和 ask 规则仍生效），`"ask"` 让用户确认；不给 `permissionDecision` 时 auto 模式可能拒绝被 hook 改过的调用。canon 不能用 `allow` 替用户批准命令。
- PreToolUse 返回 `deny` 或退出码 2 能拦住调用；D-30 已实测 bypassPermissions 下同样拦得住。
- `CwdChanged` 只在主会话里的 shell 命令改变目录时触发，不能拦截。`SubagentStop` 有，退出时不保证触发（D-11 查到 lore 的会话结束类 hook 约 16% 不触发）。

历史：D-17（C-91、C-93）做过“hook 注入身份”，D-18 撤回，理由是每次调用多约 36 ms、放行规则太宽（#26）、没装 hook 的项目没有保护，以及“canon 本来就不允许两个 agent 进同一个 worktree”。D-30 证明第一条不成立（每次约 60 ms，占 0.1%），最后一条被 C-337 证明不成立；#26 和未装 hook 的缺口仍然成立。

### 第二轮实测（2026-11-05，同一版本，`claude -p --model haiku`，haiku 子 agent，每个命令单独一个调用）

目录：`/private/tmp/claude-501/-Users-apple-Projects-zz-canon/0b2e14ae-7ccf-499b-9f18-e0c549f25f21/scratchpad/hookexp`（`hook2.sh` 是 hook，`s/raw_*.jsonl` 是 `--output-format stream-json --verbose` 的原始输出，`summarize.sh` 从中取出子 agent 每个 Bash 调用的 tool_result，`s/log_*.jsonl` 是 hook 日志）。结论以工具返回的 `is_error` 和文字为准，不用模型自述（模型自述有错：它多次把“被拒”说成“可能是子 agent 的环境问题”）。

**实测一：子 agent 的 `cwd` 不是它自己的目录。**

- 主会话 `cd a` 之后，子 agent 的第一个调用的 `cwd` 是 `a`（继承主会话当时的目录）。
- 子 agent 用一个单独的调用 `cd b`，下一个调用的 `pwd` 仍然是 `proj`（目录不跨调用保留），hook 收到的 `cwd` 也一直是主会话的目录。
- 所以子 agent 每个调用都要自己 `cd`，hook 看到的 `cwd` 永远不是子 agent 的 worktree。**原方案 2（按 `cwd` 登记在场者）的前提不成立。**

**实测二：hook 能把 `agent_id` 注入命令。** 子 agent 的命令里 `$EXP_AGENT` 是它的 `agent_id`，主会话的命令里为空。注入本身可行；问题在权限。

**实测三：只返回 `updatedInput`（不给 `permissionDecision`）时，改写后的命令还能不能被权限规则匹配。** 命令是 `git status --short`（允许规则 `Bash(git status*)`）和 `git log --oneline -1`（Claude Code 内置的只读命令，不需要规则就放行）。`none` 是 hook 不改写的对照。`-p` 模式没有人可以确认，所以“需要确认”在这里表现为 `is_error: true`；`-p` 里原文是 “requires approval” 的，交互模式下就是弹确认。

| 权限模式 | 对照（不改写） | 前缀写法 `CANON_ACTOR=<id> <命令>` | 分号写法 `export CANON_ACTOR=<id>; <命令>` |
|---|---|---|---|
| default | 两个都执行 | 两个都被拒（`Permission to use Bash has been denied`，交互时是确认） | 两个都被拒（`This Bash command contains multiple operations. The following part requires approval: export CANON_ACTOR=…`） |
| acceptEdits | 未测 | 两个都被拒（`This command requires approval`） | 两个都被拒（同上，`export` 一段需要确认） |
| dontAsk | 两个都执行 | 两个都被拒（`…denied because Claude Code is running in don't ask mode`） | 两个都被拒（同上） |
| auto | 两个都执行 | 两个都执行 | 两个都执行 |
| bypassPermissions | 未测 | 两个都执行 | 两个都执行 |

原始输出：`s/raw_{none,prefix,export}_{default,dontAsk,auto}.jsonl`、`s/raw_{prefix,export}_{acceptEdits,bypassPermissions}.jsonl`。default、dontAsk、auto 三个模式的第一次运行（没有用 stream-json，只有 hook 日志和模型自述）结果相同。

**实测四：再给一条放行规则 `Bash(export CANON_ACTOR=*)`（这是 D-17 做过、因 #26 撤回的规则）。** 分号写法和换行写法（`export CANON_ACTOR=<id>` 换行再接命令）在 default、acceptEdits、dontAsk 下，`git status --short`（有自己的规则）执行了，但 `git log --oneline -1`（原本靠内置只读放行）被拒：命令被改写成带前缀的复合命令之后，内置的只读放行不再适用，每个没有写进规则的命令都要确认或被拒。原始输出：`s/raw_w_{export,exportnl}_{default,dontAsk,acceptEdits}.jsonl`。

结论：**不给 `permissionDecision` 的注入，只在 auto 和 bypassPermissions 下不影响权限；在 default、acceptEdits、dontAsk 下，子 agent 的每个 Bash 命令都要确认（交互）或被拒（dontAsk、`-p`），连只读的 `git log` 也一样。** 补放行规则能让写进规则的命令通过，但内置只读放行失效，而且那条规则 `export CANON_ACTOR=*` 就是 #26 的问题（它匹配任何以这个前缀开头的 export，包括同一行里设别的环境变量；规则里的 id 每个子 agent 不同，写不成精确匹配）。

### 第三轮实测（2026-11-05，同一版本，`claude -p --model haiku`，hook 只拒绝、不改写）

目录：`/private/tmp/claude-501/-Users-apple-Projects-zz-canon/0b2e14ae-7ccf-499b-9f18-e0c549f25f21/scratchpad/hookexp/deny`（`hook3.sh` 是 hook，`bin/canon` 是只打印参数的假 canon，`proj` 装 hook，`proj_nohook` 没有 hook，`proj_crash` 的 hook 会崩溃；`s/raw_*.jsonl` 是 `--output-format stream-json --verbose` 的原始输出，`s/log_*.jsonl` 是 hook 日志）。结论取自子 agent（或主会话）每个 Bash 调用的 tool_result 的 `is_error` 和原文，不用模型自述。

要点：
- hook 的 deny 不触发权限问题：`reason` 原文到达子 agent（带真实 `agent_id`），带 `--as <agent_id>` 重试在 default 和 dontAsk 下都直接执行。和实测三不同，拒绝不改写命令，不影响别的命令的权限匹配。
- 命令后面带 `--as abc` 不影响 `Bash(canon work *)` 规则的匹配（实验 2），“需要先查实”的第一项已经查实。没有试的：`cd … && canon work land` 这样的复合命令与允许规则的匹配（hook 对它能解析，见 `s/raw_e1_default.jsonl` 里第一个调用）。
- hook 崩溃（退出码 1）或脚本不存在时，调用照常执行：Claude Code 把它当作非阻塞错误（只有退出码 2 或 deny 才拦）。-p 的输出里看不到提示，所以不能靠 Claude Code 自己告诉用户。

## 方案

每个方案的“拦不住”里都有三件事不在 canon 管辖内，不再逐个重复：用户自己在终端操作（不经 Claude Code，没有 hook）；非 Claude Code 的 agent（没有 `agent_id`）；故意绕过的 agent（改环境变量、换路径写法）。

1. **hook 按调用的 `cwd` 登记谁在 worktree 里，拒绝别的身份（原推荐）**：否决。前提（hook 看到的 `cwd` 是调用者自己的）被实测一推翻。独立审查还指出三点：转换规则（主会话先进入、子 agent 后进入、`SubagentStop`、空闲超时）有竞态；依赖不保证触发的 `SubagentStop`；没核对 C-337 的实际命令。核对结果：事故是同一个调用里 `cd` 进去再提交、合入，hook 只看得到调用开始时的 `cwd`，这个方案本来就拦不住它。
   - 拦得住：没有可靠的依据，hook 看到的 `cwd` 是主会话的。
   - 依据：本文实测一。
2. **hook 注入身份，不给 `permissionDecision`（恢复 D-17）**：PreToolUse hook 在子 agent 的每个 Bash 命令前加 `export CANON_ACTOR='agent:<会话>:<agent_id>'`（或前缀写法），canon 照 BR-2023 用它构成执行者。否决：在常用的权限模式下不可用，见实测三、四。
   - 拦得住（假设注入生效）：别的 agent 在这个 worktree 里运行 `canon work land`、`stop`（退出码 5），C-337 的那次合入会被拒。
   - 拦不住：`git add`、`git commit`、改文件这类不经过 canon 的操作；没装 hook 的项目；hook 失败的那一次调用（要放行，否则整个会话的 Bash 都不能用）。
   - 代价（实测）：default、acceptEdits 下子 agent 的每个 Bash 命令都要用户确认，dontAsk 下全部被拒，auto 和 bypassPermissions 下没有影响。补放行规则会重新引入 #26，而且内置的只读放行仍然失效。
   - 失败方式：身份缺失时退回会话一级，是无声的退化。
   - 依据：本文实测三、实测四。
3. **`permissionDecision: "allow"` 的注入**：否决，不实测。它跳过用户对整条命令的确认，canon 不能替用户批准命令。
   - 来源：https://code.claude.com/docs/en/hooks.md “PreToolUse decision control”
4. **只在 auto、bypassPermissions 下注入**：hook 读输入里的 `permission_mode`，别的模式不改写。否决：保护随权限模式开关，default 下的子 agent 没有身份，而“没有 `agent_id` 注入”和“主会话”在 canon 看来一模一样，没法大声失败。
5. **派发时给子 agent 起名字（自愿 `--as`，不用 hook），名字写在 canon 命令的参数里（`--as`）**：不用 hook，不改写命令。主 agent 派发时为每个子 agent 起一个名字，认领和之后的持有者命令都带 `--as <名字>`，执行者是 `agent:<会话>:<名字>`；没带名字的调用（主会话）不是这个持有者。采用（提议），作为没装 hook 时的退化形式，和方案 6 合用（见决定）。
   - 做法：`canon work start --title "…" --as <名字>`（或 `canon work start C-n --as <名字>`）认领时，持有者记为 `agent:<会话前 8 位>:<名字>`；这个 worktree 里的 `canon work land`、`stop`（BR-2104）要带同一个 `--as <名字>`，不带或带错 → 退出码 5，提示写明持有者是子 agent `<名字>`，不是它的话不要进入这个 worktree。`--as` 是普通命令参数，写在 canon 命令后面，所以匹配用户的 `Bash(canon work *)` 之类的规则，不像环境变量前缀那样让整条命令的权限匹配失效（实测三里 `git status --short` 被 `Bash(git status*)` 匹配而前缀写法不被匹配；canon 命令用 `--as` 是否同样匹配，实现时要用实测确认）。
   - 拦得住：C-337 的合入。主会话没有名字，`cd` 进别人的 worktree 之后，同一个调用里的 `canon work land`、`stop` 照样被拒，单个调用里先 `cd` 再合入也被拒，因为检查发生在 canon 命令里，不在 hook 对 `cwd` 的猜测上。
   - 拦不住：`git add`、`git commit`、改文件这类不经 canon 的操作（和方案 2 一样）；子 agent 起始时忘了 `--as`：认领记成会话一级，没有保护，而且这时是无声的；canon 能做的是让主 agent 事后看得见：`canon work status` 和 `canon events` 里执行者没有名字，canon-parallel 的核对步骤加一条。子 agent 之后再带 `--as` 运行 `land` 会被拒（持有者是 `agent:<会话>`），这时是大声的。
   - 身份缺失或格式不对要大声失败：`--as` 的值只允许字母、数字、`-`、`_`，其他 → 退出码 2、什么都不写；`--as` 不在 Claude Code 会话里用（`CLAUDECODE` 没有设）→ 退出码 2；不同时给 `--as` 和 `CANON_ACTOR`（两个来源冲突）→ 退出码 2。
   - 子 agent 结束后主会话接手：子 agent 和主会话是同一个进程，认领的进程探测（BR-2100）放不开，租约又是 12 小时（BR-2011），所以必须有一个显式命令。最小的改法不加新命令：主会话运行 `canon work stop --release --as <名字> --next "<下一步>"`，也就是它明确写出子 agent 的名字来放开认领；事件里记的执行者是这个名字，看不出是主会话还是子 agent 运行的（执行者只到名字一级，P6 的粒度没有变），再 `canon work start C-n` 认领。这样接手需要主 agent 主动写出名字，C-337 那样“误进”不会发生；它也不防主会话故意写。不恢复 BR-2129 的 `--takeover`。
   - 和现有规则的关系：BR-2023 增加“`--as` 构成 `agent:<会话>:<名字>`”一条，和 `CANON_ACTOR=agent:x:y`（照原样使用）同一个形式，不新增执行者形式；BR-2011 的“同一个执行者也被拒绝”一句、BR-2104 的“边界”一句、BR-2131 的末句要改；canon-parallel skill 的派发清单加“主 agent 起名，`start` 和之后的持有者命令都带 `--as <名字>`”。
   - 失败方式：不依赖任何 hook，没有“hook 装了但没生效”的状态；没装 canon 的项目本来就没有协调。
   - 需要先查实：`--as` 写在命令后面是否让 `Bash(canon work *)` 之类的规则照常匹配（预期照常，按“实测三”对照组的行为）；事件表、`canon stats`、`canon status` 里出现 `agent:<会话>:<名字>` 的形式是否破坏现有按执行者的统计（BR-2023 已允许这种值，D-18 留下的统计按 worktree 分，预期不破坏）。
   - 依据：本文实测三。
   - 来源：canon/decisions/D-18.md “只是一个普通的名字，不再解析”
6. **hook 只拒绝、不改写：用 Claude Code 给的 `agent_id` 校验 `--as`（方案 5 的参数加上 hook 的验证）**：采用（提议）。
   - 做法：canon 装一个 `PreToolUse` 的 Bash hook（和现有的快照 hook 同一类）。命令里含需要认领的 canon 子命令（`canon work start`、`land`、`stop`、`drop`；`test`、`status`、`after-land`、`clean` 不检查持有者，不在其中）时：有 `agent_id`（子 agent）而没有 `--as <这个 agent_id>`，或 `--as` 的值不等于它 → `permissionDecision: "deny"`，reason 写 `Re-run the same command with --as <agent_id> appended`；没有 `agent_id`（主会话）而带 `--as` → deny，reason 写 `--as is only for subagents`。一个命令里有几段 canon 命令，每一段都要符合。其余命令不管。hook 不改写命令，不返回 `allow`。
   - canon 本身的做法和方案 5 相同：`--as <名字>` 记成 `agent:<会话前 8 位>:<名字>`，名字用 `agent_id`；持有者检查（BR-2104）比较执行者，主会话（没有名字）进子 agent 的 worktree 运行 `land`、`stop` 照样退出码 5。hook 管“子 agent 必须写对名字”，canon 管“没有名字的进不了有名字的持有者”，两层各自成立。
   - 为什么可行：本文第三轮实测：deny 的 reason 原文到达子 agent，重试带 `--as` 在 default、dontAsk 下直接执行；`--as` 不影响 `Bash(canon work *)` 的匹配；主会话带 `--as` 被拒，不带的照常。deny 不改写命令，所以实测三、四里“需要确认或被拒”的问题不出现。
   - 比方案 5 好在哪：名字是 Claude Code 证明的 `agent_id`，不是 agent 自己编的；子 agent 忘了 `--as` 当场被拦，不再是无声失去保护；主会话不能冒充子 agent（带 `--as` 被拒）。
   - 子 agent 结束后主会话接手：比较两个办法。
     - (a) `canon work stop --release --as <id>`，只允许主会话对已结束的子 agent 用：主会话带 `--as` 会被 hook 拒（防冒充那条规则），自相矛盾；要给这条命令开例外，hook 就要读更多的命令语义，也无法证明子 agent 已结束。否决。
     - (b) 新命令 `canon work take <C-n> --from <agent_id>`：只在主会话运行（带 `--as` 本来就被 hook 拒，canon 也拒：退出码 2），把持有者从 `agent:<会话>:<agent_id>` 改成 `agent:<会话>`（会话一级），记 `claim.take` 事件，detail 写 `from`、`by: main-session`，没有 `--from` 或名字和持有者不符 → 退出码 2 或 5，什么都不改。只能接手本会话的子 agent（会话前 8 位相同），别的会话的持有者仍然要等租约或进程失效（BR-2011、BR-2100）。
     - canon 不能证明子 agent 已结束：子 agent 和主会话是同一进程（BR-2100 的进程探测分不开），`SubagentStop` 不保证触发（D-11）。所以接受这个风险并写明：`take` 靠主 agent 在它自己的对话里看到子 agent 已返回（Agent 工具的结果）；用在还在运行的子 agent 上，子 agent 之后带 `--as` 运行 `land` 会被拒（持有者已改成会话一级，退出码 5，大声）。选 (b)：行为明确、事件可查、不和 hook 规则冲突。
   - 拦得住：C-337 的合入（主会话没有名字）；子 agent 忘了 `--as` 或写错（hook 当场拒）；主会话带 `--as` 冒充（hook 拒）。
   - 拦不住：
     - 不经 canon 的 `git add`、`git commit`、改文件（和方案 2、5 一样）。
     - 没装 hook 的项目：退化成方案 5 的自愿 `--as`，子 agent 忘了写时无声失去保护；canon 能做的是让事后看得见（`canon work status`、`canon events` 里执行者没有名字）。`canon update --check` 和 `canon brief` 已经报告 canon 装的 hook 缺什么，新 hook 同样进这个检查。
     - hook 看不到的写法：`sh -c "…"`、`eval`、变量拼出来的命令、脚本文件里调用 canon、`canon work` 前面的别名。子 agent 这样运行，命令里没有可识别的 `canon work land`，hook 不拦；canon 看到没有名字的调用，持有者是 `agent:<会话>:<名字>` 时仍然退出码 5（第二层），但认领时没带名字则无声退回会话一级。这是故意绕过，不在“合作的 agent”的范围里（沿用 D-17、D-18）。
     - 命令里写 `CANON_ACTOR=…` 的写法：BR-2023 允许；hook 对含 `CANON_ACTOR=` 的 canon 命令一并 deny，实现时用测试验证（本文没有实测）。
     - hook 本身失败的那一次调用（见下）。
   - hook 崩溃或 canon 不在 PATH：和现有快照 hook 同一个策略（BR-2185，`src/cli/install/hook.ts` 的 `SNAPSHOT_COMMAND`）：命令写成 `canon hook pre-bash || echo '{"systemMessage":"canon hook pre-bash failed or canon is not on PATH: --as was not checked for this Bash call"}'`，失败时那次调用放行，但用户在界面里看到一条消息，不是静默的。依据是实测四：退出码 1 的 hook 调用照常执行且没有任何提示，所以大声要靠 `|| echo systemMessage`，不能靠 Claude Code。不用退出码 2 的“失败就拦”：canon 一坏，整个会话的所有 Bash 命令都被拦，包括修 canon 的命令。只有“检查成功并判定不符”才 deny。hook 的 stdout 必须是合法 JSON 或空，写错时同样走这一条。
   - 代价（要在实现前量出）：每个 Bash 调用多一个 hook 进程；D-30 量过快照 hook 每次约 60 ms。能并进现有的快照 hook 就不多一个进程（`canon snapshot take --hook` 同时做检查），实现时按实测选，并把每次调用的耗时写进变更文件。
   - 和现有规则的关系：同方案 5（BR-2023 增加 `--as`，BR-2011、BR-2104、BR-2131 改），再加：hook 的检查规则（deny 的两种情形、不改写、失败时的 systemMessage）、`canon work take` 一条；`src/cli/install/hook.ts` 增加一个由 canon 管的 PreToolUse 条目（BR-2087 的“只管自己的条目”不变），`canon update`、`canon init` 装它，`canon work take` 在 `src/work/commands.ts`。D-30 的“hook 只记录、不拦”要改成“只拒绝身份写错的 canon 命令”，所以 `amends` 加 D-30；D-1 是“不检查 agent 怎么干活”，这个 hook 只检查身份参数，接受时由评审判断是否也要列入。
   - 来源：https://code.claude.com/docs/en/hooks.md “PreToolUse decision control”
   - 依据：本文第三轮实测。
7. **不做，只靠文字**：否决为唯一手段。在 `canon brief` 和 skill 里写“进入 worktree 只用 `canon work start` 打印的路径，不要用 `ls | tail` 之类推出来”，C-337 的教训写进变更文件。理由：单独什么都拦不住，只降低误进的概率；但文字部分和方案 6 一起做（见决定）。
8. **推迟，等 Claude Code 把 `agent_id` 放进环境变量或把 `cwd` 做成子 agent 自己的**：否决（现在不做）。现在的 Claude Code 不提供这两样，canon 没办法让它们成立。如果方案 6 实现后事件表里仍然出现误进，再回来评估。

## 决定

**否决方案 1（按 `cwd` 登记）和方案 2、3、4（hook 注入）；提议方案 6（hook 只拒绝、不改写，用 `agent_id` 校验 `--as`）加方案 5 的 `--as` 参数（没装 hook 时自愿使用）加方案 7 的文字部分。** 按实测，注入在 default、acceptEdits、dontAsk 下让子 agent 的每个命令需要确认或被拒；而只拒绝的 hook 不改命令，deny 的 reason 能原文送达子 agent，重试直接执行（第三轮实测）。

- 认领的持有者可以带名字（`agent:<会话>:<名字>`），名字在装了 hook 的项目里就是 `agent_id`；主会话不带名字，进不了子 agent 持有的 worktree 的 `land`、`stop`。
- hook：子 agent 的 canon 认领类命令必须带 `--as <自己的 agent_id>`，主会话不得带 `--as`；不符就 deny 并在 reason 里给出正确写法；不改写命令，不用 `allow`。hook 自己失败时放行并用 systemMessage 告诉用户，和快照 hook 一致。
- `--as` 的值缺失、格式不对、不在 Claude Code 会话里用、和 `CANON_ACTOR` 同时给 → 退出码 2，什么都不写。
- 接手：新命令 `canon work take <C-n> --from <agent_id>`，只在主会话运行，把持有者降到会话一级并记事件；不证明子 agent 已结束，风险写在规则里。不用 `stop --release --as`（和“主会话不得带 `--as`”冲突）。
- `canon brief` 的工作流说明加一句：进入 worktree 只用 start 打印的路径；canon-parallel skill 的派发清单写明：子 agent 的 canon 命令带 `--as <自己的 agent_id>`，hook 会提示。
- 实现前先做：量一次 hook 每次调用的耗时（单独一个进程和并进快照 hook 两种）；用测试验证含 `CANON_ACTOR=` 和复合命令（`cd … && canon work land`）的情形。结果写进变更文件；耗时不可接受或复合命令与允许规则不匹配，退回本决定重新评审。

## 后果

- C-337 那类“主会话进入子 agent 的 worktree 之后 `canon work land`”会被拒绝（退出码 5），不论 `cd` 和 `land` 是不是写在同一个调用里。子 agent 忘了 `--as` 当场被 hook 拦下，主会话冒充被拦下。
- **仍然拦不住**：不经过 canon 的操作（`git add`、`git commit`、改文件）仍然会落进别人的 worktree，被拒的只有 canon 的 `land` 和 `stop`；没装 hook 的项目退化成自愿 `--as`，子 agent 没带时没有保护，且是无声的，只能靠主 agent 在事件表里核对；hook 看不到的命令写法（`sh -c`、`eval`、脚本里调用）；hook 自己失败的那一次调用；`cwd` 不是子 agent 自己的（实测一），所以没有办法在 hook 里拦 `git commit`；非 Claude Code 的 agent，用户自己在终端操作，故意绕过的 agent。
- 身份是 Claude Code 给的 `agent_id`，不是 agent 自己编的；但只在装了 hook 的项目里被 hook 强制，canon 本身仍按 `--as` 的值记执行者，不能自己验证它。
- 这是 canon 第一个会拦调用的 hook，和 D-1、D-30 的“只记录、不拦”不同：它只拦“身份参数写错”的 canon 命令，不检查 agent 怎么干活，失败时放行。`amends` 加 D-30，D-1 的措辞接受时再评审。
- 不改写命令，不装放行规则（用户已有的 `Bash(canon work *)` 照常匹配 `--as`，实验 2）。
- 要改的规则：BR-2023（增加 `--as`）、BR-2011、BR-2104（“边界”一句）、BR-2131（末句），`--as` 的错误情形各一个例子；新规则放 `work/claims`：hook 的检查（deny 两种情形、失败放行加 systemMessage），`canon work take`。D-18 的“决定”和“后果”里关于“同一会话的 agent 进同一个 worktree，canon 挡不住”的两句由本决定修正（接受时生效）。
- 要改的代码：`src/work/workspace.ts`（执行者的确定，BR-2023）、`src/work/claims/claims.ts`（持有者检查、拒绝提示、`take`）、`src/work/commands.ts`（`start`、`land`、`stop` 的 `--as`，`take`）、`src/cli/install/hook.ts` 和 `src/config/hooks.ts` 所在位置里 canon 管的 hook 条目与检查（`canon hook pre-bash` 或并进 `canon snapshot take --hook`）、`.claude/skills/canon-parallel/SKILL.md`。
