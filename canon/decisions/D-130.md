---
id: D-130
title: 版本由功能模块组合而成：版本文档列出模块，规则挂在模块上；AI 可以改目标，改动列出来给负责人看
status: accepted
---

## 背景

C-582（D-129）让整体进度看得见之后，负责人 2026-11-17 要一个让 AI 一直朝目标做下去、并能及时校准方向的 goal 机制。设计它时负责人指出两件事。第一，版本中途会调整：“本来订好了几个版本的release，但是中途存在改动，比如可能其中某些版本的某些功能不做了，或者提前了，或者合并了”；“一个release是多个功能模块”，组合版本“本质上就是组合功能模块”。第二，zhushenkongjian 的 `R-2` 到 `R-5` 全是 planned “本身就是问题”：canon 没有把版本标成进行中的命令，规则都通过了也不提示，目标从哪个版本开始只能猜。

canon 现在只有版本文档和规则上的 `release: R-n`：一个功能在“范围”里是一句话、在成功标准里是一两条、在规则里是十几条，三者之间没有关联，挪一个功能要手工分别挪，漏了也看不出来；版本只有 planned、active、shipped，取消只能删文件。

负责人选了：整个版本不做或并进别的版本时加 `dropped` 状态（问题 #51）；组合关系记在版本文档里，由版本列出模块（问题 #52）。最初的设计是每次改目标都要负责人确认；另一个会话指出这样连迁移和改错字都要问负责人，负责人说“应该给ai更多主动权”。

## 方案

1. 功能模块是自己的文档 `F-n`，规则写 `feature: F-n`；版本文档 front matter 的 `features` 列出组成它的模块，正文的成功标准只写版本层面的；调整版本就是改这个列表，取消用 `dropped`：采用（负责人选定）。一个版本由哪些模块组成在一个地方看全，合并版本就是合并列表，挪一个模块不用逐条改规则。
   - 来源：https://github.com/daniel1zz/canon/issues/248 “数据其实都在 canon 里，但分散在几个命令和文件里”
2. 模块写自己属于哪个版本（`release: R-n` 写在模块上）：否决。挪一个模块只改一行，但一个版本由什么组成要扫所有模块才知道；负责人选了版本列出模块。
   - 来源：canon/rules/knowledge/releases/README.md “版本只是给它加的一层标签和记录”
3. 不加模块，把每条成功标准当作功能的单位，规则写 `release: R-5/S3`：否决。成功标准是验收的说法，一个模块常有好几条；模块自己的目标、范围、不做就没有地方写。
   - 来源：https://github.com/daniel1zz/canon/issues/248 “五个体系各有构筑通关全部主线世界”
4. 取消版本或模块就删文件：否决（负责人选了 `dropped`）。“曾经有这个版本、为什么取消、并进了哪个”只留在 git 历史里，总览和检查都看不到。
   - 来源：canon/product.md “谁改了什么、为什么改都有记录”
5. 改目标（成功标准、组合、取消）每次都要附负责人已回答的问题才能合入：否决。负责人要给 AI 更多主动权；迁移一个旧版本、改一个错字都要问，等人的成本比目标被改偏的风险大。
   - 来源：canon/product.md “方向和明确留给人的问题走 `canon human`，其余都不等人”
6. AI 自己改目标，合入照常、列出改动，总览和会话开头的摘要列出最近 7 天 main 上的目标改动，负责人事后纠正；只有把“待负责人”的成功标准改成别的状态要负责人为这个变更回答过的问题：采用。被改偏的目标几天内就出现在负责人每次看进度的地方；“待负责人”是负责人本人的验收，AI 不能替负责人说验收过了。改动从 git 历史算，不另存。
   - 来源：canon/product.md “谁改了什么、为什么改都有记录”

## 决定

模块文档按 BR-2507，`canon feature drop` 按 BR-2513；规则的 `feature` 标签和“标着某版本的规则”包括模块的规则按 BR-2509；版本的 `dropped` 状态按 BR-2321，`canon release start` 按 BR-2508，`canon release drop` 按 BR-2511，列表按 BR-2320；组合是否成立、被取消的版本和模块还被引用由 BR-2512 拦下；改目标照常合入并列出、离开待负责人要负责人确认按 BR-2510，总览和会话开头列出最近的目标改动按 BR-2505、BR-2506；已发布版本的组合冻结按 BR-2515；规则已通过却还是 planned 的版本由 BR-2514 提示。

## 后果

- 规则上原有的 `release: R-n` 继续有效（已发布版本的标签本来就冻结，BR-2326）；新功能用模块。zhushenkongjian 的 803 条带版本标签的规则不用一次迁完。
- AI 可以自己调整目标，不用等负责人；代价是目标可能被改偏，要靠负责人在总览里看到后纠正，最多晚 7 天以上就看不到了（之后只在 git 历史里）。
- `release-frozen` 也覆盖模块：已发布版本的模块不能取消、不能挪出，对它们的后续修改走新版本（`changed_in` 或新模块）。
