## 背景

BR-2074 让合入后的评审取合入前 main 的配置和脚本，防的是变更在同一次合入里把评审命令换成总是回答 ok 的命令（#115）；D-51 让评审命令在 main 的提交上的临时 worktree 里跑。#215（2026-11-14，zhushenkongjian）：`C-618` 到 `C-623` 的评审因为评审命令读的 `luna` profile 额度用完（403）而失败；负责人把评审器换成 `review` profile（main 195e824be）后，`canon work review-landed --again` 仍在合入前的提交上跑旧的 `tools/review.sh`，同样失败，这些合入永远评审不成。

## 方案

1. 只对 `--again` 重排的评审用重排那一刻 main 的配置和脚本，提交记在 `landed_reviews.reviewer`；文档仍取自那次合入；合入时第一次排的评审照旧（按 BR-2449、BR-2074、BR-2216）：采用。重排是在失败之后、由人或主 agent 主动发起，那时 main 上的评审器正是修好的那个；第一次评审仍不受被合入的变更影响。
   - 来源：src/knowledge/review/landed-queue.ts “the reviewer is infrastructure, not part of the change judged”
2. 所有合入后的评审都用评审开始时 main 的配置：否决。评审在后台排队，开始时 main 可能已经包含这次合入本身，变更就能改掉评审自己的命令（#115 防的正是这个）。
3. 加一个 `--current-reviewer` 选项，默认仍用旧命令：否决。旧命令坏了才需要重排，默认用旧命令的重排几乎总是白跑一次。

## 决定

采用方案 1：BR-2449、BR-2074、BR-2216。

## 后果

- 一个变更改坏了评审器、评审失败后再 `--again`，用的是 main 上那个已被改过的评审器；重排日志写明用的是哪个提交的评审命令，记在 `landed_reviews.reviewer`，事后查得到。
