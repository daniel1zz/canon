## 背景

D-7 只根据对话记录里的调用次数挑 skill，负责人指出这不对（2026-11-03）：调用少可能是描述写得不好、触发不了，调用多也可能是被强制的。于是按内容重新审计了全部 42 个旧 skill（`lore-*`；另有只说明 lore 命令行的 `lore` 和公共参考资料 `shared`，不单独计）：三个只读子 agent 分组逐个读 SKILL.md 和参考资料，按同一套标准评价（有没有强模型默认不会做的具体做法，要引原文；lore 流程占多少；和 canon、Claude Code 内置功能是否重叠；在多会话并发开发里多常遇到；篇幅和质量问题），主 agent 抽查了每组的关键引用，全部属实。

几个关键发现：

- 真正有价值的内容常常藏在参考资料里，或者只占 skill 的一小部分：`shared/verification-discipline.md`（42 行，如“退出码不要隔着管道读”“正反对照成对出现”）、`lore-plan/references/ac-quality.md`（“组件存在 + 测试通过 ≠ 用户能用到”）、`lore-uat`（“执行者报告，裁判判定”“探测不了就不能算通过”）。
- 有些 skill 含有错误或自相矛盾的建议：`lore-review` 要求“不要用 git diff”；`lore-product` 的 discovery 模式让子 agent 扮演用户来给出付费意愿，而这正是它自己定义的最低一级证据；design-ui、prototype 对“变体该多不一样”有三处互相冲突。
- 已经移植的 `canon-design` 留了坏链接（指向不存在的 `shared/` 目录），并且默认每次设计都并行派 4 个子 agent。

## 方案

1. 维持 D-7（只移植 design、diagnose）。否决：漏掉了内容上明显有价值的 test、uat 和规则写作。
2. 把所有不含 lore 命令的 skill 都搬过来。否决：大多数是模型默认就会做的通用内容，或者已被 canon 和 Claude Code 内置功能取代，而每个 skill 的描述都要进入每个会话的上下文。
3. 按内容审计的结论移植 7 个，合并、修正已有的两个，其余不移植。采用。

## 决定

移植（都放在 canon 仓库的 `skills/` 下，名字加 `canon-` 前缀，正文英文，描述含中英文触发词，链接到 `~/.claude/skills/`，这部分沿用 D-7）：

1. `canon-test`：来自 `lore-test` 的“先从规则推出预期再读实现”、可疑模式扫描、mock 注明依据、多组输入，`lore-tdd` 的纵向切片，加上 `shared/verification-discipline.md` 全部八条；去掉教科书内容、凭空定的覆盖率门槛和强制浏览器测试。
2. `canon-uat`：来自 `lore-uat`；依据改成规则和例子，问题改成规则修改或 issue，补命令行驱动，默认用简版，不等人。
3. `canon-rules`：来自 `lore-baseline` 的追问清单和 `ac-quality.md`；写规则前追问失败、边界、重复、并发、谁被拒；功能必须能从真实入口用到。
4. `canon-triage`：来自 `lore-triage` 的“先复现”、写行为契约的任务说明、被拒需求按概念归档，加上 `lore-to-issues` 的纵向切片；结果是一个变更（C-n）或一个决策，不用标签状态机。
5. `canon-product`：来自 `lore-product` 的机会识别、验证、拆解三个模式和证据阶梯，以及 `lore-product-benchmark`；结论落到笔记、决策和规则，方向选择走 `canon human ask`。
6. `canon-prototype`：来自 `lore-prototype`，加上 `lore-design-ui` 的两份参考资料；统一变体规则：已有界面只做视觉和密度上的变体，结构性变体只用于新界面。
7. `canon-context-optimizer`：来自 `lore-context-optimizer` 的正文；去掉和正文矛盾的两份参考资料。

修正 `canon-design`：去掉坏链接；并行派子 agent 改成可选；加回数据隐私；并入 `lore-improve-codebase-architecture` 的“删除测试”“两个适配器才算真接缝”和依赖分类。

42 个的归类（9 + 7 + 3 + 23 = 42）：

- 移植或修正为 canon 版本的 9 个：test、uat、baseline、triage、product、prototype、context-optimizer、design、diagnose。
- 整体并入上面某个的 7 个：tdd（并入 test）、plan（只取 `ac-quality.md`，并入 rules）、to-issues（并入 triage）、product-benchmark（并入 product）、design-ui（取两份参考资料，并入 prototype）、improve-codebase-architecture 和 biz-review（并入 design）。
- 只取几句并到别处的 3 个：bug-hunt（“报告前先试着推翻一次”进代码评审提示）、research（去偏要求进 `user-01-research-first`）、ai-native-coding（`// reason:` 注释写明依据进 CLAUDE.md）。
- 不移植的 23 个：被 canon 或 Claude Code 内置功能取代的 review、iterative-review、git-workflow、autopilot、doctor、session-capture、session-review、kickoff、init-context、project-bootstrap、write-a-skill；模型默认就会的通用内容 best-practice、refactor、analyze、domain、deploy、operate、product-lens、product-to-prd；不属于 canon 范围的 npm-publish、harness-dev、auto-wire、dogfood（其中破坏性探测几条并入 uat）。

canon 本身补上审计发现的缺口：`canon check` 检查领域 `code:` 里的路径存在；CLAUDE.md 写明必须问人的情形（花钱、对共享范围不可逆、需要人的凭据）、worktree 里只跑相关测试（全量由 floor 跑；旧系统有过负载 150、70 多个假失败的记录）、停下时的收尾检查；变更模板加“陷阱和假设”。

复查：沿用 D-7 的做法，2027-02-03 统计这些 skill 的调用次数，并抽读几次使用的对话，看有没有真正帮上忙。

## 后果

- 每个移植的 skill 一个变更，可以并行做，合入时由 canon 的队列排序。
- D-7 被取代。
