---
id: D-51
title: "没有配置评审命令时拒绝合入规则、决策和常驻说明的改动，明确不评审要写 review: none"
status: accepted
---

## 背景

规则和决策文字的评审（BR-2009）和常驻说明的重复评审（BR-2143）都由配置 `review` 的命令完成，是合入时对规则文字唯一的质量关口。原来的做法（BR-2074 旧版）：没有配置 `review` 时，合入只输出一行 `review: not configured`、写一条 `review.skip` 事件，然后照常合入；`canon init` 写出的 `canon/config.yaml` 又没有 `review`。

实际后果：新项目 delegate 用 `canon init --floor "..."` 建好后，合入了 7 个变更（C-1 到 C-7），新增 16 条规则和 1 条决策，规则评审一次也没跑，`canon events` 里有 6 条 `review.skip`；会话每次都看到了那一行输出，每次都没理会。也就是说新项目的这道关口默认是关的，而且关着没人发现。负责人的原则是：必需的值缺失时必须大声失败，不能悄悄降级；方向（直接修好）由负责人定，细节在这里定。

## 方案

1. 只把提示写得更醒目（加警告字样、写进 `canon brief`）：否决。delegate 的会话已经每次都看到了提示，问题不在字够不够显眼，而在合入不停下来；提示再醒目也还是可以忽略，仍是悄悄降级。
   - 来源：canon/changes/C-259.md “那一行输出每次都被会话忽略了”
2. 只让 `canon init` 写入默认评审命令，不改合入：否决。只管以后新建的项目；delegate 这样已经初始化的项目、以及有人删掉或写空 `review` 的项目，仍然悄悄跳过评审。
3. 没有配置 `review` 时一律拒绝，不给关闭的办法：否决。有的项目确实没有可用的评审命令（离线、不用 AI），它们就再也合不进任何规则改动，只能写一个假的评审命令（比如总是输出 ok 的脚本）绕过去，这比明确关闭更难发现。
4. `canon init` 写入默认评审命令，合入在没有配置 `review` 时拒绝，并提供明确的关闭值 `review: none`：采用。新项目开箱就有评审；老项目第一次改规则时被拒，信息告诉它怎么配或怎么关；关闭要在 `canon/config.yaml` 里写下一个看得见的值，`review.skip` 事件照写，关没关一查便知。注意 `canon/config.yaml` 本身不在规则评审（BR-2009）和常驻说明评审（BR-2143）的范围内，写 `none` 的那次改动没有 AI 评审看；所以另定：关掉评审的改动不能带着要评审的文字一起合入（BR-2295），`none` 是负责人的决定。
   - 来源：scripts/review-claude.sh “exec claude -p --output-format text”
5. 关闭值用 `review: false` 或空字符串：否决。空字符串和 `null` 原来就表示“没有配置”，再让它表示“关闭”就分不清是忘了还是有意；`false` 要让这个键同时接受字符串和布尔值，`none` 读起来就是“不评审”，schema 也仍是字符串。
6. 评审命令的时限：不设时限，否决，评审命令卡住（网络、认证提示等）时合入一直占着队列，别的会话都等着；固定一个时限，否决，规则多的领域提示有几万 token，不同项目、不同评审命令需要的时间差得远；用配置键 `review_timeout_minutes`，默认 20 分钟：采用。canon 自己的评审在 C-259 的合入里（含整个 knowledge 领域的上下文）连同排队和其他检查一共 25 秒，20 分钟留了很大的余量，又能挡住卡死的进程。时限到了停下整个进程组（`sh` 和它启动的 `claude`），只停 `sh` 时子进程还拿着输出管道，canon 照样等着。
7. 已经没经评审合入的文档（例如 delegate 的 16 条规则和 D-1）怎么办，分三项：
   - 加一个补评审的命令：否决。一次补评审就是每个领域一次 AI 调用，而评审每次都拿改动所在的整个顶层领域做上下文（BR-2009），这些文档在下一次有人改同一领域时就作为上下文被读到，和新改动的矛盾那时会被拦下。
   - 要求下一次合入时把它们全部重审：否决。那会让一次无关的小改动背上整个项目的评审。
   - 不追溯评审，在这里写明：采用。这些文档的文字本身没有被逐条评审过，项目负责人要补，可以手工让评审命令读一遍。
8. `canon update` 在没有 `review` 的项目里要更新 `SKILL.md`：先开变更、到合入时被拒，否决，留下一个要人处理的变更和 worktree，而 BR-2086 要求安装能做的拒绝都在开变更之前做完；在开变更之前就以退出码 1 拒绝，信息先给评审命令的写法：采用。
9. 评审用的配置（命令、时限、`instructions`）从哪里读：
   - 读运行 `canon work land` 的 worktree 在合入开始时的配置（C-259 的做法）：否决。worktree 落后于 main 时判断错，见 BR-2074 的两个例子。
   - 读被合入的树（rebase 之后）的配置（C-265 的做法）：否决。被合入的树里有变更自己的改动，一个变更可以在同一次合入里把 `review` 换成总是回答 ok 的命令，或者把自己改的文件从 `instructions` 里拿掉，它的文字就等于没人评审；合入后的代码评审把这一点提成了 issue #115。
     - 来源：canon/rules/knowledge/review/BR-2074.md “给自己的文字放行（#115）”
   - 读 main 上已经合入的配置：采用。main 上的配置是之前的合入放进去的，变更改不了它对自己的评审；代价是第一次配评审命令要单独合入一次，之后的规则改动才被评审。
10. 评审命令在哪个目录里运行（#115）：方案 9 只管评审用哪份配置，命令仍在要合入的 worktree 里运行，变更可以改评审脚本本身，`claude -p` 也会读变更自己的 `CLAUDE.md`、`.claude/settings.json`（hook、环境变量）和 `.claude/skills`，变更还是能影响它自己的评审者。选项：
   - 在主 checkout 里运行：否决。主 checkout 可能在别的分支上、有未提交的改动、或是裸仓库；main 是否干净要到评审之后的移动 main 那一步才查（BR-2125），评审时拿它当目录不可靠。
   - 空目录，用 `git show` 取出脚本：否决。不知道脚本还读哪些文件，取多了取少了都会出错。
   - 拒绝改评审脚本的变更：否决。挡不住 `CLAUDE.md`、`.claude/settings.json` 和 skill。
   - 把评审命令挪到仓库外面：否决。命令还是在变更的目录里运行，也和方案 9 的“命令取自 main 上的配置”矛盾。
   - 在 main 提交上建一个临时 worktree 运行：采用。评审提示已带着评审要读的全部文字（规则、决策、常驻说明），换目录不丢信息；main 上已有的文件都在，变更的改动都不在。
     - 来源：canon/rules/knowledge/review/BR-2216.md “临时 worktree”

## 决定

采用方案 4。

- `canon init` 新建 `canon/config.yaml` 时写入 `review: "claude -p --output-format text"`，前面一行注释说明它评审什么、不想评审时写 `review: none`（BR-2032）。这和 canon 自己用的 `scripts/review-claude.sh` 是同一条命令；canon 装的 skill 和 hook 本来就是给 Claude Code 用的，用 canon 的机器上通常有 `claude`。没有时评审命令运行失败，合入按 BR-2009 被拒，同样是大声失败。
- 要不要评审看这次合入改了什么；评审命令、时限和常驻说明清单取自 main 上已经合入的 `canon/config.yaml`（方案 9），不取自 worktree 在合入开始时读到的配置，也不取自被合入的树：main 刚打开评审，旧 worktree 合入时也被评审；main 已经配好，旧 worktree 没有这个键时也不会被误拒；变更换掉评审命令或从 `instructions` 里拿掉自己改的文件，都不影响它自己的评审（BR-2074、BR-2143、BR-2296）。
- 合入有规则或决策改动（BR-2074），或有常驻说明改动（BR-2143），而 `review` 没有配置（没有这个键、`null`、空字符串或只有空白）时，合入被拒，退出码 1，原因 `review`（BR-2022）；信息列出要评审的文档，先给出评审命令的写法，再说明 `review: none` 是负责人的决定、要用 `canon human ask` 问。
- 关掉评审（把 `review` 改成 `none` 或删掉）的那次合入不能同时带着规则、决策或常驻说明的改动，要单独合入（BR-2295）。canon 不能核对这次合入是不是真的问过负责人，能做到的是让它成为一次单独、看得见的合入。
- 写成 `None`、`"none "` 这类多半是想写 `none` 的值是配置错误（BR-2045），不会被当成一条叫 `None` 的命令去执行。
- 评审命令在 main 提交上的临时 worktree 里运行（方案 10，BR-2216）：分离 HEAD，建在 canon 的状态目录下，一次合入的规则评审和重复评审共用一个，只在真有评审要跑时才建，各种结果和信号之后都删掉，删不掉按环境错误拒绝；批量合入也用 main 的提交。
- 评审命令超过 `review_timeout_minutes`（默认 20 分钟）时停下它的整个进程组，合入被拒；合入被信号终止时也一起停下（BR-2296）。
- `canon update` 要新增或修改 `SKILL.md` 而没有配置 `review` 时，在开变更之前就拒绝（BR-2086）。
- 已经没经评审合入的文档不追溯评审（方案 7）。
- main 上已经是 `review: none` 时保留原来的做法：输出一行 `review: none`、写 `review.skip`、照常合入。带措辞记录的合入（BR-2239）仍然被拒，因为没有评审来判断。
- 常驻说明的重复评审一并照此处理：它和规则评审用同一个 `review` 键，同一个键缺失时一处拒绝、一处放行，会让人以为配置没问题。

## 后果

- 没有 `review` 的已有项目（例如 delegate），下一次合入规则、决策或常驻说明改动时被拒，要先单独合入一个只给 `canon/config.yaml` 加上评审命令的变更，再合入规则改动（评审命令取自 main，同一个变更里设的不算）；或者经负责人同意后单独合入 `review: none`。在一次合入里改 `review`、`review_timeout_minutes` 或 `instructions`，都只对之后的合入生效。
- 新项目每次改规则都多一次 AI 调用（几分钟、若干 token），这是这道关口本来的代价。
- 评审命令的相对路径（如 `scripts/review-claude.sh`）按 main 提交里的文件解析；不在 git 里的文件（例如 `node_modules`、被忽略的文件）在评审的目录里没有，评审命令要靠绝对路径或 PATH 找它们。
- 在测试里建的临时仓库凡是合入规则、决策或常驻说明改动的，都要配置替身评审命令或 `review: none`。
