---
id: D-22
title: 排队时用 git merge-tree 预测 rebase 冲突
status: accepted
---

## 背景

N-3 的并发实测里，C-55 排队 409 秒，轮到自己做 rebase 时才知道和刚合入的 C-57 冲突。合入者在队列里等待时，main 每被别人移动一次，就可能产生新的冲突；越早知道，越早能回去解决，也不白占后面的轮次。预测必须不碰合入者的 worktree：等待期间 worktree 里可能还有人在看或在改（BR-2105），真正的 rebase 只在轮到时做。本机 git 是 2.50.1。

## 方案

1. `git merge-tree --write-tree --name-only <main> HEAD`：在内存里做一次三方合并，有冲突时退出码 1，并列出冲突的文件。采用：不碰暂存区和工作区，不需要临时 worktree，只在 main 变化时跑一次；git 2.38 起可用。它预测的是合并而不是逐个提交的 rebase，两者在少数历史上结果不同；只有预测到冲突才拒绝，预测不到的冲突仍由轮到时的 rebase 发现（BR-2015）。
   - 来源：https://git-scm.com/docs/git-merge-tree “Perform merge without touching index or”
   - 来源：https://git-scm.com/docs/git-merge-tree “just provide a list of filenames with conflicts”
2. `git replay --onto <main>`：在内存里真正逐个重放提交，和 rebase 最接近。否决：文档标明是实验性命令，输出和参数还可能变；冲突时不直接给出文件列表。
   - 来源：https://git-scm.com/docs/git-replay “EXPERIMENTAL: Replay commits on a new base, works with bare repos too”
3. 在临时 worktree 里真的 rebase 一次。否决：每次 main 移动都要签出整棵树，耗时和磁盘都随仓库变大；还要处理临时目录的清理和并发。
   - 来源：src/work/land/land.ts “git(wt, "rebase", "-q", base.value)”

## 决定

用方案 1，在等待循环里每当 main 变化时预测一次（BR-2153）。`canon work start` 时不做冲突或同文件预测：新变更此时只提交了自己的变更文件，没有可以比较的改动；别人还没提交的改动要等它合入后才会和自己冲突，那时等待中的预测会发现它。

## 后果

- 等待中的合入者每次看到 main 移动都多跑一次 `git merge-tree`，只读对象库，不写 worktree。
- 预测到的冲突用原因 `conflict` 记录，和轮到时 rebase 冲突是同一个检查，`canon stats` 里不另立一项；事件里带 `early: true` 以便区分。
- git 低于 2.38 时预测跑不起来，会打印一行说明，行为退回到只在轮到时发现冲突。
