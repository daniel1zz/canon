## 背景

计划（D-77）把「一步做没做完」存成第二份状态：变更有自己的状态，计划里的步骤又从「哪些变更写了 `plan`/`steps`」算一遍。两份对不上的情况，在 zhushenkongjian 上一天之内就出现了好几次：变更做了某一步却没写链接（`C-929` 做了 `C-897` 的第 3、4 步，`C-970` 的标题就是「`C-613` 第 11 步」却没链接），一步要几个变更做、第一个合入就显示做完（#278），一个变更做了两个计划的步却只能链接一个（`C-969`）。#269、#278 都是这个根因；修补链接规则（`C-625`，已撤掉）只是换个地方漏写。

负责人 2026-11-20 定的方向：
- 单一数据源，只在关键节点更新：「首先肯定是单一数据源最好，防止后续不一致的问题」「核心还是在于，单一数据源，以及在关键节点更新数据」。
- 不要再单独一个计划：「我们本身就有release了，release直接和变更绑定就行，变更就是我们的最小执行单元了，chore也可以走变更，所有都走变更，但是变更不要太重，就是一个执行说明」。
- 「没有版本那就不挂，如果变更没有挂在版本下面，那就说明都是要这批交付的」「如果有大的目标应该建立release然后拆解模块，创建变更」「创建新的变更就应该看还没结束的变更是否有重复」。

一个没看到推荐的独立 agent 反驳过这个方向（2026-11-20），查到的事实：
- 靠变更自己写的字段很少写全：zhushenkongjian 有了 `advances` 之后新建的 126 个变更只有 30 个写了；由命令写的 `rules:` 是 1027/1028。
- 一步常由 2 到 4 个变更做（`C-897` 第 1 步 4 个，`C-870` 第 8 步、`C-999` 第 4 步各 3 个），提前建好的一个变更和实际拆法对不上。
- 会话按「`canon change list` 里第一个没认领的」取活，依赖没完成的变更如果也是 open，就会被提前拿走。
- 杂务现在提供的是：不要求正文、main 上没有开工和关闭两个文档提交、不进待办、`canon update` 和 `canon release ship` 这类自动入口不建文档；最近一周 canon 约 53 个杂务提交，zhushenkongjian 82 个。
- 计划现在提供一页看全步骤、依赖和可开始的步，以及步骤之间的说明。

## 方案

1. **执行只有变更，关联写在变更上并由命令写入，进度看规则和成功标准**：采用。
   - 去掉计划（`## 计划` 表、`plan`、`steps`、`canon plan`）。原来的一步就是一个变更，可以提前建好（`canon change new`），也可以开工时新建；同一件事可以由任意多个变更来做，没有「这一步算不算完」。
   - 去掉杂务这个单独的东西。原来的杂务是一个轻的变更：只要标题，正文可以不写；它的文件在合入时随改动一起写进关闭提交，main 上不多出开工提交；失败或放弃时不留在待办里；`canon update`、`canon release ship` 这类自动入口照样能用。
   - 变更的关联：属于哪个版本或哪个功能模块（只写一个，写模块时版本从模块推出来，两者矛盾时 `canon check` 报错）、执行哪些规则（`rules`，现有）、修哪些 issue、依赖哪些变更。这些由 `canon change new`、`canon work start` 的参数写入，提前建好的变更开工时继承；不是靠会话事后补写。没挂版本或模块的变更属于当前这一批，总览把它们列给负责人看（它们等于 AI 自己定的交付范围，P7）。
   - 依赖：依赖的变更合入了才算满足；被作废的变更写明「已由 C-n 做了」时按 C-n 算，否则提醒依赖它的变更。依赖成环在 rebase 后的树上查，属于完整性，拒绝。`canon change list` 和 `canon brief` 不把依赖没满足的变更列为可开始，并写明在等哪个。
   - 进度：版本和模块算不算完成，只看它的规则状态和成功标准（BR-2504）；关联的变更合入了几个只当工作量显示，不当完成度。原来计划那一页总览，由一个命令按版本或模块从依赖现算出来；步骤之间的说明写进模块或版本文档。
   - 重复提醒（D-139，只提醒）：新建变更时，按标题和没结束的变更比相关度（相关文档挑选，D-90），最多列 3 条，低于阈值不出声；合入时，再按实际改动的路径和规则，和没结束的变更写下的规则、路径、模块比，重合就提醒，会话写下「是它」或「不是它，因为……」。每次提醒和会话的回应记成事件，按 P6 算准确率、调阈值。
   - 来源：canon/decisions/D-77.md “每派一个步骤就要改计划文件，同时开工的会话改同一个文件，合入时互相冲突”
   - 来源：canon/product.md “重提醒，轻拦截（D-139）”
2. **保留计划，补链接规则**（步骤写覆盖的路径，改到却没链接就提醒；链接可以写「部分」；一个变更可以链接多个计划）：否决。状态仍是两份，只是让漏写更容易被发现；负责人要单一数据源。
   - 来源：canon/decisions/D-77.md “状态不存，所以不会和变更的真实状态不一致”
3. **版本或模块列出它的变更**：否决。每开一个变更都要改那份版本或模块文件，同时开工的会话改同一个文件，合入时冲突；变更开工时只在自己分支上，main 上的版本文件还没写它。
   - 来源：src/knowledge/documents/model.ts “One file per document so concurrent sessions only conflict when they edit the same document”
4. **执行关联存进协调数据库（SQLite）**：否决。负责人认为两边都行，关键是单一数据源；变更本来就是文件，关联放在同一个文件里就只有一份，放进数据库就成了变更文件之外的第二份。协调数据库不进 git、不跨机器，只放运行时的状态。
   - 来源：canon/architecture.md “知识（规则、决策）不放这里”
5. **杂务都改成完整的变更**（开工建文件、填各节、走完整流程）：否决。杂务的价值就是轻；每周多出约 50 个要填模板的变更，会话会想办法绕开它，又回到漏记。
   - 来源：canon/decisions/D-61.md “这三样都要 canon 自己的代码，所以做成内置类型”

## 决定

采用方案 1，取代 D-77；D-79 里「版本发布要求它的计划全部完成」去掉，发布只要求它的规则全部通过（原来就有的那一半），由 C 步改相关规则。具体行为由 C-626 的各步写成规则，每一步开工时先写自己的规则。

迁移：
- 没完成的计划（canon 的 C-603、C-609、C-618，zhushenkongjian 没完成的 7 个）各建一个功能模块（需要时先建版本）；没做的步骤逐个先判断是不是已经被别的变更做了，做了的写明，没做的建成变更，依赖照抄。放计划的那个变更关掉。
- 已关闭的变更上的 `plan`、`steps` 不改写，`canon check` 不再为它们报错；在途分支上还带着这两个字段的变更，合入不因此被拒。

## 后果

- #269、#278 和「一个变更只能链接一个计划」随计划一起消失；`C-625` 已撤掉。
- 每个变更都有编号，原来的杂务也占 C 号；`canon/changes` 下文件会更多，靠变更模板只要标题来压住负担。
- 进度不再有「步骤完成百分比」，改看规则状态和成功标准；只看变更数的人会觉得进度「变慢」，这是对的：变更合入不等于目标达到。
- 重复提醒一开始一定不准，靠记下的回应调；提前建的变更可以选填路径，提醒会更准。
- 这是最后一个用计划表的变更：C-626 自己的分步用旧的 `## 计划`，迁移那一步把它和别的计划一起转成模块和变更。
