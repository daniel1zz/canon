## 背景

#139：D-30 的后果里接受了一个漏洞：“用 `git -C` 或 `cd` 去操作别的 worktree 时只快照 hook 的 `cwd` 所在的那个”，当时把它当成边角情况。事实不是这样：

- `canon work start` 让每个会话都去 `<仓库>.worktrees/C-n` 里干活，而会话常常是在主 checkout 里启动的。
- Claude Code 给 hook 的 `cwd` 是会话的起始目录；Bash 调用里的 `cd` 不改它（D-62 第一轮实测：`cd` 之后下一个调用的 hook `cwd` 仍是主会话的目录，子 agent 的 `cwd` 永远不是它自己的 worktree）。
- 所以大部分 worktree 里的工作从来没有被快照过。#139 的报告：另一个项目里主 checkout 8 个快照、worktree 2 个，之后有几百次改动，一个 worker 用 `git checkout -- .` 丢了工作。在 c10a307 复现：hook 输入的 `cwd` 是主 checkout、命令是 `cd <有未提交文件的 worktree> && git checkout -- .` 时没有快照，`cwd` 是 worktree 时有。

这直接违背 P4（不丢工作）：快照原本就是为 worktree 里的工作准备的。

实测（本机，编译后的 canon，每次调用的挂钟时间，3 个以上的数字取范围）：

- 只快照 `cwd` 的 worktree（旧行为）：约 0.22 到 0.36 秒（主 checkout 有未提交改动，内容和最近一个快照相同）。
- 另有 5 个已认领、没有未提交改动的 worktree：约 0.43 到 0.58 秒，每个多约 50 毫秒（`git status` 一次加一次 `rev-parse`）。
- 另有 5 个已认领、有未提交改动且内容和最近一个快照相同的 worktree：约 1.1 到 1.5 秒，每个多约 200 毫秒（要算出树才能和最近一个快照比较）。
- 读认领表本身（只读打开 SQLite、一次查询）不是主要开销。

## 方案

1. 按认领表找：hook 输入里的 `session_id` 取前 8 个字符，认领表里持有者是 `agent:<会话>` 或 `agent:<会话>:<名字>` 的 worktree 都做快照，加上 `cwd` 的那个：采用。会话和它的子 agent 都认得到（执行者的形式见 BR-2023、D-62）；别的会话认领的 worktree 不碰；`pushd`、子 shell、变量、脚本里的 `cd` 都不影响，因为不看命令。认领表只读打开，不判定认领是否失效（判定会写事件），失效但还没被别人接手的认领也算，因为那个 worktree 仍是这个会话的工作。
   - 来源：canon/decisions/D-62.md “所以子 agent 每个调用都要自己 `cd`，hook 看到的 `cwd` 永远不是子 agent 的 worktree。”
2. 解析命令里的 `cd` 或 `git -C` 的目标：否决。D-30 方案 1 否决拦截时已经说过，`bash -c`、变量、`pushd`、子 shell、脚本里的 `cd`、`git -C` 都解析不到；解析出的目录还要再判断是不是同一个仓库的 worktree，仍会漏掉不写在命令里的目录（命令调用的脚本自己 `cd`）。认领表不依赖命令的写法。
   - 来源：canon/decisions/D-30.md “`bash -c`、git 别名、`git -C`、脚本里调用 git 都解析不到”
3. 快照同一仓库的每一个 worktree，不看认领：否决。别的会话的 worktree 每次调用都被这个会话快照一遍，调用次数乘以 worktree 个数，成本随别人的工作增长；产出的快照也记在这个会话的调用上，找回时分不清是谁的。
   - 来源：canon/decisions/D-30.md “每次 Bash 调用多一次 canon 启动和一次 `git status`”
4. 让 `canon work start` 的会话自己 `cd` 到 worktree 里再启动 hook：否决。hook 的 `cwd` 是 Claude Code 给的，canon 改不了（D-62 第一轮实测）。

## 决定

采用方案 1，部分修改 D-30（`amends: D-30`，D-30 的正文不改，和 D-62 一样）：

- `canon snapshot take --hook` 除了 `cwd` 所在的 worktree，还对认领表里持有者是本会话（`agent:<会话>`）或它的子 agent（`agent:<会话>:<名字>`）的其他 worktree 做快照，规则见 BR-2182。会话取自 hook 输入的 `session_id`（没有时取环境变量 `CLAUDE_CODE_SESSION_ID`，都没有就只做 `cwd` 的）。
- 没有改动的 worktree 什么都不写；别的会话认领的 worktree 不做；不带 `--hook` 时只做当前目录的，行为不变。
- D-30 后果里“只快照 hook 的 `cwd` 所在的那个”这一条作废；“同一次 Bash 调用里先改后丢，快照只有调用前的状态”仍然成立。

## 后果

- 每次调用的耗时随本会话认领的 worktree 数增加（数字见背景）。一个会话通常只认领一两个变更；已提交干净的 worktree 约 50 毫秒，有未提交改动的约 200 毫秒。D-30 估计的“约 0.1 秒以内”在这个机器上，连旧行为也已经超出（约 0.25 秒），所以这里记的是实测数字，不是预算内。要压低可以并行处理各个 worktree 或先用 `git status` 的结果跳过未变的，现在没做。
- 认领表读不出来（文件损坏、没有读权限）时 hook 报错，由 hook 命令的 `|| echo` 给用户一条 `systemMessage`；`cwd` 的 worktree 仍会被快照。
- 一个 worktree 的认领已经被释放或到期后被别人接手，就不再被这个会话快照；释放认领之前（合入、停下）的工作已在分支上。
- 合入后、`after_land` 重新构建 `dist/canon` 之前，PATH 上的旧 canon 仍是旧行为。
