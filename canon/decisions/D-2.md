id: D-2
title: 可配置与可扩展：只通过配置和外部命令扩展，不提供插件 API
status: accepted
---
## 背景

负责人要求 canon 从一开始就可配置、可扩展。“可扩展”有多种做法，有些会把 D-1 删掉的流程负担带回来（比如允许扩展去检查 agent 的做法），有些会让核心变复杂（进程内插件 API）。2026-11-02 负责人从 5 个候选扩展点里选了 4 个。

## 方案

1. 进程内插件 API（加载 JS/TS 模块）。否决：需要稳定的接口、版本兼容和加载机制，扩展的 bug 会直接让 canon 崩溃；而现有需求都能用外部命令满足。
2. 配置 + 外部命令。采用。
3. 子命令扩展（`canon foo` 运行 PATH 里的 `canon-foo`）。负责人这次没有选，不做。

## 决定

扩展只有四种，全部写在 `canon/config.yaml`，核心代码里没有插件机制：

1. **策略参数可配**：现在写死在代码里的数字和路径全部进配置，都有默认值。至少包括：认领租约（默认 12 小时）、合入者无心跳多久算掉线（默认 10 分钟）、合入排队超时（默认 60 分钟）、worktree 存放位置（默认 `<checkout>.worktrees`）、测试文件匹配规则。
2. **文档类型可扩展**：项目可以声明自己的文档类型，写明编号前缀、目录、允许的状态和默认状态。规则、决策、变更、笔记这四种是内置类型，不能删除，但可以增加状态以外的字段。检查、搜索、上下文、编号分配对声明的类型自动生效。
3. **生命周期 hook**：在固定事件上运行配置的命令，事件信息通过环境变量传入。事件至少有：`after_start`、`before_land`（在 floor 和 `canon check` 之后、移动 main 之前；退出码非 0 就拒绝合入）、`after_land`（不阻断）、`after_stop`。现有的 `review` 和 `after_land` 配置并入这个机制，规则评审成为一个内置的 `before_land` 步骤。
4. **文档模板**：每种文档的初始正文来自 `canon/templates/<类型>.md`；没有这个文件时用内置模板。

边界：扩展只能检查结果或补充信息，不能拦 agent 的做法。一个 `before_land` hook 只能基于即将成为 main 的代码树做判断。

## 后果

- 新的配置项和扩展点都要有规则和测试，`canon check` 照样核对。
- 配置写错（类型不对、未知的 key、引用不存在的命令）时，所有命令都直接报错退出（退出码 2），不会悄悄用默认值。
