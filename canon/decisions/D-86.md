## 背景

D-85 让项目用 sops、age、varlock 管密钥，根目录有 `.env.schema` 就算开启，起初只出一个 skill。剩下的缺口：变更把真实的密钥值提交进文件时，合入后 main 上有了明文并被推送，合入后的代码评审把代码发给 `claude -p`，还可能把它引用进 GitHub issue；合入时的规则评审只发 `canon/` 下的文档（BR-2009），值写在规则或决策里时也会被发出去；来源核对会抓取决策里新出现的网址，值写在网址里时会发到那个网站。负责人定了（2026-11-11）：合入必须在任何内容发给模型之前拒绝这样的变更，并选了内置在合入里的做法。

在本机实测 varlock 1.24.0（2026-11-11）：`varlock scan <文件…>` 只扫给出的文件，有明文值时退出码 1，发现写在 stderr，每条一行“路径:行:列 变量名”，下一行是代码片段，片段里留着值的前两个字符；取不到 age 私钥时 `varlock scan` 输出“没有可扫的敏感值”并以 0 退出，而 `varlock load --agent` 以 1 退出并报 `Configuration is currently invalid`。

## 方案

1. 让开启了密钥管理的项目自己在 `before_land` 里配 `varlock scan`：否决。它在 main 前移之前拒绝，能挡住推送和代码评审，但它在来源核对和规则评审之后才跑，写进文档或网址里的值那时已经发出去了；而且每个项目都要自己配，忘了配就没有保护，还会碰上上面那个取不到私钥就悄悄通过的坑。
   - 来源：src/work/land/checks/steps.ts “before_land: after floor, canon check and the built-in review”
2. 在 git 的 pre-commit hook 里跑 `varlock scan --staged`：否决。提交可以用 `--no-verify` 跳过，canon 也不检查 agent 怎么干活，只在合入 main 这个边界上检查结果；只靠提交时的 hook，挡不住已经进了分支的值被合入。
   - 来源：canon/product.md “Canon 只在两个边界检查结果：协调状态写入时，和合入 main 时”
3. 按模式找密钥（gitleaks 一类，或 canon 自己写正则）：否决。它不知道项目真实的值，误报漏报都多；varlock 从 `.env.schema` 解析出真实值后逐字比对，项目开启时这些工具本来就是必需的。
   - 来源：canon/decisions/D-85.md “`varlock scan --staged` 在暂存文件里出现真实值时退出码 1”
4. 内置在合入里，项目开启时在规则评审之前扫描（BR-2407、BR-2408）：采用。合入是唯一的关口，放在评审之前就保证明文值不会发给模型，也不会进 main；项目不用自己配。
   - 来源：canon/decisions/D-85.md “合入时挡住提交进来的明文密钥”

## 决定

合入内置密钥扫描，行为见 BR-2407 和 BR-2408，在来源核对和规则评审之前运行。D-85 的决定已同步改写：canon 的合入在项目开启时运行 varlock，项目没有 `.env.schema` 时仍然什么都不跑。

## 后果

- 开启了密钥管理的项目，合入所在的机器要装 varlock、能拿到 age 私钥，合入时会运行 schema 里的 `exec()`（例如 `sops decrypt`）；做不到时合入怎样失败见 BR-2408。
- varlock 的输出格式将来变了，canon 会认不出发现；BR-2408 让这种情况失败而不是通过，代价是要跟着改解析。
- 扫描防的是不小心提交，不防有意绕过：varlock 可以来自变更自己的依赖（BR-2408），变更删掉 `.env.schema` 也会让这次扫描不运行。
- 只认保管库里已有的值：直接写进代码、从没存进 sops 的新密钥扫不到。
- 只扫最终的文件内容：中间某个提交加了又删掉的值（#185）、写在提交说明里的值（#186）都会进 main 的历史。
- 合入所在的机器拿不到 age 私钥时，开启了的项目每次合入都以退出码 4 失败，直到人把私钥配好；这是负责人要的“没有就报错”，不悄悄放行。
- 扫描只认原样的值：值被变形（编码、拆开）后提交不会被发现，这和 D-85 写的打码局限相同。
