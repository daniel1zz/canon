id: D-86
title: 合入时内置密钥扫描，不靠项目配 before_land
status: proposed
---

## 背景

D-85 让项目用 sops、age、varlock 管密钥，根目录有 `.env.schema` 就算开启，并写明 canon 的代码和检查不变。剩下的缺口：变更把真实的密钥值提交进文件时，合入的规则评审把 diff 发给 `claude -p`，合入后 main 上有了明文，合入后的代码评审还可能把它引用进 GitHub issue。负责人定了（2026-11-11）：合入必须在任何内容发给模型之前拒绝这样的变更，并选了内置在合入里的做法。

在本机实测 varlock 1.24.0（2026-11-11）：`varlock scan <文件…>` 只扫给出的文件，有明文值时退出码 1，发现写在 stderr，每条一行“路径:行:列 变量名”，下一行是代码片段，片段里留着值的前两个字符；取不到 age 私钥时 `varlock scan` 输出“没有可扫的敏感值”并以 0 退出，而 `varlock load --agent` 以 1 退出并报 `Configuration is currently invalid`。

## 方案

1. 让开启了密钥管理的项目自己在 `before_land` 里配 `varlock scan`：否决。`before_land` 在规则评审之后才跑，diff 那时已经发给模型了；而且每个项目都要自己配，忘了配就没有保护，还会碰上上面那个取不到私钥就悄悄通过的坑。
   - 来源：src/work/land/checks/steps.ts “before_land: after floor, canon check and the built-in review”
2. 在 git 的 pre-commit hook 里跑 `varlock scan --staged`：否决。提交可以用 `--no-verify` 跳过，canon 也不检查 agent 怎么干活，只在合入 main 这个边界上检查结果；只靠提交时的 hook，挡不住已经进了分支的值被合入。
   - 来源：canon/product.md “Canon 只在两个边界检查结果：协调状态写入时，和合入 main 时”
3. 按模式找密钥（gitleaks 一类，或 canon 自己写正则）：否决。它不知道项目真实的值，误报漏报都多；varlock 从 `.env.schema` 解析出真实值后逐字比对，项目开启时这些工具本来就是必需的。
   - 来源：canon/decisions/D-85.md “`varlock scan --staged` 在暂存文件里出现真实值时退出码 1”
4. 内置在合入里：被合入的树有 `.env.schema` 时，在规则评审之前先 `varlock load --agent` 再 `varlock scan` 本变更改过的文件，发现就以 `secret` 拒绝，varlock 不可用就以 `environment` 失败：采用。合入是唯一的关口，放在评审之前就保证明文值不会发给模型，也不会进 main。
   - 来源：canon/decisions/D-85.md “canon 的代码和检查不变”

## 决定

合入内置密钥扫描，行为见 BR-2407 和 BR-2408。这改变了 D-85 里“canon 的代码和检查不变”这一句：canon 的合入现在会在项目开启时运行 varlock，项目没有 `.env.schema` 时仍然什么都不跑。

## 后果

- 开启了密钥管理的项目，合入时多一次 varlock 解析（会运行 schema 里的 `exec()`，例如 `sops decrypt`），合入所在的机器必须能拿到 age 私钥，否则合入以退出码 4 失败。
- 拒绝信息只给文件、行号和变量名，不转述 varlock 的输出；varlock 将来改了输出格式、canon 认不出发现时，按环境错误失败，不会当作通过。
- varlock 优先取被合入树的 `node_modules/.bin/varlock`，这个文件来自变更自己的依赖；扫描防的是不小心提交，不防有意绕过。
- 扫描只认原样的值：值被变形（编码、拆开）后提交不会被发现，这和 D-85 写的打码局限相同。
