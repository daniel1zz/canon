---
id: D-66
title: 认领失效在第一次被发现时写一条事件，同一个认领同一种失效只写一次
status: accepted
---

## 背景

#135：派子 agent 的主会话要及时知道哪些变更没人在做。认领失效（会话进程已经不在，或租约到期）现在不是事件，只在有人运行 `canon work status` 时现算出来（BR-2192 的 `state`），所以 `canon events --follow`（#135 的第一个切片）看不到它。一个 worker 写了 handoff 再退出能被 `handoff.write` 看到；崩溃或没写 handoff 就退出时，只有轮询 `canon work status` 才知道。

事实：

- 认领表每次写入（新建、接手、续租）都让 `version` 加 1（`src/work/claims/claims.ts`）。进程退出后不再续租，所以一个失效的认领在被别人接手之前 `version` 不变，“变更编号 + version”可以唯一地标出这一次失效。
- canon 已经有只读查询顺带补写事件的做法：`canon work after-land` 和 `canon brief` 把已结束的后台命令记成 `hook.exit` 事件（BR-2166、BR-2137）。

## 方案

1. **第一次发现时写一条真实事件（采用）**：任何算认领状态的命令（`canon events --follow` 每次查询、`canon work status`、`canon brief`、`canon work start`）发现某个认领是 `holder-gone` 或 `expired`，而事件表里还没有这个“变更编号 + version”的同种事件时，写一条 `claim.holder-gone` 或 `claim.expired`（对象是变更编号，详情有执行者、worktree、version）。用唯一约束保证几个会话同时发现时也只写一条。理由：事后能查到、`canon stats` 能统计（P6），不加 `--follow` 的 `canon events` 也看得到；有现成的先例。代价：这些查询命令会写数据库。
   - 来源：canon/rules/work/hooks/BR-2166.md “先像 `canon brief` 一样把已结束的命令记成 `hook.exit` 事件（BR-2137）”
2. **只在 `--follow` 的输出里合成一行，不写数据库（否决）**：保持查询只读，但历史里查不到，`canon stats` 统计不到，两个跟踪进程各自判断、各报一次；没有在跟踪的时候发生的失效，事后完全没有记录。
   - 来源：canon/rules/work/session/BR-2192.md “租约没到期但记下的会话进程已经不在的标 `(expired: session process exited)`”

## 决定

采用方案 1。判断认领状态只用 `canon work status`、`canon work start` 共用的那一个函数（BR-2100、BR-2192），写事件放在它旁边，所有算状态的命令都经过它。同一个“变更编号 + version + 种类”只写一次；之后认领被接手（`version` 变了）再失效，是新的一次，再写一条。

## 后果

- `canon events --follow --kind claim.holder-gone,claim.expired` 能及时报出没人在做的变更，主会话不用自己轮询 `canon work status`。
- 发现的时间取决于有没有人在运行算状态的命令；有跟踪进程时最多晚一个查询间隔。没人运行任何命令时没有事件，这是已知的限制：canon 不常驻后台进程来巡检认领。
- 要新增唯一约束（旧数据库打开时补上，和其他补表的做法相同）。
- “活着的认领长时间没有文件改动”不在这个决定里：误报多，阈值因项目而异，要做时先拿数据另开 issue。
