---
id: D-77
title: 计划：写在变更文件的步骤表里，变更用 id 指明自己做哪几步，进度由变更状态算出
status: accepted
---

## 背景

负责人提的 #146：一个项目按步骤逐步写规则，规则不是事先登记的，`canon release status` 显示“规划中 0 已通过 378”，看上去已经做完，实际两个计划分别只做了约 41% 和 57%。真正的计划写在变更文件里：一种是 `## 总实施顺序` 下带“依赖”列的步骤表（51 步），一种是 `**第 N 步：…**` 标题加 `- 依赖：` 行。canon 读不出这些，项目自己写了脚本，按标题把步骤对到变更，再数 main 上的 `canon: close C-n`；手工看还漏过一步：它的依赖早就合入了，却几个小时没人派。

已有的概念都不管这件事：版本（D-61）按带 `release:` 标签的规则数进度，只数行为不数工作步骤；规划中的规则（D-32）是还没执行的行为，要事先登记，这个项目正是不这样做；待办顺序（D-20）是负责人排的变更先后，没有依赖，也没有步骤；`canon change list` 列变更，不列变更里的步骤。`canon search 计划`、`canon search plan` 和 `canon decision list` 查不到讲计划或路线图的决策。

约束：产品的“当前真相”和进度只能来自能检查的文件（P1、P5）；多个会话同时工作，一个文件被多人同时改会冲突，所以 canon 一个文档一个文件（P4）；人和 AI 读的是仓库里同一份文件（product.md 的“不做的事”：不做网页 dashboard）；一个变更开工时只存在于自己的分支上，合入前 main 看不到它（BR-2107）。

## 方案

1. 计划写在变更文件的 `## 计划` 节，是一张有固定列（步骤、内容、依赖）的表；做步骤的变更在自己的 front matter 里写 `plan: C-n` 和 `steps: [...]`；每一步的状态每次从变更的状态算出，`canon plan status` 显示：采用。格式有明文规定，`canon check` 能查（写错、依赖成环、指向不存在的步骤都报）；步骤和变更的联系是一个编号，不是猜出来的；联系写在做事的变更自己的文件里，开工时由 `canon work start --plan --step` 写进去，所以不需要改计划文件，多个会话同时开工不冲突；状态不存，所以不会和变更的真实状态不一致。
   - 来源：canon/product.md “所以能算出它准不准”
2. 计划表里每一步写出做它的变更编号（多一列“变更”）：否决。每派一个步骤就要改计划文件，同时开工的会话改同一个文件，合入时互相冲突；计划文件在别的 worktree 里被改时，开工的会话改不到它；变更只在自己分支上时 main 上的计划还没写它，进行中的步骤在 main 上看不见。
   - 来源：src/knowledge/documents/model.ts “One file per document so concurrent sessions only conflict when they edit the same document”
3. 计划放进版本文档（R-n）里：否决。版本是产品的发布节点，有“规划中、进行中、已发布”和发布后冻结的几节（D-61），计划是做的过程，会一边做一边补步骤，冻结会和它冲突；一个计划可以跨版本，也可以不属于任何版本；版本的进度数的是规则，计划的进度数的是步骤，混在一起，“已通过 378”这类数字还是会被读成别的意思。以后可以让计划标上它属于哪个版本，由版本的状态显示计划的进度，那是另一个变更。
   - 来源：src/knowledge/releases/status.ts “the rules tagged with each release, grouped by the execution state”
4. 计划做成独立的文档类型（有自己的编号、目录和状态）：现在不采用。新增一种内置类型要有编号分配、模板、目录、状态、检查和引用规则，而已有的真实计划本来就是大变更的工作说明，写在变更文件里；一个计划也没有自己独立于变更的生命周期（它的步骤就是变更）。如果以后计划需要自己的状态，或者一个计划要跨几个变更文件，再回头看这条。
   - 来源：src/knowledge/documents/types.ts “Five are built in and cannot be removed or reshaped”
5. 不做，留给项目自己的脚本（现在 `tools/plan_progress.py` 那样）：否决。#146 里项目已经为此写了脚本：它按标题把步骤对到变更，标题一改就对不上；它读的是各人各样的散文格式，canon 没法检查；每个用 canon 的项目都得重写一遍，而漏派一步这种事正是发生在没有这个工具的时候。
   - 来源：canon/product.md “每个检查都记录拒绝的原因，所以能算出它准不准”
6. 认出项目已有的各种写法（`## 总实施顺序` 表、`**第 N 步：**` 标题加 `- 依赖：`），按标题对变更：否决。从散文猜格式没有明文规则，`canon check` 无法证明读对了；对不上时只会悄悄少算（违背“必需的值缺失必须报错”），所以格式由 canon 规定，已有的计划改成这个格式。
   - 来源：canon/product.md “规划中的规则标明还没做，不冒充已实现”

## 决定

**计划的格式。** 变更文件里标题是 `## 计划` 的一节是这个变更的计划：节里有一张 Markdown 表，列 `步骤`、`内容`、`依赖`（顺序随意，别的列不读）；`步骤` 是由字母和数字组成、用 `.` 或 `-` 连接的名字；`依赖` 写 `-`、`无` 或留空，否则是用 `,`、`，`、`、` 隔开的步骤名。步骤名不能重复，依赖必须是本计划的步骤、不能是自己、不能成环；不合的报 `file-invalid`（BR-2369、BR-2370）。

**步骤和变更的联系。** 变更 front matter 的 `plan: C-n` 加 `steps: [...]`，只此一种；指向不存在的计划或步骤报 `ref-dangling`（BR-2371）。一步可以由几个变更做，一个变更可以做几步。

**步骤的状态。** 不存，每次从变更算：做它的变更（不含 `dropped`）全部已合入 main 并且 `done` 是已完成；有没完成的（`open`，或只在自己的分支上、还没合入）是进行中；依赖全部已完成是可开始；其余是被挡住。已合入 main 才算完成，因为合入是 canon 唯一承认的“做成了”（BR-2372）。

**怎么看。** `canon plan status [C-n] [--json]`：不带编号每个计划一行（已完成几步、百分比和各状态的步数），带编号列出可开始的步骤（含内容，供协调者派活）、进行中的步骤和变更、被挡住的步骤在等什么（BR-2373、BR-2374）。`canon work start --title … --plan C-n --step 名` 开工时把联系写进新变更的文件（BR-2376）。

**分片。** 这是第一片：格式、检查、状态、`canon plan status`、开工时写联系。其余几片各是一个变更：`canon brief` 和 `canon change list` 提示可开始的步骤，计划标上版本、让 `canon release status` 显示它，已有的计划迁到这个格式的办法。

## 后果

- 项目已有的计划要改成 `## 计划` 表，并且在做步骤的变更里加 `plan`、`steps`（已经开工的变更手改 front matter）；canon 不认旧写法，不按标题猜。
- 进行中的步骤只有做它的变更写了 `plan` 和 `steps` 才看得见：忘了写的变更，步骤会显示成可开始，可能被重复派。`canon work start --plan --step` 是主要的写法，让它不需要手写。
- 计划变更放在 main 上才算有计划：只在自己分支上的计划变更不出现。
- `canon plan status` 读的是 main 上的变更文件和各变更分支，不读正在改的工作区，所以本地还没提交的 `plan`、`steps` 不算。
- 变更的状态是 `done` 但还没有合入 main 时（合入被中断），步骤仍是进行中，和 `canon change list` 的“closed on branch, not landed”一致。
- 步骤名在 YAML 里写 `3.10` 会被读成 `3.1`：带小数点的步骤名要加引号，否则 `canon check` 报错，不悄悄读错。
- 步骤名一经使用就是固定的编号，不是表里的位置：改名或重新编号后，已合入变更里的 `steps` 指向不存在的步骤，`canon check` 报 `ref-dangling`（BR-2371）。所以插入新步骤用新名字（如 `3a`），不重排旧编号。
- 两个会话可以同时用 `--step` 开工同一步，开工不拒绝：一步本来就允许由几个变更做（BR-2371），front matter 也存不下互斥的认领。重复派工能从 `canon plan status` 的 `6 (C-300, C-301)` 看出来；开工时如果这一步已经有没完成的变更在做，就提示出来，这放在 `canon brief` 提示可开始步骤的那一片里做。
- 一步算完成，是指做它的变更全部合入，不是指这一步的内容做完了：只做了一半就合入的变更会让这一步显示成已完成，要接着做就再开一个变更、写上同一步。
