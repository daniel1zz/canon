---
id: D-36
title: 替换旧版本的 git 守卫：先挪走核对再排他放上，不用原子交换
status: accepted
---

## 背景

#25：`ensureGuard` 先判断 hook 的状态（缺少、旧版本），之后不再核对就用改名替换路径上的文件，判断和替换之间别人写进来的 hook 会被悄悄覆盖，违反 BR-2124。#24 之前要求过同时运行的 git 只看到旧的或完整的新 hook（BR-2123），所以修法要同时顾到两件事：不覆盖别人的文件，git 不看到写了一半的 hook。

事实：

- “缺少”状态没有取舍：`link(临时文件, 路径)` 在路径已存在时以 EEXIST 失败，既是排他的，放上的又是已经写完、可执行的文件。
- “旧版本”状态要替换一个已存在的文件。POSIX 的 `rename` 会直接替换目标，事后无法知道换掉的是谁；替换前再读一次只能缩小窗口，不能消除。
- 真正的“比较并交换”需要原子交换两个文件：Linux 的 `renameat2(RENAME_EXCHANGE)`，macOS 的 `renamex_np(RENAME_SWAP)`。Node 和 Bun 的 fs 都没有提供，只能经 `bun:ffi` 调 libc；这台 macOS 上用 Bun 1.4.4 试过 `renamex_np` 可用（编译成单个可执行文件后也可用），Linux 这边这台电脑没法实测；不是所有文件系统都支持交换。
- 守卫平时处在“旧版本”状态的时间很短：只在 canon 升级后第一次 `canon install` 或 `canon update` 之前。

## 方案

1. 原子交换（`renameat2`、`renamex_np`，经 `bun:ffi`）：否决。它是唯一两边都顾到的做法，但要为两个平台各写一段原生调用，Linux 那段在这里测不到；文件系统不支持交换时还得另有一条路，等于两套写法；`bun:ffi` 是 canon 里第一处原生调用，出错时影响所有项目的安装。
   - 来源：https://man7.org/linux/man-pages/man2/rename.2.html “RENAME_EXCHANGE Atomically exchange oldpath and newpath”
   - 来源：https://man7.org/linux/man-pages/man2/rename.2.html “EINVAL The filesystem does not support one of the flags in flags”
2. 先把旧文件改名挪到同目录的旁边，核对挪走的仍是 canon 写的，再用排他的 `link` 放上新守卫；不是 canon 的就放回原处并以退出码 5 拒绝：采用。改名是原子的，挪走的正是那一刻在路径上的文件，所以核对的就是将要丢掉的那一份；`link` 在路径上又出现文件时失败，不会覆盖。代价是挪走和放上之间有一瞬间没有 hook，这时直接移动 main 不会被拦。
   - 来源：https://man7.org/linux/man-pages/man2/link.2.html “EEXIST newpath already exists.”
3. 替换前再读一次，仍是 canon 的才改名换上：否决。只把窗口从“判断到替换”缩短到“第二次读到替换”，别人的文件仍可能被覆盖，#25 要的是消除，不是缩小。
4. 保持现状、只在 BR-2124 里写明这个窗口：否决。丢掉别人的 hook 无法恢复，BR-2124 明确不允许。
   - 来源：canon/rules/cli/install/BR-2124.md “`--force` 也不覆盖”

## 决定

“缺少”状态用排他的 `link` 放上守卫；“旧版本”状态先改名挪走旧文件，核对是 canon 写的才排他放上新的，否则放回并以退出码 5 拒绝。两种情况下 canon 都只删除自己写的文件。BR-2123 相应写明：旧版本被替换的那一瞬间 git 看不到 hook。

## 后果

- 两个坏结果的轻重不同：丢掉别人的 hook 无法恢复；漏拦一次直接移动 main 会留在 git 历史里，能看到、能改回。这次选了前者不再发生。
- 不支持硬链接的文件系统上安装守卫以退出码 4 停下（原来能装）。真遇到时再评估。
- 以后 Node 或 Bun 提供原子交换时，可以换成方案 1，去掉那一瞬间。
