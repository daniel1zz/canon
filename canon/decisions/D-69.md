title: canon events --follow 用每秒一次的按编号轮询，被信号停止算正常结束
status: proposed
---

## 背景

#135：派发子 agent 的主会话需要后台监视器能逐行读到新事件。`canon events --follow` 要持续运行，需要定下两件事：怎么发现新事件，以及它被停止时的退出码。

协调数据库开了 WAL，事件表的主键是递增的整数编号（BR-2156）。`canon work land` 被信号终止时退出 143、130，因为那是被中断的合入，没有完成（BR-2099）。`--follow` 没有“完成”这回事：用户停掉它就是它唯一的结束方式。

## 方案

1. **每秒按事件编号查一次（采用）**：`SELECT ... WHERE id > 上次的最大编号`，主键查询，开销可以忽略；只读。
   - 来源：canon/changes/C-391.md “每秒按事件编号查一次协调数据库”
2. **监听数据库文件（WAL）的变化（否决）**：各平台的文件监听表现不一致，合并写入时会漏通知；漏一次就是漏一条 handoff，正是要解决的问题。
   - 来源：canon/changes/C-391.md “各平台的文件监听表现不一致”
3. **被信号停止时退出 143 / 130，和 `canon work land` 一致（否决）**：监视器的使用者（后台监视、脚本）把非 0 当作失败，而停止 `--follow` 不是失败；`land` 的 143/130 表示合入被打断，含义不同。
   - 来源：canon/rules/work/land/queue/BR-2099.md “以 143（SIGTERM）或 130（SIGINT）退出”

## 决定

采用方案 1。`--follow` 收到 SIGTERM 或 SIGINT 以 0 退出，这是 BR-2022 里 0 的一种情形；协调数据库打不开等错误照常用 BR-2022 的退出码。

## 后果

- 新事件最多晚一秒才输出。
- `--follow` 进程一直持有数据库连接，直到被停止。
- BR-2022 加一句说明这个退出 0 的情形。
