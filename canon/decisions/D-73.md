## 背景

D-34 让负责人在 main 的 `canon/backlog.md` 的 `优先合入` 一节里标优先（BR-2232）。main 只通过合入前移，负责人改清单这个动作本身要先排队，等在它想插队的那个队列里，标了也来不及（#141）。D-34 否决了 `--urgent` 参数和读 worktree 里的清单，原因是负责人的要求（原话）：“修复变更自动插队，负责人可以标优先，agent 不能自己插队”。

负责人（canon 问题 #4，2026-11-08）选了方案 A：用一个命令把优先记进协调数据库，经问人流程确认后才生效。随后（canon 问题 #6）又改了主意，原话：“不要搞这么复杂去做人工认证，ageng没必要冒充人，他说是人那肯定是我说的”。

核对过的事实：现有问人流程对转述的回答只做标记、不拦截，而且 agent 自己能调用 `canon human record` 写出佐证记录，所以用它做“确认关卡”拦不住存心冒充的 agent，只是多出几步（D-6、D-47）。

## 方案

1. 只改清单的落地方式：只改 `canon/backlog.md` 的变更按修复 main 的变更同等待遇、不排队直接合入：否决。任何 agent 都能开一个只改这个文件的变更，自己给自己插队，正是 D-34 说的 agent 不能自己插队。
   - 来源：canon/decisions/D-34.md “agent 能自己加参数，等于自己插队，负责人明确不要。”
2. 命令记到协调数据库，要经问人流程确认（负责人先选的方案 A）：否决，负责人后来明说不要。确认的核实本来就拦不住冒充（D-47），换来的只是更复杂。
   - 来源：canon/decisions/D-47.md “所以记录里是“工具返回了什么”，不一定是“人选了什么”。”
3. 什么都不做：否决。负责人标的优先要等它想插队的那个队列走完才生效，等于没有。
4. 命令把优先记进协调数据库，立刻生效；必须带负责人的原话 `--relayed`，和转述的回答同一种信任，原话只留作记录：采用。
   - 来源：canon/decisions/D-6.md “canon 不声称能阻止冒充”

## 决定

采用方案 4：

- `canon backlog urgent <C-n> --relayed "<负责人的原话>"` 立刻把这个变更记为负责人标的优先；`--clear` 撤销。没有 `--relayed`（或是空白）时失败，什么也不记。命令的帮助、`canon brief` 都写明：agent 只在负责人在对话里要求时才用它，不为催自己的变更用。原话和转述的操作者记进事件，只用于事后查（BR-2364）。
- 优先级：修复 main 的变更最先，其次是负责人用命令标的变更，再其次是 main 上 `优先合入` 一节的变更，最后按入队顺序；正在合入的不打断。每次查看轮次时从数据库重读，所以下一次轮次就生效（BR-2363）。
- 优先在这个变更合入时自动结束，或被 `--clear` 撤销；停止、放弃的变更不自动清，由负责人撤销。
- `canon work status` 列出现有的标记（BR-2365）。

## 后果

- 部分修改 D-34：负责人标优先不再只能走 main 上的清单，D-34 的方案 3 和 5 的否决理由仍成立（命令不是 `land` 的参数，也不读 worktree 里的清单）；“agent 不能自己插队”现在靠 agent 守规则和事后可查，不靠 canon 拦截，和 D-6 一致。
- 一个存心的 agent 可以自己标优先，事件表里留着它的操作者和写下的“原话”。
- 低优先级条目仍可能被一直插队，和 D-34 的后果一样，由负责人控制。
