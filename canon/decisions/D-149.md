## 背景

D-148 让变更写明版本或模块、issue 和依赖，由命令写入，依赖没满足的不列为可开始，依赖成环拒绝。落到规则时有三件事 D-148 没定：

- 被依赖的变更常常还不在 main 上：`canon work start --title` 新建的变更，文件合入之前只在它自己的分支上。依赖它的变更写 `depends_on` 时，`canon check` 要不要求它存在？
- “合入了才算满足”按哪棵树看：当前 checkout、main 的最新提交，还是也看别的分支？
- 成环查哪些边：只看被检查的树，还是把在途分支也读进来？

还有一个 D-148 没覆盖的需要（主会话 2026-11-20 设计 C-627 时发现）：有的后续工作要等负责人确认，而不是等一个变更合入。例如一步是“负责人逐条回答清单”，放清单的那个变更一合入，后续那一步按 D-148 的“依赖的变更合入了才算满足”就能开始了，可负责人还没回答。

另外这些规则放在哪个领域：现有的 `knowledge/plans` 会在 C-626 的 E 步整体去掉，`knowledge/releases` 只管版本和模块本身，`work/session` 已经 37 条规则。

## 方案

1. **新子领域 `knowledge/changes`；满足按 main 最新提交判定，只在分支上的算没合入；`canon check` 不查依赖目标存在与否，成环只看被检查的树**：采用。
   - 依赖的目标可以只在别的分支上，所以存在与否只由写入的命令查（main、当前 checkout 和所有变更分支里都没有才拒绝），`canon check` 不报；找不到的依赖在列表里标出来，是提醒。
   - 满足看 main 的最新提交，和列表判断“只在分支上”的做法一致：worktree 可能落后于 main，按它的树看会把已经合入的依赖当成没合入。分支上写着 `done` 的变更没有合入，不算满足。
   - 成环只看被检查的那棵树：合入时这棵树就是 rebase 后的树，两个分支各加一条边、合在一起才成环的情况在后合入的那个上被拒；别的分支上的边还没进 main，可能改也可能被放弃，算进来会让 `canon check` 的结果随别人的分支变化。
   - 领域：依赖和关联是计划被去掉后接替它的东西（D-148 方案 1），单独成一个子领域，E 步去掉 `knowledge/plans` 时不用搬规则。
   - 来源：src/work/session/session.ts “a change made with --title lives only there until it”
   - 来源：src/work/session/inflight.ts “a branch is judged against main's tip, not this checkout”
   - 来源：canon/decisions/D-148.md “依赖成环在 rebase 后的树上查，属于完整性，拒绝”
2. **依赖也可以是一条成功标准（`R-n/S<k>`、`F-n/S<k>`），它已满足才算满足**：采用，修改 D-148 里“依赖的变更合入了才算满足”，只对写成成功标准的依赖。要负责人确认的事写成一条待负责人的成功标准；它离开待负责人要负责人为某个变更回答过问题（BR-2510），所以 AI 满足不了这条依赖，不用另做一套确认机制。写的成功标准不存在是 `ref-dangling`，和 `advances` 一样只查未结束的变更；列表里写出这一条的文字。
   - 来源：canon/decisions/D-148.md “依赖的变更合入了才算满足”
   - 来源：canon/rules/knowledge/releases/BR-2510.md “只有让成功标准离开待负责人要负责人为这个变更回答过的问题”
3. **要负责人确认的依赖写成 `canon human` 问题编号，问题回答了就算满足**：否决。问题回答了不等于回答的是“同意”，判断回答的内容要另写规则；成功标准已经有“待负责人只有负责人能放行”的保证，又是版本进度看的东西（D-148 方案 1），依赖它就把“等负责人”和“版本做到哪了”放在同一处。
   - 来源：canon/decisions/D-148.md “进度：版本和模块算不算完成，只看它的规则状态和成功标准”
4. **`canon check` 要求 `depends_on` 的目标在被检查的树里存在，否则 `ref-dangling`**：否决。依赖一个刚用 `--title` 开工、还没合入的变更是常见情况，它的文件不在依赖方的树里，这条检查会拒绝正常的工作；按 D-139，缺关联不算错，依赖找不到也只该提醒。
   - 来源：canon/decisions/D-139.md “其余检查（防忘事、流程是否走全、质量是否达标、该不该先做别的）都给出标准”
5. **`canon check` 和成环判定把所有在途分支上的变更也读进来**：否决。检查的结果会随别的会话的分支变化（建、改、删），同一个提交今天过明天不过；在途分支上的边还没进 main，不是 main 的事实。合入时查 rebase 后的树已经能挡住真正进 main 的环。
   - 来源：src/knowledge/check/check.ts “It checks outcomes only”
6. **满足按当前 checkout 的树判定**：否决。worktree 从 main 分出后，main 上合入的依赖它看不到，会把可以开始的变更标成在等。
   - 来源：src/work/session/inflight.ts “an old worktree lacks changes main has landed since”
7. **规则放进 `knowledge/plans`**：否决。D-148 要去掉计划，这个领域在 E 步整体作废，依赖的规则放进去还要再搬一次。
   - 来源：canon/decisions/D-148.md “原来的一步就是一个变更”

## 决定

采用方案 1 和方案 2；D-148 里“依赖的变更合入了才算满足”对写成成功标准的依赖改为“这条成功标准已满足才算满足”。新增子领域 `knowledge/changes`。关联的写法按 BR-2561，命令写入按 BR-2562、BR-2563，依赖的满足和列表按 BR-2564，成环按 BR-2565；没挂版本或模块的未结束变更在总览里列出按 BR-2505。

## 后果

- 依赖找不到时没有检查拦，只有 `canon change list`、`canon brief` 里的 `(not found)` 标记；写错编号要靠会话看到标记后改。
- 两个分支各自都不成环、合在一起成环时，后合入的那个才被拒，要在它自己的分支上改掉一条边再合入。
- 提前建的变更（`canon change new`）要等所在的变更合入 main 之后才出现在列表里、才能开工，因为列表只读 main 和变更自己的分支。
- 数据的演进：关联都在变更文件里，随合入进 git；没写关联的旧变更照常读入，不用迁移。
