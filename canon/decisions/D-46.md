id: D-46
title: canon uninstall：等进行中的工作清空后，合入一个删掉 canon/config.yaml 的变更，再清理本地
status: accepted

## 背景

负责人问安装和卸载是否都干净（2026-11-04）。实测：`canon init` 只写项目里的文件，重复 `canon install` 不产生改动；但没有卸载，而且 canon 进了 main 之后没有受支持的办法移除它：在 main 上直接 `git rm -r canon .claude` 再提交，被 git 守卫拒绝（BR-2126）；开一个删掉 `canon/` 的变更去合入，`canon work land` 从变更的树里读 `canon/config.yaml`，读不到 `floor`，以退出码 2 拒绝，设好 `floor` 也一样。唯一出路是手删 hook 文件或设没有写进文档的环境变量。手删时如果漏了 `.claude/settings.json`，每个新会话都会被 `|| echo` 的兜底提示“去装 canon”。

canon 放进项目的东西分三类：
- 进版本库的：`.claude/skills/canon-*` 和清单、`.claude/settings.json` 里 canon 的条目、`canon/config.yaml`；`canon/` 下其余文档是项目的会话自己写的知识，不是安装程序写的。
- 不进版本库、每个克隆各一份的：git 守卫、`<git 公共目录>/canon/`（协调数据库、日志）、`refs/canon/*`、`change/*` 分支和 `<主检出>.worktrees/` 下的 worktree、`.canon/` 和 `.git/info/exclude` 里它那一行。
- 找回用的：`refs/canon/archive/*`（`canon work drop` 存下的、别处没有的工作）和 `refs/canon/snapshots/*`（Bash 调用前的快照）。

几个约束：`canon work land` 合入后把 main 推到远端，守卫在每个克隆里各有一份，只要 main 上还有 `canon/config.yaml` 就继续拦；`worktree.baseRef` 是 canon 写的，但 canon 没记下写之前的值；别的会话可能正在做变更。独立评审（不看推荐）指出：只删本地守卫、保留 `canon/config.yaml` 的做法在别的克隆里留下仍然生效的守卫；先删守卫再直接提交，会和同时进行的合入抢 main，并且跳过 floor 和评审。

## 方案

1. 先确认没有进行中的工作，再把“删掉 canon 装的文件和 `canon/config.yaml`”作为一个变更走正常流程合入，合入后清理本地；别的克隆同步到这个提交后，再跑同一个命令只做本地清理：采用。`canon/config.yaml` 是开关，它离开 main 之后，每个克隆的守卫条件都不再成立，不用逐个克隆去拆；变更照常经过队列、floor 和检查，不和别的合入抢 main。代价是合入时要用删除之前的配置（floor 等），这只在卸载自己的合入里成立。
   - 来源：https://raw.githubusercontent.com/evilmartians/lefthook/master/cmd/uninstall.go “remove lefthook configs”
   - 来源：https://pre-commit.com/ “will restore your hooks to the state prior to installation”
2. 先删掉守卫，再在 main 上直接提交删除，最后清理：否决。删守卫和提交之间，别的会话的 `canon work land` 能移动 main；直接提交不经过 floor 和评审（P4、P5）；中途停下会留下没有守卫、但看起来还装着 canon 的项目。
3. 只改工作区（删守卫、状态和文件），提交交给用户，像 `rm` 一样：否决。守卫先没了，main 没人保护，别的会话的快照 hook 还在写 `refs/canon/snapshots`，直到有人提交为止；文件系统是许多会话共用的。
4. 保留整个 `canon/`（包括 `config.yaml`），只删 skill、hook 和本地守卫：否决。`config.yaml` 还在 main 上，canon 就还算开着，别的克隆的守卫照样拦。

找回用的 refs 和 `canon/` 下的知识默认保留，加 `--purge-recovery`、`--remove-knowledge` 才删，和 lefthook 默认不删配置、加 `--remove-configs` 才删一致；负责人选了这三个默认（2026-11-04）：知识默认保留、找回数据默认保留、有进行中的工作就拒绝。

## 决定

- `canon uninstall` 先确认没有进行中的工作（BR-2277）、没有改过的 skill 文件（BR-2279），再开一个变更删掉 canon 装的文件和 `canon/config.yaml`，用删除之前的配置合入（BR-2278）；配了远端时先同步。
- main 上已经没有 `canon/config.yaml` 时只做本地清理（BR-2280）：canon 写的守卫、可以安全删掉的 worktree 和已合入的 `change/*` 分支、协调数据库目录、`.canon/` 和它的 exclude 行、除找回用以外的 `refs/canon/*`。后台的合入后命令还在跑时先停下（BR-2283）。
- 找回用的 refs 默认保留并打印数量和找回方法，`--purge-recovery` 才删（BR-2281）；`--remove-knowledge` 在 canon 移除之后另提交一次删掉 `canon/`，不经过规则评审（BR-2282）。
- `worktree.baseRef` 保留并在输出里说明：canon 不知道写之前的值，删掉会悄悄改变子 agent worktree 的起点。

## 后果

- 卸载不是一步：在卸载的克隆里，合入成功后同一次运行接着做本地清理；合入被拒或排队超时时什么本地东西都不删，在变更的 worktree 里修好、合入后再跑一次。
- 卸载之后还留着 `canon/` 下的文档时，再 `canon init` 不覆盖已有文件（BR-2076），编号从文件里最大的号接着分配，旧知识照常可读。
- 规则评审不看 `--remove-knowledge` 删掉的文档：那时 canon 已经不在这个项目里了。
