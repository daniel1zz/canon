---
id: D-76
title: 评审提示快超出预算的提前提示放在 canon check，70% 起提示，worktree 里数真实的改动文档
status: accepted
---

## 背景

#145：一个领域的规则评审提示超过 `review_max_prompt_kb`（BR-2359）时，改它的变更在 `canon work review` 或合入时被拒（退出码 4），之后这个领域的每个变更都被挡住。项目事先看不到：大小要按 canon 内部的装箱（领域说明、列表、最大的一条规则）算，从外面估不出来。#145 的实例：`dungeon` 的最小一块 130 KB，固定部分 65 KB，合计 195 KB，占 250 KB 预算的 78%；下一个变更带来 56 KB 的改动文档，合计 251 KB，被拒。要定的是：在哪里提示，用谁的大小算，几成预算起提示，固定部分里的“改动文档”怎么算，提示是警告还是拒绝。

C-413 先落地的版本（80% 的线，改动文档一律按 0）经独立评审发现：在 #145 自己的数上不会提示（78% 低于 80%），所以要改。

支撑的承诺：P5（文档不说谎，文档变大到评审无法运行是要提前看到的状态）、P4（一个领域的变更不会无声地全被挡住）。

## 方案

1. **`canon check` 在标准错误输出一行提示，不算发现（采用）**：按 BR-2359 用的大小算（复用 `reviewPrompts` 的装箱计算，不另写估算）。改动文档：在 main 的检出里按 0 KB（提示是下限）；在变更的 worktree 里按这项工作真实改动的文档算，量法和合入时的评审同一份代码（`reviewScope`，BR-2358），不另写定义。合计达到预算的 70% 就说；带真实改动文档的合计超过预算时，说合入时的评审会被拒绝，并给出和拒绝信息一样的补救办法。预算和 `review` 取 main 上的配置（和 BR-2074 对评审设置的做法一致，用同一个读取函数），说的就是合入时用的那份。改文档的会话合入前都会跑 `canon check`。已有同类机制：`canon check` 的其他提示（BR-2257、BR-2150、BR-2318），标准输出和退出码不变（BR-2189），不是新机制。
   - 来源：canon/rules/knowledge/check/BR-2257.md “这是提示，不是发现（D-37）：不算进发现条数，不改变标准输出和退出码”
2. **`canon rule domains` 里提示（否决）**：这条命令列领域和规则数，谁改领域前都不一定看它；它也没有已有的提示机制，要新建。`canon check` 是每次合入前都会跑的命令，提示放在那里才会被看到。
3. **作为 `canon check` 的发现，达到 70% 就拒绝合入（否决）**：和 D-37 方案 3 一样的理由：一旦到了，之后每个合入都被拒，哪怕它根本没碰这个领域；70% 是估出来的线，不值得当门槛。
   - 来源：canon/decisions/D-37.md “一旦超了，之后每个合入都被拒，哪怕它根本没碰这些文字”
4. **改动文档用某个典型大小估（否决）**：没有改动就没有“典型”，任何数都是编的，估高了会让没有问题的领域天天报警，估低了等于 0。在 main 的检出里没有改动，所以仍按 0 算并明说是下限；在 worktree 里改动是真实存在的，直接数它（方案 1）。
5. **用 `canon work test` 也提示（否决）**：只在 `canon check` 里提示；`canon work test` 最后会跑 `canon check` 的发现，但不转发提示。需要时另开 issue。
6. **80% 的线，改动文档按 0（否决，C-413 先落地的做法）**：#145 实测固定部分加领域那一块是 195 KB，占 250 KB 的 78%，达不到 80%，不会提示；而下一个变更带来 56 KB 的改动文档就被拒。按这个线，提示在促成它的那个案例里恰好不响。70% 在 250 KB 下留 75 KB，盖得住 56 KB。
7. **按最近最大的一次变更估改动文档（否决）**：要读事件历史，两个检出的事件不一样，同一个仓库在两处给出不同的提示；最近最大的变更也不代表下一个。

## 决定

采用方案 1：`canon check` 对每个顶层领域算 BR-2359 最小一次提示的三部分，三部分之和达到 `review_max_prompt_kb` 的 70% 时，在标准错误输出一行提示（BR-2375）。改动文档：main 的检出里按 0，worktree 里按这项工作真实改动的文档（和合入时的评审同一种量法）；带真实改动文档的合计超过预算时，提示说合入时的评审会被拒绝，并给出补救办法。预算取 main 上的配置，和合入一致。补救办法的选法也同一处：顶层领域自己的 README 连同它后面的列表占那一块一半以上时，拒绝信息和提示都不再建议拆子领域，因为列表留在顶层领域，拆了缩不小（BR-2359）。

## 后果

- 在 main 的检出里提示是下限：改动文档大的变更仍可能在没提示的领域被拒；在变更自己的 worktree 里数了真实的改动文档，合入前就能看到会不会被拒。
- 大小计算只有一份（`reviewSizes`、`changedBytes` 和拒绝信息的补救办法 `refusalRemedy` 与 `reviewPrompts` 共用），将来改装箱，提示自动跟着变。
- `canon check` 在 worktree 里多做一次 git 差异，并读 main 上的配置。
- `review` 是 `none` 时不评审，也就不提示。
