---
id: D-76
title: 评审提示快超出预算的提前提示放在 canon check，改动文档按 0 估
status: proposed
---

## 背景

#145：一个领域的规则评审提示超过 `review_max_prompt_kb`（BR-2359）时，改它的变更在 `canon work review` 或合入时被拒（退出码 4），之后这个领域的每个变更都被挡住。项目事先看不到：大小要按 canon 内部的装箱（领域说明、列表、最大的一条规则）算，从外面估不出来。#145 的实例：`dungeon` 的最小一块 130 KB，而它的规则合计只有两个 50 KB。要定的是：在哪里提示，用谁的大小算，没有改动时固定部分里的“改动文档”怎么估，提示是警告还是拒绝。

支撑的承诺：P5（文档不说谎，文档变大到评审无法运行是要提前看到的状态）、P4（一个领域的变更不会无声地全被挡住）。

## 方案

1. **`canon check` 在标准错误输出一行提示，不算发现（采用）**：按 BR-2359 用的大小算（复用 `reviewPrompts` 的装箱计算，不另写估算），提示是下限（改动文档按 0 KB），达到预算的 80% 就说。改文档的会话合入前都会跑 `canon check`。已有同类机制：`canon check` 的其他提示（BR-2257、BR-2150、BR-2318），标准输出和退出码不变（BR-2189），不是新机制。
   - 来源：canon/rules/knowledge/check/BR-2257.md “这是提示，不是发现（D-37）：不算进发现条数，不改变标准输出和退出码”
2. **`canon rule domains` 里提示（否决）**：这条命令列领域和规则数，谁改领域前都不一定看它；它也没有已有的提示机制，要新建。`canon check` 是每次合入前都会跑的命令，提示放在那里才会被看到。
3. **作为 `canon check` 的发现，达到 80% 就拒绝合入（否决）**：和 D-37 方案 3 一样的理由：一旦到了，之后每个合入都被拒，哪怕它根本没碰这个领域；80% 是估出来的下限，不值得当门槛。
   - 来源：canon/decisions/D-37.md “一旦超了，之后每个合入都被拒，哪怕它根本没碰这些文字”
4. **改动文档用某个典型大小估（否决）**：没有改动就没有“典型”，任何数都是编的，估高了会让没有问题的领域天天报警，估低了等于 0。按 0 算，提示明说“不含改动文档”，所以它是下限：说到的领域一定快到拒绝线，没说到的不保证。
5. **用 `canon work test` 也提示（否决）**：只在 `canon check` 里提示；`canon work test` 最后会跑 `canon check` 的发现，但不转发提示。需要时另开 issue。

## 决定

采用方案 1：`canon check` 对每个顶层领域算 BR-2359 最小一次提示的三部分，改动文档按 0，三部分之和达到 `review_max_prompt_kb` 的 80% 时，在标准错误输出一行提示（BR-2375）。补救办法的选法也同一处：顶层领域自己的 README 连同它后面的列表占那一块一半以上时，拒绝信息和提示都不再建议拆子领域，因为列表留在顶层领域，拆了缩不小（BR-2359）。

## 后果

- 提示是下限：改动文档大的变更仍可能在没提示的领域被拒。
- 大小计算只有一份（`reviewSizes`，和 `reviewPrompts` 共用同一个装箱的价格函数），将来改装箱，提示自动跟着变。
- `review` 是 `none` 时不评审，也就不提示。
