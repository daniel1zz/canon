id: D-128
title: 设计由主会话定：worker 在派发时固定的设计版本内执行并自己合入，不能改设计，没定的设计交回主会话
status: proposed
---

## 背景

负责人 2026-11-15 定了方向：“设计不要让worker做”“worker只负责执行”“如果需要设计worker应该通知主agent”“我要最佳的设计，而不是为了兼容现在”，并要求做成 canon 的机制，不是某个项目的脚本（#232）。现在 canon 不拦子 agent 写设计：它可以新建决策、改规则的 `## 规则` 和 `## 例子`、在变更文件里写设计约定，然后自己合入。zhushenkongjian 里一个 worker 在变更文件里写了一整套敌人 AI 执行器的约定并开始写代码，之后才有人发现这份设计不是主会话定的；那个项目临时加了一个 `before_land` 脚本拦 worker 改决策和规则正文，它看不到变更文件里的设计和代码里的选择。

那个项目的顾问评审补了几点：设计不只是决策和规则正文（规则的 front matter、把规则移出规则目录、负责人的设计文件、发布范围都会改变要做什么）；hook 只看得到谁在合入，看不到文件是谁写的、设计是不是派发前定好的；认不出身份的合入不能当主会话；候选里的检查保护不了自己；`canon work take` 只认同一个会话的子 agent，接不了另一个进程里的 worker。

同目录的 Codex 不看我的倾向独立做了设计：问题应该是“设计决定权属于谁、worker 按什么约定执行、谁对集成结果负责”，不是“禁止 worker 改哪些文件”；代码里也有设计，靠文件黑名单证明不了 worker 没做设计；`currentActor` 是标签不是认证（D-125），这里防的是正常使用中的错误，不防同一个系统用户下的有意冒充。它给了两个方案（下面的 1 和 2），推荐 2；负责人在两者之间选了 1 加合入后评审补强（原话：“A + 合入后评审补强 (推荐)”）。

## 方案

1. 主会话先把设计（规划中的规则、决策）合入 main，再用 `canon work delegate` 把变更派给 worker，固定设计负责人、设计版本（这时 main 的提交）、契约清单和代次；worker 只能认领派给它的变更、不能自己开变更或杂务，派发绑定第一个认领它的会话；合入时 canon 拒绝它改设计、拒绝契约清单在派发后变了的合入、拒绝变更上还有没回答的设计请求的合入、拒绝代次已作废的合入；worker 用 `canon work need-design` 把没定的设计交回，请求跟着变更走；设计负责人在 worker 停下、没有合入在进行时可以跨进程 `take`；评审意见只由设计负责人处理；合入后的代码评审另找 worker 的代码里规则没写到的业务选择，开 issue 交给设计负责人：采用。worker 保留自己合入，并行不受影响；文件和版本检查在合入这个已有的边界上做，符合 canon 只在协调状态写入和合入 main 两个边界检查结果；代码里自己补的设计挡不住，由合入后的评审发现、交给设计负责人。
   - 来源：https://github.com/daniel1zz/canon/issues/232 “A before_land hook, `tools/check_worker_design.py`, refuses a sub-agent's landing”
   - 来源：https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners “Code owners are automatically requested for review when someone opens a pull request that modifies code that they own.”
2. worker 不能合入，只交一个固定的提交和测试证据；主会话把它取到单独的集成树里，检查代码里有没有没定过的设计，再自己合入：否决。设计控制最严，但所有合入都排到主会话一个人身上，并行变慢；“检查代码里有没有没定过的设计”同样是判断，并不比方案 1 的合入后评审更能被核对；负责人选了方案 1。
   - 来源：canon/product.md “多个会话同时工作，不丢工作、不互相覆盖”
3. 只在合入时按文件拦 worker 改决策和规则正文，不记派发、不交回：否决。这就是那个项目的临时脚本：看不到变更文件里的设计、发布范围和设计文件，派发后设计变了也不知道，worker 卡住时只能自己定或者停下等人重新交代（P3）。
   - 来源：https://github.com/daniel1zz/canon/issues/232 “It cannot see design written as change-file prose or as choices in code.”
4. 在 `canon decision new`、`canon rule new` 和编辑文件时就拒绝 worker：否决。编辑不经过 canon，拦不全；最后能保证的只有合入这一个边界。命令里早拒绝可以以后作为提示另加，不作为保证。
   - 来源：canon/product.md “Canon 只在两个边界检查结果：协调状态写入时，和合入 main 时。”

## 决定

采用方案 1：派发和交回见 `work/delegation`（BR-2497 到 BR-2500），worker 合入的检查见 BR-2501，评审意见见 BR-2502，合入后代码评审见 BR-2503。

## 后果

- 主会话派发前要先把设计合入 main：新行为写成规划中的规则（D-32），改已生效规则的写成带 `will_amend` 的规划中规则（D-127）。worker 激活规则只能改状态，规则文字要随实现改时交回设计负责人。
- `canon-parallel` skill 和 `canon brief` 的流程说明要改：子 agent 不再自己 `canon work start --title` 或 `canon chore start`，先由主会话建变更再派发。
- 合入后评审补强只在项目运行合入后的代码评审（`after_land` 里的 `scripts/code-review.ts`）时才有；没运行时派发会提示 `design-gap review: not configured`，那个项目里代码自己补的设计只能靠设计负责人自己看。
- 派发绑定第一个认领的会话和代次，所以名字相同的另一个会话、`take` 或重新派发之前的迟到操作合入不了；代价是 worker 会话换了（崩溃后重开）要设计负责人先 `take` 再重新派发；设计改了以后 worker 要明确接受新设计（`canon work accept-design`）才能继续合入。
- 防的是正常使用里的错误，不防有意冒充：执行者是标签（D-125），一个 worker 不带名字运行就会被当成主会话；delegate 工具按 BR-2495 设 `CANON_SUBAGENT`，Claude Code 子 agent 由 hook 按 BR-2340 拦。
- 最坏的情况：设计漏了一个业务选择，worker 在代码里自己定了并合入，合入检查放行；要等合入后的代码评审（BR-2503）发现，它是模型判断，可能漏报。
- 什么结果说明这个选择错了：`canon-design-gap` issue 反复出现、设计负责人每次都要补规则或改代码，说明 worker 自己合入的代价超过了并行的好处，那时改成方案 2；或者 worker 频繁被“派发后设计变了”拦住，说明设计版本的粒度太粗，要改成只比较这个变更引用的文档以外更窄的范围。
- 设计请求、派发记录放在协调数据库里（不进 git），和认领、人的问题一样；设计本身仍只在 `canon/` 下的文档里。新表和以后加的列按 BR-2078 在打开数据库时补齐，旧数据不迁移。数据库丢了，派发和设计请求跟着丢：没合入的工作还在 worktree 和分支上，设计负责人重新派发、worker 重新提请求就能接上；派发记录不是设计本身，丢了不丢设计。
