---
id: D-33
title: 用协调目录里一个 SQLite 文件的写事务串行化 canon 的 git worktree add，不靠出错重试
status: accepted
---

## 背景

issue #32：并发 `canon work start` 偶尔以退出码 4 失败，`fatal: failed to read .git/worktrees/<id>/commondir`。今天这个问题造成了本仓库 5 次 floor 拒绝里的 3 次（`session.test.ts` 的 BR-2132）。

实测（git 2.50.1 Apple Git-155，2026-11-03）：

- 只用 git，8 个并发 `git worktree add`：40 轮里 2 轮出现这个错误（issue 里另一次是 5 轮）；用 `lockf` 把同样的 8 个命令串起来：40 轮 0 次。
- 失败的状态可以稳定造出来：`.git/worktrees/half/` 里有 `gitdir`、`commondir` 是空文件，这时 `git worktree add` 和 `git worktree list` 都失败（退出码 128，`failed to read .git/worktrees/half/commondir: Undefined error: 0`）；只有 `commondir` 没有 `gitdir`、或者 `gitdir` 为空时不失败。也就是 git 写完 `gitdir`、还没写入 `commondir` 的那一刻。
- 所以读的一方不只是 `git worktree add`，还有 `git worktree list`；canon 每个命令打开工作区时都会 list（`src/work/workspace.ts`）。

## 方案

1. 识别这条错误后重试。否决：只处理症状；重试的那次同样可能撞上下一个正在建的 worktree，次数和间隔都是猜的；而且每个读 worktree 列表的地方都要各自加。
   - 来源：https://github.com/daniel1zz/canon/issues/32 “或者识别这条错误后重试一次（git 的竞争是瞬时的）”
2. 在协调数据库（`state.db`）里开一个写事务当锁。否决：协调数据库是 WAL 模式、写得很频繁，用它当锁会让认领、事件这些写入都等 git checkout；而 WAL 下读不阻塞写，做不出“读和写互斥”。
   - 来源：src/work/db.ts “enableWal(db);”
3. 自己写锁文件（`O_EXCL` 建文件，写入 pid，靠 pid 判断持有者死没死）。否决：进程被杀后锁文件留下，要自己判断过期，pid 会被复用；等待也要自己轮询。
4. 在公共目录下单独一个空的 SQLite 文件 `canon/worktree.lock` 上开事务当锁：添加和删除用 `BEGIN EXCLUSIVE`（排他），读列表用 `BEGIN` 加一次读（共享）。采用。等待交给 SQLite 的 busy timeout；锁是操作系统的文件锁，进程死了自动放开；文件始终是空的，不写任何数据。实测（bun:sqlite）：排他持有时共享要等到放开；两个共享可以同时拿到；共享持有时排他要等。
   - 来源：https://www.sqlite.org/lang_transaction.html “IMMEDIATE causes the database connection to start a new write immediately, without waiting for a write statement. The BEGIN IMMEDIATE might fail with SQLITE_BUSY if another write transaction is already active on another database connection.”

## 决定

用方案 4，放在 `src/kernel/git.ts`：`withWorktreeLock(cwd, "change" | "read", fn)`、`addWorktree`、`removeWorktree`、`listWorktreesLocked`。最多等 300 秒（一次 checkout 在大仓库里可能要几十秒），超过以退出码 4 失败、说明锁文件。持有排他锁时运行的 git 命令带环境变量 `CANON_WORKTREE_LOCK_HELD=1`，这个命令的 hook 里再运行 canon 时不再等锁，否则 hook 等父进程、父进程等 hook，直到超时（实测：去掉这一条，hook 里的读要等满超时才失败）。

本变更只改 work/session 的代码和打开工作区的地方；`src/work/land/land.ts` 的批量 worktree、`src/work/drop/drop.ts` 的删除和列表还直接调用 git，之后改用这几个函数。

## 后果

- canon 自己的 worktree 添加、删除、读列表不会再读到另一个 canon 进程建了一半的登记目录。
- 每个 canon 命令打开工作区时多开一次空 SQLite 文件（约 1 毫秒）；别人正在建 worktree 时要等它建完（checkout 的时间）。
- 不经过 canon 的 git 命令（人手动 `git worktree add`、IDE）不受这把锁约束，仍可能撞上。
