title: 设计类 skill 按情境触发，并在推荐前做独立反驳
status: accepted
---

## 背景

2026-11-03 负责人问“现在的规则集是不是最佳状态”。主 agent 把它当成缺陷审计：派三个子 agent 找缺陷，再按缺陷清单给出 A/B/C 三个方案，并推荐 B（修错 + 重整目录）。负责人追问“B 就是最佳设计了吗”之后才发现，B 没碰到根本问题：一棵目录树只能按一种方式分类，而查规则的问题来自好几个方向（拒绝原因、配置键、退出码、承诺）。A/B/C 只是同一个设计做多做少，不是不同的设计；`canon-design` 要求的“先看成熟产品”和“真实的备选方案”都没做。

当时 `canon-design` 的 description 就在上下文里。Claude Code 由模型读 description 判断要不要用 skill，不是关键词匹配；主 agent 读了它，但把问题归成“审计”而不是“设计”，所以没用。出错的是对问题类型的判断。另外 `canon-design` 正文还让人用 sequential thinking 推理，这个 MCP 已按 N-2 移除。

## 方案

1. 往 description 里多加触发关键词（“评估”“是否最佳”等）：否决。skill 由模型按语义判断，加词只是多几个例子，管不住“把设计问题归成审计”这种判断错误。
   - 来源：https://code.claude.com/docs/en/skills “Claude uses this to decide when to apply the skill”
2. 在 CLAUDE.md 加一条常驻规则“评估设计时先用 canon-design”：否决。和改写 description 作用重叠，只多占每个会话的上下文。
3. 引入 sequential-thinking 一类的分步推理工具：否决。它只记录模型自己写下的步骤，不增加推理能力，也不会让模型换一个问题框架；是否调用同样由模型判断，会在同一处失手。N-2 已因“与模型自带推理重复”移除它。
   - 来源：canon/notes/N-2.md “与模型自带推理重复”
4. 改写 description，把“判断已有结构、模型或流程是否合适、该怎么改”写成适用情境；并在 skill 里要求：给出设计推荐之前，先派一个看不到推荐的子 agent，从“问题是不是问错了、方案是不是同一设计的多做少做”反驳一次：采用。情境写法直接对准这次判断错的那类问题；独立反驳不依赖主 agent 自己发现自己框错了。
5. 每次统计 skill 的召回情况（该用没用）：否决，不放进本决定；它防不住当场的失误，只能事后发现，已由 C-34 单独跟进。

## 决定

采用方案 4：

- `canon-design` 的 description 先写适用情境，明确包括“评估已有的结构、模型或流程是否是对的设计、该怎么改”，不只是新建。
- 正文第 3 步要求：真实的备选方案必须是不同的设计，不能只是同一设计改多改少；把问题定清楚（这个设计要回答哪些问题、服务哪些场景）先于列方案。
- 给出推荐前做一次独立反驳：子 agent 只拿到问题和备选方案、看不到推荐，回答“问题是否问错、是否漏了不同的设计、推荐会在哪种场景下失败”；主 agent 处理完它的意见再给结论。小改动（单个模块内、不改接口）可以跳过，但要说明为什么跳过。
- 去掉对 sequential thinking 的引用，改为按维度逐个写出推理。

## 后果

- 设计类问题多一次子 agent 调用，几万 token；只在设计推荐时发生。
- 这条决定能不能防住同类失误，要看 C-34 的统计和以后抽读的对话；2027-02-03 和其他 skill 一起复查。
