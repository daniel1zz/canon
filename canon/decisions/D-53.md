## 背景

D-16 定下 main 守卫（`reference-transaction` hook）只拒绝：在 `prepared` 状态非 0 退出，让 git 中止 ref 更新，拒绝提示只指向 `canon work land`。#103 发现只拒绝不够：`git pull`、`git merge --ff-only`、`git reset --hard <提交>` 先把暂存区和工作区改成目标提交，最后才更新 ref；ref 更新被中止后 git 不会把暂存区和工作区改回来。main 没动，远端带来的文件全部留在暂存区，下一次提交会把它们当成新提交记下，`canon sync` 也因为 main 有未提交的改动拒绝（BR-2262 的 `main-dirty`）。

C-245、C-246 为此让守卫在拒绝后，checkout 签出的是 main 且被拒绝的是已有提交（别的 ref 包含它、是 `FETCH_HEAD`，或是 `git pull` 刚造的合并提交）时，用 `git read-tree -m -u <新> <main>` 把暂存区和工作区切回 main（BR-2284），并提示用 `canon sync`（BR-2286）。这已经超出了 D-16 的“只拒绝”。C-245 合入时的规则评审要求用一个修订 D-16 的决策把这件事写下来。2026-11-04 负责人选了“提示一行，并补一个修订 D-16 的决策 (推荐)”，C-268 照此补了这个决策，还为 `git pull --rebase` 停在 rebase 中间加了一行按后端区分的提示（BR-2298）。同一天的设计评审后，负责人确认“只拒绝 + 放回快进 + 一行提示 (推荐)”：按 D-54 以真实使用中的频率衡量，rebase 那一类没有在真实使用中出现过（本仓库只有一个 clone、`sync.*` 事件 0 条，#114 是测试时构造出来的），按后端区分的提示删掉（C-280）。

`git pull --rebase` 和快进不同：main 和远端各自前移过时，git 在分离的 HEAD 上把本地提交接到远端提交后面，最后移动 main 时被拒绝，于是停在 rebase 中间（本机 git 2.50.1 实测，见 C-268）。HEAD 是分离的，守卫按 BR-2284 不动暂存区和工作区。

## 方案

1. 只拒绝，加一行提示（D-16 原样，再加 `canon sync` 那一行）：否决。拒绝时命令已经把远端的提交写进了暂存区和工作区，提示改不了这个事实；要用户自己清理，而最顺手的 `git reset --hard` 会连用户自己没提交的改动一起丢掉。守卫没法在检出之前拦：git 没有在快进检出之前运行的 hook，它只能在 ref 更新时看到这件事。
   - 来源：canon/changes/C-245.md “git 没有在快进检出之前运行的 hook”
   - 来源：https://git-scm.com/docs/githooks “This hook is invoked by any Git command that performs reference updates.”
2. 拒绝之后用两路 `git read-tree -m -u <新> <main>` 把暂存区和工作区改回 main，只对已有提交和 `git pull` 造的合并提交这样做（BR-2284）：采用。两路切换只替换和旧树一致的条目，没提交的改动原样保留；切不过去时整个失败、什么也不写，守卫照实报出来。新提交是用户自己刚造的（`git commit`、`git merge --no-ff`）时暂存区里是用户的工作，不动。
   - 来源：https://git-scm.com/docs/git-read-tree “command makes sure that no local change is lost as the result of this”
   - 来源：canon/rules/cli/install/BR-2284.md “没提交的改动（已暂存的和没暂存的）原样保留”
3. 拒绝之后用 `git reset --hard <main>` 改回：否决。它会丢掉用户没提交的改动，而这些改动和被拒绝的命令无关。
   - 来源：canon/changes/C-245.md “`git reset --hard` 在 ref 更新之前已经丢掉了没提交的改动”
4. `git pull --rebase` 停在 rebase 中间时按后端分别提示怎么恢复（merge 后端 `git rebase --abort`，apply 后端 `git rebase --quit` 再 `git checkout main`，C-268 的 BR-2298 和 #114）：否决。这种情况没有在真实使用中出现过；每多一个后端就多一种情况，清单列不全，而且依赖 git 内部留下的状态文件（D-54）。
   - 来源：canon/decisions/D-54.md “需要不正常的配置或动作才会出现的情形记成已知限制”
5. 在 rebase 开始之前就用 `pre-rebase` hook 拒绝：现在否决，留作以后的办法。它在两个后端下都能让 git 在改动任何东西之前停下（设计评审实测），只有几行；真的出现 rebase 停在中间的情况时再加。
   - 来源：https://git-scm.com/docs/githooks “can be used to prevent a branch from getting rebased”

## 决定

修订 D-16 的“决定”和“后果”：守卫仍然只在 `prepared` 状态拒绝让 main 指向新提交的更新（BR-2126 不变），但拒绝不再是它唯一做的事。拒绝之后：

- checkout 签出 main、被拒绝的是已有提交或 `git pull` 造的合并提交时，把暂存区和工作区改回 main，保留没提交的改动（BR-2284）；
- 新提交来自远端时提示一行用 `canon sync`（BR-2286）。

除此之外不按命令或后端分情况恢复。

D-16“后果”里“hook 的拒绝提示不写绕过办法，只指向 `canon work land`”改为：提示不写绕过守卫的办法；远端的 main 指向受支持的 `canon sync`，自己的工作仍指向 `canon work land`。

## 后果

- 守卫不再是纯粹的“拒绝”：它在拒绝后会改 checkout 的暂存区和工作区。依赖的是 git 在更新 ref 之前已经写完并解锁 index（git 2.50.1 实测，C-245）；git 改了这个顺序时，`read-tree` 会因 index 锁失败，守卫照实报 `could not put the index and working tree back`，不会悄悄改错。
- 守卫脚本每改一次，已装的守卫按 BR-2085 显示为过期，要 `canon update` 或 `canon install`。
- 已知限制：`git pull --rebase` 被拒绝时停在 rebase 中间，守卫不提示怎么恢复；真的发生时，改用 `pre-rebase` hook 在 rebase 开始之前就拒绝。
- 它仍然挡的是失误和抄近路，不是安全边界（D-16 不变）。
