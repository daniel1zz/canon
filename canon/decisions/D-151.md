## 背景

负责人 2026-11-20：主 agent 平时要处理两类事，一是可以派给 worker 的活，二是需要它判断或决定的事，两类都要在合适的时机提醒；不要定时重复，按事件提醒，watch 保留（「硬件资源是动态的」）；总览要看当前状态，当前版本最关键，历史只给大纲；底层要求所有状态有正确的流转、能直接用脚本算出来，依赖也一样；允许不兼容的改动。

zhushenkongjian 和 canon 的实测（2026-11-20）：

- 状态分散在 7 处各算各的：`src/knowledge/documents/backlog.ts`（待办标记）、`src/knowledge/changes/deps.ts`（依赖）、`src/work/delegation/stall.ts`（停滞）、`src/work/reminders/due.ts`（待办）、`src/work/overview/overview.ts`、`src/knowledge/plans/status.ts`、`src/knowledge/releases/status.ts`。
- 只写在文字里、算不出来的状态：`C-343` 的代码和规则已在 main（42c1f369），只差关闭记录，交接文字里写着，它却排在待办第一；`C-406` 的交接是「等负责人恢复招降」、`C-1047` 的交接是「做完了等主会话合入」，两者都只是文字；`C-671` 只在分支上建过、2026-11-16 已放弃（事件表 `drop.done`），派发记录还在，`closedOnMainReader` 只看 main 上的变更文件，所以它在总览和 `canon work due` 里一直显示停滞。
- 处理过的提醒没有地方记结论：评审意见 #1016–#1019 正由 `C-1053` 处理（标题写着），`canon work due` 仍建议对它们 `canon finding close`。D-139 要主 agent「写下理由」，现在只能写在对话里。
- 等负责人：56 个问题里 19 个没关联变更，回答了也算不出放开了哪项工作。
- 「可开始」不等于「可派」：只有标题、设计没发布到 main 的变更，`canon work delegate` 会拒绝。
- 成功标准算错：BR-2504 把不缩进的列表项都算成标准，`R-2` 到 `R-5` 共至少 8 条说明文字（「验收方式……」「本版由开发会话自己验收……」）被算成「未证明」。
- 总览 164 行，约 86 行是「最近 7 天的目标改动」的全文；`canon work due` 25 行，23 条评审意见全文平铺，没有先后。
- 机器有空时没有任何地方建议派活：负载 19.3、8 核时 `C-1056`、`C-1057`、`C-1061`、`C-1063` 都可开始，没有提醒。
- watch 每 30 分钟把没处理的待办重复一遍（BR-2528 第 4 条）；D-136 当初把拦截改成提醒，理由之一就是「到时间会重复」。

独立挑战（只读子 agent，看了问题和三个方案、没看推荐）指出：每个变更只有一个状态会丢信息（`C-1047` 同时有交接和认领；依赖没满足也能开工）；方案 1 要补上提醒的处理结论和几处写入，否则在 `C-343`、`C-406`、`C-671` 上都会算错；两个会话同时看到「可派」会重复派发（`delegate.ts` 只在 worker 接手后才报冲突）；worker 自己合入时，合入输出只给了 worker；负载下降不产生事件；watch 启动时一次输出全部待办太长；去掉重复要改 D-136。这些都已收进下面的决定。

## 方案

1. 读的时候在一处现算：一个模块从变更文件（main 和在途分支）、协调事件和机器容量算出每个变更的主状态加附加标记，再从这些事实算出议程（可派的活、要判断的事、等负责人的事）；所有命令只读它。算不出来的状态补成命令写入的事实；主 agent 对一条提醒的处理结论记成事件；按事件提醒，watch 保留但不定时重复：采用。单一来源（D-148），和文件、事件同时更新，不会和它们对不上。
   - 来源：canon/product.md “由主 agent 判断怎么处理并写下理由”
   - 来源：canon/product.md “新会话不需要人重新交代，就能接着做没完成的工作”
2. 各命令照旧自己算，只给 `canon work due` 加「可派」、压缩输出和总览：否决。改动小，但 7 处各算各的问题还在，`C-671` 这种一处知道、一处不知道的错误会继续出现；也给不出处理结论的位置。
   - 来源：src/work/delegation/stall.ts “a change closed on main is finished whatever its delegation record says”
3. 把每个变更的状态存成协调数据库的一列，由命令在关键节点更新：否决。很多变化不经过命令（认领到期、worker 进程退出、长时间没提交、有人手动合进 main、分支被删），这一列会过时；依赖方的状态要靠被依赖方合入时去改，而依赖可能只写在依赖方的分支上；而且是变更文件之外的第二份状态，D-148 已否决这种做法。
   - 来源：canon/decisions/D-148.md “核心还是在于，单一数据源，以及在关键节点更新数据”
4. 保留 watch 每 30 分钟的重复提醒：否决。负责人要按事件提醒、不要定时重复；D-136 靠重复防止意见越积越多，这里换成：每个相关事件之后重算议程并输出变化，处理结论记成事件后不再提醒，没处理的在 brief、合入后和开工时的摘要里出现。
   - 来源：canon/decisions/D-136.md “每条带着已经开了多久，并且到时间会重复”

## 决定

采用方案 1，修改 D-136（去掉定时重复）和 D-129、D-131（总览的内容）。允许不兼容：输出格式（含 `--json`）按新模型重写，旧数据由迁移命令改写，不长期保留兼容读取。

**一、状态（knowledge/changes）**

1. 每个变更有一个主状态，按固定的先后次序判定，再加附加标记；议程读这些事实本身，不只读主状态。主状态至少区分：已合入、已放弃、代码已在 main 待关闭、在合入队列、合入被拒、进行中（有生效认领）、已派出、停滞、交接（附交接原因）、在等负责人、在等依赖、可开始；可开始里再分「可派」（设计已在 main，满足 `canon work delegate` 的条件）和「只能自己做」。附加标记包括：有交接、依赖未满足、有等负责人的问题、范围可能和别的变更重叠（D-148 第 D 步）。
2. 只用命令写下的事实：变更文件（main 和在途分支）、协调事件、git 提交；不解析交接、备注和正文文字。下面这些现在只在文字里，改成命令写入：
   - 放弃变更（包括只在分支上的）同时结束它的派发；状态计算也读 `drop.done`。
   - 代码已经在 main、变更没关：一个关闭命令写下由哪个提交完成，变更关闭；在那之前「main 上 open、没分支、没认领、它列的规则已生效」归为要判断的事，不算可开始。
   - 交接写一个固定的原因：等合入、等设计、等负责人（带问题编号或成功标准）、等依赖、做了一部分；文字说明照旧可以附上。
   - 等负责人只来自带变更编号的问题（`canon human ask --change`），或依赖一条待负责人的成功标准（D-149）。
3. `canon change list --json` 给出每个变更的主状态、附加标记和在等什么，脚本据此即可算出全部依赖和状态。

**二、版本和模块的进度（knowledge/releases，原 C-626 的 C 步）**

4. 成功标准只认带编号 `S<k>` 的列表项，说明文字不算标准（不兼容：迁移命令给现有标准编号，把说明移出列表）。完成只看规则状态和成功标准；关联变更只当工作量显示；按版本或模块现算变更的依赖图；发布不再要求计划完成。

**三、议程和提醒（work/reminders）**

5. 议程分三组，都从第一部分的事实和机器容量算出：
   - 可派的活：机器有空（同 BR-2526 的内存、负载和名额条件，负载判断带回差）时，列出可派的变更，按负责人的待办顺序（`canon/backlog.md`），最多 5 个，并写还能派几个；机器忙时写「忙，降下来后可派：……」。
   - 要判断的事：先是影响 main 正确的（main 测试失败、矛盾类意见），再是挡住别人的（停滞的派发、依赖指向没写由谁接手的放弃变更、代码已在 main 待关闭），最后是其余的，按已开时长；同一类多条合成一行，写条数和最老的时长。
   - 等负责人的事：单独一组，提醒主 agent 去问负责人，不算它要判断的事。
6. 处理结论：主 agent 对一条提醒写下「交给 C-n」「推迟，原因」或「不处理，原因」，记成事件；交给的变更合入、或推迟到期前，这条不再提醒。开工时 `--settles` 写下的同样算交给了这个变更。结论和后来的结果一起让 `canon stats` 算出提醒的准确率（P6）。
7. 时机，都只提醒、不拦：
   - `canon brief`（会话开始）：三组摘要。
   - 合入之后（不论谁合入）：三组摘要，和刚合入的变更有关的新意见单独列出。
   - `canon work start`：只列和这个变更有关的意见（点名它的规则或改到的路径），其余合成一行。
   - `canon work watch`：保留；每个相关事件之后重算议程，只输出变化；每秒读一次机器容量，只在越过阈值的那一刻输出一行（带回差）；不再每 30 分钟重复；启动时输出各组的条数和最前面几条，不再一次输出全部。worker 自己合入后，主会话靠它看到「C-n 合入，C-m 因此可开始」。
   - 议程为空时这些地方都不输出。
8. 两个会话同时派同一个变更：已有生效派发、派发人是别的会话、又没有停滞时，`canon work delegate` 按冲突拒绝（退出码 5）。这是并发安全（P4），属于完整性检查。

**四、总览（work/overview）**

9. `canon overview` 只给当前状态：最上面是当前版本（一行状态、一行规则计数、一行成功标准计数，每条标准一行只留第一句；并入的版本只给一行汇总；质量标准一行）；然后是议程的三组（可派、要判断、等负责人）和正在做、在等的变更，每个变更一行：编号、标题、状态或在等谁；历史只给大纲：最近 7 天按版本数目标改动的次数、最近合入的几个标题，细节用单独的命令查。计划一节去掉（D-148）。

**实现**：C-631 实现第一部分；`C-629`（原 C-626 的 C 步）实现第二部分；C-632 实现第三、四部分，依赖 C-631 和 `C-629`。每个变更开工时先写自己的规则（canon-rules），本决定只定方向。

## 后果

- 状态和提醒只在一处算，换来的是要先补齐几处写入（关闭命令、交接原因、放弃结束派发），旧项目要跑一次迁移命令；zhushenkongjian 的 `C-343`、`C-406`、`C-671` 和成功标准都会在迁移时改成新格式。
- 去掉定时重复后，没处理的事不会自己再响；它们在 brief、合入后、开工时的摘要里出现，watch 只报变化。如果实测发现意见又越积越多（D-126 担心的情况），由 `canon stats` 的提醒准确率和未处理时长看出来，再定是否加别的提醒。
- 没有 Monitor 的宿主（Codex）只能在下一次运行命令时看到变化，这是已知限制。
- 派发冲突改成拒绝，是新增的一项拒绝；它属于并发安全，不违反 D-139。
