## 背景

canon-design 规定设计“以决策和规则收尾，不写单独的设计文档”，理由是 P5 文档不说谎：只有规则有测试、决策有来源核对，设计文档没有人核对，会过期。结果是没有一处回答“系统现在长什么样”：

- 新会话要读决策：本仓库 64 条决策共约 422 KB，其中 5 条已被取代，每条讲的是当时为什么选，不讲现在的全貌；读不完，读了一部分又分不清哪些还有效。
- 或者逐个读领域 README：27 个 README 共约 36 KB，每个只讲本领域；只有 `work/hooks`、`knowledge/releases` 两个有行首的“依赖”一行，`install` 在正文里写了依赖，其余没有。要知道“数据存在哪、合入时先后经过哪些部件”，得把十几个领域拼起来。
- 已有的手写导览也在过期，没有任何检查盯着：`work` 的 README 列了 9 个子领域，实际有 13 个（缺 `work/execution`、`work/hooks`、`work/remote`、`work/snapshots`）；`knowledge` 的 README 列了 4 个，实际有 5 个（缺 `knowledge/releases`）。这两份清单和 `canon rule domains` 的输出重复，C-361 刚补过一次；同一件事写在两处，就是它们过期的原因。

负责人同意的方向：加一份手写的架构总览，作为 canon 的标准做法；只写 C4 的上下文和容器两层（C4 的容器是运行时部件，不是代码模块），每段指向决策和领域；`canon init` 给模板；canon-design 的 architecture 模式在改动部件或主要流程时同步更新；规则评审也读它。

要先弄清的现状（本次核对，2026-11-05）：

- `canon/product.md` 由 `canon init` 写一次，之后 canon 不碰（D-10、BR-2032）；模板只有四个标题，没有占位行；`canon check` 不读它里面的路径（BR-2171 读规则、领域 README、已接受的决策、open 的变更和根目录的 `CLAUDE.md`、`README.md`）；规则评审也不读它。它的内容是负责人定的目的和承诺，变得很慢。
- 合入时的规则评审只看 `canon/rules`、`canon/decisions`、`canon/releases` 下改动的文件，加上配置里 `instructions` 列的常驻说明（`src/work/land/checks/steps.ts`）。
- `src/` 的顶层目录和领域已经一一对应，由 `code-layout` 检查（BR-2118）；这一对应不需要读源码。
- 每个会话固定加载的文字有字节预算（BR-2257）：预算 12000 字节，现在 11975，只剩 25 字节，不能把总览放进去；加任何一句都要同时删掉别处的字。
- `canon init` 只写一次，`canon update` 只更新 skill、hook、git 守卫（BR-2084、BR-2086）：已装 canon 的项目不会因为新增了标准文件而得到它，也没有提示。
- 已装 canon 的项目在 `canon brief`、`canon work start`、`canon update --check` 里已经有“装的东西过期时提示一行”的通道（BR-2084、BR-2085）。

## 方案

1. **A 手写总览，文件 `canon/architecture.md`（采用）**：一个独立文件，不是 `canon/product.md` 里的一节。
   - 写哪几层：只写上下文（使用者和外部系统）和容器（运行时部件：职责、数据、代码目录），再加主要流程；不写组件层和代码层，那是领域 README 和 `canon context` 的事。只写现在的样子，不写历史；每段末尾列相关决策编号，要知道为什么看决策。
   - 一件事只写一处（分工）：总览只写“哪个部件、数据在哪、谁调谁”。步骤的先后和每个行为的要求（例如合入检查的顺序）写在规则里，总览指向规则，不逐个列；领域清单是 `canon rule domains` 的输出，总览不抄领域的职责描述，只用容器把领域的代码目录组织起来。样稿把“canon 做的部件”和“本项目配的东西”（`dist/canon`、`after_green`、`scripts/code-review.ts`、`scripts/review-claude.sh` 属于本仓库的 `canon/config.yaml`）分成两节，别的项目照着写自己的配置。
   - 为什么不放进 `canon/product.md`：product.md 是负责人定的承诺，改它要问人；架构总览由 agent 随代码改，改动频率完全不同。product.md 写成“只写一次，之后不碰”，把一份天天要改的文档塞进去，会让两者的所有者和更新节奏打架。
   - 更新时机怎么保证，几档叠加：
     - A1 靠指引：canon-design 的 architecture 模式在“记录设计”一步加一条：改动了容器或主要流程，就在同一次变更里改 `canon/architecture.md`。便宜，但没有机制盯着，上面已经看到会漏。
     - A2 靠合入评审：规则评审把 `canon/architecture.md` 放进它读的上下文；本次合入改了规则或决策、而总览写的部件或流程因此不对时，提一条建议（不拦截，D-21）；改了总览本身时，总览和有效规则或已接受决策矛盾才拦截（沿用评审现有的拦截条件）。AI 判断，会漏，也要花一次评审的 token。触发点的限制：合入评审只在合入改了 `canon/rules`、`canon/decisions` 或 `canon/releases` 下的文件时才跑（BR-2074），一次只改代码的合入不触发评审，A2 对它没有作用。
     - A3 靠一条确定的检查 `architecture-unlisted`，按领域和子领域查，不只看顶层：每个领域目录 `canon/rules/<领域路径>`（任意深度，含 `work/land/batch` 这样的子领域）对应的代码目录（配了 `code_root` 时是 `<code_root>/<领域路径>`，BR-2118 已保证它存在；`shared` 的每一项也算），总览里都要有一个反引号片段，整段等于这个目录（`src/work/land` 不能靠写了 `src/work/land/batch` 蒙混过去）。新增领域目录的那次合入，总览没写出它的代码目录，就报 `architecture-unlisted` 并拒绝（只拦加进它的那一次，已有项目不追溯，沿用 BR-2150 的做法）；已经存在、总览没写的，`canon check` 提示一行（提示，不算发现，D-37），所以背景里“子领域漏列”这类现成的过时也看得见。再把 `canon/architecture.md` 加进 BR-2171 读的文档：写了的路径被移走或删除就报 `path-missing`。没有 `code_root` 时 A3 不起作用。只用领域名和代码目录，不读源码，和 D-64（canon 不认语言）不冲突。
     - A4 `architecture-superseded`：总览里引用的决策编号，状态是 `superseded` 时，`canon check` 报一条发现，写明总览和决策编号。`canon decision accept` 把被指向的决策设为 `superseded`，如果这次接受和总览在同一棵树上，合入时就被这条拦住。
     - A5 `architecture-unreviewed`：一次合入新增了决策、或给决策加了 `supersedes`、`amends`，而它指向的是总览引用过的决策时，同一次合入要改 `canon/architecture.md`，或者在变更文件里写一行“总览不受影响：<原因>”，否则拒绝。A4 管“已经被取代”，A5 管“被修订”（`amends` 不改被指向决策的状态，A4 看不见）和“取代它的决策还是 proposed、还没 accept”。
   - 启用条件：总览除标题外有内容时，A2 到 A5 才起作用；`canon init` 和 `canon update` 写出的模板只有标题，没有占位行，不会卡住新项目的第一次合入，也不会卡住已装 canon 的项目。
   - 各档能抓住什么、漏什么：A3 抓“新增领域没写进总览”和已有的漏列（提示）；A4、A5 抓“总览引用的决策已经被取代或修订”；A1、A2 才碰得到流程和职责的文字。仍然漏的有：（1）没写决策、也没改规则的纯代码改动，例如把一个部件拆成两个，或者换了数据存放的位置：没有机器触发点，只靠 A1 的指引；（2）总览引用的决策没变、但它写的职责本身过期了；（3）A3 只管目录有没有出现，不管它挂在哪个容器下是否合适。
   - 与 P5 的关系：总览里的路径、领域覆盖、引用的决策有机器核对（A3 到 A5），职责和流程的文字只有评审的建议（A2），所以不能说“和规则一样可证明”。总览是读者的入口，不是判定依据：规则和决策矛盾时以规则为准，总览要改。
   - 过时风险：中。成本：写一份约 100 行的文件（本变更已给出 canon 自己的样稿）；每次改容器或流程时多改几行；A3、A4、A5 三条检查（规则、实现、测试、`check_reviews` 复审日期）。
   - 来源：https://c4model.com/abstractions/container “runtime boundary around some code that is being executed or some data that is being stored”
   - 来源：canon/product.md “新会话不需要人重新交代，就能接着做没完成的工作”
2. **A' 总览写成 `canon/product.md` 里的一节**：否决。省一个文件，但上面说的所有者和节奏冲突没解决；`canon check`、评审都不读 product.md，要为它们特批；`canon init` 写 product.md 后不再碰（D-10），已经装了 canon 的项目拿不到新的一节。
   - 来源：canon/decisions/D-10.md “`canon init` 写一次，之后不碰”
3. **B 补齐每个领域 README 的依赖，再由 `canon rule domains` 拼出图**：否决。过时风险低（依赖写在领域旁边，改领域时顺手改），也能画图，但是：依赖要么手写（和现在的 README 导览一样没人盯着，只是换了地方），要么从 import 读出来；读 import 是 JS/TS 的做法，和 D-64“canon 不认任何语言”冲突。而且领域是业务能力的划分（D-63），不是运行时部件：state.db、后台 floor watch、git 守卫、`claude -p` 评审这些部件不是任何一个领域，数据存在哪也看不出来，图拼出来仍回答不了新会话的问题。成本：其余 README 补依赖，加一个拼图命令。
   - 来源：canon/decisions/D-64.md “canon 不要有针对特定语言的处理”
4. **C 不做**：否决。成本为零，过时风险也为零，但是新会话继续读 422 KB 的决策历史或逐个拼 README，P3（新会话接着做）靠它的代价一直在付；README 导览已经漏了 5 个子领域，说明不做不会让它自己变准。
   - 来源：canon/product.md “main 上的文档和代码一致，没有断掉的引用”
5. **D 总览的一部分从已有的结构化信息生成，手写只补流程**：否决，只借用它的分工。取舍：生成的部分（领域和代码目录的对应、领域清单）永远和 `canon rule domains` 一致，不会过期；但（1）这部分信息 `canon rule domains` 已经能输出，生成进文件只是换个位置再存一份；（2）总览的价值在“容器 ↔ 领域”的组织（state.db、floor watch、git 守卫不是任何领域），这是手写的判断，生成不出来，生成的只是目录列表；（3）在手写的 Markdown 里嵌生成段，要标记、要一个命令刷新、还要检查“生成段是不是最新”，为同一个目标多一套机制，而 A3 已经用一条确定的检查保证每个目录都出现。
   - 来源：canon/decisions/D-63.md “后者是一项业务能力（把 canon 装进项目）”

## 决定

采用 A：新增手写的 `canon/architecture.md`，只写上下文和容器两层加主要流程，每段末尾列决策编号；更新靠 A1 到 A5 叠加（限制见 A2 和“各档能抓住什么、漏什么”）。这是 canon 项目的标准做法，不只是 canon 自己的文件。不采用 D，只借用它的分工：总览不抄 `canon rule domains` 能给出的东西。

- 位置：`canon/architecture.md`，和 `canon/product.md` 并列。
- A1 到 A5：见方案 A。
- 分工：一件事只写一处。总览只写部件、数据、谁调谁，步骤细节指向规则。父领域 README 不再手写子领域清单，改为一句“子领域见 `canon rule domains`”，第一段里与总览重复的“合入流程”“协调数据库”描述收短并指向总览。本次变更先改 `canon/rules/work/README.md` 和 `canon/rules/knowledge/README.md`；`work/land` 等其他手写了子领域清单的父领域 README，在本决策 accept 之后的实现变更里照此办理。
- 已装 canon 的项目怎么拿到：不用 `canon check`（会追溯拒绝所有已装项目的合入，和“不是必需文件”矛盾），也不靠 `canon init`（只写一次）。在 BR-2084 的“过期”里加一项：项目里没有 `canon/architecture.md`。`canon brief`、`canon work start`、`canon update --check` 本来就按 BR-2084 当场计算、有过期项就提示一行（BR-2085），每个会话开始都会跑 `canon brief`，所以每个新会话都看得到；`canon update` 把缺的模板（只有标题）作为一个变更写进去合入（BR-2086），已有的文件从不覆盖，也不碰里面的内容。这是对 D-10 的补充：`canon/architecture.md` 属于“只补缺的、不碰已有的”一类，放在 D-10 的第三类旁边。选它而不是在 `canon brief` 里单加一行：这个通道已经有提示、更新命令和测试，只加一项，不另起一套。没有退出方式：模板写进去后提示就消失，写不写内容由项目决定。
- 模板和启用：`canon init` 同样建只有标题的 `canon/architecture.md`。总览除标题外没有内容时，A2 到 A5 不起作用，所以它不是必需文件，已有项目不被追溯拒绝。
