title: 架构总览：手写 canon/architecture.md，只写上下文和容器两层

---

## 背景

canon-design 规定设计“以决策和规则收尾，不写单独的设计文档”，理由是 P5 文档不说谎：只有规则有测试、决策有来源核对，设计文档没有人核对，会过期。结果是没有一处回答“系统现在长什么样”：

- 新会话要读决策：本仓库 64 条决策共约 422 KB，其中 5 条已被取代，每条讲的是当时为什么选，不讲现在的全貌；读不完，读了一部分又分不清哪些还有效。
- 或者逐个读领域 README：27 个 README 共约 36 KB，每个只讲本领域；只有 `work/hooks`、`knowledge/releases` 两个有行首的“依赖”一行，`install` 在正文里写了依赖，其余没有。要知道“数据存在哪、合入时先后经过哪些部件”，得把十几个领域拼起来。
- 已有的手写导览也在过期，没有任何检查盯着：`work` 的 README 列了 9 个子领域，实际有 13 个（缺 `work/execution`、`work/hooks`、`work/remote`、`work/snapshots`）；`knowledge` 的 README 列了 4 个，实际有 5 个（缺 `knowledge/releases`）。

负责人同意的方向：加一份手写的架构总览，作为 canon 的标准做法；只写 C4 的上下文和容器两层（C4 的容器是运行时部件，不是代码模块），每段指向决策和领域；`canon init` 给模板；canon-design 的 architecture 模式在改动部件或主要流程时同步更新；规则评审也读它。

要先弄清的现状（本次核对，2026-11-05）：

- `canon/product.md` 由 `canon init` 写一次，之后 canon 不碰（D-10、BR-2032）；模板只有四个标题，没有占位行；`canon check` 不读它里面的路径（BR-2171 读规则、领域 README、已接受的决策、open 的变更和根目录的 `CLAUDE.md`、`README.md`）；规则评审也不读它。它的内容是负责人定的目的和承诺，变得很慢。
- 合入时的规则评审只看 `canon/rules`、`canon/decisions`、`canon/releases` 下改动的文件，加上配置里 `instructions` 列的常驻说明（`src/work/land/checks/steps.ts`）。
- `src/` 的顶层目录和领域已经一一对应，由 `code-layout` 检查（BR-2118）；这一对应不需要读源码。
- 每个会话固定加载的文字有字节预算（BR-2257），已经接近上限，不能把总览放进去。

## 方案

1. **A 手写总览，文件 `canon/architecture.md`（采用）**：一个独立文件，不是 `canon/product.md` 里的一节。
   - 写哪几层：只写上下文（使用者和外部系统）和容器（运行时部件：职责、数据、对应领域和代码目录），再加主要流程；不写组件层和代码层，那是领域 README 和 `canon context` 的事。只写现在的样子，不写历史；每段末尾列相关决策编号，要知道为什么看决策。
   - 为什么不放进 `canon/product.md`：product.md 是负责人定的承诺，改它要问人；架构总览由 agent 随代码改，改动频率完全不同。product.md 写成“只写一次，之后不碰”，把一份天天要改的文档塞进去，会让两者的所有者和更新节奏打架。
   - 更新时机怎么保证，三档，可以叠加：
     - A1 靠指引：canon-design 的 architecture 模式在“记录设计”一步加一条：改动了容器或主要流程，就在同一次变更里改 `canon/architecture.md`。便宜，但和 README 导览一样，没有机制盯着，上面已经看到会漏。
     - A2 靠合入评审：规则评审把 `canon/architecture.md` 放进它读的上下文；本次合入改了规则或决策、而总览写的部件或流程因此不对时，提一条建议（不拦截，D-21）；改了总览本身时，总览和有效规则或已接受决策矛盾才拦截（沿用评审现有的拦截条件）。能发现流程描述的过时，但是 AI 判断，会漏，也要花一次评审的 token。
     - A3 靠一条确定的检查：新增或删除顶层领域（或 `shared` 的一项）的那次合入，`canon/architecture.md` 里必须用反引号写出它的代码目录，否则 `canon check` 报一个新的发现；只拦加进它的那一次合入，已有的项目不会被追溯拒绝（沿用 BR-2150 的做法）。再把 `canon/architecture.md` 加进 BR-2171 读的文档：写了的路径被移走或删除就报 `path-missing`。这一条只用领域名和代码目录，不读源码，和 D-64（canon 不认语言）不冲突。查不出来的是流程步骤写得对不对。
   - 与 P5 的关系：总览里的路径和顶层领域有机器核对（A3），流程和职责的文字只有评审的建议（A2），所以不能说“和规则一样可证明”。总览是读者的入口，不是判定依据：规则和决策矛盾时以规则为准，总览要改。这是已知限制：流程文字过期不会被机器发现，只靠 A1 和 A2 降低。
   - 过时风险：中。成本：写一份约 100 到 150 行的文件（本变更已给出 canon 自己的样稿）；每次改容器或流程时多改几行；A3 要加一条检查（规则、实现、测试、`check_reviews` 复审日期）。
   - 来源：https://c4model.com/abstractions/container “runtime boundary around some code that is being executed or some data that is being stored”
   - 来源：canon/product.md “新会话不需要人重新交代，就能接着做没完成的工作”
2. **A' 总览写成 `canon/product.md` 里的一节**：否决。省一个文件，但上面说的所有者和节奏冲突没解决；`canon check`、评审都不读 product.md，要为它们特批；`canon init` 写 product.md 后不再碰（D-10），已经装了 canon 的项目拿不到新的一节。
   - 来源：canon/decisions/D-10.md “`canon init` 写一次，之后不碰”
3. **B 补齐每个领域 README 的依赖，再由 `canon rule domains` 拼出图**：否决。过时风险低（依赖写在领域旁边，改领域时顺手改），也能画图，但是：依赖要么手写（和现在的 README 导览一样没人盯着，只是换了地方），要么从 import 读出来；读 import 是 JS/TS 的做法，和 D-64“canon 不认任何语言”冲突。而且领域是业务能力的划分（D-63），不是运行时部件：state.db、后台 floor watch、git 守卫、`claude -p` 评审这些部件不是任何一个领域，数据存在哪也看不出来，图拼出来仍回答不了新会话的问题。成本：其余 README 补依赖，加一个拼图命令。
   - 来源：canon/decisions/D-64.md “canon 不要有针对特定语言的处理”
4. **C 不做**：否决。成本为零，过时风险也为零，但是新会话继续读 422 KB 的决策历史或逐个拼 README，P3（新会话接着做）靠它的代价一直在付；README 导览已经漏了 5 个子领域，说明不做不会让它自己变准。
   - 来源：canon/product.md “main 上的文档和代码一致，没有断掉的引用”

## 决定

采用 A：新增手写的 `canon/architecture.md`，只写上下文和容器两层加主要流程，每段末尾列决策编号；更新靠 A1、A2、A3 三者叠加。这是 canon 项目的标准做法，不只是 canon 自己的文件。

- 位置：`canon/architecture.md`，和 `canon/product.md` 并列。
- A1：canon-design 的 architecture 模式在“记录设计”里加一条更新要求。
- A2：规则评审读它，改动对不上时提建议，总览自己的改动和规则、决策矛盾时拦截。
- A3：一条新的检查（暂名 `architecture-unlisted`）：新增或删除顶层领域或 `shared` 项的合入，总览要写出对应代码目录；并让 BR-2171 读它。
- 不是必需文件：项目没有 `canon/architecture.md` 时这些检查和评审都不起作用，已有项目不被追溯拒绝；`canon init` 生成的模板只有标题，像 product.md 一样没有占位行，所以新项目第一次合入不会被它卡住。

## 后果

要改的东西（本决策 accept 之后的变更里做，本变更不改代码、skill 和模板）：

- 规则：
  - 在 `knowledge/check` 里改 BR-2171，把 `canon/architecture.md` 加进它读的文档；
  - 在 `knowledge/check` 里新增 `architecture-unlisted` 一条规则（加进它的那一次合入才拒绝，沿用 BR-2150 的写法），实现和测试照常，`canon/config.yaml` 的 `check_reviews` 加它的复审日期（BR-2069）；
  - 在 `knowledge/review` 里改规则评审的输入（BR-2009 一条）：总览放进上下文，不属于“改动的文件”，也不让只改了总览的合入变成要评审规则；
  - 在 `install` 里改 BR-2032：`canon init` 多建一个只有标题的 `canon/architecture.md`；
  - `knowledge/documents/README.md` 的文档类型清单、`src/knowledge/documents/model.ts` 头部注释加一行。
- `canon init` 模板：`src/install/commands.ts` 里 `canon/product.md` 旁边加一份，标题是“上下文”“容器”“主要流程”。像 product.md 一样 init 写一次，之后不碰（D-10）。
- canon-design：`.claude/skills/canon-design/SKILL.md` 第 4 节“记录设计”和 `references/mode-architecture.md` 第 4 阶段：把“不写单独的设计文档”改成“不为一次设计写单独的文档；项目的架构总览 `canon/architecture.md` 是现状，改了容器或主要流程要同一次变更里更新它”，并把 mode-architecture 里那份通用的 Architecture 文档模板改成指向它。
- `canon-domains` 读总览来看“容器 ↔ 领域”的对应；`canon-product` 不把它当输入（它的输入是要达成的结果和证据，不是现有结构）。
- `canon brief` 的工作说明加一行“先读 `canon/architecture.md`”会占固定加载的字节预算（`session_text_budget`，BR-2257），改的时候同一次变更里量一下，超出就去掉别处的重复，不上调预算。
- `floor_skip_paths`：`canon/architecture.md` 加进去（和 `canon/product.md` 一样，测试不读它）。
- 已知限制：流程和职责的文字写得对不对只有评审建议，机器查不出；新增子领域（`src/work/<新>`）不会触发 A3，靠 A1、A2。
- D-62、D-64 在实现中，本变更给出的样稿按当时的 main 写；它们落地后要同步更新样稿的这几段：
  - D-62（`src/install`、`src/work/claims`、`src/work/session`）：容器“主 checkout 与变更 worktree”的职责和领域行，流程“一个变更”的第 1 步，容器“装进项目的 hook、skill 和 git 守卫”如果有新的 hook 或安装物。
  - D-64（`src/knowledge/check`、`src/work/verify`、`canon/config.yaml`）：容器“`canon/` 文档树”里讲 `canon check` 的一句，流程第 3 步（`canon work test` 怎样挑测试、测试结果从哪来），以及上下文里“项目自己的命令”（测试报告成为 canon 读的输入）。
