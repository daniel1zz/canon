---
id: D-132
title: goal 驱动：会话用 canon goal start 主动开启目标模式，Stop hook 在目标没达成时让它接着做，连续没进展就放行
status: accepted
---

## 背景

负责人 2026-11-17 要“一个类似goal的机制可以让ai一直朝着目标完成”，问是否“要搭配Monitor或者什么来做”，并说它“应该是主动调用cli的方法才会执行”；关键是“能及时校准ai是否在朝争取的方向进行”（问题 #50）；定期问负责人“不需要”，“只需要适当提醒就行”。目标由 D-130（版本由模块组合）和 D-131（成功标准编号、变更声明推进哪条）给出，`canon overview` 能算出哪些成功标准还没满足。

Claude Code 和 Codex 都有 Stop hook：会话要结束这一轮时运行，hook 在标准输出写 `{"decision":"block","reason":"..."}`，会话就把 reason 当成下一条提示继续做；输入里有 `session_id` 和 `stop_hook_active`。

## 方案

1. `canon goal start` 由会话主动开启，按会话身份记在协调数据库；canon 装一个 Stop hook，只对开了目标的会话起作用：目标还有能做的成功标准就拦下并写明下一步和偏离提醒，达成、只剩负责人的事、或连续三次拦下之间没有任何进展时放行：采用。主动开启，符合负责人说的“主动调用cli”；提醒只给 AI 看，不问负责人；连续没进展就放行，防止会话被困在做不动的目标上空转。
   - 来源：https://learn.chatgpt.com/docs/hooks “You can also use exit code `2` and write the continuation reason to `stderr`.”
2. 用 Monitor 或 `/loop` 定时唤醒会话：否决。Monitor 等的是后台进程的输出，判断不了目标完成没有；`/loop` 要每个会话手动开、会话结束就没了，Codex 没有。
   - 来源：canon/product.md “新会话不需要人重新交代，就能接着做没完成的工作”
3. Stop hook 对所有会话都起作用，不需要开启：否决。负责人说驱动要主动调用才执行；在一个变更里修 bug 的会话会被拉去做目标。
   - 来源：canon/rules/work/session/BR-2024.md “canon brief”
4. 没有进展的判断交给模型（读最后一条回复判断是不是卡住了）：否决。每次停下多一次模型调用，结果也不能复现；提交和工作树有没有变是能直接核对的事实。
   - 来源：canon/product.md “每个检查都记录拒绝的原因，所以能算出它准不准”

5. 目标模式放进 `work/overview` 或 `work/session`，不单独建子领域：否决。`work/overview` 只读不写，只负责把进度摆出来；目标模式要存会话的状态、改变会话停下时的行为；`work/session` 管开工和交接，已有 36 条规则。所以新建子领域 `work/goal`，代码在 `src/work/goal`。
   - 来源：canon/rules/work/overview/README.md “这里只管选哪些、按什么顺序摆出来”

## 决定

开启、结束和查看按 BR-2518；停下时的判断和说明按 BR-2519；hook 装进 Claude Code 和 Codex 的项目设置按 BR-2520 和 BR-2459。

## 后果

- 开了目标的会话会一直做到目标达成或连续三次没有进展；这期间负责人看到的是它不停地合入变更。
- 最坏的情况：会话每次都改一点不相干的文件，算作“有进展”，一直不停。偏离提醒会写出最近合入的变更里有几个不推进目标，`canon overview` 也看得到；如果这种情况出现，再加上“几次合入都不推进目标就放行”。
- 数据：目标按会话身份存在本机的协调数据库，会话结束后留着不影响别人；`canon goal stop` 删掉它。换机器或换会话要重新开启。
- 能证明这个选择错了的结果：开了目标的会话里，`goal.start` 之后的合入大部分不推进目标（`canon overview` 的最近合入一节能数出来），或者会话频繁因为“连续三次没进展”被放行而目标没有推进；前者说明提醒不够，要加“几次合入都不推进目标就放行并提醒负责人”，后者说明三次的阈值或进展的判定不对。
- 两个宿主：Claude Code 的 hook 写在 `.claude/settings.json` 的 `hooks.Stop`，Codex 的写在 `.codex/hooks.json` 的 `Stop`，要在 Codex 的 `/hooks` 里 trust 才运行（BR-2459）。两端都从标准输入给 `session_id`，都认标准输出的 `{"decision":"block","reason":...}` 让会话把 reason 当下一条提示接着做，`{}` 或只有 `systemMessage` 时放行；Codex 要求 Stop hook 只输出 JSON，所以每条路径都输出一个对象。会话被用户打断时 Stop hook 不运行，目标模式不会拦住用户。
