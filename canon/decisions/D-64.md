## 背景

BR-2005 规定：规则要有一个会运行的测试在标题里点名它。标题只在 JS/TS 测试文件里读得出来（`src/knowledge/check/test-titles.ts` 的 `testTitles`，一个小词法器，D-12）。其他语言的测试文件（只能靠 `tests` 配置扫到）没有解析器，BR-2005 和 D-12 把它写成有意的退路：整个文件的文本当作一个会运行的标题。#127 来自一个 Godot/GDScript 项目，它证明这条退路让 `rule-untested` 失效：在测试文件末尾加一行 `# BR-1 is not tested here yet`，`canon check` 就从 `rule-untested` 变成 ok。

负责人的硬约束：canon 不要有针对特定语言的处理，包括 JS/TS。canon 只认一种语言中立的格式，由项目产出。这把问题从“给其他语言补解析”变成“把 JS/TS 解析也拿掉”。

标题解析现在被用在四处（都是 `JS_TS.test(file) ? testTitles(text) : 整个文本`）：

1. `src/knowledge/check/check.ts:162`：`rule-untested`（只有会运行的标题算），`ref-dangling` 和 `test-retired-rule`（所有标题都查，BR-2004、BR-2042）。
2. `src/work/execution/evidence.ts:172`（`touchedRules`）：合入时的执行证据（BR-2241）：改动的行要落在点名这条规则的测试调用里，所以要每个标题的 `start`、`end`。
3. `src/work/execution/evidence.ts:206`（`testedRules`）：第一次关闭变更时写迁移记录（BR-2245）。
4. `src/work/verify/verify.ts:263`：`canon work test` 的选择理由“测试名写了本变更碰过的规则”（BR-2157）。

canon 没有“按名字只跑一条测试”的用法：`test_command` 每次只收到文件路径（BR-2160）。

除了标题解析，canon 里还有这些只认 JS/TS 的地方（用 `JS_TS` 正则或 JS/TS 语法读源码），在语言中立的前提下都要处理：

- `src/knowledge/check/check.ts:348`（`findTestFiles`）、`src/knowledge/check/tests.ts:6` 和 BR-2046：没配 `tests` 时按 12 种 JS/TS 扩展名找测试文件。
- `src/work/verify/verify.ts:79`、`:93`、`:170`、`:180`、`:255`：按相对导入选测试（BR-2157、#113），读 CLI 命令注册表选测试（`src/work/verify/cli-tests.ts`，D-60），按源码里拼出的路径读数据文件选测试（`src/work/verify/data-reads.ts`，#117）。
- `src/knowledge/query/query.ts:203`（`importedPaths`）：BR-2119，`canon context <文件>` 的导入读法；选测试也用它。
- `src/knowledge/check/skip-reads.ts:18`、`:38`：`test-reads-skip-path` 只检查 JS/TS 测试（BR-2181）；它是 BR-2164（只改 `floor_skip_paths` 下文件的合入不跑 floor）的安全依据。
- `src/work/execution/evidence.ts:147`：`JS_TS` 用来分流上面的标题解析。

canon 对测试真正需要知道的只有：这个测试文件里有哪些测试、名字是什么、跑了没有（没被跳过）。这三样正是 JUnit XML 报告（`testcase` 的名字、`skipped`、`failure` 子元素）里已经有的，而且是测试框架自己说的，不是 canon 从源码推断的。

事实（本次核实，2026-11-05）：

- bun：官方文档给出参数：“To write a JUnit XML report, pass `--reporter=junit` together with `--reporter-outfile`.”本机实测（bun 1.4.4）：`bun test a.test.ts --reporter=junit --reporter-outfile=out.xml` 写出的报告里，`describe` 是嵌套的 `testsuite`（`name`、`file`、`line`），每个测试是 `testcase`（`name`、`classname` 为所属 `describe`、`file`、`line`）；`test.skip` 是带 `<skipped />` 的 `testcase`，`test.todo` 是带 `<skipped message="TODO" />` 的 `testcase`，`test.each` 每一组一个 `testcase`（名字是代入后的），失败的是带 `<failure>` 的 `testcase`；写在注释里的编号不产生 `testcase`；运行的退出码照常（有失败是 1）。
- bun 一次运行多个文件（本机实测，含 `--parallel=2`）：每个测试文件一个外层 `testsuite`，每个 `testcase` 都带 `file`（相对运行目录的路径，如 `sub/b.test.ts`）和 `line`（`it` 调用所在行，从 1 起；嵌套在 `describe` 里也是自己那一行）。节选：

  ```xml
  <testsuite name="BR-1" file="c.test.ts" line="2" tests="2" ...>
    <testcase name="first" classname="BR-1" time="0.000004" file="c.test.ts" line="3" assertions="0" />
    <testcase name="second" classname="BR-1" time="0.000004" file="c.test.ts" line="8" assertions="0" />
  ```

- pytest 8.4.2（本机实测，`pytest --junit-xml=out.xml`，一个有类、`skip`、参数化 id、运行时 `pytest.skip`、失败的测试文件）：默认的 `xunit2` 的 `testcase` 只有 `classname`（点分的模块路径加类名）、`name`、`time`，没有 `file`、`line`；`-o junit_family=xunit1`（官方文档称为“old style”）的 `testcase` 多了 `file`（相对 rootdir）和 `line`，而且 `line` 从 0 起、指向第一个装饰器（`def` 在第 10 行、装饰器在第 9 行的测试报 `line="8"`），和 bun 差一行。`pytest.mark.skip` 和运行时 `pytest.skip(...)` 都是带 `<skipped>` 的 `testcase`；参数化 id 进 `name`（`test_param[BR-5-one]`）；注释里的编号不出现；只有 `testsuite name="pytest"` 一个外层，不是每个文件一个。节选（xunit1）：

  ```xml
  <testcase classname="tools.tests.tmp_pytest_test.TestGroup" name="test_skipped" file="tools/tests/tmp_pytest_test.py" line="8" time="0.000"><skipped type="pytest.skip" message="disabled for the experiment">...</skipped></testcase>
  <testcase classname="tools.tests.tmp_pytest_test.TestGroup" name="test_param[BR-5-one]" file="tools/tests/tmp_pytest_test.py" line="12" time="0.000" />
  ```

  节选（xunit2，同一个测试）：`<testcase classname="tools.tests.tmp_pytest_test.TestGroup" name="test_skipped" time="0.001"><skipped type="pytest.skip" ...>`。
- 其他框架能不能输出 JUnit XML（官方文档）：go 本身不能，要 gotestsum（“`gotestsum` will write a test report, in JUnit XML format, to the file.”，`--junitfile`，`testcase` 没有 `file`）；vitest 能（“Outputs a report of the test results in JUnit XML format.”）；Godot 的 GUT 能（`-gjunit_xml_file`：“Export results of run to this file in the Junit XML format.”），但官方页面没写 pending 的测试在 XML 里怎么表示，本次没有 GUT 环境，没实测；jest 要第三方 reporter（`jest-junit`），没有查官方文档。
- gdUnit4（6.2.3，Godot，#127 的项目，在项目副本里实测，没动原目录；开关和写法读自 `addons/gdUnit4/bin/GdUnitCmdTool.gd` 和 `src/reporters/xml/JUnitXmlReportWriter.gd`，官方文档页查不到）：命令行 `GdUnitCmdTool.gd -a res://<测试文件> -rd <目录>`（项目的 `tools/run_test.sh` 已经这样调用）会在 `<目录>/report_<n>/results.xml` 写出 JUnit XML，没有“指定输出文件”的开关，所以要一个包装脚本把它拷到 `{report}`；报告在有失败时照常写出，进程退出码是 100。一个测试文件里四个测试（正常通过、`do_skip := true` 跳过、失败、函数体外有 `# BR-1 is not tested here yet` 注释）的报告原文（节选）：

  ```xml
  <testsuites id="2026-11-05" name="report_1" tests="4" failures="1" skipped="1" flaky="0" time="0.000">
  	<testsuite id="0" name="tmp_junit_test" package="tests/kernel" timestamp="2026-11-05T05:49:59" hostname="localhost" tests="4" failures="1" errors="0" skipped="1" flaky="0" time="0.027">
  		<testcase name="test_passes" classname="tmp_junit_test" time="0.001">
  		</testcase>
  		<testcase name="test_plain_passes" classname="tmp_junit_test" time="0.001">
  		</testcase>
  		<testcase name="test_BR_3_disabled" classname="tmp_junit_test" time="0.000">
  			<skipped message="SKIPPED: res://tests/kernel/tmp_junit_test.gd:14">
  ...
  		<testcase name="test_BR_4_fails" classname="tmp_junit_test" time="0.002">
  			<failure message="FAILED: res://tests/kernel/tmp_junit_test.gd:21" type="FAILURE">
  ```

  `testcase` 的 `name` 是函数名，`classname` 是文件名去掉扩展名，没有 `file`，没有 `line`（行号只在 `skipped`、`failure` 的 `message` 文字里）；跳过的测试是带 `<skipped>` 的 `testcase`；注释里的 `BR-1` 不出现。两个后果：一，项目现在用的 `it("BR-1: …")` 写法（`it` 是一个什么都不做的函数）不会进报告，编号要写进函数名；GDScript 的函数名里不能有连字符，只能写 `test_BR_3_…`，报告里就是 `BR_3`，canon 认的是 `BR-3`（`idsIn`），所以要转接脚本把报告里的 `BR_<数字>` 改成 `BR-<数字>`（只改 XML 文本，不读源码）。二，没有 `file`，测试只能一个文件一个文件地运行并记账，全量运行的报告用不上。一个文件的完整运行（含 Godot 启动）约 8 秒。
- 同一个 Godot 项目的 `tools/tests/check_provenance_test.py` 不是 pytest 测试：它用自己的 `it(title)` 登记函数、`python3 -I` 直接运行。对它运行 `pytest --junit-xml` 得到的是一份合法的空报告（`tests="0"`）。要么改成 pytest，要么让它自己写 JUnit XML（它已经有“标题加函数”的登记表，写 XML 是十几行）。canon 没法分辨“这个文件没有测试”和“框架没收集到测试”，只能靠 `rule-untested` 把后果大声说出来（见“决定”）。
- 协调数据库在 git 公共目录的 `canon/state.db`，同一个仓库的所有 worktree 共用（`src/work/db.ts`），已经记 `work.test` 事件。
- 现在 `canon work test` 一个测试文件运行一次 `test_command`（D-23），所以“这次运行对应哪个测试文件”是 canon 自己知道的，不用靠报告里的 `file`。

## 方案

每个方案先判断是否符合“不认任何语言”，再比较：能不能分清注释、字符串、跳过的测试；对已有项目（JS 项目和 Godot 项目）的影响；失败是否大声；性能；安全；要改的规则。

1. **JUnit XML 报告 + 按测试文件内容记账（采用）**：`test_command` 必须含 `{report}`，canon 在每次运行前给一个临时路径，项目的命令把 JUnit XML 写到那里；canon 读出每个 `testcase` 的名字（含 `classname` 和外层 `testsuite` 的名字）、状态和 `line`（有就读），按“测试文件路径 + 文件内容的 git blob 哈希”记进协调数据库的一张新表；`floor` 命令也可以写 `{report}`，一次全量运行按 `testcase` 的 `file` 记账。`rule-untested` 等检查读这张表。细节在“决定”。
   - 语言中立：是。canon 里没有任何一种语言的词法、语法或扩展名。
   - 分清注释、字符串、跳过：能，而且“会运行”是运行结果证明的，不是源码推断：注释里的编号不产生测试用例，`skipped` 子元素标明跳过，运行时才决定的条件跳过也如实反映，比 JS/TS 词法器对 `.if(…)` 一律当作不运行更准。项目不用写解析源码的脚本，因为报告是框架自己写的；但框架的测试名写不出 `BR-n` 时（gdUnit4 的函数名不能有连字符，实测见“事实”），项目要在名字能写的地方写（pytest 的参数 id 实测会进 `name`），或者写一个只改报告文本的转接脚本（把 `BR_3` 改成 `BR-3`，不读源码）；这是项目配置里看得见的一小段，不是语言解析。
   - 对已有项目：每个项目改一行配置（`test_command` 加报告参数）并让每个测试文件跑过一遍；没做之前大声失败（见“迁移和过渡”）。Godot 项目（gdUnit4）已经实测：报告能写出，但要一个转接脚本（拷出报告、改 `BR_n`）并把编号写进函数名（见“事实”）。
   - 失败是否大声：是。测试文件没有对应当前内容的报告、报告读不出来、`test_command` 不含 `{report}`，各有专门的发现或配置错误，都不退回宽松。
   - 性能：`canon check` 只查数据库，比现在的词法器还快；运行测试的开销本来就有（`canon work test` 已经每个文件跑一次），多的只是读一个 XML。
   - 安全：不新增（`test_command` 已经是项目命令）；报告是不可信输入，只读 `testcase` 的名字和状态，并限制大小。
   - 要改的规则：BR-2005、BR-2004、BR-2042、BR-2046、BR-2160、BR-2241、BR-2245、BR-2157，细节见“后果”。
   - 来源：https://bun.sh/docs/cli/test “To write a JUnit XML report, pass”
   - 来源：https://docs.pytest.org/en/stable/how-to/output.html “to create an XML file at”
   - 来源：https://docs.pytest.org/en/stable/reference/reference.html “produces old style output, compatible with the xunit 1.0 format”
   - 来源：https://github.com/gotestyourself/gotestsum “will write a test report, in JUnit XML format, to the file.”
   - 来源：https://gut.readthedocs.io/en/latest/Command-Line.html “Export results of run to this file in the Junit XML format.”
   - 来源：src/work/db.ts “"canon", "state.db"”
2. **项目配置一个“读标题命令”（`test_titles_command`，对每个测试文件输出 `[{title, runs, start, end}]`）**：否决为主方案，也不作现在的补充。它也是语言中立的，认真比较：
   - 语言中立：是（命令由项目写）。
   - 分清注释、字符串、跳过：只有命令写得好才能；写好就等于为该语言写一个解析器（Godot 项目要为 GDScript 的注释、字符串、跳过注解各写一遍），`grep func test_` 一类的脚本恰好分不清注释；每个项目、每种框架各写各的，质量没人检查。报告是框架作者写的，覆盖运行时的各种情形。
   - 对已有项目：每个项目要新写并维护一个解析脚本，比方案 1 的“加一个报告参数”重。
   - 失败是否大声：是（命令崩溃、超时、JSON 不合格都报）。
   - 性能：每个测试文件一个进程，依次运行，`canon check` 随文件数线性变慢；方案 1 的检查不起进程。
   - 安全：`canon check` 以前不运行项目命令，这个方案让它运行；方案 1 的运行只发生在本来就运行测试的 `canon work test` 里。
   - 它的优点：不用跑过测试就能检查（刚克隆的仓库、没有数据库的环境里 `canon check` 仍有结论）；`start`、`end` 能让证据（BR-2241）精确到测试函数。这两条正是方案 1 的代价（见后果），所以它是备选：如果“刚克隆要先跑一遍测试”或“证据只到文件一级”在使用中被证明不可接受，再提新决策把它作为补充（输出格式 `[{title, runs, start, end}]` 原样保留）。
   - 要改的规则：同方案 1，另加命令的约定。
   - 来源：src/knowledge/check/test-titles.ts “This is a small lexer, not a”
3. **保留内置 JS/TS 解析，其他语言用项目命令或不算**：否决。违反“canon 不认任何语言”；canon 里留两条路（JS/TS 内置、其他走命令或报告），同一个概念有两套语义（内置词法器只认字符串字面量的标题，变量拼接的标题认不出，D-12 的后果里写过；报告认的是运行时的名字）。canon 自己的项目只是一个 JS/TS 项目，没有理由享受特权。
   - 分清：JS/TS 能，其他取决于另一个机制。对已有项目：JS/TS 项目不用改，其他项目要改；失败是否大声：取决于另一个机制；性能：JS/TS 最快；安全：无新增；要改的规则：BR-2005 保持分语言的两段。
   - 来源：src/knowledge/check/check.ts “other languages have no title parser, so their whole text still counts”
4. **canon 内置更多语言的解析器**：否决。违反硬约束；D-12 已经因为体积否决了 TypeScript 编译器，每加一种语言还要认它的每种测试框架，覆盖永远不全。
   - 分清：只限已内置的。对已有项目：没内置的无路可走。失败是否大声：框架没认出来时解析出零个标题，分不清是没有测试还是认不出。性能：最快。安全：无新增。要改的规则：BR-2005 每加一种语言加一段。
   - 来源：canon/decisions/D-12.md “canon 编译成单个可执行文件，把 typescript 打进去体积大很多”
5. **每个 glob 配一个正则**：否决。语言中立，但分不清注释和被跳过的测试（这正是 #127 要解决的第一条），也给不出调用的结束行。
   - 分清：不能。对已有项目：写一个正则就“看起来严格”，仍可被注释骗过。失败是否大声：正则零匹配和“没有测试”分不清。性能：快。安全：无新增。要改的规则：同方案 2。
   - 来源：canon/rules/knowledge/check/BR-2005.md “其他扩展名的测试文件（只能通过 `tests` 配置扫到）整个文件里出现的编号都算。”
6. **只把非 JS/TS 改成严格（没配置时一律不算）**：否决。不是语言中立（仍要分 JS/TS 和其他）；单独做的话非 JS/TS 项目只剩 `untested:` 一条路。它的“没配置就大声失败”的思路被方案 1 采用。
   - 来源：canon/decisions/D-12.md “其他语言的项目仍是全文扫描，对它们的覆盖判断比 JS/TS 宽松。”
7. **保持现状，只加警告**：否决。提示不是发现，不挡合入；项目无人值守（product.md P7），没人读；规则仍可被一条注释“证明”，P5 的承诺不成立。
   - 来源：canon/product.md “每条生效的规则都能追到判定它的测试或验收记录”
8. **报告和读标题命令组合**（命令给静态标题和行范围，报告证明确实跑了）：否决，现在不做。两个来源都描述“有哪些测试”，不一致时要再定一套规则；方案 1 单独已经够用，它的两个代价（刚克隆要先跑一遍、证据只到文件一级）没有数据说明不可接受。需要时按方案 2 里写的条件再提。
   - 来源：canon/decisions/D-23.md “floor 是任意 shell 命令，推断不可靠，猜错时是无声的。”

9. **选测试和 `test-reads-skip-path` 的读源码部分搬进项目命令 `test_select_command`（采用）**：选测试里依赖语言的三条（相对导入、CLI 命令表、读数据文件，BR-2157、D-60、#117）和 BR-2181 的源码读法，都是“改了这些文件，哪些测试会受影响”的回答。canon 只定约定（标准输入给改动的路径，标准输出打印要运行的测试文件），读法由项目自己写；canon 自己的项目把现有的读法原样搬进 `scripts/` 下的脚本，作为它的 `test_select_command`。细节在“决定”的第 3 条。
   - 语言中立：是。canon 里不再有 `JS_TS`、导入读法、命令表读法。
   - 分清、对已有项目：JS 项目（canon 自己）行为不变（搬过去、测试跟着搬、用最近的合入对照新旧选择）；其他项目从“只有中立的三条理由”起步，要更准的选择就自己写一个。
   - 失败是否大声：是。命令崩溃、输出不是测试文件都让 `canon work test` 失败；没配置时每次输出一行说明；配了 `floor_skip_paths` 没配命令是配置错误。
   - 性能：每次 `canon work test` 多起一个进程；`canon check` 不运行它。
   - 安全：项目命令，和 `test_command` 同一信任级别；`canon check` 不运行它。
   - 要改的规则：BR-2157、BR-2164、BR-2181（退役）、BR-2119（见第 3 条）。
   - 来源：canon/decisions/D-60.md “测试的相对导入（直接或间接）到达改过的文件”
   - 来源：canon/rules/work/land/checks/BR-2164.md “这些路径由项目自己声明为测试读不到的文件”
10. **删掉按导入和 CLI 选测试，只留中立的三条理由**：否决。canon 自己的项目会悄悄漏选间接受影响的测试：D-23、BR-2157 当初要防的正是这个（#113 是“没选出来、floor 才发现”）；BR-2164 让只改 `floor_skip_paths` 下文件的合入不跑 floor，它的安全依据是 BR-2181 的源码读法，删了选测试和 BR-2181 之后，这条跳过没有任何保证。
   - 语言中立：是。对已有项目：所有项目的选择变窄，漏选无声。失败是否大声：不是（漏选看不出来）。性能：最快。安全：无新增。要改的规则：BR-2157、BR-2181、BR-2164。
   - 来源：canon/decisions/D-23.md “floor 是任意 shell 命令，推断不可靠，猜错时是无声的。”

## 决定

采用方案 1 和方案 9，删除内置的 JS/TS 标题解析（`src/knowledge/check/test-titles.ts` 和它的测试），并把按导入、CLI 命令表、读数据文件选测试的读法和 BR-2181 的源码读法从 `src/` 搬到 canon 自己仓库的脚本。canon 的产品代码里不再有按语言分流的地方。

**报告约定**：

- 文件格式：JUnit XML。canon 只读：`testcase` 的 `name`、`classname`，它外层每一层 `testsuite` 的 `name`，这个 `testcase` 有没有 `skipped`、`failure`、`error` 子元素，以及两个可选属性：`line`（有就读，只用在合入证据里）和 `file`（只在 `floor` 的报告里读，见第 4 条）。别的属性（耗时等）一律不读。
- 一个测试的“名字”是外层 `testsuite` 名、`classname`、`name` 三者；规则编号出现在其中任何一个里，就算这个测试点名了它（等价于现在 `describe("BR-1", …)` 点名了它下面的测试）。
- “会运行”：没有 `skipped` 子元素。失败（`failure`、`error`）也算会运行：它是一个存在的、运行了的测试，失败由测试结果本身挡住合入（floor、`canon work test`）。
- 空报告（没有 `testcase`）合法，表示这次运行没有收集到测试。不是合法 XML、或根元素不是 `testsuites`、`testsuite` 之一：这次运行记为“报告无效”，写明文件和原因，不记账。
- `line` 的两种约定不一样（实测：bun 从 1 起、指向调用那一行；pytest xunit1 从 0 起、指向第一个装饰器），canon 不校正，原样使用；见第 2 条里对误差的说明。

**记账**：协调数据库新增一张表，每个（测试文件路径，文件内容的 git blob 哈希）一行：`testcase` 列表（名字三元组、会不会运行、`line` 有没有）、来源（`test_command` 还是 `floor`）、时间。同一个路径保留最近的若干行，最近一行供下面“旧行”用。`canon work test` 每次运行一个测试文件时，`test_command` 里的 `{report}` 换成一个临时路径，运行结束后读报告、写这一行、删临时文件；这次运行的退出码照常（失败就是失败）。命令没写出报告（编译错误等）时，这个测试文件不记账，`canon work test` 输出“<文件> 没有写出报告”并以失败退出。

**1) `canon check`**：读这张表，不运行任何东西。

- 报告存哪：协调数据库（git 公共目录，所有 worktree 共用，本机上所有变更看得到彼此跑过的结果）。不存进仓库：报告随每次运行变化，进 git 会制造冲突和噪声。
- 和哪个提交对应：不对应提交，对应测试文件的内容。键是“路径 + blob 哈希”：测试文件内容没变就一直有效（别的变更合入、rebase 都不影响）；内容变了，哈希不同，原来的行成为“旧行”。测试文件以外的源码改动不使报告作废：测试有哪些、会不会运行由测试文件决定；一个测试只因为源码改动才开始被条件跳过，这种情况交给 floor 全量运行时的结果。
- **`rule-untested`**：生效的规则要有一个会运行的测试名字点名它。每个测试文件读哪一行：当前内容有行就读它；当前内容没有行、而且这个文件不“相关”（见下）时读它的旧行，并在输出里提示；“相关”的文件当前内容没有行时，不读旧行（它在下面报 `test-report-missing`）。`ref-dangling` 和 `test-retired-rule` 看所有名字，包括被跳过的，读法同上。
- **`test-report-missing`（挡合入，退出码 1，一个项目一条）**：收窄到本变更相关的测试文件。精确条件：文件匹配 `tests`、在当前树里存在、记账里没有它当前内容的行，并且满足下面任一条：
  1. 它是本变更改动的文件（和 BR-2157 同一份：对 main 的合并基点比较，含已提交的、未提交的和未跟踪的；删掉的不算）；
  2. 它的最近一行里，一个会运行的测试点名了本变更碰过的规则（碰过的规则同 BR-2157：规则文件被改过的，加上变更文件 `rules:` 里列的）。
  发现里写明文件数、前 5 个文件，和“运行 `canon work test <这些文件>`”这句话；不退回“整文件计”，也不按“没有测试”处理。不在任何变更里（例如主 checkout）检查时，这两条都不成立，不报这一项。
- **`test-report-stale`（只提示，退出码 0）**：匹配 `tests`、当前内容没有行、但有旧行、又不满足上面两条的文件，合起来提示一次：文件数、前 5 个，和“它们的内容在你没碰的情况下变了（别人合入、或没人跑过），点名它们的规则按旧行计”。从没有任何行的文件（刚加的、刚克隆的）在 `rule-untested` 的信息里合起来说一次“N 个测试文件没有报告”，并写“运行 `canon work test --all`”。
- 例子（方向）：别人合入改了 `a.test.ts`，我的变更没改它、没碰它点名的规则，记账里它只有旧行 → 我的 `canon check` 不报 `test-report-missing`，提示 `test-report-stale`，`a.test.ts` 点名的规则仍算有测试。我改了 `b.test.ts` 但没跑过 → 报 `test-report-missing`（条件 1）。别人改了 `a.test.ts`，它的旧行点名 `BR-5`，我改了 `BR-5` → 报 `test-report-missing`，因为 `BR-5` 的证据要读它当前的内容（条件 2）。我什么测试都没碰，`c.test.ts` 是别人新加的、没有任何行 → 不报 `test-report-missing`；`c.test.ts` 点名的规则如果只有它点名，报 `rule-untested`，信息里说明有测试文件没有报告。
- 一份测试文件的报告是空的（没有 `testcase`），而项目里有规则只有它能点名时，`rule-untested` 的信息里要列出“报告里没有 `testcase` 的测试文件”：框架没收集到测试（上面那个 `check_provenance_test.py` 的情形）和文件真的没有测试从报告看不出来，canon 不猜，把可疑的文件摆出来。
- `canon work test` 最后会运行 `canon check`（既有行为），刚写进去的报告立刻被它读到，所以“跑过再检查”是自然的顺序。
- 代价（明说）：`canon check` 不再是纯静态的：一个刚克隆的仓库、或者别人的机器上，没有数据库里的记账，要先把测试跑一遍（`canon work test --all`，或有 `floor` 报告时跑一次 floor）才能让规则检查通过。canon 本来就只支持一台电脑上开发（product.md “不做的事”），所以不是新增的限制，但对“只想检查文档”的场合是新的摩擦；备选见方案 2。
- `test-reads-skip-path`（BR-2181）退役：它读 JS/TS 源码，没法中立。它守的东西改由第 3 条里的 `test_select_command` 在合入时守。

**2) 合入时的执行证据（BR-2241、BR-2245）**：改用同一张表。

- 量化（用 canon 自己的仓库，2026-11-05，`scratchpad` 里一次性脚本，不进仓库）：
  - 每个测试文件里会运行的标题点名多少条不同的规则：91 个 `src/**/*.test.ts` 里，0 条的 1 个，1 条 15 个，2 到 3 条 22 个，4 到 9 条 41 个，10 到 19 条 10 个，20 条以上 2 个；中位数 4，90 分位 10，最大 34，平均 5.5。所以“这个测试文件被改过”平均顺带认了 5 条规则。
  - 事件表里 138 个 `land.ok` 带 `base` 和 `sha`，其中 97 个改了测试文件。对这 97 个，把“改动行落在点名测试里”（现在的 BR-2241）和另外两种算法比较，看多认了多少条（合入，规则）：按“测试文件被改过”算，83 个合入多认，一共多认 1017 条；按“报告 `line`”算（每个改动行归给 `line` 不大于它的、最近的那个测试，加上包着它的 `describe`），18 个合入多认，一共 22 条。
  - 历史上 BR-2241 按行拒绝过的合入：`canon events --kind land.refuse` 共 147 条，`reason` 字段是 `evidence` 的 6 条（5 个变更：C-225、C-260、C-277、C-285、C-341，C-341 拒了两次），可以直接区分。能复原的 4 个（C-225 的合并基点提交已经不在库里；合入时提交时间被统一改写，被拒时的确切状态靠提交标题推断，是近似）：C-260 的改动里没有点名那条规则的测试文件，三种算法都拒；C-277、C-285、C-341 的改动里都有测试文件点名了被拒的规则（BR-2291、BR-2292，BR-2150，BR-2045、BR-2276、BR-2289），只是改的不是点名它的那个测试，按文件算会放过，按行和按 `line` 都仍然拒绝；被拒之后三个变更各补了一个改在对应测试里的提交（`fe3ae2b`、`36582ce`、`8477c6e`）。也就是：按文件算，4 个里有 3 个会被无声放过。
  - 结论：“有 `line` 就按 `line`，没有就按文件”。按文件算的放过面是按行的 45 倍（1017 对 22），而且正好覆盖了 BR-2241 拒绝过的情形；按 `line` 算多认的 22 条来自改动行落在两个测试之间的辅助代码（归给前一个测试），是可接受的误差。
- BR-2241 的“测试”证据改成：这个变更的合入改动了某个测试文件，这个文件当前内容的记账里：
  - 每个 `testcase` 都有 `line` 时：每个改动的行（新一侧，被删除的行按删除点之后的位置）归给 `line` 不大于它的、最近的那个会运行的 `testcase`；改动行在第一个 `testcase` 之前的不归给任何测试；归到的 `testcase` 的名字（外层 `testsuite` 名、`classname`、`name`）点名了这条规则，就是证据，方式记 `test`。
  - 有的 `testcase` 没有 `line` 时：这个文件退到“文件被改过，文件里有一个会运行的测试点名这条规则”，方式记 `test-file`，让评审和后来的人看得出这条证据粗；信息里写“报告没有行号，证据只到文件”。项目要精确，就让它的报告带 `line`（pytest 的 `junit_family=xunit1`，gdUnit4 没有，只能是文件级）。
  - `line` 的误差：pytest 的 `line` 从 0 起，指向装饰器；bun 从 1 起。canon 不校正，所以紧挨着两个测试交界的那一行可能归给后一个测试（over-credit 一行），不会多认到第三个测试。和按文件算比（上面 1017 对 22），这个误差小得多。
  - 验收证据（`untested:` 加 `## 验收`）不变。
- BR-2245 的迁移记录读同一张表。
- 合入时要求被改动的测试文件都有当前内容的报告（`test-report-missing` 条件 1 已经保证）；rebase 后两边都改过同一个测试文件会得到新内容，需要重跑一次 `canon work test`，和现在 rebase 后重测的习惯一致。
- 不依赖 floor 的报告：`floor_timing: after` 下合入时 floor 还没跑；floor 的报告在它跑完以后补进同一张表（第 4 条），不是合入证据的前提。

**3) `canon work test` 的选测试、`test_select_command`、`floor_skip_paths` 和 `canon context`**：

- 保留在 canon 里的、不涉及语言的理由：测试文件自己被改过；记账里有会运行的测试点名本变更碰过的规则（读那张表，不再解析源码；新改的测试文件本来就因“自己被改过”被选，所以不会漏）；`always_tests`（BR-2297）。
- 新增项目配置 `test_select_command`（字符串，shell 命令，在仓库根运行，和 `test_command` 同一信任级别，沿用它的超时）：
  - 标准输入：改动的路径，每行一个，相对仓库根；已提交的、未提交的、未跟踪的，删掉的也在（BR-2157 现在的那份）。
  - 标准输出：每行一个要运行的测试文件，可以在路径后用制表符写理由；空输出表示没有。每个路径必须匹配 `tests` 且存在，否则 `canon work test` 以退出码 4 失败，列出哪些路径不对。命令以非 0 退出或超时，同样退出码 4，信息里带输出的末尾，不退回只按中立理由选。选出的文件加进选择，理由写“命令选出：<理由>”。
  - 没有配置：每次 `canon work test` 输出一行“没有配置 test_select_command，只按改动的测试文件、点名的规则和 always_tests 选；按导入选测试已移除，见 D-64”，不是无声退化。`--all` 不受影响。
- canon 自己的项目：现有的导入读法（`importedPaths`）、CLI 命令表读法（`cli-tests.ts`）、读数据文件读法（`data-reads.ts`）和 `skip-reads.ts` 的路径读法，从 `src/` 整体搬到 `scripts/select-tests/`（`code_root: src` 之外，是 canon 这个项目自己的工具），`canon/config.yaml` 加 `test_select_command: "bun scripts/select-tests/main.ts"`，`tests` 加 `scripts/**/*.test.ts`；它们的测试和例子跟着搬，BR-2157 里“导入”“CLI”“读数据文件”三条的规则文字搬成这个项目自己的规则（新建子领域，主语从 `canon work test` 改成这个脚本）。搬完要有一次对照：用事件表里最近 138 个合入的改动路径，分别跑旧的 `selectTests` 和新的脚本，选出的测试文件集合必须一样，不一样的逐个说明；这是验收的一部分，不是可选的。
- **BR-2181 的替代**（`floor_skip_paths`）：BR-2164 现在靠 `canon check` 里的源码读法保证“跳过 floor 的合入不会弄坏读那些路径的测试”。改成合入时直接问：只改 `floor_skip_paths` 下文件的合入，在决定跳过 floor 之前，把这次合入的路径交给 `test_select_command`；它选出任何测试文件，floor 照常运行（不跳过），并写明是哪个测试、为什么；没选出才跳过。所以跳过是否安全由项目自己的选择命令负责，认不出的写法仍靠项目自己保证，和 BR-2181 的局限一样，但不再要求 canon 读源码。配了 `floor_skip_paths` 却没配 `test_select_command`：配置错误，退出码 2（不然跳过就没有任何依据）。BR-2181 退役，`canon check` 不再有 `test-reads-skip-path`。
- **BR-2119（`canon context <文件>` 的导入读法）**：它也是读 JS/TS 源码，同样违反硬约束。本决定的处理：退役，`canon context <文件>` 只按代码路径找文件所在的领域，不再列“导入的领域”。理由：这个功能是给读代码的人多看几个邻居领域的规则标题，不影响任何检查或合入；要保留它就得再给项目一条命令（又一个配置键），收益不够。这是本决定里要负责人确认的一点（见“待负责人决定”）。D-15 里这一条随之改。
- 按名字只跑一条：canon 没有这个用处。以后要加，可以让 `test_command` 多一个 `{name}` 占位符，名字取自记账里的测试名；这不需要语言知识，不在本决定内。
- 没法中立的部分：一次 `test_command` 运行对应一个测试文件，报告里的测试全部归到这个文件（`test_command` 的报告不读 `file`）。按包运行的框架（go 的 `go test ./pkg`）要让 `{file}` 对应的命令只运行那个文件里的测试，否则名字会被归到别的文件；这个约定要写进规则，canon 校验不了。

**4) `floor` 的全量报告**：

- `floor` 命令里可以写 `{report}`（可选）：canon 换成一个临时路径，命令结束后（不论 floor 通过与否）读它。每个 `testcase` 必须带 `file`：相对 floor 运行的目录（仓库根），或者仓库根下的绝对路径，canon 化成相对路径；匹配 `tests` 的文件，各记一行：路径、floor 测的那棵树里这个文件的 git blob 哈希（取自那棵树，不取工作目录，免得 floor 运行期间的修改标错）、这个文件下的所有 `testcase`。这样一次全量运行就能给每个测试文件记账，不用再逐个文件跑；`floor_timing: after` 下的后台 floor 跑完也会刷新记账，所以别人合入的测试文件的旧行会在一批 floor 之后变成当前行。
- 缺 `file` 时大声失败：只要有一个 `testcase` 没有 `file` 或写在仓库之外，这份报告不记账，floor 以报告无效失败，信息写明“这个框架的报告没有 `file`，从 floor 命令里去掉 `{report}`，改用 `canon work test --all` 逐个文件记账”。测试文件匹配不上 `tests` 的 `testcase` 不记账，输出一行提示。floor 通过却没有写出报告：按失败处理（项目既然写了 `{report}`，就是要它）；floor 本身失败又没报告（前面的步骤就失败了）：只是 floor 失败，没有第二条错误。
- 本次实测：bun 有 `file`（所以 canon 自己的 floor 写 `sh scripts/test.sh --parallel=4 --reporter=junit --reporter-outfile={report}`）；pytest 要 `junit_family=xunit1`（官方称为“old style”，以后可能被去掉，是一个风险）；gdUnit4 没有 `file`，只能逐个文件运行；gotestsum 没有 `file`。vitest 没有实测，不下结论。
- 空文件：全量报告里没有任何 `testcase` 的测试文件不记账（分不清“没有测试”和“没被运行”），仍然是“没有行”，在相关时会报 `test-report-missing`，用 `canon work test <文件>` 补。

**5) 迁移和过渡**：没有宽限期，缺配置立刻大声失败。

- `test_command` 现在必须含 `{file}`（BR-2160），再加：必须含 `{report}`；不含时，所有命令以退出码 2 失败，信息里写出 JS 项目的修正（`bun test {file} --reporter=junit --reporter-outfile={report}`），以及 pytest、gotestsum、vitest、GUT 的写法（来源见上）。没写 `test_command` 的项目：`canon check` 报 `test-report-missing`，信息里同样给出写法。
- `tests` 不再有默认：没写时 `canon check` 以退出码 2 失败，要求写出（BR-2046 删去默认扫描）。canon 自己的项目已经写了。
- 已有的 JS 项目（包括 canon 自己）：改 `test_command` 一行，跑一次 `canon work test --all`（或一次带 `{report}` 的 floor），之后和以前一样。canon 自己的 `test_command` 改成 `sh scripts/test.sh {file} --reporter=junit --reporter-outfile={report}`（`scripts/test.sh` 把参数传给 `bun test`）。
- Godot 项目（#127，gdUnit4）：见“采用门槛”。
- 已有的执行记录（通过记录）按行为哈希保存，不受影响；BR-2245 只在项目还没有任何通过记录时才写迁移记录。
- 要保留旧行为（整文件计）的项目：写一个把整个测试文件当作一个测试写进 XML 的包装脚本，这是项目自己配置里看得见的选择，canon 不提供开关。

**采用门槛（Godot 项目的报告先实测，已完成）**：本决定提出时，gdUnit4 的开关和 skipped 的表示是查不到的。本次在 #127 的项目副本里实测了（结果在“事实”）：能写出带 `skipped` 和 `failure` 的合法 JUnit XML，注释里的编号不进报告，所以 #127 的两条期望（注释不算、被跳过的不算）可以满足；条件是：函数名里写 `BR_<数字>`、转接脚本拷出报告并把它改成 `BR-<数字>`、该项目现有的 `it("BR-1: …")` 写法要改成函数名（`it` 在运行时什么也不做，标题不会进报告）、逐个文件运行、证据只到文件级（没有 `line`）。这些要在该项目里落地一次（`tools/run_test.sh` 加 `{report}` 并转接，`canon work test --all` 跑通）才算 #127 解决；落地由那个项目做，不在 canon 的实现变更里。`tools/tests/check_provenance_test.py` 要改成 pytest 或自己写 XML（见“事实”）。

**被否的方案**：见上面“方案”。内置 JS/TS 解析（方案 3）因为违反“不认任何语言”并留下两套语义被否；读标题命令（方案 2）因为每个项目要自己写解析、让 `canon check` 运行项目命令、不证明“会运行”被否，保留为“刚克隆要先跑一遍测试”不可接受时的备选；删掉按导入选测试（方案 10）因为 canon 自己会无声漏选被否。
