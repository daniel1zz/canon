title: 计划可以标属于哪个版本，版本发布要求它的计划全部完成
status: accepted
amends:
  - D-61
---

## 背景

#146：一个版本按步骤写规则，`canon release status` 显示“规划中 0 已通过 378”，读起来像做完了，其实计划里还有一大半步骤没开始。D-77 给了计划和 `canon plan status`，但版本（D-61）只按标着它的规则算进度，不知道计划；负责人看版本进度时看不到计划做了多少，`canon release ship` 也只看规则。

负责人 2026-11-09 在提问工具里选了“要求全部完成（推荐）”（canon human #13）：`canon release ship` 要求标着这个版本的计划步骤全部完成。

## 方案

1. 计划变更的 front matter 可选 `release: R-n`；`canon release status` 在规则数量后面写标着它的计划的进度；`canon release ship` 要求这些计划的步骤全部已完成，和要求规则全部已通过一样；已发布版本的计划集合不再变，和 BR-2326 对规则的要求一样。采用：版本的进度和能不能发都看得到计划，#146 说的“看起来做完了”不会再出现；标签和规则上的 `release` 同名、同样冻结，读者不用学第二套。
   - 来源：canon/rules/knowledge/releases/BR-2326.md “标着它的规则的集合不许变”
2. 只在 `canon release status` 里显示计划进度，发布照旧只看规则。否决：负责人选了要求全部完成；只显示的话，一个计划只做了一半的版本照样能发出去，正是 #146 要避免的。
   - 来源：canon/rules/knowledge/releases/BR-2333.md “只在标着 `R-n` 的规则（作废的不算）全部是“已通过”时继续”
3. 从标着版本的规则反推计划（看哪些计划的步骤变更改了这些规则）。否决：步骤和规则之间没有记录下来的联系，反推只能猜；一个变更可以改好几个版本的规则。

## 决定

- 计划变更的 front matter 可以写 `release: R-n`，说明这个计划属于哪个版本；只能写在有合格计划的变更上，指向的版本要存在（BR-2386）。
- `canon release status` 在版本的规则数量之后写每个标着它的计划的进度 `计划 C-n 已完成 a/b (p%)`，`--json` 多一个 `plans` 数组；没有计划标着它时输出不变（BR-2328）。
- `canon release ship` 要求标着这个版本的每个计划所有步骤已完成，否则和规则没通过一样以退出码 1 拒绝，并列出没完成的步骤（BR-2333）。步骤已完成按 D-77 的算法：做它的变更已在 main 上 `done`。
- 版本发布后，标着它的计划集合不再变：发布时标着它的计划不能改标或去掉标签，之后也不能有新计划标它（BR-2386）。

## 后果

- 负责人看版本进度时同时看到规则和计划；计划没做完的版本发不出去。
- 一个没有任何规则、只有计划的版本仍然发不出去（BR-2333 要求至少有一条规则），这一点不变。
- 计划的步骤状态只按 main 上的变更算：还在分支上的变更不计，版本的计划进度比 `canon plan status` 少显示“进行中”，只看已完成。
