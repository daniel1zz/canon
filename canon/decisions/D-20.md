id: D-20
title: 待办顺序写在 canon/backlog.md，只由负责人排，没列进的变更排在后面
status: accepted
---

## 背景

开始一个变更不需要任何人批准（D-1），agent 想做什么就做什么，负责人没有地方表达“先做什么、后做什么”（C-40）。N-3 的并发实测里，合入是串行的，每次约 2.5 分钟，多个 agent 改同一个文件时在合入阶段才发现冲突。所以待办顺序要满足：负责人在仓库里就能看和改；agent 新建变更时不碰同一个文件；`canon brief` 和 `canon change list` 能直接读出来。

## 方案

1. `canon/backlog.md` 按顺序列出变更编号，只由负责人编辑；没列进清单的变更按编号排在清单之后，新建变更不改这个文件。采用：排序就是挪一行，人在仓库里或 GitHub 上直接看；agent 从不写它，并发的 agent 不会在这个文件上冲突。
   - 来源：canon/product.md “人直接看仓库里或 GitHub 上的文件”
   - 来源：canon/notes/N-3.md “改同一个文件的任务会在合入时冲突”
2. 同样用 `canon/backlog.md`，但新建变更时由 canon 把编号追加到文件末尾。否决：几个 agent 同时新建变更，就会在同一个文件的同一处追加，合入时 rebase 冲突；而“没列进的排在后面”已经得到同样的顺序。
   - 来源：canon/notes/N-3.md “C-55 和 C-57 改了 `src/cli/main.ts` 的同一行 import”
3. 给每个变更加一个 `priority` 字段（数字）。否决：调整一个变更的位置，常常要改好几个变更文件（插到两个相邻数字之间没有空位时要重新编号）；顺序分散在各个文件里，负责人看不到一张完整的单子；已完成的变更还留着过时的数字。
4. 顺序存在协调数据库里，用命令调整。否决：协调数据库只在本机这个 checkout 里，不进 git，负责人在 GitHub 上看不到，也没有历史记录。
   - 来源：canon/product.md “协调状态只存在本机这个 checkout 里”

## 决定

- 待办清单是 `canon/backlog.md`。列表项开头的变更编号按先后排定顺序，其余文字（标题、理由）随便写（BR-2148）。
- `canon change list` 和主 checkout 里的 `canon brief` 按这个顺序列出未完成的变更，清单之外的按编号排在最后（BR-2148、BR-2149）；没有任务的 agent 取第一个没被认领的。
- 清单里写了不存在的编号，`canon check` 报 `ref-dangling`（BR-2150）；已完成的编号留在清单里不算错，只是不再显示。
- 只有负责人改这个文件；agent 发现的新工作照常建成变更，自动排在最后，由负责人决定是否提前。

## 后果

- 负责人要调整顺序就编辑 `canon/backlog.md`，像其他改动一样合入 main。
- 清单里会留下已完成的编号，需要负责人偶尔清理；它们不影响显示。
- `canon brief` 在主 checkout 里多一行；变更多的时候这一行会变长。
