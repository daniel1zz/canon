## 背景

议程能开工的一组只给一种做法：每个变更一行 `canon work delegate <C-n> --to <name>`（BR-2581）；D-155 的打断提醒（BR-2606）也按机器有没有空写死了下一步。主会话照着做，结果并不好。

zhushenkongjian 近 7 天的派发数据：

- 派发到合入的时长中位数 123 分钟、平均 200 分钟；
- 60% 的派发被交回或收回；
- 派出去的 95 个变更里，主会话合入了 84 个，worker 合入的只有 11 个；
- 86 次交回的说明提到规则：worker 不能改规则文字（D-128），实现时碰到要改的规则只能写提议交回；BR-2501 因契约过期拒绝的只有 5 次。

canon 自己这一轮也是这样：

- `C-661` 和 `C-662` 同时派出去，两个契约里都有 `BR-2527`；`C-661` 应用提议改了 `BR-2527` 以后，`C-662` 被 BR-2501 拒绝，只能收回由主会话合入。
- 主会话的子 agent 认领事先建好的变更时被拒（“未派发”），要先 `canon work delegate` 再恢复它。

负责人的要求是：主 agent 能判断，自己做更合适就自己做，调度不应死板；同时保留 D-128，设计定了再派。

## 方案

1. 给事实和做法，由主 agent 判断：采用。
   - 议程和打断提醒对每个能开工的变更写出“自己做”和“派出去”两种做法，以及判断要用的事实：机器容量、牵连、设计有没有定。canon 不给默认做法。
   - 开工和派活时提示和在做的活有牵连、设计还没定；只提醒，不拒绝。
   - 主会话自己的子 agent 直接认领，canon 替它记派发。
   - `canon stats` 按做法对比结果，主 agent 判断时有数据。
   - 这和 D-152 的方向一致（先补主 agent 看到的上下文，不加检查）；“不给默认做法”是本决定新做的选择，依据是背景里的数据和负责人的要求。
   - 来源：src/work/reminders/agenda.ts “→ canon work delegate ${c.id} --to <name>”
   - 来源：.claude/skills/canon-parallel/SKILL.md “the main agent already holds the context and the work is small: doing it yourself is cheaper than briefing someone”
2. 按变更算分，给出默认执行方式：否决。
   - 例如按文件数、有没有计划中的规则修订、机器负载算出“建议自己做”或“建议派出去”。
   - 分数只看得到改动大小。上面数据里交回的主要原因是规则文字和契约牵连，看不到这些的分数会照样把这类变更判成“派出去”。
   - 默认值会被当成指令执行，等于换个形式写死，和负责人“不死板”的要求相反。
   - 来源：canon/decisions/D-152.md “发现问题先补上下文，再考虑加检查”
3. 只修这一轮遇到的摩擦：否决。
   - 例如只让子 agent 免派发认领、只放宽 BR-2501。
   - 这是按缺陷清单打补丁：议程仍只给“派出去”一种做法，主会话仍看不到牵连和设计没定，下一次照样按默认去派。
   - 来源：canon/rules/work/reminders/BR-2581.md “每个一行 `ready:<C-n> - <标题> → canon work delegate <C-n> --to <name>`”

负责人在 2026-11-21 选定：保留 D-128，设计定了再派；方向按方案 1。

## 决定

采用方案 1，规则如下：

- BR-2607：议程能开工的一组写出两种做法和事实。
- BR-2608：开工或派活时提示和在做的变更共用规则。
- BR-2609：派活时提示设计还没定。
- BR-2610：主会话自己的子 agent 直接认领还没派发的变更。
- BR-2611：`canon stats` 按执行方式对比。
- BR-2606 改为写出两种做法和事实，不再写死下一步。这修订 D-155 的打断步骤；D-155 其余部分和 D-128 不变。

## 后果

- BR-2607 修订 BR-2581 的可派一组，BR-2610 修订 BR-2498 的认领范围。
- 主会话自己的子 agent 直接认领时，机器忙也不拒绝，只提醒（BR-2610）：这修订 D-136 的“负载过高时拒绝新增 worker”。子 agent 在主会话进程里跑，被拒时已经花了 token；整组测试仍按 BR-2576 全机排队。负责人 2026-11-21 选定这样做。
- 议程每个能开工的变更多一到几行事实。最多列 5 个（BR-2581），输出长度可控。
- 牵连按契约里的规则算，看不到只改同一个代码文件、规则不重叠的牵连。这类冲突合入时有重叠提示（`overlap.notice`）和 rebase 冲突兜底，所以只在规则一层提醒。
- 子 agent 直接认领时，派发记录照样有设计版本和契约，BR-2501 的检查不变。别的会话启动的 worker 仍只能认领派给它的。
- 主 agent 选错做法时没有检查挡住，只能靠 BR-2611 的对比数据事后看出来；这是按负责人的要求有意为之。
- 实现分成几个变更：BR-2607 和 BR-2606（议程），BR-2608 到 BR-2610（派发），BR-2611（stats）。
