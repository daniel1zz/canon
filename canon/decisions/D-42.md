## 背景

D-26 规定一起测的那批任何一步失败就整批作废，成员都标成单独合入，一批 k 个失败时要多跑 k+1 次 floor。2026-11-03 本仓库一起测了 11 批，6 批失败：5 批是某个成员自己的步骤（`canon check` 或规则评审）不过，只有 1 批是 floor 不过；floor 不过大多是同一个偶发失败的测试。负责人的原话：“一批失败后每个成员都要单独重跑一遍 floor，不应该这样”；“并且不要限制批次多个个，在队列离的就一起”。

给出推荐前请一个看不到推荐的子 agent 反驳过一次。它指出：批里每个成员和 main 比较，有的成员要等前面的先合入才通过（BR-2248 的例子），而规则评审是大模型、每次结果不一定一样；事件表里 C-181 在批里因 `check` 被拒，几分钟后单独合入成功。所以成员自己的步骤不过时不能直接判它失败。它还算出“floor 失败时领头先合、其余继续一起测”最坏要约 2k 次 floor。

## 方案

1. 只放开批的大小，失败时照旧整批作废：否决。设每个成员被自己步骤拒绝的概率为 p，k 个整体通过的概率是 (1−p)^k，批越大越几乎必然失败，每次失败多花 k+1 次 floor。
2. 成员自己的步骤不过就直接拒绝它：否决。它的结果可能取决于前面还没进 main 的成员，评审又是一次抽样；直接拒绝会把“晚一轮就能合入”的变更判成失败。
3. 成员自己的步骤不过就让它离开这一批、回到队列，其余照常；floor 不过时按前缀二分找出加入后开始失败的变更，拒绝它，前面通过的前缀合入，后面的回到队列：采用。步骤失败不再拖累别人，也不花 floor；floor 失败约 log₂k 次 floor，GitHub 合并队列和 bors 也在批失败时拆开定位。
   - 来源：https://github.com/bors-ng/bors-ng “bors actually tests them in batches (and bisects if a batch fails)”
4. floor 不过时领头先合入、其余成员留在队列继续一起测：否决。肇事的是第 j 个时每一轮都再失败一次，最坏约 2k 次 floor，后面的成员一直被拖着。
5. floor 不过时把失败的测试重跑一遍，确认能复现再归责：否决。这是在 canon 里掩盖项目偶发失败的测试；偶发失败要由项目修掉，单独合入时它同样会让合入被拒。
6. 在排队等待时就先跑成员自己的步骤，没通过的不进批：否决（这次不做）。步骤结果取决于当时的 main，排队期间 main 一直在变，要另设何时作废的规则；方案 3 已经让步骤失败不影响别人。

## 决定

采用方案 3（BR-2172、BR-2173）：

- `land_batch_max` 可以写 `all`：队列里等着的都一起测。
- 领头自己的步骤先跑，不过就拒绝领头，成员回到队列。成员按排队顺序加到链上，rebase 冲突或自己的步骤不过就回到队列（记 `batch.drop`），后面的接着加，不再标成单独合入。
- floor 不过时按前缀二分，拒绝加入后开始失败的那个变更，前面通过的合入，后面的回到队列；`batch.fail` 记下被找出的变更和 floor 次数。
- 移动 main 前某个成员的 worktree 变了或它的合入者停了，它和后面的回到队列，剩下的前缀没测过就再测一次。

## 后果

- 一批里有成员被步骤拒绝时，其余成员仍只跑 1 次 floor。floor 不过时多跑约 log₂k 次。
- 被找出的变更如果是偶发失败的测试造成的，它会被冤枉拒绝一次，和它单独合入时撞上偶发失败一样；它可以再合入。
- 离开批的成员可能排在同批里它后面的成员之后合入（BR-2020）。
- 批很大时，floor 开始前要依次跑每个成员的步骤（含规则评审），等得更久；期间成员改了 worktree 只影响它和它后面的成员。
