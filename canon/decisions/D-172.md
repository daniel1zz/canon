## 背景

#317 报：zhushenkongjian（8 核）2026-11-26 两次后台 floor（main `2b41940e3`、`547820aea`）四个测试分片都以 142 结束（项目脚本给每个分片设了时限，到点用 SIGALRM 杀掉），floor 判 main 没通过，`pause_on_red_main` 让所有合入停下，自动撤回开始找“打破 main 的合入”。在新 worktree 里手动跑同一个 main，负载 30 时 15 分钟里约 6000 个用例 0 失败，只是没跑完。issue 以为后台 floor 不等负载。

查那个项目的协调数据库和日志，结论不是这样：

- 后台 floor 一直过负载关（BR-2630）：`547820aea` 的日志第二行是 `canon: waiting for the machine load: 5-minute load 16.4 on 8 CPUs (limit 16)`，事件表 13:28:33 有 `load.wait`（`kind: floor`），13:29:08 负载 16.0 时 `load.start`；15:58 那次负载 24.9 时等了 745 秒，降到 15.8 才开始。`2b41940e3` 开始时负载低于 16，没有等待行，直接开始了。
- 失败来自开始**之后**：关只在开始时判断一次。别的重步骤在负载 15.8 到 15.9 时先后放行（事件表里那个项目的变更 `C-1280` 的 `load.start` 是 15.9 和 15.8），5 分钟负载跟不上刚开始的步骤，再加上不过关的工作（轻派发的 worker、Godot import），floor 跑的 40 多分钟里负载冲到 20 到 38，分片被自己的时限杀掉。D-161 当时就写了这个缺口。
- 2026-11-27 起关整个失效了：负责人选了“派发只看内存”，项目提交 `c6925a1c31` 把 `delegate_max_load_per_cpu` 设成 1000。按 D-161 这个键也是重步骤的上限，于是 floor、`canon work test`、合入的上限都成了 8000，等于不再等负载。负责人要放开的只是派发。

## 方案

**一、上限的键**

1. **采用：重步骤用自己的键 `heavy_max_load_per_cpu`，不写时取固定默认值 2，不跟着 `delegate_max_load_per_cpu` 走（BR-2665）。** 派发和重步骤是两件事：派发挡的是新 worker，重步骤挡的是 CPU；负责人放开前者时不该连带关掉后者。默认值固定为 2，没写新键的项目重步骤的行为和 D-161 默认时一样；把派发键调大的项目（如 zhushenkongjian 的 1000）重步骤重新在 2 × CPU 数等。
   - 来源：canon/decisions/D-161.md “配置名 `delegate_max_load_per_cpu` 现在也管重步骤”
2. **否决：新键不写时取 `delegate_max_load_per_cpu` 的值。** 对没改过派发键的项目和方案 1 一样；对改过的项目，正好把 #317 的失效原样保留，而且没有任何提示。
   - 来源：canon/rules/work/delegation/BR-2526.md “`delegate_max_load_per_cpu` 倍”
3. **否决：仍用一个键，告诉项目不要把它调大。** 一个数表达不了“派发不看负载、重步骤要看”，负责人 2026-11-27 的选择正是这样的组合；改由文字约束，下一个项目照样会踩。
   - 来源：canon/decisions/D-161.md “配置名 `delegate_max_load_per_cpu` 现在也管重步骤”
4. **否决：把 `delegate_max_load_per_cpu` 改名。** 要迁移所有项目的配置，也解决不了一个键管两件事。

**二、开始后负载冲高时的失败**

5. **采用：后台 floor 失败时，floor 结束那一刻的 5 分钟负载达到重步骤上限，就记为过载失败（`floor.overload`），不记 main 没通过、不撤回、不暂停合入；重测时照常先过负载关，所以要等负载降下来；连续第 3 次过载失败按普通失败处理（BR-2666）。** 过载下的失败说明不了 main 有问题，而误判的代价是所有合入停下、自动撤回去找一个不存在的坏合入。重测前的负载关保证重测在负载低于上限时开始。
   - 来源：canon/rules/work/land/BR-2644.md “所以偶发失败不会暂停合入”
6. **否决：一直重测，直到负载低时的一次结果。** 负载长期高于上限时（BR-2630 不设等待上限），一个真坏的 main 永远记不下来，没人去修，合入也不暂停，坏代码一直往上叠。所以设了次数：最多重测两次，第 3 次照常记下，原因里写明是过载下连续失败，人看得到是负载问题还是代码问题。
   - 来源：canon/rules/work/verify/BR-2630.md “不设等待上限：等到负载降下来”
7. **否决：放行更保守（留余量、把正在跑的重步骤算进去），让负载不冲高。** 只能减轻：轻派发的 worker、项目的 import 等不过关的工作照样推高负载，floor 跑 40 多分钟，开始时的判断管不了后面。可以以后另做，不能替代方案 5。
   - 来源：canon/decisions/D-161.md “两组测试仍可能先后开跑后负载超过上限”
8. **否决：负载升高时暂停或打断正在跑的 floor。** 时限在项目自己的脚本里（`godot_run 900`），canon 暂停进程组照样让墙钟时限到点；打断等于白跑，还是要重测。
9. **否决：用运行期间的最高负载判断，而不是结束时的。** 要在 floor 运行时一直采样；5 分钟平均本来就反映结束前几分钟的负载，分片被时限杀掉正发生在结束前。多一个采样器换不来不同的判断。
10. **否决：过载失败也走撤回，只是不暂停合入。** 撤回要在同样过载的机器上二分探测，探测本身也会超时，BR-2535 会因为“探测 G 不通过”放弃，白占几轮 floor。
    - 来源：canon/rules/work/watch/BR-2535.md “以下情况不定位、不撤回”

## 决定

1. 重步骤的负载上限用 `heavy_max_load_per_cpu`，默认 2，和 `delegate_max_load_per_cpu` 互不影响（BR-2665、BR-2630）。
2. 后台 floor 结束时负载达到这个上限的失败是过载失败：前两次不记 main 没通过、不撤回、不暂停合入，负载降下后重测；连续第 3 次照常记失败（BR-2666）。

## 后果

- 实现时修改的已有规则：BR-2631 的 hook 按新键的上限拦命令（它的上限按 BR-2630 算，文字不变）；BR-2219、BR-2220、BR-2534、BR-2535、BR-2644 写明过载失败这个例外。
- zhushenkongjian 不用改配置：它的 `delegate_max_load_per_cpu: 1000` 仍然只放开派发，合入新 canon 后重步骤恢复在负载 16（8 核）时等。负责人想让重步骤也更宽，就另写 `heavy_max_load_per_cpu`。
- 合入时的 floor（`floor_timing: before`）不在这次范围里：它失败时是这个变更被拒，不是 main 被判坏，也不触发撤回；过载下被拒的变更可以再合入一次。
- 过载失败期间 main 的最新提交显示为没测过（BR-2313），后台测试在负载关前等着；负载一直高时，main 最多晚两次 floor 的时间才被记为没通过。
- 设了次数，所以负载持续高于上限、main 又真坏时，第 3 次会被照常记下，原因里写明是过载下连续失败。
- 什么结果说明这个选择错了：`floor.overload` 之后负载降下来的重测经常也失败，而且是同一个原因（说明负载不是原因，过载判断只是推迟了真失败）；或者过载失败连续 3 次的记录经常出现（说明机器长期过载，该调 floor 的分片或时限，或调低派发，而不是靠重测）。
