## 背景

#234：C-514 一次合入后评审拆成 131 次调用、约 52 MB；单份提示预算和并发限制没有限制总量。负责人要求预览、合入后评审超总调用数或 KB 时零调用、先问负责人，明确同意后再跑；默认值交由 agent 决定。#233 跟踪两层拆分重复领域文字；D-72 的整领域覆盖不在此改变。

## 方案

1. 在完整的实际调用计划前检查，自动关联负责人问题、一次消费同意，继续用原重试命令。采用：既有 questions/events 可在同一 SQLite 写事务核对，预览与后台共用一个闸门；缓存和增量先决定，规则与重复提示一起计量，不会先付一半费用才停下。
   - 来源：https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments “Use required reviewers to require a specific person or team to approve workflow jobs”
2. 加 --budget-approval 参数，重试显式点名问题号。否决：两个命令和后台任务都增加参数关联，而后台仍需要持久计划和一次消费；本次没有必要增加这一层入口。
   - 来源：https://developer.hashicorp.com/terraform/cli/commands/apply “Terraform interprets the act of passing the plan file as the approval”
3. 相同计划一次获准后，所有重跑永久放行。否决：一次同意会变成重复付费授权，失败重试和并发运行都能无限消费。
4. 每次调用前累计，达到阈值再停。否决：超过预算的整个评审已经先调用了 reviewer，不符合负责人要求。

独立子 agent 在不知道推荐项时挑战各方案，要求先确定缓存和增量、同时计算重复评审，不把队列号加入指纹，绑定 reviewer 提交，批准原子消费、失败不返还，并把相关文档挑选延后。本方案采用这些修正。模块检查：共享模块只管计划量及批准，提示与复用各留在原入口，问题仍属既有协调库，没有新进程、表、adapter 或依赖环。

## 决定

按 BR-2490 先构造实际计划，再判阈值；默认 6 次 / 4096 KB。最初定的是 16 次，理由是 C-560 的普通修复预览为 7 次、约 2.3 MiB，8 次会连它都拦住；负责人 2026-11-15 改成 6 次（原话：“review_max_calls 最大6次就要问我，我觉得6次就很多了”，选了“6 次直接跑，7 次起问”）。之后 `review_max_prompt_kb` 调到 600、C-566 去掉了重复正文，常规合入的评审是 2 到 3 次调用（C-564、C-567、C-568），C-514 那种 131 次、#237 那种 127 次的计划会被拦住。项目仍可按实际费用改 main 的配置。

同意对应有序提示、评审种类、工作项、可信 reviewer 提交、命令及阈值，一次消费；失败或被杀也不补回。--again 改队列号不改变同一计划的批准，但它改用当前 main 的 reviewer 提交时，必须重新取得同意；不能拿原 base 的同意替换成对另一提交的授权。未答/拒绝无模型调用，同意后原命令即可继续；合入后的预算拒绝沿用现有失败状态，保留已成功合入。

## 后果

- 总量从完成拆分后的真实 UTF-8 输入计算，按两种提示合计；命中缓存和已通过文档的增量路径仍按原规则省调用，不为便宜缩小正文。
- 并发重试在共享写事务内消费，避免一份同意放行两笔费用；记录问题和消费失败时停下。
- 较大但正常的评审也会需要负责人回答，这是费用闸门的目的。后台不会自动重新付费。
- KB 不是金额，不能保证货币成本；未提交的外部 reviewer 配置、PATH 中的程序不能完整指纹化，本次不读取密钥或另建配置监控。缓存键的既有边界不变。
- 发布、reconcile 与独立措辞判断仍用原入口；本次只把负责人明确点名的预览和合入后整次规则/重复评审纳入闸门。
