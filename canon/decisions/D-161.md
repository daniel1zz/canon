## 背景

D-160 让会话在变更上写 `cpu_light`，派发这个变更时不看负载（BR-2627）；其余派发照 BR-2526 第 2 条，5 分钟负载达到 `delegate_max_load_per_cpu` × CPU 数就拒绝。D-160 否决了“派发不看负载，CPU 交给测试排队控制”，理由是只有整组测试排队（BR-2576），点名文件的测试、合入时补跑的测试和构建都不排队，负载没人管。

负责人 2026-11-22 在 #305 指出两处不对：

- 轻重是一段工作的属性，不是变更的属性。同一个变更常常先由一个 worker 设计（读资料、写决定和规则文字，几乎全在远端模型上跑），再派给另一个 worker 实现（跑测试和构建）。#304 让 Opus 级 worker 也能设计之后，这种两段派发会更常见。写在变更上的 `cpu_light` 要在两段之间改变更文件并发到 main，否则第二段也按轻派出去。
- 负载来自测试、构建和录制，不来自派发。当天 zhushenkongjian 5 分钟负载 22 到 27（8 核，上限 16），四个设计阶段的变更都派不出去；而已经派出去的 worker 继续跑测试，不受任何限制。挡住派发不能让负载降下来，挡住重步骤才能。

## 方案

- **采用：派发时声明轻重（`canon work delegate … --light "<理由>"`），负载限制改到重步骤上，谁跑都一样；变更上的 `cpu_light` 废除。**
   - 轻派发不看负载，内存和名额照查；重派发（不写 `--light`）照旧看负载，因为 canon 管不到 worker 直接跑的、不在清单里的重命令，重 worker 等在重步骤前也照样占内存。
   - 重步骤：`canon work test`（点名文件的也算）、合入在被合入的树上跑的 floor 和它自己补跑的测试文件、后台 floor watch、`canon heavy run -- <命令>` 包起来的项目命令。负载达到上限时它们在整机队列里等，负载降下来后一次放一个、两次放行至少隔 60 秒，避免几组同时开跑又把负载推回去。
   - 项目在 `heavy_commands` 里列出自己的重命令（录制、导出、构建）的写法；负载达到上限时，Bash 前的 hook 拒绝没有经过 `canon heavy run` 的这类命令，提示改用它等待。
   - 解决了 D-160 否决“派发不看负载”时的那条理由：不排队的测试和构建现在都受负载限制。
   - 来源：canon/decisions/D-160.md “点名文件的测试、合入时补跑的相关测试、构建（例如游戏项目的导出）都不排队”
- **否决：保留变更上的 `cpu_light`，只给重步骤加负载限制。** 两段派发的问题还在：第一段轻、第二段重，要在两段之间改变更文件并合入 main，忘了改第二段就按轻派出去。
   - 来源：canon/rules/work/delegation/BR-2627.md “变更的 front matter 可以写”
- **否决：派发完全不看负载，只管重步骤。** 改动最少，但重 worker 除了 canon 的命令和项目列出的命令，还可能直接跑别的构建；负载已经很高时继续派重 worker，它们都会排在重步骤前，各占约 300 MB 内存和一个名额，什么也做不了。
   - 来源：canon/rules/work/delegation/BR-2526.md “5 分钟平均负载达到 CPU 数”
- **否决：重步骤在负载超限时直接拒绝，不等待。** worker 无人值守，被拒后只能隔一会儿重试，变成轮询；几个 worker 在负载刚降下来时同时重试，又一起把负载推高。等待加整机队列能保住先后顺序，并控制放行间隔。整组测试排队已经是这种做法。
   - 来源：canon/rules/work/verify/BR-2576.md “先在整台机器的队列里拿一个名额”
- **否决：canon 按变更会改的路径自动判断轻重。** 理由同 D-160：派发时还没改任何文件，`要改什么` 不是机器能读的路径清单。

## 决定

1. 派发可以声明为轻派发：不看负载，内存和名额照查；轻改重时查负载（BR-2632）。
2. 负载限制管重步骤，谁跑都一样：整机队列里等，一次放一个，两次放行至少隔 60 秒，不设等待上限（BR-2630）。
3. 项目的重命令用 `canon heavy run` 纳入同一个等待，`heavy_commands` 让 hook 在负载超限时拦下没经过它的命令（BR-2631）。

## 后果

- 等负载的两条规则放在 `work/verify`：它已经管整组测试按机器排队，负载队列和整组测试队列是同一类整机排队，不新开领域。

- 实现时修改的已有规则：BR-2526 第 2 条和重新派发的例外、BR-2581 的可派一组、BR-2582 的 `heavy:` 一行（新文字在 C-693 的提议里），BR-2497 的派发记录，BR-2466、BR-2580 的时限，BR-2045 的配置项；BR-2627 和变更上的 `cpu_light` 字段退役，它的合入提醒移到 BR-2632。

- 负载高时设计、调研可以照常派出去，重 worker 的测试和构建排队等负载降下来。
- 不设等待上限：负载长期高于上限（例如机器上有和 canon 无关的长期任务）时重步骤一直等。等待行写明负载和上限，会话可以 `--stop`，负责人可以调高 `delegate_max_load_per_cpu`。
- 60 秒的放行间隔只是缓解：5 分钟负载 60 秒内只反映新进程的一小部分，两组测试仍可能先后开跑后负载超过上限；已经在跑的步骤不被打断。
- 轻派发的 worker 如果其实跑了测试，它的测试照样等负载，不会压垮机器；合入时它改了测试覆盖的路径仍会提醒（原 BR-2627 的提醒移到新规则）。
- 配置名 `delegate_max_load_per_cpu` 现在也管重步骤，名字不完全贴切；改名要迁移所有项目的配置，这次不改。
- 什么结果说明这个选择错了：轻派发的 worker 经常出现在负载队列里（`load.wait` 的主题是轻派发的变更），说明轻重判断不可靠；或者有了负载关之后，5 分钟负载仍经常长时间高于上限（重 worker 直接跑了不在 `heavy_commands` 里的命令），说明只管 canon 能看到的步骤不够。
