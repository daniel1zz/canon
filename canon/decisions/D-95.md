id: D-95
title: 引用复核记在引用方 front matter 的 links 里，有记录只看记录，没记的和 links_since 起点提交比较
status: proposed

## 背景

D-90 方案 4 定了：正文里的编号引用是关系的唯一来源；被引文档的行为变了，这条引用就是可疑的，直到引用方的作者复核；`canon context` 列出双向引用；验收（C-464 G 步）要求零可疑。D-90 把“复核过的指纹存在哪”留给 C-464 的 D 步，约束是：元信息不能和正文说法不一（P5）；不能有一个每次合入都要改的共享文件（并发合入会在它上面冲突）；不能有一次改动几百份文档的迁移（会和每个开着的变更冲突）；任何一个提交上都能确定地算出来。

实测（2026-11-11，机器负载 8 到 11；基准的三种取法用一次性脚本比较，其余是 C-469 按历史算基准的实现，即方案 6）：

- canon：1708 个提交里 575 个改过规则或决策，共 1573 个不同的文件版本。一次 `git log --first-parent --raw`（约 30 毫秒）加一次 `git cat-file --batch` 读完全部版本、算出每份文档每个版本的指纹和引用，合计约 130 到 145 毫秒；`canon context BR-2236` 从约 0.25 秒变成约 0.39 秒。zhushenkongjian（810 条规则，1016 个相关提交，3327 个版本；`git log` 约 60 毫秒）合计约 240 到 340 毫秒。`canon check` 约 2.1 秒，不读历史（只查 `links` 和正文对得上），不受影响。
- 现有引用 1671 条（zhushenkongjian 2846 条）。按 C-469 落地的历史基准（方案 6），现在可疑的 584 条，涉及 270 份引用方（zhushenkongjian 897 条、430 份）。一次性脚本比较三种基准（没排除作废的规则和被取代的决策，所以总数略多）：行为改过或引用新写进去 627 条（zhushenkongjian 903 条）；只算引用写进去的时候 923 条（1365 条）；引用方文件任何改动都算 561 条（767 条），但只改标题也会被当成复核过。
- canon 合入时把变更 rebase 到 main 上，提交的先后是合入的先后，不是写的先后。
- C-469 按 git 历史算基准落地后，独立评审复现了三个由它而来的缺陷（C-473）：同一个提交，完整克隆 605 条可疑，`git clone --depth 1` 输出没有可疑、退出码 0；引用方指纹一变就算复核过它点名的一切，给 BR-2424 加一行例子就清掉了它的两条可疑引用，之后 `canon links confirm` 什么都不写；记录和历史基准取“或”，分支上复核并改了引用方、main 同时改了被引方，rebase 后不可疑。负责人对 canon human #25 选了：取一个起点提交，之前的引用算复核过，只跟踪之后的变化。按起点算（C-473，2026-11-11，机器负载约 6）：`canon links list` 整个进程 0.32 到 0.37 秒，只读起点那一棵树；起点设为当时的 main 时，C-473 的 worktree 里只剩它自己改的规则带来的 40 条，设为 400 个提交之前时 765 条。

## 方案

1. **复核时在引用方 front matter 的 `links` 里记下被引文档当时的指纹，有记录只看记录；没记的引用和配置里的起点提交比较；合入给变更新加的引用写记录（采用）**：`canon links confirm` 只改引用方一个文件，并发只和同样改它的变更冲突；记下的是作者复核时读到的那个版本，rebase 之后被引文档在 main 上又变了照样认得出（按 BR-2425）。没记的引用不用迁移：起点提交里已有的引用和被引方在起点的版本比较，只读那一棵树（按 BR-2424）；起点之后新写的引用由合入写下作者读到的版本（按 BR-2440）。`links` 和正文对不上由 `canon check` 报出（按 BR-2426），所以元信息不会和正文说法不一；放在 front matter 里也不碰规则的行为哈希（BR-2236）。代价：起点之前的引用一律算复核过，那时已经过时的引用不会再被发现；每次 `canon context`、`canon links`、`canon brief` 多读一遍起点那棵树。
   - 来源：canon/rules/knowledge/documents/BR-2237.md “`passes` 只由 canon 在关闭提交里写”
2. **只从 git 历史算，复核写成提交的 trailer（否决）**：不改任何文件、不会冲突；但复核只在历史里，`canon check` 没法在树上核对，也看不到；trailer 不带被引文档的指纹时，rebase 后复核的提交排在被引文档的改动后面，就被当成复核过了新版本；只为复核而做的空提交在 rebase、压缩提交时可能丢掉。
   - 来源：canon/rules/work/execution/BR-2244.md “加 `--finish` 的合入 rebase 到 main 之后”
3. **每条引用都必须有记录，一次补齐（否决）**：一次要改 canon 270 份、zhushenkongjian 430 份文档（只算现在可疑的；全部引用涉及更多），和每个开着的变更冲突；之后每写一条新引用都要先运行命令，否则 `canon check` 报错，写规则的摩擦变大，而这份记录和“这条引用写进来的那个提交”给的信息一样。
   - 来源：src/knowledge/documents/model.ts “one file per rule 0% false conflicts vs 53% for a shared append-only file”
4. **一个共享的指纹文件，或放在协调数据库里（否决）**：共享文件每次复核和合入都改，并发合入在它上面冲突；协调数据库不提交、不跨机器，换一台机器或换一个提交就算不出来，验收没法要求它。
   - 来源：canon/architecture.md “本机所有 worktree 共用，不提交、不跨机器”
5. **每份文档旁边一个记录文件，例如 `canon/links/BR-n.yaml`（否决）**：和方案 1 记的东西一样，但文档改名、移动领域、作废时要同时管两个文件；front matter 里已有 canon 写的 `passes`，同一种做法更少新东西。
   - 来源：canon/rules/knowledge/documents/BR-2236.md “标题、front matter（状态、`untested` 等）、其他段落、领域 README 和术语都不影响它”
6. **没记的引用按 git 历史算基准：引用方指纹最后一次变化或引用写进去的那个提交（C-469 落地的做法，否决）**：不用配置，但结果取决于克隆里有多少历史（浅克隆把最早的提交当成一切的起点，说没有可疑）；改引用方的任何行为文字都被当成复核过它点名的一切；rebase 把变更里的改动排在 main 上并发改动之后，又和记录取“或”，所以有记录的引用也会被藏掉。
   - 来源：canon/rules/work/execution/BR-2244.md “加 `--finish` 的合入 rebase 到 main 之后”

## 决定

采用方案 1。

- 复核记录放在引用方 front matter 的 `links` 里，由 `canon links confirm` 和带 `--finish` 的合入写；没记的引用不迁移、不补记录，和 `canon/config.yaml` 的 `links_since` 起点提交比较；什么都不另存。
- 作废和取代计入被引方的指纹。
- 引用、指纹和可疑的定义按 BR-2423；起点提交和读不出来时怎么办按 BR-2424；`links` 的写法和有记录时怎么判按 BR-2425；合入写记录按 BR-2440；`links` 和正文对得上由 `canon check` 查，按 BR-2426；`canon links list`、`canon context`、`canon brief` 怎么说按 BR-2427、BR-2428、BR-2429。
- 不加缓存：实测的耗时可以接受；以后文档多到不能接受时，按起点树的 git 对象编号缓存（内容决定结果，不会过期）。

## 后果

- 起点之前现有的可疑引用（canon 当时 605 条；zhushenkongjian 897 条）按负责人的选择算复核过，不再列出；每个使用 canon 的项目都要设一次 `links_since`，没设之前看不到可疑引用，只看到读失败（按 BR-2424）。
- C-469 的三个漏报都没有了：结果不再取决于克隆深度；改引用方不再算复核；提交的先后不再参与判断，所以 rebase 藏不住被引方的并发改动。
- 已知限制：两个会话在同一份文档里各复核一条引用，两边都改 `links:` 块，合入时文字冲突，后合入的被拒，要 rebase 后再复核一次。合入时自动合并只限于 `links:` 块的冲突要改 rebase 的冲突处理，没有做；合入写记录之后手工复核少了很多，冲突也随之少见。
- 合入写记录有覆盖不到的合入（按 BR-2440），那些新引用宁可多报为可疑。
- 被很多文档引用的规则一改，会一次出现很多可疑引用（D-90 的后果）。
