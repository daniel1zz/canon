## 背景

canon 的检查有两类。一类保证 main 是对的：floor、合入前的 hook、变更测试的证据、设计门、规则评审，没过就不能合入。另一类只是防止主会话忘事：BR-2464 在未处理的评审意见多了或放久了时不让开新变更（D-126）。第二类挡住的是和意见无关的工作，worker 只能空等。负责人 2026-11-18 定下：这一类改成提醒，「所有类似的情况都可以通过monitor处理」「monitor和我们的Canon正好搭配」（#260）。第一类不变。

另一个问题是机器容量（#258）。主会话派 worker 前要自己查负载和内存。忘了查就会同时跑太多 worker，内存开始换页，合入时的测试一起超时。负责人把它定为安全限制，仍然拒绝。

要送到会话的状态，canon 大部分已经有了：
- 事件表记下每次写入和拒绝，`canon events --follow` 每秒输出新事件（BR-2357）。
- 未处理的评审意见带档位和打开时间（`review_findings`）。
- 认领失效时写 `claim.holder-gone`（BR-2360）。
- 停滞的派发每次读的时候算（BR-2522）。

缺的只有机器容量，还有“已经开了多久”这类随时间变化、不产生事件的提醒。

Claude Code 的 Monitor 在后台运行一个命令，命令每输出一行就向会话发一条消息，会话空闲时也会被唤醒。输出太多时它会被自动停掉。每个 Monitor 最多运行 30 分钟，到期时向会话发一条通知，由会话重新挂上。Codex 没有 Monitor，但两边都有 SessionStart 和 PreToolUse hook。D-132 否决过用 Monitor 驱动目标模式，理由是 Monitor 判断不了目标是否完成。这次 Monitor 只负责转发 canon 已经算好的状态，不需要它自己做判断。

本机实测（2026-11-18，8 核，16 GB）：
- 18 个 `claude -p` 在运行，5 分钟负载 12.65；
- swap 总量 3 GB，剩余 1.3 GB；
- `kern.memorystatus_vm_pressure_level` 是 1（正常）。

worker 数已经超过 #258 估计的 8 到 10 个，机器没有出问题。macOS 的 swap 总量按需扩大，“剩余”只是已分配的 swap 文件里还空着的部分，每次扩容前都会跌到很低。负责人在 human #67 选了按内存压力判断，并补充「内存和cpu都需要」。

`canon work delegate` 只写派发记录，不启动进程。worker 进程由 delegate 之类的工具启动（`src/work/delegation/delegate.ts`）。

## 方案

1. 防止忘事的检查一律不挡工作，改成提醒；BR-2464 不再拒绝开工：采用。负责人的方向（#260）。D-126 否决“只提醒”的理由是：没人催时意见会越积越多。这次的提醒是主动推送的，会话空闲时也会被唤醒，每条带着已经开了多久，并且到时间会重复。以后新加的检查也按这条分类：只是防止忘事的做成提醒，保证 main 正确的才拒绝。
   - 来源：https://github.com/daniel1zz/canon/issues/260 “所有类似的情况都可以通过monitor处理”
2. 保留 D-126 的上限，另外再加提醒：否决。上限一到，和意见无关的工作仍然被挡住，正是 #260 要去掉的情况。
   - 来源：canon/decisions/D-126.md “或积压到 6 条，新变更就开不了”
3. 一份只读的待办清单（`canon work due`）算出调用者现在该处理的事，每件带下一步命令。三处使用它：
   - 长期运行的 `canon work watch` 只输出清单的变化和相关事件，宿主用 Monitor 挂着它；
   - `canon brief` 和 `canon work start` 把清单列出来；
   - 没有 Monitor 的宿主（Codex）靠这两处看到同样的内容。

   采用。“该处理什么”只算一处，怎样送到会话由宿主决定；会话空闲时只有长期运行的命令能唤醒它。
   - 来源：src/work/delegation/stall.ts “Worked out on every read, never stored”
4. 给 `canon events --follow` 加一个整理过的输出模式：否决。它定义的是原始事件流，除了认领失效以外不写事件，也不算状态。停滞、容量和“开了多久”都不产生事件，加进去等于在它里面再造一个 watch，读它输出的脚本也分不清两种行。
   - 来源：canon/rules/work/stats/BR-2357.md “才能及时看到；此外不写事件”
5. 只用宿主的 hook 推送提醒，不要长期运行的命令：否决。主会话等 worker 时是空闲的，没有工具调用就不会触发 hook，worker 死了没人知道。用 Stop hook 拦下会话来提醒，又会和目标模式的 Stop hook 互相干扰（D-132）。
   - 来源：canon/decisions/D-132.md “Stop hook 在目标没达成时让它接着做”
6. watch 在协调数据库里登记自己，`canon brief` 在没有 watch 运行时报警：否决。这只是把“忘了处理意见”换成“忘了挂 watch”。SessionStart 时 brief 提示挂上 watch，Monitor 到期时宿主自己会通知会话，这两处已经够了。
   - 来源：canon/decisions/D-132.md “Monitor 等的是后台进程的输出”
7. 机器紧张的判断：
   - 内存用系统自己的压力信号：macOS 读 `kern.memorystatus_vm_pressure_level`，warn 及以上算紧张；Linux 用 `/proc/pressure/memory` 的 `some avg10`，没有这个文件时用 `MemAvailable` 占总内存的比例；
   - CPU 用 5 分钟负载除以核数；
   - 内存和 CPU 任意一项超过就算紧张。

   采用（human #67）。压力信号是内核按回收和换页的实际情况给出的，平时稳定，真正不够时才变。
   - 来源：https://docs.kernel.org/accounting/psi.html “some avg10=0.00 avg60=0.00 avg300=0.00 total=0”
8. 按 swap 剩余低于 500 MB 判断内存紧张：否决（human #67）。macOS 的 swap 按需扩大，剩余量在每次扩容前都会跌到很低，造成误报；刚扩完容时剩余量又很大，会漏报。Linux 没配 swap 时剩余永远是 0，会一直判断为紧张。
   - 来源：https://github.com/daniel1zz/canon/issues/258 “tight when swap free < 500 MB”
9. 在 `canon work delegate` 拒绝，而且只拒绝新增 worker：采用。
   - 重新派发一个停滞的变更只是替换死掉的 worker，不增加负载，BR-2522 让主会话做的正是这一步，所以不算新增；
   - 占用名额的是生效、变更还开着、又没有停滞的派发；
   - 数名额和写派发记录放在同一个写事务里，两个会话同时派发时不会都看到同一个空位。

   拒绝放在 canon 里，而不放在启动进程的工具里，是因为每种宿主和工具都会经过 canon。
   - 来源：canon/rules/work/delegation/BR-2522.md “不自动重新派发，也不自动接手”
10. 数机器上的 `claude` 进程来决定名额：否决。会把和这个项目无关的会话也算进去。名额按本仓库的派发数算；整台机器的情况由内存压力和负载反映。
    - 来源：canon/rules/work/BR-2208.md “协调数据库在 git 公共目录下”
11. 待办清单和 watch 放进新子领域 `work/reminders`（代码 `src/work/reminders`）：采用。`work/session` 管开工和交接，已有 37 条规则；`work/stats` 只管原始事件流和统计；`work/watch` 是后台 floor 测试。提醒是一件独立的事：算出该处理什么，并送到会话面前。
    - 来源：canon/architecture.md “`src/work/watch`”
12. 测不到某个信号（Windows 上负载总是 0、没有压力信号的系统）时拒绝派发：否决。会让 canon 在测不到的平台上完全不能派发。测不到时照常派发，但输出一行写明哪个信号测不到，派发事件里也记下。
    - 来源：canon/rules/work/BR-2026.md “边界上的每次拒绝都带原因记进事件表”

## 决定

- 机器容量和派发时的拒绝：BR-2526。
- 待办清单：BR-2527。
- `canon work watch`：BR-2528。
- SessionStart 时提示挂 watch：BR-2529。
- 开工不再被评审意见挡住：BR-2530（它的 `will_amend` 列出要一并修改的规则）。

BR-2527 到 BR-2530 是计划中的规则，由后续变更实现。

## 后果

- 开工不再被评审意见挡住。意见有没有人处理，靠 watch 每 30 分钟的重复提醒（带已开时长），以及 brief 和开工时列出的清单。
- 最坏的情况：会话没挂 watch，又不看开工时列出的清单，意见就会堆着没人处理。能证明这个选择错了的结果是：去掉拦截以后，未处理意见的最长已开时长中位数比去掉之前长（从 `review_findings` 和事件表能算出来）。真出现这种情况时，加的是更强的提醒，不是恢复拦截。
- Codex 会话没有 Monitor，只能在 brief 和开工时看到清单。对它来说，提醒比原来的拦截弱。
- 两个主会话会收到同一条意见的提醒，可能都去处理。关闭意见时有冲突检查，第二个会被拒绝，所以不额外加归属。
- Linux 的两个阈值（PSI `some avg10` 达到 10，即最近 10 秒里至少有一个进程等内存的时间占 10%；或 `MemAvailable` 低于 10%）是起始值，没有实测依据，因为本机是 macOS。能证明它们定错了的结果是：在 Linux 上，`delegation.refuse` 记下的读数和合入测试成批超时的时间对不上。真出现时，调这两个数，不改信号。
- 5 分钟负载反应慢，一口气派出的几个 worker 都会通过负载检查；能挡住这种情况的是名额上限。
- 负载在容器里看到的是宿主机的核数，在那里可能偏松。
