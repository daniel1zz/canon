## 背景

delegate 起的 worker 是独立的 `claude -p` 会话，hook 输入里没有 `agent_id`。D-114 让 canon 按进程表或 `CLAUDE_DELEGATE_CHILD=1` 认出它，但 worker 还得自己在每条认领命令后面补 `--as <名字>`，名字由它自己定，漏了就被 hook 拒绝；`CLAUDE_DELEGATE_CHILD` 也只有 delegate 一家会设。负责人 2026-11-15 回答待答问题 #42（“canon 该怎么认出这种 worker？”）时，在三种做法里选了“派发方设通用环境变量”。这也是 #232（子 agent 只执行、设计留在主会话）区分主会话和 worker 的前提。

## 方案

1. 派发方设通用的 `CANON_SUBAGENT=<worker 名>`，canon 把它当 `--as`：采用。名字由派发方给，worker 不用记得补 `--as`，记账不会落到主会话名下；约定不绑定某一个工具，以后别的派发工具照设即可。
   - 来源：canon/rules/work/claims/BR-2468.md “hook 进程的环境里 `CLAUDE_DELEGATE_CHILD` 等于 `1`（`delegate run` 给 worker 设的，D-114）时也是 worker”
2. 只认 delegate 自带的 `CLAUDE_DELEGATE_CHILD`：否决。它只说明“是 worker”，不带名字，worker 仍要自己补 `--as`；别的派发工具也不会设这个 delegate 专用的变量。
   - 来源：canon/rules/work/claims/BR-2468.md “Re-run the same command with --as <your worker name> appended”
3. 认不出时也接受 worker 自己带的 `--as`，不再核对：否决。任何会话都能自称子 agent，主会话的认领和合入可以被记到随便一个名字下，记账不可靠。
   - 来源：canon/rules/work/claims/BR-2468.md “`canon` 命令本身照 BR-2023 不验证 `--as`”

## 决定

采用方案 1，见 BR-2495。

## 后果

- 原来按进程表和 `CLAUDE_DELEGATE_CHILD` 认 worker 的做法保留，用来认出没按约定设 `CANON_SUBAGENT` 的启动工具起的 worker。
- 派发方要在启动 worker 时设 `CANON_SUBAGENT`：delegate 要改，它的仓库另开变更。
- `CANON_SUBAGENT` 由谁设 canon 核对不了：会话自己设了它，就会被记成那个名字的子 agent。这和 `--as` 一样只防写错、不防冒充（BR-2023）。
