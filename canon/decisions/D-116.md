## 背景

codex:4bdb7ebf 审计 zhushenkongjian（2026-11-14）时，要按 canon 版本分组衡量每次迭代的效果，却只能按发布记录推断：事件表只有 id、ts、actor、kind、subject、detail、worktree，没有版本；长时间的后台任务还跨版本。canon 里唯一叫“版本”的是装进项目的 skill 文件的内容哈希（`canon update --check` 打印的 `version`），审计明确指出它不能代替引擎版本。PATH 上的 canon 是 `scripts/release.ts` 用 `bun build --compile` 构建、按 main 的提交发布的。负责人授权实施这一项。

## 方案

1. 发布构建时用 `bun build --define` 把发布的提交编进二进制，每条事件写进 `events` 的新列 `canon`，源码运行记 `dev`（按 BR-2475）：采用。每条事件都带，按版本统计只要一条 SQL；不增加运行时的开销。
   - 来源：src/kernel/build.ts “embedded at build time by”
2. 运行时读 `dist/` 指向的发布提交：否决。读的是现在发布的版本，不是这个进程启动时的版本，长时间的后台任务和发布交替时会记错。
3. 用 skill 内容哈希：否决。它只说明装进项目的文件是哪一版，引擎可能已经换了；审计也明确排除了它。
4. 只在少数事件（合入、测试、评审）的 detail 里记：否决。要一条条加，漏了就分不了组；放在一列里一次覆盖全部。

## 决定

采用方案 1：BR-2475。

## 后果

- 本次发布之前写的事件 `canon` 为空，按版本分组只能从这次发布开始；更早的照旧按发布记录推断。
- 评审命令取自哪个提交另记（`--again` 记在 `landed_reviews.reviewer`，BR-2449），不归这一列管。
