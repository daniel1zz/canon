## 背景

负责人提的问题：规则太零散，领域下面直接挂规则，中间没有东西。他举的例子是 `canon/rules/install/BR-2089.md`，说它「很明显属于 Update」，但 canon 里根本没有「Update」这个东西；一个业务应该由几条规则描述它的全部边界。后果是写新规则的人看不到这个业务已经有哪些规则，就写一条重叠的，之后改了其中一条、漏了另一条。

本仓库的事实（2026-11-11 在 `main`=ced5e59a 上实测）：

- `canon rule domains`：30 个领域，直接挂的生效规则数中位数 8.5 条，5 个超过 BR-2114 的 25 条提示（install 33、knowledge/review 33、knowledge/check 31、work/session 31、knowledge/documents 26）。这 5 个一直超着，提示没起作用。
- 负责人举的例子确实是一个业务横跨三个命令：BR-2081 讲 `canon install` 不覆盖项目改过的文件，BR-2084 讲 `canon update --check` 怎么算过期，BR-2089 讲「项目改过、canon 没有新版本」不算过期；三条互相点名（2081→2089、2084→2089、2089→2081），但都在 `install` 这一个平铺的目录里，没有名字把它们连起来。
- 同一个业务还会横跨领域：「基线怎么分成领域」这一个业务的 11 条规则分散在三个领域——`knowledge/documents`（BR-2114、BR-2115、BR-2317）、`knowledge/check`（BR-2006、BR-2116、BR-2117、BR-2118、BR-2318）、`knowledge/query`（BR-2007、BR-2113、BR-2120）。
- 规则会被塞长：BR-2084 的「规则」段是一个自然段，列了十几种过期项、点名十条规则，已经读不动了。它是在没有任何「不准新建规则」的拦截下长成这样的。
- 最近 120 个合入里 78 个没改任何规则文件，42 个改了 1 到 9 个（17 个改 1 个，16 个改 2 个）。所以「改到的规则要多写一行」落在大约三分之一的合入上，每次一到两行。

## 方案

1. **领域 README 加一个「业务」段列出这个领域管的业务，规则 front matter 写 `business:` 指向其中一个；`canon check` 只对本次工作新增或改动的规则双向核对（采用）**：业务是一个名字，不是一个目录，所以一个业务可以横跨命令（BR-2081、BR-2084、BR-2089 同属「更新策略」），目录不动，D-15 不受影响。README 是唯一的来源，所以不会凭空多出一个业务。核对什么、什么时候不报按 BR-2431，和 BR-2344 同一种棘轮：存量不迁移。写新规则的人在 `canon rule new` 和 `canon context` 上先看到这个业务现在有哪几条规则，正是会写重复规则的那一刻。代价：这份清单靠人维护，会写错、会过期，`canon check` 只能核对「指向的业务在不在清单里」，核对不了「分得对不对」；粒度也挡不住——可以把 33 条规则写成 33 个业务，检查照样全绿。粒度交给 BR-2009 的规则评审（它每次都拿到受影响领域的全文，包括 README）。
   - 来源：canon/rules/knowledge/check/BR-2344.md “在 main 分支的检出里（不在任何变更里）检查时，没有相关的文件，不报这一项。”
2. **按规则条数做棘轮：某个领域直接挂的规则超过上限后不再接新规则，除非同一次合入拆出子领域（否决）**：数的是规则文件数，所以它奖励把新行为塞进已有规则的「规则」段——不新建文件就不触发，而 `canon check` 看不见段落变长；BR-2084 已经是这样长成的，加了这个门只会更多。而且条数不等于业务数：`knowledge/check` 的 31 条是一个业务的多条边界（每多一种 finding 多一条规则），按条数拒它等于逼它按技术层拆，和 BR-2318 相反。出口（同一次合入把条数降下来）要求在「加一条规则」的变更里同时搬规则、建代码目录、搬代码、改 import，比原来的工作大得多。
   - 来源：canon/rules/install/BR-2084.md “缺少的或旧形式的会话 hook，BR-2087；缺少的 Bash 快照 hook，BR-2185；缺少的检查 `--as` 的 hook，BR-2343”
3. **只靠子领域目录承载业务：规则必须挂在叶子领域下，叶子领域就是业务（否决）**：目录是树，一条规则只能有一个家。负责人举的 BR-2081、BR-2084、BR-2089 按命令分会落进三个子领域，按策略分又要从 init、install、update、uninstall 各切一块；同一条业务的实现也会被切到两个代码目录（D-15 要求代码和领域一一对应）。业务是标签，不是位置。
   - 来源：.claude/skills/canon-domains/SKILL.md “In canon one domain is both, because code mirrors domains and the README `## 术语` is the vocabulary.”
4. **把 BR-2114 的提示改成 `canon check` 的发现，合入时拒（否决）**：改一个数字就能拦住 5 个领域，但拦的还是条数，方案 2 的两条毛病一条不少；而且它会让现在 5 个超标领域的所有在途变更立刻落地失败，拦住的是写规则本身，不是写重复的规则。
   - 来源：canon/rules/knowledge/documents/BR-2114.md “这只是提示，`canon check` 不报，合入不受影响。”
5. **向量检索找相近的规则（否决）**：负责人已经否决过，理由是靠引导而不是靠相似度；相似度也给不出「这个业务的边界是不是齐了」，只能给出「长得像的几条」。
   - 来源：canon/rules/knowledge/check/restatement/BR-2401.md “共有至少 10 个不同的四词片段”

## 决定

采用方案 1。

- 业务写在领域 README 的 `## 业务` 段里，规则用 front matter 指向它，写法和名字的范围按 BR-2430。
- `canon check` 核对哪些规则、报什么、什么时候不报，按 BR-2431；存量不迁移。
- 写新规则的人在 `canon rule new` 上先看到这个领域现在的业务（按 BR-2432），在 `canon context` 上看到每条规则属于哪个业务（按 BR-2007）。
- 跨领域的关联仍然靠正文里的编号引用和 `links`（D-90、D-95）：业务本身不跨领域，按 BR-2430。
- BR-2114 的 25 条提示保留原样，仍然只是提示。

## 后果

- 这条检查按 BR-2431 生效之后，最近 120 个合入里有 42 个会碰到它，每次多写一到两行。
- 现在开着的变更改到规则时会遇到这条检查，要补上 `business:` 和 README 的那一行。
- 写规则的测试 fixture 也要补：本仓库有 15 个测试文件、23 处规则模板、26 处领域 README 因此要加业务，不加就在它们自己的变更 worktree 里被这条检查拒掉。装了 canon 的项目第一次改到规则时会遇到同样的事。
- 存量的 480 条生效规则大多数不会有 `business:`，`canon context` 的标题行上它们不带业务标记；按业务分组的清单只在 `canon rule new` 的输出里。这个数字只会随着规则被改到而下降，不会一次清零。
- `canon check` 核对不了业务分得对不对，也挡不住把每条规则写成一个业务。这两件事只能由 BR-2009 的规则评审看出来，没有机械保证。
- 跨领域的业务（例如「基线怎么分成领域」横跨 knowledge/documents、knowledge/check、knowledge/query）表达不了，只能等规则搬到同一个领域；本次新建的 `knowledge/domains` 是它们以后的去处。
