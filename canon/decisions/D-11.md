---
id: D-11
title: 会话和合入者是否还活着，用进程探测判断，租约只兜底
status: accepted
---

## 背景

认领和合入队列原来只靠时间判断对方是否还在：认领租约 12 小时，合入者心跳超过 `lander_stale_minutes`（10 分钟）才算掉线。旧系统 lore 记下过同样的问题（ADR-033：被杀掉的 agent 的认领在整个租约期内看起来都是新的）。实际影响：

- 关掉的会话还占着认领 12 小时，别的会话接不了手（C-50 之后另一个执行者会被拒绝，这个等待更明显）。
- Claude Code 的 Bash 工具默认 2 分钟杀掉命令，排在别人后面的合入者经常在等待或合入中途被杀；被杀的合入者让后面所有人多等 10 分钟，被杀在 rebase 中途时 worktree 还停在 rebase 状态。

本机查证（2026-11-03）：Claude Code 给每个 Bash 调用设了 `CLAUDE_PID`，它就是父进程链上的 `claude` 进程；同一会话的子 agent 共用这个进程和同一个会话 id（事件表里多个并行子 agent 都记为同一个 `agent:<会话 id>`）。lore 的 SPEC-245 也查到同一个会话的所有运行共用一个 harness 进程。`ps -o lstart= -p <pid>` 在 macOS 和 Linux 上都能给出进程启动时间，pid 不存在时退出 1、没有输出。

## 方案

1. 只用时间租约（现状）：否决。死掉的持有者要等满租约或心跳超时，正是要解决的问题。
2. 进程探测（pid 加启动时间），时间租约保留作兜底：采用。只在能证明进程不在时提前释放，不会把活着的持有者误判为死；pid 被系统复用时启动时间不同，也能识别。
3. 会话结束 hook（SessionEnd）里释放认领：否决。lore 实测这类 hook 有约 16% 的运行没有触发（KN-821），被 `kill -9`、断电、终端直接关掉时根本不会运行；作为唯一机制不可靠。
4. 认领时沿父进程链找名字叫 `claude` 的进程：否决。依赖进程名，换了安装方式或包装脚本就找不到；`CLAUDE_PID` 是 Claude Code 自己提供的，再用祖先关系核实一次就够了。

## 决定

- 排队条目记下合入者自己的进程（canon 进程的 pid 和启动时间）。等待者看到前面条目的进程已经不在就立刻作废它（BR-2098）；读不到进程表时退回心跳超时。
- 合入者收到 SIGTERM 或 SIGINT 时停掉 floor、撤销做到一半的 rebase、把条目标成失败（`killed`）后退出（BR-2099）。`kill -9` 无法拦截，由上一条兜住。
- 认领记下会话进程：`CLAUDE_PID`，只有它是当前进程的祖先时才采用；同一个执行者之后的工作命令更新它。另一个执行者在这个进程已经不在时可以立刻接手，否则仍按租约（BR-2100）。
- 不在 Claude Code 里（人在普通终端，或其他 agent 工具）时认领不记进程，只按租约。

## 后果

- 关掉 Claude Code 之后，它持有的认领马上可以被新会话接手；被杀的合入者不再让队列空等 10 分钟。
- 进程探测只能分辨“会话”，分不开同一个会话里的子 agent：一个子 agent 结束了而主会话还在，它的认领仍要等租约或 `canon work stop --release`。这和 C-50 里执行者分不开子 agent 是同一个限制。
- 同一个 Claude Code 进程里换了会话（例如 `/clear`）时，进程还在、执行者却变了，新会话要等原认领被放开或租约到期。
- 每次认领和每次排队检查多跑一两次 `ps`，开销是毫秒级。
