## 背景

负责人问：领域是不是应该枚举，规则要用的业务没有对应的领域就先去加领域，这样是不是更容易控制；不然 agent 随意写领域会越写越多，可能好几个说的是同一件事却没有复用。

业务那一层已经是枚举：业务名必须先写进它所在领域 README 的 `## 业务`，指向没列进去的名字的规则被 `canon check` 拒绝（BR-2430、BR-2431）。没有枚举的是领域。

本仓库的事实（2026-11-12 在 main=824ced715 上实测）：

- 32 个领域。按每个 README 第一次提交的日期：11-02 两个、11-03 十四个、11-04 六个、11-05 五个、11-08 一个、11-10 一个、11-11 三个。爆发在最初定基线的两天，之后大约每天一个。
- 历史上只有一个领域被删过：`config`，D-63 把它和 `cli` 并成 `invocation`。所以「几个领域说的是同一件事」真发生过一次，代价是一次重划。
- 建一个领域已经有三道硬关卡：没有对应的 `<code_root>/<领域路径>` 目录时 `canon check` 报 `code-layout`（BR-2118）；没写进架构总览时拦截合入（BR-2352）；规则评审看到新的 README（BR-2009）。名字像技术层只给提示，不拦（BR-2317）。
- 这三道都在问「形式上齐了吗」，没有一道在问「是不是已经有一个一样的」。
- 最近建的 6 个领域里，4 个本来就有决策点名它（`knowledge/links`→D-90、`knowledge/domains`→D-96、`knowledge/check/restatement`→D-96、`work/remote`→D-65、D-38），2 个没有（`knowledge/review/findings`、`knowledge/plans`）。
- 阈值和判断的实测对比：BR-2114 的「直接挂的规则超过 25 条就建议拆子领域」是提示，install、knowledge/review、knowledge/check、work/session 四个领域从 11-03、11-05 起一直超着，到 11-12 没有一个因此动过。同一天，规则评审的 `restatement` 和 `duplication` 两条拦截标准在 C-472 拦了 3 次、C-482 拦了 2 次，每一次都指出了真的重复并被改掉。

## 方案

1. **新领域要有一条决策点名它（硬拦），新业务和已有业务重复由规则评审拦截，建领域前先把现有的摆出来（采用）**：两道拦截都照搬本仓库已经验证过的形状——「新增的东西必须在另一处被写出来」同 BR-2352，「说不清的事交给评审的拦截标准」同 BR-2367。决策天然要求写出被否决的方案，「为什么不复用已有的 X」正好填那一栏；实测最近 6 个新领域有 4 个本来就有决策，成本不高。业务的膨胀交给评审而不是数量：业务越多，新加的那个和已有的重叠越容易被看出来，而阈值只会在某个数字上发作一次然后被忽略。不新增任何要同步的地方。代价：评审多一条标准，提示长一点；加一个明显该加的子领域也要写一条决策。
   - 来源：canon/rules/knowledge/check/BR-2352.md “这次工作新增的，`canon check`、`canon work test` 和合入报告一条 `architecture-unlisted`（位置 `canon/architecture.md`），拦截合入，原因 `check`。”
2. **在 `canon/config.yaml` 里枚举领域，`canon rule domain` 只接受列表里的名字（否决）**：这份清单是规则目录、`<code_root>` 下的代码目录、架构总览之外第四处要同步的地方，而且它和前三处一样靠人维护、会过期；更要紧的是改 config 的还是同一个 agent，它是减速带不是关卡，挡不住「写了一个和已有的意思一样的新名字」。
   - 来源：canon/decisions/D-63.md “名字是症状，原因是规则放错了领域。”
3. **枚举，并且这份清单只有负责人能改（否决）**：控制最强，但每加一个子领域都要等人拍板，和「人只负责定方向、只回答留给人的问题」相反；基线的细分是干活的会话每天都在做的事，不是方向。
   - 来源：canon/product.md “人只负责定方向，只回答留给人的问题。”
4. **给业务数或每个业务的规则数设阈值，超了就报（否决）**：和 BR-2114 的 25 条是同一种东西，而那条提示被四个领域忽略了七到十天；阈值也判不出「这两个业务说的是同一件事」——把 25 条规则写成 25 个业务，任何数量阈值都是绿的。
   - 来源：canon/rules/knowledge/domains/BR-2114.md “这只是提示，`canon check` 不报，合入不受影响。”
5. **保持现状，只在建领域时多打几行提示（否决）**：提示该加，但只有提示就是方案 4 的结局；本仓库同一天的对比摆在那里，拦截改掉了重复，提示没有。
   - 来源：canon/rules/knowledge/review/BR-2367.md “有任何一条的 `criterion` 不是 `note`，结论就是 `block`，否则是 `ok`。”

## 决定

采用方案 1。

- 新增一个领域的合入里必须有一条决策点名它，按 BR-2446。
- 和已有业务说的是同一件事的新业务由规则评审拦截，按 BR-2447。
- `canon rule domain` 在建出领域之前先把现有的领域和它们的业务摆出来，按 BR-2115。
- 领域不在 `canon/config.yaml` 里枚举：规则目录就是那份清单，别处不再抄一遍。
- 不给业务数或每个业务的规则数设阈值。

## 后果

- 加一个领域比现在多一步：要么这次合入里有一条新决策点名它，要么已有的某条决策正文里写了它。实测最近 6 个新领域有 2 个会因此要多写一条决策。
- 规则评审多一条拦截标准，提示每次长几行；按 BR-2359，接近预算的领域会多分一次调用。
- 这条标准只看这次合入新加的业务，已经存在的业务不追溯，和 BR-2431 的棘轮同一种做法。
- 「两个业务说的是不是同一件事」没有机械保证，靠的是评审这一次判断；判错了会放过去，也可能拦错。拦错时按合入被拒的常规处理：改措辞让区别说清楚，或者合并成一个业务。
