title: 排他的身份是 worktree：执行者回到会话一级，不再给子 agent 注入身份
status: accepted
supersedes: D-17

## 背景

D-17（C-91、C-93）为了修 issue #23，让 PreToolUse hook（`canon hook pre-bash`）在子 agent 的每个 Bash 调用前加一行 `export CANON_ACTOR='agent:<会话>:<agent_id>'`，并往项目的 `.claude/settings.json` 里装一条放行规则 `Bash(export CANON_ACTOR='agent:*')`。合入后的代码评审发现 issue #26：这条规则里的 `*` 也能匹配空格和引号，agent 写出的 `export CANON_ACTOR='agent:x' GIT_SSH_COMMAND='...'` 也会被放行，等于替用户批准了任意环境变量。

负责人随后问：“我的意思是不是通过独立的子session上下文绑定的方式吗，怎么又通过export了”，指的是更早的做法：身份从所在的 worktree 推出来，不注入。又说：“或者你自己判断下，哪种更合适”，把判断交给了主 agent。

事实：

- canon 里一个变更就是一个 worktree、一个分支、一个认领，一个 agent 只做一个变更。认领挡住同一个执行者的 start 和 drop（C-87，BR-2011），所以两个 agent 不会通过 canon 进入同一个 worktree。
- 旧系统 lore 起初正是这样确定身份的（SPEC-047）：只看所在的 worktree 和分支，不存任何状态。它后来改成注入运行身份，是因为它要求每一次写入都归到一个经过证明的运行上（ADR-044、ADR-060），要做进程祖先链核对；canon 不要求这一点，它只需要排他（P4）和事后能分开谁做的（P6）。
- C-91 实测：装了 hook 后每个 Bash 调用多约 36 ms，主会话和子 agent 都一样。

## 方案

1. worktree 就是排他的身份：执行者回到会话一级（BR-2023），不注入任何东西；认领照旧挡住所有人，同一个执行者也被告知去做别的变更，而不是进入那个 worktree（BR-2011）；每条协调事件记下运行它的 worktree（BR-2131），统计时按 worktree 分开不同的 agent。采用。这和 lore 最初的做法一样：身份从环境推出，没有新状态，没有要装的 hook，也没有要放行的命令。
   - 来源：https://raw.githubusercontent.com/daniel1zz/lore/main/docs/requirements/spec/SPEC-047-session-seat-auto-briefing-worktree-aware-sessions.md “no new state, no config: linked-worktree test via git plumbing; actor from branch”
2. 保留 D-17：PreToolUse hook 给每个 Bash 调用注入执行者。否决：每个 Bash 调用多约 36 ms；放行规则太宽，已经出了 #26，收窄也要依赖 Claude Code 怎么拆分和匹配命令；没装 hook（或 PATH 上没有 canon）的项目里 #23 照样存在；它唯一多出来的能力是分开同一个 worktree 里的两个 agent，而这种情况 canon 本来就不允许出现。
   - 来源：canon/changes/C-91.md “所以每个 Bash 调用多约 36 ms”
   - 来源：canon/rules/cli/install/BR-2128.md “Bash(export CANON_ACTOR='agent:*')”
3. 照 lore 的做法：登记每个运行，注入身份，再在 canon 里沿进程祖先链核对。否决：lore 这样做是为了让每次写入都归到一个被证明的运行上，canon 面对的是互相配合的 agent，不需要防冒充；它还多一张登记表和每次调用的进程链遍历，而且仍然要注入。
   - 来源：https://raw.githubusercontent.com/daniel1zz/lore/main/docs/requirements/adr/ADR-060-a-bash-call-s-run-identity-travels-in-a-per-call.md “walks from itself up its ancestor chain”
   - 来源：https://raw.githubusercontent.com/daniel1zz/lore/main/docs/requirements/adr/ADR-044-run-identity-is-issued-by-lore-and-attested-by-the.md “Attested by the harness, never self-reported”
4. 回到 D-17 之前的现状：会话一级的执行者，事件不记 worktree。否决：排他已经由认领做到，但事后分不开同一个会话的几个子 agent（C-43 的实测和 `canon stats` 只能看到一个执行者），P6 的“谁做的”只到会话。
   - 来源：canon/decisions/D-11.md “事件表里多个并行子 agent 都记为同一个”

## 决定

- 删除 `canon hook pre-bash`、`canon work stop --takeover` 和 `agent:<会话>:<agent_id>` 这种执行者形式。`CANON_ACTOR` 里的 `agent:x:y` 只是一个普通的名字，不再解析。BR-2127、BR-2128、BR-2129 退役。
- canon 不再往 `.claude/settings.json` 里装 PreToolUse hook 和放行规则；`canon install`、`canon update` 把已经装进去的这两项删掉，`canon update --check` 把它们列为过期（BR-2130）。
- 认领照旧挡住每一次 start 和 drop，同一个执行者也一样；拒绝同一个执行者时，提示写明这个变更正在那个 worktree 里进行，不是在这个对话里开始的就换一个变更（BR-2011）。
- worktree 里的持有者检查（续期、停下、放开、合入，BR-2104）仍按执行者比较。执行者只到会话一级，所以同一个会话的任何 agent 进入别的 agent 的 worktree，都会被当成持有者。canon 假设 agent 互相配合，不阻止这种情况（这就是 #23 的边界）。
- 每条协调事件记下运行它的 worktree（BR-2131）。

## 后果

- 每个 Bash 调用少一次 canon 启动；项目的 `.claude/settings.json` 里不再有 canon 放行的命令，#26 不再存在。
- 同一个会话的两个 agent 如果不顾提示进入同一个 worktree，canon 分不开它们，也挡不住。前提是 agent 照提示做：start 被拒绝后去做别的变更。
- 按 agent 统计要用事件的 worktree 加执行者，而不是只看执行者；C-94 之前的事件没有 worktree。
- 主会话启动认领再派子 agent 进同一个 worktree 合入的做法又可行了：它们是同一个执行者。
