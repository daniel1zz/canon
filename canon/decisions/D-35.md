---
id: D-35
title: 评审拦截的去向由没参与的执行者对照拦截前后的代码判定，按判定者是 agent 还是人分开记
status: accepted
---

## 背景

`canon stats` 用“拒绝之后同一个变更合入时改动指纹变没变”判断一次拒绝拦得对不对（BR-2068）。2026-11-04 用事件表核对（事件 1 到 3177）：

- 第一条带改动指纹的拒绝是事件 163。它之后的拒绝全部判出了去向，唯一的 `unknown` 是事件 434：在主 checkout 里执行合入，没有变更编号，按 BR-2068 本来就是 `unknown`。之后的 `land.ok` 全部带指纹。其余 5 个 `unknown`（事件 38、52、60、89、101）都在指纹加入之前。所以指纹本身不用再修。
- 评审（`review`）拦截 26 次：`changed` 23、`same` 0、`unknown` 3。评审拦截之后作者一定会改规则或决策的文字，不改就过不了第二次评审，所以 `changed` 只说明“改了”，说明不了“拦得对”。
- 只改文字常常就是真问题的修复：例如事件 3057 拦下 BR-2244 的正文里混进了一段残片，修复只是删掉残片。“改了代码还是只改了文字”也区分不了两种情况。
- 拦截的材料都在：`review.block` 事件记着评审读的文档和每条意见，`land.refuse` 记着拦截时的改动指纹，`land.ok` 记着合入后的提交（`sha`），从事件 3063 起还记着合入前的 main（`base`）；更早的合入没有 `base`，但 main 只靠合入前移，前一条 `land.ok` 的 `sha` 就是这次合入前 main 的位置。合入保留了变更自己的每个提交，没有压成一个，所以在 `base..sha` 里能找到改动指纹等于拦截时指纹的那个提交，也就是拦截时的代码。

问题是：用什么判断“评审指出的是真问题”还是“为了过评审改了字”，谁来判断，结果放哪里，样本多少才算数。

## 方案

1. 维持现状，评审拦截照样按指纹算 `changed`。否决：评审拦截之后指纹一定会变，26 次里 0 次 `same`，这个数字对评审没有信息。
   - 来源：src/work/stats/stats.ts “the same change later landed with different code: the refusal caught something”
   - 来源：canon/changes/C-42.md “评审拦截之后，作者一定会改文字”
2. 只用拦截之后改了什么来判断：改了代码或测试算真问题，只改了规则文字算改字过关。否决：只改文字常常就是修复本身（规则写得自相矛盾、例子对不上、正文损坏），这种拦截恰恰是对的；反过来，为过评审也可能顺手改测试。
3. 用之后发生的机器事实判断：拦截涉及的规则后来被回滚、有 issue 指向它、很快又被别的变更改了。否决作为判定依据：这些事实说的是规则合入之后稳不稳，不是当时那次拦截对不对；真问题修好之后规则也可能因为别的原因再改，改字过关之后规则也可能再也没人动。事件表里也没有把 issue 和某次拦截连起来的记录。到复审日期如果判定样本够了，可以拿这些事实和判定对照，看它们有没有关系。
   - 来源：canon/changes/C-42.md “优先用之后发生的机器事实判定（被回滚、之后有 issue 指向它、规则很快又被改）”
4. 换一个模型对拦截前的文字重新跑一次评审，看它拦不拦。否决：重跑的仍是只读规则文字的评审，和被判定的对象是同一类判断，不是独立的证据；判断要看得到代码。
   - 来源：canon/changes/C-42.md “判断的 agent 必须能看到代码，不能只读同一份规则文字”
5. 由没有参与这个变更的执行者，对照拦截时的提交和合入的提交，判断这次拦截指出的是真问题（`real`）还是只是改字过关（`wording`），写一条 `review.verdict` 事件；判定者是 agent 还是人由执行者决定（BR-2023），两种分开统计、从不合在一起算；每一种不到 10 个判定时不给比例。采用：判定者能看到前后两版代码和评审意见；“谁判的”由系统记录，不让判定者自己填；agent 判定的偏差有研究记录，所以和人的判定分开，人的判定可以用来校准 agent 的。
   - 来源：https://arxiv.org/abs/2306.05685 “including position, verbosity, and self-enhancement biases, as well as limited reasoning ability”
   - 来源：https://arxiv.org/abs/2306.05685 “strong LLM judges like GPT-4 can match both controlled and crowdsourced human preferences well, achieving over 80% agreement”
   - 来源：canon/changes/C-42.md “用 agent 抽样时，结果必须标明来自 agent，不能和人的判断混在一起算”
6. 每次评审拦截都由负责人判定。否决作为唯一的判定办法：要占负责人的时间，而 canon 三天里就有 26 次评审拦截。负责人想判定时用方案 5 的同一个命令，记成 `human`。

## 决定

采用方案 5：

- `canon verdict pending` 列出当前判定者这一种（agent 或人）还没判定过、变更已经合入的评审拦截，每条附上拦截意见、拦截时的提交和合入的提交，判定者照着去读代码（BR-2253）。
- `canon verdict record <拒绝事件编号> real|wording --reason "<理由>"` 写一条 `review.verdict` 事件。判定者不能是这个变更的作者（在这个变更上写过判定以外任何事件的执行者；判定过同一变更另一次拦截的执行者不算作者）；同一次拦截，agent 和人各只记一次（BR-2254）。
- `canon stats` 按判定者分开报告判定结果，每一种不到 10 个判定时只报个数、不报比例（BR-2255）。`review` 那一行原有的去向不变，它仍然回答“之后改没改”。

## 后果

- 评审拦截有了第二种、和指纹无关的统计；`--json` 的输出不变（BR-2202 规定了字段），判定只在 `canon stats` 的文字输出里。
- 判定要花 token（agent）或负责人的时间。多久判一次、每次判多少、用哪个模型由负责人决定，在负责人决定之前不自动运行任何判定。
- 最少样本和放弃标准：agent 和人各自不到 10 个判定时不报比例；到 `review` 的复审日期（`check_reviews`）时，agent 判定不到 10 个就停止抽样、不再用这个办法；人和 agent 判过的同一批拦截有 10 个以上时，两者结论不一致超过 3 个就不再采用 agent 的判定。这两条目前没有程序强制，复审时对照 `canon stats` 的数字判断。
- 拦截时的提交靠指纹在合入的提交范围里找：变更被压成一个提交，或者 rebase 时解决冲突改了内容，就找不到，列出时写 `?`，判定者只能看合入的范围。指纹加入之前的拦截也是 `?`。2026-11-04 对真实数据试过：C-47、C-76、C-181 的拦截都找到了拦截时的提交，C-76 找到的正是评审拦截前的最后一个提交。
