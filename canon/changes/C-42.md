## 为什么

`canon stats` 的目的是回答“这个检查值不值得留”（P6、C-9）。现在 3 次评审拦截的去向都是 `unknown`，原因是它们发生在加入代码指纹之前。但还有一个更根本的问题：评审拦截之后，作者一定会改文字，所以按现在的算法，评审拦截永远会被算成 `changed`（拦对了），无法区分“真问题”和“为了过评审而改字”。

## 要改什么

- 先用新数据确认：指纹加入之后的拒绝是否都能被正确判定，修掉仍然判成 `unknown` 的情况。
- 对评审拦截单独设计判定方式，例如定期抽样，由一个没有参与该变更的 agent 对照拦截前后的文字判断拦得对不对，结果写回事件表；或者其他能区分“真问题”和“改字过关”的办法。在设计时决定并写成决策。
- 规则和测试。

落实（D-35）：

- `canon verdict pending`（BR-2253）：列出当前判定者能判、还没判的评审拦截，附拦截时的提交（按指纹在合入范围里找）和合入的提交。
- `canon verdict record <拒绝编号> real|wording --reason`（BR-2254）：写 `review.verdict` 事件，判定者种类由执行者决定，作者不能判，同一种判定者只判一次。
- `canon stats` 加一节按判定者分开的判定统计，不到 10 个不给比例（BR-2255）。
- 代码在 `src/work/stats/verdict.ts` 和 `src/work/stats/commands.ts`。

## 陷阱和假设

- 拦截时的代码靠指纹在合入的 `base..sha` 里找：合入保留了变更的每个提交，所以通常找得到；压成一个提交或 rebase 解决冲突时改了内容就找不到，写 `?`。
- `canon stats --json` 的字段由 BR-2202 固定，判定不进这个 JSON。
- 判定命令不能挂在 `canon stats` 下面做子命令：citty 把第一个不以 `-` 开头的参数当子命令名，`canon stats --since 5` 里的 `5` 会被当成子命令。所以是单独的 `canon verdict`。
- 多久判一次、花多少 token 留给负责人，这个变更不建任何定期运行的东西。

对比 lore 时补充（2026-11-03）：

- 优先用之后发生的机器事实判定（被回滚、之后有 issue 指向它、规则很快又被改），不用另一个 agent 的判断。lore 的 KN-825 里 94% 到 96% 的“人工判断”其实是 agent 写的，lore 自己的结论是这个数字不能用。
- 用 agent 抽样时，结果必须标明来自 agent，不能和人的判断混在一起算；判断的 agent 必须能看到代码，不能只读同一份规则文字（KN-287）。
- 事先写好最少样本数和放弃标准：canon 到现在只有 5 次评审拦截，几个月内算出的比例都没有意义（lore KN-823 的规格评审 AUC 只有 0.406，每类至少 10 个样本才算）。
- 检查拒绝按检查项分开记录由另一个变更完成，这里直接用。

## 核对结果（2026-11-04）

- 事件 1 到 3177 里第一条带改动指纹的拒绝是事件 163。它之后的拒绝全部判出了去向；唯一的 `unknown` 是事件 434（在主 checkout 里合入，没有变更编号，按 BR-2068 本来就是 `unknown`）；之后的 `land.ok` 都带指纹。其余 5 个 `unknown`（38、52、60、89、101）都在指纹加入之前。指纹这部分不用修。
- 评审拦截 26 次：`changed` 23、`same` 0、`unknown` 3，印证了“为什么”里的问题。

## 教训

- 用数据核对之前，以为“仍有 `unknown`”是指纹的问题；逐条算过才知道剩下的都在指纹之前或本来就没有变更编号 → 只靠文字：这是“先查数据再改代码”的习惯，没有可以检查的触发点。
