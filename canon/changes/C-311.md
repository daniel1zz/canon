## 为什么

D-58（C-309）的独立审查找出两处缺陷和两处缺测试：

1. 破坏性：`canon work land` 在 `moveMain` 之后、记 `land.ok` 之前被 `kill -9`，main 已经含有关闭提交，却没有终结事件。下一次 `land` 把它当成被杀掉的合入，撤回分支上的关闭提交并把排队条目标成 `abandoned`：main 说变更做完了，分支说还开着。信号路径（BR-2099）早就处理了“main 已经动过”，这条路径没有。
2. D-58 说入队前收到信号时处理函数补记 `land.killed`，代码在 `entry === undefined` 分支只撤回关闭提交、不记事件；现在靠“入队之前没有 await”才没出问题，一旦以后在入队前加了 await 就会出错。
3. BR-2309“入队前被杀、下一次合入撤回关闭提交并报出”没有测试。
4. BR-2308 里“进程还在 → running”没有单独的测试。

## 要改什么

- 判定合入者进程不在（interrupted）之后，先看这次合入的 HEAD 是否已经在 main 上：在，就是合入到了 main 只是没记结果。`status` 把它标成 `landed`（不当成有遗留物的 interrupted）；下一次 `land` 不撤回关闭提交、不放弃条目，把条目标成 `landed`，补记 `land.ok`（带 `recovered: true`），说出“上一次合入已经到了 main”，释放认领（--finish）并结束，不再重新合入。改 BR-2308、BR-2309、BR-2310 和 BR-2307（终结事件里 `land.ok` 可以是补记的）。
- `entry === undefined` 的信号分支也记 `land.killed`；D-58 的文字改成实际顺序。
- 补 BR-2309（入队前被杀）和 BR-2308（running）的测试。
- 非阻塞：D-58 加一句“卡住但进程还活着的合入一直是 running”；`interrupted.ts` 里按 `worktree = ? OR subject = ?` 匹配终结事件，加 `// reason:` 说明。

## 陷阱和假设

- 补记 `land.ok` 而不是 `land.interrupt landed:true`：stats（合入数、拒绝之后的结果）、红 main 的修复判定（`fixLandedIn`）、`earlierLandings` 都只认 `land.ok`。补记的没有 `base` 和 `diff`，这些消费者本来就把缺这两项的 `land.ok` 当成“不知道”。after_land 命令没有跑过，信息里说明。
- 判定“已在 main”用 HEAD 是 main 的祖先，并且这个进程在队列里有过条目；没有 rebase 进行中。一个分支没有任何自己的提交时在 floor 里被杀，也会被当成已合入（它本来就没有东西可合）。
