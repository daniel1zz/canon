## 为什么

D-159 第 2 步。第 1 步（C-678）让类型能声明字段的格式和 `due: create`，但新建命令还不要求它们：会话建变更时忘了写 `owner_gate`（#293）、建规则时忘了写 `business`，都要等到后面的检查才发现。负责人选的是“声明+按步表态”：新建文档的那一步就要求会话对这些字段表态，变更的 `owner_gate`、`advances`，规则的 `business`，决策的 `amends`，版本的 `features` 和其余类型的字段都一样（2026-11-21）。

## 要改什么

- 内置类型在代码里声明新建时表态的字段（BR-2623）：变更 `owner_gate`、`advances`，规则 `business`，决策 `amends`（改或取代别的决策时还有 `revised_because`），版本 `features`，质量标准 `aspect`、`judge`、`covers`。
- 新建命令（`rule new`、`decision new`、`change new`、`work start --title`、`note new`、`release new`、`feature new`、`quality new`、`doc new`）接受 `--set <字段>=<值>`（可以写多次，BR-2382 为它开例外）和内置字段的同名参数；缺字段或格式不对时退出码 2，不分配编号，一次列出所有问题，规则的 `business` 列出领域的业务（BR-2620）。
- 新建命令只写拿到的字段，不再写空值（BR-2054、BR-2619）。
- 读文档：`owner_gate: "none: <理由>"` 不算关卡（BR-2615），`amends`、`features` 可以写 `none: <理由>`（BR-2512）；`canon doc set` 对内置字段用同一套检查。
- `canon work start --fix-main` 开的变更由 canon 写上两个 `none: <理由>`（BR-2623）。
- 工作说明、skill、README 和提示里的新建命令示例补上这些参数。

## 陷阱和假设

- 第 3 步（BR-2624：合入时本次新增的文档缺字段就拒绝）上线时，已经在做的变更的文件只在它自己的分支上，算“新增”；它们和其中新建的规则、决策都是在本步之前建的，没有这些字段。第 3 步必须给上线前建好的文档一个过渡办法，否则 canon 和 zhushenkongjian 里每个在做的变更第一次合入都会被拒（旁注 2026-11-21）。
- 库函数 `start()`、`createDoc()` 不检查这些字段，测试和 canon 自己的流程直接调用它们；只有命令行入口检查。
