## 为什么

#167：变更为自己的功能或修复新加的规则、回归测试，被会话写进 `## 教训`（“固化在 BR-n”），评审就提示要负责人确认，会话于是去问负责人，其实没有需要确认的事（另一个项目一天 8 次）。三处 canon 自己的文字把会话推向这样做：新建变更的模板说“教训 → 现在由哪条规则、检查或命令保证（写编号）”；合入评审对“本次合入新增的规则、检查或命令作为机制、又没写负责人确认”的教训给提示（BR-2162）；合入后的提醒说“能成为机制的教训先问负责人”（BR-2163）。D-24 没有说变更自己的规则不算教训。

负责人 2026-11-09 定了（canon human #8，“不算（推荐）”）：变更为自己的功能或修复写的规则和测试不算教训，不用问他。

## 要改什么

- 教训只指对流程或工具的认识，并且可能做成超出本变更的机制（规则、检查、命令、hook、skill）。变更为实现自己的功能或修复自己的缺陷而写的规则、测试、检查不是教训，不写进 `## 教训`，也不需要负责人确认。
- 新决策修订 D-24（amends），写明这个区分和负责人的选择。
- 改 BR-2162（评审提示只针对流程或工具的教训；变更自己的规则不提示）、BR-2163（提醒的措辞）、BR-2037（模板里 `## 教训` 的提示文字），各有两侧例子：为自己的修复加的规则 → 不提示；为“以后所有变更都要 X”加的检查、没写负责人确认 → 提示。

不做：不改关闭变更必须填写教训（BR-2161）；不改“只靠文字却没写原因”的提示。
