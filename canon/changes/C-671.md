## 为什么

D-156 第一部分：主 agent 决定自己做还是派出去时，要看得到和在做的活有没有牵连、设计有没有定；主会话自己的子 agent 认领事先建好的变更时不该先被“未派发”挡一次。

## 要改什么

- 让 BR-2608、BR-2609、BR-2610 生效，BR-2498 写明 BR-2610 的例外。
- `src/work/delegation/notices.ts`：契约里的规则、共用规则的提示（开工和派发）、设计没定的提示（派发）。
- `src/work/delegation/implicit.ts`：认出主会话自己的子 agent，替会话派发；`delegate()` 加 `implicit`，不按机器容量拒绝，事件带 `implicit: true` 和 `by`。
- `src/work/session/session.ts`：开工时先做隐式派发，成功后输出共用规则的提示。
- 规则按实现写准：提示和开工、派发的其它提示一样在标准输出；“设计没定”是被修订的规则在 main 上的文字还没提到计划中的规则。

## 陷阱和假设

- 隐式派发在认领之前写；之后的开工步骤（建 worktree、setup）失败时，派发留着，和先 `canon work delegate` 再开工失败一样，由设计负责人 `canon work take` 或重新派发。
