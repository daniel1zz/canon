## 为什么

issue #250。合入证据门（BR-2241）要求要执行的规则有“一个改动的、会运行的、名字点名这条规则的测试行”，改动的行是什么内容不看。只加注释也算，方式记 `test`，和真的改了断言或执行语句的一样。

复现：zhushenkongjian 的 C-891、C-892 改了 BR-452、BR-1078 的 `## 例子` 和 `## 规则`，评审判为行为改动，合入被拒；会话在点名这两条规则的测试里各加了两行 `#` 注释（提交 38eee8ee7、ebd6cdd34、dd2abae7e，三个提交都只有注释），合入就过了，通过记录写 `test`。真正的证据是已有断言加 `## 变异证据` 的变异测试，变更文件里写了，但记录看不出来，之后读记录的人会把它当成新的行为证据。

负责人 2026-11-18 定的方向（在 #250 的三个方案里选了“单独记录方式”，没选“不算证据、直接拦下”和“不改、记成决策”）：照样放行，但这种证据单独记一种方式。

## 要改什么

想要的行为：

- BR-2241 第 1 种证据（`line` 齐全的报告）里，归给某个点名规则的 `testcase` 的改动行，如果每一行（新一侧的行；删除点算给后面那一行的情况，按被删掉的旧行看）去掉首尾空白后都是空行或注释行，方式记 `test-comment`；只要有一行不是，记 `test`。同一条规则在这次合入里既有 `test` 又有 `test-comment` 的测试，记 `test`。
- 注释行按测试文件的扩展名认：`#` 开头（`.py`、`.gd`、`.rb`、`.sh`），`//` 开头（`.ts`、`.tsx`、`.js`、`.jsx`、`.go`、`.rs`、`.swift`、`.kt`、`.java`、`.c`、`.cc`、`.cpp`、`.cs`），`--` 开头（`.lua`、`.sql`）。列表写在规则里。不在列表里的扩展名，所有非空行都按代码算（记 `test`），规则写明这一点，不是悄悄退回。块注释（`/* */`、`"""`）的中间行不认，按代码算，规则写明。
- `test-file`（报告没有 `line`，退到文件一级）不变：它本来就不看行。
- 通过记录里的方式多一种 `test-comment`（BR-2237 的方式列表、`PassMethod` 类型、`passes:` 的读写和 `canon check` 对方式取值的检查都要认它）。合入输出说明这条规则的证据只是注释，让会话和评审看得到。
- 证据门的放行结果不变：`test-comment` 和 `test` 一样算有证据。

要改的规则：BR-2241（加 `test-comment` 和注释行的认法、例子），BR-2237（方式列表）。动手前 `canon context src/work/execution` 和 `canon search "test-file"` 找出所有列举了方式的规则和读方式的代码（例如 `canon release status`、`canon verdict`、统计），都要认新方式。

回归测试：

- 只在 `test("BR-1: …")` 里加一行 `// note` → 有证据，方式 `test-comment`；
- 同一测试里加一行注释和一行 `expect(...)` → 方式 `test`；
- `.gd` 文件里加 `# note` → `test-comment`；扩展名不在列表里的文件加 `# note` → `test`；
- 报告没有 `line` 的文件 → 仍是 `test-file`。

不做：

- 不拦只改注释的合入，不要求基线上红绿验证（human #37、#197 已决定不做）。
- 不解析块注释、字符串里的 `#`、或语法树。
- 不改措辞路线（BR-2243）和验收路线。
