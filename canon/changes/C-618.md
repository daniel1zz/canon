## 计划

| 步骤 | 内容 | 依赖 |
|---|---|---|
| A | 声明和读取：文档类型给段落声明项的格式模板（槽位和分隔，槽位类型：自由文字、文档编号、编号列表、取值表、样式），内置类型的声明写在代码里，项目在 `types:` 里给自己的类型声明、给内置类型的其他段落加声明；一个匹配器按声明读出每一项的槽位，读不出的项记为未知；声明过的非文字槽位在算行为哈希前去掉；`canon check` 按每条声明写的处理方式提示或报告；读出的元信息有 JSON 导出 | - |
| B | 内置声明和迁移：给内置类型写声明（变更的教训去向、决策方案的采用和否决及其来源子项、规则例子的编号、版本和模块的成功标准）；改写命令把文档改成声明的写法，写不出的项列出来、不猜；canon 仓库一次迁移成一个可以整体撤回的提交，迁移前后每条规则的行为哈希不变；其他项目升级后运行同一个命令得到同样一个提交 | A |
| C | 教训：`canon overview` 的等负责人列出去向是待负责人确认的教训；接手暂停的 C-617，把它的专用解析器换成读声明 | B |
| D | 决策方案：BR-2109 改为读采用和否决的槽位，删掉排除“不采用”的正则；来源核对（BR-2111）读来源子项 | B |
| E | 规则例子：编号由 canon 分配、删掉的不复用；测试标题写 `BR-n#eK` 点名一条例子；`canon check` 算出没有测试点名的例子；评审的 `untestable` 只判断例子之外的部分（#265）；先在一个领域试，再推到全部 | B |
| F | 成功标准：`src/knowledge/releases/criteria.ts` 换成读声明，行为不变 | B |

C、D、E、F 互不依赖，可以同时做；每一步开工时先写自己的规则（canon-rules），本变更只定方向（D-144）。

## 为什么

程序要判断的元信息散在正文里，各写各的解析：决策方案的采用和否决靠正则猜（#48）；教训的去向没人读，约 31 条待负责人确认的教训负责人看不到；规则例子有没有测试只能让模型判断（#265）。负责人定的方向是把元信息抽出来标准化，并且作为设计文档类型时的机制，项目自己的类型也能用（D-144）。

## 要改什么

按上面的计划分步做；本变更只合入方向：D-144。各步的规则在开工时写，`status: planned` 的规则随实现变成 active。

## 教训

- 设计前让看不到推荐的子 agent 挑战一次，发现了“往例子加标记会让约 540 条规则的通过记录和引用指纹一起失效”这个我漏掉的问题 → 由 canon-design 第 3 节的挑战要求保证（已有机制）
- 写决策来源时凭印象写的两段引文都不是原文，合入前逐字核对才发现 → 由 BR-2111 合入时的来源核对保证（已有机制）
