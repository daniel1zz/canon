## 为什么

baseline 核对发现 `canon human answer` 的两个漏洞（issue #56、#57）：

- `human:` 操作者在没有 TTY 时带 `--relayed ""`，命令层把它当成“给了转述”跳过 TTY 检查，`answer()` 又把空原话当成没给，于是记成了人直接回答（#56）。
- TTY 检查在命令层、`answer()` 之前就退出，agent 不带转述的回答（最常见的情形）没有写 `human.answer.refuse`，违反 BR-2026（#57）。
- 同一个问题第二次回答被拒绝时也不写事件。

## 要改什么

- 所有拒绝都在 `answer()` 里判定：命令把“stdin 是不是终端”传进去；`relayed` 只在没给 `--relayed` 时是 undefined，人带空的 `--relayed` 也算带了。
- 每种拒绝写一条 `human.answer.refuse`，原因各不相同：`human-relayed`、`no-tty`、`not-human-no-relay`、`answered`、`not-found`。
- 规则：BR-2021 写明每种拒绝的原因和新例子；BR-2040 写明再次回答和不存在的问题的事件。
- 测试：通过 CLI 覆盖每种拒绝；用 script(1) 给出终端，覆盖人在终端里直接回答（BR-2021 例子 3、4）。

## 教训

- 拒绝分在命令层和领域函数两处判定，命令层那份就漏写事件 → 现在由 BR-2021 的 CLI 测试保证每种拒绝都有事件；“拒绝只在领域函数里判定”只靠文字：没有检查能看出命令层提前退出。
