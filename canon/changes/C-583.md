## 为什么

goal 机制（让 AI 一直朝目标做、及时校准方向）要建在一个靠得住的目标上，负责人 2026-11-17 指出现在的目标靠不住：版本中途会调整（“某些版本的某些功能不做了，或者提前了，或者合并了”），而“一个release是多个功能模块”、组合版本“本质上就是组合功能模块”；canon 里没有模块，挪一个功能要分别挪范围、成功标准和规则，取消版本只能删文件；zhushenkongjian 的 `R-2` 到 `R-5` 全是 planned “本身就是问题”：没有命令把版本标成进行中，规则都通过了也不提示。另外，合入后评审意见 #159 问谁能把成功标准判成已满足。最初设计成每次改目标都要负责人确认，另一个会话指出连迁移、改错字都要问，负责人说“应该给ai更多主动权”。

负责人的选择：取消版本加 `dropped` 状态（问题 #51），组合关系记在版本文档里、版本列出模块（问题 #52）。整体拆成三个变更：本变更（模块和组合），之后是校准（成功标准编号、变更写 `advances`、总览按模块展开）和驱动（`canon goal` 和 Stop hook）。

## 要改什么

- D-130：版本由模块组合、取消用 dropped、改目标要负责人确认，以及否决的方案。
- 模块：新的内置文档类型 `feature`（`F-n`，状态 active、dropped），`canon feature new/list/drop`（BR-2507、BR-2513）；规则的 `feature` 标签，“标着版本的规则”包括版本模块的规则，`canon release status/ship`、冻结、`canon show` 都按这个范围（BR-2509）。
- 版本：状态加 `dropped` 和 `merged_into`（BR-2321），`canon release start`、`canon release drop --into`（BR-2508、BR-2511），列表默认不列已取消的（BR-2320）。
- 检查：组合不成立、还引用已取消的版本或模块（BR-2512），已发布版本的模块冻结（BR-2515），规则已通过的 planned 版本给提示（BR-2514）。
- 合入：改了成功标准、组合或取消版本和模块照常合入并列出改动，杂务不能改目标；只有让成功标准离开待负责人，要变更的 `owner_answers` 里有为这个变更问过、已回答的问题（BR-2510），由此修掉意见 #159。
- 总览和会话开头的摘要列出最近 7 天 main 上改了目标的提交（BR-2505、BR-2506），从 git 历史算。

## 陷阱和假设

- 规则上原有的 `release: R-n` 继续有效，和 `feature` 不能同时写；zhushenkongjian 的迁移是那个项目自己的变更。
- 合入后的规则评审不读 `canon/features` 下的文档，另提 issue。
- BR-2510 只按文字对应成功标准；成功标准编号在下一个变更里加，加编号只改文字前缀，所以那时要把编号从比较里去掉（它会说明）。
