## 为什么

删除 worktree 时有两种情况会悄悄丢东西或弄坏别的会话：

- 判断“干净”用的是 `git status --porcelain`，它不显示被 git 忽略的文件。实测（git 2.50.1，临时仓库）：worktree 里只有被忽略的 `.env` 和 `node_modules/` 时，`git status --porcelain` 输出为空，不带 `--force` 的 `git worktree remove` 照样退出 0，把 `.env` 一起删掉；有未跟踪的普通文件时它才拒绝（退出 128）。所以 `canon work clean` 会删掉只存在于 worktree 里的 `.env` 之类的文件，`canon work drop` 用 `--force` 更是什么都删。
- 另一个会话的 shell 或进程可能还把当前目录放在这个 worktree 里，删掉之后它的命令全部失败（旧 lore SPEC-171 D3 用 `lsof` 检查过这一点）。

## 要改什么

- `canon/config.yaml` 新增平铺的 `regenerable`（D-3 的形状）：能重新生成的被忽略文件或目录名，按路径的每一段匹配，可以用 glob；配置了就取代默认列表（`node_modules`、`dist`、`build` 等，见 BR-2019）。
- `canon work clean`：被忽略的文件里有不在 `regenerable` 里的，保留这个 worktree 并列出这些路径；有别的进程的当前目录在 worktree 里，保留并写明 pid 和命令名（macOS 用 `lsof -d cwd`，Linux 读 `/proc`）；查不出进程时也保留并写明原因（BR-2019）。
- `canon work drop`：不能重新生成的被忽略文件算会丢的东西（`ignored: <路径>`）；有进程在 worktree 里时什么都不删，退出码 5（BR-2064、BR-2065）。被忽略文件的存档由下一个变更（存档后删除）处理。

## 陷阱和假设

- `git ls-files --others --ignored --exclude-standard --directory` 把整个被忽略的目录列成一行 `dir/`，所以 `node_modules/` 不会展开成几万行；也因此一个整体被忽略、里面放着 `.env` 的目录会整个算作不能重新生成，这是偏安全的一侧。
- macOS 的临时目录是 `/var/...` 的符号链接，`lsof` 报的是真实路径，比较前要先 `realpath`。
- 进程检查只看当前目录，不看打开的文件；一次 `clean` 只跑一次 `lsof`。
