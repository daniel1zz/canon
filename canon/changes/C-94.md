## 为什么

C-91、C-93（D-17）为了修 #23，让 PreToolUse hook 给子 agent 的每个 Bash 调用注入 `CANON_ACTOR='agent:<会话>:<agent_id>'`，并装了一条放行规则。合入后的评审发现 #26：放行规则 `Bash(export CANON_ACTOR='agent:*')` 太宽，agent 写出的 export 行可以顺带设置 `GIT_SSH_COMMAND` 之类的变量而不经用户确认。负责人问为什么要靠 export 注入身份，而不是按更早的做法从所在的上下文推出来，并把判断交给主 agent。判断结果（D-18）：canon 里一个变更就是一个 worktree、一个分支、一个认领，一个 agent 只做一个变更，所以排他的身份就是 worktree，不需要注入任何东西。

## 要改什么

- 删除 `canon hook pre-bash`（`src/cli/install/prebash.ts`）、`canon work stop --takeover` 和 `agent:<8>:<agent_id>` 的解析与一致性检查；`CANON_ACTOR` 的值是不透明的名字（BR-2023）。BR-2127、BR-2128、BR-2129 退役。
- `canon install`、`canon update` 删掉项目 `.claude/settings.json` 里 canon 撤回的 PreToolUse hook 和放行规则，`update --check` 把它们列为过期，其余内容不动（新规则 BR-2130；BR-2084、BR-2087 恢复到 C-91 之前并引用 BR-2130）。canon 自己的 `.claude/settings.json` 在这个变更里用 `canon install` 改好（恢复到 C-93 之前的内容），不再单独跑一次 `canon update`。
- 认领拒绝同一个执行者时，提示不再让它进入那个 worktree，而是说明变更正在那里进行、不是在这个对话里开始的就换一个变更（BR-2011）。
- BR-2104 写明边界：执行者只到会话一级，同一个会话的 agent 进入别的 agent 的 worktree 就算持有者，canon 假设 agent 互相配合，不阻止。
- 事件表加 `worktree` 列，每条事件记下运行它的 worktree（新规则 BR-2131，按 BR-2078 补列）。
- 决策 D-18，取代 D-17。
- 规则 README（cli/install、work、work/claims）恢复并改写。

## 陷阱和假设

- 撤回的条目只认 canon 写过的形式：PreToolUse 里以 `canon hook pre-bash` 开头的命令（任何 matcher），和完全相同的那条放行规则；用户自己写的相似规则不动。
- C-94 之前的事件 `worktree` 为空；按 agent 统计只能从这次以后算。
- 这个变更合入后，主 checkout 的 `.claude/settings.json` 不再有 PreToolUse hook，正在运行的会话里子 agent 的执行者变回 `agent:<会话>`；合入前由 `agent:<会话>:<agent_id>` 持有的认领，要等租约到期、会话进程退出，或由同名执行者放开。
- 假设 agent 照拒绝提示去做别的变更；同一个会话的两个 agent 硬要进同一个 worktree，canon 分不开也挡不住（D-18 后果）。
