## 为什么

负责人要“一个类似goal的机制可以让ai一直朝着目标完成”，驱动“应该是主动调用cli的方法才会执行”，关键是“能及时校准ai是否在朝争取的方向进行”，提醒给 AI 看、不定期问负责人。C-582 到 C-584 已经让目标看得见（总览、版本由模块组合、成功标准编号、变更声明推进哪条），这个变更让它驱动会话：开了目标的会话要停下时，canon 看目标达成了没有，还有能做的就让它接着做。

## 要改什么

- D-132：为什么用会话主动开启加 Stop hook，否决 Monitor、`/loop`、对所有会话生效和让模型判断有没有进展。
- 新子领域 `work/goal`：`canon goal start/stop`、不带子命令显示目标（BR-2518），按会话身份记在协调数据库的 `goals` 表。
- `canon goal check --hook`（BR-2519）：没目标放行；全部满足就结束目标；只剩负责人的事放行；连续三次停下都没进展放行；否则拦下，写明还没满足的成功标准、谁在推进、下一步和偏离提醒。读不了项目也输出放行的 JSON。
- 安装：Claude Code 的 `hooks.Stop`（BR-2520）和 Codex 的 Stop（BR-2459），canon 仓库自己的设置一起更新。

## 陷阱和假设

- 两个宿主的 Stop hook 都靠标准输出的 `{"decision":"block","reason":...}` 让会话继续（Codex 文档 https://learn.chatgpt.com/docs/hooks 原文 “Codex continues and creates a new continuation prompt, using your `reason` as that prompt's text”），Codex 要求 Stop hook 必须输出 JSON，所以每条路径都输出一个对象。
- PATH 上的 `canon` 是主 checkout 的 `dist/canon`；没重新构建前 `canon goal` 不存在，hook 走 `|| echo` 的后备，放行。
