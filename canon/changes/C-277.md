## 为什么

D-50 的最后一次独立质疑复现了两个问题，都是拿当前 worktree 比，而 main 已经往前走了：

- 旧 worktree 里 `canon change list`（不带 `--all`）把已经合入、分支留着的变更（本仓库的 `change/C-146`、`C-148`、`C-237`）列成 `closed on branch, not landed`，排在“已开始”一组；agent 取了它，`canon work start` 退出码 2。主 checkout 的 brief 按 main 判断，两处列的不是同一组（BR-2149）。原因：`src/work/session/inflight.ts` 只拿当前 checkout 的变更判断“分支上的是不是 main 没有的”。
- 负责人在 main 上删掉清单里一行失效编号后，所有没 rebase 的旧 worktree 里 `canon check`、`canon work test` 都报 `ref-dangling` 失败，虽然它们没碰清单。原因：“已经列过”只看 main 的最新提交，和 worktree 里的旧清单比。

## 要改什么

- BR-2291、BR-2294：只在分支上的变更按 main 的最新提交判断，main 上已经有这个编号就不从分支列；BR-2294 加旧 worktree 的例子。
- BR-2150：编号在 main 最新提交的清单或这个 checkout 起点（`git merge-base HEAD main`）的清单里出现过，就只提示不拦截；加“main 删了那一行、worktree 没 rebase”的例子。
- BR-2149：brief 待办行提示取第一个 `unclaimed, not ambiguous` 的。
- D-50（仍是 proposed）：后果里写全哪些命令多跑 git 调用，以及按 main 判断的理由。
- 代码：`src/work/session/inflight.ts`（`changeIdsAt`、`listedBefore`），`canon check` 和 `canon work test` 改用 `listedBefore`，brief 的提示文字。合入检查（`src/work/land/checks/steps.ts`）不动：合入先 rebase 到 main，起点就是 main。
