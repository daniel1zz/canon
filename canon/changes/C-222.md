## 为什么

#25（C-90 合入后的代码评审）：`ensureGuard` 先用 `guardStatus` 判断 hook 是“缺少”还是“旧版本”，之后 `renameSync` 不再核对，直接替换那一刻在 hook 路径上的任何文件。判断和替换之间，别的工具（比如同时运行的 lefthook、husky 安装）或人写进去的 `reference-transaction` 会被 canon 的守卫换掉，退出码 0，没有任何提示。这违反 BR-2124（别人的 hook 永远不覆盖，退出码 5）。

## 要改什么

- 代码（`src/cli/install/githook.ts` 的 `ensureGuard`）：
  - “缺少”：临时文件写好、设为可执行后用 `link(临时文件, hook 路径)` 放上去。这一步是排他的：路径上已经有文件时失败（EEXIST），不会替换任何东西。失败后重新判断：已经是当前的守卫就算成功；是别人的就按 BR-2124 退出码 5；是 canon 别的版本就退出码 5，提示再运行一次。
  - “旧版本”：先把 hook 路径上的文件改名挪到旁边（改名是原子的，挪走的正是那一刻在路径上的文件），再核对挪走的文件仍然是 canon 写的（普通文件、第二行是标识行）。是 canon 的：用排他的 `link` 放上新守卫，删掉挪走的旧文件。不是 canon 的：用排他的 `link` 放回原处，退出码 5；放回时路径上又有了文件，就把挪走的文件留在原地、提示里写明它的路径，什么都不删。
  - 测试用的注入点：`ensureGuard` 可选的第三个参数在判断之后、替换之前调用，测试在这里写进别人的 hook 模拟竞争。
- 规则：BR-2124 写明判断和写入之间出现的别人的 hook 也不覆盖，补两侧的例子；BR-2123 把“同时运行的 git 只会看到旧的或完整的新 hook”改成按状态写清：缺少时 git 只会看到没有 hook 或完整的新 hook；旧版本时有一瞬间（挪走和放上之间）看不到 hook。
- 决策：新决策记下“旧版本”状态的做法和被否决的原子交换。
- 测试：`src/cli/install/githook.test.ts` 加 BR-2124 的竞争用例（缺少、旧版本两种状态），去掉修复后会失败。

## 陷阱和假设

- 不支持硬链接的文件系统（比如把 `core.hooksPath` 指到 exFAT 盘上）上 `link` 会失败，这时以环境错误（退出码 4）停下并写明原因，不退回会覆盖的写法。
- “旧版本”状态的挪走和放上之间，同时运行的 git 看不到守卫，这一瞬间直接移动 main 不会被拦。这是有意的取舍（见新决策）：丢掉别人的 hook 无法恢复，漏拦一次直接提交能从 git 历史里看到。
- 判断“是不是 canon 的”只看标识行，不比对和第一次读到的内容逐字相同：另一个 canon 同时把它换成了别的版本，它仍是 canon 的，可以替换。

## 教训

- 先判断再写入的安装代码，判断依据的状态在写入时可能已经变了；#24 只修了“写入不原子”，没有同时看“判断和写入不是一步” → 只靠文字：这是并发审查的习惯，合入后的代码评审已经抓到，没有能通用判定“检查后再写”的检查。
