## 为什么

本会话里四个已经修好的 issue（#11、#14、#19、#22）一直开着，直到主 agent 手工逐个核对才关掉。修复提交的信息里本来写着 issue 编号（`(C-n, #17)` 或 `fixes #28`），只是没有东西把它们和开着的 issue 对上。负责人 2026-11-03 同意做这个命令。

## 要改什么

子领域：work/issues（新建，代码在 `src/work/issues/`）。

- `canon issues [--json]`：用 `gh issue list` 读出开着的 issue，扫描 main 上的提交信息，列出每个 issue 有没有提交写明修复了它；只读，不关闭任何 issue（BR-2168）。
- 什么算写明修复：GitHub 的关闭关键字加 `#n`，或括号里同时有变更编号和 `#n`；`canon: open` 开变更的提交不算（BR-2169）。
- gh 没装、没登录或调用失败时以退出码 4 失败，提示怎么办（BR-2170）。
- skill canon-triage 的收集步骤加上 `canon issues`，并说明它只是线索，关闭前要核对提交。

## 陷阱和假设

- 只扫描 main 上的提交；修复还在别的分支上时不算。
- 括号里写了变更编号的 `#n` 都算修复，包括“部分修复”的写法；所以输出只说“写明修复”，关闭前由 agent 核对。
- `gh` 在主 checkout 里运行，由 gh 自己按远端找到仓库。
