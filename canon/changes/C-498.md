## 为什么

继续给没划业务的领域划。work/land/queue 21 条里只有 2 条写了业务，其余 19 条平铺在一起。这里面是五摊各自独立变化的事：排队拿轮次、谁先轮到、合入者掉线、被拒之后保住位置、合入被杀之后怎么认出来。

## 要改什么

README 的业务一节写出 6 个业务，21 条生效规则全部归属。只加 front matter 的 `business`，`## 规则` 和 `## 例子` 一字不动，行为哈希不变（BR-2236）。

- 排队和心跳（4）：BR-2020、BR-2048、BR-2049、BR-2122
- 合入的优先级（4）：BR-2232、BR-2363、BR-2364、BR-2399
- 掉线的合入者（3）：BR-2044、BR-2098、BR-2144
- 等待时提前拒绝（1）：BR-2153
- 保留位置和拿回（4）：BR-2177、BR-2178、BR-2368、BR-2380
- 被中断的合入（5）：BR-2099、BR-2307、BR-2308、BR-2309、BR-2310

原有的两个业务保留名字：「排队和心跳」的说明补上到达顺序和等待时限，「被中断的合入」的说明补上「当场让出轮次」，因为 BR-2099 说的是被终止那一刻的事。

## 陷阱和假设

- 「掉线的合入者」和「被中断的合入」分开：前者是别人从心跳和进程看出它没了并绕过去，后者是这个合入自己的 worktree 和命令事后怎么说出它。
- BR-2153（预测冲突就拒绝）单独一个业务：合入前评审指出它和保留位置的几条触发点不同，装在一个名字里是两件事；预测用什么方法、什么时候拒绝，和被拒之后位置保留多久、怎么拿回，各自独立变化。
