## 为什么

2026-11-04：子 agent 把 `canon work land --finish`（C-273）当后台任务启动后结束了回合，合入进程被 harness 杀掉。事件表里 `start.ok`、`work.test` 之后什么都没有，`canon work status` 里认领还在、队列是空的，协调者过了约 1 小时 45 分钟才发现。复现和各阶段留下的东西见 D-58：SIGKILL 拦不住，BR-2099 的信号处理不起作用；合入没有记下自己是哪个进程，死掉的队列条目只在别人查轮次时被悄悄标成放弃。

## 要改什么

按 D-58（proposed）：合入开始时记 `land.start`（带 pid 和启动时间，BR-2307）；`canon work status` 列出没有结果的合入，进程不在的标 interrupted 并点出留下的队列条目、关闭提交、做到一半的 rebase（BR-2308）；同一个 worktree 的下一次 `land` 先报出、清理并记 `land.interrupt`（BR-2309）；`after-land <C-n>` 和 `brief` 也说出来（BR-2310）。BR-2099 补一条例子指向它们。代码在 `src/work/land/queue/interrupted.ts`，由 land.ts、`work status`、`brief`、`after-land` 调用。

## 陷阱和假设

- 合入里入队之前的步骤（关闭提交、检查重叠）都是同步的，信号要等它们做完才处理，所以 SIGTERM 总是在条目存在之后才被处理；入队前没有信号分支要补。
- 报告只对 worktree 还在的合入；`kill -9` 之前（启动到认领续期之间的几十毫秒）被杀掉没有记录，是已知限制。
- floor 子进程在 SIGKILL 之后成为孤儿继续跑，canon 没有记它的 pid，不在本变更内（已另记 issue）。

## 教训

- 一个只靠信号处理函数兜底的流程，对 SIGKILL 没有任何办法，必须在开始时留下可核对的记录 → 现在由 BR-2307 到 BR-2310 保证（land.start 加进程探测）。
- 其他会长时间运行的命令（floor 监视、`canon work test`）可能有同样的盲区 → 待负责人确认是否固化
