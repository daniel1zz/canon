## 为什么

N-3 流程问题 2：冲突要等轮到自己 rebase 时才发现，C-55 排了 409 秒才知道和 C-57 冲突；同文件提示（BR-2062）只在双方都提交后出现，开工时一次也没触发。

## 要改什么

子领域：work/land（`src/work/land/land.ts` 的等待循环）。

- 等待时每当 main 变化，用 `git merge-tree --write-tree` 在内存里合并 main 和 HEAD；预测到冲突就立刻以 `conflict` 拒绝，列出文件，条目标为失败，worktree 不动。预测跑不起来时打印一行，照常等待。选型见 D-22。
- 新规则 BR-2153，新决策 D-22。
- `canon work start` 不改：新变更开工时只提交了自己的变更文件，没有可比较的改动；别人没提交的改动要等它合入 main 后才会冲突，那时等待中的预测会发现（写在 D-22 的决定里）。

## 陷阱和假设

- `git merge-tree` 遇到不存在的提交也以 1 退出，和“有冲突”相同；只有输出第一行是树的编号时才算冲突。
- 预测的是合并，不是逐个提交的 rebase；预测到的冲突才拒绝，漏掉的仍由轮到时的 rebase 发现（BR-2015）。
