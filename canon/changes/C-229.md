## 为什么

#89：`testCommit` 通过时先移 `refs/canon/green`，在一个事务里记 `floor.pass`，然后才运行 `hooks.after_green`（本仓库是重新构建 PATH 上的 `dist/canon`）。进程在记下 `floor.pass` 之后、`after_green` 跑完之前被杀掉，这个提交已算测过，`after_green` 没有任何地方补跑，PATH 上的 canon 一直是旧的。

根本原因：“after_green 还欠着”这件事没有任何记录，`floor.pass` 一写下就等于全部做完。

复现（改动前）：`src/work/watch/watch.test.ts` 的 BR-2270 用例：`after_green` 运行时 SIGKILL 整个进程组，之后 `canon brief` 不启动后台测试，`after_green` 只跑过半次。

## 要改什么

- 新规则 BR-2270、决策 D-44：`floor.pass` 带 `after_green: true` 表示欠着，跑完记 `floor.after_green`；`refs/canon/green` 指向的提交欠着时，合入和 `canon brief` 也启动后台测试，后台测试先在临时 worktree 里跑 `setup` 和 `after_green`（不重跑 floor），全部以 0 结束时照 BR-2251 交接。
- BR-2222：写明欠着和补跑（指向 BR-2270）；处理评审建议：删除记录出错时 `refs/canon/green` 已经前移、`after_green` 不运行，补测试断言。
- 代码：`src/work/watch/watch.ts`：`afterGreen`、`dueAfterGreen`、`rerunAfterGreen`；交接抽成 `handOff`，测完和补跑共用；`ensureWatcher` 多一种启动条件。

## 陷阱和假设

- 只补 `refs/canon/green` 指向的提交；这条规则之前的 `floor.pass` 没有标记，不会被补跑。
- 补跑时 `setup` 失败也记 `floor.after_green`（带 `setup_exit`），否则每次 `canon brief` 都会重试。
- `floor.after_green` 不在 `canon stats` 的事件列表里（`src/work/stats/stats.ts` 按种类列举），不算 floor 的运行。

## 教训

- 一个“做过了”的标记后面还跟着别的步骤时，标记要么等全部做完再写，要么另记“还欠着什么” → 只靠文字：哪些步骤属于同一件事要看语义，没有通用检查。
