## 为什么

2026-11-14 的全量 review：zhushenkongjian 的 `canon work test` 有 45/254 次被中途杀掉，其中 17 次死在 600 秒左右，那是 agent 执行命令的时间上限，不是 canon 定的。负责人要求：不靠 600 秒杀掉，设一个更宽松的总时限，只防测试真的一直跑；触发它就说明测试套件有问题，不应允许特别长的测试频繁跑。数据：正常跑完的运行，canon 中位 2.8 分钟、最长 28.5 分钟（那次是 canon 自己的全量测试和 zhushenkongjian 同时在跑，负载 15.6/8 核）；zhushenkongjian 中位 6.1 分钟、只有 1 次超过 30 分钟。

## 要改什么

按 BR-2466：新配置项 `test_timeout_minutes`（默认 30），超时像收到信号那样停下、以 1 退出，写明最慢的文件和开始、停下时的负载，区分“机器太忙”和“测试太慢”。让 `canon work test` 在后台跑、不再被 agent 的时间上限杀掉，是下一个变更。

## 教训

- 测试一个时限，用很短的时限（这里 3 秒）测“到点触发”，不要真的等那么久（负责人 2026-11-14 的提醒）→ 待负责人确认的机制在后续变更里做：按实际耗时找出长时间等待的测试。
