## 为什么

D-136 定下：评审意见积压时挡住开工（BR-2464、D-126）防的是“忘了处理”，而 canon 现在能把该处理的事实时推给会话，拦截就换成提醒（#260）。C-599 已经做了容量部分，并把这里的四条规则写成计划中；本变更实现它们。

## 要改什么

- `src/work/reminders`：`due.ts` 按调用者身份算待办清单（主会话：意见、问题、停滞的派发、交回自己的设计请求、main 变红、机器紧张；worker：设计请求的回答、被重新派发或收回、自己被拒的合入），`watch.ts` 是 `canon work watch` 的循环，`commands.ts` 注册 `canon work due`、`canon work watch`，`config-keys.ts` 加 `remind_every_minutes`。BR-2527、BR-2528 转为生效。
- `canon brief`：主会话列出 `Due now`，Claude Code 下输出挂 Monitor 的提示（BR-2529，BR-2024 补一句指向它）。
- `canon work start`：去掉欠账拦截和 `--urgent`/`--relayed`，第一次开始一个变更时在开工之后列出欠的意见（BR-2530）；BR-2464、BR-2489 退役。
- 配置：去掉 `debt_max_findings`、`debt_max_age_hours`；还写着它们时退出码 2，信息写明删掉那一行（负责人在对话里要求的）。
- `human.ask` 事件带上问题编号，watch 的那一行能写出 `canon human answer <n>`。
- `capacity.ts` 抽出 `pressure`，派发拒绝和待办里的 `capacity` 共用同一判断。

## 陷阱和假设

- SQLite 删掉的数据库文件仍能读，watch 每轮自己看文件在不在，不然协调数据库被删时会一直不出声。
- worker 的 `delegation:<C-n>` 在 worker 对这个变更再有动作（接受设计、交接、释放、开始合入）后消失；之前一直列着。
- `claim.expired` 这类事件只有在有命令判断认领时才写出来，watch 每 30 秒判断一次，所以认领失效最多晚 30 秒被看到。
