## 为什么

D-151 第一部分：变更的状态要能直接用脚本算出来。现在状态分散在 7 处各算各的；`C-343`（代码已在 main 但没关）、`C-406` 和 `C-1047`（交接原因只是文字）、`C-671`（只在分支上放弃，派发记录还在，一直显示停滞）都算错。

## 要改什么

按 D-151 第一部分：一个模块从变更文件（main 和在途分支）、协调事件和 git 提交算出每个变更的主状态和附加标记，所有读状态的命令改为读它；补上关闭命令、交接原因、放弃结束派发、等负责人只认带变更编号的问题；`canon change list --json` 给出主状态、附加标记和在等什么。规则先写（canon-rules），名字 D-151。

规则：
- 新 BR-2571（knowledge/changes，变更的状态）：14 种主状态的先后次序和每一种的算法，7 个附加标记。
- 新 BR-2572：`canon change list` 每行先写主状态，`--json` 加 `state`、`flags`、`owner_questions`、`delegation`、`land_refused_at`、`not_delegatable`，`handoff` 加 `reason`、`on`；`--all` 列出只在协调数据里出现的变更。
- 新 BR-2573：`canon change close <C-n> --commit <提交>` 写 `status: done` 和 `landed_in`，记 `change.close`；`landed_in` 由 `canon check` 查写法。
- 新 BR-2574（work/drop）：`canon work drop` 和 `canon change drop` 结束生效的派发，记 `delegation.end`。
- 新 BR-2575：`canon work handoff-reason <C-n> --reason … [--on …]`，旧交接的迁移办法。
- 改 BR-2025：`canon work stop` 必须给 `--reason land|design|owner|deps|partial`，`owner` 必须 `--on` 一个关联到这个变更的问题或 main 上的成功标准。
- 改 BR-2522、BR-2526、BR-2497：“关闭”按 BR-2571 判定，只在分支上放弃的也算。
- 改 BR-2564、BR-2149：brief 的取活行不列等依赖、等负责人和代码已在 main 待关闭的，各另起一行（顺带消掉评审意见 #184 指出的 BR-2149 和 BR-2564 的矛盾）。
- 改 BR-2291、BR-2192：列表和 status 的交接行写出主状态、交接原因。

代码：`src/knowledge/changes/state.ts` 是唯一算状态的地方；`canon change list`、`canon brief`、`canon work status`、`canon work due`、`canon overview`、派发名额（`capacity.ts`）、计划命令都改为读它；`stall.ts` 只剩 BR-2522 的两个条件（`stallCandidates`），是否关闭交给状态模块；`delegate.ts` 抽出 `contractWanted`，派发和“可派”判断共用；交接表加 `reason`、`on_ref` 两列。计划（`src/knowledge/plans/status.ts`）按 D-148 第 E 步去掉前不动，只是停滞集合改从状态模块来。C-632 才重写 due、watch、overview 的输出。

## 陷阱和假设

- D-151 写的“main 上 open、没分支、没认领、它列的规则已生效”会误判提前建好、要改已生效规则的变更（它列的规则本来就是 active）。BR-2571 多加了一个事实：事件表里有过它的 `claim.take`（开过工）。没开过工的不算 `awaiting-close`。
- 状态只认 main：只在这个 checkout 或分支上改成 `done`/`dropped`、没合入的文件，主状态仍按后面的次序判定（多半是 `ready-self`，原因写明没合入）。
- `land-refused` 排在 `in-progress` 前面（D-151 的次序）：被拒后会话还在修，也显示 `land-refused`，`flags.claimed` 是 true。
- `handed-off` 排在 `waiting-owner`、`waiting-deps` 后面：原因是 `owner` 且问题没答时显示 `waiting-owner`，答了才回到 `handed-off: owner #n`，这样“等的东西到了”能从状态看出来。
- 旧交接没有原因，显示 `unrecorded`，不猜；迁移靠主会话逐个 `canon work handoff-reason`（zhushenkongjian 的 `C-406`、`C-1047`）。`C-343` 用 `canon change close C-343 --commit 42c1f369` 关闭。`C-671` 这类只在分支上放弃过的，不用迁移：状态读 `drop.done` 就算 `dropped`。
- “可派”判断对每个可开始的变更读一次 main 的文件列表和分支差异；`delegatable: false` 时跳过（brief、status、due、overview、派发名额不需要它）。
