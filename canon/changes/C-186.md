## 为什么

baseline 核对（N-4）发现：`canon work start` 认为租约到期或会话进程已经不在的认领可以接手（BR-2100），但 `canon work clean` 把它当成仍然有效而保留 worktree，`canon brief` 照样标 `(claimed)`，`canon work status` 也看不出它已经失效。另外，`canon work stop` 在一个正被 clean 或 drop 删除的 worktree 里执行时，只说“没有变更”（退出码 3），看不出真实原因。负责人 2026-11-04 选择推荐方案：“全部按推荐”。

## 要改什么

- `src/work/claims/claims.ts`：一个判断 `stateOf`（`live` / `expired` / `holder-gone`），`liveClaim`、新的 `liveClaims`、`claimsWithState` 和 `holdClaim` 都用它；`holdClaim` 去掉“有任何认领行就拒绝”的参数，clean 和 drop 一样只被仍然有效的认领或占位挡住；新增 `deletionOf` 找出正在删除这个 worktree 的占位。
- `canon work clean`：只把有效认领当作“claimed”；失效认领的 worktree 照常判断，删掉时这条认领一起去掉（BR-2019）。
- `canon brief`：只给有效认领标 `(claimed)`（BR-2149）。
- `canon work status`：仍列出每一行认领，失效的在行尾标 `(expired: lease ended)` 或 `(expired: session process exited)`，`--json` 每项加 `state`（BR-2192）。
- `canon work stop`：worktree 正被删除时退出码 5，提示 `being deleted`（BR-2025，BR-2022 的冲突列表加这一种）。

## 陷阱和假设

- 占位（hold）行的 worktree 列是 `hold:<路径>#<id>`，不是真路径；`deletionOf` 按前缀找，用 `substr` 比较，不用 `LIKE`，因为路径里可能有 `%`、`_`。
- 进程探测每个认领跑一次 `ps`；status 和 brief 的认领一般只有几条。
- `claimOfWorktree` 仍然不看租约：worktree 属于那个变更（BR-2024、BR-2075）。

## 教训

- 同一个“认领是否有效”的问题在 start、clean、brief、status 里各自写了一遍，其中三处漏了租约和进程 → 现在由 claims.ts 里唯一的 `stateOf` 保证，BR-2019、BR-2149、BR-2192 的测试分别覆盖失效的两种情况。
