## 为什么

GitHub issue #31（C-108 合入后的代码评审发现）：C-108 让 `renewClaim` 在队列里有同一合入进程的活动条目时保留合入进程。合入进程被 SIGKILL 杀掉后，它的队列条目仍是 waiting / landing，于是会话之后的 `canon work stop` 或再次 `canon work land` 都把认领留在已死的合入进程上；重试合入结束时又把这个死进程写回，别人就能在会话还活着时接手。

## 要改什么

子领域：work/claims（`src/work/claims/claims.ts` 的 `renewClaim`）。

- 判断“正在合入”时再确认合入进程还在（`isGone` 不为 true；读不到进程表时按还在处理，D-11）。
- BR-2142 补一句规则和一个例子，加对应测试。

## 陷阱和假设

- 进程探测在 `renewClaim` 的事务里进行，和同一函数里 `bindsStill` 的做法一致。
