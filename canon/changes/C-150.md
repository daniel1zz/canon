## 为什么

baseline 核对发现安装和更新先写后查，四个现象同一个根因：

- #49：`.claude/settings.json` 不是合法 JSON 或是符号链接时，`canon install` / `canon init` 退出码 2，但 skill 和清单已经写了（BR-2087 说什么也不写）。
- #51：`canon/config.yaml` 的 `main` 是 `rel+1` 这类 git 接受的名字时，写守卫抛异常，退出码 70，而 skill 和 settings 已经写了。
- #52：`canon update` 先开变更和 worktree，再做符号链接和清单检查，退出码 2 后留下变更、分支和 worktree（BR-2083、BR-2086）。
- 别人的 `reference-transaction` hook 和不合法的 settings.json 同时存在时，`canon update` 报 2，BR-2124 要求先查 hook（5）。

## 要改什么

- `installSkills` 拆成只读的 `planSkills` 和写入的 `applySkills`；`ensureHook` 拆成 `planHook` 和 `writeHook`。
- `installAssets` 先做完全部检查（main 分支名、别人的 hook、skill 的链接和清单、改过的文件、settings.json），再写 skill、settings 和守卫。
- `canon update` 先查别人的 hook，再在开变更之前跑同一组检查。
- 守卫脚本里 main 的名字按 shell 双引号转义；git 不接受的名字（`git check-ref-format`）算配置错误，退出码 2。只含字母、数字和 `._/-` 的名字写出的脚本和以前逐字相同，已装的守卫不会变成过期。
- 规则：BR-2086（安装的拒绝都在开变更前）、BR-2087（例子补 init）、BR-2123（分支名）、BR-2124（排在 settings.json 检查之前）。

## 陷阱和假设

- `canon update` 的预检查在当前目录做，真正安装在新 worktree 里做；两边内容不同（当前目录有未提交的改动）时，worktree 里仍可能被拒，这时变更会留下。

## 教训

- 先查后写要靠结构保证：把“算出要写什么”和“写”分成两个函数，调用方先拿到全部计划再写 → 由 BR-2087、BR-2086、BR-2123 的测试保证。
