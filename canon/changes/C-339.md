## 为什么

D-61 的第三步（C-336、C-338 已合入）：版本有了文档、标签、检查和进度，还缺“发布”：把一个版本定格成快照，并且只有负责人确认过才能发。

## 要改什么

- `canon release ship R-n`（BR-2331、BR-2333、BR-2334）：标着版本的规则全部已通过才继续；负责人的 yes 取自 `canon human` 的已回答问题（文字含 `ship R-n`，回答是 yes，直接回答或转述并和提问工具的记录 `match`）；通过后和 `canon update` 一样自己开一个变更、写 `status: shipped` 和 `shipped_at`（开始时 main 的提交号）、`--finish` 合入，之后在 `shipped_at` 上打 tag `release/R-n`，打不上只警告。没有选“必须在一个已开的变更里运行”，因为发布是负责人确认触发的独立动作，不该混进别人的工作。
- 合入时的 `release` 检查（BR-2332）：一个版本变成 shipped 必须有这个变更的 `release.ship` 事件，已发布的版本不能改回去、不能删、`shipped_at` 不能改，所以 agent 手写 `status: shipped` 合不进 main。新增拒绝原因 `release`（`canon stats` 的检查名里加上它；`check_reviews` 里的复审日期按 BR-2248 要在这次合入之后另行加）。
- `canon-product` skill：版本的故事地图切片写进版本文档，笔记留调研和证据，线上方的行变成标着该版本的规则。

## 陷阱和假设

- `shipped_at` 取 `ship` 开始时 main 的提交，不是发布变更自己的提交；`ship` 检查完到发布变更排队合入期间 main 有人改了这个版本的三节或标签，合入时的 `canon check` 会拒绝（BR-2325、BR-2326），重新运行 `ship`。但“规则全部已通过”只在 `ship` 开始时查一次，合入时不重查（假设：规则状态在这几分钟里变坏的可能很小，且发布后 `canon release status` 照样能看到）。
- 负责人的 yes 靠 BR-2276 的记录核对转述；canon 分不出转述和编造，只保证没有提问工具的记录就不算数。
