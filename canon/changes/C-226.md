## 为什么

C-222（#25）合入后的代码评审在 #25 下留言：hook 目录不支持硬链接、`link` 以 EEXIST 以外的错误失败时，`replaceOld` 把挪走的 canon 旧守卫放回原处的写法是“先查路径空着（`existsSync`），再 `renameSync`”。两步之间别的工具写进来的 hook 会被 canon 的旧守卫换掉，canon 只报一个环境错误，违反 BR-2124。这正是 #25 本身的“先查后替换”。

## 要改什么

- 代码（`src/cli/install/githook.ts` 的 `replaceOld`）：放新守卫失败（环境错误）后，只用排他的 `link` 把旧守卫放回；放回成功就删掉挪走的那份；路径又被占了就删掉挪走的那份（那是 canon 自己的旧文件），不动路径上的文件；放回也失败就把旧守卫留在挪走的位置，提示里写明它的路径。不再用改名放回。
- 规则：BR-2124 写明这种情况，补例子；顺带处理 C-222 评审留在 BR-2124 上的意见：补“放回时路径又被占了”“不支持硬链接时退出码 4”“旧版本挪走后另一个 canon 放上了当前守卫”三个例子。BR-2022 的退出码 4 情形里加上“hook 目录不支持硬链接、装不了 git 守卫”（同一条评审意见）。
- 测试：`src/cli/install/githook.test.ts` 用 `spyOn` 让 `linkSync` 失败，并在失败那一刻写进别人的 hook，证明别人的 hook 留着、旧守卫留在旁边；去掉修复会失败。

## 陷阱和假设

- `link` 失败多半整个文件系统都不支持，放回用的 `link` 也会失败，所以“留在旁边并写明路径”是这种文件系统上的常见结果，不是少见分支。
- 测试靠 `spyOn(fs, "linkSync")` 替换 `node:fs` 的导出；已在 Bun 1.4.4 上试过，命名导入也会被替换。

## 教训

- C-222 修 #25 时，新加的出错分支（硬链接失败后放回）又写成了“先查后替换”：修一个竞争时只看主路径，没有把每个出错分支也当成同样的竞争去看 → 只靠文字：没有能通用判定“检查后再写”的检查；合入后的代码评审抓到了。
