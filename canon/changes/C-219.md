## 为什么

决策的来源写成 `来源：<网址或仓库路径> “<摘录>”`（D-14）。`canon check`（BR-2110）只看格式和仓库路径是不是文件（或历史里有过），合入时的核对（BR-2111）只核对新增的来源。代码挪动或改写后，仓库文件里的摘录会悄悄失效：C-218 里 D-14、D-21、D-32 的三条来源引用的代码已经挪走，是靠 grep 才发现的（C-218 的教训）。负责人 2026-11-04 选择“canon check 离线核对摘录 (推荐)”：`canon check` 离线核对每条仓库路径来源的摘录仍在那个文件现在的内容里，网址照旧只在合入时核对。

另外处理 C-182 留在 BR-2235、BR-2033、BR-2034 上的同一条评审建议：BR-2235 说规划中的规则“不挡任何合入”，和 BR-2033、BR-2034 的发现会拒绝合入矛盾。

## 要改什么

- 新规则 BR-2252（`knowledge/check`）：没被取代的决策（`accepted`、`proposed`）里，`## 方案` 的每条仓库路径来源，去掉 `:行号` 后现在是仓库里的文件时，摘录必须在文件现在的内容里，比较方法和 BR-2111 一样（连续空白合并成一个空格后找子串）；不在时报 `source-quote-missing`，写明决策、文件和摘录。文件现在不存在时由 BR-2110 处理（历史里有过就不报，D-25、C-209 的选择）。被取代的决策是历史，不核对（和 BR-2171 一致）。网址不核对。
- 代码：`src/knowledge/check/sources.ts` 把 BR-2111 核对单个仓库文件来源的那段抽成同步函数 `fileSourceFailure`，`verify`（合入）和 `canon check` 都用它，不写第二份匹配；`src/knowledge/check/check.ts` 加 `source-quote-missing`。
- BR-2110：“摘录是否真在文件里，到合入时才核对”改成仓库文件由 BR-2252 核对、网址到合入时核对；写明只在历史里有过的文件只对 main 上已有的来源放行，新增的来源合入时仍要指向现有文件（BR-2111），处理 C-209 的评审建议；补两个例子（`..` 路径、仓库没有提交）。
- BR-2111（`work`）：写明 `canon check` 先跑，没被取代的决策里摘录不在文件里的来源由它以 `check` 拒绝，不再走到 `source` 这一步；`src/work/land/land.test.ts` 里 BR-2111 的 “File wrong” 用例跟着改成期望 `check: source-quote-missing`（和已有的 “File missing” 用例同一种情况）。
- BR-2235：“也不挡任何合入”改成“缺测试不挡合入”；BR-2033、BR-2034 写明对规划中规则的发现同样拒绝合入（BR-2016）。
- 现有决策的来源：本仓库 38 条仓库路径来源，新检查核对其中没被取代的 37 条，报出 1 条：D-15 方案 4 的摘录 `export function importedPaths(root: string, file: string): string[]`，函数签名后来多了一个参数，摘录改成仍在文件里的前半段。另外 D-29 的两条来源指向 C-218 挪走的 work/land 下的 BR-2153、BR-2020 规则文件，BR-2110 不报（历史里有过），但顺手改成 `queue/` 下的新路径。两处都只改来源行。

## 陷阱和假设

- 合入时 `canon check` 也会跑，所以以后改了被决策引用的代码、让摘录不再成立的变更会被拒绝，要顺手改决策的来源行。这正是负责人要的效果。
- 文件现在存在但内容已经和做决定时不同，被取代的决策不报；没被取代的决策要改来源行。
- 匹配只看整个文件，`:行号` 只用来去掉，不核对行号是否对得上（BR-2111 也不核对）。
- 装在 PATH 里的 `canon` 是编译好的二进制，在 worktree 里跑 `canon check` 用的不是 worktree 里的代码；要看新检查的效果用 `bun src/cli/main.ts check`。
