## 为什么

会话必须做的判断（变更要不要负责人批准、推进哪个目标，规则属于哪个业务，决策修订了哪些决策）现在多是可选字段，只能手写，所以会被忘掉（#293 的 `C-1068`）。负责人 2026-11-21 要求所有文档类型都在新建时由命令当场表态并校验。

## 要改什么

设计变更，只写决定和计划中的规则，代码在后续的实现变更里写：

- D-159，修订 D-144（front matter 也放会话交给命令的判断）和 D-158（`owner_gate` 改成新建时表态）。
- 计划中的规则：BR-2619（字段声明）、BR-2620（新建命令要求）、BR-2621（`canon doc set`）、BR-2622（`canon check` 校验格式）、BR-2623（内置表态字段）、BR-2624（合入拒绝缺字段的新文档）。
- knowledge/documents 加业务“声明的字段”。

## 陷阱和假设

- BR-2054 的旧写法（`fields` 是名字列表）要照样能读；它原来要求所有文档都填，改成只要求新文档。
- 内置的 `owner_gate` 写成 `none: <理由>` 时不算带关卡，实现 BR-2623 时要同时改 BR-2615 和 D-158 的判定代码。

## 方案依据

- 沿用：字段格式用 BR-2546 的槽位类型和 RE2 正则（D-144、D-153）；新建前就拒绝照 `canon quality new` 的做法（BR-2552）；`none: <理由>` 照 `advances` 的写法（BR-2517）。
- 新的选择：判断类字段由新建命令当场要求；合入拒绝缺字段的新文档；旧文档不追溯；front matter 也放会话交给命令的判断（修订 D-144）。
- 数据怎么演进：值都在文档文件里，跟着 git 走，坏了用 git 历史恢复，没有新的数据库表。给类型加一个新建时表态的字段，只影响之后新增的文档；去掉一个声明，文件里的旧值留着，`canon check` 不再校验它；改字段名要先声明新名字、用 `canon doc set` 逐个补上，再去掉旧的。
- 最坏的失败：会话填 `none: n/a` 这类敷衍的理由，字段都在，判断没做；或者新建命令的参数太多，会话复制旧文件绕开，合入才拦住。
- 能证明它错的结果：上线后带 `none` 的字段大多是敷衍的理由；或者合入因 `fields` 被拒的次数多到成了来回的主要原因（超过 `check` 被拒的一成）。
