## 为什么

C-247 让 floor 和 `test_command` 都经过 `scripts/test.sh`（用 `--timeout` 设 30 秒测试超时，用 `GIT_CONFIG_GLOBAL`、`GIT_CONFIG_NOSYSTEM` 固定 git 配置），但直接运行 `bun test` 仍是 5 秒超时、读本机的 git 配置，结果可能和 floor 不一样，而 canon-test skill 里的例子写的正是直接 `bun test`。负责人 2026-11-04 的选择是“报错并提示改用脚本 (推荐)”。

这是本仓库的测试基础设施，不是产品行为：canon 对用户项目做的事没有变，所以和 C-247 一样不新增、不修改规则。

## 要改什么

- `scripts/test.sh` 在启动 `bun test` 时设 `CANON_TEST_SCRIPT=1`。
- 新增 `bunfig.toml`，`[test] preload` 加载新增的 `scripts/test-guard.ts`：没有 `CANON_TEST_SCRIPT=1` 时在标准错误写明要改用的命令（`sh scripts/test.sh <文件>`），以退出码 2 结束，一个测试都不跑。
- `package.json` 的 `test` 脚本改成 `sh scripts/test.sh`。
- `.claude/skills/canon-test/SKILL.md` 第 6 节的例子改成 `canon work test` 和项目 `test_command` 写的命令，不再写直接 `bun test`；这个 skill 也装进别的项目，所以写成按 `test_command` 选命令，两种写法都给例子。

依据：bun 1.4.4 自带文档 `docs/runtime/bunfig.mdx`：“### `test.preload` Same as the top-level `preload` field, but only applies to `bun test`.”；同一文档写 `bunfig.toml` 放在项目根目录。实测（本变更的 worktree）：改动前 `bun test src/config/key.test.ts` 退出码 0；改动后同一命令退出码 2，输出 `bun test refused: …` 和 `sh scripts/test.sh src/config/key.test.ts`；`sh scripts/test.sh src/config/key.test.ts` 照常通过。

## 陷阱和假设

- bun 只在当前目录找 `bunfig.toml`：在子目录里运行（例如 `cd src && bun test config/key.test.ts`）不经过这个检查，实测照常运行。floor、`canon work test` 和 skill 里的命令都在仓库根目录运行。
- preload 里拿不到 `bun test` 的原始参数（`process.argv` 只有 bun 和第一个测试文件），所以提示里给的是第一个文件的命令，并写明脚本接受和 `bun test` 一样的参数。
- 测试里启动的子进程如果又在仓库根目录运行 `bun test`，会继承 `CANON_TEST_SCRIPT=1`；现在没有这样的测试。

## 教训

- 测试只经过包装脚本运行才可信，而直接运行测试工具不会提醒 → 现在由 `bunfig.toml` 的 preload（`scripts/test-guard.ts`）在本仓库根目录保证；子目录里运行仍只靠文字：bun 不往上层目录找 `bunfig.toml`。
