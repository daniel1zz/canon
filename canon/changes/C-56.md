## 为什么

PATH 上的 `canon` 靠合入后在后台运行 `bun run build` 更新，代码评审也在后台运行。它们的退出码只写在 `.git/canon/logs/after-land-N.log` 里，`canon brief` 和 `canon stats` 都不读。构建失败时，之后每个会话都在用旧程序、看旧的工作说明，没有任何提示。lore 的 KN-314 测到过同样的事：代码合入了，PATH 上的程序没重新构建，lore 的总结是“合入了”不等于“用上了”。

## 要改什么

- 后台命令结束时把退出码写进事件表（现在 `hook.run` 事件的 `exit` 对后台命令是空的）。
- `canon brief` 发现最近一次合入的后台命令有非 0 退出时提示一行，给出日志路径。
- 可选：构建时把提交号写进程序，`canon brief` 拿它和 main 比较，不一致时提示。
- 规则和测试。

## 子领域

`config`（生命周期 hook：BR-2059 所在的地方）。brief 只是调用 `src/config/hooks.ts` 里的函数输出一行。

## 陷阱和假设

- 后台命令跑完时，没有一个 canon 进程在等它，所以退出码不能在命令结束的那一刻由 canon 写进事件表。让后台脚本自己调 canon 写也不可靠：最要报告的正是构建失败，而那时 PATH 上的程序可能是坏的。被否决的另一种办法是在脚本里调 `sqlite3`，它不一定装了。所以退出码以日志里已有的 `[hook i/n exited X]` 行为准，由下一次 `canon brief` 读出来补记成 `hook.exit`。
- 多个会话可能同时运行 `canon brief`，补记放在一个写事务里先查后写，同一条命令只记一次。
- 本变更之前的 `hook.run` 没有日志路径，读不到退出码，这些旧记录不提示。
- 可选的“构建时写入提交号并和 main 比较”这次不做：要改构建脚本和 brief 的比较逻辑，和退出码提示是两件事。

## 任务

- [x] 测试
