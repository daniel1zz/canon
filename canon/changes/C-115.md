## 为什么

N-3 流程问题 1：`canon work land --finish` 在排队之前就提交了 `canon: close C-n`（状态 done）。合入被拒、之后又没人再合入时，变更文件在 worktree 里显示 done，实际从没进 main；下一次合入也不会再提交关闭（它已经是 done），看起来像已完成。2026-11-03 的并发运行里，一次被规则评审拦下的合入就留下了这个状态。

## 要改什么

子领域：work/land（`src/work/land/land.ts`）。

- 两个方案：(1) 等 floor、`canon check`、评审都过了再提交关闭，再移动 main；(2) 照旧在排队前提交关闭，合入没有移动 main 时撤回。选 (2)：(1) 会让进 main 的树和验证过的树不同（BR-2106 只允许验证过的提交成为 main），关闭提交本身也该被 `canon check` 看到。
- 撤回用 `git reset --keep HEAD~1`，只在最上面仍是这个关闭提交、且它只改了变更文件时做；拒绝、排队超时、lost-turn、异常都走 `land()` 的 finally，SIGTERM/SIGINT 走信号处理。撤回不了时如实提示，不动 worktree。
- 改 BR-2018，补 floor 被拒、排队超时、被信号终止三个测试。

## 陷阱和假设

- rebase 之后才被拒时，最上面是 rebase 过的关闭提交，撤回后 worktree 停在 rebase 后的提交上，这和没加 `--finish` 时被拒的结果一致。
- `before_land` 又提交了东西时关闭提交不在最上面，不撤回（那次合入本来也会被 moved-during-land 拒绝）。
