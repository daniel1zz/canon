## 陷阱和假设

- 本机 git 2.50.1 实测：merge 后端（默认）的 `git pull --rebase` 在移动 main 时，`rebase-merge/` 还在，`head-name` 是 `refs/heads/main`，`onto` 是远端的提交（等于 `FETCH_HEAD`）；被拒绝后 `git rebase --abort` 退出码 0，HEAD 回到 main，工作区干净；用了 `rebase.autoStash` 时 abort 还会把自动暂存的改动放回来。
- apply 后端（`rebase.backend=apply` 或 `--apply`）不同：移动 main 时 `rebase-apply/` 里已经没有 `head-name` 和 `onto`，被拒绝后 `git rebase --abort` 失败（`could not read '.git/rebase-apply/head-name'`），HEAD 停在分离状态。从那里恢复要 `git rebase --quit` 再 `git checkout main`（实测可行，main 没动）。这条规则不处理它，只是不给出错误的提示。
- 只认 `rebase-merge/head-name`，不看 `GIT_REFLOG_ACTION`：用户直接 `git rebase origin/main` 停下时情形一样，同样提示；rebase 接到只在本地的提交时 `canon sync` 帮不上，不提示。
- `--git-path` 按 worktree 解析，链接 worktree 里的 rebase 状态在 `.git/worktrees/<名字>/rebase-merge`，不会读到别的 worktree 的。

## 教训

- 一个让 git 命令中途失败的 hook，会把命令留在 git 自己没预料到的状态，不同后端留下的还不一样（merge 后端能 abort，apply 后端不能）→ 只靠文字：没有通用检查能列出每个命令在 ref 更新前后做了什么，只能逐个命令、逐个后端实测。
