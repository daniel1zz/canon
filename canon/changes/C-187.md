## 为什么

2026-11-03 的 baseline 核对（N-4）和合入后的代码评审在 work/land 里留下两处要负责人选的地方，负责人 2026-11-04 选择推荐方案：“全部按推荐”。

4. 等待中的合入者每 2 秒查一次轮次，这也是它的心跳；`lander_stale_minutes` 设得比 2 秒还短时，正常等待的合入者在后面的合入者看来已经掉线，会被标记为放弃。推荐：等待的轮询间隔取 2 秒和掉线时间三分之一中较小的，和 BR-2049 的心跳一致，不新增拒绝。
5. issue #82：`--finish` 的关闭提交失败时，C-174、C-183 先核对文件仍是 canon 写入的内容、再写回原来的内容。核对和写回之间，以及 setMeta 读文件前后，都有空档；这期间别的进程保存的编辑会被旧内容盖掉。文件系统没有跨进程的比较并交换，这个空档关不掉。推荐：完全不写回，变更文件留着没提交的 `status: done`，拒绝信息写明下一步。

## 要改什么

- `waitAndLand` 的两处等待用 `waitPollMs(landerStaleMs)` = min(2 s, max(50 ms, 掉线时间 / 3))；BR-2044 写明等待时的心跳间隔并加例子。
- 关闭提交失败时只取消暂存，不再读 `before`、不再比较、不再写回；信息写明 `is left with status: done and not committed` 和下一步。新规则 BR-2229 写这个行为（处理 BR-2193 的评审建议：把关闭提交失败时文件怎样留下拆成单独一条规则；“之前已经保存的编辑都保留”现在对任何时间保存的编辑都成立，例子写明）。BR-2193 第一条改为引用 BR-2229。
- BR-2018 写明关闭提交没做成时没有要撤回的提交（BR-2229）；同时处理 BR-2018、BR-2173 上的评审建议：领头不在了，被锁定的成员下一次查轮次时解除锁定、回到队列，之后被信号终止时自己撤回关闭提交；加对应的例子和测试。
- C-174、C-183 的“只在仍是自己写的内容时才恢复”被这次取代。

## 陷阱和假设

- 不写回之后，worktree 留着一处没提交的改动，下一次 `canon work land` 会因 BR-2013 以 dirty 拒绝；所以信息必须写明怎样处理。下一步建议改回 `open` 再合入，而不是直接提交 `done`：直接提交后再合入失败，就没有关闭提交可撤回了（BR-2018 最后一种情况）。
- 掉线时间很短时等待轮询会到 50 ms 的下限，和心跳的下限一样；`lander_stale_minutes` 本来就只接受正数，不新增拒绝。
- 测试里等待的合入者和排在后面的条目在同一个进程里，靠测试自己反复调用 `tryTurn` 来模拟后面的合入者。

## 教训

- 跨进程的“先核对再写回”没法做成原子操作；与其把空档缩小，不如不写回，把状态和下一步交给人 → 只靠文字：哪里需要回滚要看语义，没有通用检查。
