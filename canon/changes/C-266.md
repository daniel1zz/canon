## 为什么

#112（C-263 合入后的代码评审）：合入检查只因为“此刻本地有这个分支”才放过待办清单里只在分支上的变更编号。清单进了 main 以后，别的会话 `canon work drop` 删了那个分支，之后每个变更的合入、main 上的 `canon check` 都报 `ref-dangling` 被拒，而它们根本没碰清单。这是 C-263 引入的回退。协调者决定：方案 1（只拦截改清单的那次）加方案 3（drop 时提示）。

## 要改什么

- BR-2150：失效的编号只在 main 上提交的清单还没列它时报 `ref-dangling` 并拦截（只会出现在改了清单的工作里）；main 已经列了的只输出一行 `note:`，写明行号和怎么修，不影响退出码。`canon check` 写在标准错误上，`canon work test` 和合入写在输出里。
- BR-2064：`canon work drop C-n` 删除后，main 的清单还列着 `C-n` 时提示一行，不拒绝。
- D-50（仍是 proposed）：记下这次的方案和否决的方案。
- 代码：`src/knowledge/check/check.ts`（`backlogBase`、`backlogNotes`）、`src/knowledge/documents/backlog.ts`（`backlogAt`，brief 原来的 `mainBacklog` 挪过来）、`canon check`、`canon work test`、合入检查（`src/work/land/checks/steps.ts` 只加读 main 清单和打印提示几行）、`src/work/drop/commands.ts`。
