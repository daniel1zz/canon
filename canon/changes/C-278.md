## 为什么

GitHub 上 115 个 issue 里有 65 个来自合入后的自动代码评审（`canon-review`）。后台测试那一串 #99、#101、#102、#106、#107、#108、#109 都是推演出来的事件交错，真实使用里没出现过：`.git/canon/state.db` 的 `events` 里 5 条 `floor.after_green` 没有一条带 `rerun: 1`。修它们却让 `src/work/watch/watch.ts` 和 `stop.ts` 涨到约 630 行，BR-2270、BR-2285 多了一串例外。

负责人 2026-11-04 的原话：“不要设想不存在的问题”；“这个应该固化到canon的认知中，同时不要为极端情况下的问题付出很多努力导致架构复杂”。选的方案是“评审和分拣都改 (推荐)”。

## 要改什么

- 新决策 D-54：按真实使用中的频率和代价、对比修它要加的复杂度来判断问题；极端情况记成已知限制；丢数据和安全问题例外。否决“能在测试里构造出来的都修”。
- BR-2070：代码评审的提示只要求报正常使用中会遇到的问题，出错情形写明谁在哪个正常操作里遇到；少见交错、极端配置、不越过安全边界的恶意输入不报，丢数据和安全问题除外。`src/knowledge/review/code-review.ts` 的提示照此改，测试验证提示里有这几句。
- `canon/product.md`：不新增 P 编号。product.md 只有“承诺”和“不做的事”，没有原则一节；canon 已有的工作原则（“证明责任在保留一方”，D-1）在 product.md 里体现为“承诺”开头那句“一个机制如果不支撑任何一条，就删掉”。这条新原则是对这句话的补充（为极端情况加的机制也算不支撑），不是一条新的承诺，所以接在那句后面。
- skill（D-8、D-9、D-10，文字，没有规则）：canon-triage 第 2、3 节，只在测试里构造出来的情形不算复现，新增“只能构造出来”这一结果和对应的关闭方式；canon-design 按情形在真实使用中的频率衡量复杂度，并发一项只要求正常使用中的交错；canon-diagnose 第 2 阶段，只能强行做出来的失败记成已知限制。
- 不改：规则评审的提示（只要求规则有边界、例子钉住边界，没有要求列出每个边界情况）；`canon brief` 的工作说明（没有要求处理每个边界情况）；后台测试和 main 守卫的代码（负责人安排在设计评审之后另做简化）。

## 教训

- 评审能在测试里构造出的问题不等于真实问题，按构造出的情形修会让代码越修越复杂 → D-54、BR-2070（评审提示）和 canon-triage 的“只能构造出来”结果；负责人 2026-11-04 已确认固化。
