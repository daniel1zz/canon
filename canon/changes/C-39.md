## 为什么

合入只更新本机的 main，推到 GitHub 一直靠人手动做。同样的问题出现过两次：旧 lore 有 3122 个提交两个多月没推上去；canon 第一晚也有 45 个提交只在本机。机器坏了就会丢工作，违反 P4。

对比 lore 时补充（2026-11-03）：推送不只是为了备份。lore 的 KN-534 发现子 agent 的 worktree 默认从 `origin/main` 建，origin 落后时子 agent 会在旧代码上干活（另见 C-60）。

## 要改什么

- 合入成功、main 移动之后，把 main 推到配置的远端；推送失败不改变合入结果，但要写事件（`push.fail`，带原因），并在 `canon brief` 里提示“有 N 个提交没推上去”。
- 用 C-1 已有的 `after_land` 机制实现，还是作为内置步骤，在设计时决定并写成决策。
- `canon sync`：把远端的 main 拉到本地。只在本地 main 能快进到远端 main 时才移动，并带上 main 守卫（D-16）要求的标记；不能快进时报错、什么也不动，不自动合并。负责人决定和推送放在同一个变更里做（2026-11-03）。原因：main 守卫会拒绝 `git pull`，现在要拉取只能用 `git -c core.hooksPath=/dev/null` 绕过守卫。
- 规则和测试（测试用本地裸仓库当远端）。
