## 为什么

合入只更新本机的 main，推到 GitHub 一直靠人手动做。同样的问题出现过两次：旧 lore 有 3122 个提交两个多月没推上去；canon 第一晚也有 45 个提交只在本机。机器坏了就会丢工作，违反 P4。

对比 lore 时补充（2026-11-03）：推送不只是为了备份。lore 的 KN-534 发现子 agent 的 worktree 默认从 `origin/main` 建，origin 落后时子 agent 会在旧代码上干活（另见 C-60）。

## 要改什么

- 合入成功、main 移动之后，把 main 推到配置的远端；推送失败不改变合入结果，但要写事件（`push.fail`，带原因），并在 `canon brief` 里提示“有 N 个提交没推上去”。
- 用 C-1 已有的 `after_land` 机制实现，还是作为内置步骤，在设计时决定并写成决策：D-38 定为内置步骤，两种 `floor_timing` 下每次合入都推（不等 `refs/canon/green`）。
- `canon sync`：把远端的 main 拉到本地。只在本地 main 能快进到远端 main 时才移动，并带上 main 守卫（D-16）要求的标记；不能快进时报错、什么也不动，不自动合并。负责人决定和推送放在同一个变更里做（2026-11-03）。原因：main 守卫会拒绝 `git pull`，现在要拉取只能用 `git -c core.hooksPath=/dev/null` 绕过守卫。
- 归属：新建子领域 `work/remote`（让本地 main 和远端一致：合入后推送、`canon sync` 拉取），规则放在 `canon/rules/work/remote/`，代码放在 `src/work/remote/`；land 合入成功后调用它。不放进 `work/land`，因为拉取不经过排队、floor 和比较并交换，放进去 land 的边界就不清楚了。命令入口照旧在 `src/cli/main.ts`（2026-11-03 和负责人确认归属原则）。
- 具体：
  - 决策 D-38（修正 D-16：main 也能由 `canon sync` 快进移动）。
  - 规则 BR-2259（推送）、BR-2260（推送失败）、BR-2261（brief 提示）、BR-2262（sync 快进）、BR-2263（sync 分叉）；BR-2022 加上 sync 的退出码。
  - 配置项 `remote`、`remote_timeout_seconds`，在 `src/work/remote/config-keys.ts` 声明，`src/config/config.ts` 的领域列表加一项。
  - 代码 `src/work/remote/remote.ts`（推送、数未推提交、sync）、`commands.ts`（`canon sync`）、`guide.ts` 不加（工作说明不变）。land 只在 `src/work/land/land.ts` 的 `land()` 里加一处调用：合入结果是 landed 时推送。brief 在 `src/work/session/commands.ts` 的 `briefState` 里加一行。
  - 测试 `src/work/remote/remote.test.ts`，远端用本地裸仓库，不联网。
- 本仓库启用（`remote: origin`）放在下一个变更：同一次合入新增并使用配置键会被 BR-2248 拒绝。

## 陷阱和假设

- 并发合入挨得近时，后读 main 的推送可能先到，先读的旧推送会被拒（实测 `[rejected] (non-fast-forward)`）。不加锁：被拒后取一次远端，远端已包含要推的提交就算成功（BR-2259）。
- 推送放在 `land()` 的排队轮次结束之后，所以不占别人的轮次；但合入者自己要多等一次推送，最多 `remote_timeout_seconds`。
- `GIT_TERMINAL_PROMPT=0` 只挡住 git 自己的密码提示；ssh 的提示靠超时结束（stdin 是空的）。
- `remote` 读 main 上已提交的配置，不是合入者 worktree 里的：推的是 main，配置也跟着 main。
- 假设：`git push` 成功后会把 `refs/remotes/<远端>/<main>` 更新成推上去的提交（实测 git 2.50.1 如此，前提是远端有标准的 fetch refspec）；brief 的数目靠它。canon 推送和 sync 都显式写 refspec，不依赖 fetch 配置去取。
- sync 和合入同时移动 main 时，由 `moveMain` 的比较并交换决定谁赢，输的一方 `main-moved`。

## 教训

- 一个后台命令一次推送的做法（比如 `after_land` 里配 `git push`）在几次合入挨得近时会留下假的失败：先读 main 的推送晚到会被远端以 non-fast-forward 拒绝 → 由 BR-2259 保证：被拒后取一次远端，远端已经包含要推的提交就算推上去了（本变更的规则，D-38 写明理由）
- 只在合入时推送，远端有本地没有的提交后，之后每次推送都会失败 → 只靠文字：怎样合并两边是人的决定，canon 只能记 `push.fail` 并在 brief 里提示（BR-2260、BR-2261），不能替人处理
