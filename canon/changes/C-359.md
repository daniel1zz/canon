## 为什么

D-64 让 canon 不再认任何语言：测试有哪些、跑没跑由项目产出的 JUnit 报告说了算。整件事拆成四步合入，本步先建地基：读报告、记账，但还没有任何检查读账，所以 main 的行为不变，只是多了账。

## 要改什么

- `test_command` 和 `floor` 可以写 `{report}`：canon 换成临时路径，命令结束后读 JUnit XML（BR-2160、BR-2337、BR-2339）。
- 新增 `src/work/verify/report.ts`（读 JUnit，BR-2338）、`ledger.ts` 和协调数据库的 `test_reports` 表（按“测试文件路径 + git blob 哈希”一行，每个路径留最近 5 行）。
- `canon work test` 每个文件运行后记账；没写出可读的报告就失败（BR-2337）。floor（合入时、后台）要求每个 testcase 带 `file`，缺则失败并提示改用 `canon work test --all`（BR-2339）。
- canon 自己的 `canon/config.yaml`：`test_command` 和 `floor` 带 bun 的 `--reporter=junit --reporter-outfile={report}`。
- 本步里 `{report}` 还是可选的；第 4 步改成必填并给出各框架的写法。
- 夹具：真实的 bun 报告，pytest xunit1/xunit2 和 gdUnit4 的报告（取自 D-64 的实测）。

## 陷阱和假设

- 已安装的（旧）canon 不认 `{report}`，会把它当普通文字交给 shell，bun 会在运行目录写一个叫 `{report}` 的文件。本步只用 worktree 里的代码（`bun src/invocation/main.ts work test`）跑测试；合入后要 main 全量测试通过、已安装 canon 重编，之后的合入才会记账。
- 账只写不读：`canon check` 等任何检查都还不读它（第 2 步）。
