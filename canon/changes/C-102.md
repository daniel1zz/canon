## 为什么

GitHub issue #20：`canon work start C-n` 对只在变更分支上的变更，先读分支、变更文件和 worktree 路径，再拿认领，拿到后只看 worktree 目录和分支在不在。另一个会话的 `canon work drop` 正好在两步之间跑完（删分支、删 worktree、放认领），start 就会用 `worktree add -b <分支> <路径> main` 从 main 建一个同名新分支，报告成功，但这个分支上根本没有变更文件。drop 的结果被悄悄撤销，接手的会话在一个不存在的变更上干活。

## 要改什么

子领域：work/session（`src/work/session/session.ts` 的 `start`）。

- 从变更分支接手时，拿到认领后再确认分支还在；不在就放掉认领，记 `start.refuse`（reason `gone`），返回 not_found（退出码 3）。认领把 start 和 drop 排成先后：drop 全程持有认领，所以拿到认领之后看到的分支状态就是 drop 跑完或没开始时的状态。
- 新规则 BR-2136；BR-2107 不变。

## 陷阱和假设

- 只覆盖“从分支接手”这条路。main 上有的变更不受 drop 删分支影响：从 main 重建分支是 BR-2107 之前就有的正常行为。
- 测试在 `takeClaim` 的事务开始前插入一次 drop 等价操作，模拟交错，不改产品代码的接口。
