## 为什么

业务层（D-96）落地后，唯一能按业务分组看规则的地方是 `canon rule new`，而它会建出一个文件。只读的三个检索面都给不出「这个领域有哪些业务」：`canon context <领域>` 把 34 条规则平铺按编号排，只在行末尾标 `[业务: X]`，要自己扫着归类；`canon rule domains` 完全不显示业务。原来目录层级一眼看清结构的作用，业务层没有对应物。

## 要改什么

把分组放进 agent 本来就在跑的两个只读命令，不新增命令。

- BR-2007：`canon context <领域>` 只列标题时按业务分组（领域 README 一个业务都没列时保持原来的平铺，并保留行末的业务标记）；`--full` 不变，仍按编号给全文，所以规则评审拿到的输入形状不变。
- BR-2114：`canon rule domains` 在领域行下面缩进列出它的每个业务和指向它的生效规则数，最后一行是没有指向已列业务的规则数；没列业务的领域不多出任何行。
- BR-2432：`canon rule new` 的输出改成和 BR-2007 同一套分组，三处共用 `src/knowledge/domains/business.ts` 里的 `groupByBusiness` 和 `businessListing`。
- 行内标记从 `[业务: X]` 改成 `[business: X]`，和 `business:`、`in no business` 一套词。
- canon-rules 第 1 节改成指向 `canon context` 和 `canon rule domains`，不再让人为了看清单去跑 `canon rule new`。
- BR-2114 从 `knowledge/documents` 搬到 `knowledge/domains`（新业务「领域清单」），`canon rule domains` 的实现跟着搬到 `src/knowledge/domains/list.ts`，点名它的两个测试搬到 `src/knowledge/domains/list.test.ts`。这是 BR-2431 的棘轮拦出来的：改 BR-2114 时它所在的领域还没声明业务，按 D-96 的后果，这类规则被改到时搬到 `knowledge/domains`。

## 陷阱和假设

- 只有 README 列了业务的领域才分组。现在 32 个领域里只有 2 个列了，所以绝大多数领域的输出一个字都没变，存量测试不受影响。
- `--full` 故意不分组：规则评审按 BR-2009 读它，改了形状会动到每一次评审的输入。
