## 为什么

C-254 的教训：在 Bun 的测试里写 `process.env.X = …`，传不到不带 `env` 启动的 `Bun.spawn` / `Bun.spawnSync` 子进程（子进程拿到的是 bun 启动时的环境），所以一个测试一直空过、什么都没验证。负责人 2026-11-04 的选择是“加检查，只报不拦 (推荐)”：静态判断有误报，所以只提示。

依据（本变更里实测，bun 1.4.4）：同一个测试里先写 `process.env.PROBE_X = "set"`，不带 `env` 的 `Bun.spawnSync` 子进程读到空值，带 `env: { ...process.env }` 的读到 `set`；`node:child_process` 的 `spawnSync`、`execSync` 和 Bun 的 `$` 读到 `set`。所以只看 `Bun.spawn` 和 `Bun.spawnSync`。

## 要改什么

- 新规则 BR-2300：`tests` 找到的 JS/TS 测试文件里，既改了 `process.env`、又有看得出不传 `env` 的 `Bun.spawn` / `Bun.spawnSync` 调用时，`canon check` 和 `canon work test` 在标准错误上每个文件提示一行（`hint env-spawn: …`），不算发现，不改变退出码。
- 代码：新增 `src/knowledge/check/env-spawn.ts`，`src/knowledge/check/commands.ts` 和 `src/work/verify/verify.ts` 输出提示；测试在 `src/knowledge/check/env-spawn.test.ts`。`knowledge/check` 的 README 写上“提示”这个词。

## 陷阱和假设

- 本仓库现在有 7 个测试文件得到提示（`hook-run`、`claims`、`drop`、`config-first`、`lander`、`session`、`watch`），逐个看过都是误报：子进程是 `sleep`、`git`、`chmod`、`sh -c <恢复命令>`，或者只读配置的 canon 命令，不读被改的变量。每个文件一行，而不是每个调用一行，是为了让这类误报少占输出（每个调用一行时是 25 行）。
- C-254 那次真正出问题的子进程是被测的代码（hook 运行器）启动的，不在测试文件里，这个提示看不到；规则的“局限”写明了。
- 测试文件自己的夹具文字要拼起来写（`["process", "env"].join(".")`），否则这个测试文件会提示它自己。

## 教训

- 静态提示一开就在本仓库报了 25 处，全是误报 → 只靠文字：按文件合并成一行，能不能再少要看负责人是否要一种“看过了”的标记（见合入后的汇报）。
