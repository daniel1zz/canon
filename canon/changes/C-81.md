## 为什么

负责人选定渐进式查找的方案 A + B，并要求子领域按业务能力（DDD 的子领域）拆，归属靠代码路径机械判断（2026-11-03）。C-80 做了 A（默认只列标题），这个变更做 B：work 领域 47 条规则、knowledge 领域 27 条，`canon context` 改任何一个文件前都要列出整个领域。

## 要改什么

- 领域可以有子领域（子目录，各有 README 和代码路径）；`canon context <路径>` 只返回代码覆盖这个路径的子领域和外层领域（BR-2113）。
- `canon rule domain <领域>/<子领域>` 只能建在已有领域下（BR-2115）；`canon rule domains` 缩进显示子领域，直接规则超过 25 条时提示拆分（BR-2114）；`canon rule list --domain` 包含子领域。
- 规则评审仍然拿整个顶层领域的全文，跨子领域的矛盾照样能看到（BR-2009）；子领域目录也必须有 README（BR-2006）。
- 拆分：work 拆成 session、claims、land、drop、humans、stats，顶层留 3 条贯穿全领域的规则；knowledge 拆成 documents、check、query、review。每个 README 写这一块的现状、代码位置和术语，作为现状总览。

## 陷阱和假设

- 实测：改 `src/work/drop.ts` 前要读的规则从 47 条降到 6 条，`src/check/check.ts` 是 9 条；`src/work/work.ts` 仍是 33 条，因为开始、合入、清理的代码都在这一个文件里，子领域的代码路径只能写到文件这一级。
- 进行中的其他变更如果改了被移动的规则文件，rebase 时靠 git 的改名识别合并；冲突时按新路径解决。
