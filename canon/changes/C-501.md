## 为什么

继续给没划业务的领域划。work/land/checks 19 条里只有 6 条写了业务，其余 13 条平铺。这里的规则按「拦的是什么」分得很清楚：合入前的前提、轮到之后的顺序、rebase、`canon check`、新增编号和配置键、floor 跑多少、测试报告、密钥。

## 要改什么

README 的业务一节写出 8 个业务，19 条生效规则全部归属。只加 front matter 的 `business`，`## 规则` 和 `## 例子` 一字不动，行为哈希不变（BR-2236）。

- 合入的前提（4）：BR-2013、BR-2031、BR-2043、BR-2105
- 合入的步骤（3）：BR-2014、BR-2106、BR-2355
- rebase 冲突（1）：BR-2015
- canon check 的拒绝（2）：BR-2016、BR-2094
- 新增的编号和配置键（2）：BR-2248、BR-2362
- floor 跑多少（3）：BR-2164、BR-2165、BR-2398
- 测试报告（2）：BR-2339、BR-2381
- 密钥扫描（2）：BR-2407、BR-2408

BR-2164 原来写的是「合入的步骤」，这次改成「floor 跑多少」：它和 BR-2165、BR-2398 说的是同一件事——这次合入该跑多少 floor，三条一起改。

## 陷阱和假设

- 「合入的步骤」只留下顺序本身和不拒绝的提示；具体某一项拦什么各归各的业务，这样改一项检查时不用动「步骤」。
- 「测试报告」里 BR-2381 的触发点是 rebase，但它改的是测试报告够不够，和 BR-2339 一起变；rebase 冲突单独一个业务，只管冲突时怎样拒绝。
