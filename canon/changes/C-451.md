## 为什么

D-85 让项目用 sops、age、varlock 管密钥，项目根目录提交了 `.env.schema` 就算开启。但一个变更如果把真实的密钥值提交进文件，合入时规则评审会把 diff 发给 `claude -p`，合入后 main 上就有了明文，合入后的代码评审还可能把它引用进 GitHub issue。负责人定了（2026-11-11）：合入必须在任何内容发给模型之前拒绝这样的变更。

## 要改什么

- 合入时，被合入的树根目录有 `.env.schema`，就在规则评审之前用 varlock 检查：先 `varlock load --agent` 确认 schema 能解析出值（`varlock scan` 在取不到私钥时会说“没有敏感值可扫”并以 0 退出，不先检查就会悄悄放行），再 `varlock scan` 本变更相对 main 改过（不含删除）的文件。
- 扫到明文值时以新原因 `secret` 拒绝，退出码 1；输出和事件表只写文件、行号和变量名，不转述 varlock 的原始输出（它的代码片段里带着值的前几个字符）。
- varlock 的查找：被合入树的 `node_modules/.bin/varlock`，没有就找 PATH；找不到、`load` 失败或 `scan` 的结果读不懂，都以 `environment` 失败，退出码 4，写明原因和安装办法；没有 `.env.schema` 什么都不跑。
- 新规则放 `work/land/checks`（一条写扫描和拒绝，一条写 varlock 不可用时的失败），改 BR-2014 的步骤清单和领域 README；`src/work/stats/checks.ts` 的 `LAND_STAGES` 加 `secret`；新决策写为什么内置在合入里而不是让项目配 `before_land`（以 proposed 合入）；`canon/architecture.md` 加上 varlock。

## 陷阱和假设

- 假设 varlock 1.24.0 的 scan 输出格式：发现写在 stderr，每条一行 `  <路径>:<行>:<列> <变量名>`，下一行是打了码的代码片段。canon 只认路径是本次传入文件之一的行；扫描以 1 退出却一条都认不出，按环境错误处理，不当作通过。
- 一起测时被合入的树是临时 worktree，通常没有 `node_modules`，会用 PATH 上的 varlock。
