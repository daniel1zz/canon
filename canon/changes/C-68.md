## 为什么

C-52 和 C-65 合入后的代码评审各发现一个同类的并发问题：

- issue #12：`canon work clean` 只在开头读一次认领表，之后做各项检查和一次 `lsof`；这期间另一个会话 `canon work start` 认领了这个变更，start 看到 worktree 已存在就直接让它 `cd` 进去，而 clean 接着把 worktree 和分支删了，那个会话拿着一个指向不存在目录的认领。
- issue #13：`canon work drop` 同样只读一次认领、不持有它；存档到删除之间别的会话可以接手，在 worktree 里新建文件、提交，这些都不在存档里，随后被 `--force` 删掉，`branch -D` 也会删掉带新提交的分支，最后连它的认领也被删除，违反 BR-2102 的承诺。

## 要改什么

- `coord/state.ts` 新增 `holdClaim`/`unholdClaim`：在一个事务里检查并占住变更的认领行，不写认领事件（`canon stats` 按认领事件计数，BR-2067）；放开时只删自己占的那一行，并恢复被替换的旧行。
- `clean`：删除前用“只在完全没有认领时”的方式占住，占不住就保留并写“claimed”，删完放开（BR-2019）。
- `drop`：认领检查改为占住（别人的有效认领仍是退出码 5），一直持有到删除结束，失败时放开并恢复；进程检查在占住之后；删除分支改为 `update-ref -d <分支> <列出时的提交>` 比较后删除，并先于删除 worktree；存档后重新列一遍会丢的东西，有变化就什么都不删，退出码 4（BR-2064、BR-2103）。

## 陷阱和假设

- 测试用一个假的 `lsof`（PATH 最前面）在 clean/drop 等它的时候模拟另一个会话：clean 的测试里它用 `sqlite3` 直接插入认领，drop 的测试里它运行真正的 `canon work start`；用 git 的 `reference-transaction` hook 在存档 ref 写入时往 worktree 里加文件。这几个测试只在 macOS 上跑（Linux 读 `/proc`，不调用 lsof）。
- 去掉修复后，这两个竞争测试都会失败（已验证）。
- 删除分支先于删除 worktree：分支删掉之后若 worktree 删除失败，分支已经不在了，但它的提交在存档里（有会丢的东西时）或已经在 main 上（没有时）。
