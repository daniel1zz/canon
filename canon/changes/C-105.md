## 为什么

C-56 合入后的代码评审提出 issue #28：`canon work land` 在标记排队条目为已合入、交出轮次之后，才写下后台命令的 `hook.run`。负载高时，排在后面的合入可能先写下它的记录，`canon brief` 按事件编号取“最近一批”，就会拿到排在前面那次合入的那批，后面那次的失败被藏起来，BR-2138 要的提示就丢了。C-56 的规则评审还提了三条不阻塞的意见：BR-2137 重复了 BR-2059 的内容、没写日志不见时是否记 `hook.exit`、BR-2138 缺“有的失败有的还在跑”的例子。

## 子领域

`config`（生命周期 hook）；`work/land` 只改一行，把排队序号传给后台 hook。

## 要改什么

- `hook.run` 记下这次合入的排队序号 `batch`；`settleBackgroundHooks` 按 `batch` 取最近一批，旧记录没有 `batch` 时排在最后。轮次严格按排队序号给出（`tryTurn`），所以排队序号就是合入顺序。
- BR-2059 加上 `batch`；BR-2137 去掉和 BR-2059 重复的部分，加上日志不见时不记的例子；BR-2138 写明按合入顺序，并加两个例子。
- 测试：直接调用 `runHooksInBackground`，让排在后面的一批先写记录，验证提示的是它。

## 陷阱和假设

- 被否决的办法：把 `runHooksInBackground` 挪到 `finishEntry` 之前，在持有轮次时写记录。它也能修，但会让“main 已经前移、条目还没标记”的窗口变长，进程在这里被杀时条目会被标成失败。
- 两次合入的后台命令仍可能同时在主 checkout 上运行（比如两个 `bun run build` 一起跑）；这是另一个问题，不在这里改。
