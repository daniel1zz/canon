## 为什么

C-618 计划的 A 步（D-144）：文档类型要能声明段落里每一项的格式，canon 用同一个匹配器读出元信息，取代各功能各写一个解析器。

## 要改什么

- 新子领域 `knowledge/documents/items`（代码 `src/knowledge/documents/items`）。
- BR-2546：`types.<类型>.items` 的声明格式和配置校验；内置类型的声明写在代码里。
- BR-2547：匹配器，按声明把一段分成项、对模板、取出槽位；读不出的记为未知。
- BR-2549：`canon check` 按 `on_mismatch` 提示（只看这次改动的文档）或报告（全部文档）。
- BR-2550：`canon show <编号> --json` 输出文档和读出的各项。
- BR-2551：内置的变更类型声明教训的格式，第一条内置声明。
- 行为哈希不在这一步改：这一步没有给任何规则段落写声明，哈希不受影响；去掉元信息的哈希在 B 步改（C-618 计划已改）。

总览不受影响：新子领域是 `knowledge/documents` 里读文档的一部分，没有新部件、数据位置不变。

## 方案依据

- 沿用 D-144 定下的部分：按段落声明项的格式、元信息由作者写在正文、读不出不猜、默认只提示。
- 新的选择：元信息槽位只能写在可省略段里、文字槽位只能在外面。这样同一个模板能读带标记的新写法和没有标记的旧写法，B 步改哈希时只要去掉可省略段，迁移前后哈希就不变。最坏的失败：一种元信息天然要写在正文中间、没法放进可省略段，这种声明写不出来；目前要支持的四种（教训去向、方案采用否决、例子编号、成功标准的编号和状态）都能放进可省略段。
- 证据：四种写法都按这个约束写成了 BR-2546、BR-2547 的例子。
- 什么结果能证明选错了：B 步迁移 canon 仓库时，有规则的行为哈希在迁移前后不一样；或者 C 到 F 步里有一种元信息要靠可省略段外的槽位才写得出来。

## 陷阱和假设

- 可省略段的对法要按 BR-2547 的顺序选：先让出现的可省略段最多，再靠前的出现，再前面的槽位尽量长；用一个贪婪的正则一次匹配做不到“可省略段尽量出现”，要按可省略段出现与否的组合依次试。
- 元信息槽位的值不符合类型时，算作这个可省略段没出现，不算未知（BR-2547）。
