## 为什么

规则文字的改动，产品行为不变。从事件 #978 起的事件表里，10 次冲突拒绝集中在“每加一个功能就追加一行”的中心登记文件上，`canon/rules/work/stats/BR-2067.md` 有 2 次冲突：它把每个拒绝原因手抄了一遍，每加一个检查都要改这条规则。代码里本来就有这份列表（`src/work/stats/checks.ts`），规则只需指向它；负责人要求同样处理其他手抄代码列表的规则。

## 要改什么

涉及的子领域：work/stats、work/session。

- BR-2067：检查的名字和顺序不再抄写，改为指向 `src/work/stats/checks.ts` 的 `LAND_STAGES`（各步，按合入顺序）和 `CHECKS`（全部检查）；“用顿号连在一起的”改成“`LAND_STAGES` 里同一组的”。规则的意思不变。
- BR-2019：默认的 `regenerable` 不再抄 19 个名字，改为举几个例子，完整列表指向 `src/work/session/config-keys.ts` 的 `DEFAULT_REGENERABLE`（C-135 把它搬到了这里）。
- 新测试核对规则和代码对得上：`src/work/stats/checks.test.ts` 读 BR-2067，确认它指向的文件和常量存在、它在反引号里写的每个检查名都在 `CHECKS` 里，以及 `CHECKS` 的组成；`src/work/session/config-keys.test.ts` 读 BR-2019，确认它指向的文件和常量存在、它举的例子都在默认列表里。故意把规则里的名字改错（`flor`、`.venvx`）时两个测试都失败，改回后通过。
- `canon/config.yaml` 里 `floor_skip_paths` 的依据注释补上这个例外（见下）。

查过的其他规则：用 `grep` 统计每条规则正文里反引号名字的个数，超过 8 个的有 BR-2046、BR-2045、BR-2169。BR-2046 的扩展名和跳过的目录是一条正则和几个固定目录，不随功能增长；BR-2045 列的是错误的种类，是规则本身的定义，不是代码列表的拷贝；BR-2169 的关闭关键字是 GitHub 定的，规则就是它的定义。这三条不改。

## 陷阱和假设

- 这两个测试读真实仓库里的规则文件，而 `canon/rules` 在 `floor_skip_paths` 里：只改 BR-2067 或 BR-2019 的合入不跑 floor，写错的检查名要到下一次跑 floor 的合入才被发现，被拒的会是那个无关的合入。规则指向的路径被移走或删掉时 `canon check`（BR-2171）每次合入都会拦住，常量改名或检查名写错则拦不住。

## 教训

- 让规则指向代码、再用测试核对，和“只改规则的合入不跑 floor”（BR-2164）互相冲突：测试读 `canon/rules` 时，跳过 floor 就跳过了核对 → 待负责人确认是否固化（可选：把这类核对做成 `canon check` 的一部分；或者让 `floor_skip_paths` 不覆盖被测试读取的规则文件）。
