## 为什么

负责人按版本逐步开发（MVP、v1、v2 提前规划），现在的 baseline 只有一份“当前真相”，看不出规则属于哪个版本，版本自己的 PRD（目标、范围、不做什么）没处放，发布后也没有快照和进度。设计和被否决的方案见 D-61（`proposed`，等负责人接受）。D-61 分三个变更落地，这是第一个：版本文档类型、规则上的标签、检查和评审。进度命令、`canon show` 的显示、发布命令和 skill 在后两个变更。

## 要改什么

- 新的内置文档类型 `release`（`R-n`，`canon/releases/R-n.md`，状态 planned、active、shipped，六个必有的节）。没用声明类型（`types:`）：它写不了只能由命令写的 `shipped_at`，也没有 `canon release` 命令和发布后的冻结检查（D-61）。
- `canon release new --title` 建版本文档，`canon release list` 列出（BR-2319、BR-2320）。
- 版本文档的 front matter 检查（BR-2321）；规则上可选的 `release`、`changed_in`（BR-2322），标签引用必须存在（BR-2323），标签不影响执行状态（BR-2324）。
- 已发布版本的三节和规则标签集合与 `shipped_at` 那个提交比较，不许变（BR-2325、BR-2326）。
- 合入时的规则评审也收 `canon/releases`（BR-2009、BR-2010、BR-2074 的触发范围同步），评审的提示给出版本全文和标着它的规则（BR-2327）。
- 新子领域 `knowledge/releases`（代码 `src/knowledge/releases`）：版本是知识库里的一种文档，它的检查、进度和发布都围着同一个概念；规则评审的提示放在 `knowledge/review`，因为代码在那里。

## 陷阱和假设

- 前缀 `R` 现在是内置的：项目里已声明前缀 `R` 或目录 `releases` 的类型，升级后会报配置错误。
- 冻结检查要读 `shipped_at` 那个提交；浅克隆里没有它时 `canon check` 报 `release-frozen`，不静默放过。
- 本变更只让 `status: shipped` 能被检查；谁能把版本改成 shipped（负责人确认）是第三个变更的事，在它合入之前手写 `status: shipped` 能合入。
