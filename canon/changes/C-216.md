## 为什么

C-182 新增了四个检查名（`evidence`、`activate`、`rule-changed`、`passes`），却不能在同一次合入里把它们写进 `canon/config.yaml` 的 `check_reviews`：其他会话装的旧 canon 读到不认识的检查名，所有命令都以退出码 2 失败（BR-2069、BR-2045），直到重新构建；这些日期后来由 C-215 单独补上。C-181 碰到的是同一类问题（配置键），C-210 的 BR-2248 已经把配置键这一半做成了合入检查，检查名这一半还只靠文字。负责人 2026-11-04 对这条教训选择了“做成检查 (推荐)”。

## 要改什么

- 规则 BR-2248（work/land）扩展：除了配置键，被合入的树里 `check_reviews` 用到的检查名，如果在被合入的树里声明了、而 main 的 base 提交里没有声明，合入同样以原因 `config-key` 被拒（退出码 1），提示先合入只新增检查的变更，第二次合入再写复审日期。检查名的声明是任何目录下名为 `checks.ts` 的文件里用双引号写的名字（canon 里是 `src/work/stats/checks.ts`）。标题和例子跟着改。
- 代码：`src/work/land/config-first.ts` 新增读两棵树里 `checks.ts` 的检查名（`git grep`，每棵树一次）和被合入的树里 `check_reviews` 的名字；`src/work/land/land.ts` 的 `verifyChange` 在同一处调用，信息同时列出键和检查名。
- 测试：`src/work/land/config-first.test.ts` 按 BR-2248 新增的例子加用例。

## 陷阱和假设

- 沿用原因 `config-key`，不新增原因：两种情况是同一个检查（`canon/config.yaml` 写了旧 canon 不认识的名字），新增原因本身又是一个新检查名，它的复审日期也得分两次合入才能写上。
- 只认 `checks.ts` 里双引号写的名字；现在这个文件里双引号字符串都是检查名，注释用反引号。有人在里面写别的双引号字符串，最坏是把它当成检查名：只有它同时出现在 `check_reviews` 里才会拒绝，不会误拒正常合入。
- main 的 base 提交里没有 `checks.ts` 时不比较检查名（用 canon 的普通项目）；和配置键那一半各自判断。
- 两边都没声明的检查名（拼错）不在这里报，由 BR-2069 的配置错误处理。
