## 为什么

#71：`src/knowledge/review/code-review.ts` 用“需要给全文的文件”列表判断这次合入有没有改代码。删掉的文件、二进制文件和超过 100 KB 的文件都不在这个列表里，所以一次只删除代码、或只改这几类文件的合入会输出 `no code changed; nothing to review`，评审命令根本不跑。BR-2070 说的是“没有改动 `canon/` 以外的文件时”才不评审，这里矛盾。

baseline 核对（N-4）还发现：代码评审提 issue 时正文写什么、调用 `gh` 失败时怎么办，都没有规则；BR-2070 的几条例子（超过 100 KB 的文件、只改 `canon/` 下文件、脚本以退出码 1 结束）没有测试。

## 要改什么

- `code-review.ts`：“有没有改代码”按 `CANON_BASE..CANON_HEAD` 里 `canon/` 以外所有改动过的路径（含删除）判断，全文列表只决定给评审哪些全文。
- BR-2070 补例子：只删掉代码文件、只改二进制或超大文件时照样评审。
- 新规则：代码评审提的 issue 和评论的正文格式。
- 新规则：列出未关闭 issue、新建 issue、评论失败时报错、退出码 1。
- 补测试：超过 100 KB 的文件、只改 `canon/` 下文件、脚本在评审命令失败时以退出码 1 结束。

## 陷阱和假设

- 按标题搜同根因 issue（`gh issue list --search`）失败时，现在的代码当作没找到、新建 issue。这是要负责人决定的（报错还是照样新建），这次不改，也不写进规则。
- `src/work/land/` 的 agent 同时在改 land，这个变更不碰那里。
