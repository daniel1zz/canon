## 为什么

product.md 说 canon 在两个边界检查结果，其中一个是“合入 main 时”。可是到现在为止，agent 在主 checkout 里 `git commit`、`git merge`、`git push . x:main`、`git update-ref` 都能直接移动 main，绕过 floor、`canon check` 和规则评审。lore ADR-052 实测（E3、E7）：main 签出在别处时 `update-ref` 照样成功、留下反向的暂存改动；`prepared` 状态的 `reference-transaction` hook 能拦住这些移动，但要忽略新旧值相同的行。决策见 D-16。

## 要改什么

- 新增 `src/cli/install/githook.ts`：hook 脚本、标识行、状态（current / missing / old / foreign）、安装。
- `canon init`、`canon install`、`canon update` 安装它，`canon update --check` 报告它（BR-2123）；已有别人的 hook 时退出码 5、写明路径、什么也不写（BR-2124）；只有它过期时 `canon update` 直接装好、不开变更（BR-2086）。
- hook 的行为（BR-2126）：只在 `prepared` 状态看 `refs/heads/<main>`；放行删除、不动的行、main 还不存在、main 上还没有 `canon/config.yaml`，其余要求 `CANON_LAND_MAIN` 等于新值。
- `canon work land` 只在它移动 main 的那条 git 命令里设置 `CANON_LAND_MAIN=<新提交>`（BR-2125）。
- 改 BR-2080、BR-2084、BR-2086 和 `cli/install` 的 README，把 git 守卫写进去。

合法移动 main 的地方，逐个检查过：

| 位置 | 是否移动 main | 处理 |
|---|---|---|
| `moveMain` 里的 `git update-ref`（main 没签出，比较并交换） | 是 | 带标记 |
| `moveMain` 里签出 main 的 worktree 的 `git merge --ff-only`（BR-2039） | 是 | 带标记 |
| `land --finish` 的关闭提交 `canon: close C-n` | 否，在变更分支上，随后一起合入 | 不需要 |
| 合入时的 `git rebase` | 否，只动变更分支 | 不需要 |
| `canon init` | 不提交；用户之后在 main 上的第一次提交时 main 里还没有 `canon/config.yaml` | hook 放行 |
| `canon update` | 通过 `land` 合入 | 同上两行 |
| `canon work drop` 的 `update-ref` | 只写归档 ref、删变更分支 | 不需要 |

## 本机实测（git 2.50.1，Apple Git-155，2026-11-03）

临时仓库里 `canon init --floor true` 后提交：

| # | 操作 | 结果 |
|---|---|---|
| M0 | 仓库的第一次提交（还没有 canon） | 退出码 0 |
| M1 | `canon init` 之后提交，把 canon 放进 main | 退出码 0（main 上还没有 `canon/config.yaml`） |
| M2 | 在 main 上 `git commit` | 退出码 128，`canon: refusing to move main …`、`fatal: ref updates aborted` |
| M3 | `git merge --no-ff x`（在 main 上） | 退出码 128，`fatal: ref updates aborted by hook` |
| M4 | `git update-ref refs/heads/main <x>` | 退出码 128，`fatal: ref updates aborted by hook` |
| M5 | main 签出时 `git push . x:main` | 退出码 1，git 自己就拒绝（`branch is currently checked out`） |
| M5b | main 没签出时 `git push . x:main` | 退出码 128，hook 拒绝（stderr 有 canon 的提示） |
| M6 | `git reset -q HEAD`（不动的行） | 退出码 0 |
| M7 | `git pack-refs --all` | 退出码 0 |
| M8、M9 | 删除、移动别的分支 | 退出码 0 |
| M10 | main 签出在主 checkout 时 `canon work land --finish`（快进路径） | 退出码 0，`landed … on main` |
| M11 | 主 checkout detached 时 `canon work land --finish`（`update-ref` 路径） | 退出码 0，`landed … on main` |
| M12 | 另一个 clone 里 `git pull --ff-only` 远端的新 main | hook 拒绝 |
| M13 | `git commit --no-verify` 在 main 上 | 退出码 128，仍被拒绝 |
| M14 | `git -c core.hooksPath=/dev/null pull --ff-only` | 退出码 0，绕过了守卫 |

## 陷阱和假设

- `git pack-refs` 会产生一行“新值等于当前值”的 main 和一行“新值全零”的 main，所以 hook 要用 `git rev-parse` 读 main 的当前值来判断“不动”，并放行删除；只比较 hook 收到的旧值不够：`git commit` 时旧值也可能是全零（文档：强制更新或新建时旧值是全零）。
- hook 文件不在提交里：每个 clone 都要 `canon install`；`canon update` 只有它过期时不开变更。
- 测试里要在 main 上直接造提交，要用 `git commit-tree` 加带标记的 `update-ref`（见 `src/cli/install/update.test.ts`）。
- 同步远端的 main（`git pull`）现在也被拒绝，见 D-16 的后果；要不要给远端同步开一条路，留给负责人决定。
- 拒绝提示里有反引号会被 sh 当成命令替换执行，提示里不要用反引号。
