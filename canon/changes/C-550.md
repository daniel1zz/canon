## 为什么

顾问复核 C-546（D-118）时用两条真实的数据库连接复现了三处漏洞：定档、结案、问负责人都是先在锁外检查、再进写事务，中间别的会话升档、记反对或也去问负责人都看不到（#222、#223、#224）；子 agent 可以拿它上级会话的支持结 B 档（#225）；按不成立结案的支持和负责人批准只绑定引文，文档改了也照样能用（#226）。

## 要改什么

- 读状态、检查和写入放进同一个 immediate 事务，git 在事务前按同一个 main 提交读（BR-2477、BR-2478、BR-2480）。
- 支持按会话编号去掉同一会话的；子 agent 和派出的 worker 不能凭支持结 B 档，带负责人批准的照旧（BR-2478）。
- 支持和 `canon finding ask` 记下意见挂着的文档在 main 上的版本，按不成立结案时文档变了就不算（BR-2479、BR-2480）。
- 代码在 `src/knowledge/review/findings/tier.ts`、`close.ts`、`commands.ts`，文档版本的读法在新的 `docs.ts`；`src/work/db.ts` 加 `docs_at` 两列。

总览不受影响：总览只写到意见带档位和这两张表。

## 教训

我自己写 C-546 时只做了单连接的测试，并发和父子会话这两类绕过是顾问用双连接和真实身份复现出来的。可以做成机制的部分：canon 已有“共享状态先查后写”的模式（例如结案前复查 closed_at），这次是同一类错误；能否加一条检查（例如测试工具里提供 between 这样的插入器，要求改协调数据库的命令都有一条并发测试）要先问负责人，这里只记下，不自行固化。
