## 为什么

C-603 计划的 C 步（D-137）。`floor_timing: after` 下 main 的后台测试失败时，现在只记下来，等某个会话开修复 main 的变更向前修（D-31）。实测 11 月 8 日以后 11 次失败里 8 次是不稳定的计时测试，下一轮自己就过了；真正要修的 3 次，修的人往往不是写坏它的会话。D-137 定的方向是：不稳定测试不算 main 坏；真坏了就找出那次合入，撤回它，把变更连同失败退回去由模型纠正。

## 要改什么

- BR-2534（新）：后台测试失败时，把报告里失败的测试文件用 `test_command` 原样重跑一次，都通过就记 `floor.flaky`、按通过处理，`canon work due` 提醒 7 天去开 issue。
- BR-2535（新）：真失败时在通过的提交和失败的提交之间、按合入二分，找出第一个让它失败的合入；探测用失败的测试文件，测试之前就失败时用 `typecheck_command`。先确认在通过的提交上探测通过，才相信探测。
- BR-2536（新）：杂务和碰到单向门类别的合入不自动撤回；其余在临时 worktree 里撤回、变更文件状态改回 `open`、检查撤回后的树（类型检查、失败的测试、`canon check`），都过了才比较并交换移动 main 并推送；在撤回后的 main 上把 L 重放到 `change/C-n` 分支；`canon work due` 列出 `reverted:C-n`。撤回提交带 `Canon-Reverts:` 标记，后台测试中途被杀时下次补做。
- BR-2220：被记为不稳定测试的失败不记 main 没通过。
- D-137 随这一步接受；它的决定、后果和新补的方案 5 一起改了。work/watch 的 README 和总览的后台 floor 一节跟着改。
- 代码：`src/work/watch/revert.ts`（定位、撤回、重放、补做、提醒的数据）、`src/work/watch/run.ts`、`src/work/watch/watch.ts`（重跑和接上撤回）、`src/work/verify/report.ts`（报告里记下失败的测试）、`src/work/land/checks/floor.ts`（交出失败的文件）、`src/work/reminders/due.ts`。

## 方案依据

沿用：后台测试的临时 worktree 和单个 watcher（BR-2219）、合入移动 main 的比较并交换和 git 守卫标记（`moveMain`）、合入后的推送（`pushMain`）、测试报告（BR-2339）、编号从协调数据库分配（被撤回变更的编号不会被别人重用）。

新选的：撤回是在 main 上追加反向提交，不改历史，已经基于坏提交开工的分支只需 rebase。独立评审提出的另一种做法（合入先进暂存分支、main 只前进到测过的提交）写进 D-137 的方案 5，否决原因见那里。评审还指出两处原设计的错，已改：按合入范围撤回会把变更文件一起删掉，所以变更文件改为从合入的提交取回、状态改为 `open`；在原合入提交上重建分支会是空的，所以分支改为在撤回后的 main 上重放。

最坏的失败：撤回了一个无辜的合入。防护是三层：先确认探测在通过的提交上通过；二分的结果要求它探测失败、它前一个通过；撤回后的树必须通过类型检查、失败的测试和 `canon check` 才移动 main。依赖它的后续合入在第三层就会被挡下，退回向前修。

已知的限制：每条“main 没通过”记录最多自动撤回一次。一批里有两个坏合入时，撤回第一个后重测还会失败，就退回向前修：第二个坏合入的提交里已经包含第一个，单靠探测 main 上已有的提交分不出它，要在临时分支上撤掉第一个再探测，这要另外设计。评审按 D-137 估的合入出错率（约 6%）算过，E 步去掉合入前的测试后约 12% 的批次会有不止一个坏合入。能证明这里需要改的结果：C 步上线后到做 E 步之前，`revert.skip` 里原因是「已经撤回过一次」的，占 main 没通过次数的明显比例（例如超过四分之一）时，先实现连续撤回再做 E 步。

持久化的东西怎么演进和恢复：协调数据库只多了几种事件（`floor.flaky`、`revert.start`、`revert.skip`、`land.revert`），表结构不变，旧数据不用迁移；事件丢了只影响 `canon work due` 的提醒。main 上只追加提交、不改历史，撤回本身也能再被撤回。撤回到一半被杀时，main 上的撤回提交带 `Canon-Reverts:` 标记，下次后台测试开始前按它补建分支和事件（有测试）；main 还没移动就被杀时什么都没发生，下次照常重测。

撤回和合入会碰到一起：撤回移动 main 时，正在合入的会话会收到「main 在合入期间前移，再合入一次」（`main-moved`），重新合入即可；撤回自己遇到 main 前移时从新的 main 重做，最多 3 次。
