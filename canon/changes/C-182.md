## 为什么

负责人先设计好整个 baseline 再开发，baseline 要约束执行。现在生效规则没有测试就拒绝所有合入（BR-2005），先写的 baseline 合不进 main；也没有地方记录一条规则有没有被执行过、执行后有没有被改过，做了一半的工作只能靠任务清单和 handoff 看。设计和取舍见 D-32。

## 要改什么

- 决策 D-32（修改 D-1 的“验收就是测试”）。
- `canon/product.md` 的 P1、P5 按负责人确认的写法修改。
- 规则状态加 `planned`；规划中的规则不报 `rule-untested`，`canon context`、`canon show` 标明。
- 加 `--finish` 合入时，`rules:` 里合入后生效、且行为哈希没有匹配通过记录的规则，每条都要有证据（本变更新增或修改了点名它的测试，或 `untested:` 规则在 `## 验收` 里有一行）；关闭提交把通过记录写进变更文件的 front matter。
- rebase 后要执行的规则行为哈希变了，拒绝合入。
- 规则审查判断只改 `## 规则` 的修改是措辞还是行为；措辞修改沿用上一条通过记录。
- 新的进度命令，按领域和变更列出规划中 / 已通过 / 待重新执行。
- 为现有生效规则写迁移的通过记录。
- 规则：在 knowledge/documents、knowledge/check、knowledge/query、knowledge/review、work/land 里新增和修改，代码改动前列出编号。

## 陷阱和假设

- 代码要等并发的 knowledge/query、knowledge/review 修复组合入以后再改，免得改到同一批文件。
- 假设规则审查能可靠区分措辞和行为；判错时通过记录里留有“审查判定为措辞修改”，可以事后查。
- 迁移记录假设现有生效规则的测试真的验证了规则；D-12 引用过“测试全绿却什么都没测”的先例，迁移不证明这一点。
