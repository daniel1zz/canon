## 为什么

负责人先设计好整个 baseline 再开发，baseline 要约束执行。现在生效规则没有测试就拒绝所有合入（BR-2005），先写的 baseline 合不进 main；也没有地方记录一条规则有没有被执行过、执行后有没有被改过，做了一半的工作只能靠任务清单和 handoff 看。设计和取舍见 D-32。

## 要改什么

- 决策 D-32（修改 D-1 的“验收就是测试”）；实现时补上先合后测下的状态、审查判断怎么进关闭提交、迁移带 `untested:` 的规则、D-12 不变。
- `canon/product.md` 的 P1、P5 按负责人确认的写法修改。
- knowledge/documents：BR-2001（规则状态多了 planned），规则的三种状态 BR-2235，行为哈希 BR-2236，通过记录的格式 BR-2237。
- knowledge/check：BR-2005（规划中不报 `rule-untested`）、BR-2033、BR-2034（规划中也要规则段和例子）。
- knowledge/query：BR-2007、BR-2213 和新的 BR-2238（`canon context`、`canon show` 标明规划中）。
- knowledge/review：BR-2036（规则索引带规划中的规则），BR-2010、BR-2074（带措辞记录时的例外），新的 BR-2239（评审判断措辞还是行为）。
- 新子领域 work/execution（代码 `src/work/execution`）：规划中改生效 BR-2240，`--finish` 的证据 BR-2241，关闭提交写记录 BR-2242，措辞修改 BR-2243，rebase 后规则被改 BR-2244，迁移 BR-2245，执行状态 BR-2246，`canon progress` BR-2247。
- 合入的新拒绝原因 `evidence`、`activate`、`rule-changed`、`passes` 加进 `src/work/stats/checks.ts`；`land.ok` 事件记下 `base`，供 BR-2241 找同一变更之前的合入。
- 迁移通过记录：本变更的关闭提交按 BR-2245 自动写。

## 陷阱和假设

- 代码要等并发的 knowledge/query、knowledge/review 修复组合入以后再改，免得改到同一批文件（已合入）。
- 本变更要用源码里的 canon 合入（`bun src/cli/main.ts work land --finish`）：PATH 上旧的 canon 不会写通过记录和迁移记录。
- 新的检查名不写进 `canon/config.yaml` 的 `check_reviews`：PATH 上旧的 canon 读到不认识的检查名会以退出码 2 失败（C-181 的教训、BR-2224）。
- 假设规则审查能可靠区分措辞和行为；判错时通过记录里留有“审查判定为措辞修改”，可以事后查。
- 迁移记录假设现有生效规则的测试真的验证了规则；D-12 引用过“测试全绿却什么都没测”的先例，迁移不证明这一点。

## 教训

- 关闭提交在 rebase 之前算记录：变更分支上“已有相同记录、不用执行”的规则，rebase 后可能因为 main 改了它而变成要执行却没有证据；最初只核对已写的记录，测试才发现 → 已改进 BR-2244（核对 `rules:` 里每条规则 rebase 前后的状态和哈希）：BR-2244 本身是 D-32 要求的行为，这里只是把它写完整，不是为固化教训新加的机制。
- D-32 原先假设 main 上的测试都通过了 floor，D-31 的先合后测让这个假设不成立 → 写进 BR-2246（`after` 下记录要等 `refs/canon/green` 覆盖才算已通过）和 D-32 正文：这是任务交代要定下的设计点，不是为固化教训新加的机制。
- 新的拒绝原因不能在同一次合入里写进 `canon/config.yaml` 的 `check_reviews`：PATH 上旧的 canon 不认识这些检查名，会以退出码 2 让所有会话失败（同 C-181 的教训） → 待负责人确认是否固化（例如让合入时“新配置键先合入”的检查也覆盖 `check_reviews` 里的检查名）。
- 改合入本身行为的变更要用源码里的 canon 合入，PATH 上旧的 canon 不会执行新行为（这里是写通过记录和迁移记录） → 只靠文字：只在改 `canon work land` 自己的变更里发生，无法从合入的树判断“这次合入需要新代码来做”。
