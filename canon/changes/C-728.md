## 为什么

负责人：“我的意思是主AGENT应该充分发挥主观能动性，能真正智能调度，而不是等着我发现问题 应该是一个固化的机制”。待办清单里要判定的事积了 114 条、最老 8 天，有空位却没人派活，主会话一轮做完就停下等负责人。待办清单只是被打印，没有任何东西让会话在停下前处理它（D-170）。

## 要改什么

- 已有的 Stop hook `canon goal check --hook` 在目标没拦下会话时做调度检查：待办清单里有这个主会话现在能做的事（有空位时能开始的变更、不需要别的会话的 judge 项）就拦下一次，列出最多 5 行；它自己有了进展才再拦，没进展放行；worker、关了调度、没有能做的事时放行（BR-2655，D-170）。
- `canon goal dispatch [on|off]`：负责人要求暂停时关掉这个会话的调度检查（BR-2660）。
- BR-2519：没有目标时不再直接放行，而是接着做调度检查。
- 协调数据库加 `dispatch_state` 表；`dispatch.hold`、`dispatch.off`、`dispatch.on` 事件。
- hook 本身不用重装：每个项目已经装了 `canon goal check --hook`（BR-2520）。

## 陷阱和假设

- 进展只看这个会话自己（和它的子 agent）记下的事件和它的工作树，不看 main：别的会话的合入会推进 main。
- 会话身份是 `agent:<会话编号前 8 位>`，子 agent 是 `agent:<前 8 位>:<名字>`。

## 教训

- 子 agent 在 canon 里一律是 worker，不能写规则；`canon work due` 却把 `rules: []`、实际要新规则的变更列为可派（C-647 被 BR-2501 挡回、交回设计）→ 待负责人确认是否固化
