## 为什么

C-708 把 5 条 canon-* 常驻规则算进每个会话固定加载的文字以后，canon 自己的会话一共要加载 17673 字节，而 session_text_budget 是 12000（BR-2256、BR-2257、D-167）。负责人 2026-11-28 回答问题 #82：「压缩工作说明和 skill 描述（推荐）」。

## 要改什么

按 canon-context-optimizer 压缩，原文是提交 c0258b27 里的 `src/*/guide.ts` 和 `.claude/skills/canon-*/SKILL.md`。

- 11 个 canon-* skill 的 description 只写什么时候该触发：保留每个触发场景和用来区分两个 skill 的 NOT for 边界，删掉同义的触发词。从 4699 字节降到 3034 字节。
- 工作说明改写最长的 4 行（Change 和杂务、问人、合入后评审、canon work test），命令、参数、条件和顺序都不变。从 5960 字节降到 5775 字节。
- 合计从 17673 字节降到 15823 字节，仍然超出预算 3823 字节。工作说明原本就紧凑，再压就得删要求；剩下的差额要么调预算，要么删要求，留给负责人决定。

不改行为，不改规则。

## 核对

- 脚本比对了改写前后工作说明里的命令、参数、占位符、配置键和路径，一个没少。
- 删掉和改写的条目交给另一个模型（sonnet 子 agent）评判：工作说明的 9 项都只是解释，另外指出“as the question”要保留；skill 描述里 canon-rules（PRD、acceptance criteria、what should happen when）、canon-triage（review issues、break this into issues）、canon-product（竞品）、canon-diagnose（报 bug）、canon-domains（reorganising）的触发场景要补回。这些都已补回。
- 第 5 步的行为对比没有做：工作说明只改了措辞，评判没有发现丢掉的指令；skill 描述只影响什么时候加载，场景都已补回。

## 教训

- 工作说明和常驻规则原本就紧凑，压缩省不下多少；文字预算超出靠压缩解决不了，要么调预算，要么由负责人决定删哪些要求 → 只靠文字：预算该定多少是负责人的取舍，做不成检查
