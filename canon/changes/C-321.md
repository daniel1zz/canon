## 为什么

#118：批量代码评审的互斥用一个锁文件（`openSync(path, "wx")` 之后再另一步写进程号）。别的进程恰好在这两步之间读到空文件，把它当成持有者已经不在，删掉活着的锁并自己拿锁，结果两个评审同时评审同一个范围、提两份重复的 issue、其中一个在比较并交换引用时失败。释放时的 `rmSync` 也会删掉已经属于别人的锁；接手死锁（先删再重试）在两个等待者之间同样有竞态。

## 要改什么

- 协调数据库新增 `code_reviewer` 表（和 `watcher` 表同样的做法：id = 1、pid、pid_start、started_at）。
- 认领在一个 `.immediate()` 事务里：没有持有者、持有者是自己、或持有者的进程确认已经不在（`isGone(...) === true`，读不出进程表按还在算，D-11）才写下自己；释放只删 pid 和 pid_start 都是自己的那一行。等待、`busy`、30 分钟上限的行为不变。
- `reviewRunning`（`canon brief` 判断要不要后台启动评审）改读这张表；`scripts/code-review.ts` 把工作区的协调数据库传给 `reviewBatch`。删掉锁文件的代码。已有的 `canon/code-review.lock` 旧文件不再读、不删（留在 git 公共目录里没有影响）。
- 就地修改 BR-2314 里关于互斥的句子，加五个边界例子；测试里有真正的并发测试（三个进程同时启动）。

## 陷阱和假设

等待者每 2 秒轮询一次，所以并发测试里评审命令要睡够 3 秒，等待者才会真的等。

## 教训

先写入再读的两步锁文件会让读到空文件的人误判持有者已死 → 这次改用数据库事务，由 BR-2314 的并发测试保证；是否加检查禁止新的锁文件写法，待负责人确认是否固化
