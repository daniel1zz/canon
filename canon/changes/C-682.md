## 为什么

D-159 第 3 步。第 2 步（C-681）让新建命令要求新建时表态的字段，但复制文件、手写文件、`canon rule apply` 写出的新文档，以及 main 在分支开始后才声明的字段，都绕得过新建命令。合入是唯一一定会经过的一步，所以这里检查本次新增的文档（BR-2624）。

负责人 2026-11-21 选择上线不设过渡：本检查上线时已经在做、只在分支上的变更文件和其中新建的规则、决策，第一次合入各被拒一次，照拒绝信息里的 `canon doc set` 补上（问题见旁注：上线时两个项目在做的变更都会被拦一次）。

同时修复评审意见 #229：BR-2623 要求决策写了决策编号就给 `revised_because`，BR-2492 对只指向自己、不存在的编号或不是决策的文档不要求，两者矛盾。

## 要改什么

- 合入在 BR-2463 的提醒之后、排队之前，对本次新增的文档按 main 的类型声明找缺的新建时表态字段，缺了就拒绝，原因 `fields`，每个字段一行 `canon doc set` 和允许的格式（BR-2624）。
- `revised_because` 只在 `amends`/`supersedes` 指向存在的别的决策时要求，新建命令和合入检查一样（BR-2623，#229）。
- 测试的 `startNew` 建变更时写上两个 `none:` 字段，和真实会话一样。
