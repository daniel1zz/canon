## 为什么

D-148 决定执行只有变更：变更写明属于哪个版本或模块、修哪些 issue、依赖哪些变更，并且由命令写入，不靠会话事后补（会话自己写的字段填写率只有 24%，命令写的接近 100%）。现在变更只能用 `plan`/`steps` 挂到计划上，没有地方写版本、模块、issue 和依赖；`canon change list` 和 `canon brief` 会把还在等别的变更的工作当成可开始，被没任务的会话提前拿走；没挂版本的变更等于 AI 自己定的交付范围，负责人在总览里看不到（P7）。这是 C-626 计划的 A 步，B、C、D 步都依赖它。

主会话在设计中途补了一个 D-148 没覆盖的需要：有的后续工作要等负责人确认，而不是等一个变更合入，所以依赖也可以是一条成功标准。

## 要改什么

- 新子领域 `knowledge/changes`（D-149 说明为什么不放进 `knowledge/plans` 等现有领域），规则：
  - BR-2561 关联的写法：`release` 或 `feature`（只写一个）、`issues`、`depends_on`（变更或成功标准 `R-n/S<k>`、`F-n/S<k>`）、放弃的变更上的 `done_by`；格式和矛盾报 `file-invalid`，版本、模块、成功标准不存在报 `ref-dangling`；依赖的变更不存在不报。新键加进 canon 保留的字段。
  - BR-2562 `canon change new`、`canon work start --title` 的 `--release`、`--feature`、`--issue`、`--depends`；`canon change new` 本来就能提前建变更（不建 worktree，守卫的 main 上按 BR-2409 拒绝），开工时关联照旧。
  - BR-2563 `canon change link` 修改已有变更的关联，`--done-by` 写在放弃的变更上，`none` 删掉一项；会成环时拒绝。
  - BR-2564 依赖按 main 最新提交判定：变更 `done` 才算满足，放弃的按 `done_by` 算，只在分支上的算没合入；成功标准已满足才算满足。`canon change list` 标 `waiting for …`（`--json` 有 `waiting_for`），`canon brief` 的取活那一行不列它们、另起一行列出；工作说明里取活跳过 `waiting`。
  - BR-2565 依赖成环：`canon check` 报 `depends-cycle`，合入在 rebase 后的树上同样拒绝。
- 改 BR-2386：没有计划的变更也可以写 `release`，不再报 `file-invalid`；冻结和已取消的检查仍只管有计划的变更（BR-2512 原文就是“计划变更”）。
- 改 BR-2505：`canon overview` 多一节“当前这一批”，列出没挂版本或模块的未结束变更（含只在分支上的），`--json` 有 `current_batch`。
- D-149：领域、依赖读哪棵树、成环看哪棵树、依赖成功标准；它修改 D-148（`revised_because: requirement`）。
- 架构总览“知识文档”和“主要流程”里变更文档的部分。

## 陷阱和假设

- `release` 这个键原来只给计划变更用（D-79）；现在任何变更都能写。冻结（BR-2386）和已取消（BR-2512）只看有合格计划的变更，没有计划的变更写了已发布或已取消的版本不会被拦：按 D-139 这只是关联，不拒绝。E 步去掉计划时要重新决定这两条检查是否推广到所有变更。
- 依赖的变更不存在不由 `canon check` 报（它可能只在别的分支上，D-149），写错编号只在列表里显示 `(not found)`。
- 依赖满足按 main 最新提交判定，所以在一个落后的 worktree 里 `canon change list` 也按 main 算；`listedChanges` 多了一个 main 语料参数，`canon change list` 传 `mainCorpus`。
- `canon change new` 在一个变更的 worktree 里提前建的变更，要等那个变更合入 main 才出现在 `canon change list` 里、才能开工。
- 成功标准依赖靠 BR-2510 保证只有负责人能把待负责人改成已满足；如果以后放宽 BR-2510，这条依赖就不再只等负责人。
- `canon brief` 的取活那一行的文字没变（BR-2149 的例子照旧），等依赖的变更只是不出现在那一行。

## 教训

- D-148 定方向时只想到“等变更合入”，实现时才发现还有“等负责人确认”这种依赖 → 由 D-149 方案 2 和 BR-2564 补上；设计时把“依赖可能等什么”列全只靠文字：原因是需要的种类无法事先枚举，canon-design 的检查表能提醒但判断不了是否列全。
