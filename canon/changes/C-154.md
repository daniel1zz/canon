## 为什么

issue #65：仓库里有悬空的符号链接（如 `src/dangling -> nowhere`）时，`canon check` 找测试文件和检查反引号路径都对每个目录项调用 `statSync`，抛出 ENOENT，以内部错误退出（70）；循环链接（`src/loop -> .`）会让遍历一直递归下去，同样崩溃。合入关卡因此被一个无关的链接卡死。

## 要改什么

- `src/knowledge/check/check.ts` 的 `findTestFiles` 和 `src/knowledge/check/paths.ts` 的 `topDirs`、`fileNames` 改用目录项自己的类型，不跟随符号链接；链接不当测试文件读，和配置了 `tests` 时 Bun 的 glob（只返回普通文件）一致。
- 反引号路径的“现在存在”改用 `lstat`：路径本身在就算存在，悬空链接不被误报为 `path-missing`。
- 新规则 BR-2186 写下这个行为，测试覆盖悬空链接、循环链接、指向测试文件的链接和反引号里的链接。

## 陷阱和假设

- `code_root` 的布局检查（BR-2118）只递归进领域目录，名字有限，不会被循环链接拖进无限递归；那里的悬空链接按文件报 `code-layout`，是一条发现而不是崩溃，没有改。
- BR-2046 属于 config 领域，这里不改它的文字，新行为写在本领域的 BR-2186。

## 教训

- 遍历文件系统时对每一项 `statSync` 会跟随链接，悬空或循环的链接就会崩溃 → 现在由 BR-2186 的测试保证本领域的两处遍历；仓库里其他遍历只靠文字：本变更只管 knowledge/check。
