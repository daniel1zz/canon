## 为什么

- #47：`supersedes` 写的是决策自己时，`canon decision accept` 先写 accepted 再把同一个文件改成 superseded，退出码 0，结果和 BR-2027 相反。
- 基线审计：文档读写（knowledge/documents）里有几条行为没有规则描述（front matter 格式、状态取值、文件名格式、slug 长度、空标题、文件已存在、领域已存在、`decision new --supersedes` 不检查、`(no changes)`），还有几条规则的例子没有测试检查（BR-2003 消息写出另一个文件、BR-2037 决策四段和 README 术语、陷阱和假设占位、BR-2114 不数作废规则）。

## 要改什么

- `canon decision accept`：`supersedes` 等于自己的编号时退出码 2，什么也不写。
- 规则：BR-2001 写全 `file-invalid` 的条件（front matter 缺失/没结尾/不是映射、状态不在允许值里、文件名格式、slug 最多 60 字符）；BR-2027 加自取代和 `new --supersedes` 不检查；BR-2115 加领域已存在退出码 5；BR-2148 加 `(no changes)`；新 BR-2187：新建文档标题为空退出码 2、文件已存在退出码 5。
- 新测试文件 `src/knowledge/documents/documents.test.ts`（不改共享的 `src/cli/main.test.ts`，避免和别的变更冲突）。

## 陷阱和假设

- `canon change drop` 对已完成的变更、`canon rule retire` 对已作废的规则照样执行，这是产品取舍，没写成规则也没改，交负责人决定。

## 教训

- 审计发现的“没有规则描述的行为”多数是报错分支（退出码 2/5、file-invalid）：写规则时只写了正常路径 → 只靠文字：canon check 只能看出规则有没有测试，看不出代码里哪个分支没有规则。
