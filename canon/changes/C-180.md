## 为什么

issue #32：并发 `canon work start` 偶尔以退出码 4 失败，`fatal: failed to read .git/worktrees/<id>/commondir`。git 添加 worktree 时先建登记目录、写 `gitdir`，再写 `commondir`；这期间另一个 `git worktree add` 或 `git worktree list` 读到空的 `commondir` 就失败。今天本仓库 5 次 floor 拒绝里有 3 次是它（BR-2132 的并发测试），每个会话都为它白白重跑。

## 要改什么

- 子领域 work/session。`src/kernel/git.ts` 新增 worktree 锁（D-33）：`withWorktreeLock`、`addWorktree`、`removeWorktree`、`listWorktreesLocked`；不改已有函数。
- `canon work start` 的添加、失败回滚和 `canon work clean` 的删除改用加锁的版本；打开工作区、start、clean、重叠提示读 worktree 列表改用共享锁。
- 新规则 BR-2223；BR-2132（并发 start 都成功）由它保证。
- 不改 `src/work/land/land.ts`、`src/work/land/queue.ts`（另一个会话在改），`land.ts` 的批量 worktree 之后改用 `addWorktree`；`src/work/drop/drop.ts` 同样还直接调用 git。

## 陷阱和假设

- 锁文件必须是空的、非 WAL 的 SQLite 文件：共享锁靠 `BEGIN` 加一次读拿到，WAL 模式下读不挡写，就不互斥了。
- 持有锁时运行的 git 命令的 hook 里再跑 canon，靠 `CANON_WORKTREE_LOCK_HELD=1` 跳过等锁，否则互相等到超时。
- `withWorktreeLock` 的 `fn` 里不能再调用加锁的函数（同一进程两个连接，会等自己到超时）。

## 教训

- git 的 worktree 登记目录在添加期间是半成品，读它的 git 命令会直接失败 → BR-2223 和它的测试保证 canon 的 start、clean 和打开工作区不撞上（这是本变更要修的行为本身）；land 和 drop 改用加锁函数、以及不经过 canon 的 git 命令，待负责人确认是否固化。
