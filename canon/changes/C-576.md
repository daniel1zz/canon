## 为什么

评审额度用得快（负责人 2026-11-15 问“怎么评审模型用的这么快”）。实测评审接口支持前缀缓存：同一段开头的第二次调用几乎全部算作命中缓存。现在每份提示的开头是评审说明，接着是改动文档和领域全文，规则标题索引和已接受决策的标题在最后，所以同一次评审的几次调用、相邻几次评审之间能共用的开头很短。也看不到每次调用实际用了多少 token。

## 要改什么

- 提示改成：不变的评审说明 → 规则标题索引和已接受决策的标题 → 答复格式、分次说明、改动文档等 → 领域全文（`assemble`，各部分和字节数不变，拆分算法不受影响）。BR-2359 写明发送顺序。
- `scripts/review_openai.py` 请求带 `stream_options.include_usage` 和固定的 `prompt_cache_key`，每次调用在 stderr 打一行 prompt、cached、completion 三个 token 数。

## 陷阱和假设

- 实测中转对部分输入报的 token 数大得反常（2000 个重复汉字报 12 万 token、其中 11.7 万命中缓存），是否按这个数计费只能看中转后台；这次的日志行就是为了以后能看真实数字。
