## 为什么

#145 的实测：固定部分 65 KB 加领域那一块 130 KB 是 195 KB，占 250 KB 预算的 78%，下一个变更带来 56 KB 的改动文档就被拒。C-413 落地的提示（80% 的线，改动文档一律按 0）在这个案例上不会响，独立评审发现了这一点，和 BR-2375 对照后确认。所以提示按现在的规定救不了促成它的那个案例。

## 要改什么

- 线从 80% 降到 70%：默认预算下留 75 KB，盖得住 56 KB。
- 在变更的 worktree 里运行 `canon check` 时，改动文档按这项工作真实改动的文档算，量法和合入时的评审同一份代码，不另写定义；提示写明用的是哪一种。带真实改动文档的合计超过预算时，提示说合入时的评审会被拒绝，并给出和拒绝信息一样的补救办法。在 main 的检出里或没有文档改动时仍按 0。
- 预算和 `review` 取合入时用的那份：worktree 里读 main 上的配置。
- 改 BR-2375 和 D-76（仍是 proposed，由主会话接受）：写明 70% 的理由、worktree 的算法，D-76 增加否决的“80% 加 0 KB”和“按最近最大的变更估”两个方案。

## 陷阱和假设

- BR-2074 的正文只点名 `review`、时限和常驻说明清单，没有点名 `review_max_prompt_kb`；合入的代码（`reviewSettingsOn`）实际是从 main 读它的，提示用同一个函数，所以和合入一致。
- 超过预算的说法只在带真实改动文档时出现；main 上的提示仍是下限。
