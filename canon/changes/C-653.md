来自 C-626 的 E 步（D-148 迁移，计划表不再列这一步）。

## 为什么

执行只有变更（原计划 C-626，D-148）的一步。计划把「一步做没做完」存成变更状态之外的第二份状态，两份对不上（#269、#278）；D-148 定了去掉它，各步落地之前计划规则照旧有效，由这一步一并作废。canon（C-642）和 zhushenkongjian（它的 `C-1055`）已经手工把没做的步骤转成提前建好的变更，所以这一步只剩去掉计划本身和处理旧数据。

## 要改什么

修好 #269、#278（随计划一起消失，D-148 后果；关 issue 由主会话做）。

- 作废计划的规则：`knowledge/plans` 的 BR-2369 到 BR-2374、BR-2383、BR-2384、BR-2389，`work/session` 的 BR-2376、BR-2385（按计划开工），`knowledge/releases` 的 BR-2386（变更的 `release` 写法已在 BR-2561，发布只冻结规则标签，BR-2326）。`knowledge/plans` 这个子领域去掉：README 删除，作废的规则文件挪到 `knowledge/changes`（目录没有 README 读不进来，代码目录也已删除，D-149 方案 7 说的就是这里整体作废）；`work/session` 的业务清单去掉「按计划开工」。
- 新规则（`knowledge/changes` 新业务「旧计划数据」）：BR-2594 旧的 `plan`、`steps` 和 `## 计划` 节不再读、不报错，在途分支带着它们合入不被拒，`canon plan` 和 `--plan`、`--step` 不再有，两个键仍保留；BR-2595 `canon check` 对还有没做完的旧步骤的变更提示一行迁移办法。
- 改掉还在描述计划的生效规则：BR-2561（保留字段的说法、例子）、BR-2521 和 BR-2511（并入版本带走的东西里去掉计划）、BR-2512、BR-2333、BR-2335（发布条件里去掉计划）、BR-2522（停滞不再显示在计划步骤上）；只说「计划不再显示」的 BR-2328、BR-2505、BR-2506、BR-2568 不改，它们说的仍然成立。
- 代码：删掉 src/knowledge/plans 整个目录（解析、状态、检查、`canon plan status`/`link`）和 src/knowledge/documents/planlink.ts；`canon work start` 去掉 `--plan`、`--step` 和开工前的计划检查、步骤已有人做的提示；`canon change list` 去掉计划标记和 `plan_progress`，`canon brief` 去掉 `Plan C-n` 行；变更模型和写文件去掉 `plan`、`steps`；主 checkout 和分支上的变更文件都不再读这两个键；`RESERVED_FIELDS` 保留它们并写明原因；新的 `src/knowledge/changes/old-plans.ts` 只为 BR-2595 读旧表。
- 文字：canon-triage 的「写成计划」一段改成提前用 `canon change new --depends` 建变更、大目标建版本和功能模块、`canon change graph` 看进度；canon-design 里「计划的后续步骤」改成「后续变更」；`canon/architecture.md` 的计划一节换成「大工作怎么拆」，发版一节和 `src/knowledge` 代码清单去掉计划。工作说明（`src/work/session/guide.ts`）里本来没有计划。

迁移办法为什么用提示而不是迁移命令（D-139、D-152）：用 canon 的项目只有两个，都已手工迁完（canon 的 C-642、zhushenkongjian 的 `C-1055`）；迁移命令要判断一步是不是已经被别的变更做了，这正是 D-148 说的漏写链接的问题，命令判断不了，最后还是要会话逐步判断，命令只多了一份要维护、几乎不会再运行的代码。提示的代价是一行标准错误输出，判断留给会话。实测：按 BR-2595 的算法，canon 现在没有提示；zhushenkongjian 的 main 有一条，`C-1046` 的步骤 1、3 留在表里却没有已合入的变更写着它们（迁移时当作已做完留下的，属于 D-148 说的「做了却没链接」），提示里写了已做完的步骤也删掉那一行。

## 陷阱和假设

- 假设：在途分支上的变更即使还写着 `plan`/`steps`，合入时也只当普通字段带进 main，不再有任何检查；`canon change list --json` 也不再原样输出它们（它们不在变更模型里了）。
- BR-2595 的「做完」只看被检查的树里 `done` 的变更，不再区分「只在分支上写着 done」：提示只在已合入的数据上算，和原来 BR-2372 按 main 判定在 main 上结果一样。
- 作废的规则挪到 `knowledge/changes` 后，`canon context knowledge/changes` 只列生效的规则，不受影响；它们的 `business` 仍是原来的名字，业务检查只看生效和计划中的规则。

## 教训

- 计划从加上到去掉只用了约两周（D-77 到 D-148），证明错的是 D-77「状态不存，所以不会和变更的真实状态不一致」：状态虽然现算，链接却靠会话手写，漏写链接就等于状态错 → D-148 已接住（单一数据源，关联由命令写入），不另做机制。
