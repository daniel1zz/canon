## 为什么

负责人 2026-11-28：「所有新加的命令都要检查一下是否还存在加了命令但是没有引导的情况」。起因是 C-716 加了 `canon work adopt`，却没有任何地方告诉主 agent 去用它。逐个检查 108 个命令后，有一批 agent 该用的命令在工作说明、canon 自带的 skill 和别的命令的输出里都没被提到，只能靠 `--help` 碰巧看到：

- `canon human withdraw`、`canon human provisional`：撤回过时的问题、给没回答的问题一个临时答案让工作继续，直接关系到 P7（不等人），但议程列出待答问题时不提它们。
- `canon quality new`：brief 提示“还没有质量标准，用 canon-product skill 调研”，那个 skill 却没写用什么命令建标准。
- `canon goal start`：目标模式要会话自己开启（D-132），只在一行代码注释里出现过。
- `canon feature status`、`canon feature drop`、`canon progress`、`canon work remaining`、`canon usage`、`canon work handoff-reason` 也一样。
- 顺带：`canon doc new --help` 的说明是 “Create a  (allocates…”，类型名是空的。

## 要改什么

- 补引导，放在用得上的地方：议程的待答问题一项写明 `canon human provisional` 和 `canon human withdraw`（BR-2527）；没有质量标准的那行提示写明 `canon quality new`（BR-2558、BR-2506）；brief 的进度摘要在 agent 会话里有进行中的版本、还没开目标模式时提示 `canon goal start`（BR-2506）；`canon change list` 有没记原因的交接时最后一行提示 `canon work handoff-reason`（BR-2575）；canon-product skill 写 `canon quality new`、`canon feature status`、`canon feature drop`，canon-uat 写 `canon progress`，canon-triage 写 `canon work remaining`，canon-context-optimizer 写 `canon usage`。
- 新规则 BR-2648 和测试 `src/invocation/every-command-guided.test.ts`：遍历命令树，每个命令要在工作说明、canon 自带的 skill 或别的代码的输出里被提到（不算注释，不算它自己的注册文件和同名实现文件），否则写进豁免清单并写明理由；豁免的命令有了引导就要删掉。测试读遍 `src/`，加进 `always_tests`。
- 修 `canon doc new` 的说明。

## 教训

- 加命令时只想着命令本身能用，没想到 agent 怎么知道它存在；C-716 加 `canon work adopt` 是负责人追问才补上议程提示的 → BR-2648（`src/invocation/every-command-guided.test.ts`）。这条检查就是负责人 2026-11-28 要求本变更做的事，按 D-78 不是另行固化的教训，不用再问负责人
