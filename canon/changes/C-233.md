## 为什么

#96（C-227 合入后的代码评审）：`settleLocked` 把排队条目里没有 pid 的领头（进队列时读不到 `ps`）当成已经不在，于是被锁定、收到信号的成员马上解除锁定、撤回关闭提交；领头从 `lockBatch` 到 `moveMain` 不再看成员，照样把含有成员关闭提交的链顶移成 main。结果 main 说 done，成员分支说 open。`tryTurn` 对没有 pid 的条目只看心跳，`settleLocked` 和它不一致。

复现（改动前）：`src/work/land/queue/queue.test.ts` 的 BR-2099 用例：领头没有 pid、心跳新鲜时，`settleLocked` 返回 `settled`。

## 要改什么

- `src/work/land/queue/queue.ts` 的 `settleLocked`：只有记下了领头进程、而且确定它已经不在时才算不在；没记下进程时只看心跳，和 `tryTurn` 一样。
- BR-2099：写明这一点，补两侧的例子。

## 陷阱和假设

- 评审里提到的另一种情况仍在：领头从最后一次 `await` 到 `moveMain` 之间是同步执行的，心跳在这段时间不更新；如果这段时间超过 `lander_stale_minutes`，成员会当领头已经停了、自己撤回，而领头接着移动 main。`tryTurn` 解锁成员（BR-2173）也有同样的窗口，这不是本变更引入的；要彻底关掉，需要领头在移动 main 之后发现成员已经离开时补救，或者成员不按心跳自行解锁，这是取舍，交给负责人。

## 教训

- 新写一处“领头还在不在”的判断时，要对照已有的那处（`tryTurn`）用同一标准 → 只靠文字：两处判断写在不同的事务里、读的列不同，没有通用检查能发现标准不一致；这次由合入后的代码评审发现。
