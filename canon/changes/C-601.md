## 为什么

已经合入 main 的变更，如果派发记录没有结束，仍被 BR-2522 算成停滞，`canon work status`、`canon overview`、`canon brief` 和 `canon work due` 都会提示设计负责人重新派发它（#264，实例是 C-577）。

## 要改什么

- BR-2522：停滞多一个前提，变更在 main 上还没关闭（不是 `done` 或 `dropped`），加一条例子。
- `src/work/delegation/stall.ts`：有候选的停滞派发时读一次 main 上的变更状态，跳过已关闭的。这和 BR-2526 的派发名额把 main 上已关闭的变更当作空出名额是同一个判断。

## 方案依据

另一种修法是合入关闭变更时结束它的派发记录。没选它：它只管以后的合入，已经留下的记录（如 C-577）照样误报，还要另写迁移。在读的时候排除，旧记录和新记录都对。如果以后发现别处也被未结束的派发记录误导（例如 `canon work take` 或重新派发一个已关闭的变更），就说明应该在合入时结束记录。
