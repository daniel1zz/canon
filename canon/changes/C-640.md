## 教训

- 一条规则新增拒绝（BR-2526 的派发冲突）或改掉一段输出（BR-2505 去掉待办顺序）时，别的规则的例子和测试还写着旧行为（BR-2497、BR-2499、BR-2564），各自变更只跑和自己有关的测试，合在一起才失败 → 只靠文字，不固化（负责人 2026-11-20 交给主 agent 判断）：合入后的后台测试（floor_timing: after）几十分钟内就抓到了，`--fix-main` 向前修好，没有发布坏的版本；这类过时只在几个变更同时改共用代码时集中出现，在评审里加对照会挤占预算、带来误报。改在调度上防：几个变更改到同一批共用代码时，后合入的那个合入前把受影响的目录并行跑一遍，写在主 agent 给 worker 的任务说明里。
- 两个变更都往同一个命令输出的末尾追加内容（BR-2584 和 BR-2306/BR-2163）时，没有一处规定整体顺序，后加的就排到最后 → 只靠文字：输出顺序分散在各条规则里，这次在 BR-2584 里写明了相对顺序。
