## 为什么

核对一次并发运行时，agent 自己报的数字不可靠（lore KN-276），要从事件表核对。这次会话里主 agent 一直手写 `sqlite3` 查询协调数据库：从某个事件编号之后数合入、拒绝原因、排队等待、冲突、参与的执行者和 worktree。这些查询每次都重写，容易写错，也只有会写 SQL、知道表结构的人能用。

## 要改什么

子领域：work/stats（`src/work/stats/`）。

- `canon stats --since <n>`：检查统计和搜索统计只用编号大于 `n` 的事件（BR-2154）；另外输出这段事件的并发摘要：合入成功、按原因分的拒绝、丢失、被终止；`land.turn` 的排队等待次数、中位数、最大值；冲突（含提前发现的）；同文件提示；认领被拒；不同的执行者和 worktree；第一条和最后一条事件的时间（BR-2155）。`--json` 时输出 `{since, checks, window}`；不加 `--since` 时输出不变。
- `canon events [--since <n>] [--kind <k>]... [--subject <C-n>] [--json]`：列出原始事件，最新的在最后（BR-2156）。
- 新文件 `src/work/stats/window.ts`；`computeStats`、`searchStats` 加一个可选的 `since` 参数。

## 陷阱和假设

- `--since` 是“之后”：编号等于 `n` 的事件不算。这样可以直接把上次看到的最后一个编号传进去。
- 拒绝的去向（BR-2068）只看窗口内的后续事件；窗口外更早的事件不影响结果，因为去向只看拒绝之后的事件。
- citty 对重复的 `--kind` 给出数组，只写一次时给出字符串，两种都要处理。
