## 为什么

继续给没划业务的领域划。work/stats 23 条里只有 4 条写了业务。这个领域从事件表算各种数字，但算的东西互不相干：检查该不该留、拒绝之后变更怎样了、一次并发跑得怎么样、原始事件、canon 自己的健康指标、会话里注入了什么、评审意见真不真、评审跑了几次。

## 要改什么

README 的业务一节写出 8 个业务，23 条生效规则全部归属。只加 front matter 的 `business`，`## 规则` 和 `## 例子` 一字不动，行为哈希不变（BR-2236）。

- 检查值不值得留（4）：BR-2067、BR-2069、BR-2095、BR-2202
- 拒绝的去向（3）：BR-2068、BR-2203、BR-2379
- 一段时间的并发核对（3）：BR-2154、BR-2155、BR-2204
- 原始事件流（2）：BR-2156、BR-2357
- 产品自身的指标（3）：BR-2121、BR-2135、BR-2205
- 会话用了什么（2）：BR-2265、BR-2266
- 评审意见的判定（4）：BR-2253、BR-2254、BR-2255、BR-2290
- 评审的统计（2）：BR-2397、BR-2451

原有的「拒绝的去向」说明补上一起测的去向（BR-2379），另外两个原有业务的名字和说明不动。

## 陷阱和假设

- 「检查值不值得留」把复审日期（BR-2069）和次数统计放在一起：复审日期是「现在该重新判断这个检查」的触发点，次数是判断的依据，两边一起改。
- 「产品自身的指标」把共享代码占比和没有结果的搜索比例放在一起：都是 canon 从自己的工作区和事件里算出来的健康数字，和检查、评审的统计无关。
- 这个领域有 8 个业务、23 条规则，接近 25 条的拆分提示；要不要拆成领域是另一件事，本变更不动。
