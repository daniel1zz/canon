## 为什么

baseline 核对（N-4）在 `canon human` 里发现三处规则没写或和代码不一致：`canon human ask --change C-999` 对不存在的变更照样记下问题；`canon human answer abc` 把非数字编号当成“问题不存在”（退出码 3，写一条 `not-found` 事件），其实是用法错误；不给 `--change` 时，问题挂在 worktree 认领记下的变更上，即使认领已经失效，规则没说这是有意的。负责人 2026-11-04 选择推荐方案：“全部按推荐”。

## 要改什么

- `src/work/humans/commands.ts`：`--change` 先按 `canon work start` 的方式找变更（main 上，或者它的变更分支，编号不分大小写），找不到退出码 3，什么都不写；`answer` 的编号不是数字时退出码 2，不写事件。`src/work/session/session.ts` 导出 `changeOffMain` 供它使用。
- BR-2075：写明 `--change` 必须是变更，以及没有 `--change` 时认领失效也照样挂在 worktree 的变更上（有意的）。
- BR-2040：非数字编号是用法错误；处理评审建议：回答方式不合法和问题不存在或已回答同时成立时，先按回答方式拒绝（BR-2021 同样写明并加例子）。BR-2021、BR-2040 上“BR-2026 没列 `human.answer.refuse`”的建议由 C-198 改 BR-2026 时处理。

## 陷阱和假设

- 找变更要读 main 上的文档；git 读不出 main 时是环境错误（退出码 4），和 start 一样。
- 变更是 done 或 dropped 时也算存在，问题照样挂上去：规则只要求它是一个变更。
