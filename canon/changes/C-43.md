## 为什么

canon 的并发机制（认领、合入队列、同文件冲突提示、比较并交换移动 main）只经过单元测试和脚本模拟。到 2026-11-03 为止，真实运行中只有两个会话自然并行过一次。旧 lore 真正出问题的地方，都出在多个会话同时干活的时候。

## 要改什么

- 选 3 到 5 个互相独立、但有一部分文件重叠的真实变更，同时开 3 到 5 个会话去做。
- 记录：每次合入的排队等待时间、rebase 冲突次数、同文件提示是否在冲突前出现、有没有丢工作或 main 被弄坏、`canon stats` 的数据。
- 结论写成笔记；发现的缺陷提 issue 或直接修。
- 实测前先加一个“轮到我合入了”的事件，否则排队等待时间和 floor 用时分不开。
- 专门制造这几种情况：合入进程被 Bash 超时杀掉；两个会话 start 同一个变更；一个会话在 floor 运行时继续提交。参照 lore 的 KN-821（237 次合入尝试：floor 失败 14%，输掉竞争 8.9%，冲突 6.8%）。
- 以事件表为准，不用 agent 自己汇报的数字（lore KN-276）。同文件冲突提示至今触发 0 次，要专门看它在冲突前有没有出现、有没有人看到（lore KN-258：检测对了但没送到人，8 天没起作用）。
- 这是一次实测，不是代码改动。负责人在对话里选定了要并行做的变更（2026-11-03：#17 和 #20、C-56、C-57、C-55），并选择用本会话的子 agent。

- [x] 结论笔记（N-3）
