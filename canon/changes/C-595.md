## 为什么

issue #255。派出去的变更（BR-2497），worker 进程已经退出、分支几个小时没有新提交时，没有任何地方提示：`canon work status` 照样写 `delegated to <名字>; … acceptor …`，`canon overview` 和 `canon plan status` 里它的计划步骤还是“进行中”。计划步骤的状态只看有没有关联的变更（`src/knowledge/plans/status.ts`：有变更就是 `working`），不看有没有人在做。认领里存了持有者的进程号和启动时间（BR-2100 用它判断进程还在不在），信息是现成的。

某个项目 2026-11-18：两个派出去的变更，worker 分别在约 5 和 7 小时前退出，worktree 干净，计划步骤显示进行中，整夜没人发现，排在它们后面的计划步骤一直被挡住。

## 要改什么

想要的行为：

- “停滞”的定义：变更有生效的派发（BR-2497），并且（a）没有人持有它的认领，或认领已过期，或持有认领的进程已经不在（BR-2100 的认法）；并且（b）变更分支最后一次提交（没有提交时是派发时间）早于现在减去 `delegation_stall_minutes`（`canon/config.yaml`，默认 60）。
- `canon work status`：停滞的派发变更单独一行标出 `stalled`，写明 worker 名字、分支最后提交的时间、worker 最后一次交接（`--next`）的内容，以及要做什么（设计负责人重新派发 `canon work delegate`，或 `canon work take`）。
- `canon overview` 的“等负责人”一节、`canon brief` 的整体进度摘要（BR-2505、BR-2506）列出停滞的派发变更数量和编号。
- 计划步骤：关联的变更里只要有一个不停滞，就是 `working`；全部停滞时是新状态 `stalled`（标签“停滞”），排序放在 `working` 之前。`canon plan status` 和 overview 的计划一节显示它。
- `--json` 输出带上同样的字段。

要改的规则：`canon work status` 的规则、BR-2505、BR-2506、计划状态的规则（`canon search "可开始"` 找）；新配置键按 `config-keys` 的规则登记。

回归测试：派发 `C-1`，worker 认领、提交一次后进程退出、认领释放，把时间拨过阈值 → `status` 有 `stalled` 一行，计划步骤是 `stalled`，overview 的等负责人里有 `C-1`；worker 进程还在 → 不标；没过阈值 → 不标；没有派发的普通变更没人认领 → 不标（这条只管派发）。

不做：

- 不自动重新派发、不自动 `take`。
- 不改认领的租约和续期。
- 不给普通（没派发的）变更加停滞判断。
