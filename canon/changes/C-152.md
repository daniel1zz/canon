## 为什么

基线审计发现合入者在三个时间段里失去对自己合入的控制：

- issue #60：一起测时临时 worktree 里的 `setup` 用 `Bun.spawnSync` 跑，整个进程被阻塞，心跳定时器和信号处理都停了；`setup` 比 `lander_stale_minutes` 慢时，成员把领头当成掉线，领头被拒、成员单独合入（违反 BR-2049）。
- issue #75：成员在别人的批里被测的时间仍算进它自己的排队时限；批作废、成员回到队列后，下一次查轮次就以 75 放弃。负责人 2026-11-03 决定：时限往后推迟在批里待的时间。
- `--finish` 先做关闭提交，信号处理却在进队列之后才注册；这中间收到 SIGTERM，进程按默认行为直接退出，关闭提交留在分支上，变更显示 done 却没有合入（违反 BR-2018）。

## 要改什么

- 批的 `setup` 改为异步运行，并登记到 `running`，信号到来时一并停掉。
- 排队等待时记下进入批的时间，回到队列时把截止时间往后推这段时间。
- 信号处理在 `--finish` 的关闭提交之前注册；还没进队列时收到信号只撤回关闭提交。
- 规则：BR-2048 写明时限推迟；BR-2049 把批的 `setup` 列进心跳覆盖的步骤；BR-2018 加一个例子。

## 教训

- 合入流程里任何同步的长调用都会让心跳和信号处理停下 → 现在由 BR-2049 的例子（批的 `setup`）和它的测试保证；别的同步调用（`git`、`ownDiffId`）都是短命令，只靠文字：逐个加测试的成本高于收益。
