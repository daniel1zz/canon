## 为什么

负责人 2026-11-04 看到后台测试跑全量时“cpu起码一半空闲的”，选择“直接改，批量跑”。实测原因：floor 里所有测试文件在一个 `bun test` 进程里按顺序跑，测试大多在等它启动的 canon 子进程和 git，8 核的机器上 `bun test` 进程只占约 0.2% CPU，`top` 里排不进前八；一次全量 21 到 24 分钟。

本机的 bun 1.4.4 支持 `--parallel=<N>`（`bun test --help`：“Run test files in parallel using N worker processes. Implies --isolate. Defaults to CPU core count.”）。在本变更的 worktree 里，后台 floor 同时在跑的情况下，`sh scripts/test.sh --parallel src/config src/knowledge` 用 8 个 worker 跑 31 个文件、306 个测试全部通过，用时 155 秒，CPU 211%。

## 要改什么

- `canon/config.yaml` 的 `floor` 把 `sh scripts/test.sh` 改成 `sh scripts/test.sh --parallel`。`scripts/test.sh` 把参数原样交给 `bun test`，30 秒超时和固定的 git 配置照旧，环境变量会传给 worker 进程。
- `test_command`（`canon work test` 一个文件一次）不变。
- 这是本仓库的测试设置，不是 canon 的产品行为，不改规则（和 C-247 一样）。

## 陷阱和假设

- 假设测试文件之间不共享端口、固定路径这类资源；`--parallel` 隐含 `--isolate`，每个文件一个全新的全局对象。合入后第一次 floor 就是全量验证：出现只在并行时才有的失败，就按 BR-2232 修 main。
- 负载会更高，接近 30 秒超时的测试可能变慢；第一次 floor 的结果里要看有没有超时。
