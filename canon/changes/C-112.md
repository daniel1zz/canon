## 为什么

GitHub issue #29（N-3 并发实测里 C-105 合入后的代码评审发现）：`tryTurn` 把自己的条目改成 landing 时不检查它是否仍是 waiting。合入者 A 被暂停超过掉线时间，后面的 B 把 A 标成 abandoned 并开始合入；A 恢复后下一次 `tryTurn` 看到前面没人，照样拿到轮次，可能和 B 同时合入，也可能在 B 之后才合入但用着更小的条目编号，打乱后台命令按批次排序。

## 要改什么

子领域：work/land（`src/work/land/queue.ts`、`src/work/land/land.ts`），另改 work/stats 的检查列表（`src/work/stats/checks.ts`）。

- `tryTurn` 在同一个写事务里先读自己的状态：不是 waiting 就返回 `lost`（状态和原因），不再改任何行；改成 landing 的语句也加上 `state = 'waiting'` 条件。按心跳判定放弃时记下原因 `no heartbeat`。
- `waitAndLand` 收到 `lost` 时以原因 `lost-turn` 拒绝，记 `land.refuse`，不动 worktree，条目保持 abandoned。
- 拿到轮次后才被判定放弃的情况：心跳只在 landing 时写；移动 main 之前用 `holdsTurn` 再确认一次，确认不了同样以 `lost-turn` 拒绝。
- 新规则 BR-2144；BR-2067 的检查列表加上 `lost-turn`（和 `timeout` 同一步）。

## 陷阱和假设

- 原因名不用 `abandoned`：`canon stats` 已经用 `abandoned` 表示“拒绝后变更被放弃”，同名会混淆。
- 移动 main 前的确认和移动本身不在一个事务里，仍有极小的窗口；main 的比较并交换兜底，最坏结果是某一方 `main-moved`，不会丢工作。
