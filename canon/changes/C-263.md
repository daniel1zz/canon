## 为什么

独立评审对 D-50（C-260 合入，proposed）提出的问题，协调者核实过：

- 负责人排不了只在分支上的变更：`canon check` 只看 main 上的变更，待办清单写了它就报 `ref-dangling`（`src/knowledge/check/check.ts` 读清单那段）。
- 一个分支上的坏变更文件让每个会话的 `canon brief` 失败（`src/work/session/commands.ts` 的 `if (!open.ok) return open;`）。
- 同一个变更在几个分支上时，列表把它当成可以开始的，但 `canon work start` 会拒绝（BR-2107）。
- 合入被杀掉时关闭提交留在分支上（`status: done`），这个变更从列表里消失。
- D-50 没写它也修订了 D-20 的“新工作自动排在最后”。
- 提交在别的变更分支上的变更文件列不列，没有决定。

## 要改什么

- BR-2150：清单里的编号在它自己的变更分支上有变更文件时不报 `ref-dangling`；`canon check`、`canon work test` 和合入时的检查都用同一份分支列表。
- 新规则 BR-2292：读不了的分支变更文件只影响这一项；brief 说一行、退出码 0；change list 列完其余的、在标准错误上报出、退出码 4。
- 新规则 BR-2293：同一变更在几个分支上标 `ambiguous: <分支>, <分支>`；工作说明让 agent 跳过标了 claimed 或 ambiguous 的。
- 新规则 BR-2294：只在分支上标成 `done` 的变更不带 `--all` 也列出，标 `closed on branch, not landed`，`canon work start` 能接手。
- BR-2291：去掉“总排在清单之后”，只在分支上的变更服从清单；写明别的变更分支上的变更文件不列及原因；读不了、几个分支、关闭未合入分别指向新规则。
- D-50 保持 proposed，更新方案和决定（含修订 D-20“新工作自动排在最后”的说明）。
- 代码：`src/work/session/inflight.ts`（列出结果带读不了的文件、按分支查变更编号、新标记）、`src/knowledge/check/check.ts` 和三个调用处、`canon change list`、`canon brief`、`src/work/session/session.ts` 的 start。
