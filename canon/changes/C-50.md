## 为什么

`canon work start` 总是把变更放在 `<worktrees>/C-n`，而认领只在 worktree 路径不同时才拒绝。会话 B 对会话 A 正在做的变更运行 `canon work start C-n`，拿到的是同一个路径，认领被续到 B 名下，两个会话在同一个目录里改文件，违反 P4。BR-2011 的测试用了一个 CLI 永远不会产生的路径（`/elsewhere`），所以没发现。

## 要改什么

- 认领在租约有效期内被另一个执行者持有时拒绝（退出码 5），不管路径是否相同；同一个执行者重新进入自己的变更照常成功。拒绝提示写明怎么放开（持有者 `canon work stop --release`，或等租约过期）。
- BR-2011 的标题、正文和例子写明“一个执行者”。
- 新测试通过真实 CLI 用两个不同的 `CANON_ACTOR` 验证；BR-2038 的测试原先让 agent:b 直接拿走 agent:a 仍持有的变更，改为 agent:a 先放开。

## 陷阱和假设

- 同一个 Claude Code 会话派出的子 agent 共用一个会话 id，所以执行者相同，这个检查分不开它们（本机事件表里多个并行子 agent 都记为同一个 agent:<会话 id>）。这里只解决不同会话之间的接手。
- 没带 `--release` 的 `canon work stop` 会保留认领；之后换一个会话接手，要等租约过期或持有者放开。存活探测（下一个变更）会缩短这个等待。
