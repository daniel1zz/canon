## 为什么

D-62 的第二部分：Claude Code 的 PreToolUse hook 校验子 agent 的 canon 认领命令带 `--as <自己的 agent_id>`（C-358 已做 canon 侧的 `--as` 和 `canon work take`）。

## 要改什么

- 新命令 `canon work check-as --hook`（hook 用，BR-2340）：只拒绝不改写；识别命令位置的 `canon work start|land|stop|drop|take`（拆段、跳过引号、heredoc、注释）；跳过检查记 `hook.skip`（BR-2341）。
- hook 命令名：选“换一个不在撤回前缀下的命令名”（D-62 的三个办法之二）：`canon work check-as` 不以 BR-2130 撤回的 `canon hook pre-bash` 开头，BR-2130 的前缀不用改；单独的 PreToolUse 条目，不并进快照 hook（失败时互不影响，`canon update --check` 能分别报告）。
- `canon init`、`install`、`update` 装这个条目，`update --check` 报告缺它，`uninstall` 删它（BR-2343；BR-2087、BR-2084、BR-2130 的文字同步）。
- `canon work land` 在 Claude Code 下没装 hook 时提示（BR-2342）。
- 新规则：BR-2340、BR-2341、BR-2342（work/claims），BR-2343（install）。

## 陷阱和假设

- 与 D-62 原文的两处差别：（1）`hook.skip` 的原因只记 `unparsable` 和 `bad-input`：`db-error` 时没有数据库可写，只能 systemMessage；（2）“整条命令文本里含 canon work 而无可识别段算解析不出”按字面会让 D-62 自己列的不触发例子（`echo "canon work land"` 等）全记成 skip，所以改为：命令词是 sh、bash、eval、xargs 等包装命令且那一段里有 `canon work`、或 `$(…)`、反引号、变量里有 `canon work`、或子命令是变量/带引号，才算解析不出（BR-2341 的两侧例子）。
- 拒绝的事件不记（D-62 没要求）；只有跳过记 `hook.skip`。
- canon 自己仓库的 .claude/settings.json 没有 check-as 条目：要用户说“更新”时才运行 `canon update`（CLAUDE.md），所以在这之前本仓库里的 `canon work land` 会打印 BR-2342 的提示。
