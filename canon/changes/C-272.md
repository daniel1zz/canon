## 为什么

一次独立评审核对了 D-48（C-254 实现，proposed），提出五点，每点都对着代码或实测核对过，都属实。负责人 2026-11-04 说“不要设想不存在的问题”：只处理正常使用里真会碰到、或规则和代码直接矛盾的。

- 处理：`canon work start` 范围用完时仍以退出码 5 被拒。D-48 否决“分不到端口就不跑 hook”的理由（大部分命令不用端口）对开始一样成立；worktree 清理不及时攒多了，改文档的变更也开不了。
- 记为已知、不处理（写进 D-48 后果）：回收的端口排序用的是“最后一次交给变更”的时间（要碰上旧服务恰好在重启才出错）；探测漏掉只在具体网卡地址上监听的程序（本机实测属实，但开发服务器通常监听 localhost 或 0.0.0.0）；测试只测 127.0.0.1（只在改代码时才有影响）。
- 记为已知的后果：单独合入时 `before_land` 和开发服务器拿到同一个端口（D-41 遗留）。会碰到，但另分端口要每个变更占两个端口或在合入时分配，代价大于“合入前停掉开发服务器”。

## 要改什么

- `src/work/session/session.ts`：范围用完时开始照常进行，`setup` 和 `after_start` 的 `CANON_PORT` 为空，`setup` 之前写一行 `start: CANON_PORT is empty: <原因>`，不撤回 worktree、不释放认领、不记 `start.refuse`。
- 规则：BR-2269 改成开始照常进行；BR-2267、BR-2287、BR-2288 里引用它的地方相应改。
- D-48 就地修订、保持 proposed（先例：C-263 修订 proposed 的 D-50）：背景、方案 9 到 11、决定、后果。
- 测试：范围用完时开始成功且 `CANON_PORT` 为空；之后端口空出来再开始就拿到端口；改代码前先看到它们失败。

## 教训

- 评审意见先按“正常使用里会不会碰到”分拣，再动手 → 只靠文字：是否值得修是负责人的判断，没有能自动判断的检查；待负责人确认是否写进 canon-triage 或 canon-design 的说明。
