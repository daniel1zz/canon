## 为什么

C-119 合入后的代码评审找出两个并发问题：

- #38：合入先启动后台 shell，再一条一条记 `hook.run`。第一条命令很快结束、第二条还没记下时，`canon work after-land` 只读到一条，以为整批已经结束且成功，退出 0。
- #39：`--wait` 每次轮询都重新找“最近一批”。等待期间别的会话合入且很快结束，等待就换到那一批，报告别人的成功，自己的失败被藏住。工作说明又叫大家不带变更编号运行，所以并发合入时一定会遇到。

## 要改什么

子领域：config（`src/config/hooks.ts`）。

- `runHooksInBackground` 在启动 shell 之前，用一个事务把整批 `hook.run` 记下（BR-2166）。
- `settleBackgroundHooks` 可以按日志路径找批次；`waitBackgroundHooks` 第一次读到哪批，之后都按它的日志路径读（BR-2167）。
- 工作说明改成 `canon work after-land --wait <C-n>`，写明是自己的变更；BR-2090 跟着改。

## 陷阱和假设

- #38 的测试让第一条后台命令去数这批的记录，证明命令开始时记录已经齐全；旧代码下这个时间窗口很小（启动 bun 就要几十毫秒），所以这个测试在旧代码上通常也会通过，它防的是以后又把记录挪到启动之后。
- 记录先于启动：如果启动 shell 本身失败，会留下一批永远“还在运行”的记录；这时 canon 会以内部错误退出，`--wait` 只会等到超时。
