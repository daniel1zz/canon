## 为什么

#115（C-265 合入后的代码评审提出）：合入的评审命令、时限和 `instructions` 取自被合入的树（`steps.ts` 的 `cfg = landing.value`），而这棵树里有变更自己的改动。一个变更可以在同一次合入里把 `review` 换成总是回答 ok 的命令，或者把自己改的 `CLAUDE.md` 从 `instructions` 里拿掉，它的规则或常驻说明文字就等于没人评审。BR-2295 只挡住了改成 `none` 或删掉这一种。协调者的决定：这三项取自 main 上已经合入的配置。

## 要改什么

- `src/work/land/checks/steps.ts`：从 `v.main`（一起测时是整批的 base）的 `canon/config.yaml` 读 `review`、`review_timeout_minutes`、`instructions`，按 canon 读配置的方式校验；要不要评审仍看这次合入改了什么。main 上没有 `review` 时，即使这次合入设了也拒绝，信息说先单独合入只设 `review` 的变更。
- 规则：BR-2074（配置来源、两侧例子）、BR-2143（`instructions` 用 main 上的清单）、BR-2296（时限用 main 上的值）。BR-2295 不变：它比较的本来就是被合入的树和 main。
- D-51（仍是 proposed）：加方案 9，否决“读被合入的树”，理由是 #115。

## 陷阱和假设

- main 上的配置在被合入之前已经被 canon 校验过；这里读不了（YAML 坏了、值不合法）时以 `environment` 拒绝，不悄悄用默认值。
- 评审命令在被合入的树里运行（cwd 是 worktree），命令开头的脚本路径按 main 上的配置写，变更改了这个脚本本身时，运行的是变更里的脚本；这一点不在这次范围内，见报告。

## 教训

- 防止自我放行的检查，读的设置不能来自被检查的对象本身 → BR-2074（评审设置取自 main）。协调者按负责人的方向指派。
