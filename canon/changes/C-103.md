## 为什么

用 canon 的项目里，多个 worktree 同时启动开发服务器、数据库这类本地服务时会抢同一个端口；git worktree 本身不隔离这些。2026-11-03 对并发隔离方式的调研发现，社区工具的做法是每个 worktree 分一个端口：uzi 从配置的 `portRange` 里给每个 agent 找一个能监听的端口，替换进 `devCommand` 里的 `$PORT`（github.com/devflowinc/uzi，2026-11-04 核对源码：是文字替换，不是环境变量），Conductor 给每个本地 workspace 分 10 个端口，`CONDUCTOR_PORT` 是第一个（conductor.build/docs/reference/environment-variables）。canon 自己是命令行工具，用不上；这是给接入 canon 的项目用的。同一次调研还发现每个 worktree 装依赖的成本可以压到很低：bun 在 macOS 上默认用 clonefile（实测 40 毫秒），pnpm 有 `virtualStoreType: global`（pnpm.io/git-worktrees）。

## 要改什么

- 归属：`config` 领域（setup 和 hook 命令的运行环境，代码在 `src/config/hooks.ts`）。
- `setup` 和各个 hook 命令的环境里加 `CANON_PORT`：每个变更一个，在配置的范围里分配（例如 `ports: 4100-4199`），同一个变更每次拿到同一个值，两个进行中的变更不会拿到同一个值；怎么分配（按编号算还是记在协调数据库里）在设计时写成决策。
- 在 `canon/config.yaml` 的说明里推荐依赖安装的配置：bun 用默认设置，pnpm 用 `virtualStoreType: global`，`setup` 只做依赖安装。
- 规则和测试。

## 设计结果

- 决策 D-41：端口记在协调数据库的 `ports` 表里，从范围里取最小的空闲值；变更的 worktree 不在之后端口才回收；范围用完时明确失败。按编号算、每次探测、每个变更一段这三种做法都否决了，理由见 D-41。
- 规则：BR-2267（`CANON_PORT` 的值：同一变更不变、进行中的两个变更不同、没设时为空）、BR-2268（`ports` 的写法）、BR-2269（范围用完时 start 退出码 5、hook 当作失败）；BR-2199 的环境变量列表加上 `CANON_PORT`。
- 代码：`src/config/ports.ts`（读配置、分配、给 hook 的查找函数），`src/config/config-keys.ts` 登记 `ports`，`src/config/hooks.ts` 设 `CANON_PORT`，`src/work/session/session.ts` 在建好 worktree、跑 `setup` 之前分配。`HookContext` 多了必填的 `port`，所以 `src/work/land/checks/steps.ts`、`src/work/land/finish/finish.ts`、`src/work/watch/watch.ts` 各改了一行传入它。
- 依赖安装的推荐写在本仓库 `canon/config.yaml` 的 `setup` 注释和 `setup` 配置项的说明里（`canon config` 能看到）。

## 陷阱和假设

- BR-2248：本仓库的 `canon/config.yaml` 只在注释里提到 `ports`，不写这个键；要用得在另一次合入里写。
- 端口表 `ports` 由 `src/config/ports.ts` 第一次用时建（`CREATE TABLE IF NOT EXISTS`），不在 `src/work/db.ts` 的总表里。
- 一起测（D-26）时批的临时 worktree 里跑的 `setup` 不属于任何变更，canon 不给它设 `CANON_PORT`（`src/work/land/batch/batch.ts` 没改）。
- hook 时还没有端口的变更（`ports` 配置之前开始的）按约定路径 `<worktrees 目录>/<变更编号>` 记录；worktree 不在约定路径的变更，记录可能被当成已经不在而回收。

## 教训

- 改动前写在变更里的外部做法（uzi 设 `$PORT`）和源码不符：uzi 是文字替换，不是环境变量 → 只靠文字：引用外部做法时核对原文本来就是 D-14 要求的，合入时也会核对决策里的来源，但变更文件里的说法不在核对范围内
