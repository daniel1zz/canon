## 为什么

基线审计发现几处 git 或文件操作本身失败时，合入记了错误的拒绝原因，`canon stats` 的检查统计因此被污染，退出码也和 BR-2022（git 命令失败是 4）不符：

- `--finish` 的关闭提交做不成（改变更文件失败、`git commit` 失败）记成 `check`；而且改过的变更文件留在工作区里，worktree 变脏。
- 轮到后 `git rev-parse main`、rebase 后 `git rev-parse HEAD` 失败记成 `main-moved`；移动 main 前列不出 worktree 也记成 `main-moved`。
- rebase 失败但没有冲突的文件（例如 `index.lock` 已存在）记成 `conflict`：保留排队位置，提示“conflicts in:”后面是空的。

## 要改什么

- 这些地方改用新的拒绝原因 `environment`，`canon work land` 以退出码 4 退出；`environment` 不在 `LAND_STAGES` 里，所以不算任何检查。
- 关闭提交失败时把变更文件恢复成提交前的样子。
- rebase 失败而没有冲突文件时以 `environment` 拒绝，不保留位置；有冲突文件时照旧是 `conflict`。
- 新规则 BR-2193。

## 教训

- 拒绝原因选错，会悄悄污染 `canon stats` 的检查统计 → 现在由 BR-2193 和它的测试保证这几处；以后新加的拒绝路径只靠文字：没有检查能判断一个原因选得对不对。
