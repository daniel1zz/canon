## 为什么

合入串行，floor 是吞吐上限（N-3）。负责人要求提速（2026-11-03，“按照你这个能提速的思路做”）。带权重的多队列只改顺序，不减少 floor 次数；几个等着的合入一起测一次才减少。方案比较和来源见 D-26。

## 要改什么

子领域：work/land（`land.ts`、`queue.ts`），config（`land_batch_max`），work/stats，work（`db.ts` 新列）。

- 新配置 `land_batch_max`（默认 1，不合并；本仓库 4）。
- 轮到的合入者 rebase 后，取紧跟在后面、合格的等待条目，在 `.git/canon/batch/<条目>` 的临时 worktree 里依次 rebase 成提交链；每个变更自己的步骤（check、来源、评审、before_land）在它那一段链顶上跑，floor 只在链顶跑一次；通过就比较并交换地把 main 移到链顶，成员条目记为已合入，成员进程把自己的分支移到它在 main 上的提交并收尾（BR-2172）。
- 任何一步失败、成员 worktree 变了或成员停了 → 整批作废，成员标成单独合入回到队列，领头单独合入（BR-2173）。
- 抽出 `verifyChange`（check 到 before_land）、`runFloor`、`afterLand`、`finishLanding`，单独合入和一起测共用。
- 队列表加 `batch`、`head`、`solo` 三列；成员在批里时状态仍是 `waiting`（`state` 列的 CHECK 约束是旧库就有的，改不了），靠 `batch` 列区分。
- `canon stats` 里成员的成功不算 floor 运行。BR-2020、BR-2106、BR-2067、BR-2045 写明例外。
- 顺带修 issue #40（C-122 合入后代码评审发现）：判断能否跳过 floor 时，用 rebase 后那棵树上的 `canon/config.yaml`，不用开工作区时读到的旧配置；BR-2164 加一个例子。

## 陷阱和假设

- 状态不能加新值：旧数据库 `queue.state` 带 CHECK 约束，`ALTER` 改不了，所以“在批里”= `state='waiting' AND batch IS NOT NULL`。
- 成员先记已合入、领头后记，成员才不会看到“领头已结束、自己还在批里”而误以为领头死了。
- 领头移动 main 之后、记下成员之前死掉：成员回到队列再合入一次，rebase 后没有新内容，不丢工作。
- 临时 worktree 里先跑 `setup`，floor 在那里跑；成员自己的 worktree 在批里期间不能改，否则整批作废。
- 一批里中间的提交没有单独跑过 floor，只有链顶跑过。
- 失败时用的是退回逐个合入，不是对半拆（D-26 写了理由）；批量上限越大，失败时浪费越多，所以上限要小。

## 教训

- 改一个编号时用 `sed` 批量替换整个 `src`，会改到别人规则的测试名（这次误改了 `after-land.test.ts`、`hooks.ts` 里另一个变更的 BR-2166/BR-2167，提交前发现并还原）→ 只靠文字：先用占位编号再批量替换本身就不该做，规则先建、拿到编号再写代码即可。
- 给协调数据库的状态列加新值前，要查旧库的 CHECK 约束（`ALTER` 改不了）→ 只靠文字：这次第一次运行测试就以 `SQLITE_CONSTRAINT_CHECK` 失败，已有的测试足以暴露。
- 新旧版本的合入者会同时排在一个队列里：新机制必须让旧版本的条目保持原样 → 已由 BR-2172（旧条目 `solo` 为空，永远不进批）和 `queue.test.ts` 保证。
- 合入时用到的配置必须来自即将成为 main 的那棵树（#40）→ 已由 BR-2164 的新例子和测试保证。
