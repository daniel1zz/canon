## 为什么

C-464 的 C 步（#183）：同一组文档在相邻几轮评审里得到方向相反的意见，一轮要求的写法正是下一轮拦的写法，重新措辞不收敛。D-89 定了方向：两条一起交给评审求两边都满足的写法，给不出记成留给人的问题，裁决前挡住验收（验收在 G 步）。触发方式、幂等和与 G 步的衔接在 D-103。

## 要改什么

- 新命令 `canon finding reconcile <n> <m>`（BR-2461，新）：检查顺序、评审回答的 JSON 约定、三种结果、给不出写法时自动记问题并和两条意见互记（`review_findings` 加 `question` 列，迁移按 BR-2078）。
- 记录新拦截意见时文档组与某条未处理意见相同 → 日志提示 reconcile（BR-2442 点名 BR-2461）。
- `CANON_REVIEW_KIND` 增加 `reconcile`（BR-2366），配置参考同步。
- 不自动发起合并评审（D-99 不变，D-103 方案 2 否决）。

## 陷阱和假设

- `widenFindingsCheck` 用 `FINDINGS_TABLE` 的列重建表，新增列必须排在它之后迁移，否则同一次打开里刚加的列会被重建丢掉（db.ts 里有 reason 注释）。
- 交替轮次里相反的一对常是「一条已关、一条未处理」，所以 reconcile 接受已关闭的意见；机械提示只对比未处理意见。
