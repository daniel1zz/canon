## 为什么

#135（两个切片中的第一个；第二个是 C-392，认领的会话进程退出也能被跟踪到）：派子 agent 的主会话没有办法从 canon 及时知道需要它处理的事。它只能自己再跑 `canon work status` 或 `canon events` 去查，或者等整个派发结束。在 Godot 项目里，一个 worker 遇到阻塞，`canon work stop --next` 写了 handoff 后退出；另外两个 worker 还在跑，所以派发命令没结束，handoff 放了约 30 分钟，直到负责人问进度才被发现。那个项目只好自己写脚本，每 60 秒轮询 `canon events --json` 和 `canon work status --json`。

main be6c0d7 上 `canon events` 只有 `--since`、`--kind`、`--subject`、`--json`，输出一次就退出，没有持续输出的方式。C-119（`canon work after-land`）也是为了替换 agent 自己写的轮询循环才做的，理由相同。

## 要改什么

`canon events --follow`：先像现在一样输出符合条件的已有事件（`--since` 照常生效，默认从当前最新事件之后开始，不重放全部历史，这一点在规则里写明），然后一直运行，每出现一条符合条件的新事件就输出一行（`--json` 时每行一个 JSON 对象，即 JSON Lines，不是一个数组），并立即刷新输出，这样后台监视器能逐行读。

- 过滤条件和现在一样：`--kind` 可重复，`--subject`。
- 每秒按事件编号查一次协调数据库（`id > 上次输出的最大编号`），间隔写进规则；只读数据库，不写事件（C-392 的认领状态事件除外，见那个变更）。
  - 否决：监听数据库文件（WAL）的变化。各平台的文件监听表现不一致，合并写入时会漏通知；每秒一次按主键查询的开销可以忽略。
- 收到 SIGINT/SIGTERM 时以 0 退出；协调数据库打不开时和现在一样以 4 退出（BR-2209）。
- 不加 `--follow` 时行为完全不变。

规则：改 BR-2156 或新增一条（`work/stats`），例子覆盖：跟踪中出现新的 `handoff.write` → 输出一行；`--kind land.ok` 时出现 `land.refuse` → 不输出；`--json --follow` 每行是一个对象；收到 SIGTERM → 退出码 0。

canon-parallel skill 里派发子 agent 的说明加一句：主会话用后台监视跟踪 `canon events --follow --kind land.ok --kind land.refuse --kind handoff.write --kind human.asked`。

不在范围内：会话进程退出、长时间没有改动这类推导出来的状态（不在事件表里，C-392）；推送通知或 HTTP 接口（product.md 不做）。
