## 为什么

baseline 核对（N-4）说 config 这一组有用户看得到、却没有规则写明的行为，还有规则的例子没有测试验证。逐个读 `src/config/` 的代码、用探针跑过后确认：

- `hooks` 的值怎样写才算对（一条命令或列表、`null`、空白命令、YAML 布尔值 `true`）没有规则，只有 BR-2045 一句“类型不对”。
- 每条 hook 命令都拿到 `CANON_ACTOR`、`CANON_WORKTREE`、调用者原有的环境，标准输入是空的；只有 `after_start` 的规则提到其中一部分。
- 前台 hook 打印 `hook <事件>: <命令>` 和输出的最后 40 行，没有规则。
- 后台的 `after_land` 每条命令在自己的子 shell 里运行，`cd`、变量、`exit` 不带到下一条，没有规则。
- `canon work after-land` 的结论有四种写法，BR-2166 只写了三种。
- `canon config --json` 写不了 schema 文件时说明写到标准错误，BR-2176 没写。
- 没有测试的例子：BR-2174 的 `floor = (unset)`、BR-2166 的“第二条以 1 退出”、BR-2057 的“合入退出码 1”（原来只测了函数的返回值）、BR-2050 的第一个 `SP-1`、BR-2060 的“打印文件内容”、BR-2093 的“有模板用模板”和“没有段落也没有模板时为空”。

## 要改什么

- 新规则：BR-2198（hooks 的写法）、BR-2199（运行方式和环境变量）、BR-2200（前台 hook 的输出）、BR-2201（后台命令各在子 shell 里）。
- BR-2166 写全四种结论；按 C-127 的评审建议，把“合入在启动前整批记下”这一段和它的例子挪进 BR-2059（触发点是合入，不是 after-land），测试名跟着改。
- BR-2176 写明 `--json` 时说明写到标准错误。
- 测试都放在 `src/config/` 下的新文件里（`hook-run.test.ts`、`after-land-report.test.ts`、`doc-types.test.ts`、`reference/config-list.test.ts`），避免和并行的变更改同一段。
- 不改代码行为。

## 陷阱和假设

- 规则只写现在的行为；拿不准是不是产品选择的（例如前台 hook 的输出把标准输出放在标准错误前面，而不是按时间交错；`canon config --schema` 在配置写错时也以退出码 2 失败）没有写进规则，留给负责人。
- `after_land` 的命令里写 `./notify.sh` 这种路径会在读配置时检查是否存在（C-170），规则例子用 `bun run notify`。
- BR-2166 的评审建议里还有一条：不加 `--wait` 时“还没结束”用退出码 75，而 75 在 BR-2022 里是排队超时；这要负责人定，本变更不动。

## 教训

- 同一条规则的例子散在别的领域的测试文件里（声明类型的规则在 `src/knowledge/documents/types.test.ts`），核对时容易以为没测过 → 只靠文字：`canon check` 只认测试名里的编号，不管测试放在哪里。
