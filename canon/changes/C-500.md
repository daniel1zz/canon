## 为什么

继续给没划业务的领域划。work/hooks 17 条里只有 2 条写了业务。这个领域里是三摊事：hook 命令本身怎么配怎么跑、五个生命周期时刻各自的约束、以及给每个变更分端口。

## 要改什么

README 的业务一节写出 6 个业务，17 条生效规则全部归属。只加 front matter 的 `business`，`## 规则` 和 `## 例子` 一字不动，行为哈希不变（BR-2236）。

- hook 怎么运行（4）：BR-2198、BR-2199、BR-2200、BR-2201
- 每次运行的记录（2）：BR-2059、BR-2137
- 开始和停下的 hook（2）：BR-2056、BR-2058
- 合入时的 hook（1）：BR-2057
- 合入后的报告（3）：BR-2138、BR-2166、BR-2167
- 变更的端口（5）：BR-2267、BR-2268、BR-2269、BR-2287、BR-2288

原有的「合入后的报告」说明补上 `canon brief` 的提示（BR-2138）。

## 陷阱和假设

- 「每次运行的记录」和「合入后的报告」分开：前者是写进事件表的事实，后者是怎样读出来讲给人听；换一种报告方式不动记录，换记录字段才动两边。
- 「合入时的 hook」只有 BR-2057 一条：`before_land` 是唯一能拒绝合入的 hook，它的边界和别的时刻不同，和「开始和停下的 hook」分开。
