## 为什么

负责人在 zhushenkongjian 上的体会：规则都遵守了，产品好不好一直没解决，验收只验逻辑。查下来是三个环节都断了：调研没按产品被评判的各个方面展开，结论没有落点，落了的标准没人按时判定（D-145 背景）。canon 现在只有「做什么」（canon-product）和「做得对不对」（规则、canon-uat），没有「做到什么程度才算好」。

## 要改什么

本变更只放决策 D-145 和上面的计划，各步骤作为它的计划变更（`--plan C-609 --step <名>`）去做。怎样按产品类型调研、调研结论怎样逐条交代去向，是另一个变更（canon-product 的调研标准）；按产品类型生成项目自己的 skill 也是另一个变更。

总览不受影响：本变更只加决策和计划，没有改部件、数据位置和主要流程；A 步加内置类型时一起改总览。

## 方案依据

- 复用：版本成功标准的标记和状态（BR-2504）的做法，用于 Q-n 的判定结果；待办清单（BR-2527）和 `canon brief` 的摘要，用于提醒；内置类型的做法（D-61，功能模块 F-n 的接入点）。
- 新选择：Q-n 作为内置类型；判定记成协调数据库里的事件；「过期」按它管的路径上又合入的变更数算。
- 最坏的失败：调研退化成一份通用清单，判定沦为自评走过场；或者提醒太多，会话和负责人都不看。对策是每条 Q-n 必须写来源，自评单列，提醒只列和当前工作相关的。
- 证据：zhushenkongjian 里按暖雪实测出数字的标准（关卡空间）一直被逐条对照使用，而只写推论的调研（`N-4`）用完就沉底（D-145 背景）。
- 什么结果说明选错了：在 zhushenkongjian 上用两周后，负责人试玩发现的问题里，仍有一半以上是已有 Q-n 覆盖、却没被判出来的，说明判定这一环没起作用，要重新设计判定，而不是加拦截。
- 数据的演进和恢复：Q-n 是 git 里的文件，和规则、决策一样随提交演进，可以回滚；内置类型以后只能加字段、不能删（`src/knowledge/documents/types.ts`），旧文件照样能读。判定事件在本机数据库里，丢了只会让相关 Q-n 显示为「过期」，下一次判定补上，标准本身不丢。

## 教训

- 有标准不等于标准起作用：zhushenkongjian 的 A2、A4 早就写了，仍然失守，因为判定可以写「待录帧」推迟 → 本计划 B、C 步（判定记录、过期提醒、独立判定）；本变更只定方向，不写代码，所以机制落在这两步。
- 调研只看题材和玩法，没有按方面细到能量、能判 → 下一个变更（canon-product 的调研标准）；它改的是 canon-product，和本计划分开做、分开验证。
