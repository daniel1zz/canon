## 计划

| 步骤 | 内容 | 依赖 |
|---|---|---|
| A | 内置文档类型 Q-n（`canon/quality/Q-n.md`）：方面、来源、门槛、判定人、管的领域或路径；状态 `draft`（生效、标明负责人未确认）、`active`、`retired`（写原因）；`canon quality new/list/status`；`canon/quality/README.md` 列出产品的方面，每个方面有 Q-n 或写明负责人定为不适用、推迟；一条 Q-n 都没有、有方面没覆盖时 `canon brief` 和 `canon overview` 提醒；合入后的规则评审读到 `canon/quality` 的改动 | - |
| B | 判定记录：`canon quality verdict`（哪条 Q-n、构建提交、判定人、通过与否、证据路径），负责人判定经 `canon human` 记下原话；判定人是写这个变更的会话时标为自评；过期（它管的路径上又合入的变更数超过门槛，agent 判和负责人判分开设）和不通过进待办清单；开工、合入改到它管的路径时列出相关 Q-n 的状态，会话在变更文件里写怎么处理；发布问题里列出没证明或不通过的 Q-n。不新增拒绝 | A |
| C | 独立 agent 从真实入口判定：配置一条验收命令，合入后在后台运行；同一套东西用于判定人是 agent 的 Q-n（过期时排进来），以及 D-141 的关键变更合入后验收（BR-2543 关键程度、BR-2544 合入后验收在这一步生效）；结果记成判定，不通过进待办清单或走撤回 | B |
| D | canon-uat：验收时把相关的 Q-n 列进清单，按判定人分别判；canon-design、canon-rules 写明体验类目标落成 Q-n 而不是规则 | A |

A 和 D 之后可以同时做 B；每一步开工时先写自己的规则（canon-rules），本变更只定方向（D-145）。

## 为什么

负责人在 zhushenkongjian 上的体会：规则都遵守了，产品好不好一直没解决，验收只验逻辑。查下来是三个环节都断了：调研没按产品被评判的各个方面展开，结论没有落点，落了的标准没人按时判定（D-145 背景）。canon 现在只有「做什么」（canon-product）和「做得对不对」（规则、canon-uat），没有「做到什么程度才算好」。

## 要改什么

本变更只放决策 D-145 和上面的计划，各步骤作为它的计划变更（`--plan C-609 --step <名>`）去做。怎样按产品类型调研、调研结论怎样逐条交代去向，是另一个变更（canon-product 的调研标准）；按产品类型生成项目自己的 skill 也是另一个变更。

总览不受影响：本变更只加决策和计划，没有改部件、数据位置和主要流程；A 步加内置类型时一起改总览。

## 教训

- 有标准不等于标准起作用：zhushenkongjian 的 A2、A4 早就写了，仍然失守，因为判定可以写「待录帧」推迟 → 本计划 B、C 步（判定记录、过期提醒、独立判定）。
- 调研只看题材和玩法，没有按方面细到能量、能判 → 下一个变更（canon-product 的调研标准）。
