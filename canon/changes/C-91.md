## 为什么

issue #23：一个会话的子 agent 和主会话环境完全一样，canon 的执行者（BR-2023）只到会话一级，分不开它们。C-87 让有效的认领挡住同一个执行者的 start，但提示又把兄弟子 agent 引进持有者的 worktree，那里只比较执行者，兄弟子 agent 就能续期、合入或放开别人的认领。实测 PreToolUse hook 的输入在子 agent 里带 `agent_id`，只返回 `updatedInput` 就能改写命令，负责人 2026-11-03 选了“子 agent 身份”这个方向（D-17）。

## 要改什么

- 新命令 `canon hook pre-bash`（BR-2127，`src/cli/install/prebash.ts`）：子 agent 的 Bash 命令前加一行 `export CANON_ACTOR='agent:<会话前 8 位>:<agent_id>'`，主会话和无效输入什么都不输出，永远退出 0，不做权限决定。
- `canon init`、`install`、`update` 把 PreToolUse hook（`canon hook pre-bash 2>/dev/null || true`）和放行规则 `Bash(export CANON_ACTOR='agent:*')` 合并进 `.claude/settings.json`；`update --check` 列出缺少的或旧形式的（BR-2128、BR-2084、BR-2087）。
- 执行者（BR-2023）：接受 `agent:<8>:<agent_id>`；在 Claude Code 会话里，`agent:<x>:<y>` 的 `<x>` 不是本会话时退出码 2。
- 认领按子 agent 分开（BR-2104、BR-2011），修好 #23。主会话可以用 `canon work stop --release --takeover` 放开自己子 agent 的认领（BR-2129），别人不行；拒绝提示里写明这个选项，所以工作流说明不用改。
- 决策 D-17。

## 陷阱和假设

- 实测耗时（编译后的 `dist/canon`，本机 macOS，通过 `/bin/sh -c 'canon hook pre-bash 2>/dev/null || true'` 跑 50 次）：中位数 39.2 ms、p90 40.4 ms，空命令 `sh -c true` 是 3.0 ms，所以每个 Bash 调用多约 36 ms，主会话和子 agent 一样（都要启动一次 canon）。一个什么都不做的 bun 编译程序本身就要约 16 ms；试过单独的入口文件跳过加载整个 CLI，只省约 6 ms，不值得多一个入口，没有采用。
- 放行规则依赖 Claude Code 按换行把命令拆成几行逐行核对（permissions.md 的 Compound commands）。hook 写出的那一行只含 `[A-Za-z0-9_-]` 和冒号，没有可执行的部分；Claude 自己写出以 `export CANON_ACTOR='agent:` 开头、里面带命令替换的命令时是否被放行，取决于 Claude Code 对命令替换的处理，没有实测。
- 测试里在进程内用子 agent 执行者时，会话前缀要取当前环境的 `CLAUDE_CODE_SESSION_ID`（session.test.ts 的 `S`），否则在别的会话里跑 floor 会被 BR-2023 的一致性检查拒绝。
- 装上 hook 之后，正在进行的变更如果由主会话认领、再交给子 agent 合入，会被拒绝；要先 `stop --release` 再由子 agent `start`（D-17 后果）。
- 没装 hook 的项目里子 agent 仍共用执行者，#23 在那里仍然存在。
- 子 agent 的实际运行（真的派一个子 agent 看 `canon work status` 里的执行者）这个会话做不了（子 agent 不能再派子 agent），留给主会话验证。
