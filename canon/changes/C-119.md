## 为什么

合入后 `after_land` 的命令（构建、代码评审）在后台运行，结果只写在 `.git/canon/logs/after-land-<n>.log` 里。这次会话里主 agent 和每个子 agent 都写 shell 循环轮询这个日志，等 `[hook 2/2 exited` 出现，再 grep `code-review:` 行，做了十几次。`canon brief` 只在失败时提示一行（BR-2138），不能等，也不显示评审结果。

## 要改什么

子领域：config（hook，`src/config/hooks.ts`），CLI 接线在 `src/cli/main.ts`。

- 新命令 `canon work after-land [<C-n>] [--wait [--timeout <分钟>]] [--json]`：找最近一次合入（或这个变更最近一次合入）的后台命令，复用 BR-2137、BR-2138 的事件和日志解析，记下 `hook.exit`，输出每条命令的退出码和日志里的 `code-review:` 行。退出码：0 全部成功、1 有失败、75 还在运行、3 没有、4 日志不见了（BR-2166）。
- `--wait` 等到全部结束或超时（默认 20 分钟），超时退出 75（BR-2167）。
- `settleBackgroundHooks` 加可选的变更编号，返回值多出每条命令的退出码和 `code-review:` 行；`canon brief` 的行为不变。
- 工作说明（`src/cli/guide.ts`）加一行：合入后用 `canon work after-land --wait`，不要轮询日志；BR-2090 跟着改。

## 陷阱和假设

- 后台进程被杀掉、没写退出行时，没有办法知道它死了（没记 pid），`--wait` 只能等到超时，退出 75。
- 不带变更编号时，“最近一次”按排队顺序（BR-2138）。合入命令返回之前已经记下这批命令，所以自己合入后立刻运行能看到自己的那批；但别的会话随后合入，就会看到别人的，此时写上自己的变更编号。
- 另一个 agent 正在改 `land.ts` 的批量合入；这里不改 `land.ts`。
