## 为什么

D-151 第三、四部分：可以派的活和要判断的事要在合适的时机提醒主 agent，处理过的提醒要能记下结论，watch 不再定时重复；总览只给当前状态。

## 要改什么

按 D-151 第三、四部分：议程三组（可派、要判断、等负责人）从 C-631 的状态和机器容量算出；处理结论命令和事件，`canon stats` 算提醒准确率；brief、合入后、开工时、watch 的提醒时机；派发冲突拒绝；`canon overview` 改成当前状态视图。规则先写（canon-rules），名字 D-151。

细节：

- 议程（work/reminders）：BR-2527 改写成议程三组，要判断的事分三档（影响 main 的、挡住别人的、其余），同类两条以上合成一行；新增 BR-2581（可派一组和机器有没有空：BR-2526 的三个条件，整组测试在跑时负载上限降到 0.9 倍、每组占一个名额）、BR-2582（正在跑的整组测试，读 C-637 的整机队列）。代码：`src/work/reminders/agenda.ts`（唯一算议程的地方，读 `state.ts`）、`due.ts`（各项）、`room.ts`、`heavy.ts`。
- 处理结论：新增 BR-2583 `canon work handled <键> --to C-n | --defer "<原因>" --for <时长> | --not-doing "<原因>"`，写 `reminder.handled` 事件；`--settles` 同样写成交给；新增 BR-2585，`canon stats` 的 `Reminders` 一节。
- 送达：BR-2529（brief 的议程摘要）、新增 BR-2584（主会话合入成功后输出摘要和有关的意见）、BR-2530（开工只列有关的意见，其余一行）、BR-2528（watch 启动给摘要，之后只报事件和变化，合入后说哪些因此可以开始，每秒读容量、越过阈值带回差时一行，去掉 `still` 和 `remind_every_minutes`）。
- 派发冲突：BR-2526 加上别的会话已派、没停滞时退出码 5；是否新增和容量都在一个事务里判断（#261）。
- 总览：BR-2505 改成四节（当前版本、议程、正在做和在等、历史大纲），`--history` 给细节；BR-2506 的 brief 摘要去掉计划、等负责人和停滞那几行（它们在议程里）。进行中的版本和成功标准挪到 `src/knowledge/releases/current.ts`，goal 和 overview 共用。
- 顺带：`executionStates` 可以只算点名的规则，议程的 `unverified:` 项在 zhushenkongjian 上从 4.9 秒降到 0.05 秒；`src/work/verify/slot.ts` 加只读的 `fullRunsNow`（不拿锁、不删项）。

## 陷阱和假设

- 状态一律读 `src/knowledge/changes/state.ts`（BR-2571），议程只读主状态和附加标记，不自己判断停滞、关闭或依赖；watch 的「可以开始」比较的是两次议程的 `ready-delegatable` 和 `ready-self` 集合。
- 正在跑的整组测试读整机队列（BR-2576、BR-2577），不从 `test.full.*` 事件推算：队列已经覆盖所有仓库、剔除死进程；事件只留给历史。测试要给自己的 `CANON_MACHINE_DIR`，否则会读到同一次测试运行里别的测试的整组测试（`scripts/test.sh` 给的目录是整次运行共用的）。
- 处理结论的「这一项又出现了」靠开始时间比较：没有开始时间的项（`awaiting-close`、`dropped-dep`、`criterion`）写了不处理就一直不出现，直到这一项本身消失。
- 总览去掉了「当前这一批」一节（D-148、D-149 要列给负责人看的那部分）：按 D-151 第四部分只列正在做和在等的，`canon change list` 仍能看到全部。这是按较新的 D-151 取舍，负责人如果还要那一节需要再定。
- 最近合入的大纲列出轻变更（杂务合入后 main 上有写着 `chore:` 的变更文件时，按它的 C 编号和标题列），没有轻变更文件的杂务不列。
- 合入之后的议程摘要只给主会话：worker 合入时它的主会话从 watch 看到「C-n landed; C-m can start now」。
- zhushenkongjian 的 `canon overview` 用这个变更的代码是 26 行（F-2/S4 要求不超过 40）。

## 教训

- 议程每读一次都要算一遍全部规则的执行状态（为了 `unverified:` 那几条），大项目上一次 5 秒 → 改成只算点名的规则（`executionStates` 的 `only` 参数），只靠文字：没有检查能发现「为一小部分算了全部」，要在性能回归测试里加才能固化，待负责人确认是否固化。
- 两个变更同时定一个接口（C-632 读、C-637 写整组测试的记录）时，先由协调会话定下读写边界再各自实现，避免了两份记录 → 只靠文字：属于派活时的协调习惯。
