## 为什么

D-6 让 agent 用 `--relayed` 转述负责人的原话，并且明说防不住冒充。lore 的 SPEC-234 在提问工具（AskUserQuestion）返回后挂了一个只记录的 hook，直接从 Claude Code 返回的数据里记下人的选择，agent 改不了这份记录。D-6 的备选方案里没有考虑这种做法。

## 要改什么

- 新规则 BR-2274（cli/install）：`canon init`、`canon install`、`canon update` 在 `.claude/settings.json` 的 `hooks.PostToolUse` 里合并一个 `matcher` 为 `AskUserQuestion` 的条目，命令是 `canon human record || echo '{"systemMessage":...}'`；缺少时 `canon update --check` 列为过期。只记录、不拦截（D-1）。
- 新规则 BR-2275（work/humans）：`canon human record` 从标准输入读 Claude Code 的 PostToolUse 数据，把每个问题和人的选择（`tool_response.answers`，以及人自己打的 `response` 和备注 `notes`）写成一条 `human.asked` 事件，操作者按 BR-2023 的顺序认（会话 id 取自数据里的 `session_id`）；数据不对时退出码 2，什么也不写。
- 新规则 BR-2276（work/humans）：`canon human answer --relayed` 记下时，找同一个操作者最近一条 `human.asked`，原话（去掉首尾空白）和其中某个回答、`response` 或备注完全相同就标“matches Claude Code's record”，否则标“no matching Claude Code record”；标记存进问题和 `human.answer` 事件；`canon human pending --all` 在回答后面显示 `[matches Claude Code's record]` 或 `[no matching Claude Code record]`。不一致也照样记下，不拦截。
- BR-2084（过期项清单；顺带处理 C-60 的评审意见：文件不能解析时是退出码 2）、BR-2087（canon 管哪几项）、BR-2196（`{}` 的例子多一行），cli/install 领域 README 的“过期”术语补上 `worktree.baseRef` 和这个 hook（C-60 的评审意见）。
- 新决策 D-45 记下做法、被否决的方案和来源；D-6 不改原文，由 D-45 部分修改（“canon 不声称能阻止冒充”仍然成立，D-45 加的是佐证）。
- 代码：`src/cli/install/hook.ts`、`src/cli/install/update.ts`（安装和过期检查），`src/work/humans/questions.ts`、`src/work/humans/commands.ts`（记录、对照、显示），`src/work/db.ts`（`questions` 加 `witness` 列）。
- canon 自己仓库的 `.claude/settings.json` 同一个提交里加上这个 hook，否则合入后 main 上 `canon update --check` 报过期。
- 测试：`src/cli/install/update.test.ts`、`src/work/humans/questions.test.ts`。

## 核实（Claude Code 官方文档，2026-11-04 查）

- PostToolUse 拿到的是工具的结构化输出：https://code.claude.com/docs/en/hooks.md “`PostToolUse` hooks fire after a tool has already executed successfully. The input includes both `tool_input`, the arguments sent to the tool, and `tool_response`, the result it returned.” 以及 “`PostToolUse` passes the tool's structured `Output` object”。
- AskUserQuestion 的输出里有人的回答：https://code.claude.com/docs/en/agent-sdk/typescript.md 的 `AskUserQuestionOutput`：`questions`、`answers: Record<string, string>`、`response?: string`、`annotations?: Record<string, { preview?: string; notes?: string }>`，说明是 “Returns the questions asked and the user's answers. `response` is set when the user typed a freeform reply instead of answering the structured questions”。
- `answers` 的形状：hooks.md 的 AskUserQuestion 一节：“Maps question text to the selected option label. Multi-select answers join labels with commas.”
- 数据里有 `session_id`、`tool_name`、`tool_use_id`（hooks.md 的 PostToolUse 输入示例），matcher 可以写工具名 `AskUserQuestion`（hooks.md：PreToolUse 的 matcher “Matches on any tool name … `AskUserQuestion`”，PostToolUse “Matches on tool name, same values as PreToolUse.”）。
- 这台电脑上没有实际触发一次 AskUserQuestion 看原始数据（子 agent 里不能向人提问）；字段按官方类型定义写，测试用按文档构造的数据。

## 陷阱和假设

- 这份记录是佐证，不是证明：agent 也能自己用 Bash 运行 `canon human record`、喂一份编造的数据。它挡住的是“随手写一句人没说过的话”，挡不住存心伪造；D-45 和规则都这样写，不夸大。
- 对照只看同一个操作者，记录和转述都按 BR-2023 的顺序认操作者（`CANON_ACTOR` 优先，否则 `agent:` 加会话 id 前 8 位；hook 这边的会话 id 取自数据里的 `session_id`，因为 hook 的环境里不一定有 `CLAUDE_CODE_SESSION_ID`）。子 agent 和主会话共用会话 id（D-18），所以子 agent 转述主会话问到的回答也能对上；只在 Bash 里设了 `CANON_ACTOR`、hook 的环境里没有时，两边认出的操作者不同，会标“没有对应记录”。
- 只和“最近一条”比，不往前翻：人回答了第二个问题后再转述第一个问题的回答，会标“没有对应记录”。这是有意的：往前翻越多，越容易碰巧对上。
- 人用自己的话回答（不点选项）时，原话常常和选项不同；规则只认完全相同，这时标“没有对应记录”，这如实反映了“没有能对上的记录”。
- 旧的回答（这个变更之前记下的）没有标记，显示时不加任何标记。
- lore 里 90 个问题只有 22 个用上了这个记录，原因没核实；canon 这边“没有对应记录”的比例以后可以从事件表数出来。
