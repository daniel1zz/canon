## 为什么

D-8 定下要移植 7 个旧 skill，其中两个现在缺得最明显：

- 写规则除了模板之外没有任何指导。规则写得含糊、只写成功路径、没有从真实入口驱动的测试，实现者就会按最窄的理解去做（旧系统反复出现“组件在、测试绿、用户用不到”）。
- 合入后的代码评审会持续往 GitHub 提带 `canon-review` 标签的 issue，但没有任何流程去复现、去重、修复或拒绝它们，issue 只会越积越多。

## 要改什么

- 新增 `skills/canon-rules/SKILL.md`：来自旧的 baseline skill 和 ac-quality 参考资料。保留写规则前的追问清单（失败、边界值、重复、并发、谁被拒、看到什么）、写明取整和阈值的哪一边、只靠提示保证的金钱或权限、禁用的含糊动词、必须有一个测试从真实入口驱动行为。改写：去掉树形结构、引用关卡、覆盖率、adopt 和置信度字段；“只写业务”改成“只写可观察的行为，不写内部实现的名字”；没定的问题，方向类走 `canon human ask`，其余写决策；拆分按 D-5；流程是 `canon rule new` → 规则和例子 → 以编号开头的测试 → 和代码同一个提交。
- 新增 `skills/canon-triage/SKILL.md`：来自旧的 triage、agent brief、out-of-scope 和 to-issues。保留“先复现再判断”的三种结果、任务说明写行为契约而不是文件路径和行号、被拒的需求按概念记录、纵向切片和“agent 能独立完成 / 需要人”的区分。改写：去掉外部 setup skill 的依赖和七个标签的状态机；结果只有四类：不可复现或重复（写明原因并关闭）、简单的当场修、开一个变更（任务说明写进变更文件，合入后关闭 issue 并注明变更和提交）、用决策记录拒绝；去掉“反复给用户看直到批准”，按 P7 由 agent 决定，只有方向问题走 `canon human ask`。
- 不新增、不修改规则：skill 是给 agent 读的说明，不改变 canon 的行为。
