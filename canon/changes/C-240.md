## 为什么

负责人问安装和卸载是否都就绪、都干净（2026-11-04）。实测安装是干净的（只写项目里的文件，重复安装没有改动），但没有卸载；而且 canon 进了 main 之后没有受支持的办法移除：在 main 上直接提交删除被 git 守卫拒绝（BR-2126），开变更删掉 `canon/` 去合入，又因为读不到 `floor` 被拒（退出码 2）。负责人选择做 `canon uninstall`，并选定默认：`canon/` 下的知识保留、找回用的 refs 保留、有进行中的工作就拒绝。

## 要改什么

按 D-46 新增 `canon uninstall [--force] [--purge-recovery] [--remove-knowledge] [--timeout <分钟>]`（`src/cli/install/uninstall.ts`）：

- 有进行中的工作时以退出码 5 拒绝并列出（BR-2277）；项目里改过的 skill 文件不删，除非 `--force`（BR-2279）。
- main 上还有 `canon/config.yaml` 时：配了远端先同步，再开一个变更删掉 canon 的 skill 和清单、`.claude/settings.json` 里 canon 的条目和 `canon/config.yaml`，用删除之前的配置合入，合入后推到远端（BR-2278）。
- 之后（以及别的克隆里）只做本地清理：canon 的守卫、worktree、已合入的 `change/*` 分支、协调数据库目录、`.canon/` 和 exclude 行、非找回用的 `refs/canon/*`（BR-2280）；找回用的 refs 默认保留，`--purge-recovery` 才删（BR-2281）；后台命令还在跑时以 75 停下（BR-2283）。
- `--remove-knowledge` 在本地清理后另提交一次删掉 `canon/`（BR-2282）。

配套：`hook.ts` 的 `planUnhook`、`install.ts` 的 `planUnskills`/`applyUnskills`、`githook.ts` 的 `removeGuard`（先挪走再核对，别人的 hook 放回去），`session.ts` 导出 `keepReason`。

## 陷阱和假设

- canon 自己合入后推送时从 main 的配置读远端，而卸载的提交刚删掉了这份配置，所以卸载自己推送。
- 被守卫拒绝的 `git pull` 会把远端的文件留在工作区、main 不动；所以判断 canon 还在不在 main 上时看 main 分支，不看工作区。这个现象和卸载无关，另提 issue。
- 本地清理列 worktree 时不能拿 worktree 锁：锁文件在 `<git 公共目录>/canon/` 里，拿锁会把刚要删的目录又建出来。

## 教训

- 被守卫拒绝的 `git pull` 会把工作区和索引更新到远端的状态，main 却没动，下一次提交会悄悄带上这些差异 → 另提 GitHub issue，待负责人决定修法。
