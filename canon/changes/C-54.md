## 为什么

规则评审只看文字，测试检查只看测试名里有没有规则编号（BR-2005）。规则写“退出码 3”、代码返回 1、带编号的测试测的是别的东西时，两道检查都会放行。C-13 用独立子 agent 逐条对照过一次，查出 4 个真问题（#1 到 #4），但没有定期机制。lore 的教训：KN-287 里一份规格连续 8 轮评审都判“通过”，错误码却是错的，因为作者和评审读的是同一份过期文档；KN-565 里只看规则作答的 agent 错得很笃定。

## 要改什么

- 仿照合入后的代码评审，作为 `after_land` 在后台运行，不拦合入：只抽查这次合入改到规则或代码的领域，把规则、引用它的测试、领域代码一起交给一个独立 agent，回答“测试是否覆盖了例子的两侧”和“代码是否和规则一致”。
- 发现的问题按代码评审的方式提 issue，一个根因一个；按 issue 的结案情况统计准确率，准确率低就停用。
- 规则和测试。

## 陷阱和假设

- 每次运行的 token 花费没有测过；先只抽查改动涉及的领域，控制在一次合入一次调用。
- lore 的自查曾经比它省下的还贵（D-1），所以要先定好停用标准。
