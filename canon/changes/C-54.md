## 为什么

规则评审只看文字，测试检查只看测试名里有没有规则编号（BR-2005）。规则写“退出码 3”、代码返回 1、带编号的测试测的是别的东西时，两道检查都会放行。C-13 用独立子 agent 逐条对照过一次，查出 4 个真问题（#1 到 #4），但没有定期机制。lore 的教训：KN-287 里一份规格连续 8 轮评审都判“通过”，错误码却是错的，因为作者和评审读的是同一份过期文档；KN-565 里只看规则作答的 agent 错得很笃定。负责人 2026-11-04 要求现在做（“先保证其他”）。

## 要改什么

- D-43：后台运行、只查改到的领域、单独的 `canon-consistency` 标签、按结案原因算准确率并自动停用的标准，以及否决的方案。
- BR-2271：`scripts/consistency-review.ts` 找出改到的领域，每个领域一次评审调用，交给它规则全文、点名这些规则的测试段落、领域代码；`--max-domains`（默认 1）和 `--max-bytes`（默认 150000）限制每次合入的花费。
- BR-2272：发现必须点名这个领域的一条规则；提交、去重和失败处理复用代码评审（BR-2072、BR-2210、BR-2211），标签 `canon-consistency`。
- BR-2273：`--precision` 输出准确率；已关闭的 issue 够 `--min-closed`（默认 10）个、准确率低于 `--min-precision`（默认 0.5）时不再调用评审命令。
- 代码：`src/knowledge/review/code-review.ts` 把解析发现、找同根因 issue、提交拆成带标签和名字参数的函数，代码评审照旧用 `canon-review`；新文件 `src/knowledge/review/consistency.ts` 和 `scripts/consistency-review.ts`。
- 不写进 canon 仓库的 `hooks.after_land`：开不开、每次查几个领域留给负责人。

## 陷阱和假设

- after_land 运行时工作目录不一定是 `CANON_HEAD` 的代码树（main 可能又前移了），所以和代码评审一样只从 git 读：把 `CANON_HEAD` 的代码树 `git archive` 到临时目录，再用 canon 自己读配置、规则和测试标题的函数。
- 输出行用 `code-review: consistency: ` 开头，`canon work after-land` 不改就能照抄（BR-2166）；没有改 `src/config/hooks.ts`。
- 重复 issue 按 triage 的做法以 `not planned` 关闭，会算成误报；停用线是 0.5，有余量。
- 每次调用花多少 token 没有实测：提示的字节数每次都输出，可以从 after-land 日志里看。
