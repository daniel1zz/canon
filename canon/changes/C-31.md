## 为什么

D-8 定下要移植的 7 个 skill 里，有两个和“做什么、做成什么样”有关：`lore-product` 的机会识别、验证、拆解三个模式和证据阶梯，`lore-product-benchmark` 的对标拆解，以及 `lore-prototype` 加上 `lore-design-ui` 的两份参考资料。旧版本混着 lore 流程（PRD 更新、批量治理、`lore create`）、强制的逐步思考，discovery 模式还让子 agent 扮演用户给出付费意愿，这正是它自己定义的最低一级证据（E6）。design-ui、prototype 对“变体该多不一样”有三处说法互相冲突。

## 要改什么

- 新增 `skills/canon-product/`：SKILL.md 加 `references/` 下 benchmark、opportunity、validate、decompose 四个模式文件。保留证据阶梯 E1–E6、“伪装成需求的方案”检测、每个机会至少 3 个方案（去掉、自动化、默认值等方向）、“熟人来源降一级”、Problem Score 和“变通办法这一维最诚实”、拆解时“把不改的步骤也画上”、对标的三个样本位（领头产品、最接近的同类、非产品替代）和四种分类。去掉 ideation、roadmap、tech-assessment、ux-research、discovery、PRD 模式，以及交接表、治理流程和强制的逐步思考。明确写出“子 agent 扮演用户”只算 E6，并分清 AI 会话能自己做的实验和需要人的实验。结果的去处：调研写成笔记（`canon note new`），方向选择用 `canon human ask` 交给人并附证据，产品行为通过正常的变更流程写成规则。
- 新增 `skills/canon-prototype/`：SKILL.md 加 `references/` 下 logic、ui、design-system-inheritance、prototype-fidelity 四个文件。保留逻辑原型“核心模块保持纯净，TUI 调用它，反过来不行”、UI 变体挂在已有页面上、切换条在生产构建里隐藏；继承现有 UI 的两份清单、破坏性改动先问人、范围外区域冻结为空框（不许对构建者说“简化占位”）；保真要求（任务按行号范围引用原型、标准组件逐字复制、视觉对比、色值漂移检查、axe、标记一致性检查）。去掉治理流程、硬拦截清单和预览脚本、本地预览服务器之类的工具。
- 用一条明确的规则解决变体冲突：已有界面（包括挂在其中的新区块）上的变体只在视觉和密度上不同；结构不同的变体只用于新界面，或者人明确选择了这样做（`canon human ask`）。选中的变体记成一个决策，其余变体写进被否决的方案。
- 不新增、不修改规则：skill 文件不在任何领域的 `code:` 范围里。
