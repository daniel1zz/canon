## 为什么

C-255 / D-49 做了评审拦截的判定，包括自动判定 `canon verdict run`。2026-11-04 的独立评审发现：事件表里有 45 条 `review.block`、0 条 `review.verdict`，没有任何真实使用，而 `run` 的实现和测试已经写完。负责人 2026-11-04 选择了“缩小：去掉自动判定 (推荐)”。评审还指出：按指纹找“拦截时的提交”在并发合入时找到的不是评审看到的代码；`pending` 在 `run` 判完后仍然列出全部拦截，手工记也清不空；统计的分母算了判不了的拦截。

## 要改什么

- 去掉 `canon verdict run`：退役 BR-2290，删除它的代码和测试；保留 `pending` 和 `record`。
- `review.block` 事件多记 `commit`（评审那一刻变更的 `HEAD`）；`pending` 和 `record` 直接读它，删掉 `commitWithFingerprint` 和“前一条 `land.ok`”的回退。没有 `commit` 的旧拦截不可判定：不列出（BR-2253）。
- 每条意见有一条判定（`model` 或 `human`）这次拦截就算判完，手工记完能清空 `pending`（BR-2253）。
- `canon stats` 的分母只算可判定的拦截（BR-2255）。
- BR-2254 的 agent 拒绝信息不再提 `run`。
- D-49 就地改：只手工记；自动判定写成暂不采用的选项，去掉“由构造保证盲判”和与 `run` 有关的后果。
- 不做（负责人决定）：评审意见里拦截与建议混在一起的问题，写进 D-49 后果作为已知限制，等手工判过一批、重新考虑自动判定时再一起看。
