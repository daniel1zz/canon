## 为什么

#74：BR-2009 要求规则评审拿到“每个受影响领域的完整上下文”，但 `src/knowledge/review/review.ts` 只为改动过的文档和改动过的 README 生成上下文。一次只用 `git rm` 删掉一条规则的合入，评审只看到被删的原文和全局索引，看不到这条规则所在领域里剩下的规则，判断不了删掉它会不会让别的规则失去依据。

核对 #74 时还发现：BR-2009 说评审收到“被删除文件在 main 上的原文”，但被删除的领域 README 只给了路径，没有原文。

baseline 核对（N-4）还发现 knowledge/review 里没有规则的行为：评审命令的输入输出约定（提示从标准输入进，结论 JSON 从标准输出出，前后可以有别的文字）；skill 没有 description 或 front matter 解析不了时重复评审怎么处理；规则评审提示里附上的已接受决策列表。

## 要改什么

- `review.ts`：被删除的规则给它所在顶层领域的当前内容；被删除的决策给它原文里提到的规则所在顶层领域的当前内容；被删除的 README 给原文。
- `src/work/land/land.ts`：被删除的 README 连同 main 上的原文一起交给 `reviewPrompt`（只改这一处，几行）。
- BR-2009：写明删除时给哪个领域的上下文、README 也给原文，补例子。
- BR-2036：写明提示里还有已接受决策的编号和标题。
- 新规则：评审命令的输入输出约定。
- 新规则：skill 的 description 缺失或解析不了时，重复评审照常进行，提示里写明。

## 陷阱和假设

- 被删除的规则所在的整个领域也被删掉时，没有当前内容可给，只给原文。
- `src/work/land/` 的 agent 同时在改 land；`land.ts` 的改动只限于 `deletedReadmes` 那几行。
- `instructions` 列出的文件不存在时现在是跳过（BR-2143 的评审建议问到这一点），要负责人决定，这次不改、不写规则。
