## 为什么

规则评审已经三次拒绝同一类问题：规则的 `## 例子` 写了改动前产品怎样（C-243、C-252、C-257、C-258 改 BR-2285，C-246 改 BR-2284），而例子应该只写产品现在必须怎样。每次都要等到合入时的 AI 评审才发现，再开一次合入。负责人 2026-11-04 的选择：“加检查，拒绝合入 (推荐)”。

找过 git 历史：`git log -p -- canon/rules` 里删掉的、含这类写法的例子行一共 6 行（BR-2285 五行，BR-2284 一行），全都用 `改动前`。现在的 main 上还有两行：BR-2284 的第一个和第三个例子（`；改动前 ... 留在暂存区`）。

复现（改动前）：`src/knowledge/check/check.test.ts` 的 BR-2301 用例：期望两条写了改动前行为的规则各报一条 `example-before-change`，实际一条也没有。

## 要改什么

- `src/knowledge/check/check.ts`：新的发现 `example-before-change`，只看没作废的规则的 `## 例子` 段，去掉代码后找固定的几个写法。它是 `canon check` 的一种发现，合入时归在已有的 `check` 这一步，不是新的检查名，所以不用改 `checks.ts` 和 `check_reviews`，也没有 BR-2248 的两次合入顺序问题。
- 新规则 BR-2301（`knowledge/check`）。
- BR-2284：去掉例子里的两处 `改动前`；顺手处理它的评审建议：补一个 `git pull --rebase` 停在 rebase 中间时不放回的例子（HEAD 分离，不算签出 main），测试在 BR-2298 用例里加断言。D-16 修订的那条建议已由 D-53（C-268）处理；BR-2278 的那条等改 BR-2278 时再处理。

## 陷阱和假设

- 写法列表：`改动前`、`修改前`、`修复前`、`原来会`、`以前会`、`before this change`、`before the fix`、`previously`。历史里真出现过的只有 `改动前`，其余是同义的说法，在现在所有规则的例子里都没有命中。
- 没收的写法：`之前会`、`改动之前`（“在 X 之前会 Y”“在做任何改动之前检查”说的是先后顺序，BR-2277 的规则段就有）；`原来是`（BR-2176 的例子“`info/exclude` 原来是 `.env`”说的是输入原先的状态）。
- 反引号里的文字不查：产品的输出里可能真有这些词。
- PATH 上的 `canon` 是主 checkout 构建的旧版本，本地验证要用 `bun src/cli/main.ts check`。

## 教训

- 规则评审反复拦下的同一类文字问题，能写成固定写法时就该做成 `canon check` 的发现 → BR-2301 是这一次的机制；以后同类问题要不要都这么做，待负责人确认是否固化。
