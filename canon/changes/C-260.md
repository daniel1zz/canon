## 为什么

用 `canon work start --title` 新建的变更，变更文件只在它自己的分支 `change/C-n-…` 上，合入前 main 上没有。delegate 项目里 C-1 就是这样：做它的会话执行了 `canon work stop --release --next "..."`，之后在主 checkout 里 `canon change list` 输出 `(no changes)`，而工作说明写的是“没有任务时取 canon change list 里第一个没被认领的”；照着做的新会话找不到事做。C-1 只出现在 `canon brief` 最后一行 `Unfinished changes with handoffs: C-1` 和 `canon work status` 里。工作说明让 agent 去看的那张单子，恰好漏掉最需要人接手的工作（交接了、释放了认领、只在分支上的变更），brief 里的两张单子对“哪些变更没做完”说法也不一致。

## 要改什么

- 新规则 BR-2291（work/session）：`canon change list`（含 `--json`）和主 checkout 里 `canon brief` 的待办行，除了当前 checkout（brief 是 main）上的变更，也列出只在变更分支上的变更：从分支 `change/C-n` 或 `change/C-n-…` 直接读变更文件（`git show <分支>:canon/changes/…`），不需要 worktree 还在。每个变更标出 `on branch <分支>`（只在分支上时）、`handoff: <下一步>`（change list 写全，brief 只写 `handoff`）和 `claimed`（认领仍然有效）；`--json` 每项多 `on_branch`、`handoff`、`claimed` 三个键。顺序：待办清单里的先按清单，然后是没列进清单、已经开始的（有 handoff 或有变更分支），最后是其余的，各自按编号。
- 改 BR-2148：顺序里加“已经开始的排在没开始的前面”，指向 BR-2291。
- 改 BR-2149：列的是和 `canon change list` 同一组变更、同样的标记，不只是 main 上的。
- BR-2024 的说法跟着调整（待办行不只列 main 上的）。
- 决策 D-50（proposed，修订 D-20）：从哪里找这些变更、怎么排序，否决的方案写进去。
- 工作说明（src/work/session/guide.ts）里“取 canon change list 里第一个没被认领的”那句写明列表包括只在分支上的变更和已开始的排前面。
- 代码：新文件 `src/work/session/inflight.ts`（读变更分支、标记、排序），`canon change list`（src/knowledge/documents/commands.ts）和 `canon brief`（src/work/session/commands.ts）都用它；`inBacklogOrder` 加“已开始”这一档。

## 陷阱和假设

- 待办清单不能列只在分支上的变更（`canon check` 会报 `ref-dangling`，BR-2150），所以它们只会排在“已开始”这一档。
- 同一个编号有两个分支时（`canon work start` 会拒绝，BR-2107）照样列出，标出全部分支。
- 分支上的变更文件读不了或格式不对时命令失败（退出码 4），不悄悄跳过。
