## 为什么

会话开始的 hook 运行 `canon brief`，而 `canon brief` 先调用 `workspace()` 再输出工作说明（BR-2090）。所以在仓库外、`canon/config.yaml` 写错（退出码 2）、或者机器上 PATH 里没有 canon 时，会话对 canon 一无所知，agent 可能直接改 main。旧系统 lore 的 KN-402：让 canon 能用起来的说明，不能只放在需要 canon 能用的渠道里。另外，hook 失败时它的 stdout 不会给模型看，只写 stderr 的错误等于没说。

## 要改什么

- `canon brief`（`src/cli/main.ts`）：先输出工作说明，再打开工作区；失败时除了 stderr 和原来的退出码，还在 stdout 输出 `canon brief failed:`、原因，以及“修好后重新运行 canon brief，在那之前不要直接改 main”。工作区打开之后的异常也同样先在 stdout 说一句再抛出。
- hook 命令（`src/skills/hook.ts`）改为 `canon brief || echo '...'`：brief 失败或 canon 不在 PATH 上时 echo 一段说明，整条命令以 0 结束。旧形式 `canon brief` 仍能识别：`canon update --check` 列为过期（`older form`），`canon install`、`canon update` 原地改写那条命令，不会出现两条。
- 本仓库的 `.claude/settings.json` 用 `canon install` 升级成新形式。
- 规则：BR-2090（说明在任何可能失败的事之前输出，失败也写到 stdout）、BR-2087（hook 的新形式、旧形式的升级）、BR-2084（旧形式算过期）。

## 陷阱和假设

- 假设 Claude Code 只在 hook 退出码为 0 时把 stdout 给模型看，所以 hook 用 `||` 把失败变成 0；`canon brief` 自己仍按 BR-2022 用非 0 退出码，命令行上直接运行时能看出失败。
- 还没升级的旧版 canon 不认识新形式：它会把新形式当作缺少，`canon install` 会再加一条旧形式。本仓库合入后 after_land 会重新构建 dist/canon，只有这之间的短暂窗口；其他项目在用旧版 canon 时不要跑新版的 `canon install`。
- echo 的说明不能出现单引号（整条命令用单引号包住）。
