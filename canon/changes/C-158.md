## 为什么

baseline 核对（N-4）在 `canon work start` 和 `canon work clean` 里找到几处和规则不符、或没有规则描述的行为：

- issue #54：`canon work clean c-1` 用原样的编号去比 worktree 目录名，报 `kept c-1: no worktree`，什么都不删；`canon work start` 却接受小写编号（BR-2152）。
- `start --title` 建好 worktree 之后，写或提交变更文件失败时直接返回，worktree、分支和认领都留着，违背 BR-2029“不留半成品”的意思。
- `git worktree add` 失败时 start 放掉了认领，但没写 `start.refuse`；BR-2026 要求每次拒绝都记进事件表。
- clean 删掉 worktree 后用 `git branch -d` 删分支，没有规则写这件事；git 拒绝删时分支静默留下。
- 分支名会截到 80 个字符，BR-2012 没写；slug 本身最多 60 个字符也没写。
- BR-2012 的分支名和默认路径、BR-2047 的默认路径、BR-2029 重试会重新执行 setup、BR-2062 被拒绝的 start 不提示、BR-2019 clean 中途被杀之后 start 照常成功，这些例子没有测试。

## 要改什么

- `clean` 按大写比较编号，信息里保留原样的写法（BR-2152 加例子）。
- `start` 在写或提交变更文件失败时，像 setup 失败一样删掉刚建的 worktree 和新分支、释放认领，写 `start.refuse`（原因 `change-file`），退出码按失败的原因；`git worktree add` 失败时写 `start.refuse`（原因 `worktree`）。改 BR-2029、BR-2026。
- 新规则 BR-2188 写明 clean 删分支的行为，包括 git 拒绝时分支留下（是否改成报出来，留给负责人）。
- BR-2012 写明 slug 规则和 80 个字符的上限。
- 补上面列的测试。

## 陷阱和假设

- 分支名 80 个字符的截断只有编号长到 10 位以上才会起作用（slug 最多 60 个字符），所以 BR-2012 没有为它写例子。
- `git branch -d` 按主 checkout 当前签出的提交判断是否已合入，不是按 main；主 checkout 不在 main 上时，已合入的变更分支会留下。

## 教训

- clean 静默留下删不掉的分支 → 待负责人确认是否固化（报出来，或改成按 main 判断后删除）。
