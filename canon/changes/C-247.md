## 为什么

负责人 2026-11-04 选了两条教训要固化：“统一设测试超时 (推荐)”和“测试里用固定的 git 配置 (推荐)”。

- 超时：起好几次 canon 或 git 子进程的测试，机器负载高时超过 bun 默认的 5 秒（C-59 的 `drop.test.ts`，C-238 的 `backlog.test.ts`，后者让 main 的后台 floor 失败过一次）。现在是 34 个测试文件各自写 `setDefaultTimeout`，新文件忘了写就又回到 5 秒。
- git 配置：#27 漏掉，是因为测试只在这台机器默认的 git 配置下跑过（开发者的 `~/.gitconfig` 里 `branch.autoSetupMerge=always` 才会出问题）。反过来，开发者或 CI 机器上的 git 设置也能改变测试结果。

这是测试基础设施，不是产品行为：canon 对用户项目做的事没有变，所以不新增、不修改规则。D-32 和 BR-2005 管的是规则要有测试点名，不管测试怎么运行，这里不适用。

## 要改什么

- 新增 `scripts/test.sh`：写一个只含测试需要的设置的临时 git 配置文件，设 `GIT_CONFIG_GLOBAL` 指向它、`GIT_CONFIG_NOSYSTEM=1`，再用统一超时运行 `bun test --timeout <毫秒> "$@"`，结束时删掉临时目录，退出码就是 `bun test` 的退出码。
- `canon/config.yaml` 的 `floor` 和 `test_command` 都改成调用这个脚本，所以 floor、`canon work test`、`canon work test --all` 都用同一个超时和同一份 git 配置。
- 删掉和统一超时一样长或更短的文件级 `setDefaultTimeout`；更长的（写了 `reason` 的、故意等真实时间的）保留。
- 固定的 git 配置只写：`user.name`、`user.email`、`init.defaultBranch = main`、`core.excludesFile` 和 `core.attributesFile` 指向空文件（这两个的默认路径在 `$XDG_CONFIG_HOME/git/` 下，不在配置文件里，`GIT_CONFIG_GLOBAL` 挡不住）。

依据：

- bun 的 `bunfig.toml` 没有测试超时这一项（bun 1.4.4 自带文档 `docs/runtime/bunfig.mdx` 的 `[test]` 一节没有 `timeout`；实测写 `[test] timeout = 7000`，测试仍在 5000 毫秒超时）。官方文档写的是命令行参数：“Use the `--timeout` flag to specify a _per-test_ timeout in milliseconds. If a test times out, Bun marks it as failed. The default value is `5000`.”（`docs/test/index.mdx`）。实测 `--timeout` 对同一次 `bun test` 里的每个文件都生效，文件自己的 `setDefaultTimeout` 和单个测试的超时参数仍然优先。
- 不能在 `bunfig.toml` 的 `test.preload` 里调 `setDefaultTimeout`：实测只对第一个文件生效，floor 一次跑全部文件时其余文件仍是 5 秒（和 C-111 记下的“`setDefaultTimeout` 只作用于调用它的文件”一致）。
- 不能在测试工具代码（`src/work/testkit.ts` 或 preload）里改 `process.env` 来设 git 变量：bun 的 `Bun.spawn` 文档写“Defaults to `process.env` as it was when the current Bun process launched. Changes to `process.env` at runtime won't automatically be reflected in the default value.”（`bun-types` 1.4.4 `bun.d.ts`），实测子进程看不到。测试里的 git 有很多条路径启动（`src/kernel/git.ts` 的 `git()`、测试自己的 `Bun.spawnSync`、子进程里的 canon 命令行、fixture 的 floor shell），只有在 `bun test` 启动前设好环境变量，才能全部覆盖。
- git 文档（git 2.50.1 `man git`）：“GIT_CONFIG_GLOBAL, GIT_CONFIG_SYSTEM: Take the configuration from the given files instead from global or system-level configuration files. … if GIT_CONFIG_GLOBAL is set, neither $HOME/.gitconfig nor $XDG_CONFIG_HOME/git/config will be read.”；“GIT_CONFIG_NOSYSTEM: Whether to skip reading settings from the system-wide $(prefix)/etc/gitconfig file.”。`man git-config`：`core.excludesFile` “Defaults to $XDG_CONFIG_HOME/git/ignore”，`core.attributesFile` 的默认值也在 `$XDG_CONFIG_HOME/git/` 下。

测量和超时取值：

- 以前的 `canon work test` 日志只记失败测试的时间（最慢的是 30 秒文件超时下被打断的 BR-2251、BR-2099），量不出通过的测试多慢。所以在改动前的代码（main fe8f3da）上用 `bun test --reporter=junit` 跑了一次全量（80 个文件，915 个测试，1139 秒，系统负载 16 到 22）。
- 最慢的单个测试：`batch.test.ts` 的 BR-2049 BR-2172 13.35 秒、`batch-edges.test.ts` 的 BR-2172 BR-2173 11.92 秒、`main.test.ts` 的 BR-2154 10.19 秒、`uninstall.test.ts` 的 BR-2283 9.27 秒，另有约 20 个在 6 到 9 秒。它们都在文件或测试自己设了 30 秒以上超时的地方，否则在 5 秒时就失败了。
- 取 30000 毫秒：比测到的最慢一个多一倍以上。C-111 记过负载到 40 以上的情况，测试时间大约随负载翻倍，13.35 秒翻倍后约 27 秒，仍在 30 秒以内。30 秒也是现在 25 个文件各自写的值。
- 于是这 25 个文件的 `setDefaultTimeout(30_000)` 和它们的 `reason` 注释删掉了。60 秒和 90 秒的文件级超时，以及单个测试自己的超时都保留：它们是故意设的，而且改 `src/work/land`、`src/work/watch` 的测试会和别的会话正在做的变更冲突。

验证：用一个 `HOME` 里写着 `branch.autoSetupMerge=always`、`init.defaultBranch=trunk`，并带全局 ignore 文件的探针测试。经过 `scripts/test.sh` 时，`git config --show-origin --list` 只列出脚本写的文件和仓库自己的 `.git/config`，新仓库的分支是 `main`，`a.txt` 没有被忽略。直接 `bun test` 时会读到那份 `.gitconfig` 和系统的 `/Library/Developer/CommandLineTools/usr/share/git-core/gitconfig`，分支变成 `trunk`，`a.txt` 被忽略。

## 陷阱和假设

- 直接运行 `bun test`（不经过 `scripts/test.sh`）仍是 5 秒超时、读本机 git 配置；floor 和 `canon work test` 都经过脚本。
- 临时 git 配置每次运行写一份新的，测试就算用 `git config --global` 改了它也不会留到下一次。
- 测试里只带 `PATH` 启动的子进程（`update.test.ts` 的几处）拿不到这两个变量，它们不运行 git。

## 教训

- bun 的测试超时只能用命令行 `--timeout` 统一设，`bunfig.toml` 没有这一项，preload 里的 `setDefaultTimeout` 只管第一个文件 → 由 `scripts/test.sh` 保证（floor 和 `test_command` 都调用它）。
- 测试进程里改 `process.env` 传不到 `Bun.spawn` 的子进程 → 只靠文字：这是 bun 的行为，canon 没有检查能发现某段代码依赖这一点。
