## 为什么

#103：main 落后远端的 clone 里 `git pull` 被 main 守卫（BR-2126）拒绝，但 git 的 `merge --ff-only` 先把暂存区和工作区改成远端的提交，再移动 main；守卫在 `prepared` 状态拒绝时只中止 ref 更新，git 不会把暂存区和工作区改回来。结果 main 没动，远端的改动全部留在暂存区，下一次提交会把它们当成新提交记下，`canon sync` 也因为 main 有未提交的改动而拒绝。`git merge --ff-only <分支>`、`git reset --hard <提交>` 同样如此。

复现（改动前）：issue 里的脚本（clone b 里 `git pull` 后 `git status --short` 显示 `A  canon/changes/C-1-t.md`、`A  new.txt`）；`src/cli/install/githook.test.ts` 的 BR-2284 用例。

## 要改什么

- `src/cli/install/githook.ts`：守卫拒绝 main 的一行后，如果 hook 所在的 checkout 签出的是 main、新提交是已有的提交（别的 ref 包含它或它是 `FETCH_HEAD`），用 `git read-tree -m -u <新> <main>` 把暂存区和工作区切回 main，保留没提交的改动；切不回去时写明原因。新提交在远端跟踪分支上或是 `FETCH_HEAD` 时提示用 `canon sync`。
- 新规则 BR-2284（`cli/install`）。BR-2126 不变：拒绝什么、退出码都照旧。
- 守卫脚本的内容变了，已装的守卫按 BR-2085 显示为过期，`canon update` 或 `canon install` 换成新的。

## 陷阱和假设

- git 没有在快进检出之前运行的 hook（`pre-merge-commit` 只在要造合并提交时运行），所以拦不在前面，只能在拒绝时改回来。
- 只在新提交是已有提交时改回：`git commit`、`git merge --no-ff`、`git cherry-pick` 造的新提交没有别的 ref 包含它，暂存区里是用户自己的工作，两路切换会把它换成 main 的内容，只剩一个没人引用的提交，所以不动。
- 两路 `read-tree -m -u` 按 git 的规则只替换和旧树一致的条目，工作区里没暂存的修改不会被覆盖；冲突时整个失败、什么也不写。`git update-ref` 这种没碰过暂存区的命令走同一路径也安全：暂存区和 main 一致的条目原样保留。
- 依赖 merge、reset 在更新 ref 之前已经写完并解锁 index（git 2.50.1 实测）；hook 运行时 git 还拿着 ref 的锁，`read-tree` 不碰 ref。
- `git reset --hard` 在 ref 更新之前已经丢掉了没提交的改动，这是 git 自己做的，守卫找不回来。
- `git pull --rebase` 在 main 上被拒绝时 HEAD 是分离的，不在这条规则里，留给 git 的 rebase 状态处理。

## 教训

- 一个在 `prepared` 状态拒绝的 ref 守卫只能保证 ref 不动，命令在 ref 之前做的事（检出、写 index）照样留下 → 由 BR-2284 保证快进这一类；其他命令只靠文字：要逐个命令看它在 ref 更新前做了什么。
