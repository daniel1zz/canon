## 为什么

#134（两个切片中的第一个；第二个是 C-390，合入时先评审再跑 floor）：规则评审只在 `canon work land` 里运行，变更要知道评审怎么看，只能去合入。评审对照整个领域（BR-2009），作者通常只读了 `canon context` 的标题和自己改的规则，所以和没打开过的规则矛盾，要到合入时才暴露。

证据（Godot 项目，约 25 个并发会话，`canon stats --since 5300`，2026-11-06 20:50 到 11-07 02:44）：31 次合入成功、40 次被拒；评审拒绝 12 次，占拒绝的 30%，是最多的一类；其中 8 次是新改的规则和作者没打开过的规则矛盾。main be6c0d7 上没有任何命令能在合入之外运行评审（`canon work --help` 里没有）。

## 要改什么

新命令 `canon work review`，在变更的 worktree 里运行：

- 收集这个变更相对 main 的合并基点改动的规则、决策、版本、领域 README 和常驻说明（含已提交、未提交和未跟踪的，和 `canon work test` 选文件用同一份改动清单），按合入时完全相同的方式生成评审提示，用 main 上配置的 `review` 命令和时限，在同样的临时 worktree 里运行（BR-2216），所以结论和合入时一致。规则评审和常驻说明的重复评审（BR-2143）都跑，就像合入时一样。
- 输出结论和每条意见；退出码：`ok` 为 0，`block` 为 1，评审命令失败或结论无效为 4，没有要评审的改动时为 0 并说明“没有规则、决策或常驻说明的改动”，`review: none` 时为 0 并说明已配置为不评审，没配置 `review` 时为 2 并说明要配置。
- 不在主 checkout 或不在变更的 worktree 里运行时，退出码 2。
- 记一条事件（种类新定，例如 `review.preview`），带结论和意见数，不当作合入的评审结果：合入时照常再评审一次（最终关口不变）。
- 建议不像合入那样挂到文档上（D-21 只针对合入的评审），免得同一条建议记两遍。
- 分支落后 main（合并基点不是 main 的最新提交）时，照样评审 worktree 当前的文字，并多打印一行：main 在合并基点之后又有 N 个提交，合入时的评审以 rebase 后的文字为准，结果可能不同，先 `git rebase main` 再跑更准。退出码不受影响。
  - 否决：在临时目录里先把变更（含未提交的改动）合到最新 main 上再评审。结果更接近合入时，但要复制未提交的改动、处理冲突，复杂很多；一行提示加上作者自己 rebase 就够了。
- 每次运行就是一次模型调用（本仓库改一条 `work` 规则约 42 万字节的提示），工作说明里只建议改了规则或决策时、准备合入前跑一次，不建议每次小改都跑。

规则放在 `knowledge/review` 下（新增一条），例子覆盖：ok、block、命令失败、没有改动、`review: none`、没有配置、在主 checkout 里运行。`canon brief` 的工作说明里“合入前”那一段加一句：改了规则或决策的变更，合入前运行 `canon work review`。

不在范围内：调整合入里评审和 floor 的顺序（C-390）；评审提示过大（C-388）；缓存评审结果让合入复用（结论依赖 main 的上下文，main 一变就失效，不做）。
