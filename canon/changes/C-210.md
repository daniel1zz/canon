## 为什么

同一次合入里既在 canon 的代码里新增配置键、又在本仓库的 `canon/config.yaml` 里用上它，其他会话装的旧 canon 读到未知键，所有命令都以退出码 2 失败（BR-2045），直到重新构建。C-181 和 C-194 的教训都记下了这件事，C-194 靠文字分两次合入才避开；2026-11-04 main 上的后台测试又因为同类原因失败了一次（979c475，一个还用旧代码的 watcher 读到了 `typecheck_command`）。负责人 2026-11-04 在 AskUserQuestion 里选择：“新配置键不能在同一次合入里就用上”。

## 要改什么

- 新规则 BR-2248（work/land）：被合入的树的 `canon/config.yaml` 用到一个键，这个键在被合入的树里声明了、main 的 base 提交里没有声明时，合入以新的原因 `config-key` 被拒（退出码 1），提示先合入键、第二次合入再用。
- 代码：新文件 `src/work/land/config-first.ts` 读两棵树里 `config-keys.ts` 的键声明（`git grep`，每棵树一次）和被合入的树里 `canon/config.yaml` 的顶层键；`src/work/land/land.ts` 的 `verifyChange` 在 `canon check` 之前调用它，所以单独合入（两种 `floor_timing`）和一起测的每个成员都会走到；一起测时传 main 的 base，不传批里的前一个成员。
- `src/work/stats/checks.ts` 的 `LAND_STAGES` 在 `floor` 和 `check` 之间加 `config-key`（BR-2067 以这个列表为准，不用改规则文字）。
- 测试：`src/work/land/config-first.test.ts`，按 BR-2248 的例子。

## 陷阱和假设

- 只认 `key: "<键名>",` 这种一行写法，这是现在 22 个键的统一写法（`src/config/key.ts` 的 `configKey`）；有人换了写法，这一步会漏报而不是误报。
- 只在 main 的 base 提交里有 `config-keys.ts` 声明时检查，普通项目里没有这种文件，不受影响。
- 要求键在被合入的树里有声明，才算“本次新增”：两边都没声明的键（拼错）由 BR-2045 处理，不在这里报一个误导人的“先合入”。
- after 模式下 main 已经声明、但 PATH 上的 canon 还没重新构建的情况仍由 BR-2224 处理，两步互补。
- 本变更和 C-182 都改 `src/work/land/land.ts`，改动只加几行，先合入。
