## 为什么

#170：一个变更合入时因为和规则无关的原因被拒（floor 失败、超时、有没提交的改动），再合入时规则文字一个字没改，规则评审却又完整跑一遍。另一个项目一天里评审通过 130 次、拦下 32 次，复用只有 4 次，真正合入 77 次；每次评审要调 2 到 9 次模型、每次约 300 KB，用完了提供方的 5 小时额度。

原因：复用的键是整份评审提示的哈希（D-70、BR-2361），提示里带着整个顶层领域和全部规则索引（BR-2009、BR-2036）；main 上只要又合入了别的规则，键就变了。合入越频繁越难复用。

负责人 2026-11-09 把怎么改交给 agent 判断（原话“按照你的判断来”），选的是下面这个“只对新变化再评一次”的做法。它修订 D-70（复用只看整份提示）和 D-72（不为省钱缩小评审上下文）：完整评审照旧给整个领域，只有重新合入、改动文字没变时才用小评审。

先做的是减少重新合入的变更：C-435（#154）、C-438（#161）、C-428（#156）；这个变更在它们之后。

## 要改什么

- 合入的规则评审前：这个变更有一次合入评审通过（`review.ok`），并且这次评审的改动文档（规则、决策、版本、领域 README）和那次逐字节相同，就不跑完整评审，而是：
  - 找出那次评审时的 main 到这次 rebase 后的 main 之间，新增或改过的生效或规划中规则和已接受决策（不限领域：完整评审通过索引看得到别的领域，小评审只看同领域会看得更少，见 D-81）；
  - 一份都没有 → 沿用那次的结论（记 `review.reused`，注明是按改动文档沿用）；
  - 有 → 跑一次小评审：提示只含改动文档、这些新文档和原来的评审要求，问它们之间有没有矛盾；通过就算这次评审通过，记 `review.ok`（注明是增量评审），拦下就照常拒绝。
- 改动文档有任何变化、没有之前通过的评审、或者那次评审的 main 提交读不到 → 照常完整评审。
- 措辞判断（BR-2239）需要的、上次评审没确认过的规则照常要完整评审。
- 新决策 D-81 修订 D-70、D-72，写明这个例外和被否决的方案（#170 原来要的“改动文档没变就无条件复用”：会漏掉和新规则的矛盾）；BR-2361 指向新规则 BR-2396；BR-2397 让 `canon stats` 分开数。
- `canon stats` 能区分完整评审、增量评审和沿用，便于看省了多少。

不做：不改完整评审的上下文（仍是整个顶层领域）；不改预览评审（`canon work review`）；不改常驻说明的重复评审。
