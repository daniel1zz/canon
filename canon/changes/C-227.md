## 为什么

#43（C-131、C-218 合入后的代码评审）：一起测的成员被领头锁定后收到信号，它的 `failIfActive` 因为被锁定返回 false，于是不撤回关闭提交，接着退出；领头移动 main 被拒后解锁，只在那一刻查一次成员进程还在不在（`reopenForGoneLander`）。成员这时还在 `failIfActive` 和 `process.exit` 之间（例如 `unbindFromLander` 在等协调数据库的写锁），两边都跳过它：成员分支留着 `status: done`，什么都没合入，违反 BR-2018。

根本原因：撤不撤回由两个进程各在一个时刻单独判断，中间没有交接。

复现（改动前）：`src/work/land/batch/batch.test.ts` 的两个 BR-2099 BR-2018 用例：被锁定的成员收到 SIGTERM 后立刻退出，从不等这一批的结果；领头解锁后查它时如果它还在（问题里的情形），没有人撤回。

## 要改什么

- 成员的信号处理在被锁定时不立刻退出，而是等这一批有结果（`settleLocked` 轮询）：领头把它记为已合入就保留关闭提交直接退出；被解锁（main 没移动），或领头不在了、心跳过期，就回到等待，再照常标失败、记 `land.killed`、自己撤回关闭提交。等待期间更新自己的心跳。这样“成员自己撤回”和“领头替不在的成员撤回”按成员进程在不在分开，不会两边都跳过。
- BR-2099：锁定时收到信号改为等结果，补两侧的例子；BR-2018 的例外段和例子跟着改。
- 代码：`src/work/land/queue/queue.ts` 新增 `settleLocked`；`src/work/land/land.ts` 的信号处理先 `waitWhileLocked`。
- 测试：`batch.test.ts` 两个用例（解锁 → 自己撤回、领头查时它还在所以领头不动；记为已合入 → 保留关闭提交），`queue.test.ts` 一个 `settleLocked` 用例（领头被 SIGKILL 后放开）。

## 陷阱和假设

- 等待在信号处理里同步进行（`Bun.sleepSync`），这期间这个合入的其他代码都不运行，这是有意的：否则轮询可能同时走到“已在批里合入”的收尾。
- 等待的上限由领头决定：领头不在了或心跳超过 `lander_stale_minutes` 就放开；工具超时之后再发的 SIGKILL 会结束等待，那时成员进程已不在，领头解锁后会替它撤回。
- 仍然留下的一种情形：领头查成员时它还在、之后、它自己撤回之前被 SIGKILL 杀掉。这和任何一个合入者被 SIGKILL 杀掉一样（进程来不及做任何事），不是这个问题特有的。

## 教训

- 一件事由两个进程各自在某一时刻判断“该不该由我做”时，两次判断之间的状态没人管；要让其中一方等到另一方的结果，或者把判断放进同一个事务 → 只靠文字：哪两处判断互为补充要看语义，没有通用检查。
