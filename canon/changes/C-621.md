## 为什么

D-139 定下 canon 的检查只有四类可以拒绝：保证 main 正确和文档不说谎的完整性检查、防止丢数据和安全问题、保护机器容量、负责人明确要求拦的。其余给出标准，在和当前工作相关时提醒，由主 agent 判断。D-139 的后果说现有的拒绝不在当时逐个复查，下次改到哪条就按它重新判断。这次按它复查五处：它们挡的都只是防止忘事，和 main 对不对、文档说不说得通无关。

- BR-2463：分支上 `canon work test` 留下的失败会拦住合入，即使那是环境原因（#279：worker 会话里的 `as-hook.test.ts`）或已经修过但没重跑。D-141、BR-2542 之后合入自己会跑这次工作相关的、没有当前内容报告的测试，这条拒绝不再需要在合入里。
- `canon check` 的五种文档完整性发现：规则没指向业务（BR-2431）、决策的决定点名的规则没链回（BR-2469）、决策的方案没有真实取舍（BR-2109）、改决策没写 `revised_because`（BR-2492）、新领域没有决策点名（BR-2446）。它们说的都是“这件工作还没写完”，不是文档在说谎。
- 架构总览没写某个代码目录（BR-2352）、修订或取代总览引用过的决策后没改总览也没声明（BR-2354）。总览引用的决策已被取代（BR-2353）仍是错误，那是总览在说一件假事。
- 新决策一条来源都没有（BR-2111）。已有的来源仍要核对：摘录不在、打不开、来源行格式不对就拒绝，那才是文档在说谎。
- canon 自己的发布评审：skill 和工作说明里的重复文字会拦发布（BR-2411、D-107）。重复是文字质量的提示，不是文档说错；拦下时二进制和 skill 停在旧版本。

## 要改什么

五处拒绝改成提醒（`canon check` 的标准错误、合入的输出），退出码不变地放行；保证 main 正确和文档不说谎的部分原样保留。按 D-139 的分类，改动由 D-139 决定，不再为每一处各写一条决策；改到 D-107 的拦截那一段，按 amends 补了一条决策 D-147。

1. **BR-2463**：`canon work land` / `canon chore land` 照旧算出这个分支上 `canon work test` 留下的失败（测试文件以最后一次结果为准，类型检查以最后一次运行），有失败时只输出一行 `note: ` 提醒，写明失败的文件、类型检查的退出码和重跑命令，然后照常排队；列不出分支的提交时也输出一行提醒，照常排队。代码在 `src/work/land/land.ts`；BR-2463 改写。
2. **`canon check` 的五种发现改成提醒**：`check()` 不再返回它们，新增 `checkNotes()` 算出它们；`canon check` 把提醒写标准错误，`canon work test` 和合入用 `say` 输出。`checkNotes()` 由 `src/knowledge/check/commands.ts`、`src/work/verify/verify.ts`、`src/work/land/checks/steps.ts` 调用；`canon accept` 的条件只看发现，所以这些也不再挡验收。BR-2431、BR-2469、BR-2109、BR-2492、BR-2446 改写。
3. **架构总览的 A3、A5 改成提醒**：`architectureFindings()` 只保留 A4（`architecture-superseded`）；新增 `architectureNotes()` 返回 A3（`architecture-unlisted`）和 A5（`architecture-unreviewed`），由 `checkNotes()` 打印。BR-2352、BR-2354 改写；BR-2353 不动。
4. **合入的新决策没有来源改成提醒**：`checkSources()` 对本次新增、一条来源都没有的决策输出一行 `note: `，照常合入；有来源时照旧逐条核对，任何一条不成立（文件里没有摘录、网址打不开或页面里没有摘录、来源行格式不对）仍以原因 `source` 或 `check` 拒绝。BR-2111 改写。
5. **发布评审的重复改成提示**：`releaseParser()` 不再产生 `block`，每条 `duplication` 都成为打印的提示（早已发布的那条仍加 `(already released) `，读过旧记录时只读发现）；`scripts/release.ts` 不再有不发布的拦截和 GitHub issue，`--check` 退出码 0。评审跑不了（没有 `review`、`review: none`、命令失败、最大的 skill 放不进预算）仍退出码 4 且不发布。`reportBlock` 和它的 issue 标题删掉；BR-2411 改写，BR-2412 的第一句随之一改，D-107 由 D-147 修订。

文档：`canon/architecture.md` 的 GitHub 上下文和 `dist` 那段同步；`canon/config.yaml` 的 `after_green` 注释同步。变更文件补 `rules` 和 `advances: none`。

测试：每条规则的测试改成断言提醒和放行（第 2、3 项加真实入口的 `canon check` 断言）；`src/work/verify/verify.test.ts`、`src/work/land/land.test.ts`、`src/knowledge/domains/business.test.ts`、`src/knowledge/domains/decision.test.ts`、`src/knowledge/check/commitments.test.ts`、`src/knowledge/check/options.test.ts`、`src/knowledge/check/check.test.ts`、`src/knowledge/check/architecture.test.ts`、`src/knowledge/check/design-basis/design-basis.test.ts`、`src/knowledge/review/release-review.test.ts`。

## 陷阱和假设

- 任务说明把 `architecture-unlisted` 写成了 BR-2353、把 `architecture-superseded` 写成了 BR-2352，和仓库里的规则文件相反（BR-2352 是 unlisted，BR-2353 是 superseded）。这次按行为名处理：unlisted 和 unreviewed 改成提醒，superseded 保持错误。以后收到带编号的任务说明，先用 `canon show <编号>` 核对它说的是哪个行为。
- `check()` 不再返回这五种发现后，`canon work test` 的 `result.check` 计数、`canon accept` 的条件和 BR-2388 的重复拒绝都跟着放行。这是 D-139 要的；但它们会在 `canon check` 的标准错误里以 `note: ` 出现，合入时在合入输出里出现。
- 发布评审改写后，旧的 `release.review` 事件里记着 `verdict: "block"`。沿用这些记录时只读 `findings`、不读 `verdict`，否则旧的一次拦截会继续挡住发布。
- 合入自己跑相关测试（BR-2542）只跑没有当前内容报告的测试文件；一个在分支上失败并已有报告的测试文件不会在合入时重跑。这是去掉 BR-2463 拒绝后留下的口子，由后台 floor（`floor_timing: after`）兜底。
- 教训部分的检查（BR-2161、D-24）不在这次范围，另一个会话的变更 `C-617` 正在重做它；本变更按现有的教训要求写了这一节。
- 发布评审的提示只写到 `after_green` 的日志。若长期没人处理，可以把它们列进 `canon work due` 或 `canon brief`，这次不做（见 D-147 的后果）。
