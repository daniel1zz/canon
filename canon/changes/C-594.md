## 为什么

issue #254。按 D-128，worker 不能改设计文档（规则、决策），合入时改了就拒绝（BR-2501 第 1 项），规则文字要随实现改时，交回设计负责人（`canon work need-design`，BR-2499）。现在交回的方式是 worker 在变更文件里写散文，一句一行：`- BR-n：<旧句> → <新句>`，设计负责人再手工或用脚本贴进规则文件。这样很脆：

- 例子行本身就有 `→`，按第一个 ` → ` 切开的脚本会写出“条件 → 新结果 → 旧结果”；
- 规则文件会折长行、缩进续行，旧句对不上原文；
- 贴完以后没有任何检查确认旧文字没了、新文字到位了。

某个项目 2026-11-17/18 一晚碰到三次：13 条规则贴成了新旧结果连在一起，`canon check` 没报，靠另一个会话读规则才发现，恢复后重贴。worker 交回规则文字是派发流程里的正常操作。

## 要改什么

想要的行为（设计在动手时按 canon-design 定细节，下面是要满足的契约）：

- worker 提议规则文字用 canon 命令，写的是**完整的新文件**，不是句子对照：例如 `canon rule propose BR-n`，把这条规则当前的全文复制到变更自己的提议目录（例如 `canon/changes/C-n/proposed/BR-n.md`），worker 直接编辑这份副本。新规则同样可以提议（还没有编号的，按提议目录里的临时名）。提议目录不是设计文档，worker 改它不触发 BR-2501 第 1 项。
- 提议文件记下它基于的规则内容哈希（取副本时 main 上的版本）。
- `canon work need-design` 的请求列出这个变更所有的提议；设计负责人看请求、`canon work review`、`canon work take` 时能看到每份提议相对 main 上规则的 diff。
- 设计负责人用一条命令套用（例如 `canon rule apply C-n [BR-n ...]`）：把提议文件原样写进规则文件，删掉提议文件；提议基于的哈希和 main 上规则现在的哈希不同时拒绝（退出码 5），写明 main 在提议之后改过这条规则，要 worker 重新提议或设计负责人手工合并。
- 设计负责人以外的执行者（包括 worker）运行套用 → 拒绝。
- `canon check` 报：合入到 main 的变更还留着没套用的提议（套了一半也报，写明哪几条没套）。
- 套用后的规则改动照常走规则评审和证据门，不因来自提议而少任何检查。

要改的规则：`work/delegation` 领域新增提议和套用的规则；BR-2499（need-design 请求列出提议）、BR-2501（写明提议目录不算设计文档）；`canon check` 的新检查一条规则。动手前读 D-128、BR-2497 到 BR-2501。这里有真实的取舍（提议放哪、套用是否允许部分、和 need-design 是否合并成一个命令），写一份决策。

回归测试：worker 在派发的变更上 `canon rule propose BR-1`、改副本，`canon work land` 不因改设计被拒；设计负责人 `canon rule apply` 后 `BR-1` 的文件和副本一字不差、副本删掉；main 在提议后改过 `BR-1` → 套用退出码 5；变更合入后还留着提议 → `canon check` 报。例子里带 `→` 的规则提议后套用，文字原样。

不做：

- 不让 worker 直接改规则文件（D-128 不变）。
- 不做决策文件的提议（先只做规则；决策有需要再开）。
- 不做三方自动合并。
