## 为什么

负责人 2026-11-03：“我觉得固化到机制本身就应该是一个最底层的认知机制，你应该要提醒我是不是要固化成机制”，“需要固化的需要我确认啊，不允许直接固化”。现在做完一件事发现的教训没有固定的去处：要么只留在会话里丢掉，要么 agent 自己顺手加一条规则或检查，负责人不知道。需要让每个变更写下教训和它的去向，并在把教训变成机制之前问负责人。

## 要改什么

子领域：knowledge/documents（变更模板）、work/land（`--finish` 要求填好教训）、knowledge/review（规则评审读教训）、work/session（`stop` 和 `land --finish` 收尾提醒）。

- 变更模板在“陷阱和假设”和“任务”之间加 `## 教训`：每条教训写它现在由哪个机制保证（编号），或“只靠文字：原因”，或“待负责人确认是否固化”；没有写“无”。BR-2037 跟着改。
- `## 教训` 不加进变更类型的必需段落（那样 117 个旧变更全部报 `doc-missing-section`）；改为 `canon work land --finish` 关闭变更前要求这一节存在且有内容，否则拒绝。已经关闭的旧变更不受影响。新规则在 work/land，选择理由写进决策。
- 规则评审的提示带上这次合入所属变更的 `## 教训`，两种情况给不拦截的建议：可以做成机制的教训标了“只靠文字”却没写原因；这次合入为某条教训新加了机制，却没写负责人确认过。新规则在 knowledge/review。
- `canon work stop` 和 `canon work land --finish` 成功后最后一行提醒：发现了能变成机制的教训，写进 `## 教训`，固化前先问负责人。新规则在 work/session。

## 陷阱和假设

- 评审建议按 BR-2145 挂到它点名的被评审文档上；变更本身不是被评审的文档，只点名变更编号的建议会挂到这次评审的每份文档上。
- 规则评审只在合入改了规则或决策时才跑；只改代码的合入没有评审，也就没有教训建议。加机制的合入一般都会加规则，所以够用。
- 项目自己的 `canon/templates/change.md` 没有 `## 教训` 时，新变更也没有这一段，`--finish` 会拒绝，按提示补上即可。
- `canon update` 自己建变更并 `--finish`，它写的变更正文也要带 `## 教训`（`src/cli/install/update.ts`）。
- 正在进行中的其他变更（用旧代码合入）不受新要求影响，直到它们用新代码 `--finish`。

## 教训

- 模板占位行里不能再嵌套尖括号，否则整行不算占位行，`template-unfilled` 抓不到 → 只靠文字：这是写模板的人一次性的注意事项，BR-2035 的现有例子已经写明反引号和其他文字的情况，再加检查得不偿失。
- 给 `--finish` 加要求时，canon 自己生成并关闭变更的地方（`canon update`）也会被拦 → 已由 `src/cli/install/update.test.ts` 的合入测试保证（不改 update.ts 时它失败 2 个）。
- 新的拒绝不能借用已有的原因（第一次合入用了 `check`，会让 `canon stats` 失真）→ 已由 BR-2026（每种拒绝原因各不相同）和规则评审保证；这次改成单独的 `lessons`，BR-2067 和 `check_reviews` 跟着加上。
