## 为什么

独立评审（D-31 一节）用 2026-11-04 的真实数据指出 D-31 的缺口：main 在 733 分钟里红了 258 分钟（35%），最长一段 103 分钟，期间 16 次合入落在红的 main 上，修复变更在第一次失败 57 分钟后才开出，因为“main 没通过”只在 `canon brief` 里显示，已经在干活的会话不会再运行它。另外评审按代码推断：修复变更合入后 main 仍红时，记录上的修复变更编号不会清，`canon work start --fix-main` 一直退出码 5。BR-2250（`floor.stale`）一次都没触发过。

## 要改什么

- `canon work land` 成功和被拒时都在输出末尾写 brief 里“main 没通过”那段的第一行和修复者行（新规则 BR-2306）。
- 复现第二条：正常流程下（修复变更合入，下一次后台测试仍失败）记录确实还写着已合入的修复变更，`--fix-main` 被拒（测试在补丁之前失败，输出 `Received: "C-1"`）。修法：后台测试在包含该变更合入提交的提交上失败时，记录上的修复变更编号清掉；失败的提交不含它（测试中途 main 前移）时不清（BR-2221）。
- D-31 的“后果”换成当天实测的数字，写明后台 floor 和会话抢 CPU（C-301 限 4 个 worker）、D-38 下远端也收到没测过的 main、负载超时的处理；P4 里的“短时”同步改掉。
- 退役 BR-2250，删 `floor.stale`、`CANON_WATCH_HANDOFF`、`newerCanon` 的代码和测试：BR-2224 在合入时挡住 PATH 上的 canon 读不了的配置，BR-2251 在每次重新构建后交接，正常操作不会再碰到 BR-2250 兜的情况；只有手工重新构建 PATH 上的 canon 才会，记成 D-31 的已知限制（D-54）。

## 陷阱和假设

- 判断“失败的提交包含修复”用合入事件里的提交和 `git merge-base --is-ancestor`；合入事件记的是合入时的提交，main 是快进的，所以它就是 main 上的那个提交。
- 合入输出只写两行，不写日志和输出尾部，避免合入的输出变长；细节仍看 `canon brief`。
