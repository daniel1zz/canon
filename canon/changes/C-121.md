## 为什么

工作说明只说“在 worktree 里只跑和改动相关的测试”，哪些相关由 agent 自己猜。本会话一次改认领的变更弄坏了 `src/config` 和 `src/cli` 下的测试，agent 没跑到，只有 floor 发现：一次被拒的合入，加上约 2.5 分钟重新排队。把多个测试文件放进一次 `bun test` 还卡住过一次（Bun 1.3.x 的缺陷，#35，已升级到 1.4.4）。负责人 2026-11-03 同意做这个命令。

## 要改什么

子领域：work/verify（新建，代码在 `src/work/verify/`）；配置项在 config 领域（`src/config/config.ts`）。

- `canon work test [--all]`：和 main 的合并基点比较，选出改过的测试文件、通过相对导入（传递，复用 `canon context` 的导入读法）用到改过文件的测试文件、测试名写了碰过的规则的测试文件；列出每个文件和理由，一个文件一次地运行 `test_command`，打印每个文件的结果和汇总，有失败时退出码 1。`--all` 运行全部测试文件。新规则 BR-2157、BR-2158、BR-2159。
- 新配置项 `test_command`，必须含 `{file}`（BR-2160）；canon 自己的配置写 `bun test {file}`。没写时 `canon work test` 以退出码 2 失败并给出例子。
- 决策 D-23：挑选和运行的方式，以及否决的方案。
- 工作说明（`src/cli/guide.ts`）改成合入前运行 `canon work test`。

## 陷阱和假设

- 只在运行时读文件（不导入）的测试不会被选出，例如读 skill 文件的安装测试、通过子进程运行 CLI 的测试只在它们导入了改过的文件时才会被选出；输出写明这点，floor 仍跑全量。
- 改了 `src/config/config.ts` 这种被大量导入的文件，几乎所有测试都会被选出，这是对的。
- 导入只认 JS/TS 的相对路径；别的语言的项目只靠“改过的测试文件”和“测试名写了规则”两条挑选。
