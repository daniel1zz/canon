## 为什么

死掉的会话仍然占着认领 12 小时；被杀掉的合入者让后面的合入者空等 `lander_stale_minutes`（10 分钟）。Claude Code 的 Bash 工具默认 2 分钟就杀掉命令，排队的合入者经常在中途被杀，被杀在 rebase 中途时 worktree 还停在 rebase 状态。见 D-11。

## 要改什么

- 排队条目记下合入者进程的 pid 和启动时间；等待者发现前面条目的进程不在了就立刻作废（BR-2098）。
- 合入者收到 SIGTERM/SIGINT：停 floor、撤销做到一半的 rebase、条目标成失败 `killed`、记事件，退出 143/130（BR-2099）。rebase 被信号打断时先让信号处理跑完，不把它报成 `conflict`。
- 认领记下会话进程（`CLAUDE_PID`，核实是祖先），持有者之后的工作命令更新它；进程不在时另一个执行者可以立刻接手（BR-2100），BR-2011 指向它。
- 协调数据库的 claims、queue 表各加 `pid`、`pid_start` 两列（沿用 BR-2078 的补列）。
- 工作说明加一行：合入可能要等几分钟，给足超时或放后台，直接读退出码，不要经过管道（BR-2090 随之更新）。
- 决策 D-11 记下方案对比。

## 陷阱和假设

- 同一个 Claude Code 会话的子 agent 共用一个进程，探测只能分辨会话，分不开子 agent。
- 信号处理在同步的 git 调用返回之后才运行，所以 rebase 失败时要先 `await` 一次，让待处理的信号先跑。
- 读不到进程表（`ps` 不可用）时一律当作还活着，退回时间判断，不会误释放。
