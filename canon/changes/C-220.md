## 为什么

`floor_timing: after`（D-31）下，`canon floor watch` 是一个长时间运行的后台进程：它测 main 的最新提交，通过后 `after_green` 从这个提交重新构建 PATH 上的 canon，然后它接着测下一个提交。可它自己一直跑着启动时的旧代码，所以会比它测的代码旧（issue #90）。C-217（BR-2250）只修了最窄的一处：自己读不了 main 的配置、PATH 上的 canon 读得了时，才把这个提交交给 PATH 上的 canon；旧代码在别的地方的不同行为（比如 floor 的跑法、结果怎么记）都没管。

负责人 2026-11-04 选了“每次重新构建后就交接 (推荐)”：每次 `after_green` 跑完，后台测试进程就把下一次测试交给新构建的 PATH 上的 canon（在后台启动 PATH 上的 `canon floor watch`，和 BR-2250 里 `spawnWatcher` 的做法一样），自己结束，旧代码不再接着测。

## 要改什么

- 新规则 BR-2251：后台测试通过、`after_green` 的每条命令都以 0 结束后，进程交出后台测试的位置，记一条 `floor.handoff` 事件（带刚通过的提交和 PATH 上 canon 的路径），在主 checkout 里后台启动 PATH 上的 `canon floor watch`，自己以 0 结束，不再测别的提交。定下这几处边界：
  - 没配 `after_green`，或者其中一条以非 0 结束（没有重新构建成功）→ 不交接，同一个进程照 BR-2219 接着测。
  - PATH 上没有 canon，或者启动它失败 → 不交接，同一个进程接着测，不让最新提交没人测。
  - 不来回交接：新启动的进程先看 main 的最新提交，已经测过就什么都不做、以 0 结束；只有它自己又通过了一次、又跑完 `after_green`，才会再交接。
  - 同一时间仍只有一个：先交出位置再启动新的，新的照 BR-2219 用协调数据库里的同一个占位，和合入、`canon brief` 同时启动的谁先拿到谁测，另一个以 0 结束。
  - 不漏测最新提交：交出位置前 main 又前移了，新进程启动后测最新的；新进程没起来时，下一次合入或 `canon brief` 按 BR-2219 启动后台测试。
- BR-2219：“测完 main 又前移了就接着测”改为除了 BR-2251 交接的情况；顺带补上评审建议里没写的边界：`setup` 失败记 `floor.fail`、main 记为没通过、不跑 floor。
- BR-2250：写明它是 BR-2251 之外的兜底（进程不是交接来的，比如由别的 canon 启动），处理它上面的评审建议：规则里写明在主 checkout 里启动；补“PATH 上没有 canon”的例子；写明它是 BR-2220 的例外；写明 `floor.stale` 和 `floor.handoff` 不算 floor 的运行，不进 `canon stats`。
- 代码只改 `src/work/watch/watch.ts`，测试加在 `src/work/watch/watch.test.ts`。

## 陷阱和假设

- 假设：`after_green` 的命令全以 0 结束就当作 PATH 上的 canon 已从这个提交重新构建。canon 不知道 `after_green` 构建的是什么；项目若 `after_green` 里不构建 canon，交接也只是多启动一次同样的 canon，结果不变。
- 新进程不带 `CANON_WATCH_HANDOFF`：那个环境变量只表示 BR-2250 的“为这个提交交接来的”，从旧进程继承来的值要去掉，否则会错误地阻止新进程按 BR-2250 交接。
- 交出位置和启动新进程之间，合入或 `canon brief` 可能也启动一个；两个都去抢 BR-2219 的占位，只有一个测，这是 BR-2219 已有的保证，不另加锁。
- 本仓库主 checkout 的 `dist/canon` 就是 PATH 上的 canon；交接后看事件表里的 `floor.handoff` 和下一条 `floor.pass` 的 `actor` 和日志确认新进程接手了。

## 教训

- 长时间运行的后台进程会比它所测的代码旧 → 由 BR-2251 保证（负责人 2026-11-04 确认）：每次重新构建后就交给新构建的 canon，旧代码不再接着测；BR-2250 只剩兜底
- 不是 PATH 上的 canon 启动的后台测试（比如从源码 `bun src/cli/main.ts` 启动的）在它第一次重新构建前仍可能比 main 旧 → 只靠文字：canon 判断不了任意启动方式的代码新旧，BR-2250 兜住读配置这一处，第一次 `after_green` 后由 BR-2251 换成新的
