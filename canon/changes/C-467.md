## 为什么

负责人在本次对话选择「全部由主 agent 亲自写规则」。现有 canon-rules 要求写前检索和优先复用，但没有区分主会话和子 agent；canon-parallel 把规则编写也放进子 agent 的实施范围。需要把 baseline 的需求解释与实际写入统一交给负责该任务的主会话，避免实现者自行修改验收依据。

## 要改什么

范围：canon 自带 skill 的工作引导，不增加 CLI 权限检查或 hook。

- 记录负责人的分工选择和被否决方案。
- canon-rules：只有主会话能新增、修改、作废或移动 baseline 规则，包括正文、例子与元信息；子 agent 只读规则，提供差异和建议。
- canon-parallel：主会话先确定规则及引用，再派实现与测试；发现需求缺口或矛盾交回主会话，不授权子 agent 代写已定文字。
- 核对其他 skill 是否与新分工直接冲突，只修改必要的引导。
- 根据负责人追加要求和问题 #24 的选择，在 canon-rules 统一说明真实冲突按最后生效的需求修改处理；设计和测试入口引用它，主会话修正旧说法，不用文件时间或编号猜先后。
- 按既有流程运行 canon work test、规则预审和合入。

## 陷阱和假设

- 主会话指负责这项任务的顶层会话，不是唯一的全项目会话；多个主会话仍在各自 worktree 内按任务范围协作。
- 主会话不进入子 agent 持有的 worktree 改规则；需要调整时先停下并交接，主会话按既有接管流程处理。
- 规则与代码仍按项目既有流程同次合入，不为本变更新增主会话直接编辑共享 checkout 的例外。
- 这次只固化已经由负责人选定的分工，不宣称更强模型必然降低错误率，也不更新其他项目的安装副本。
