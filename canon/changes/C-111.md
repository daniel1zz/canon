## 为什么

N-3 记下：负载 8 到 12 时测试不稳，一个测试超时，一次把 5 个测试文件放进一个 `bun test` 卡了 10 分钟以上。floor 在别的 agent 工作时跑全量测试，测试不稳就会变成误拒。

## 要改什么

只改测试，不改产品行为，不改规则。涉及的子领域：`work/land`、`config`、`cli`、`cli/install`、`knowledge/documents`。

- 量了每个测试文件的耗时和启动的子进程数（用 preload 包住 `Bun.spawn` / `Bun.spawnSync` 计数），分别在只有别的 agent 的负载下、和另外并行 3 份、5 份全量测试时。
- `work/land`：BR-2111 的测试在一个测试里连做 8 次完整合入，负载 15 到 25 时 5 份并行全量测试里 5 份都因它超时。拆成 8 个测试，每次合入一个。
- `work/land`：故意等真实时间（sleep、租约、过期时间）或者启动 `canon work land` 子进程的 6 个测试，超时改为 30 秒，并写明 `reason`。
- `cli`、`cli/install`、`knowledge/documents`：`main.test.ts`、`update.test.ts`、`githook.test.ts`、`types.test.ts` 测的就是 CLI 本身（退出码、输出），启动子进程是测试的目的，文件级 `setDefaultTimeout(30_000)`，写明 `reason`。没有改成在进程内调用：每次启动 bun 只占约 50 毫秒（实测 `bun src/cli/main.ts --version` 49 毫秒，打包后 36 毫秒），时间主要花在命令自己的 git 调用上，改成进程内省不了多少，反而丢掉对 CLI 外表的覆盖。
- `config`：`hooks.test.ts` 等后台 hook 结束的 `finished()` 最多等 5 秒，正好等于默认测试超时；改为最多 25 秒，文件级超时 30 秒。

## 测量

每个文件单独 `bun test`，秒数 / 启动 CLI 次数 / 子进程总数（改动前，只有别的 agent 的负载约 11）：

| 文件 | 秒 | CLI | 子进程 |
|---|---|---|---|
| work/land/land.test.ts | 50.2 | 4 | 2272 |
| cli/main.test.ts | 26.5 | 147 | 257 |
| work/session/session.test.ts | 18.4 | 18 | 1184 |
| cli/install/update.test.ts | 11.8 | 40 | 102 |
| work/drop/drop.test.ts | 11.1 | 0 | 788 |
| config/hooks.test.ts | 9.1 | 7 | 640 |
| cli/install/githook.test.ts | 5.6 | 17 | 85 |
| knowledge/documents/types.test.ts | 5.0 | 35 | 55 |
| work/stats/stats.test.ts | 4.6 | 0 | 362 |
| 其余 10 个文件 | 各 < 3 | | |

另外并行 3 份全量测试时（负载约 7 到 10），文件耗时增加 5% 到 50%（main.test.ts 35.7 秒，land.test.ts 52.3 秒），全部通过。

单个测试耗时（junit，另外并行 5 份全量测试）：

- 改动前（负载 11 到 26）：BR-2111 4.99 秒、BR-2108 4.64 秒、main.test.ts 的 BR-2024 4.20 秒、BR-2049 3.84 秒，另有 20 多个在 2.5 到 3.4 秒。5 份并行的全量测试全部失败，都是 BR-2111 超时（5001 毫秒）。
- 改动后（负载 10 到 18）：最慢的是 BR-2108 4.56 秒（超时现在 30 秒），BR-2111 拆开后每个 0.5 到 0.8 秒。6 份全量测试（5 份并行加 1 份 junit）全部通过，265 个测试。

## 卡住 10 分钟

没有复现。试过：6 份并行、各把 `land`、`session`、`drop`、`hooks`、`main` 5 个文件放进一个 `bun test`，跑两轮共 12 次，负载 20 到 30，每次约 3 分钟全部通过；加上 8 次全量测试，也没有卡住。

查到的相关机制：

- 子进程继承了 `bun test` 的 stdout 时，`bun test ... | tail` 要等这个子进程退出才结束。测试里有好几个 `Bun.spawn(["sleep", "30"])` 用的是默认的继承 stdout，所以管道最多会多挂 30 秒左右，不到 10 分钟。
- 同步测试（`Bun.spawnSync`）里子进程不结束时，bun 的测试超时打断不了它。
- 测量中发现并发 `git worktree add` 的竞争，偶尔让 BR-2132 的 8 个并发 start 有一个以退出码 4 失败，已提 issue #32（附只用 git 的复现）。

## 陷阱和假设

- `setDefaultTimeout` 只作用于调用它的文件（实测：两个文件放进一个 `bun test`，另一个文件仍是 5 秒）。
- 负载更高时（40 以上），进程内但 git 调用多的测试（drop、session、stats，负载 20 时最慢约 2.1 秒）也可能接近 5 秒，这次没动。
