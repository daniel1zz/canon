## 为什么

两个变更各自在自己的树上测试通过，合在一起才坏：合入时只跑这个分支自己挑出的测试，main 分叉以来新进的改动会影响哪些测试没人看，要等后台测试把 main 测红才发现，然后撤回、修复，其余合入都被 BR-2644 暂停。负责人经对面会话转述选了「canon 挑测试更全」。

但每次合入都把 main 那边的测试也跑一遍会让所有合入变慢（本仓库选测一次常挑出约 195 个文件）。负责人问「普通情况普通处理？」：D-137 定的就是关键的多查、普通的抽查。所以只在两边真的有重叠时才加跑。

## 要改什么

- 新规则 BR-2645：合入在 rebase 之后、`canon check` 之前，算出分叉点，两边各自改了哪些路径；同一路径两边都改了，或 `test_select_command` 给两边挑出同一个测试文件，就在要合入的树上跑它给 main 那边挑的测试，失败就拒绝；没有重叠什么都不跑。
- `src/work/land/checks/cross-tests.ts`：`crossTests()` 算重叠和要跑的文件；`steps.ts` 接上它，先等负载，再一个文件一次地跑。
- `policies.landing.cross_tests`（默认 `true`，D-164）：读 main 上已合入的配置，变更不能给自己关掉。
- 等 BR-2543（关键程度）做出来后，critical 可以作为第二个触发条件，这次不做：它还是 planned，而交叉测试防的是两边重叠，不是改动本身的分量。

## 陷阱和假设

- 依赖项目的 `test_select_command` 挑得准：它漏挑，交叉测试也漏；没有它就不跑（D-64）。
- 给 main 那边挑的是分叉以来 main 改过的全部路径，main 走得远时文件会多；只有出现重叠才跑，所以普通合入不受影响。

## 教训

- 用 grep 过滤测试输出时，`bun test` 被 `scripts/test.sh` 的要求拒绝，输出里没有 `(fail)`，被当成通过；过滤输出时必须同时看退出码 → 待负责人确认是否固化
