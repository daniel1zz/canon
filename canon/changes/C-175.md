## 为什么

baseline 核对（N-4）在 `work/stats`、`work/issues` 和 `work` 顶层找到用户看得见、却没有规则写的行为，以及没有测试验证的规则例子。补规则时又发现一个真问题：`code_root` 下跟踪了一个指向目录的符号链接（或子模块）时，`canon stats` 读它报 `EISDIR`，以 canon 的 bug 退出。

## 要改什么

新规则，每条一个测试点名：

- BR-2202：`canon stats --json` 的字段。
- BR-2203：认领和 setup 的拒绝不分去向（表格是 `-`，JSON 是 null）。
- BR-2204：并发摘要里没有原因的拒绝记为 `unrecorded`，次数相同按原因名排。
- BR-2205：共享代码只数工作区里的普通文件；同时改代码，符号链接和子模块不再让 `canon stats` 崩溃。
- BR-2206：`canon issues` 每个修复提交一行、新的在前，`--json` 的字段。
- BR-2207：`gh issue list` 输出读不懂时退出码 4。
- BR-2208：协调数据库在 git 公共目录下，所有 worktree 共用。
- BR-2209：协调数据库打不开时退出码 4 并写明路径。

已有规则补测试或例子：

- BR-2023：Claude Code 里 `CANON_ACTOR=human:alice` 经命令行退出码 2、不写事件；`CANON_ACTOR` 只有空白时当作没设（加例子）。
- BR-2067：`dirty`、`on-main` 例子按原数字测。
- BR-2131：主 checkout 里 `canon work start` 的 `start.ok` 记主 checkout。
- BR-2154：`canon stats --since x` 的错误信息和“不输出统计”；去向只看这段事件里的。
- BR-2156：没有 worktree 或对象的事件在文字输出里写 `-`（加例子）。
- BR-2170：gh 别的失败时 stdout 没有汇总行。
- `canon stats` 表格的检查名列按最长的名字对齐（`moved-during-land` 原来把那一行挤歪），没有规则写表格排版，只改代码。

测试放在 `src/work/stats/output.test.ts`、`src/work/stats/rules.test.ts`、`src/work/issues/issues.test.ts`、`src/work/workspace.test.ts`、`src/work/db.test.ts`，不碰 `src/cli/main.test.ts`，也不碰那个变更改的 `stats.test.ts`。

## 陷阱和假设

- 修 #68 #69 #70 的另一个变更同时在合入，也改 `stats.ts`、`commands.ts`；这里只改 `sharedShare` 和表格的列宽，和它改的地方不重叠。
- BR-2205 按现在的做法写成“按工作区里的内容数”；改成按提交的内容数是另一种合理的产品，留给负责人（报告里写明）。
- `canon issues` 最多读 1000 个开着的 issue（`gh issue list --limit 1000`），多出的不说就丢掉；怎么处理留给负责人，这里不写规则也不改。
