## 为什么

负责人 2026-11-23（本会话）：「我觉得我们很多策略应该是有一套配置的，可以通过配置来支持」，范围是「canon整个」，每个项目一份；结构选了「全部放进分组的 policies 段」，顺序选了「检查、议程、容量先做」。盘点（只读子 agent）找到约 25 个写死的策略，分 6 组。理由、否决的方案和来源见 D-164。

## 要改什么

- 决策 D-164（修订 D-157 的「门槛是常量」）。
- 配置框架（BR-2638）：配置项名字可以写成 `policies.<组>`，从 `policies:` 下的同名组读；未知的组或项是配置错误；组里没写的项用默认值；`canon config` 和编辑器 schema 认得这个结构。代码：`src/invocation/key.ts`（`rawAt`、`readGroup` 和几种项的校验）、`config.ts`、`reference/reference.ts`。
- `policies.agenda`（BR-2639）：`slow_hours`、`slow_test_failures`、`interrupt_tiers`、`flaky_days`。代码：新 `src/work/reminders/config-keys.ts`，`slow.ts`、`interrupt.ts`、`due.ts`、`src/work/watch/revert.ts`。
- `policies.capacity`（BR-2640）：`memory_tight_level`、`memory_psi_percent`、`memory_available_percent`、`full_run_load_share`。代码：`src/kernel/machine.ts`、`src/work/delegation/capacity.ts`、`config-keys.ts`、`src/work/reminders/room.ts`、`agenda.ts`。
- `policies.checks`（BR-2641）：九种说文档不完整的检查，加上合入时的 `lessons`（`## 教训` 没填，BR-2161），可设 `refuse`、`remind`、`off`；合入按 main 上的设置。代码：新 `src/knowledge/check/policy.ts`，`check.ts`、`config-keys.ts`，调用 `canon check` 的五处传入策略（合入的两处读 main 的配置）。
- 原来写死这些数字的规则（BR-2612、BR-2606、BR-2534、BR-2526、BR-2581）注明对应的配置项。

没做（D-164 决定之后再做）：子 agent 卡住几次、评审标准、保留期限和统计门槛三组。

## 方案依据

- 复用：D-2 第 1 条（写死的策略参数进配置、都有默认值）和 C-135 的「配置项由用它的领域声明」，只复用了「进配置、有默认值、由领域声明」这一部分。
- 新选择：一是 `policies` 下按组放（负责人在本会话里从三种结构里选的）；二是「拒绝还是提醒」能配置的范围只限说文档不完整的检查，说文档是错的不能配（依据 D-139 的四类拒绝和 P5）；三是合入时检查策略读 main 上的配置（照 BR-2074 对评审设置的做法）。
- 最坏的失败：项目把门槛调得太松，例如 `policies.capacity.memory_psi_percent: 100`，机器内存已经很紧还继续派 worker，测试大面积超时；或者把 `checks` 里的几项都设成 `off`，文档慢慢缺章节、缺例子没人提醒。两种都要改配置、走合入才会发生，负责人看得到；默认值和以前一样。
- 什么结果说明选错了：配置之后，同一类问题反复出现，比如设了 `remind` 的检查对应的缺项在 `canon stats` 里持续增长，或者调松容量后 `canon work test` 超时的次数明显上升；那时应该给这些项加上下限，或者把某项移出可配置表。
- 外部做法：ESLint 的规则级别（off、warn、error）就是「同一个检查由项目决定是报错、警告还是关闭」，警告不影响退出码；本变更的 `refuse`、`remind`、`off` 对应这三级。它说明这种按检查设级别的做法成熟可用，但不回答「哪些检查不该让项目关」，这一点由 D-139 决定。

## 陷阱和假设

- `policies.checks` 的默认表放在 `src/knowledge/check/policy.ts`，不能挪回 `check.ts`：`config-keys.ts` 在配置加载时就要用它，放回去会形成循环引用，从 `check.ts` 先加载时报「初始化前访问」。

## 教训

- 合入时用哪份配置要逐项想：会放宽检查的配置必须读 main 上的，否则变更能放宽对自己的检查 → BR-2641（测试：分支放宽、合入仍被拒）
