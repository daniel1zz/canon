来自 C-626 的 D 步（D-148 迁移，计划表不再列这一步）。

## 为什么

执行只有变更（原计划 C-626，D-148）的一步：会话新建变更时不知道已经有人在做同一件事，合入时也不知道自己改的正是另一个未结束变更打算改的。D-148 要求在这两个时刻提醒，只提醒、不拦截（D-139），并按 P6 量出提醒准不准。

## 要改什么

怎样算相关、阈值、比哪些内容、回应怎样写，记在 D-171。

- 新建变更（`canon change new --title`、`canon work start --title`）时按标题提醒至多 3 个可能重复的未结束变更（BR-2656）。
- 合入时按改到的规则和路径提醒和它重合的未结束变更（BR-2657），和同文件重叠提示在同一时刻、同样不拦截。
- 新命令 `canon change duplicate <C-n> <C-m> --same | --not "<理由>"` 记下回应（BR-2658）；没回应的提醒让两边的 `overlap` 标记成立（BR-2571 的 `overlap` 从总是 false 改成按事件算）。
- `canon stats` 加 `Duplicate reminders` 一节，按阶段算准确率（BR-2659）。
- 两个领域的 README 各加一项业务：`knowledge/changes` 的「重复提醒」，`work/stats` 的「重复提醒的准确率」。

总览不受影响：没有新的部件和数据位置，事件仍在协调数据库的事件表里；新建、合入和统计的流程只多一行提示。

## 方案依据

- 复用：D-90 的分词（汉字二元组、拉丁词）和 BM25 式 idf；同文件重叠提示（BR-2062）在合入中的时刻和写法；变更状态（BR-2571）判断哪些变更未结束；事件表记提醒和回应（P6）。
- 新选择：标题用按稀有度加权的共有词比例、去掉单个汉字、阈值 0.40；合入只比规则和反引号里的路径；回应按变更对记，见 D-171。
- 证据：对 canon 仓库 715 个变更标题两两比较（255255 对），加权并去掉单字后不低于 0.4 的 124 对，0.40 到 0.50 的样本都是真相关的一对（D-171 背景）。
- 最坏的失败：误报多到会话一律答「不是它」，提醒成了噪声；对策是阈值按测量定、同一阶段同一对只提醒一次、已回应的不再提醒，`canon stats` 把自报的准确率和事后被放弃的对数放在一起看。
- 什么结果说明选错了：两周内有回应的提醒里「是它」不到一成，或事后放弃了一方的那一对多数从没被提醒过（D-171 后果）。
- 数据的演进和恢复：只新增两种事件（`duplicate.remind`、`duplicate.answer`），不改已有表；去掉这个功能时事件留着无害。
