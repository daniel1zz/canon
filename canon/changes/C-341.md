## 为什么

独立审查 D-61 的版本功能（C-336、C-338、C-339）发现：

1. 负责人确认可以绕过：`canon human answer N yes --relayed "no"` 记下的回答是 yes，提问工具记录里的原话是 no，witness 是 match，`canon release ship` 放行。ship 只用 YES 判断 agent 自己填的回答，不看原话；`canon human answer` 也不比较两者。
2. ship 的状态检查和确认只在开始时查一次，而且先查状态、后取 sha；排队期间规则变了或负责人回了 no，合入照样放行。
3. 别的项目已声明前缀 `R` 或目录 `releases` 的类型时，只报通用的 “already the prefix of another type”。
4. BR-2332 只有进程内 `land()` 的测试，没有从命令行入口走的；ship.test.ts 里有几处断言偏松。
5. `changed_in` 可以指向规则自己的 `release`，或比它更早的版本。
6. D-61 没写：`release.ship` 事件是本地库里的一行、状态 planned→active 靠手改、拆分已发布规则时新规则不能标已发布版本。

## 要改什么

- BR-2021：问题带 `--option` 时，转述的回答必须就是原话对应的那个选项，否则退出码 1、不写入（两侧例子）。BR-2276、BR-2289 的例子注明那几个问题没有选项。
- BR-2331：确认词表收窄为 `yes`、`是`；回答和转述的原话都要是确认词。
- BR-2332（或新规则）：合入时再查一次版本内规则全部已通过、负责人确认仍有效，不满足以原因 `release` 拒绝；ship 先取 main 的 sha，用这个 sha 下的规则状态检查。
- BR-2322：`changed_in` 的编号要大于 `release`，不能等于它。
- BR-2045：别的类型占用 `R` 或 `releases` 时的专门报错。
- ship.ts 的确认和阻塞检查拆到 gate.ts，合入检查（landing.ts）和 ship 共用，避免互相引用。
- D-61 原地补写（仍是 proposed）。
