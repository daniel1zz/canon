## 为什么

#134（两个切片中的第二个；第一个是 C-389，`canon work review`）：`floor_timing: before` 下单独合入（不一起测）时，floor 在规则评审之前运行。评审拒绝的合入先白跑一次 floor：Godot 项目里 floor 要 3 到 4 分钟，评审只是一次模型调用。那个项目 6 小时里有 12 次评审拒绝，等于白跑 12 次 floor，排队的其他会话也跟着等。

一起测时已经是反过来的：每个成员自己的步骤（`canon check`、规则评审等）在整批的 floor 之前跑（BR-2248 写明“在整批的 floor 之前”，D-26、D-42）。单独合入和一起测的顺序不一致，没有记录说这是有意的。

本变更不依赖 C-389，可以先做。

## 要改什么

设计（2026-11-07 分析）：`floor_timing: before` 下单独合入改成和一起测完全相同的顺序：先跑每个变更自己的全部步骤（配置键核对、`canon check`、执行记录、来源核对、规则评审、常驻说明的重复评审、`before_land`），全部通过才跑 floor。任何一步拒绝时不跑 floor，拒绝原因照旧，`canon stats` 不算一次 floor 运行。floor 通过后，“合入过程中 worktree 变了”的核对和比较并交换照旧在最后。

依据：一起测时每个成员自己的步骤本来就在整批 floor 之前（BR-2248 写明“在整批的 floor 之前跑”，D-26、D-42）；`canon check` 读的测试报告记账由 `canon work test` 写入（D-64），不依赖这次 floor。单独合入是唯一先跑 floor 的路径，没有记录说这是有意的。

否决：只把两个评审挪到 floor 之前、`canon check` 留在之后。这样会留下两种顺序，而一起测已经证明全部步骤放在 floor 之前可行。

代价（写进规则的例子）：以前靠这次 floor 当场写出测试报告、`canon check` 才通过的单独合入，现在会以 `test-report-missing` 被拒，提示先运行 `canon work test`。这和一起测时的现状相同。

规则：改 BR-2014（floor 在每个变更自己的步骤之后运行），`work/land/checks` README 里的步骤顺序跟着改；核对 BR-2248 里“`floor_timing` 为 `before` 时在 floor 之后”这句，改成和一起测相同。例子：评审 `block` → 不跑 floor，拒绝原因 `review`，日志里没有 floor 的输出；评审通过、floor 失败 → 拒绝原因 `floor`；评审命令失败 → 不跑 floor；测试文件改了但没跑过 `canon work test` → `test-report-missing`，不跑 floor。

`floor_timing: after` 不跑 floor，不受影响（本仓库就是这种配置）。

不在范围内：新增 `canon work review`（C-389）；评审提示过大（C-388）。
