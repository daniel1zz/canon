## 为什么

issue #90：`floor_timing: after` 下，后台的 `canon floor watch` 进程测完 191f9c6（通过，`after_green` 重新构建了 PATH 上的 canon），接着测 979c475。979c475 的配置用了 C-194 新增的 `typecheck_command`，而这个进程还在跑 C-194 之前的代码，自己的配置读取不认识这个键，于是记了 `floor.fail`（exit 2，原因 `its canon/config.yaml cannot be read`）。main 的测试其实没问题，但每个会话的 `canon brief` 都显示 main 没通过，直到下一次后台测试通过。

根因：后台测试用进程自己的（可能更旧的）代码读被测提交的配置，并把读取失败当成 main 的 floor 失败。

## 要改什么

- 新规则 BR-2250：后台测试自己读不了被测提交的配置时，问 PATH 上的 canon（`canon config --schema`，同 BR-2224）；它读得了就记 `floor.stale`（不算测过），交出位置，在后台启动 PATH 上的 `canon floor watch` 接着测，不记 `floor.fail`；它也读不了才照旧记 `floor.fail`。用环境变量 `CANON_WATCH_HANDOFF` 防止来回交接。
- 代码只改 `src/work/watch/watch.ts`，测试加在 `src/work/watch/watch.test.ts`。

## 陷阱和假设

- 假设：`after` 模式下 PATH 上的 canon 至少和被合入的配置一样新（BR-2224 在合入时保证），所以 PATH 上的 canon 读得了而自己读不了，就是自己旧了。
- 交接出去的进程就是 PATH 上的 canon；它若还读不了，是 PATH 变了之类的少见情况，按真失败记，不再交接，避免无限启动。
- 只处理“读不了配置”这一种过时表现；旧代码在别的地方行为不同（比如 floor 的跑法变了）不在这次范围内。

## 教训

- 长时间运行的后台进程会比它所测的代码旧；凡是“用自己的代码解释被测提交”的地方，失败都可能是自己的问题而不是被测提交的 → BR-2250（只覆盖读配置这一处）
