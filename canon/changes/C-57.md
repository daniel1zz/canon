## 为什么

`canon search` 要求每个词都出现。实测 `canon search "review split"` 什么也搜不到，而讲这件事的正是 D-5：英文的词碰上中文文档就失败。canon 也不记录搜索，所以不知道 agent 多常搜不到东西。lore 的数据：1118 次搜索里有 149 次（13%）没有结果，大多是多个词的自然语言查询。

## 要改什么

子领域：`knowledge/query`（搜索本身、提示、事件）和 `work/stats`（统计）。

- 每次搜索记一个 `search` 事件（查询词、结果数、全部命中的个数），`canon stats` 报出没有结果和没有全部命中的比例（BR-2134、BR-2135）。
- 多个词时，全部命中的排在前面，只命中部分词的也列出（标明命中了几个）（改 BR-2073）。
- 没有文档包含全部词时提示换中文关键词或用编号（BR-2133）。只在“完全没有结果”时提示不够：有了部分命中以后，`review split` 这种查询几乎总有结果，但真正要找的文档埋在里面。
- 规则和测试。

## 陷阱和假设

- 有了部分命中，“没有结果”会变少，但 agent 照样找不到东西；所以事件里同时记 `full`，stats 同时报“没有全部命中”的比例，否则这个指标会假装变好。
- 事件在 CLI 里记，`search()` 本身保持纯函数，规则评审等内部调用不算一次搜索。
- 顺手修了一个和本变更无关的超时：BR-2114 的 CLI 测试串行启动 26 个 `canon rule new` 进程，机器负载高时超过 5 秒测试超时，被杀掉的那个进程让规则数少一条；改成直接写规则文件。
- 同时 C-55 在改 `src/knowledge/query/query.ts`，合入时可能要 rebase 解决冲突。
