## 为什么

#104：C-236（`rules: []`）改了 BR-2045、BR-2172、BR-2248、BR-2177 的 `## 规则`，合入时既没要证据，也没让规则评审判断是不是只改措辞，四条规则悄悄变成待重新执行。根因：一次执行要验证的规则只取变更文件的 `rules:`，不看这次合入实际改了哪些规则的行为哈希（D-32、BR-2241）。

## 要改什么

- 要执行的规则 = `rules:` 里列出的规则 ∪ 这个变更的合入（这次合入，加上事件表里同一变更之前每次合入的 `base..sha`）改了行为哈希的规则。按编号比较每段合入前后两棵树里的行为哈希（BR-2236）；只移动、内容没变的规则哈希不变，不算；新建的生效规则（之前没有）算。作废和规划中的规则照旧不用执行（和列在 `rules:` 里时一样，BR-2246 里作废的规则没有执行状态）。
- 代码：`src/work/execution/evidence.ts` 的 `plan` 用这个并集算记录和缺的证据，第一次关闭时的迁移记录（BR-2245）也不给这些规则写 `migration`；`landing.ts` 的 `rulesAt` 挪到 `evidence.ts` 共用。
- 规则：BR-2241 改“要执行的规则”的定义并补例子（两侧：没列进 `rules:` 但改了例子 → 要证据；只移动 → 不要），同时处理它的两条评审意见（删掉一行的例子；BR-2062 补上 `evidence` 拒绝）；BR-2245 写明迁移不覆盖要执行的规则；BR-2062 补上 `evidence`；`work/execution` README 的术语和 D-32 跟着改。
- 同一个变更在 `rules:` 里列出 BR-2045、BR-2172、BR-2248、BR-2177，让这次合入重新执行它们：C-236 只改了它们 `## 规则` 的措辞，`## 例子` 没动，按 BR-2243 记 `wording`，由规则评审确认。

## 陷阱和假设

- 这次合入走 PATH 上旧的 canon，它只看 `rules:`；所以这里改到的每条规则都列进了 `rules:`，新旧代码算出的记录相同。
- 一个变更分几次合入时，之前合入改的规则在这次的 base 上已经是新哈希；所以按每段合入的 `base..sha` 比较，和测试证据的范围（BR-2241）一样，而不是只比较这次合入的 base。
- 同一段里改了又改回原样的规则，前后哈希相同，不算被改过。

## 教训

- 一次执行验证哪些规则只靠变更自己声明，声明漏了就没有任何东西兜底 → 现在由 BR-2241（按合入前后的行为哈希算出要执行的规则）保证；这样固化是负责人在 #104 里要求的（issue 的“Expected”）。
- 规则评审判 BR-2172、BR-2177、BR-2248 的措辞修改为行为（去掉了“单独合入标记”的说法）→ 只靠文字：删掉一个已不存在的机制的描述，评审也可能认为行为变了，要备好补测试；这类判断本来就交给评审（D-32 方案 7）。
