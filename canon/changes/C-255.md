## 为什么

2026-11-04 的独立评审发现 D-35（C-42）有几处真问题，负责人当天选择按评审重做（选项“D-35、D-43、D-40 一并重做”）。逐条核对过：作者检查只比较执行者名字，`CANON_ACTOR` 一设就绕过（本会话实测 6 次变 38 次）；agent 和人的区分只看 `CLAUDECODE=1`，不在 Claude Code 里的 agent 会记成人；36 次评审拦截里 33 次不止一条意见，一次只记一个结论判不出哪条对；判定者看得到修复，有事后偏差；引用的论文只支持“模型判定有偏差”，不支持“和人一致”。设计和取舍写在 D-49（取代 D-35，待评审后接受）。

## 要改什么

按 D-49：

- `review.verdict` 改成每条意见一条，`judge` 是 `model`（canon 运行判定命令做出）或 `human`（自报）。
- `canon verdict pending`（BR-2253）：按拦截列出每条意见和已有判定，只写拦截时的提交，不写合入的提交；不再按执行者过滤。
- 新增 `canon verdict run --limit <n> [--dry-run]`（BR-2290）：把拦截时的代码树导出到没有 `.git` 的临时目录，在那里运行项目的 `review` 命令，提示里只有意见和改了哪些文件；结论按每条意见记成 `model`。
- `canon verdict record <拦截事件编号> <意见编号> real|spurious|unclear --reason`（BR-2254）：只给不在 Claude Code 会话里的执行者，记成 `human`。
- `canon stats` 的判定一节改成按每条意见统计、`model` 和 `human` 分开，写明 `human` 是自报的（BR-2255）。
- 代码在 `src/work/stats/verdict.ts`、`src/work/stats/commands.ts`，测试在 `src/work/stats/verdict.test.ts`；`work/stats` 的 README 改说明。
- 判定频率和花费不定，写在 D-49 的“需要负责人决定”里。
- 按 D-54 判评审的发现：`record` 不再检查“执行者写过这个变更的事件”（只防无心之失，D-49 写成已知限制）；`CANON_ACTOR` 绕过、不在 Claude Code 里的 agent 记成 `human` 都是已知限制。
- 同一次重做 D-40：D-57（取代 D-40）给 `canon usage` 的每个未用项加 `scope`（`project`/`other`）和一行固定说明（BR-2266）；注入量少算、内存随记录增长、记录保留期、路径编码有损四项记成已知限制，不加机制。

## 陷阱和假设

- 一条 `review.block` 对应它之后第一条同一变更、原因为 `review` 的 `land.refuse`（`steps.ts` 先写 `review.block` 再返回拒绝）。原因为 `review` 但没有 `review.block` 的拒绝（评审没能运行、BR-2239 的文字判断）没有意见，不判。
- 判定命令的相对路径（`scripts/review-claude.sh`）按当前 worktree 解析成绝对路径，因为工作目录是导出的临时目录；导出的树里那个脚本是拦截时的旧版本，不能用它。
- 导出用 `git archive`，不建 worktree：不碰 worktree 锁（BR-2223），导出目录里也没有 `.git`，判定命令看不到之后的历史。
- 判定命令和评审命令一样受信任，它如果自己去读别的路径（比如主 checkout），canon 挡不住；“看不到修复”靠的是工作目录和提示里没有。
- 真实数据的提示大小（`canon verdict run --limit 50 --dry-run`，2026-11-04 实测）：37 个拦截、114 条意见、提示合计 62999 字符（约 1400 到 1600 字符一个）；判定命令还会读导出目录里的文件，实际 token 以第一次运行为准。

## 教训

- 一个检查如果比较的是执行者自己能设的值（`CANON_ACTOR`），它只防无心之失，不能写成保证；D-35 写成了保证 → 只靠文字：执行者名字是不是“执行者能设的”取决于每个检查的用途，程序判断不了；评审时看决策是否写清 canon 能保证什么。
- 判定的单位要和被判定的数据的单位一致（拦截有一组意见，就按意见判）→ 只靠文字：这是设计时的判断，没有可以机械检查的形式。
