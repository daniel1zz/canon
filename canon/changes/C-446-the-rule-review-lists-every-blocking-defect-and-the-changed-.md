## 为什么

#173：在 zhushenkongjian 里，改了很多文档的变更要被规则评审拒绝很多轮（C-439 8 次、C-440 17 次、C-441 12 次）。每轮只报 1 到 6 个问题，每轮报的还不一样。实测（D-83）：评审每次调用最多报 1 个拦截问题，报哪个是随机的；领域全文越大，改动文档本身的问题越容易漏。

负责人还关心速度（2026-11-10：“不止前的问题，主要还是效率问题”）：拆开的调用一次接一次地跑，一次评审有十几次调用，每次 40 秒到 4 分钟。

#175（每次调用只带相关的改动文档）合并进来一起评估：实测只省 0 到 4%，负责人决定关闭它（数据记在 D-72）。

## 要改什么

- BR-2009：评审说明要求列出每一个拦截问题；只在没改动的文档之间的问题只能是 `note`。
- BR-2359：一次完整评审改了两份以上有编号的文档时，每份改动文档先有一次不带领域全文的单文档调用，只能因为这份文档被拦；领域全文装箱成领域调用，只能因为点名了这次领域全文里的文档被拦；canon 把越界的拦截意见改成 `note` 并写明原因。各次调用最多同时运行 `review_parallel` 次（新配置项，默认 4）；一次失败就停下其他正在跑的调用。合入输出写明单文档调用和领域调用各几次。
- BR-2074：`review_parallel` 和其他评审设置一样取自 main 上的配置。
- D-83（修改 D-67）记录方案和实测；D-72 补上 #175 的测量数据。
- 代码：`src/knowledge/review/review.ts`（`reviewCalls`、`runReviews`、`splitNote`、`parseAnswer`），`config-keys.ts`，`review-scope.ts`，合入和预览两处调用。

## 陷阱和假设

- 单文档调用的判断依据是“意见文字里有没有这份文档的编号”，评审不写编号的拦截意见会变成 `note`；提示早已要求每条意见点名编号（BR-2367）。
- 领域 README 没有编号，不单独调用：改动的 README 的新文字在领域全文里，由领域调用评审。
- 同时运行时，被停下的调用也会返回失败；只报最先失败的那一次。
- 假设：单文档调用不带领域全文能提高召回，是从“去掉领域全文召回更高”的实测推断的，没有单独测过（D-83 后果里写了合入后复测）。

## 教训

- #175 的数字来自一个极端变更（43 份文档）；先按真实分布（中位数 5、九成不超过 14）量常见情况，才看出分组几乎省不了 → 只靠文字：什么算“常见情况”要按项目的数据判断，没有通用的检查能做。
