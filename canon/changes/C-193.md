## 为什么

baseline 核对（N-4）在配置领域发现三件事，负责人 2026-11-04 选择推荐方案：“全部按推荐”。

- 前台 hook（`after_start`、`before_land`、`after_stop`）先打印全部标准输出、再打印全部标准错误，两者交替写的命令看到的顺序是错的（BR-2200）。
- `canon config --schema` 在配置写错时以退出码 2 失败；schema 和配置内容无关，正是配置写错时最需要它（编辑器靠它标错）。
- 固化教训（负责人已同意）：BR-2175 的 schema 测试只给手写想到的键配了 `null` 样本，canon 自己对 null 的处理（null 等于没写）和 schema 可能在没想到的键上不一致；改成为每个配置项自动生成一个 null 样本来比较。

## 要改什么

- BR-2200：输出的标准输出和标准错误进同一个管道，按写出的先后排列；加两侧的例子。
- `src/config/hooks.ts`：前台的两个运行函数用 `sh -c 'exec 2>&1\n<命令>'`，标准错误重定向到标准输出的管道。
- BR-2175：`--schema` 不读配置，配置写错、不在 git 仓库里也照样打印，退出码 0；加 null 样本的例子。BR-2045：“所有命令都失败”写明不读配置的例外（`--help`、`canon config --schema`）。
- `src/config/reference/commands.ts`：先处理 `--schema`，再打开 workspace。
- 测试：`src/config/hook-run.test.ts`（同步和异步两个运行函数）、`src/config/reference/reference.test.ts`（无效配置和仓库外的 `--schema`；每个键的 null 样本）。

## 陷阱和假设

- 命令前面多了一行 `exec 2>&1`，所以 sh 报的语法错误行号比命令自己的行号大 1；进程自己的标准错误仍然读并接在后面，接住 sh 在重定向之前说的话。
- 后台的 `after_land` 本来就把两个流写进同一个日志文件（BR-2201），不用改。
- 自动生成的 null 样本要求两边完全相同，不允许 schema 更宽：BR-2175 列出的“表达不了的例外”里没有 null。现在所有键两边一致，测试一加上就通过。

## 教训

- schema 和 canon 读配置的对照样本只覆盖手写想到的键 → 现在由 BR-2175 的测试为每个键自动生成 null 样本保证（负责人已同意固化）。
