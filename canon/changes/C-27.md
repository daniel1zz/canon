## 为什么

D-8 按内容审计旧 skill 后，决定移植 `lore-test` 和 `lore-uat` 里强模型默认不会做的具体做法：先从规则推出预期再读实现、可疑模式扫描、mock 注明依据、纵向切片、验证纪律八条；验收时执行者和裁判分开、结果必须由机器探测证明、拒绝类要求同样要验收。旧 skill 依赖 lore 的语料库、PRD 和记录命令，还有凭空定的覆盖率门槛、强制浏览器测试和“等人批准计划”的步骤，不能直接用。

## 要改什么

- 新增 `skills/canon-test/SKILL.md`：来源是 `lore-test`（规则先行、Step 2b 可疑模式表、mock 注明依据、至少两组输入得到不同输出）、`lore-tdd`（纵向切片，每个新测试先看到它失败）和 `shared/verification-discipline.md` 的全部八条（退出码不隔着管道读、正反对照成对出现等）。依据改成 canon 规则的“规则”和“例子”，测试名以规则编号开头；worktree 里只跑相关测试，全量由 floor 在合入时跑。去掉等价类和边界值教科书内容、70/20/10 金字塔、覆盖率门槛、强制 agent-browser 端到端测试、lore 持久化步骤和用户批准计划。
- 新增 `skills/canon-test/references/false-green-patterns.md`：旧假绿模式清单的压缩版，附 grep 命令。
- 新增 `skills/canon-uat/SKILL.md`：来源是 `lore-uat`（执行者报告、裁判判定；H1 任务完成、H2 机器探测否则 UNVERIFIED 不能通过、H3 不作弊；P0 的 H1 失败要第二个独立执行者复现才能驱动 REJECT；拒绝类要求是一等公民），并入 `lore-dogfood` 的破坏性探测（重复提交、两处同时编辑、中途中断）。依据改成 `canon context` 给出的规则和例子；发现的问题落成规则修改或 GitHub issue；新增命令行驱动（一次性 git 仓库里跑真实命令，断言输出、退出码、文件和 git 状态）；默认简版；原来遇到未确认就停下问人的分支改成记为 UNVERIFIED 继续。
- 不新增也不修改规则：skill 是给 agent 读的说明，不是产品行为。
