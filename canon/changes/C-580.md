## 为什么

#232 的最后一块（D-128，负责人选的“A + 合入后评审补强”）。worker 已能在固定的设计版本内自己合入（C-570、C-577、C-579），C-579 让 `land.ok` 记下了派发快照；但合入后的代码评审还不会找 worker 在代码里自己定下、契约清单没写到的业务选择，这类选择不会回到设计负责人手里。

## 要改什么

按规划中的 BR-2503 实现并激活它（`status` 改成 active、删 `will_amend`），同时按它的“生效时”改 BR-2070、BR-2071：

- `scripts/code-review.ts` 的评审范围里有改了 `canon/` 以外文件的 worker 合入时，提示另外给出：按 `land.ok` 的派发快照，契约清单每一项在快照设计版本上的全文、这次合入自己的 diff、它的 `land.ok` 事件编号和合入提交，以及找 `design-gap` 的要求。
- 接受类别 `design-gap`；发现要写一个范围内 worker 合入的 `land.ok` 编号，否则丢弃并打印 `dropped ...`；每条开一个带 `canon-design-gap` 标签的 issue，写明变更、合入者、设计负责人、代码位置和没写到的选择。

做了的：

- `src/knowledge/review/code-review-batch.ts`：`landedEvents` 多读 `land.ok` 的事件编号、`base` 和派发快照；`workerLandings` 挑出范围里有快照的合入（有快照却没有 `base` 时报错，不猜）交给评审。
- `src/knowledge/review/code-review.ts`：`workerContexts` 只留改了 `canon/` 以外文件的 worker 合入，契约清单每一项按快照的设计版本 `git show` 全文（读不到就报错、评审不算跑过），diff 取 `land.ok` 的 `base` 到它的提交；提示在有这样的合入时才加 `design-gap` 一节（业务选择的四类、命名和函数拆分不算、只按这里给的设计版本上的全文判断），每个合入的标题写 `land.ok` 编号、提交、变更、合入者、设计负责人、代次和设计版本；`parseFindings` 接受 `design-gap`，编号不是范围里 worker 合入的就丢弃并打印 `dropped ...`；每条 `design-gap` 开一个 `canon-design-gap` issue，按它写的那次 `land.ok` 的快照写变更、合入者、设计负责人、设计版本和契约清单、没写到的选择和代码位置。
- 测试在 `src/knowledge/review/design-gap.test.ts`：一条走真的派发和 worker 合入，其余按 `snapshotDetail` 记 `land.ok`，覆盖 BR-2503 的例子。
- BR-2503 激活；BR-2070 的提示改成“只找安全和并发问题（另加 BR-2503 的 `design-gap`）”，BR-2071 接受的类别加上 `design-gap`，并各加一条例子。
- `canon work delegate` 在没配 `scripts/code-review.ts` 时提示 `design-gap review: not configured`，BR-2497 已经要求、代码和测试已经有，这次不改。

## 陷阱和假设

- 测试用假的评审命令和假的 `gh`，不调用真的模型或 GitHub。
