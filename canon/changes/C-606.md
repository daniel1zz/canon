## 为什么

C-603 计划的 A 步（D-137）。canon 不记录会话用的是哪个模型，所以没法回答「不同模型要不要不同的流程轻重」：F 步要用两周以上的实测数据决定，这一步先让数据开始积累。

## 要改什么

- BR-2531（新）：`canon work model --hook` 从宿主 hook 的输入记一条 `session.model` 事件（宿主、模型、来自哪个 hook，取不到时记为未知并写原因），模型没变就不再记；Codex 的启动 hook（BR-2023）读到的同一份输入也记下模型。
- BR-2532（新）：`canon stats` 的文字输出加 `landings by host and model` 一节，按合入和被拒时会话的模型分开计数；子 agent 没有自己的记录时借用会话的模型，单独成行并标出 `(session's)`。
- BR-2533（新）：Claude Code 项目的 SessionStart 和 PostModelSwitch 装上这条 hook。
- BR-2459：Codex 项目另加一个 Stop 条目，在会话中途换模型时记下来（Codex 没有切换模型的 hook）。
- 代码：`src/work/stats/model.ts`（解析、记录、统计）、`src/work/stats/commands.ts`（`canon work model`、stats 一节）、`src/work/agent-session.ts`（Codex 启动时记模型）、`src/install/hook.ts`、`src/install/update.ts`、`src/install/codex.ts`；本仓库自己的 `.claude/settings.json` 也加上这两个条目。
- 被撤回的次数不在这一步：撤回事件由 C 步加，统计也在那里加。

总览不受影响：只是在协调数据库的事件表里多一种事件、`canon stats` 多一节，部件、数据位置和主流程都没变。

## 方案依据

沿用 C-603 定的方向：只往协调数据库的事件表追加 `session.model` 事件，不改已有的表结构；之前的事件没有模型，统计里算作「unknown: no record」，不补写。新选的是归属方式：合入事件本身不带模型，统计时按执行者找它之前最近一条模型记录，这样模型切换后的合入自动归到新模型，也不用改合入的代码。

hook 输入里的字段是实测的，不是猜的：Claude Code 2.1.328 的程序里，SessionStart 的输入带 `model`（可能为空），PostModelSwitch 的输入带 `from_model`、`to_model`；Codex 0.170.0 的程序里每种 hook 的输入都有 `session_id`、`model`。字段改名或消失时，记录是「未知」加原因，不会报错，也不会把合入算错。

最坏的失败：宿主里开的子 agent（Claude Code 的 Agent 工具）不单独记模型，它的合入借用开它的会话的模型；它可能用了别的模型，按模型分档就会被这部分带偏。所以统计把它们单独列出（`(session's)`），F 步决定前要先看它占多少。如果两周后这一行占合入的比例很大，就说明需要给子 agent 单独记模型（例如 Claude Code 的 SubagentStart hook 或 `--as` 时声明），再做 F 步。

事件表坏了按现有的协调数据库恢复处理，丢掉的只是统计。
