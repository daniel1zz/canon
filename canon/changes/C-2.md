## 为什么

D-1 决定代码评审在合入之后运行、不阻断。旧系统的数据显示，安全评审 8 条里 7 条是真问题，并发评审 14 条里 11 条是真问题；但因为只看一个 plan 的 diff，同一个问题被重复提交（一个问题被拆成 10 个 issue），修好的问题还被反复报。

## 要改什么

写一个 `after_land` 用的脚本（C-1 完成后作为 `after_land` hook 配置）：

1. 读取 `CANON_BASE..CANON_HEAD` 的完整 diff，以及受影响文件在当前 main 上的全文（不是只看 diff）。
2. 让 AI 只找安全和并发问题，每条写清楚：在什么输入或时序下会出错、在哪个文件哪一行。
3. 提 issue 前先用 `gh issue list --search` 查同一根因有没有未关闭的 issue，有就在那个 issue 下补充，没有才新建。一个根因一个 issue。
4. 默认不开启。负责人确认之后再写进配置，因为它会往 GitHub 写东西。

实现时定下的细节：

- 脚本是 `scripts/code-review.ts`，逻辑在 `src/review/code-review.ts`；评审命令和 `gh` 都可以用环境变量换掉（`CANON_CODE_REVIEW_AI`、`CANON_GH`），测试用的是替身，没有访问 GitHub。
- 去重分两层：把带 `canon-review` 标签的未关闭 issue 交给评审，让它指出同根因的编号（只接受确实未关闭的编号）；它没指出时再用 `gh issue list --search` 按标题找。
- 开启方法：在 `canon/config.yaml` 的 `hooks.after_land` 里加一条 `bun scripts/code-review.ts`（在 `bun run build` 之后）。开启前要先在仓库里建 `canon-review` 标签。

开启前用真实的评审命令、假的 `gh` 在 `9c2938a..d42824f`（C-18 到 C-22）上试跑了一次：38 秒，报 3 条，其中 2 条是真问题（另开变更修复或提 issue），1 条基本是误报（中文文件名，规则和决策的文件名本来就只能是 ASCII）。
