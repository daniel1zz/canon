## 为什么

N-3 的并发实测和本会话的几轮派发说明，派并发子 agent 有一套固定的做法：什么任务适合拆、每个子 agent 的说明里必须写什么、主 agent 怎样从事件表核对结果。这些现在只存在于主 agent 每次手写的派发说明里，换一个会话或换一个项目就要重新摸索；子 agent 漏掉其中一条（比如进了别人的 worktree、通过管道读合入的退出码、为评审建议开跟进变更）的代价是返工或多占合入队列。负责人 2026-11-03 同意把它写成随 canon 一起装进项目的 skill。

## 要改什么

子领域：cli/install（canon 自带的 skill 放在 `.claude/skills/canon-*`，由 `canon install`/`canon update` 装进项目）。

- 新增 `.claude/skills/canon-parallel/SKILL.md`（英文）：什么时候拆、什么时候不拆（互相独立、中等规模、一次 3 到 5 个；floor 是吞吐上限；改同一文件的会在合入时冲突）；每个子 agent 的说明必须包含的内容（自己的变更、不进别人的 worktree、合入前 `canon work test`、长超时合入并直接读退出码、`canon work after-land --wait` 或读后台日志、只清自己的 worktree、不为不阻塞的评审意见开变更、汇报带测量数字）；主 agent 怎样用 `canon stats --since`、`canon events --since` 和 `git log` 核对，而不是信子 agent 的汇报；命令不存在时怎么办。
- CLAUDE.md 的 skill 列表加上它。
- 不新增规则：装哪些 skill 由现有规则覆盖（每个 `canon-*` 目录都装），skill 文字不引用 canon 自己的文档编号由现有测试检查。

## 陷阱和假设

- skill 里提到的 `canon work test`、`canon work after-land --wait`、`canon stats --since`、`canon events` 在别的项目装的 canon 版本里可能还没有；skill 写明了没有时的做法。
- 数字（约 2.5 分钟一次合入、5 个子 agent 快约 2.8 倍）来自一次实测，写成“在一次实测里”，不当成通用结论。
