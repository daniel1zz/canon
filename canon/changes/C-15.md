## 为什么

C-7、C-9、C-2 和 C-14 合入时，规则评审提了一批不拦截的建议，大多是例子没把边界定死；其中两条其实是代码和规则对不上：`canon doc list` 写着按编号排序，代码却按文件名的字典序（`SP-10` 排在 `SP-2` 前面）；代码评审脚本只给“新增和修改”的文件全文，改名的文件被漏掉了。

## 要改什么

- `canon doc list`（以及其他 list 命令）按编号的数字顺序排序（BR-2061）。
- 代码评审脚本给除删除以外的所有改动文件全文，包括改名的（BR-2070）；删掉的文件只在 diff 里。
- 补例子和测试：BR-2062（只提交了变更文件时不提示、合入在进队列前被拒时不提示、不看变更状态）；BR-2067（claim、setup 的计数）；BR-2068（只提了问题的 drop 不算放弃、多次被拒都算 pending、没有变更编号算 unknown）；BR-2069（日期等于今天算到期）；BR-2070（缺环境变量、二进制文件、删掉的文件）；BR-2072（按标题找时也只认带标签的 issue）。
- N-1 补上本会话实际遇到的一次误拦（`git checkout -- <文件>`）。
