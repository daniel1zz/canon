## 为什么

规则太零散：领域下面直接挂规则，中间没有东西。一个业务的边界分散在几条规则里，彼此没有名字连起来，写新规则的人看不见它们，就写一条重叠的；之后改了其中一条、漏了另一条。负责人举的例子是 BR-2089「很明显属于 Update」，但 canon 里没有「Update」这个东西（见 D-96 的背景）。

## 要改什么

按 D-96 加一层业务：领域 README 的 `## 业务` 段列出这个领域管的业务，规则 front matter 用 `business:` 指向其中一个，`canon check` 只对本次工作新增或改动的规则双向核对。

- 新规则 BR-2430（业务怎么写、规则怎么指向）、BR-2431（`canon check` 的核对和拒绝）、BR-2432（`canon rule new` 先列出这个领域的业务和规则），都在新领域 `knowledge/domains`。
- 改 BR-2007：`canon context` 只列标题时，每条规则后面标出它的业务。
- 代码：新增 `src/knowledge/domains/business.ts`（读 README 的业务清单、算发现、给 `canon rule new` 列清单）；`model.ts` 和 `read.ts` 读 `business`；`templates.ts` 的领域 README 模板带 `## 业务`；`check.ts` 加 `rule-business-unmapped`；`commands.ts` 让 `canon rule new` 先列清单；`query.ts` 在上下文里标业务。
- 引导：canon-rules 的第 1 节改成「先找业务，读完这个业务现在的全部规则，再决定改哪条或新建」；canon-domains 加一句，领域内部的细分走业务清单，不是再开目录。

## 陷阱和假设

- 「本次工作新增或改动的规则」用的是 `canon check` 输入里 `architecture.since`（本次工作的基点），不是另给一个基点；在主检出（primary worktree）里一条都不报，判别方式是 `git rev-parse --git-dir` 和 `--git-common-dir` 相同。
- 存量 480 条规则大多没有 `business`，这是故意的：只有被改到的规则才要补，不做一次性迁移。
- 业务名只在它所在的领域里有效，跨领域的业务表达不了（D-96 的后果）。
