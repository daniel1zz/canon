## 为什么

负责人想方便地看到 `canon/config.yaml` 能设置的全部项并进行设置。网页配置页违反产品的“不做的事”、并会绕过合入，改为命令加编辑器 schema（D-28）。

## 要改什么

- 新子领域 `config/reference`，代码在 `src/config/reference/`。
- `ConfigKey` 加必填的 `schema` 片段和可选的 `needs`；19 个配置项都写上 schema。
- `canon config`：列出每个配置项的值或默认值和说明，`--json`，没有 modeline 时提示（BR-2174）；`canon config --schema` 输出 JSON Schema（BR-2175）。
- `canon brief` 和 `canon config` 写被 git 忽略的 `.canon/config.schema.json`，`/.canon/` 加进 git 公共目录的 `info/exclude`；清理和放弃 worktree 时 `.canon` 总算可重建（BR-2176）。
- `canon init` 写的 `canon/config.yaml` 第一行是 modeline（BR-2032）；本仓库的 `canon/config.yaml` 也加上。
- 开发依赖 ajv，测试用它比较 schema 和 canon 读取的结论。

## 陷阱和假设

- schema 片段必须比 canon 的读取更宽或一样：只要 schema 拒绝了 canon 接受的值，编辑器就会把有效配置标红。新加配置项时在 `reference.test.ts` 的样例里补边界两侧的值。
- 用 `stringValue` 读的键把 null 和空字符串当作没设，schema 要接受这两种写法（`test_command` 因此写成 `anyOf`）。
- 方案里不要写“xx 来源：”这种字样，`canon check` 会把它当成引用来源行去解析。

## 教训

- 带子命令的父命令不做参数严格检查（BR-2097 只检查叶子命令），所以 `canon config` 用 `--schema` 选项而不是子命令 → 待负责人确认是否固化（可以让严格检查也覆盖有 `run` 的父命令）。
- 决策方案正文里的“来源：”会被当成来源行 → 只靠文字（本变更的陷阱一节）：检查按“来源：”识别来源行是有意的格式约定，改成更严的识别会让真正写错格式的来源漏报。
