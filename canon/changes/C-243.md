## 为什么

#101（C-237 合入后的代码评审）：后台测试被 SIGTERM 或 SIGINT 终止时，`killTree` 用一次次 `pgrep -P` 拍下 `after_green` 的进程树，先杀子进程再杀父进程。拍完以后进程树还在变：父 shell 在子进程死后、自己的 SIGTERM 到达前启动下一条命令（`after_green` 是 `bun build ...` 和 `cp dist/canon ~/bin/canon` 两行，`cp` 不在快照里）；命令放到后台、父进程已经退出的进程被 launchd 收养，`pgrep -P` 找不到。这些进程留下来，和下一个后台测试补跑的 `after_green` 同时写 PATH 上的 canon，就是 #99 说的重叠。另外 `setup` 和 floor 只登记了 `sh` 本身，`proc.kill()` 只杀 `sh`，`bun test` 这类子进程留在已删掉的临时 worktree 里继续跑。

复现（改动前）：`src/work/watch/watch.test.ts` 的 BR-2270 用例：`after_green` 用两次 fork 放出一个脱离父进程、1 秒后写文件的进程，后台测试以 143 退出后它照样写出了文件；BR-2219 的用例对 floor 做同样的事。

## 要改什么

- `src/work/watch/stop.ts`（新）：停掉这个进程启动的所有进程。后台测试是自己进程组的组长时（合入、`canon brief`、交接都这样启动它），对象是组里除自己以外的每个进程，包括父进程已退出、被 launchd 收养的；不是组长时（在不带作业控制的 shell 里手动运行），对象是自己的子孙进程。先从上往下发 SIGSTOP 并反复重新列出，直到没有新进程，这时谁也没法再启动新进程；再给每个发 SIGTERM、SIGCONT。
- `src/work/watch/watch.ts`：`onSignal` 用它代替 `running.proc.kill()`；去掉 `Running`。
- `src/config/hooks.ts`：去掉 `killTree` 和 `HookContext.running`，后台测试不再需要登记正在跑的命令。
- BR-2270、BR-2219：写明被信号终止时停掉的是后台测试启动的全部进程（`setup`、floor、`after_green` 和它们启动的），包括之后才启动的和父进程已退出的；自己调用 `setsid` 脱离进程组的进程（守护进程）不在其中。

## 陷阱和假设

- 依赖 macOS 和 Linux 的 `ps -axo pid=,ppid=,pgid=,stat=`；读不出进程表时什么都停不了，照旧退出并在日志里写一行。
- 列进程用的 `ps` 自己也在组里，按 `spawnSync` 返回的 pid 排除，否则会把它停住，自己永远等下去。
- 僵尸进程（stat 以 `Z` 开头）不算：它们已经结束，只是还没被父进程回收。
- SIGTERM 发给已停住的进程时要等 SIGCONT 才生效；有 TERM trap 的 shell 继续后执行 trap，trap 里新启动的进程是清理工作，不再去杀。等它们结束再交出位置是 #102 的事，不在这个变更里。

## 教训

- 停一组进程时，先冻结再发信号，否则拍快照和发信号之间进程树会变 → 只靠文字：这是进程管理的通用做法，项目里只有这一处，没有可以检查的模式。
