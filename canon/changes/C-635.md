## 为什么

#280：项的声明（C-619）里，项目在 `canon/config.yaml` 写的 `pattern` 槽位和 `none` 是任意正则，`src/knowledge/documents/items/read.ts` 用 JavaScript 自带的回溯引擎同步地拿它们去对文档的每一项。复现（临时仓库，Bun 1.4.4）：类型 `adr` 声明 `format: "(?:[{tag}] ){text}"`、`tag: {pattern: "(a+)+"}`，文档里 30 项 `- [` 加 36 个 `a` 加 `!] item n`，`canon show ADR-1 --json` 用了 22 秒（每项约 0.7 秒，`canon check` 读全部文档时同样按项累加）；修复后 0.15 秒。

实测还发现第二个问题：Bun 用的 JavaScriptCore 引擎回溯到一定步数就放弃，不报错，直接当成没对上。`/^(?:(a+)+$|a+!)/` 对 40 个 `a` 加 `!` 本该对上第二个分支，实际返回 null，用了 0.9 秒。所以这类正则不只是慢，还会悄悄读错：对得上的项被当成对不上，`none` 该清空的段落被当成有项。

## 要改什么

- 读项时所有正则（模板拼出的整条、`pattern` 槽位、`none`）改用 re2js 匹配：Google RE2 的纯 JavaScript 移植，按输入长度线性匹配，不回溯（D-153）。BR-2547 加一条「用时」和三个例子。
- 声明 `pattern` 和 `none` 时按 RE2 语法核对：向前、向后查找和反向引用等 RE2 不支持的写法是配置错误，退出码 2，信息写出 `canon/config.yaml`、出错的 key、正则原文和 RE2 给的原因。BR-2546 写明语法和这几个例子。
- `ids` 槽位分隔符后的空白原来用 JavaScript 的 `\s`（含全角空格）；RE2 的 `\s` 只认 ASCII，所以写成等价的字符类，行为不变。
- 新增开发依赖 `re2js`（打包进 `dist/canon.js`）。

领域：`knowledge/documents/items`。

总览不受影响：只换了读项时用的正则引擎，没有新部件，数据位置和主流程不变。

## 方案依据

- 沿用：D-144 的声明格式和 BR-2547 的选择顺序都不变，只换匹配用的引擎。
- 新选择：用 re2js，而不是在声明时检测危险写法或给匹配加时限；理由和被否决的做法见 D-153。
- 为什么用这个依赖而不是自己写：线性时间的正则引擎要用自动机实现，自己写一个是重造 RE2；re2js 没有运行时依赖，是纯 JavaScript，`bun build` 能直接打包，不像 node-re2 要编译原生模块。
- 它在实际运行环境里的限制（Bun 1.4.4 上实测）：只支持 RE2 语法，`(?=`、`(?<!`、`\1`、`一` 都编译不过（要写 `\x{4e00}`）；`\s`、`\S` 只认 ASCII，`.` 匹配 ` `；打包后 `dist/canon.js` 从 1,800,802 字节变成 2,042,377 字节；启动时间没有可测的差别（同一命令三次都在 0.3 到 0.5 秒）；本仓库 622 个变更的 221 条教训全部读一遍从 3 毫秒变成 15 毫秒。
- 最坏的失败：项目已经在 `pattern` 或 `none` 里用了查找或反向引用，升级后所有命令退出码 2。错误信息写明文件、key、正则和原因，改写即可；项的声明是 C-619 刚加的，本仓库没有项目声明。
- 什么结果说明选错了：re2js 的分组取值和 BR-2547 要求的选择顺序不一致（前面的槽位取尽量长），或读文档明显变慢。前者由 BR-2547 的现有测试守着（多个 ` → ` 按最后一个分开）。

## 陷阱和假设

- re2js 的 `exec` 和 JavaScript 一样是「找到第一处」，所以 `none` 的 `^`、`$` 仍由声明自己写；模板拼出的整条已经加了 `^…$`。
- 编译后的正则按源字符串缓存在 `read.ts`，同一个声明不会对每一项重新编译。
- 假设 RE2 的「最左优先」取值规则和 JavaScript 对不含反向引用、查找的正则取到的分组一致；RE2 文档这样写，现有的 BR-2547 测试也都通过了。

## 教训

- Bun（JavaScriptCore）的正则回溯超过上限时不报错、直接返回没对上，测试看到的是「答案错」，不是「超时」 → 只靠文字：这是引擎行为，canon 已不再用回溯引擎跑项目声明的正则（D-153）
