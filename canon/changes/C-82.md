## 为什么

C-81 让子领域的 README 用 `code:` 写自己管哪些代码。负责人（2026-11-03）要求子领域只写业务：“业务是业务……不然每次都要更新还可能出错”，并要求“业务的代码目录和baseline的目录应该一一对应”；分析利弊后选了建议的方案（“按建议做”）。取舍和被否决的方案记在 D-15。这个变更做机制；canon 自己的代码按领域重新组织放在下一个变更里。

C-41（`src` 下每个源文件都归属一个领域）被 D-15 取代，已标为 dropped：启用 `code_root` 后，代码目录和领域一一对应，BR-2118 报出每个没有归属的目录，不再需要逐个文件的归属检查。

## 要改什么

- 配置 `code_root`、`shared`（BR-2116，写错时退出码 2，BR-2045 指向它）。
- 领域的代码位置：有 `code_root` 时按约定；没有时顶层 README 的 `code:`，子领域没有（BR-2006、BR-2079、BR-2113）。README 可以没有 front matter。
- `canon check`：多余的 `code:` 报 `domain-code-declared`（BR-2117）；有 `code_root` 时目录和领域对不上报 `code-layout`（BR-2118，只放测试的目录不例外）。
- `canon context <文件>`：带上它导入的代码所在的领域，单独标出（BR-2119）；列出同一顶层领域下没有返回的子领域名字（BR-2120）。
- `canon rule domain`：子领域、或有 `code_root` 时不接受 `--code`；没有 `code_root` 的顶层领域必须有（BR-2115）。
- 合入评审跳过原样挪动的文件（BR-2009）。
- `canon stats` 报出共享代码的比例，超过 20% 时提示（BR-2121）。
- 删掉所有子领域 README 的 `code:` 和正文里的代码路径；更新 CLAUDE.md 对领域的说明；决策 D-15。

## 陷阱和假设

- canon 自己这次还没有 `code_root`，所以子领域的 README 去掉 `code:` 后，`canon context src/work/drop.ts` 暂时只落到 work 顶层（4 条规则加子领域名字），下一个变更启用 `code_root` 后才能落到子领域。
- 读导入只认 `./`、`../` 开头的路径，按 JS/TS 的写法解析；路径别名不认。
- `readCorpus` 多了第三个参数 layout，调用的地方传 `ws.config`（Config 里有 `codeRoot` 和 `shared`）。
