## 为什么

基线审计列出合入领域里两类缺口：

- 有几种行为代码里明确这样做了，但没有规则写下来：一起测时临时 worktree 里的 `setup` 失败让这批作废；临时 worktree 建不了时领头单独合入、成员不标单独合入；领头在移动 main 前失去轮次时成员回到队列、不标单独合入；成员在批里合入后分支或文件跟不上时保持原样并提示 `git rebase main`；`--finish` 遇到已经是 `done` 的变更时不做关闭提交，照常合入并释放认领。
- 好几条规则的例子没有测试验证：BR-2013、BR-2031、BR-2043 的退出码 2（经 CLI）；BR-2014 拒绝信息里的日志路径；BR-2048 的 `land_timeout_minutes`；BR-2049 被拒后后面的人立刻开始；BR-2122 例子 2、3；BR-2161 例子 5；BR-2172 的 `after_land`、锁定后 SIGTERM、锁定前成员停下、`land_batch_max: 2`、旧版本条目；BR-2177 的 `resolving` 和 `resolve_ms`；BR-2178 例子 1 到 3 的端到端。另外 `src/cli/main.test.ts` 里验证 BR-2048 `--timeout abc` 的测试名写成了 BR-2044。

## 要改什么

- 新规则 BR-2190（一起测没开始或领头失去轮次时成员不标单独合入）、BR-2191（成员跟不上时保持原样并提示）；BR-2173 加 `setup` 失败；BR-2018 写明已是 `done` 的变更。
- 只描述现有行为，不改代码。
- 新测试文件 `src/work/land/cli.test.ts`、`src/work/land/batch-edges.test.ts`，`keep-place.test.ts` 加端到端测试；改正 `main.test.ts` 的规则编号。

## 陷阱和假设

- 合入在测试进程里跑时，它的 `git` 调用是同步的，会把测试自己的轮询也卡住；要在合入中途（例如移动 main 时、rebase 时）插一手的测试，合入者必须用 CLI 另起进程。

## 教训

- 端到端测试要在合入某一步中途动手时，用 git hook（`post-merge`、`post-checkout`）卡住那一步，合入者另起进程 → 只靠文字：写在本变更的“陷阱和假设”里，测试本身就是例子。

- 第一次合入被 floor 拒绝：新测试有类型错误，而 `canon work test` 只跑 `bun test`，不做类型检查，所以落地前没发现 → 待负责人确认是否固化（例如让 `canon work test` 先跑一次 `tsc --noEmit`）。
