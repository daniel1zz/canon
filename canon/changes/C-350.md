## 为什么

独立审查认为 D-64 方向对，但有缺陷：选测试的替代被推给后续决策，删掉按导入和 CLI 选测试后 canon 自己的项目会无声漏选（D-23、BR-2157 要防的）；全量运行（floor）的报告用不上；`test-report-missing` 触发太宽；合入证据降到文件级没有量化；Godot 项目的报告没有实测；pytest 的对策与“项目不用写解析脚本”矛盾；BR-2181 同样违反“不认任何语言”。

## 要改什么

只改 D-64（仍是 proposed，不接受）和本文件，不写实现，不改规则：

- 选测试：`test_select_command` 放进同一个决定，canon 自己把现有的导入、CLI 命令表、读数据文件读法搬进自己仓库的脚本；BR-2181 改由合入时问这个命令；BR-2119 退役（待负责人确认）。
- `floor` 可以写 `{report}`，读 `testcase` 的 `file`，缺 `file` 大声失败；实测 bun、pytest（xunit1 才有 `file`）、gdUnit4（没有）。
- `test-report-missing` 收窄到本变更改动的、或旧行点名了本变更碰过的规则的测试文件；其余只提示（`test-report-stale`）。
- 证据粒度：用 canon 自己的仓库量化（点名规则数分布、138 个合入、6 次 evidence 拒绝），结论“有 `line` 按 `line`，没有按文件”。
- Godot（gdUnit4）和 pytest 报告实测写进“事实”和“采用门槛”；改 pytest 的说法；更新代码路径到 main 的 0c7acdb。

## 陷阱和假设

- 量化的历史合入只有 138 个有 `base` 和 `sha`；被拒状态靠提交标题推断，是近似。
- pytest 的 `line` 从 0 起，bun 从 1 起，canon 不校正。
- 实测在 /private/tmp 的副本里做，没动 #127 的项目目录。

## 教训

- 决定里“推给后续决策”的依赖，会让中间阶段有无声退化 → 只靠文字：这是评审时才看得出的设计缺口，没有可机械检查的形状。
