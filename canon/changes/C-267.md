## 为什么

C-262 的教训：C-240 弄坏了 BR-2223 扫描源码的测试（`src/work/session/worktree-lock-callers.test.ts`），但 `canon work test` 没选出它，因为它既不导入改过的文件，测试名里也没有改过的规则；main 因此红了大约两个小时。负责人 2026-11-04 的选择是“总是跑扫描源码的测试 (推荐)”。canon 也给非 TS 项目用，所以做成不认语言的配置项：`canon/config.yaml` 新增可选的 `always_tests`（glob 列表），匹配的测试文件 `canon work test` 每次都选出。

## 要改什么

- 新规则 BR-2297：`always_tests` 的含义、理由 `always`、glob 匹配不到测试文件时输出一行并退出码 1（改名后悄悄失效不行），写错时退出码 2。
- BR-2158、BR-2227：退出码的来源加上匹配不到的 glob，事件里记 `unmatched`。
- BR-2157：选出的条件和理由里加上 `always`。BR-2045：配置错误的列表加上 `always_tests`。`work/verify` 的 README 改“相关的测试文件”。
- 代码：`src/work/verify/config-keys.ts` 声明键，`src/work/verify/verify.ts` 选出和报告；测试在 `src/work/verify/verify.test.ts`。
- 按 BR-2248，这个变更只新增键，不在本仓库的 `canon/config.yaml` 里用它；下一个变更再写进去。

## 陷阱和假设

- `always_tests` 只在 `tests` 找到的测试文件里挑，不会把不是测试的文件交给 `test_command`；写了 `tests` 之外的路径算匹配不到。

## 教训

- 不靠导入、也不写规则编号的测试，按改动挑测试时永远选不到 → 现在由 BR-2297（`always_tests`）保证（负责人 2026-11-04 选“总是跑扫描源码的测试 (推荐)”，即同意固化成这个机制），前提是项目把它们列进去；哪些测试该列，只靠文字：canon 判断不了一个测试读了哪些文件。
