## 为什么

#232 的第四块（D-128）。worker 已经能被派发（C-570）、能交回设计请求、设计负责人能接手（C-577），但 worker 的合入还不查它有没有改设计、派发后设计变没变、有没有待答的设计请求、代次是否作废；C-577 只在认领续期时拒绝旧代次，已经排队的合入没有重查。

## 要改什么

按规划中的 BR-2501 实现并激活它（`status` 改成 active、删 `will_amend`），同时按它的“生效时”改 BR-2458：

- `canon work land` 的合入者是 worker 时，在重新基于 main 之后、移动 main 之前查四项：改了设计、派发后设计变了、还有 pending 的设计请求、代次作废；排队时把代次记在队列项上，移动 main 前和重新派发、take 在同一个事务里再查一次。
- 批量合入按每个成员自己的合入者和派发检查。
- worker 合入成功时 `land.ok` 记下派发快照（合入者、代次、设计负责人、设计版本、契约清单），BR-2503 要用。
- 退出码按规则（1）；BR-2022 的清单按需补。
- 合入后评审意见 #153、#155：BR-2500 的自动接手（start、land、stop 遇到失效认领）和显式 `take` 对“worker 进程还在”的处理不一致。改成自动接手也要求 worker 已停：认领记下的进程已不在 → 当作 take；进程还在 → 退出码 5，认领不变，提示停下 worker 后用 `canon work take --stopped`（和别的会话里的进程一样，`--stopped` 也不行）；认领没记进程、canon 判断不了时，租约过期就当作已停（没有别的信号可用）。改 BR-2500 的文字和例子，改 C-577 的自动接手代码，加测试。

## 陷阱和假设

- 设计文档的范围和 `design_paths` 从 main（合入的 base）读，不从候选读。
- C-577 已让旧代次的 `land` 在续期时被拒；本变更补上已排队合入的重查。
