## 为什么

canon 现在只管「做什么」（canon-product）和「做得对不对」（规则、canon-uat），没有地方写「做到什么程度才算好」：zhushenkongjian 的体验类标准一直没被验收（D-145 背景）。C-609 计划的 A 步先给质量标准一个落点：一种内置文档、一份产品的方面清单，以及项目里还没有标准、或有方面没覆盖时的提醒。判定记录、过期、独立判定人是后面 B、C 步的事。

## 要改什么

新建子领域 `knowledge/quality`（代码 `src/knowledge/quality`），决策 D-146 定格式：

- 内置文档类型 `quality`，编号 `Q-n`，文件 `canon/quality/Q-n.md`：front matter `aspect`、`judge`（`test`/`agent`/`owner`）、`covers`（领域或路径），退役时 `retired_reason`；必有 `## 门槛`、`## 来源`；状态 `draft`（默认）、`active`、`retired`（BR-2552）。
- `canon quality new`（BR-2553）、`canon quality list`（BR-2554）、`canon quality status`（BR-2557）。
- `canon/quality/README.md` 的 `## 方面`：`- **<方面>**：…`，负责人的处置写 `不适用：` 或 `推迟：` 加原话或 `#<n>`（BR-2556）；一个方面有哪些 Q-n 由 Q-n 的 `aspect` 算出。
- `canon check`：方面不在清单里、`covers` 不存在报 `ref-dangling`，负责人搁置的方面还有生效标准报 `quality-aspect`（BR-2555），清单格式错误报 `file-invalid`（BR-2556）。
- 提醒：`canon overview` 每次一行质量标准，`canon brief` 的进度摘要只在没有标准或有方面没覆盖时一行（BR-2558；改 BR-2505、BR-2506，BR-2024 的「什么都没有时只输出工作说明」加上「质量标准都有着落」这个条件）。不新增任何拒绝。
- 合入后的规则评审读 `canon/quality` 下的 Q-n（方面清单除外），有 Q-n 改动时提示多一节方面清单，节里写明门槛判不出通过与否用 `untestable`（BR-2559；改 BR-2009、BR-2010）。
- `canon/architecture.md` 写进新类型和新目录。

## 方案依据

- 复用：内置类型的接入点照功能模块 F-n（D-61、D-130，提交 52198b9d）；方面清单的写法照领域 README 的业务清单（BR-2430）；评审接入照 C-590 加 `canon/features` 的做法；提醒放进已有的进度摘要（BR-2506）和总览（BR-2505）。
- 新选择：字段名和放 front matter 还是节（D-146 方案 1）；方面和 Q-n 的对应只写在 Q-n 上（D-146 否决方案 2、3）；方面清单不进规则评审（BR-2559），由 `canon check` 查格式。
- 最坏的失败：每个用 canon 的项目的会话开头都多一行提醒，而没人去写标准，提醒变成噪音；或者 AI 随手把方面标成「不适用」来消掉提醒。对策：处置必须附负责人原话或问题编号（BR-2556），总览里看得到；提醒只占一行。
- 证据：D-145 背景里 zhushenkongjian 按暖雪实测出的关卡空间标准被反复逐条对照，说明「方面 + 来源 + 能判的门槛」这种写法会被用起来。
- 什么结果说明选错了：B 步实现「按 `covers` 算过期」时发现领域名和路径混在一个列表里算不准，或者方面清单和 Q-n 的 `aspect` 经常对不上（`canon check` 的 `ref-dangling` 频繁出现），那就要把对应关系改成清单列编号。
- 数据的演进和恢复：Q-n 和方面清单都是 git 里的文件，可以回滚；内置类型以后只能加字段，`aspect`、`judge`、`covers`、`retired_reason` 定下就不能删或改名；旧项目没有 `canon/quality/` 时一切照旧，只多提醒。

## 陷阱和假设

- `canon/quality/README.md` 和 Q-n 在同一个目录，读文档时要跳过它（`src/knowledge/documents/read.ts`），合入评审的范围也要跳过它（`src/work/land/checks/review-scope.ts` 的 `ASPECT_LIST`），否则 `canon accept` 会要求一次不存在的评审。
- 方面清单的原文放在 `Corpus.qualityReadme` 里，由 `knowledge/quality` 解析：总览从 main 读的文档是解到临时目录再删掉的，不能事后再去读文件。
- `draft` 改 `active` 没有命令，也不查负责人的回答（D-146 后果）；`canon-product` 还没有写怎么调研出方面和 Q-n，提醒里指向它，现在只有它原有的对标办法（D-145 后果）。

## 教训

- 加进每次规则评审提示的说明文字会让所有评审变长，按提示预算定的测试（`src/knowledge/review/context-dedup.test.ts`）随之失败 → 只和某类文档有关的说明放进那类文档改动时才出现的节（BR-2559）；由这些预算测试保证。
- `src/knowledge/documents/types.ts` 顶部注释被 D-77 的来源逐字引用，改注释就让 `canon check` 报 `source-quote-missing` → 由 BR-2252 的检查保证，已发现并改回。
