## 为什么

C-245 合入时的规则评审指出：本地 main 和远端各自前移过时，`git pull` 不走快进，而是先在暂存区和工作区里做出合并结果、造一个新的合并提交，再移动 main。这个合并提交没有别的 ref 包含它，BR-2284 把它当成用户自己的工作，不改回来，远端带来的文件照样留在暂存区，正是 #103 要解决的情形。

复现（改动前）：`src/cli/install/githook.test.ts` 的 BR-2284 合并提交用例：被拒绝后 stderr 没有 `back at main`，`new.txt` 留在暂存区。

## 要改什么

- `src/cli/install/githook.ts`：`GIT_REFLOG_ACTION` 以 `pull` 开头（`git pull` 调起的 merge 继承它）、新提交的第一个父提交是 main 的提交时，也按已有提交处理：切回 main，提示 `canon sync`。
- BR-2284：加上这一种和它的例子；处理评审建议：第一个例子里“留在暂存区”说的是哪个文件写清楚；补 `git merge --no-ff` 不改回的例子。
- 新规则 BR-2286：处理评审建议，把提示 `canon sync` 的那一行从 BR-2284 拆出来单独一条。
- C-245 的教训：处理评审建议，改成只靠文字，写明 BR-2284 是修的 bug 本身，不是固化教训的机制。

## 陷阱和假设

- 只认 `git pull` 造的合并提交：有冲突时 pull 停下，用户解决后用 `git commit` 或 `git merge --continue` 结束，那时 `GIT_REFLOG_ACTION` 不以 `pull` 开头，暂存区里是用户解决冲突的工作，不改回。
- 依赖 `git pull` 把 `GIT_REFLOG_ACTION`（`pull <参数>`）传给它调起的 merge（git 2.50.1 实测，hook 里能读到）。用户自己在环境里设了以 `pull` 开头的 `GIT_REFLOG_ACTION` 再 `git commit` 一个合并，会被改回；这个提交对象还在，只是没有 ref 指向它。
