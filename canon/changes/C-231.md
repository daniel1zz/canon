## 为什么

#93（C-226 合入后的代码评审）：hook 目录在不支持硬链接的文件系统上（比如 `core.hooksPath` 指到 exFAT、某些 FUSE 或网络盘），hook 是 canon 的旧版本时，`replaceOld` 先把旧版本改名挪走，再用 `link` 放新守卫，失败；放回也用 `link`，同样失败，于是旧版本留在旁边，canon 退出后 hook 路径一直空着，之后在 main 上直接提交不再被拦，直到有人手动挪回去。C-222 之前这里用改名，这种文件系统上能正常装。

## 要改什么

- 代码（`src/cli/install/githook.ts` 的 `replaceOld`）：动旧版本之前，先把临时文件硬链接到同目录下的一个试探文件再删掉；建不了就以环境错误停下，旧版本原样留在原处。之后才挪走、核对、放上。
- 规则 BR-2124：写明不支持硬链接时先发现、不动旧版本；“放回也失败、旧版本留在旁边”只剩试建成功后又遇到读写错误这一种情况，例子相应改。
- 测试：`src/cli/install/githook.test.ts` 不支持硬链接、旧版本的用例改成“旧版本留在原处”（去掉修复会失败）；另加“试建成功、之后两次放置都失败”的用例；原来按临时文件判断的模拟改成只在放到 hook 路径上时触发，不被试探文件干扰。

## 陷阱和假设

- 试探只证明“这一刻能建硬链接”，之后遇到读写错误仍可能把旧版本留在旁边，这时提示里写明它的路径；这种情况只能靠人处理，不再假装能自动恢复。
- 不支持硬链接的目录上，canon 装不了守卫（缺少时也装不了，BR-2124 已有例子）：旧版本不会被更新，`canon update --check` 会一直报它过期。这比留下没有守卫的 main 好；要支持这种文件系统得另想办法（D-36 的后果里已写“真遇到时再评估”）。

## 教训

- C-226 修出错分支时只证明了“不覆盖别人的文件”，没有问“出错之后守卫还在不在”：修一个保证时没有把同一段代码要守的另一个保证（BR-2123：main 有守卫）一起过一遍 → 只靠文字：没有能通用判定的检查；合入后的代码评审抓到了。
