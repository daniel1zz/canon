## 为什么

`canon work land --stop` 只向合入进程发 SIGTERM。合入的信号处理只停 floor 的 `sh`、补报告的测试文件和评审，`before_land` 的命令根本没登记；合入退出后，hook 和它的子进程变成孤儿（父进程 1），在变更的 worktree 里继续改文件。zhushenkongjian 的变异证据 hook 就这样在 `--stop` 之后继续套用变异，`git commit -a` 把一个变异体当成真代码提交了（#262）。

复现（`src/work/land/detach.test.ts` 的 #262 一组）：`before_land` 的命令启动一个子进程，它往跟踪的 `app.txt` 追加一行，写下自己的 pid，一直跑；合入停在这一步时运行 `canon work land --stop`。修之前：`--stop` 退出 0 并打印 `stopped the landing`，子进程还活着，`app.txt` 还是改过的样子（`expect(alive(child)).toBe(false)` 得到 `true`）。

同类问题：floor 和一起测的 `setup` 只停了最外层的 `sh`，它们的子进程同样会留下；rebase 之后为补报告跑的测试文件（BR-2381）在自己的进程组里，却没登记，信号到了也没人停。

## 要改什么

- 合入启动的命令（floor、一起测的 `setup`、`before_land` 的每条命令、补报告的测试文件）都在自己的进程组里运行，进程组登记在合入里；命令结束但留下子进程的组也留在登记里。
- 合入收到 SIGTERM 或 SIGINT 时，先停这些进程组再做别的：SIGTERM，最多等 10 秒让它们自己收尾（变异工具可以把文件改回去），还在的发 SIGKILL，再最多等 5 秒；SIGKILL 后还剩进程就输出一行，并记在 `land.killed` 的 `left_running` 里（BR-2099）。
- `--stop` 等合入进程结束后：`left_running` 里的组现在还有进程 → 不说已停止，退出码 4，写明进程组和 `kill -KILL -<进程组>`；worktree 里有和 HEAD 不同的已跟踪文件 → 输出一行列出这些文件，提示提交前先看 `git diff`（BR-2393）。
- 别的 hook 不变：`after_green` 在 watcher 的进程组里，watcher 停下时向整个组发信号，已经能停到；`after_start`、`after_stop` 在调用命令的进程组里同步运行；`after_land` 本来就要在合入之后继续跑。

规则：改 BR-2099（被信号终止时先停下启动的命令和子进程）、BR-2393（`--stop` 何时说已停止、留下的文件怎么说）。

## 陷阱和假设

- 信号处理函数是同步的（它最后调用 `process.exit`，期间不能让合入的主流程接着跑），等待只能用阻塞的 sleep。被停的命令的 `sh` 是合入的直接子进程，阻塞期间事件循环不回收它，它成了僵尸，`kill(-组, 0)` 仍把这个组算作活着，于是每次都要等满 10 秒再 SIGKILL。所以同步的停法用 `ps` 看组里有没有非僵尸的进程（`stopGroupsSync`）；读不到 `ps` 时退回 `kill(-组, 0)`，只会多等、多报，`--stop` 在合入进程结束后用 `kill` 再查一次。
- 离开了自己进程组的进程（`setsid`）和合入被 SIGKILL 杀掉时留下的进程管不到，和 `canon work test` 一样（BR-2304）。
- 进程组号可能在组结束后被别的进程重用；命令结束时就把没有进程的组从登记里去掉，窗口只剩合入还在跑的时间。

## 教训

- 停止命令只核对了被它直接发信号的那个进程，就报告“已停止”；它启动的东西是不是都停了没人核对，新加的步骤（`before_land`、rebase 后补报告的测试）也就没人登记 → 待负责人确认是否固化（例如规则评审遇到“停止、取消、超时”类规则时，问它启动的子进程怎么停、停没停干净）。
- 在同步代码里等自己启动的子进程结束，会被没回收的僵尸进程骗成“还在跑” → 只靠文字（`stopGroupsSync` 的 reason 注释）：这是写法上的细节，没有能机械识别同类写法的检查。
