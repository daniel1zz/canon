## 为什么

合入不会结束派发记录（BR-2500 只有 `take` 结束它），而 `canon work status` 把派发表里的每条记录都列一行。于是派出去的变更做完之后，`status` 还一直显示它“派给了某个 worker”，并且越积越多。实例：C-577 早已合入，`canon work status` 仍显示 `C-577: delegated to codex-462; …`，而且没有命令能结束这条记录（`take` 要求 worker 还持有认领）。C-601 已经让停滞判断（BR-2522）跳过在 main 上已关闭的变更，名额计数（BR-2526）也早就跳过；只剩 `status` 的列表没跳过。

## 要改什么

- `src/work/delegation/stall.ts`：把 C-601 写的“这个变更在 main 上是否已关闭”提成 `closedOnMainReader`，停滞判断和新的 `listedDelegations` 共用；`listedDelegations` 返回 `status` 要列的派发记录，跳过在 main 上已关闭的变更。
- `src/work/session/commands.ts`：`canon work status` 只列 `listedDelegations` 返回的记录。
- BR-2497：写明 `status` 每条派发记录一行，变更在 main 上已关闭的不列，加一个例子。
- 测试：`stall.test.ts` 加一个 BR-2497 测试。

## 方案依据

沿用 C-601 的做法：读的时候排除已关闭的变更，而不是合入时结束派发记录。理由和 C-601 一样：已有的旧记录（C-577）合入时结束不了，读时排除对新旧记录都有效，也不用改数据。新选择只有一处：`status` 也按这个条件过滤。最坏的失败是读 main 的文档失败时 `status` 整个报错退出，而不是悄悄少列；这和 `status` 里停滞判断读 main 失败时的表现一致。如果出现“变更在 main 上已关闭，但它的派发还需要有人处理”的情况，就证明这个选择错了；目前派发只在变更没做完时有意义，想不出这种情况。
