## 为什么

#232 的第三块（D-128）。派发（BR-2497、BR-2498）已在 C-570 实现；worker 碰到没定的设计还没有交回的命令，设计负责人也接不了另一个进程里 worker 的变更（`canon work take` 只认本会话的子 agent）。

## 要改什么

按规划中的 BR-2499、BR-2500 实现并激活它们（只改 `status`、删 `will_amend`，规则文字由设计负责人改）：

- `canon work need-design <C-n> "<原文>"` 记设计请求（状态 `pending`，`design.request` 事件），请求属于变更，随设计负责人转移；`canon work design-answer <n> "<回答>"` 只由现在的设计负责人回答（`design.answer` 事件，detail 为 `{ request, answer, main }`，C-570 的 `accept-design` 已按这个格式读）；设计负责人和持有变更的 worker 的 `canon brief`、`canon work status` 列出请求和回答。
- `canon work take <C-n> --from <名字>`：设计负责人按派发记录接手，不论 worker 在哪个进程；有合入在进行时拒绝；worker 进程还在或 canon 判断不了时要 `--stopped`；接手让代次加 1、派发结束。派发变更上 `start`、`land`、`stop` 的自动接手（BR-2100、BR-2104）也只由设计负责人、按同样条件进行。BR-2336、BR-2100、BR-2104 的 `will_amend` 改动由设计负责人在规则正文阶段写。
- 退出码按规则；BR-2022 的清单由设计负责人补。

## 陷阱和假设

- 认领的进程判断按 BR-2100：Codex 认领记的是共用的 app-server 进程，判断不出单个会话已经结束（#239），`--stopped` 就是为这种情况。
- 规则正文和决策只由设计负责人（派发者）改；实现中发现规则有问题用 `canon work need-design` 交回，这个命令在本变更里实现之前，用 Concord 告诉设计负责人。
