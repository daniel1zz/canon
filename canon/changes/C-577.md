## 为什么

#232 的第三块（D-128）。派发（BR-2497、BR-2498）已在 C-570 实现；worker 碰到没定的设计还没有交回的命令，设计负责人也接不了另一个进程里 worker 的变更（`canon work take` 只认本会话的子 agent）。

## 要改什么

实现并激活 BR-2499、BR-2500，按 BR-2500 的“生效时”改写 BR-2336、BR-2100、BR-2104，并补 BR-2022 的退出码清单：

- 协调数据库加 `design_requests` 表（请求属于变更）和 `delegations.ended` 列（`take` 之后派发结束的时间，重新派发时清空），旧库按 BR-2078 打开时补齐。
- `canon work need-design <C-n> "<原文>"`（`src/work/delegation/requests.ts`）：只有持有派发变更的接受者能提，记 `pending` 请求和 `design.request` 事件，输出 `#n` 和设计负责人；不是持有者、原文为空 → 2，没有派发 → 3。`canon work design-answer <n> "<回答>"`：只有变更现在的设计负责人能答，记回答、当时 main 的提交和 `design.answer` 事件（detail `{ request, answer, main }`）；不存在 → 3，不是设计负责人 → 2，已回答 → 5。
- `canon brief`：设计负责人在任何 worktree 都看到自己负责的 `pending` 请求；在变更 worktree 里列出这个变更的全部请求和回答（设计版本已在派发提示里）。`canon work status` 列出全部 `pending` 请求和各自的设计负责人（`--json` 有 `design_requests`）。
- `canon work take <C-n> --from <名字> [--stopped]`（`src/work/delegation/take.ts`）：有派发记录的变更只由现在的设计负责人接手；合入在排队、在跑或在一个还在跑的批量合入里 → 5；worker 进程还在或判断不了 → 不带 `--stopped` 时 5，进程还在且不是同一个会话 → 带 `--stopped` 也 5；成功时持有者改成设计负责人、租约重算、代次加 1、派发结束，记 `claim.handover`（`by: design-owner`，用了 `--stopped` 且进程不能证明已退出时有 `stopped: asserted`）。没有派发记录的走原来的 BR-2336。
- `start`（`takeClaim`）、`land` 和 `stop`（`renewClaim`）接手失效认领前，派发中的变更只让设计负责人接手、没有合入在进行时当作一次 `take`，别人 → 5，认领不变，记 `claim.refuse`（`delegated`）。
- 派发结束后 worker 的 `start` 被拒（退出码 1，提示重新派发），`stop`、`drop`、续期和 `land` 被拒（退出码 5）：`land` 在进队列之前的续期就被拒，main 不动。BR-2501 第 4 项里排队后才作废的情形没有做，留给 BR-2501。
- `canon/architecture.md` 写明设计请求和 `take` 的新分工。

## 陷阱和假设

- 认领的进程判断按 BR-2100：Codex 认领记的是共用的 app-server 进程，判断不出单个会话已经结束（#239），`--stopped` 就是为这种情况。
- 规则正文和决策只由设计负责人（派发者）改；实现中发现规则有问题用 `canon work need-design` 交回，这个命令在本变更里实现之前，用 Concord 告诉设计负责人。
