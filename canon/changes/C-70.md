## 为什么

C-68 合入后的代码评审发现它加的占位认领（`holdClaim`）有两个缺口：

- issue #15：占位和普通认领长得一样（同一个操作者、同一个 worktree 路径）。同一个操作者（例如同一个人的两个终端，或都是 `agent:unknown` 的 agent）在占位期间 `canon work start`，`takeClaim` 把它当成自己的认领续期放行，删除之后 `unholdClaim` 还会把那个 start 的认领删掉，又回到 issue #12 的症状。
- issue #16：占位不记进程、租约固定 12 小时。clean 或 drop 被中途杀掉（工具超时、Ctrl-C）时，占位留下来，BR-2100 的进程存活检查对它不起作用，别人一整个租约都开不了这个变更。

## 要改什么

- 占位的 worktree 字段写成 `hold:<路径>`，永远不等于真正的 worktree 路径：同一个操作者的 `takeClaim` 也会看到“别人的认领”而被拒（退出码 5）；`unholdClaim` 只删 `hold:` 行，不会删到真正的认领。
- 占位记下执行 clean/drop 的进程（`selfProcess()`），进程不在了就按 BR-2100 立刻失效；租约用项目配置的 `claim_lease_hours`。
- BR-2019、BR-2064 写明这两点并补例子。

## 陷阱和假设

- 占位在 `canon work status` 里会显示成 `hold:<路径>`，这是有意的：一眼能看出那是删除期间的占位。
- 被杀掉时占位替换掉的旧认领行（drop 接手过期或自己的认领时）不会被恢复；那本来就是不再生效或要被删除的认领。
