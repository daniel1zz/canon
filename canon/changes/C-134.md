## 为什么

负责人问“规则集是不是最佳状态”时，主 agent 把设计评估当成缺陷审计，按缺陷清单给出同一设计做多做少的三个方案，没有先定义问题、没有看外部做法、也没有用 `canon-design`（D-27 背景）。`canon-design` 的 description 只写“新建”类情境，正文还引用已经移除的 sequential thinking（N-2）。

## 要改什么

按 D-27 改 `.claude/skills/canon-design/SKILL.md`：

- description 把“判断已有结构、模型或流程是否是对的设计、该怎么改”写成适用情境，中英文触发例子各补几条；写明不用于只找缺陷的审计。
- 第 3 步：先定义问题再列方案；真实方案必须是不同设计；推荐前由看不到推荐的子 agent 反驳一次，小设计可跳过但要说明。
- 去掉 sequential thinking 的引用。

不新增或修改规则：skill 正文是给 agent 的做法说明，不是产品行为；能检查的部分（不引用 canon 编号）已由 BR-2096 管。

## 教训

- 设计评估被当成缺陷审计，补丁方案冒充设计方案 → 只靠文字（D-27、`canon-design` 第 3 步）：问题类型判断由模型做，没有能机器检查的信号；是否有效由 C-34 的统计和 2027-02-03 的复查判断。
- 移除工具后 skill 里还留着对它的引用 → 待负责人确认是否固化（可以做成检查：skill 正文提到的 MCP 或工具名必须在可用清单里，但可用清单因用户而异）。
