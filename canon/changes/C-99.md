status: open

## 为什么

实测（git 2.50.1，APFS）：8 个并发 `git worktree add -b X <base>`，base 是本地 main 时全部成功；base 是 `origin/main` 时 8 个里有 3 个失败，报 `could not lock config file .git/config: File exists`，因为从远程跟踪引用建分支会写 upstream 配置（Claude Code 的 anthropics/claude-code#34645、#47266 报的是同一个问题）。canon 现在从本地 main 建变更 worktree，所以没事，但哪里都没写为什么，以后有人改成 `origin/main` 就会坏。

写测试时还发现第二个并发问题：协调数据库还是新的时候，多个进程同时第一次打开，`PRAGMA journal_mode = WAL` 会立刻报 `database is locked`（SQLite 在这一步不调用 busy handler，busy_timeout 不起作用），10 次 8 并发里有 2 次有进程失败。

## 要改什么

子领域：work/session。

- 新规则 BR-2132：不同变更同时 `canon work start` 都成功；分支从本地 main 建，不写 upstream 配置；协调数据库是新的时候也一样。
- `src/work/session/session.ts` 的 `worktree add -b` 处加 `// reason:` 注释指向 BR-2132。
- `src/work/db.ts`：先设 busy_timeout，再切 WAL；切 WAL 遇到 `database is locked` 时在 busy timeout 内重试，其余错误照常失败。
- 测试：临时仓库带 `origin`（`origin/main` 存在），通过真实 CLI 同时启动 8 个 `canon work start --title`，断言全部退出码 0、8 个 worktree、8 个认领、`.git/config` 里没有 `branch.change/…` 配置。

## 陷阱和假设

- 测试能区分对错：把 base 改成 `origin/${main}` 后测试稳定失败（锁不到 `.git/config`）。
- WAL 重试只处理 `database is locked`；锁超过 5 秒仍然失败退出，不静默降级。
