## 为什么

#135（第二个切片；先合入 C-391 的 `canon events --follow`）：认领的会话进程退出（`canon work status --json` 里 `state: holder-gone`，BR-2192）不是一条事件，而是查询时推导出来的状态，所以 C-391 的跟踪看不到它。#135 的项目里，worker 写完 handoff 退出这种情况能被 `handoff.write` 看到；但 worker 崩溃、或者没写 handoff 就退出时，只有轮询 `canon work status` 才知道它的变更没人在做。

## 要改什么

跟踪中（`canon events --follow`）一个认领从 `live` 变成 `holder-gone` 或 `expired` 时，输出一行，格式和事件行相同，种类例如 `claim.holder-gone`、`claim.expired`，对象是变更编号，详情里有执行者和 worktree；`--kind` 能按这两个种类过滤。同一个认领状态不变时只报一次；判断和 `canon work status` 用同一个函数（BR-2100、BR-2192）。

先决定这一行是真写进事件表，还是只在跟踪输出里出现：

1. 在第一次发现时写一条真实事件（谁发现谁写，用唯一约束保证只写一次）：`canon events` 不加 `--follow` 也看得到，`canon stats` 能统计，但读命令会写数据库。
2. 只在 `--follow` 的输出里合成，不写数据库：保持只读，但历史里查不到。

倾向 1（P6：每件事都有记录），但它让一个原本只读的查询写事件，要写一条决策说明取舍。

规则：新增一条（`work/session` 或 `work/stats`，按决策选），例子覆盖：跟踪中认领的会话进程退出 → 输出一行 `claim.holder-gone`；之后这个认领被 `canon work start` 接手 → 不再报；租约到期 → `claim.expired`；状态没变 → 不重复报。

不在范围内：“活着的认领长时间没有文件改动”（#135 里写的是可选项）。它要在每个 worktree 里扫描文件修改时间，误报多（agent 在读代码、在等长测试），阈值也因项目而异；要做时另开 issue，先拿数据看它是否真有用。
