## 为什么

2026-11-27 zhushenkongjian 从笔记本迁到 Mac Studio 后，它协调数据库里 65 个没结束的派发，设计负责人都是笔记本上的主会话 `agent:9e301322`。这个会话已经不存在，新主会话 `agent:decd0d37` 收不回也重派不了：`canon work take C-1320 --from w1320-tools` 报 "only its current design owner can take it back"，`canon work delegate` 报 "held by agent:eb0704ab:w1320-tools; canon work take it before changing the worker"。BR-2500 只允许现在的设计负责人接手，canon 里没有任何转让设计负责人的路径。

这不只发生在换机器：主会话只要换了身份（会话结束后开新会话、上下文用完重开），它派出去的活就全部收不回，评审意见也只有设计负责人能分档和关闭（BR-2502）。这违反 P3（连续性）。

当天负责人选了先直接改数据库解锁（备份在 zhushenkongjian 的 `.git/canon/state.db.before-owner-handover-2026-11-27`，事件表里有一条 `delegation.owner-handover`，`manual` 为 1），同时做本变更加正式的命令。

## 要改什么

- 新命令（名字设计时定，比如 `canon work adopt <C-n>|--from-owner <agent>`）：主会话（不是 worker，也不是子 agent）把一个或一批派发的设计负责人改成自己。旧设计负责人的会话已经不在时才行：canon 能判断它的进程不在就直接接管；判断不了（比如进程记在另一台机器上），要带上确认（像 `take --stopped` 那样声明，或者带负责人的原话 `--relayed`），设计时二选一并记成决策。旧设计负责人还活着时拒绝，退出码 5。
- 接管改的是设计负责人，不动 worker 的认领和代次；之后新设计负责人照常用 `canon work take` 收回、或重新派发。
- 记一条事件（谁接管、从谁、哪些变更、怎么确认的），`canon work due` 和 `canon brief` 在设计负责人会话不在时提示可以接管。
- 认领里记下的进程号来自另一台机器时（认领的 worktree 路径不在本机），不能当成进程还在：和 C-706 一起处理，否则 `take --stopped` 会因为进程号碰巧被本机别的进程占用而被拒。
- 改 BR-2500（只有现在的设计负责人能接手）和 BR-2502，新增接管规则；领域按 `canon context src/work/delegation` 选。

## 教训

- 设计负责人记的是会话身份，会话身份会随新会话、换机器改变；D-128 定“只有设计负责人能收回”时没考虑身份会失效，结果派出去的活全部收不回 → BR-2646（`canon work adopt`），`canon work take` 被拒时提示它（BR-2500）
- 先直接改协调数据库解锁后，调用方因为参数粘连误以为交接没生效；手工改数据库只应在负责人同意时作为过渡，改完让对方用原样命令验证一次 → 只靠文字：直接改数据库发生在 canon 之外，canon 的命令和检查看不到它；有了 `canon work adopt` 之后这种情形不该再出现
