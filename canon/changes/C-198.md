## 为什么

baseline 核对（N-4）在 `canon work drop` 里发现三件事：一是变更的分支签出在 worktree 目录以外（旧布局，或用 `git worktree move` 挪走了）时，drop 只找 worktree 目录下的路径，会把别处正签出着的分支删掉；二是读分支、列出会丢的东西时 git 失败，drop 以退出码 4 拒绝，却不写 `drop.refuse`（C-155 的教训：拒绝和写事件分在两处，漏写看不出来）；三是找不到（退出码 3）和用法错误（退出码 2）不写事件，规则没有说这是有意的。负责人 2026-11-04 选择推荐方案：“全部按推荐”，其中第 9 项明确同意把“拒绝必须写事件”固化成代码结构和测试。

## 要改什么

- `src/work/drop/drop.ts`：拒绝只能经过 `refuse(reason, detail, error)` 或 `giveUp(reason, detail, error)` 返回，这两个函数自己写 `drop.refuse`，原因的类型是 `DropRefusal`，不给原因就编译不过；读分支或列出会丢的东西时 git 失败的原因是 `git`。
- `locate`：任何一个登记的 worktree 不在 worktree 目录下的 `<C-n>`、却签出了这个变更的分支 → 退出码 2，写明那个 worktree 和 `git worktree move` 命令，什么都不删，不写事件（新规则 BR-2233）。
- BR-2026：列出 drop 的全部拒绝原因和 `human.answer.refuse`（处理 BR-2021、BR-2040 上“BR-2026 没列 `human.answer.refuse`”的评审建议），写明 drop 的用法错误和找不到不写事件。
- 测试：一个测试逐个制造 drop 的每种边界拒绝，断言各写一条带原因的 `drop.refuse`，找不到和用法错误不写；BR-2233 的两侧。

## 陷阱和假设

- 挪走的 worktree 是靠它签出的分支名认出来的；分离 HEAD 的 worktree 没有签出分支，删分支不会弄坏它，所以不拦。
- 认这种情况的检查要列一次 worktree，用 `listWorktreesLocked`，和别的 canon 进程的添加、删除不同时进行（D-33）。

## 教训

- 拒绝的返回和写事件分在两处，新增一种拒绝时很容易只写了返回 → 现在由 drop.ts 的 `refuse` / `giveUp` 保证（原因是必填参数），BR-2026 的“每种边界拒绝都写事件”测试逐个核对；负责人 2026-11-04 同意这样固化（任务第 9 项）。
