来自 C-609 的 B 步（D-148 迁移，计划表不再列这一步）。

## 为什么

质量标准 Q-n（原计划 C-609，D-145）的一步。

## 要改什么

判定记录：`canon quality verdict`（哪条 Q-n、构建提交、判定人、通过与否、证据路径），负责人判定经 `canon human` 记下原话；判定人是写这个变更的会话时标为自评；过期（它管的路径上又合入的变更数超过门槛，agent 判和负责人判分开设）和不通过进待办清单；开工、合入改到它管的路径时列出相关 Q-n 的状态，会话在变更文件里写怎么处理；发布问题里列出没证明或不通过的 Q-n。不新增拒绝

细节：

- 判定是 `quality.verdict` 事件（BR-2586），不写文件；负责人的判定引用 `canon human` 里已回答、点名这条标准、没被用过、确是负责人本人回答的问题（BR-2587，判断“负责人本人”的函数从发布的 BR-2331 抽出共用）。
- 判定状态每次读时由最近一次判定和 `land.ok` 事件、git 现算（BR-2589）：门槛默认 agent/test 判的 30、负责人判的 150，配置键 `quality_stale_agent`、`quality_stale_owner`。状态只在 `src/knowledge/quality/verdicts.ts` 算；议程（`src/work/reminders/due.ts` 的 `qualityItems`）、开工和合入后的提醒（`src/knowledge/quality/related.ts`）、发布行、`canon quality list/status`、`canon overview` 都读它。
- 提醒的位置：议程判断组（BR-2591）、第一次开工和合入后（BR-2592）、`canon release status R-n` 和 `canon release ship`（BR-2593）。不新增任何拒绝。

## 陷阱和假设

- 自评（BR-2588）按“判定人在这条标准管的路径上合入过变更”算，用 `land.ok` 事件的执行者；只看事件，不看提交作者。
- 过期的“之后合入数”数的是 `land.ok` 事件，不是提交数；一次合入带几个提交也只算一次。事件在本机数据库里，别的机器上的合入数不到。
- 没判过的标准不进议程（D-145 只要求过期和不通过进待办），只在开工、合入和发布问题里列出；所以一条一直没人判的标准不会自己冒出来，靠 `canon overview` 的“没判过”计数和方面提醒。这一点留给负责人看实际用起来是否够。
- `covers` 写领域名时，管的路径取领域的代码目录；没有代码目录的领域取它的规则目录。开工时只能按变更列出的规则所在领域判断相关，变更还没列规则时只有管 `.` 的标准会列出。
- 合入后列出相关标准用的是合入最后一个提交改的文件（同 BR-2584 现有做法）。
