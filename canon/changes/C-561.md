## 为什么

#234：C-514 的 34 份文档被两层拆分成 131 次调用、约 52 MB 提示，没有总预算和负责人确认。负责人经 Claude 交接原话“发你同目录下的codex处理”，要求一次评审的调用次数或总 KB 超限时零调用、留负责人问题，同意后再运行；默认值由本会话定。

C-560 已按共同根因修复并逐条关闭 #71–#132。#233 单独记录重复发送领域正文的问题，不在本变更改动提示覆盖范围。

## 要改什么

- BR-2490：预览及合入后一次评审先确定缓存、增量评审和重复评审的实际提示计划，调用数或 UTF-8 总字节严格超过配置时，任何 reviewer 都不运行，建立或复用负责人问题。
- 默认 `review_max_calls: 16`、`review_max_total_prompt_kb: 4096`，只由可信 main 的配置决定；BR-2074、BR-2358、BR-2441 引用统一闸门。等于阈值允许。
- 明确同意只原子消费一次，绑定种类、工作项、评审器提交、命令、阈值和实际提示；同意后原命令重试即可，--again 的新队列号不使同意丢失。失败、被杀也不返还；拒绝或未答持续零调用。
- 复用 questions/events，不加服务、CLI 旗标或表；D-123 记录选择及独立挑战，总览写明新的调用前检查。
- CLI marker 回归验证合计超限零调用、边界、否决/同意/输入变化、并发只消费一次、合入后失败及 --again 重试；验证缓存和增量只计实际调用。
- 范围限预览与合入后的规则及常驻说明评审，不修改发布、reconcile、合入时独立措辞判断的入口。

- 收尾 C-560 的 #137/#139：管理段明确为两行正文；#138：身份归一化与前置 Bash hook 的阶段边界明确，各加强真实 CLI 断言。

- 预览发现的文档澄清：总览区分预览与合入后配置来源；管理段绑定有效入口并列出固定两行正文；BR-2045 明确两项新预算配置属于已知键。

## 陷阱和假设

预算是提示输入量而非货币上限。评审器外部未提交配置不能完整指纹化，不读取密钥来构造指纹。超限时相关文档挑选命令也不先运行。
