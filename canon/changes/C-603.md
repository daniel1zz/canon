A、B、C 互不依赖，可以同时做；每一步开工时先写自己的规则（canon-rules），本变更只定方向。

## 为什么

最后验收（`canon accept`）只成功过一次，main 已经走过它 455 个提交，707 条可疑引用挡着；真正把关的是过程中的强制步骤，它们又慢又会误拒：合入前测试中位数 8.6 分钟，评审一次约 900 KB，措辞判断拒了 137 次。负责人要的是反过来：过程信任模型、默认轻，关键节点才重，最后验收要强，模型靠验收失败的信号自己纠错。数据和方案比较见 D-137。

## 要改什么

- 新决策 D-137（方案 4：自动撤回、按规则验收，加上关键程度）。
- 本变更只落方向和计划，不改代码、不改规则；A 到 F 每一步由各自的变更实现，在那里新写或修改规则，并按 D-137 的后果修改 D-89、D-104、D-32。

## 方案依据

沿用 D-89 的「评审在合入之后」和验收点 `refs/canon/accepted`；新选的是验收的单位（每条规则，而不是整个仓库）、main 坏了的处理（撤回退回，而不是向前修）和流程轻重的依据（canon 算出的关键程度，模型只能调高）。最坏的失败：关键程度把一个有破坏性的改动判成普通，它不跑全量测试就合入，弄坏 main 上别人正在依赖的代码，直到后台测试发现并撤回，期间其他会话基于它开工。证据见 D-137 背景里的实测：11 月 8 日以后真正需要修 main 的只有 3 次，其余是不稳定测试。如果 C、E 落地后，被撤回的合入每天超过 2 次，或者有坏提交在 main 上停留超过一个后台测试批次，就证明这个选择错了，要把合入前的测试加回来。

## 陷阱和假设

- 假设后台测试的批次够快：`floor_max_untested` 10、`floor_quiet_minutes` 20；如果批次变大，坏提交在 main 上停留得更久，撤回的代价也更大。
- C 的撤回是改 main 的历史还是追加一个反向提交，要在 C 里定；追加反向提交不改历史，别的会话的分支只需要 rebase。
- 关键程度一开始不准；E 必须同时记下「被判为普通、后来被撤回」的改动，否则没有办法校准。
- F 之前不要按模型分档：没有数据时分档就是猜。
