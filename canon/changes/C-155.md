## 为什么

baseline 核对发现 `canon work drop` 不是全有或全无，几种拒绝也没有记事件（BR-2026）：

- 先删分支、再删 worktree；worktree 删不掉（例如被锁住）时分支已经没了，worktree 显示没有提交，存档 ref 没有提到，也没有 `drop.refuse`（issue #58）。
- 按读到的最新提交删除分支失败（分支动过）时退出码 4，但没有 `drop.refuse`（issue #59）。
- 列不出进程时退出码 4，没有 `drop.refuse`。

## 要改什么

- worktree 删不掉时，把刚删掉的分支按原来的提交建回来（只建不覆盖），写原因为 `remove` 的 `drop.refuse`，提示写明 `nothing was deleted` 和存档 ref。
- 分支删除失败写原因为 `archive` 的 `drop.refuse`（BR-2103 本来就把它算作存档失败）。
- 列不出进程写原因为 `no-process-list` 的 `drop.refuse`。
- 规则：BR-2064 写明全有或全无、编号不区分大小写、worktree 签出 main 时退出码 2、`no-process-list`；BR-2103 写明分支删除失败的例子。
- 测试：锁住的 worktree、分支删除失败、列不出进程的事件；BR-2064 里还没测的例子（同一个执行者的有效认领、失败时恢复原来的认领、handoff 被删、仍是 open 的提示、clean 和 drop 同时进行、main、小写编号）；BR-2102 的“删除前不动 worktree 的索引和文件”和 `drop.done` 里的丢失内容。

## 陷阱和假设

- 建回分支和删除 worktree 之间不是一个事务：`git worktree remove --force` 在别的原因下中途失败，可能已经删了一部分文件；这些文件都在存档里，所以提示里总是写出存档 ref。
- worktree 不在 worktree 目录里（旧布局，或被 `git worktree move` 挪走）时，drop 只找到分支，删分支后那个 worktree 显示没有提交；这是产品选择，报告给负责人，没有改。

## 教训

- “全有或全无”只写在规则里、删除顺序却没有回滚，核对才发现 → 现在由 BR-2064 锁住 worktree 的测试保证。
- 边界上的拒绝漏记事件在 drop 里出现了三次 → 只靠文字：每个 `return giveUp(...)` 都要配一条 `drop.refuse`，没有检查能看出漏了；待负责人确认是否固化。
