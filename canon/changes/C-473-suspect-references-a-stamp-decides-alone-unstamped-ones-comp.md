## 为什么

C-469（C-464 的 D 步）落地的可疑引用有几处真实缺陷，独立评审复现过：

1. 结果取决于克隆深度：同一个提交，完整克隆 605 条可疑，`git clone --depth 1` 输出 `no suspect references`、退出码 0，验收（G 步）会在没检查的情况下通过。
2. 改引用方等于复核了它点名的一切：BR-2424 在引用方指纹变了时重置基准，给 BR-2424 加一行例子就清掉了它的两条可疑引用，之后 `canon links confirm` 说 `not suspect; nothing written`，按文档的顺序（先改引用方、再复核）永远写不下记录。
3. 有记录也会被 rebase 藏掉：`now !== base && now !== stamp` 让历史基准也能清掉可疑。分支复核 A→B 并改 A，main 同时改 B，rebase 后不可疑；历史顺序是合入顺序，变更里的一切都排在 B 的并发改动之后。
4. 两个会话在同一份文档里复核不同的引用，在 `links:` 块上文字冲突，合入被拒。
5. 作废或取代 B 从不让指向它的引用变可疑。

负责人对 canon human #25 的回答是 A：选一个起点提交，起点之前的引用算复核过，只跟踪之后的变化。

## 要改什么

- 有记录的引用只看记录：被引方现在的指纹不等于 `links` 里的值就可疑，不再和历史基准取“或”；改引用方不算复核（BR-2425）。
- `canon/config.yaml` 新键 `links_since`（完整提交编号）：没记录、起点时引用方已经点名被引方的引用，以被引方在起点提交里的指纹为基准，只读起点那一棵树（一次 `git ls-tree` 加一次 `git cat-file --batch`），不再走历史；起点之后才写的没记录的引用在复核前都可疑。没设、起点不在当前提交的历史里（浅克隆、改写过的历史）时，`canon links` 退出码 4，`canon context`、`canon brief` 写一行原因，从不说“没有可疑引用”（BR-2424、BR-2427、BR-2428、BR-2429）。
- 合入带 `--finish` 时，rebase 之后把这个变更新加的引用的记录写进关闭提交：值是被引方在变更 rebase 前的分支上的指纹（作者读到的版本），所以 main 上同时改过的被引方会显示为可疑；写在 rebase 之后，不会造成 rebase 冲突；只改这个变更自己加了引用的文档；合入没成功时随关闭提交一起撤回（新规则）。
- 作废的规则、被取代的决策的指纹带上状态，作废或取代算一次改动（BR-2423）。
- 缺陷 4 不在这里解决：只限于 `links:` 块的冲突在合入时自动合并需要改 rebase 冲突处理，不是小改动；合入自动写记录之后手工复核少了很多，写进 D-95 的后果作为已知限制。
- D-95 改正：有记录的引用并不能防住 rebase 漏报（旧实现），起点提交、合入写记录、作废计入；仍是 proposed。
- 本仓库的 `links_since` 在 BR-2248 下不能和新键同一次合入：先合入代码，canon 发布后再用第二个变更设成那时 main 的提交。

## 陷阱和假设

- 合入写记录只在 `--finish` 的关闭提交里做；不带 `--finish` 的合入、和别人的合入一起测的批次成员（BR-2172）不写，它们新加的引用保持可疑，直到手工复核。
- 起点提交必须是当前提交的祖先；在一个起点设置之前开出的分支上，配置里还没有这个键，`canon links` 会报错，rebase 到 main 之后就好。

## 教训

- 一个“没有可疑引用”的结果依赖输入是否完整（浅克隆）却不报错 → 现在由 BR-2424（起点不可达时退出码 4）保证。
- 关闭提交在 rebase 之前做，不是之后（简报的前提不对）；合入写记录改为 rebase 之后修改关闭提交 → 只靠文字：这是这次实现的事实，已写进新规则。
