## 为什么

2026-11-03 派发 baseline 核对时暴露了两条教训，负责人确认把它们写进 canon-parallel（只是文字，负责人知道）：

- 我把 18 个核对子 agent 的花费估成约 20 万到 30 万 token，按本会话实测，一个子 agent 通常用 7 万到 28 万 token，实际是好几倍。
- 让并发的核对子 agent 各自直接提 issue：几组代码互相调用，可能发现同一个根因，“先查重再提”会互相撞车；而且主 agent 没核实就提出去了。中途已改为只报告，由主 agent 去重、核实后再提。

## 要改什么

- 归属：skill canon-parallel（`.claude/skills/canon-parallel/`）。
- “派发前”加两步：按实测数据估算花费并告诉用户；并发的只读核对只报告，由主 agent 去重、核实后提 issue。

## 陷阱和假设

- 无。

## 教训

- 并发核对的子 agent 只报告、由主 agent 提 issue → 只靠文字：canon 管不到子 agent 调用 `gh`；负责人确认写进 skill。
- 派发前按实测估算花费 → 只靠文字：token 用量只在 Claude Code 里，canon 读不到；负责人确认写进 skill。
