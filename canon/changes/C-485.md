## 为什么

接着 C-484 做：knowledge/review 是和 install 并列最大的领域，34 条规则平铺，没有东西把同一件事的规则连起来。这个领域里其实混着几摊词汇互不通用的事——规则评审说「拦截/建议」，合入后的代码评审说「根因/issue/refs/canon/code-reviewed」，评审命令的约定说「标准输入/退出码/超时」——读的人要扫完 34 条标题才知道自己要改的是哪一摊。

## 要改什么

给 knowledge/review 声明 7 个业务，把 34 条生效规则全部归属。不改任何一条规则的行为：只加 front matter 的 `business`，`## 规则` 和 `## 例子` 一个字不动，行为哈希不变（BR-2236），不要求重新执行测试。

- 规则评审（9）：BR-2009、BR-2010、BR-2036、BR-2141、BR-2145、BR-2162、BR-2239、BR-2327、BR-2405
- 评审的提示和复用（4）：BR-2359、BR-2361、BR-2375、BR-2396
- 常驻说明的重复评审（5）：BR-2143、BR-2151、BR-2217、BR-2410、BR-2411
- 合入后的代码评审（6）：BR-2070、BR-2071、BR-2314、BR-2315、BR-2316、BR-2356
- 代码评审提的 issue（3）：BR-2072、BR-2210、BR-2211
- 评审命令的约定（6）：BR-2074、BR-2216、BR-2295、BR-2296、BR-2366、BR-2367
- 合入前的预览评审（1）：BR-2358

## 陷阱和假设

- 已有的子领域 `knowledge/review/findings`（未处理的评审意见）不动：它是子领域，不是业务，两者并存，业务的行排在子领域的行之前（BR-2114）。
- BR-2367（结论由 canon 按点名的标准推出）同时管规则评审和重复评审，归在「评审命令的约定」，因为它说的是 canon 和评审命令之间谁说了算，不是某一种评审看什么。
- BR-2151（`instructions` 的格式）归在「常驻说明的重复评审」：它定义的就是常驻说明有哪些文件。
- 「合入前的预览评审」只有 BR-2358 一条。它是一个独立的能力（自己先看一遍、不影响合入），不是别的业务的边界。
