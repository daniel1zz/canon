## 为什么

`canon work drop` 现在只要会丢工作就问人（BR-2065、BR-2066），每次都要等负责人回答。旧 lore 的 KN-783 统计过 42 次同类的问人，几乎都是同意，结论是有可靠的存档就不需要这一步。2026-11-03 负责人在对话里被问到是否改成“存档到 `refs/canon/archive/C-n`、确认能读回后直接删除”，原话是「存档后直接删」。决策写在 D-13。

## 要改什么

- `canon work drop` 会丢东西时，用临时索引把 worktree 当前的全部文件（含未跟踪的和 C-52 引入的不能重新生成的被忽略文件，不含 `node_modules` 这类能重新生成的）存成一个提交，父提交是分支最新提交，放在新建的 `refs/canon/archive/<C-n>/<时间>`；读回校验后才删除；`drop.done` 记下存档 ref，输出列出丢掉的内容和恢复命令（新规则 BR-2102）。
- 存档或校验任何一步失败，什么都不删，写原因为 `archive` 的 `drop.refuse`，退出码 4（新规则 BR-2103）。
- 别的操作者持有有效认领时不再问人，改为退出码 5，和进程占用一样在存档之前检查（BR-2064 写明检查顺序）。
- BR-2065、BR-2066 退役；BR-2068、BR-2022 里关于 drop 问人的说法改掉；BR-2019 补上列不出进程的例子（C-52 评审的建议）；D-6 里关于 drop 的部分标明被 D-13 取代；CLAUDE.md 改掉“drop 会问人”。

## 陷阱和假设

- 实测（git 2.50.1）：`git stash create` 只记录已跟踪文件的改动，未跟踪的文件和被忽略的文件都不在里面，所以不用它，改用 `GIT_INDEX_FILE` 指向临时索引，`read-tree HEAD`、`add -A`、`add -f -- <被忽略的文件>`、`write-tree`、`commit-tree`。worktree 自己的索引不受影响；暂存区和工作区的区别不保留，存的是磁盘上的当前内容。
- `update-ref <ref> <提交> ""` 只新建，已有同名 ref 时失败；测试用一个名为 `refs/canon/archive/C-1` 的 ref 挡住它下面的路径，制造存档失败。
- 存档 ref 不自动清理。嵌套的 git 仓库只存成 gitlink。
- 存档提交的作者是执行 drop 的操作者，邮箱 `canon@localhost`，不依赖 worktree 有没有配置 git 身份。
