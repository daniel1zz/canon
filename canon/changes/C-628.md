## 为什么

D-148 决定去掉杂务这个单独的东西：杂务是只要标题的轻变更，占 C 号，文件在合入时随改动一起写进关闭提交，main 上不多出开工提交，失败或放弃时不留在待办里，`canon update`、`canon release ship` 这类自动入口照样能用。现在杂务没有变更文件、不占 C 号（BR-2457、BR-2458），工作做了却不在任何变更下；BR-2510 还按通道拒绝杂务改目标，和 D-139“只有四类拒绝”不一致。这是 C-626 计划的 B 步。

## 要改什么

- 新决策 D-150：轻变更的工作身份仍是 `chore-<UUID>`，C 号和变更文件在合入做关闭提交时生成、重试沿用同一个号，在途的旧杂务不迁移；否决了开工就分配 C 号（当身份或只输出）和开工时就把文件提交到分支上。
- `work/session` BR-2457：`canon chore start` 多输出一行说明它是轻变更、文件和 C 号合入时写出；旧杂务照常接回。
- `work/land` BR-2458：`canon chore land` 排队前做关闭提交 `canon: close chore-<UUID>`，只新建 `canon/changes/C-n-<slug>.md`（`status: done`、`rules: []`、`chore: <身份>`、正文为空），C 号重试沿用，没合入就随关闭提交撤回；输出 `completed as C-n`；front matter 新键 `chore` 保留（RESERVED_FIELDS），值不是杂务身份时 `file-invalid`。
- `knowledge/check` BR-2091：有 `chore` 的轻变更不要求 `## 为什么`、`## 要改什么`。
- `knowledge/releases` BR-2510：不再按通道拒绝；杂务改了目标照常合入，`goal:` 一行写它的 C 号，再加一行提醒它是轻变更、没有 `## 为什么`；只有成功标准离开待负责人仍拒绝（负责人的验收），杂务没有 `owner_answers`，提示改用变更。
- 关闭提交的连带规则：BR-2355（杂务新增的决策也在关闭提交里接受）、BR-2440（杂务也写引用复核记录）、BR-2501（worker 旧杂务由合入写出的变更文件不算改设计）。
- 自动入口的文字：BR-2086、BR-2196、BR-2334、BR-2278 不再说“不创建 Change 文档”，main 上多的是杂务的关闭提交和它的变更文件。
- 总览「主 checkout 与工作 worktree」「合入流水线」两处、`work/session` README、`canon brief` 的工作说明和 `canon chore` 的帮助文字改成轻变更的说法。

## 陷阱和假设

- 关闭提交按提交标题 `canon: close <工作身份>` 认（撤回、批次、被杀后的恢复、重复拒绝），所以杂务的关闭提交标题仍写杂务身份，C 号写在提交正文里；被杀后的恢复按“关闭提交新增的那个 `canon/` 文件”找杂务的变更文件，不按文件名里的身份。
- C 号重试沿用靠协调数据库里的 `chore.number` 事件；数据库被清掉时重新分配一个号，只多一个空号。
- 轻变更不计算执行证据（`rules: []`、不写 `passes`），和原来的杂务一样；改规则的工作仍该用变更。
- BR-2560（让质量标准变成 active 要负责人回答）对杂务的拒绝没改：理由本来就是杂务的变更文件没有 `owner_answers`，按内容判断结果相同。
