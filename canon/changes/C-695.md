## 要改什么

两个失败，两个根因，不改规则：

1. `designer.test.ts`：测试里的 `agent:s9:w1` 没带启动方标记，按 BR-2610 被当成主会话 `agent:s9` 自己的子 agent，开工时替 `agent:s9` 做了隐式派发，于是负责人再派给 `w3` 撞上 BR-2526 的冲突。代码是对的，测试场景写错了：BR-2633 说的能设计的 worker 是别的会话启动的。改为在这两次 `work start` 时带 `CLAUDE_DELEGATE_CHILD=1`（BR-2468；`CANON_SUBAGENT` 不能和测试用的 `CANON_ACTOR` 同时设）。
2. `detach.test.ts`：C-693 让 floor、`test_command` 和 `canon heavy run` 用显式的 `env: heavyEnv()` 启动，环境从 `process.env` 拷贝；后台落地在 `backgroundRun` 里早已把 `CANON_LAND_RUN` 从 `process.env` 删掉（原来靠 Bun 不传 env 时用进程启动时的环境），所以 floor 读不到它，违反 BR-2307。单独跑这个测试每次都失败，不是负载导致的偶发。改为 `heavy-step.ts` 的 `hideFromSelf` 删掉变量时记下原值，`heavyEnv` 把它补回给子命令。
3. `canon check` 在 main 上还有一条 `path-missing`：BR-2633 写了 `canon/proposals/`，这个目录只在有提案时才有（BR-2525），C-693 应用完提案后它没了。改成和别处一样的占位写法 `canon/proposals/<C-n>/`。

## 教训

- 一条 `// reason:` 注释写着依赖 Bun 不传 env 时的默认行为，C-693 改成显式 env 时没人看到这条注释 → 只靠文字：这类对运行时默认行为的依赖没有可机械检查的形式，新测试（BR-2307 的 envfile 断言）已经在 floor 上抓住了它。
