## 原因

C-555（BR-2486）加的后台删 worktree 和 `canon uninstall` 抢在了一起。复现：单独跑 `sh scripts/test.sh src/install/codex.test.ts -t "BR-2460: the active override"` 4 次，失败 2 次。uninstall 以 5 退出，信息是 `work is still in this clone ... <chore worktree>: in use by pid 27068 (git)`，那个 git 就是后台删除在 worktree 里做检查时跑的。加上 `CANON_CLEAN_AFTER_LAND=0` 后 4 次全过。这不只是测试的问题：uninstall 自己就是用 `land --finish` 合入的，它的本地清理总会撞上自己启动的后台删除。

## 要改什么

- `canon update` 和 `canon uninstall` 从主 checkout 合入，worktree 里没有它们的进程，所以改为在同一个进程里立刻删（`LandOptions.removeWorktree: "now"`），不启动后台删除（BR-2486）。
- 后台删除启动时记一条 `clean.start` 事件，写下进程号；uninstall 遇到还在运行的后台删除时，和遇到 `after_land`、floor 观察进程一样，以退出码 75 等它（BR-2283）。
- `canon work after-land --wait` 不写变更时，取最近一次开始的删除（BR-2486）。

## 陷阱和假设

测试默认关掉后台删除（testkit 里设 `CANON_CLEAN_AFTER_LAND=0`），但 codex.test.ts 没导入 testkit，所以 C-555 的测试没覆盖到这次竞争；C-555 的 `canon work test` 当时报了 "failed alongside other files, passed alone: src/install/codex.test.ts"，那就是它。

## 教训

- `canon work test` 报"一起跑时失败、单独跑通过"时，我把它当成了不稳定的测试放过去了，其实是这次改动引入的竞争 → 待负责人确认是否固化：比如这种情况下，对这个文件在 main 上和变更上各重复跑几次，对比失败率，拿结果决定要不要拒绝合入。
