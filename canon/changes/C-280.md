## 为什么

C-268 为 `git pull --rebase` 停在 rebase 中间加了按后端区分的提示（BR-2298），#114 又要为 apply 后端再加一种。设计评审发现这两种情况都是测试时构造出来的，真实使用中没出现过：本仓库只有一个 clone 往远端推，`sync.*` 事件 0 条。按 D-54，用真实频率和代价衡量，它们不值得在守卫里按后端一种一种加。

负责人 2026-11-04 的确认：“只拒绝 + 放回快进 + 一行提示 (推荐)”。

## 要改什么

- `src/cli/install/githook.ts`：删掉检测 `rebase-merge/` 并提示 `git rebase --abort` 的那段。保留 BR-2284（拒绝已有提交的快进后放回暂存区和工作区）和 BR-2286（一行 `canon sync`）。
- BR-2298 作废（`canon rule retire`）；它的两个测试删掉，其他测试名里的 BR-2298 和 `rebase --abort` 断言去掉。
- BR-2284 里 `git pull --rebase` 的例子保留（守卫不放回，HEAD 分离），改成指向 D-53 的已知限制；它的测试缩成一个不依赖 BR-2298 的用例。
- D-53（proposed）就地收窄：方案 4 改为否决按后端提示，方案 5 记下 `pre-rebase` 这个以后的办法；后果写一行：rebase 停在中间是已知限制，真的发生时用 `pre-rebase` hook 提前拒绝。
- 守卫脚本内容变了，已装的守卫按 BR-2085 显示为过期，`canon update` 换成新的。
- #114 以 not planned 关闭。

## 陷阱和假设

- 删掉之后，main 和远端各自前移过时 `git pull --rebase` 被拒绝，只看到拒绝的话；merge 后端靠 `git rebase --abort` 恢复，apply 后端要 `git rebase --quit` 再 `git checkout main`（C-268、#114 实测）。这是有意接受的已知限制。

## 教训

- 合入后的评审和测试里构造出来的场景，会一种一种长成守卫里的分支，而每一种都没在真实使用中出现过 → 由 D-54 处理（评审和分拣按真实频率判断），这次不另加机制。
