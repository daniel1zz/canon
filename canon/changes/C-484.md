## 为什么

install 是最大的领域，34 条规则平铺在一个目录里，没有任何东西把同一件事的规则连起来。负责人举的例子就在这里：BR-2089 「很明显属于 Update」，但 install 下面没有「更新」这个东西，读的人要扫完 34 条标题才知道更新这件事由哪几条规则划边界。业务层（D-96）落地后，32 个领域里只有 2 个声明了业务，418 条生效规则只有 8 条归了属；棘轮只在规则被改到时才拉一条进来，像 install 这种近期没人动的领域不会自己变好。

## 要改什么

给 install 声明 7 个业务，并把它的 34 条生效规则全部归属。不改任何一条规则的行为：只加 front matter 的 `business`，`## 规则` 和 `## 例子` 一个字不动，所以行为哈希不变（BR-2236），不要求重新执行测试。

- 初始化（2）：BR-2032、BR-2076
- 安装（5）：BR-2080、BR-2081、BR-2082、BR-2083、BR-2195
- 更新（5）：BR-2084、BR-2085、BR-2086、BR-2089、BR-2196
- 项目设置（8）：BR-2087、BR-2130、BR-2185、BR-2264、BR-2274、BR-2305、BR-2343、BR-2404
- main 守卫（5）：BR-2123、BR-2124、BR-2126、BR-2284、BR-2286
- 卸载（7）：BR-2277 到 BR-2283
- 发布（2）：BR-2096、BR-2412

## 陷阱和假设

- 按能力分，不按横跨的策略分。「canon 不动项目自己改过的东西」是一条横跨 init、install、update、uninstall 的策略（BR-2076、BR-2081、BR-2089、BR-2124、BR-2279），本可以单独立一个业务；这里按负责人的说法（BR-2089 属于更新）走能力划分，横跨的关联仍由正文里的互相引用和 D-95 的可疑引用管（D-96 的决定）。
- install 仍然超过 BR-2114 的 25 条提示。业务是标签不是目录，声明业务不会让这个提示消失；要不要真拆成子领域是另一回事。
- 规则评审按 BR-2009 会拿到 install 的全部 34 条，提示大小接近上限时合入会分几次调用。
