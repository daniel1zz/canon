## 为什么

D-148 定了版本和模块算不算完成只看规则状态和成功标准，关联的变更只当工作量，发布不再要求计划完成；D-151 第二部分又定了成功标准只认带编号 `S<k>` 的列表项。现状对不上：

- BR-2504 把 `## 成功标准` 里每个不缩进的列表项都算成标准，zhushenkongjian 的 `R-2` 到 `R-5` 至少 8 条说明文字（“验收方式……”“本版由开发会话自己验收……”）被算成“未证明”，进度看起来比实际差，`canon goal` 也会一直等这些“标准”。
- `canon release status` 和 `canon release ship` 还按计划的步骤算进度、挡发布（D-79），计划要在 E 步去掉，留着它们就是第二份进度。
- 计划那一页“哪些步可以开始、在等谁”的视图，D-148 要改成按版本或模块从变更的 `depends_on` 现算，还没有命令。

## 要改什么

规则（都写 D-151 或 D-148）：

- BR-2504 改：只有以 `S<k>` 加空格开头的不缩进列表项是成功标准，别的列表项是说明，不计数（不兼容）；没写标记的带编号标准仍是未证明。
- 新 BR-2566：`canon check` 一行提示有哪些版本、模块的成功标准一节里还有没编号的列表项（只提示，D-139）。
- 新 BR-2567：`canon release migrate-criteria [R-n|F-n] [--note <id>#<n>,…] [--write]`：给没编号的列表项按顺序编号，`--note` 指定的移出列表放到这一节末尾；不加 `--write` 只列出。
- 新 BR-2568：版本或模块算完成 = 规则全部已通过 + 成功标准全部已满足 + 至少有一条；关联变更、计划步骤都不算。
- BR-2328、BR-2329 改：`canon release status` 去掉计划进度，加成功标准已满足数、关联变更的工作量（四种状态的个数）和完成/未完成；单个版本再逐条列成功标准。
- 新 BR-2569：`canon feature status [F-n]`，和版本同样的内容。
- 新 BR-2570：`canon change graph <R-n|F-n> [--json]`：从 main 和变更分支读变更，按 `depends_on` 排出依赖在前的顺序，每个变更一个状态（已合入、进行中、在等谁、可开始）。
- BR-2333 改：发布只看规则，计划、关联变更、成功标准都不挡（去掉 D-79 那一半）。
- BR-2386 改：发布不再冻结标着版本的计划（计划不再是发布条件，冻结它没有意义）；去掉一项拒绝。
- BR-2512 改：未结束的变更（有没有计划都一样）关联到无处可去的已取消版本或已取消模块，从 `release-dropped` 拒绝改成 `canon check` 的一行提示（D-139）；规则仍然拒绝。BR-2521 跟着改说法。

代码：`src/knowledge/releases/criteria.ts`（只认编号，另给出全部列表项）、`migrate.ts`（新）、`status.ts`（版本和模块共用的进度、完成）、`gate.ts`、`check.ts`（去掉计划的冻结）、`features.ts`（两个提示）、`commands.ts`（`migrate-criteria`、`canon feature status`、工作量）；`src/knowledge/changes/graph.ts`（新）和 `canon change graph`；`src/work/overview/overview.ts` 的版本行带上工作量；版本模板和 canon-product skill 写明编号的写法；总览（`canon/architecture.md`）的发版和变更的关联两段。

## 陷阱和假设

- 依赖图里每个变更的状态只在 `src/knowledge/changes/graph.ts` 的 `graphState` 一处判定（已合入 → 进行中 → 在等 → 可开始，放弃的不画），读的是现有的 `listedChanges` 和变更分支列表。C-631 在做 D-151 第一部分的变更状态模块，接进来时只换这个函数的函数体，把它的主状态映射到这四种；不要在别处再写一份。
- “进行中”现在按“有生效认领、有变更分支或有交接”算，所以一个开过工、分支还在却没人做的变更也算进行中；C-631 的停滞、交接原因接进来后会更准。
- 迁移命令分不出一条没编号的列表项是标准还是说明，所以默认全部编号、只把 `--note` 点名的移出列表；先不加 `--write` 看清单，由会话判断哪些是说明。
- 编号让旧的列表项第一次成为成功标准，合入时会在 `goal:` 里列成“新增”（BR-2510），这是如实的；没编号的待负责人条目原来就不是标准，编号它不算离开待负责人。
- 计划这一步还保留（E 步才去掉）：计划仍可写 `release`，`canon plan status` 不变，只是版本的进度和发布不再看它。
