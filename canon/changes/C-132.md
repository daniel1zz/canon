## 为什么

纯机械重构，行为不变。从事件 #978 起的事件表里，10 次冲突拒绝和大部分重叠提示集中在“每加一个功能就追加一行”的中心登记文件上：`src/cli/main.ts`（所有命令都登记在这里）有 2 次冲突、25 次重叠提示。根因是中心登记：每个新命令都要改同一个文件。负责人选的改法是结构性的：每个领域在自己的目录里登记自己的东西，中心文件只做组装，只在新增领域时才改，这也符合 D-15 的领域目录布局。这是同一批的第一个（后面依次是工作说明、配置项、BR-2067 的检查清单、拆分 land.test.ts）。

## 要改什么

涉及的子领域：cli、cli/install、config、knowledge/documents、knowledge/query、knowledge/check、work/session、work/land、work/verify、work/drop、work/humans、work/stats、work/issues。

- 新文件 `src/cli/command.ts`：从 main.ts 搬来的公共部分（退出码 `EXIT`、`fail`、`must`、`workspace`、`corpusOf`、`list`、`say`、`json`），加上领域登记命令用的类型（`CommandEntry`、`CommandGroup`、`DomainCommands`）和组装函数 `assemble`。每个命令带一个 `rank`，决定它在 `--help` 里的位置，所以帮助的顺序不依赖领域的排列；两个领域定义同名命令、子命令挂在没人声明的组下、组里没有子命令，组装时直接抛错，任何命令都跑不起来，所以任何一个命令行测试都会失败。
- 每个子领域在自己目录的 `commands.ts` 里定义命令，代码原样搬过去：
  - `src/knowledge/documents/commands.ts`：rule、decision、change、note、doc
  - `src/knowledge/query/commands.ts`：search、context、show
  - `src/knowledge/check/commands.ts`：check
  - `src/cli/install/commands.ts`：init、install、update，以及 start 和 brief 共用的更新提示 `noticeUpdates`
  - `src/work/commands.ts`：只声明 `work` 这个组（说明和位置）
  - `src/work/session/commands.ts`：brief、work start / stop / status / clean
  - `src/work/land/commands.ts`：work land；`src/work/verify/commands.ts`：work test；`src/work/drop/commands.ts`：work drop
  - `src/config/commands.ts`：work after-land（BR-2166 在 config 领域）
  - `src/work/humans/commands.ts`：human；`src/work/stats/commands.ts`：stats、events；`src/work/issues/commands.ts`：issues
- `src/cli/main.ts` 只剩领域列表、`assemble` 和原来的参数检查与退出码处理；以后加命令不再改它，只有新增领域时才改。
- `canon/rules/cli/README.md` 写明命令在哪里定义。
- 不改任何规则：没有行为变化。

证明行为没变：改动前后对 46 个命令路径（`canon --help` 和每个命令、子命令的 `--help`，含退出码）各跑一次，输出逐字节相同（`cmp` 无差异）；新增 `src/cli/command.test.ts` 测组装的顺序和三种错误；worktree 里跑了 `canon work test` 和一次全量测试（逐个文件一个进程）。

## 陷阱和假设

- 帮助里的顺序由 `rank` 决定，不是领域在 main.ts 里的顺序；新命令要挑一个不和兄弟命令重复的 rank（重复时按领域列表顺序，不会报错）。
- 编译后的二进制（`bun build --compile`）不能在运行时按目录动态加载模块，所以 main.ts 里的领域列表是静态 import，不能换成扫描目录。
