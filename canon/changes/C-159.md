## 为什么

baseline 核对（N-4）留下几处 BR-2171 和代码对不上或没写明的地方，逐一用探针复现过：

- `src/knowledge/check/paths.ts` 只把三个反引号围起来的部分当代码块，`~~~` 代码块里的已删除路径被报 `path-missing`。
- 去掉规则的 `## 例子`、决策的 `## 背景` 和 `## 方案` 时，按行找 `## ` 标题，不管这一行是不是在代码块里：`## 规则` 里的代码块有一行 `## 例子`，后面真正的正文就被当成例子跳过，漏报；反过来例子里的代码块有一行 `## 规则`，例子就被当成正文，误报。
- 规则写“有候选路径、但目录不是 git 仓库时报一条”，代码只在有现在不存在的候选路径时才读历史；候选路径都存在时不报。代码的做法是对的（存在的路径不需要历史），规则文字要改。
- 仓库还没有任何提交时什么都不报，规则没写。

## 要改什么

- `paths.ts` 按行识别代码块（三个以上反引号或 `~~~`，最多缩进三格，用同一种字符、不短于开头的行关闭，没关闭就到结尾），去掉代码块，找段落标题时跳过代码块里的行。
- BR-2171 写明 `~~~` 代码块、代码块里的 `## ` 行、不是 git 仓库时只在有不存在的候选路径时报一条、没有提交时不报，并补例子。
- 测试补上：`README.md` 写已删除的 `state.ts`、dropped 的变更、两种代码块和代码块里的标题、不是 git 仓库时只报一条和候选都存在时不报、没有提交时不报。

## 陷阱和假设

- 编号检查（`stripCode`）和占位行检查（`hasPlaceholderLine`）同样不认 `~~~`，它们在 knowledge/documents，不归本变更，已提 issue #76。
- `src/knowledge/documents/templates.ts` 的 `section()` 找段落时也不跳过代码块里的 `## ` 行；没找到会让检查结果出错的输入，没有提 issue。

## 教训

- 一个“代码块”的判断在三个地方各写了一份正则，改一处其他两处不会跟着变 → 只靠文字：本领域只改了 `paths.ts`，合并成一个共用函数留给 issue #76 的修复。
