## 为什么

issue #62：只写 `shared: null`、不写 `code_root` 时，canon 读配置接受（null 等于没写，和别的配置项一样），而 `canon config --schema` 生成的 schema 用 `dependencies` 要求“只要有 `shared` 这个键就必须有 `code_root`”，把它判成错。BR-2175 承诺 canon 接受的配置 schema 一定接受，编辑器不会把有效配置标红，这里违反了。反过来 `code_root: null`、`shared: [src/kernel]` canon 拒绝，schema 却接受，而这一点 schema 完全表达得出来。

## 要改什么

- `src/config/reference/reference.ts`：`needs` 生成的 `dependencies` 改成“这个键不是 null 时，需要的键必须存在且不是 null”。`src/config/key.ts` 里 `needs` 的说明跟着改。canon 读配置的行为不变。
- BR-2116 写明 `shared: null`、`code_root: null` 都等于没写，补例子；BR-2175 里 `shared` 需要 `code_root` 的说法改成不是 null 时，补例子。
- 测试：schema 和 canon 对 `shared: null`、`code_root: null` 加 `shared` 列表的判断一致；BR-2116 的两个新例子。

## 陷阱和假设

- 修法有两种：让 canon 也拒绝 `shared: null`，或让 schema 接受。选后者，因为 null 在所有配置项里都表示没写（`hooks: null`、`floor_skip_paths: null`、`code_root: null` 都是），canon 已有的行为不变，只把 schema 补准。
- 现在只有 `shared` 用 `needs`；以后别的键用它，也按“null 等于没写”生成。

## 教训

- schema 片段和 canon 的读取是两份独立写的东西，“null 等于没写”这种跨所有键的约定只在读取那边 → 现在由 BR-2175 测试里的样例表保证，样例要覆盖每个键的 null。
