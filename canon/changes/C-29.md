## 为什么

D-8 按内容审计旧 skill 后定了两件和本变更有关的事：

- 已移植的 `skills/canon-design` 有问题：五个 `references/mode-*.md` 第 5 行都链接到不存在的 `../../shared/docs-lookup-guide.md`；每个模式都要求“一次并行派 4（架构模式是 6）个子 agent”，不管设计大小，每个子 agent 都要从零读上下文，花几万 token；横切关注点表里漏了数据隐私；`module` 模式没有旧 `lore-improve-codebase-architecture` 里真正有用的判断方法（删除测试、两个适配器才算真接缝、依赖分类、加深模块后删掉旧单元测试）。
- 旧 `lore-context-optimizer` 的正文（先测量、逐句追踪、只评被删的部分、换一个评审者）值得移植；它的两份参考资料建议“最大密度、把句子压成箭头”，和正文的“用正常句子”矛盾，不移植。

## 要改什么

只改 skill 文件，不涉及产品行为，不新增或修改规则。

- `skills/canon-design/SKILL.md`：设计一节加两条，一是每个场景至少点名一个必须处理的业务级失败（来自旧 `lore-biz-review`），“没有失败模式”要论证；二是按视角评审默认自己做，并行子 agent 只在影响面大（跨模块、公开 API、数据迁移、安全）时用。横切表加回数据隐私。`module` 模式的说明和质量关卡加上删除测试和接缝要求。
- `skills/canon-design/references/mode-*.md`：坏链接换成一句“先查当前官方文档（context7 或厂商文档）再写库、版本或 API”；“一次派 N 个子 agent”改成默认自己逐个视角评审，子 agent 可选并写明成本和适用条件。
- `skills/canon-design/references/mode-module.md`：新增“Depth and seams”一节（约 20 行）：删除测试、“One adapter = hypothetical seam. Two adapters = real seam.”、接口即测试面、四类依赖表、加深模块后替换而不是叠加测试。不带旧 skill 的追问循环和 CONTEXT.md 耦合。
- 新建 `skills/canon-context-optimizer/SKILL.md`：保留旧正文的全部方法；快照改为 `git show HEAD:<file>` 或笔记（`canon note new`）；适用对象写明本项目的 CLAUDE.md、skill 和 `src/review/` 里的评审提示；去掉两份参考资料。
