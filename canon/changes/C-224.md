## 为什么

#36（C-117、C-129、C-218 合入后的代码评审）：`reopen()` 先用 `git update-ref HEAD parent sha` 移动分支，再用另一条 `git read-tree -m -u sha parent` 更新索引和变更文件。两条命令之间 HEAD 已经是 parent，索引还是关闭提交的树；会话这时 `git commit -am fix`，新提交里变更仍是 `status: done`，reopen 却报告 `reopened`，HEAD 说 done 而变更没合入（违反 BR-2018），工作区还多出一个改回 open 的未提交改动。一起测的成员跟上 main（`landedInBatch`）是同样的两步，间隙里的提交会把这一批带来的文件（领头的 `a.txt`）删掉。

复现（改动前）：`src/work/land/finish/finish.test.ts` 和 `src/work/land/batch/batch-edges.test.ts` 的 BR-2258 用例用 reference-transaction hook 在分支移动后立刻提交：reopen 返回 true 但 HEAD 是间隙里的新提交；成员的间隙提交以 0 退出。

## 要改什么

- 新规则 BR-2258：这两处都在 git 的 `index.lock` 下移动分支、索引和文件；锁被占着时最多等 2 秒，否则不动并说明。
- 决策 D-39：为什么拿 git 自己的索引锁，而不是调换顺序或改用 `git reset --keep`。
- 代码：`src/kernel/git.ts` 新增 `moveBranch`（独占建 `index.lock`，持锁时比较并交换 HEAD，`GIT_INDEX_FILE` 指向副本运行 `read-tree -m -u`，改名成索引，删锁）；`finish.ts` 的 `reopen` 和 `batch.ts` 的 `landedInBatch` 改用它。
- 测试：两处间隙提交各一个用例，加锁被占着时不撤回的用例；`gapCommit` 放进 `src/work/testkit.ts`。

## 陷阱和假设

- 假设所有写索引的 git 命令都先以独占方式建 `index.lock`（git 的锁文件约定）；实测 `git commit -am` 和普通 `git commit` 在锁存在时都以 128 失败。
- `read-tree` 要用 `GIT_INDEX_FILE` 指向副本运行：它自己也要拿索引的锁，真索引的锁已在 canon 手里。
- 别人的 `index.lock` 从不删：一个崩溃的 git 留下的锁会让撤回不做，这和 git 自己拒绝一样。
- C-39（合入后推送）可能同时改 `finish.ts`，合入时注意 rebase。

## 教训

- 两条 git 命令分别改 HEAD 和索引时，比较并交换只保护了第一条；要看的是两条之间别的进程能做什么 → 只靠文字：哪些 git 操作需要成对加锁要看语义，没有通用检查；这次的新规则 BR-2258 只覆盖这两处。
