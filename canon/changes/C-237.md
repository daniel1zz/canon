## 为什么

#99（C-229 合入后的代码评审）：`runHooks` 启动的 `after_green` 子进程没有登记到后台测试的 `running` 里，后台测试收到只发给它自己的 SIGTERM（`kill <pid>`、`pkill -f 'canon floor watch'`）时不会停掉它；后台测试交出位置、不记 `floor.after_green` 就退出，C-229 加的补跑（BR-2270）随后把它当成没跑完，又启动一份，两份同时写 PATH 上的 canon，可能写出半个文件。

复现（改动前）：`src/work/watch/watch.test.ts` 的 BR-2270 SIGTERM 用例：后台测试以 143 退出后，`after_green` 的进程还活着。

## 要改什么

- `src/config/hooks.ts`：`HookContext` 可以带 `running`，`runHooks` 把正在跑的命令登记进去，停止时连同它的子进程一起发 SIGTERM（`killTree`）。
- `src/work/watch/watch.ts`：`after_green`（测完运行和补跑）都带上后台测试的 `running`。
- BR-2270：写明被信号终止时先停掉 `after_green`；处理评审建议：补跑时 `setup` 失败的例子写明不交接。BR-2219：处理评审建议，写明 BR-2270 这个例外。

## 陷阱和假设

- 只停 `after_green` 命令这一棵进程树（用 `pgrep -P` 逐级找子进程）；一个把自己放进新进程组或脱离父进程的命令找不到，这和任何 shell 里的 kill 一样。
- SIGKILL 杀掉后台测试时它来不及做任何事；整个进程组被杀时 `after_green` 也一起死（BR-2270 的第一个例子），只杀后台测试一个进程时 `after_green` 会留下，这种情况仍可能和补跑同时进行。

## 教训

- 加一个“没跑完就补跑”的机制时，要先确认“没跑完”时旧的那份确实已经停了 → 只靠文字：这要看每个被补跑的步骤怎么启动、谁负责停它，没有通用检查。
