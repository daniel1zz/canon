## 为什么

一次独立评审核对了 D-41（C-103）的实现，找到几处真问题，负责人 2026-11-04 选了按评审修订 D-41（选项“D-41 端口 (推荐)”）。逐条对着代码核对过：

- 端口范围用完时，后台 `after_land` 的每条命令都被换成“not run”、退出码记 1（`src/config/hooks.ts` 的 `runHooksInBackground`），前台 hook 也一条都不跑（`prepare`）。`after_land` 和 `before_land` 都会为变更要端口（`src/work/land/finish/finish.ts`、`src/work/land/checks/steps.ts` 调 `changePort`），所以范围满了会让和端口无关的代码评审、一致性抽查都不跑，还会拦下合入。
- 记录的 worktree 一不在，端口就立刻按“最小空闲值”给下一个变更（`src/config/ports.ts` 的 `existsSync(h.worktree)`），而删掉 worktree 不会停掉它的开发服务器；canon 以外的程序占着范围里的端口时也照样分出去。
- 已合入、worktree 已清理的变更跑 `after_land` 时，`changePort` 按约定路径 `<worktrees 目录>/<变更编号>` 新建一条记录，指向一个不存在的路径，下一次分配又删掉它。
- 一起测（D-26）时批的临时 worktree 里跑 `setup` 没有传环境（`src/work/land/batch/batch.ts`），运行 canon 的进程环境里原有的 `CANON_PORT` 会原样传下去。
- D-41 背景说“停下会释放认领”，实际只有 `canon work stop --release` 才释放（`src/work/session/session.ts` 的 `if (release) releaseClaim(...)`）。

## 要改什么

- 新决策修订 D-41（`amends: [D-41]`）：只有知道变更的 worktree 在哪的地方（`canon work start`、`after_start`、`after_stop`）分配端口；`before_land`、`after_land` 只读已有的记录，没有就是空字符串，不再按约定路径建记录。hook 分不到端口时照常运行所有命令，`CANON_PORT` 为空，输出和 `hook.run` 事件写明原因，`before_land` 不因此拒绝。首次分配时探测端口能不能监听，绑不上的跳过；没用过的端口先分，回收的端口按 canon 最后一次把它交给变更的时间，最久的先分。批的 `setup` 显式设 `CANON_PORT` 为空字符串。
- 规则：改 BR-2267（谁分配、谁只读、批的 `setup`、“记下的端口不在范围内”的措辞）；BR-2269 只管 `canon work start` 被拒（补上 `start.refuse` 的原因和没有任何命令时的例子）；新增两条规则：hook 分不到端口时照常运行、首次分配时跳过绑不上的端口并按最久没用的顺序复用。
- 新决策 D-48（`amends: [D-41]`，proposed，等主 agent 派人挑刺后再决定是否采纳）。
- 代码：`src/config/ports.ts`（探测、复用顺序、`ports_used` 表；`changePort` 改成只读）、`src/config/hooks.ts`（分不到端口不再替换命令）、`src/work/land/batch/batch.ts`（一行：`setup` 的环境）。`after_stop` 本来就按变更自己的 worktree（`ws.root`）分配，`src/work/session/session.ts` 不用改；`before_land`、`after_land` 的调用点不变，只是 `changePort` 不再分配。
- 处理 BR-2267、BR-2269、D-41 上还开着的评审建议：BR-2267 改成“记下的端口不在范围内”；BR-2269 补上 `start.refuse` 的原因 `port`、只设 `ports` 没有任何命令时照样被拒的例子，并把 hook 的部分拆到 BR-2287（原来“前台只写一条 `hook.run`”的问题随之没有了：现在每条命令照常写一条）。

## 陷阱和假设

- 探测要绑 127.0.0.1、0.0.0.0、::1、:: 四个地址：在 macOS 上实测，别的进程监听 0.0.0.0 时绑 127.0.0.1 仍然成功，监听 ::1 时绑 0.0.0.0 也成功，只绑一个地址探不出来。某个地址本机没有（`EADDRNOTAVAIL`、`EAFNOSUPPORT`）时跳过那个地址。
- 探测只在首次分配时做：变更自己的服务占着自己的端口是正常的，再探测就会换端口（D-41 否决方案 3 的理由）。
- 假设：需要端口的命令自己检查 `CANON_PORT` 是否为空（例如 `${CANON_PORT:?}`）；没配 `ports` 时它本来就是空的，这次只是把“分不到”也归到这个约定里，并在输出里写明原因。
- `before_land`、`after_land` 只读记录：`ports` 配置之前就开始的变更在这两个事件里没有端口，要端口就再 `canon work start <C-n>` 一次或停下一次。
- 探测用真实端口，别的 worktree 可能同时在跑同一个测试文件，测试里占着端口的那几个会让对方拿到别的值；所以每个测试随机选一段（20000 以上、先确认整段能绑）再按相对位置断言，不用规则例子里的 4100。

## 教训

- `Bun.spawn` 不传 `env` 时，子进程拿到的是 bun 进程启动时的环境，测试里改 `process.env` 传不下去（实测 `process.env.CANON_PORT = "9999"` 之后子进程读到空值）。所以原来 BR-2267 “运行 canon 的环境里原有的 `CANON_PORT` 不会传下去”那个测试一直是空过的，批的 `setup` 的测试一开始也空过；这次都改成用设好环境的 CLI 子进程来跑 → 只靠文字，可以做成检查但还没做：测试里写 `process.env[...] =` 又在同一测试里期望子进程看到它，可以由测试评审或一条 lint 拦下；待负责人确认是否固化。
- 评审时“分配失败就整批不跑”这种一刀切的失败处理，容易把和这个值无关的命令一起拦下 → 只靠文字：哪些命令真的用到某个环境变量，程序看不出来（命令可能是读环境变量的脚本），只能在设计时逐个事件想清楚。
